# Regenerate the frontend Database type from the migrations, before merge

*2026-08-08T15:22:27.878Z*

Typegen used to require a live, already-migrated hosted project — which is impossible before a migration merges, now that CI is the only thing that applies migrations. `npm run gen-types -w database` closes that gap: it applies every committed migration to a throwaway Postgres cluster and describes the result with postgres-meta's TypeScript template (the engine inside the Supabase CLI's typegen container), so it needs no live database, no access token, and no Docker.

One command rebuilds the type the whole frontend is typed against:

```bash
npm run gen-types -w database 2>&1 | grep -E "^(→|✓)"
```

```output
→ applying every migration to a throwaway cluster…
✓ wrote ../frontend/lib/database.types.ts (974 lines)
```

It is also a gate: --check regenerates in memory and compares, so a migration whose types were never regenerated is caught rather than merged. Here it passes on the file just written, then catches a deliberately stale one:

```bash

npm run gen-types -w database -- --check > /tmp/chk1.log 2>&1
echo "up-to-date  -> exit $?"
grep -E "^(✓|✗)" /tmp/chk1.log

cp frontend/lib/database.types.ts /tmp/types.bak
printf "\n// a migration landed but nobody regenerated\n" >> frontend/lib/database.types.ts
npm run gen-types -w database -- --check > /tmp/chk2.log 2>&1
echo "stale       -> exit $?"
grep -E "^(✓|✗)" /tmp/chk2.log
cp /tmp/types.bak frontend/lib/database.types.ts
```

```output
up-to-date  -> exit 0
✓ ../frontend/lib/database.types.ts matches the migrations
stale       -> exit 1
✗ ../frontend/lib/database.types.ts is stale — it first differs from the migrations at line 975. Run `npm run gen-types -w database` and commit the result.
```

Is the local generator faithful? Diffing what it produced against the types that were committed before this change (generated the old way, against the live hosted project) shows the whole ~950-line body regenerated byte-identically — the only delta is Supabase's hosted-only graphql_public schema, which a local cluster has no pg_graphql extension to build, and which app code never touches:

And the frontend still typechecks against the regenerated type — nothing depended on the dropped schema:

```bash
npm run typecheck -w frontend > /tmp/tc.log 2>&1; echo "frontend tsc --noEmit -> exit $?"
```

```output
frontend tsc --noEmit -> exit 0
```

So the workflow for a schema change is now entirely pre-merge: write the migration, run `npm run gen-types -w database`, commit both, and let the migrate CI job apply the SQL when it lands.
