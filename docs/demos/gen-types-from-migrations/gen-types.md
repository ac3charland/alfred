# Regenerate the frontend Database type from the migrations, before merge

*2026-08-08T15:22:27.878Z*

Typegen used to require a live, already-migrated hosted project — which is impossible before a migration merges, now that CI is the only thing that applies migrations. `npm run gen-types -w database` closes that gap: it applies every committed migration to a throwaway Postgres cluster and describes the result with postgres-meta's TypeScript template (the engine inside the Supabase CLI's typegen container), so it needs no live database, no access token, and no Docker.

One command rebuilds the type the whole frontend is typed against:

```bash
npm run gen-types -w database 2>&1 | grep -E "^(→|✓)"
```

```output
→ applying every migration to a throwaway cluster…
✓ wrote ../frontend/lib/database.types.ts (995 lines)
```

It is also a gate: --check regenerates in memory and compares, so a migration whose types were never regenerated is caught rather than merged. Here it passes on the file just written, then catches a deliberately stale one:

```bash

npm run gen-types -w database -- --check > /tmp/chk1.log 2>&1
echo "up-to-date  -> exit $?"
grep -E "^(✓|✗)" /tmp/chk1.log

cp frontend/lib/database.types.ts /tmp/types.bak
printf "\n// a migration landed but nobody regenerated\n" >> frontend/lib/database.types.ts
npm run gen-types -w database -- --check > /tmp/chk2.log 2>&1
echo "stale       -> exit $?"
grep -E "^(✓|✗)" /tmp/chk2.log
cp /tmp/types.bak frontend/lib/database.types.ts
```

```output
up-to-date  -> exit 0
✓ ../frontend/lib/database.types.ts matches the migrations
stale       -> exit 1
✗ ../frontend/lib/database.types.ts is stale — it first differs from the migrations at line 996. Run `npm run gen-types -w database` and commit the result.
```

So the workflow for a schema change is now entirely pre-merge: write the migration, run `npm run gen-types -w database`, commit both, and let the migrate CI job apply the SQL when it lands.

Forgetting to regenerate is now a red push, not a surprise later. The integration suite (check:slow, so pre-push and CI) asserts the committed types match the migrations — but only on a branch that touches database/migrations/, since nothing else can make them stale. Below: the gate skipping on a branch with no migration, then a throwaway migration added to force it red, then green once the types are regenerated.

```bash

run() { npm run check:slow -w database 2>&1 | grep -E "committed database types|↳" ; }

echo "--- no migration on this branch ---"
run

echo "--- migration added, types not regenerated ---"
cat > database/migrations/0028_gate_probe.sql <<SQL
create table public.gate_probe (id uuid primary key);
grant select, insert, update, delete on public.gate_probe to anon, authenticated, service_role;
SQL
cp frontend/lib/database.types.ts /tmp/types.pre-probe
run

echo "--- after npm run gen-types -w database ---"
npm run gen-types -w database > /dev/null 2>&1
run

rm database/migrations/0028_gate_probe.sql
cp /tmp/types.pre-probe frontend/lib/database.types.ts
```

```output

✓ the committed database types match the migrations — skipped — this branch changes no migration, so the committed types cannot be stale
--- migration added, types not regenerated ---
✗ the committed database types match the migrations
```
