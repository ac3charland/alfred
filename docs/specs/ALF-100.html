ALF-100 — Story detail on a phone

On a phone, a story opens as a full-screen sheet above the keyboard, with shorter buttons, a notes editor that grows and a clearer layout.

Working detail

Everything below is for the implementing agent. Approving needs only what’s above.

Context

The ticket (dictated, so “code cards” means the Code board's story detail modal) lists three phone problems: the Notes box shrinks while you type, so long descriptions can't be read; the buttons are wordy and large; and nothing avoids the on-screen keyboard. It also asks for the mobile Storybook screenshots to be checked, and written and captured where they're missing. The human scoped it to phones only (D5) and chose a full-screen sheet (D6). In the first review they also found the layout crowded: the editable notes and the read-only spec look alike, and the headings don't stand out. D7 and D8 answer that.

What exists today

  • frontend/components/code/story-detail-modal.tsx renders FormDialog (atoms/dialog.tsx) as a centred max-w-2xl card with flex max-h-[85vh] flex-col. The header, action row and the Priority + Move this story footer are fixed. Only the Notes/Spec middle (overflow-y-auto) scrolls. At 390×844 that footer takes about 220px, so the scrolling middle gets roughly a quarter of the screen, and nearly nothing once a keyboard is up.
  • EditableNotes (same file) shows the full note while reading, then switches to TextareaField (atoms/textarea-field.tsx), which has a fixed rows=2 and resize-none. That switch is the “box shrinks while typing” bug. When reading, the note is plain text styled exactly like the markdown spec below it, which is why the two are hard to tell apart.
  • Refinement now writes HTML specs. SpecView renders those in a white, sandboxed h-[28rem] iframe, which is cramped inside a phone sheet. FullScreenDialog already exists “for handing a cramped embedded document (a week plan, a rendered spec) the whole screen on a phone”. Flavor C reuses it.
  • Section headings are 12px, uppercase, text-muted-foreground (#8a96a8) on bg-surface (#0f1626). That contrast is about 6:1, which passes WCAG AA. So the problem isn't legibility, it's hierarchy: headings use the same size, weight and colour as the breadcrumb and the checkbox hint. D8 fixes this with size, weight and case, not only colour.
  • The dialog is positioned with fixed top-1/2 -translate-y-1/2. iOS Safari doesn't resize the layout viewport for the keyboard, and dvh ignores the keyboard too, so the card's lower half ends up under the keyboard. Nothing in the app reads window.visualViewport yet.
  • iOS focus-zoom is already solved app-wide: globals.css sets inputs and textareas to 16px under (pointer: coarse) (ALF-115, e2e/mobile-input-zoom.spec.ts). The dialog × is already a 44px target on mobile (ALF-138, e2e/mobile-modal-close.spec.ts).
  • Buttons: PriorityControls draws four labelled outline buttons that wrap to two rows. ManualControls draws the status menu, Block and Abandon. LaunchButton solid uses LAUNCH_LABELS (lib/code/launch.ts), which all end in “in Claude Code”. DropdownMenuCheckboxItem already exists in atoms/dropdown-menu.tsx (flavor C's Needs refinement item).
  • Screenshots: code-storydetailmodal--mobile-ready-for-dev.png is the only mobile baseline. No mobile baseline exists for editing notes, a needs-refinement story, a blocked story, the block-reason editor, or the keyboard-up case. Step 1 of the plan captures those against today's code.

Decision records

D7Which layout direction for the sheet? · open

All three use D1's menus, D2's editor, D3's labels and D8's headings. They differ in how sections are grouped and where actions live.

A: cards. Notes, Spec and Move this story each sit in a bordered bg-background card (rounded-lg p-3) on the bg-surface sheet. Notes gets a visible ✎ Edit affordance. The spec renders inline as today. Only the header row is pinned. It's the smallest change, but the spec is still an inline 28rem iframe and the actions stay at the far end of a long scroll.

B: tabs. The title, breadcrumb, launch/PR row and refinement mark stay above a full-width Notes · Spec · Move tab bar (teal underline on the active tab). Only one panel shows at a time, so the spec tab gets the full remaining height, and the status controls are one tap away in Move. Costs: a new tab state (reset to Notes on each open), a tap to reach the status controls, and the one-scroll document becomes three short views.

C: spec row + bottom bar (★). The body holds only what you read: title, breadcrumb, PR links, Notes (in a tinted editable well with a pencil) and the spec as a document row (file icon, spec title, “Tap to read full-screen”, chevron). Tapping the row opens the spec in the existing FullScreenDialog, stacked over the sheet. View in repo stays beside the Spec heading. Every action moves into a pinned bottom bar: the primary launch (flex-1), the status menu, an icon-only Priority menu (aria-label="Priority"), and ⋯. To fit 390px, the refinement mark becomes a DropdownMenuCheckboxItem in ⋯, and the secondary launch (Skip to dev) moves into ⋯ as well. Costs: two controls that were one tap away are now two taps, and the sheet has two pinned regions (header and bar) instead of one.

Why C: it puts the actions you use on a phone within thumb reach. It separates “edit” (the well) from “read” (the document row) by shape, not just by heading. And the full-screen spec reader is exactly what FullScreenDialog was built for, so the white 28rem iframe no longer squeezes into the sheet. D2's editor footer lives where C's bar is, so while you edit, the bar swaps to Save/Cancel.

D2How the notes editor behaves · proposed (revised in review 1)

On a phone the notes TextareaField auto-grows to its content, with a four-row floor so an empty note still has room. There's no max height and no inner scrollbar: the sheet's body is the one scroller. Its Save/Cancel row moves out of the scroll content into the sheet's footer, a shrink-0 bar between the scrolling body and the bottom of the visible viewport (the keyboard's top edge, per D6). The body's scroll region therefore ends at the bar's top edge, and scrolling to the end always shows the editor's last line and bottom border above the bar (Plate II). The block-reason editor uses the same footer.

Considered: a position: sticky action row inside the scroll content. That was the first draft, and the review rejected it because it floated over the editor and covered its last lines until you scrolled all the way down. Also considered: capping the editor at the visible height with an inner scroll (two nested scrollers on a touch screen), and moving Save/Cancel into the pinned header iOS-style (a different save location from every other editor in the app).

D8How section headings read · proposed

In the sheet, section headings (Notes, Spec/Findings, Move this story) become text-sm font-semibold text-foreground, in sentence case, with no tracking, and the title steps up to text-xl. That gives three clear levels (title, section, body) where today there are two. The breadcrumb and hints stay muted text-xs, so headings now outrank them. The desktop modal keeps its eyebrow headings (D5). Implement this as a class the heading takes from a layout-aware helper, not as edits to SpecView's markup, which the epic spec modal shares.

D1How compact the controls get · settled

Menus. A Priority ▾ outline button opens the four labelled jumps as menu items, with the icons, disabled states and titles they have today. A ⋯ button (aria-label="More story actions") holds the rarer actions: Unblock to <lane> (blocked only, first), Block… (when not blocked; it opens the same reason editor today's Block button opens), and Abandon (when not abandoned, destructive item variant). The full ⋯ contents per flavor and state are in Behaviour. Button height stays at the sm 32px. Considered: four icon-only priority buttons in one row, rejected by the human.

D3Launch button wording on phones · settled

LAUNCH_LABELS gains a short per phase: refinement “Refine”, implementation “Implement”, bypass “Skip to dev”, spike “Run spike”, bug “Fix bug”. The busy labels are unchanged. Only the sheet uses the short form. Board card chips and the desktop modal keep idle.

D4What stays pinned while scrolling · now part of D7

In every flavor the header is one pinned h-11 row: ref, state chip, kind badge, and the 44px ×. The title scrolls with the body. Flavors A and B pin nothing else. C also pins its bottom action bar. While an editor is open, every flavor pins the D2 footer.

D5Which screens change · settled

Phones only, meaning viewports under Tailwind's md (48rem = 768px). Every desktop modal baseline must pass untouched. Consequence: the desktop notes editor still opens at two rows. That's the same bug in a smaller form, and it's listed under Not doing so it can be picked up separately.

D6The phone shell · settled

A full-bleed, radius-free sheet whose top and height track window.visualViewport, so it always fills exactly the visible screen above the keyboard. See D10 and D11 for the mechanics.

Implementation decisions

D9 · Detect “phone” in JS, with a query that is false under jsdom

Add export const MOBILE_QUERY = '(width < 48rem)' beside useMediaQuery in lib/hooks/use-media-query.ts, matching Tailwind v4's max-md. The modal reads useMediaQuery(MOBILE_QUERY). The query must be the mobile one, not !useMediaQuery(DESKTOP_QUERY): jest.setup.ts stubs every matchMedia to false, so a mobile-positive query keeps the 1,200-line story-detail-modal.test.tsx on the desktop layout it asserts today. Mobile RTL tests override globalThis.matchMedia for that one query. The switch is JS rather than CSS max-md:/md:hidden because the two layouts have different DOM (menus vs buttons). CSS-hidden duplicates would double every getByRole in jsdom, which loads no Tailwind. The modal opens only on the client, so useSyncExternalStore's server snapshot never flashes the wrong layout.

D10 · useVisualViewport() hook, not viewport meta or dvh

New lib/hooks/use-visual-viewport.ts: useSyncExternalStore subscribing to visualViewport resize + scroll. It returns { height, offsetTop } | null (null when the API is absent or on the server). The snapshot must be referentially stable between identical readings, so cache the last object and return it unless a value changed. interactive-widget=resizes-content was rejected because iOS Safari ignores it and it would relayout every page on Android. 100dvh was rejected because it doesn't shrink for the keyboard on iOS.

D11 · A new SheetDialog atom with a footer slot; FullScreenDialog untouched

Add SheetDialog to atoms/dialog.tsx: the same Root → Portal → DialogOverlay → Content scaffold and fade classes as FormDialog. Content is fixed inset-x-0 z-50 flex w-screen flex-col bg-surface, with style={{ top: vv.offsetTop, height: vv.height }} from D10, falling back to top-0 h-[100dvh] when the hook returns null. Its children are the header and the min-h-0 flex-1 overflow-y-auto body. After them it renders an always-present, shrink-0 footer element. It publishes that element through a SheetFooterContext, using a callback ref held in state so consumers re-render once it mounts. It also publishes a claim() function that returns a release callback; the footer's resting content (flavor C's bar) hides while any claim is held. FullScreenDialog keeps its 100dvh body and serif header; moving it onto SheetDialog is a follow-up (see Out).

D12 · Keep the focused field visible after a keyboard resize

When D10's reading changes and document.activeElement is an input or textarea inside the sheet, SheetDialog calls activeElement.scrollIntoView({ block: 'nearest' }) in the next animation frame. Feature-detect it, since jsdom lacks it (precedent: lib/hooks/use-focus-item-highlight.ts). The browser's own caret-following handles typing after that. Because the footer is outside the scroll region (D2), the caret can never be followed into a spot the bar covers.

D13 · TextareaField gains opt-in autoGrow and actionsTarget

Both are off by default, so every existing caller (epic notes, InlineNoteField, the desktop modal) renders byte-identically. autoGrow: a useLayoutEffect keyed on value sets height = 'auto', then height = scrollHeight + 'px', with overflow-hidden; rows is the floor. actionsTarget?: Element | null: when set, the action row renders through createPortal into that element (the D11 footer) as a full-width bar (flex gap-2 border-t border-border bg-surface px-4 py-2). The warning variant keeps its right-aligned amber confirm. The editor takes a D11 claim() while mounted. Not CSS field-sizing: content, because WebKit support can't be relied on for this user's iPhone.

D14 · One jump list behind two presentations

Extract usePriorityJumps(story) from story-detail/priority-controls.tsx, returning today's Jump[]. The desktop PriorityControls keeps its markup. The new PriorityMenu (labelled trigger, or icon-only in flavor C) consumes the same list, so labels, icons, disabled flags and the useMoveBurst commits can't drift between layouts.

D15 · Layout is a prop, not a second component tree

DetailBody takes layout: 'dialog' | 'sheet' and passes it to EditableNotes (D2), PrimaryAction → LaunchButton (compact for D3), ManualControls (D1), and the heading helper (D8). StoryDetailModal picks FormDialog or SheetDialog from D9. The file is already 320 lines, so move EditableNotes to story-detail/editable-notes.tsx as part of this, plus a new story-detail/more-actions-menu.tsx for ⋯.

Acceptance criteria

  • Phone baselines for editing notes, needs-refinement, blocked, block-reason and keyboard-up exist and were first captured against the pre-change code.
  • At 390×844 the story opens as a sheet filling the viewport (box 0,0,390,844), with no radius or border.
  • When the visible viewport shrinks (keyboard stand-in), the sheet's height follows it, and the focused editor stays in view.
  • Scrolling the sheet body to the end leaves the header row and the × in view. In C, the action bar also stays in view.
  • In the phone notes editor a long note shows in full with no inner scroll (scrollHeight === clientHeight), and an empty note opens at four rows.
  • While editing, Save/Cancel sit in the sheet footer, outside the scroll region. Scrolled to the end, the editor's bottom edge is above the footer's top edge, with no overlap at any scroll position. The block-reason editor behaves the same.
  • Sheet section headings render at 14px, semibold, in text-foreground and sentence case. Desktop headings are unchanged.
  • Phone launch buttons read Implement / Refine + Skip to dev / Run spike / Fix bug. Card chips and the desktop modal keep the full labels.
  • Priority ▾ lists the four jumps with today's disabled states. The ⋯ contents match the Behaviour table for each state. Each item calls the same store action as today's button.
  • The sheet matches the D7 pick as drawn in Plate I.
  • Every existing desktop code-storydetailmodal--* baseline and story-detail-modal.test.tsx assertion passes unchanged.

Out of scope, risks & unknowns

  • Desktop notes still open at two rows. Excluded by D5. The fix is one prop (autoGrow) once D13 lands, so it makes a good follow-up ticket.
  • Other dialogs and FullScreenDialog keep 100dvh. The mobile search's input has the same keyboard exposure, and moving it onto SheetDialog is the natural follow-up.
  • Risk: iOS pans the visual viewport when a fixed element's field is focused. The sheet re-positions to offsetTop on every scroll event, which can jitter for a frame. If it looks bad on device, throttle to requestAnimationFrame. Only a real iPhone shows this.
  • Risk (C): the bar's width. The longest status label (“Needs Refinement”) plus Implement, the icon Priority trigger and ⋯ come to about 360px against the 358px usable at 390. The launch button is flex-1 with min-w-0 truncate, so it gives up space first. Check at 375px (iPhone mini/SE) too.
  • Unknown: whether Radix's onOpenAutoFocus ring on the title (visible in today's mobile baseline) shows on a real touch open. If it does, focusing the sheet content instead is a one-line follow-up, not part of this spec.
