ALF-100 — Story detail on a phone

On a phone, a story opens as a full-screen sheet that stays above the keyboard. The notes editor grows with what you type, and the buttons get shorter and fewer.

Decisions

  1. D1How compact should the bottom controls get?

    A · four icon-only priority buttons in one row · B · one Priority menu, with Block/Abandon under ⋯ ★

    B keeps every label readable and folds two sections into one row.

  2. D2How the notes editor behaves

    It grows to fit the text, and Save/Cancel stick just above the keyboard.

    You see the whole note, and Save is never hidden under the keyboard.

  3. D3Launch button wording on phones

    Implement · Refine · Skip to dev · Run spike · Fix bug

    Every launch opens Claude Code, and that suffix is what makes them wrap.

  4. D4What stays pinned while scrolling

    Only the ref · state · × row. Everything else scrolls as one.

    Close is always one tap away, and the content gets the rest of the screen.

  5. D5Which screens change

    Phones only (narrower than 768px). The desktop modal stays pixel-identical.

  6. D6The phone shell

    A full-screen sheet sized to the part of the screen above the keyboard.

Working detail

Everything below is for the implementing agent. Approving needs only what’s above.

Context

The ticket (dictated, so “code cards” means the Code board's story detail modal) lists three phone problems: the Notes box shrinks while you type, so long descriptions can't be read; the buttons are wordy and large; and nothing avoids the on-screen keyboard. It also asks for the mobile Storybook screenshots to be checked, and written and captured where they're missing. The human scoped it to phones only (D5) and chose a full-screen sheet (D6) when asked.

What exists today

  • frontend/components/code/story-detail-modal.tsx renders FormDialog (atoms/dialog.tsx) as a centred max-w-2xl card with flex max-h-[85vh] flex-col. The header, action row and the Priority + Move this story footer are fixed. Only the Notes/Spec middle (overflow-y-auto) scrolls. At 390×844 that footer takes about 220px, so the scrolling middle gets roughly a quarter of the screen, and nearly nothing once a keyboard is up.
  • EditableNotes (same file) shows the full note while reading, then switches to TextareaField (atoms/textarea-field.tsx), which has a fixed rows=2 and resize-none. That switch is the “box shrinks while typing” bug.
  • The dialog is positioned with fixed top-1/2 -translate-y-1/2. iOS Safari doesn't resize the layout viewport for the keyboard, and dvh ignores the keyboard too, so the card's lower half ends up under the keyboard. Nothing in the app reads window.visualViewport yet.
  • iOS focus-zoom is already solved app-wide: globals.css sets inputs and textareas to 16px under (pointer: coarse) (ALF-115, e2e/mobile-input-zoom.spec.ts). The dialog × is already a 44px target on mobile (ALF-138, e2e/mobile-modal-close.spec.ts).
  • Buttons: PriorityControls draws four labelled outline buttons that wrap to two rows. ManualControls draws the status menu, Block and Abandon. LaunchButton solid uses LAUNCH_LABELS (lib/code/launch.ts), which all end in “in Claude Code”.
  • Screenshots: code-storydetailmodal--mobile-ready-for-dev.png is the only mobile baseline. No mobile baseline exists for editing notes, a needs-refinement story, a blocked story, the block-reason editor, or the keyboard-up case. Step 1 of the plan captures those against today's code.
  • Precedent: FullScreenDialog (atoms/dialog.tsx, used by the mobile search and the week-plan viewer) is full-bleed at h-[100dvh] with a serif-title header. useMediaQuery (lib/hooks/use-media-query.ts) is the house media-query hook.

Decision records

D1How compact should the bottom controls get? · open

A: icon-only priority row. The four jumps become 32×32 outline icon buttons in one row, grouped under small “Project” and “Backlog” captions. Each keeps today's title and gets its label as aria-label. Move this story is unchanged (it already fits one row at 390px). Cost: the icons alone don't separate “this project” from “whole backlog” as well as words do, and it still takes two sections.

B: menus (★). Priority and Move this story merge into one row under the Move this story heading: the status menu (unchanged), a Priority ▾ outline button that opens the four labelled jumps as menu items (icons, disabled states and titles as today), and a ⋯ button (aria-label="More story actions") holding the rarer actions. Block/Abandon become menu items. The ⋯ menu lists, in order: Unblock to <lane> (blocked only), Block… (not blocked), Abandon (not abandoned, destructive item variant). Block… opens the same inline reason editor under the row that the Block button opens today. Cost: Unblock and Abandon each take one more tap. Unblock can also go through the status menu, which moves a blocked story to any lane.

Button height stays at the sm 32px in both. The ticket's “large” is width and wrapping, not height: today's controls fill three rows.

D2How the notes editor behaves · proposed

On a phone the notes TextareaField auto-grows to its content, with a four-row floor so an empty note still has room. There's no max height and no inner scrollbar: the sheet's body is the one scroller. Its Save/Cancel row is position: sticky; bottom: 0 inside the sheet body. It sits right under a short editor (Plate II, short) and pins to the sheet's bottom edge, which is the keyboard's top edge per D6, once the editor runs past it (long). The block-reason editor gets the same two behaviours, so every text editor in the sheet acts the same.

Considered: capping the editor at the visible height with an inner scroll, which gives two nested scrollers on a touch screen. Also considered: Save/Cancel moving into the pinned header iOS-style, which means two different save locations across the app's editors.

D3Launch button wording on phones · proposed

LAUNCH_LABELS gains a short per phase: refinement “Refine”, implementation “Implement”, bypass “Skip to dev”, spike “Run spike”, bug “Fix bug”. The busy labels are unchanged. Only the sheet uses the short form. Board card chips and the desktop modal keep idle. Considered: an icon-only launch button, rejected because it's the primary action and should say what it does.

D4What stays pinned while scrolling · proposed

The sheet header is one h-11 row: ref, state chip, kind badge, and the 44px ×. It stays fixed (shrink-0), and everything else, including the title, breadcrumb and controls, sits in one overflow-y-auto body. On a phone the pinned footer is dropped: it was the main thing eating the visible height. Considered: pinning the title too, which costs about 50px of permanent chrome; the ref already names the story.

D5Which screens change · settled

Phones only, meaning viewports under Tailwind's md (48rem = 768px). Every desktop modal baseline must pass untouched. Consequence: the desktop notes editor still opens at two rows. That's the same bug in a smaller form, and it's listed under Not doing so it can be picked up separately.

D6The phone shell · settled

A full-bleed, radius-free sheet whose top and height track window.visualViewport, so it always fills exactly the visible screen above the keyboard. See D8 and D9 for the mechanics.

Implementation decisions

D7 · Detect “phone” in JS, with a query that is false under jsdom

Add export const MOBILE_QUERY = '(width < 48rem)' beside useMediaQuery in lib/hooks/use-media-query.ts, matching Tailwind v4's max-md. The modal reads useMediaQuery(MOBILE_QUERY). The query must be the mobile one, not !useMediaQuery(DESKTOP_QUERY): jest.setup.ts stubs every matchMedia to false, so a mobile-positive query keeps the 1,200-line story-detail-modal.test.tsx on the desktop layout it asserts today. Mobile RTL tests override globalThis.matchMedia for that one query. The switch is JS rather than CSS max-md:/md:hidden because the two layouts have different DOM (menus vs buttons). CSS-hidden duplicates would double every getByRole in jsdom, which loads no Tailwind. The modal opens only on the client, so useSyncExternalStore's server snapshot never flashes the wrong layout.

D8 · useVisualViewport() hook, not viewport meta or dvh

New lib/hooks/use-visual-viewport.ts: useSyncExternalStore subscribing to visualViewport resize + scroll. It returns { height, offsetTop } | null (null when the API is absent or on the server). The snapshot must be referentially stable between identical readings, so cache the last object and return it unless a value changed. interactive-widget=resizes-content was rejected because iOS Safari ignores it and it would relayout every page on Android. 100dvh was rejected because it doesn't shrink for the keyboard on iOS.

D9 · A new SheetDialog atom; FullScreenDialog untouched

Add SheetDialog to atoms/dialog.tsx: the same Root → Portal → DialogOverlay → Content scaffold and fade classes as FormDialog. Content is fixed inset-x-0 z-50 flex w-screen flex-col bg-surface, with style={{ top: vv.offsetTop, height: vv.height }} from D8, falling back to top-0 h-[100dvh] when the hook returns null. It has no header of its own (the modal supplies D4's row). FullScreenDialog keeps its 100dvh body and serif header. Moving it and the mobile search onto SheetDialog is a follow-up (see Out).

D10 · Keep the focused field visible after a keyboard resize

When D8's reading changes and document.activeElement is an input or textarea inside the sheet, SheetDialog calls activeElement.scrollIntoView({ block: 'nearest' }) in the next animation frame. Feature-detect it, since jsdom lacks it (precedent: lib/hooks/use-focus-item-highlight.ts). The browser's own caret-following handles typing after that.

D11 · TextareaField gains opt-in autoGrow and stickyActions

Both default to false, so every existing caller (epic notes, InlineNoteField, the desktop modal) renders byte-identically. autoGrow: a useLayoutEffect keyed on value sets height = 'auto', then height = scrollHeight + 'px', with overflow-hidden; rows is the floor. stickyActions: the action row gets sticky bottom-0 z-10 bg-surface border-t border-border/60 py-2 (both variants), bled to the sheet's edges with negative margins so the bar spans the width as drawn. Not CSS field-sizing: content, because WebKit support can't be relied on for this user's iPhone.

D12 · One jump list, two presentations

Extract usePriorityJumps(story) from story-detail/priority-controls.tsx, returning today's Jump[]. The desktop PriorityControls keeps its markup. The D1 winner (A's icon row, or B's PriorityMenu) consumes the same list, so labels, icons, disabled flags and the useMoveBurst commits can't drift between layouts.

D13 · Layout is a prop, not a second component tree

DetailBody takes layout: 'dialog' | 'sheet' and passes it down to EditableNotes (D2 props), PrimaryAction → LaunchButton (compact for D3), and ManualControls/PriorityControls (D1). StoryDetailModal picks FormDialog or SheetDialog from D7. The file is already 320 lines, so move EditableNotes to story-detail/editable-notes.tsx as part of this.

Acceptance criteria

  • Phone baselines for editing notes, needs-refinement, blocked, block-reason and keyboard-up exist and were first captured against the pre-change code.
  • At 390×844 the story opens as a sheet filling the viewport (box 0,0,390,844), with no radius or border.
  • When the visible viewport shrinks (keyboard stand-in), the sheet's height follows it, and the focused editor stays in view.
  • Scrolling the sheet body to the end leaves the header row and the × in view.
  • In the phone notes editor a long note shows in full with no inner scroll (scrollHeight === clientHeight), and an empty note opens at four rows.
  • With the editor taller than the visible sheet, Save and Cancel sit inside the visible viewport. The block-reason editor behaves the same.
  • Phone launch buttons read Implement / Refine + Skip to dev / Run spike / Fix bug. Card chips and the desktop modal keep the full labels.
  • The bottom controls match the D1 pick as drawn, and each of the four jumps plus Block, Unblock and Abandon still calls the same store action as today.
  • Every existing desktop code-storydetailmodal--* baseline and story-detail-modal.test.tsx assertion passes unchanged.

Out of scope, risks & unknowns

  • Desktop notes still open at two rows. Excluded by D5. The fix is one prop (autoGrow) once D11 lands, so it makes a good follow-up ticket.
  • Other dialogs and FullScreenDialog keep 100dvh. The mobile search's input has the same keyboard exposure, and moving it onto SheetDialog is the natural follow-up.
  • Risk: iOS pans the visual viewport when a fixed element's field is focused. The sheet re-positions to offsetTop on every scroll event, which can jitter for a frame. If it looks bad on device, throttle to requestAnimationFrame. Only a real iPhone shows this.
  • Unknown: whether Radix's onOpenAutoFocus ring on the title (visible in today's mobile baseline) shows on a real touch open. If it does, focusing the sheet content instead is a one-line follow-up, not part of this spec.
