ALF-113 — Add ability to attach images to code tickets and pass to Claude Code

Refinement Code module DB · Storage · API · UI · Prompts Spec only — no implementation. Build in a later session.

1 · Context & problem

Half of what a code ticket is really about is visual: a screenshot of the broken layout, a mockup of the target design, a stack trace captured from a phone. Today alfred has nowhere to put any of it. A story carries a title and free-text notes (items.notes) and nothing else, so the owner ends up describing a picture in prose — and the launched Claude Code session gets that prose instead of the picture.

The launch path is the constraint that shapes this whole ticket. A story is handed to Claude Code by a human click on a prefilled deep link built in frontend/lib/code/links.ts: 

https://claude.ai/code?repo=<owner>/<name>&q=<urlencoded prompt>

That URL carries text only — there is no attachment parameter, no multipart body, no way to hand the surface a binary. So "pass to Claude Code" cannot mean "upload the image with the prompt." It has to mean: host the image somewhere the session can reach, and put its address in the prompt with an instruction to go fetch it. Claude Code can already do the rest — it downloads the file into its sandbox and reads it, and its file-read tool renders images visually.

The one thing this spec cannot prove up front: whether the Claude Code web sandbox's network policy lets it reach the Supabase Storage host. Outbound HTTPS in that sandbox goes through an agent proxy whose allowlist is environment-configured. This is called out as risk R1 (§12) with a verification step in the acceptance criteria and a human-paste fallback baked into the prompt text — it does not block the build.

2 · Decisions locked during refinement

Four forks were resolved with the owner before this spec was written:

Transport
Supabase Storage + URL in the prompt. Images live in a Storage bucket; the launch prompt lists each one's signed URL and tells the agent to download and read it. Rejected: committing images into the project repo (needs a GitHub write token in the frontend and puts binaries in the repo); clipboard-paste-only (manual, one image at a time, unreliable on mobile).
Where you attach
The story detail modal (the code board / backlog surface) and the inbox row's "Open details" panel once the item is classified as Code. Both surfaces render the same shared component. A task's detail panel is unchanged.
What can carry images
Code stories only. Epics and tasks are untouched — no epic attachments, no change to the epic-refinement prompt.
Which prompts get them
All three story launches — refinement, implementation, and the skip-refinement bypass. A screenshot is as useful when building as when speccing.

One consequence of the second decision drives the data model: an inbox item classified as code has no code_items sidecar and no ref yet — it only gets those at the gate. So attachments must key off items.id, not the story ref. That id survives enter_code_module unchanged, so images attached in the inbox travel with the item into the factory for free.

4 · Data model & migration

One new migration, database/migrations/<next>_item_attachments.sql — take whatever number is free when you build this; do not assume the number in this sentence's neighbourhood is still available. Follow the 0001/0020 conventions: comment on for non-obvious columns, RLS authenticated full access, explicit grants to anon, authenticated, service_role, and a trailing notify pgrst, 'reload schema';.

4.1 The table

-- Image attachments on an item (ALF-113). Keyed on items.id — NOT on a code ref —
-- so an inbox item classified as `code` can carry images BEFORE it has a
-- code_items sidecar, and keeps them across enter_code_module (same item id).
create table item_attachments (
  id           uuid primary key default gen_random_uuid(),
  item_id      uuid not null references items (id) on delete cascade,
  storage_path text not null unique,   -- object key inside the ticket-images bucket
  filename     text not null,          -- the human-facing name, echoed into the prompt
  mime_type    text not null,
  size_bytes   integer not null,
  created_at   timestamptz not null default now()
);

create index item_attachments_item_id_idx on item_attachments (item_id, created_at);

comment on column item_attachments.storage_path is
  'Object key in the ticket-images Storage bucket: <item_id>/<uuid>.<ext>. Unique so a '
  'row and its object are 1:1; the object is removed best-effort when the row is deleted.';
comment on column item_attachments.filename is
  'Original upload name (or pasted-image.png for a clipboard blob). Display only — never used to '
  'build the storage key, so it is not a path-traversal surface.';

alter table item_attachments enable row level security;
create policy "authenticated full access" on item_attachments
  for all to authenticated using (true) with check (true);
grant select, insert, update, delete on item_attachments to anon, authenticated, service_role;
Cascade, and what it does not cover. Deleting an item drops its attachment rows, but Postgres cannot reach into Storage — the objects are orphaned. At single-user volume that is a few stray blobs, not a problem; a sweeper is explicitly out of scope (§11). Do not attempt a trigger against storage.objects.

4.2 The bucket

Private, not public — everything else in alfred sits behind auth, and a public bucket would be the app's first world-readable surface. Reads happen two ways: the UI streams through a cookie-authed route handler (§6), and the launch prompt carries a time-limited signed URL, so exposure is bounded even though the URL travels into a Claude tab. 

insert into storage.buckets (id, name, public, file_size_limit, allowed_mime_types)
values ('ticket-images', 'ticket-images', false, 4194304,
        array['image/png','image/jpeg','image/gif','image/webp'])
on conflict (id) do nothing;

create policy "authenticated ticket-image read" on storage.objects
  for select to authenticated using (bucket_id = 'ticket-images');
create policy "authenticated ticket-image write" on storage.objects
  for insert to authenticated with check (bucket_id = 'ticket-images');
create policy "authenticated ticket-image delete" on storage.objects
  for delete to authenticated using (bucket_id = 'ticket-images');

The bucket enforces the type allowlist and the size cap server-side; the app validates the same two rules earlier (§6.1) so the user gets a readable message instead of a raw Storage error.

4.3 Credentialed tail

supabase db push and supabase gen types need frontend/.env.local, which a web/CI sandbox does not have (the §4 sandbox note in the code-module spec). The implementation session should write the migration and leave applying it + regenerating frontend/lib/database.types.ts as an explicit checklist for a local session. If credentials are present, run both and commit the regenerated types verbatim — never hand-edit that file.

5 · Storage layout & limits

ConcernDecisionWhy
Object key <item_id>/<uuid>.<ext> Server-minted; the user's filename never touches the key, so no traversal or collision. The extension comes from the validated MIME type, not the upload name.
Accepted types image/png, image/jpeg, image/gif, image/webp Images only — this ticket is about screenshots and mockups, not general file storage.
Max size 4 MB per image The upload goes through a Next route handler, and Vercel caps a serverless request body at 4.5 MB. 4 MB keeps a margin. Screenshots are well under it; the escape hatch if this ever bites is a direct-to-Storage signed upload (out of scope).
Max per item 10 Bounds the prompt block (§8) and the thumbnail grid. Enforced client-side (the add affordance disables) and re-checked in the route handler.
Signed-URL TTL 7 days (604800 s) A launched tab can sit unread for a day or two before the human hits enter; a one-hour URL would be dead by then. Long enough to be useful, short enough to expire.

6 · API surface

Four route handlers, all following the house shape — withSession, parseUUID on uuid segments, jsonOk/jsonError, mapSupabaseError (see frontend/app/api/code/epic/route.ts as the model). All Supabase Storage calls happen server-side, so the browser never touches Storage directly and the data-flow layering holds.

RouteBody / paramsBehaviour
POST /api/items/[id]/attachments multipart/form-data, field file Validate (type, size, per-item count) → upload to ticket-images under the minted key → insert the item_attachments row → 201 with the saved row. On a failed insert, remove the just-uploaded object so a half-write leaves nothing behind.
DELETE /api/attachments/[id] uuid segment Read the row for its storage_path, delete the row, then remove the object best-effort. Row first: the row is what the UI reads, so a stray object is the harmless failure and a row pointing at a missing object is not.
GET /api/attachments/[id]/raw uuid segment Stream the object back with its Content-Type and Cache-Control: private, max-age=3600. This is the <img src> for every thumbnail and the lightbox — cookie-authed, so no signed URLs anywhere in the UI.
GET /api/items/[id]/attachment-links uuid segment Mint a 7-day signed URL per attachment and return { filename, url }[] in created_at order — exactly the shape links.ts consumes. Called only at launch, and only when the story has attachments.

6.1 Shared validation

Put the rules in one pure module, frontend/lib/attachments/validate.ts, imported by both the client (to reject before uploading, with a toast) and the route handler (to reject a crafted request). One source of truth, trivially unit-tested: 

export const ACCEPTED_IMAGE_TYPES = ['image/png','image/jpeg','image/gif','image/webp'] as const;
export const MAX_ATTACHMENT_BYTES = 4 * 1024 * 1024;
export const MAX_ATTACHMENTS_PER_ITEM = 10;

/** null when the file is acceptable, otherwise the user-facing reason. */
export function rejectionReason(
  file: { type: string; size: number },
  existingCount: number,
): string | null;

/** '<item_id>/<uuid>.<ext>' — extension derived from the VALIDATED mime type. */
export function buildStoragePath(itemId: string, mimeType: string, uuid: string): string;

buildStoragePath takes the uuid as an argument rather than generating one, so it stays pure and the tests stay deterministic — the caller passes crypto.randomUUID().

7 · Frontend

7.1 The store

A new AttachmentsProvider in frontend/lib/stores/attachments-store.tsx, seeded once at the shell layout exactly like Folders / Tasks / Code (frontend/app/(shell)/layout.tsx), from a new server reader frontend/lib/data/attachments.ts → getAttachments(). Metadata rows are tiny, so the house "fetch-all, seed once, filter client-side" choice applies unchanged. Mount it inside ToastProvider so rollbacks can toast.

ExportShapeNotes
useItemAttachments(itemId)AttachmentEntry[] The item's attachments in created_at order.
useAttachmentActions() { uploadAttachment(itemId, file), deleteAttachment(id) } Both optimistic with reconcile/rollback, per the data-flow skill.

AttachmentEntry (in frontend/lib/types.ts) is the saved row plus two client-only fields: 

export type ItemAttachment = Database['public']['Tables']['item_attachments']['Row'];

export interface AttachmentEntry extends ItemAttachment {
  /** Object-URL preview shown while the upload is in flight, so the thumbnail is instant. */
  previewUrl?: string;
  /** True until the server row reconciles — drives the dimmed/spinner treatment. */
  pending?: boolean;
}

Upload: validate → insert an optimistic entry (temp id, pending, previewUrl from URL.createObjectURL(file)) → POST → replace the temp entry with the saved row and URL.revokeObjectURL(previewUrl). On failure, drop the entry, revoke the preview, and fire the existing error toast. Delete: remove the entry, DELETE, restore it at its original index on failure.

The thumbnail src is entry.previewUrl ?? `/api/attachments/${entry.id}/raw` — one expression covering both the in-flight and the saved case.

8 · The prompt change (links.ts)

This is where the feature actually pays off. Add one more context block, appended after notesContext(...) in all three story builders — buildRefinementUrl, buildImplementationUrl, buildBypassUrl. buildEpicRefinementUrl is untouched (§2). 

export interface PromptAttachment {
  filename: string;
  url: string;
}

/** Cap the listed images so the block can't push the prompt past the ~14k desktop truncation. */
const MAX_PROMPT_ATTACHMENTS = 10;

function attachmentsContext(attachments: readonly PromptAttachment[]): string { … }

export function buildRefinementUrl(
  project: Project,
  story: CodeStory,
  attachments: readonly PromptAttachment[] = [],
): string { … }

The parameter defaults to [], so every existing caller and test keeps compiling and a story with no images produces a byte-identical prompt to today. The emitted block: 

Attached images (2) — these are part of the ticket. Download each one into your sandbox and
READ it so you can actually see it (e.g. `curl -fsSL "<url>" -o /tmp/<filename>`, then open
that path with your file-read tool — it renders images). The links are time-limited; if a
download fails, tell me here and I'll paste the image into this tab instead.
1. login-error.png — https://<project>.supabase.co/storage/v1/object/sign/ticket-images/…
2. target-spacing.png — https://<project>.supabase.co/storage/v1/object/sign/ticket-images/…

Three details that matter and should each be pinned by a test: the block is absent entirely when there are no attachments (an empty "Attached images (0)" heading invites an agent to go looking for nothing); past MAX_PROMPT_ATTACHMENTS the list is clipped and the agent is told it was clipped, the same way notesContext announces truncated notes; and the explicit failure instruction is what makes risk R1 (§12) survivable rather than silent.

8.1 The launcher

openClaudeSession in frontend/lib/stores/code-store.tsx gains one step, before the state write: 

// 1. Sign the images FIRST — a signing failure must not leave the story transitioned
//    to in_refinement with no session ever opened. Skipped entirely (no round trip)
//    when the store already knows the story has no attachments.
const attachments = hasAttachments ? await api.getAttachmentLinks(itemId) : [];
// 2. …then the existing await-the-state-write → copy prompt → window.open sequence.

Order matters: signing before the write means a failure aborts cleanly with an error toast and the story stays where it was. The clipboard paste-fallback (the mobile app drops q) copies the same prompt, images included, so mobile is covered for free.

9 · The e2e mock backend

frontend/scripts/mock-supabase.mjs fakes the Supabase wire protocol for the Playwright suite — and it has no Storage surface at all today. Without one, every upload path 404s under e2e. Extend it (self-contained, Node builtins only, matching its existing style):

EndpointBehaviour
POST|PUT /storage/v1/object/ticket-images/<path> Keep the bytes in an in-memory map keyed by path; respond { Key }.
GET /storage/v1/object/…/ticket-images/<path> Return the stored bytes with the recorded content type (serves both the authenticated download and a signed-URL fetch).
POST /storage/v1/object/sign/ticket-images/<path> Respond { signedURL: '/object/sign/ticket-images/<path>?token=mock' } — supabase-js resolves it against the configured Storage URL, so the deterministic token=mock is directly assertable in a prompt test.
DELETE /storage/v1/object/ticket-images/<path> Drop the entry; respond 200.
/rest/v1/item_attachments CRUD alongside the existing tables, plus an attachments array in SeedState / /__mock__/{reset,seed,state} and a makeAttachment() helper in frontend/e2e/support/constants.ts.

Reset must clear the object map as well as the rows, or images leak between tests.

12 · Acceptance criteria

  • A migration adds item_attachments (keyed on items.id, cascade delete) with RLS, grants, and comments, plus the private ticket-images bucket and its three storage.objects policies.
  • From the story detail modal, an image can be added by file picker, by drag and drop, and by paste; it appears as a thumbnail immediately and survives a reload.
  • From an inbox item classified as Code, "Open details" shows the same uploader with the same three input methods. A task or unclassified item shows no such section.
  • Clicking a thumbnail opens the full image; each thumbnail can be deleted, and the delete rolls back with an error toast if the request fails.
  • Non-image files, images over 4 MB, and an eleventh image are rejected client-side with a readable message, and rejected again by the route handler.
  • Images attached to an inbox item are still attached after the gate moves it into the factory (same items.id).
  • The refinement, implementation, and bypass prompts each carry an "Attached images" block listing every attachment's filename and signed URL, with the download-and-read instruction and the paste fallback. A story with no images produces the prompt unchanged from today.
  • The epic-refinement prompt is unchanged.
  • The launch signs the URLs before the factory-state write, and a signing failure leaves the story's state untouched.
  • The e2e mock Supabase serves Storage upload / download / sign / delete plus item_attachments, and resets cleanly between tests.
  • Root npm run check is green, every behaviour above is pinned by a test, and the demo doc verifies.
  • R1 verified by hand: one real launch from a story with an image, confirming the Claude Code session can fetch the signed URL and see the image. Record the outcome in the demo doc or the PR.
  • The supabase skill's line "Supabase Storage … not used in alfred's schema" is updated to describe the ticket-images bucket and the server-side-only access rule, per the compounding-learning rule.

13 · Out of scope

  • Epic and task attachments. Stories only (§2). The table is keyed on items.id, so extending later is additive.
  • Non-image files — no PDFs, logs, or zips.
  • Attachment count chips on board cards, backlog rows, or inbox rows. The store has the data if this is wanted later; it is not part of this ticket.
  • Annotation, cropping, reordering, or renaming — attach and delete only.
  • Attaching from the capture box before an item exists.
  • An orphaned-object sweeper for blobs left by a cascade delete (§4.1).
  • Feeding images to the webhook Worker — the Worker is unchanged by this ticket.

14 · Risks & open questions

Risk / questionHandling
R1 The Claude Code web sandbox reaches the network through an agent proxy with an environment-configured allowlist. If the Supabase Storage host is blocked, the agent cannot download the image and the whole transport fails. Flag, don't block. The prompt tells the agent to say so and ask for a paste, so the failure is loud and recoverable. Verify with one real launch (§12) before calling this done. If it is blocked, the fallback fork is committing images into the project repo — respec that separately rather than bolting it on.
R2 Vercel's 4.5 MB serverless request-body limit caps what can flow through the upload route. Accepted: 4 MB per image (§5). A direct-to-Storage signed upload is the documented escape hatch if a larger file is ever needed.
Q1 Is 7 days the right signed-URL TTL? A tab left open longer than that yields dead links in an already-prefilled prompt. Ship 7 days; it is a one-constant change. Revisit only if a real launch actually goes stale.
Q2 Should the images also render inside the spec that a refinement session writes? Deferred — that is the refinement session's call, and the signed URLs expire, so a committed spec should not embed them. Not specified here.
