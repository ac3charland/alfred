ALF-129 — Support constructing epics like projects in the inbox, and converting 1-deep projects to code epics

Refinement Inbox · Code module DB · RPC · store · UI Spec only — no implementation. Build in a later session.

1 · Context & problem

Alfred has no way to plan a multi-step coding effort before it enters the factory. Today a code-classified inbox item is a single flat thought: it carries a title, notes, and an optional intended project, and the gate turns it into exactly one code story under an epic you have to pick (or create) in the dialog. Anything bigger than one story has to be captured as several unrelated inbox rows, sent one at a time, and re-ranked on the Backlog afterwards.

Meanwhile the tasks side already has the shape we want: a parent row with an inline + (desktop) or a Add subtask menu item (mobile, ALF-118), children that can be dragged into gaps or nudged with Move up / Move down (ALF-117), and a persisted manual order (items.sort_order).

ALF-129 lends that shape to code items: build the epic in the inbox as a parent plus an ordered list of children, then send the whole group across in one action. The parent becomes the epic; each child becomes a story, created at the top of its project's Backlog in the order you arranged them. The same conversion is offered from the tasks module for a task that has already been decomposed into subtasks (Convert to Code Epic).

2 · Decisions (locked during refinement)

Depth
Exactly one level. A code item may have children only if it is a root; a code child may never have children of its own. Enforced in the UI (no + on a code child) and in the database (a trigger — adjacency depth can't be a CHECK).
Child type
A child inherits its parent's family. A child added under a code row is created as code; a child under a task stays task, exactly as today. Mixing is rejected by the same trigger.
Parent → epic
The parent is the epic: the epic takes the parent's title as its name and the parent's notes as epic notes. Its ref comes from the shared per-project counter, like every other epic (create_epic).
Parent's fate
A code parent's item row is deleted — it has no completion concept (the items_task_only_fields CHECK pins non-task rows to status='active'), and nothing is lost because the epic carries its title and notes. A task parent is marked completed instead, so it drops into the Completed view with its completed children still beneath it — the decomposition history stays intact.
Which children convert
Active children only, in sort_order order. Completed children are finished work: they stay as children of the now-completed task parent. (A code parent can't have completed children at all — non-task rows are always active.)
Story priority
The stories land at the top of their project's Backlog, in display order: the first child ranks highest, the last child ranks lowest of the new group, and every other story in that project sits below them. No other project's stories are displaced — the conversion reuses top_of_project_priority(), so it inherits ALF-110/ALF-120 semantics exactly.
Send flow
Skip the dialog when the project is already known. A code parent captured with a <project>: prefix (so it carries intended_project_id) converts immediately from the menu — no dialog. Without an intended project, a project-only gate dialog opens (the epic is not picked; it is being created). The tasks-module Convert to Code Epic… path always opens that dialog, since a task can never carry an intended project.
Menu shape
Convert to Code Story… and Convert to Code Epic… sit adjacent and are always rendered for a convertible row, each disabled (with a hint) when it doesn't apply — so the epic path is discoverable rather than appearing only in the one state that allows it.
Not draggable across families
Drag-and-drop never mixes the two trees: a code child reorders among code siblings (its own parent, or another code root); a task can't be dropped onto a code row and a code child can't be dropped onto a task row. This also closes a latent hole — today a task can be re-parented onto a code inbox row, because the drop resolver never checked item types.
Bulk bar
The Inbox bulk Send to Code… stays story-per-item and is disabled whenever any selected row has children (same disabled+hint pattern as Classify as / Move to folder). Epic-shaped rows go through their own row menu.

3.3 · What the conversion does

One RPC: allocate the epic, walk the active children bottom-up so each lands above the last, then consume the parent.

3.4 · Why the children are walked bottom-up

top_of_project_priority(p) returns a priority that sits just above the project's current top outstanding story and below whatever other project's story ranks nearest above it. Calling it once per child, iterating the children in reverse display order (S3 → S2 → S1), makes each new story land above the one created before it — so the final ranking reads S1 < S2 < S3 < everything else in the project. No new priority maths, and the group inherits the “don't displace other projects” guarantee (ALF-110) and the “ignore done/abandoned” fix (ALF-120) for free.

4 · Proposed change

4.1 · Schema — let a code item nest, one level deep

database/migrations/0019_code_epics.sql (new)

items_task_only_fields currently makes every non-task row structurally incapable of holding a parent_id. Relax it for code only — due dates and completion stay task-only: 

alter table items drop constraint items_task_only_fields;
alter table items add constraint items_task_only_fields check (
  item_type = 'task'
  or (due_date is null and status = 'active' and completed_at is null
      and (parent_id is null or item_type = 'code'))
);

Depth and family-matching are adjacency properties, so they need a trigger rather than a CHECK. One before insert or update trigger enforces all three rules — a code child hangs only off a code root, a code row with children may not itself be nested, and the two families never mix: 

create or replace function enforce_subtask_shape() returns trigger
language plpgsql security invoker as $$
declare v_parent items;
begin
  if new.parent_id is null then return new; end if;
  select * into v_parent from items where id = new.parent_id;
  if v_parent is null then
    raise exception 'parent % not found', new.parent_id;
  end if;
  if new.item_type = 'code' then
    if v_parent.item_type <> 'code' then
      raise exception 'a code item may only be nested under another code item';
    end if;
    if v_parent.parent_id is not null then
      raise exception 'code subtasks are one level deep';
    end if;
    if exists (select 1 from items where parent_id = new.id) then
      raise exception 'a code item with children may not itself be nested';
    end if;
  elsif v_parent.item_type = 'code' then
    raise exception 'only a code item may be nested under a code item';
  end if;
  return new;
end; $$;

create trigger items_subtask_shape
  before insert or update of parent_id, item_type on items
  for each row execute function enforce_subtask_shape();
Order of operations inside the migration matters. Create the trigger after the constraint swap, and note that enter_code_module already nulls parent_id in the same UPDATE that flips item_type, so gating an item into the factory takes the trigger's early-return path.

No column is added to items, so the task_items “select i.* freezes its column list” gotcha (0011/0013/0018) does not apply — the view is left alone.

4.2 · The conversion RPC

One atomic RPC does the whole conversion. It returns json (the complete_and_spawn precedent from 0006) because the client needs both the new epic row and the created story sidecars: 

create or replace function convert_to_code_epic(p_item uuid, p_project uuid)
returns json language plpgsql security invoker as $$
declare
  v_parent items; v_epic epics; v_child items; v_row code_items;
  v_key text; v_n int; v_priority double precision;
  v_stories code_items[] := '{}';
begin
  select * into v_parent from items where id = p_item;
  if v_parent is null then raise exception 'item % not found', p_item; end if;
  select key into v_key from projects where id = p_project;

  -- The parent IS the epic: same title, same notes, ref from the shared project counter.
  select * into v_epic from create_epic(p_project, v_parent.title);
  if v_parent.notes is not null then
    update epics set notes = v_parent.notes where id = v_epic.id returning * into v_epic;
  end if;

  -- Active children, BOTTOM-UP: each top_of_project_priority() call lands the next child
  -- ABOVE the previous one, so display order comes out as priority order (§3.4).
  for v_child in
    select * from items
     where parent_id = p_item and status = 'active'
     order by sort_order desc, created_at desc
  loop
    v_n        := next_code_ref(p_project);
    v_priority := top_of_project_priority(p_project);
    update items set item_type = 'code', due_date = null, parent_id = null,
                     status = 'active', completed_at = null
      where id = v_child.id;
    insert into code_items (item_id, project_id, epic_id, ref_number, ref, priority)
    values (v_child.id, p_project, v_epic.id, v_n, v_key || '-' || v_n, v_priority)
    returning * into v_row;
    v_stories := v_row || v_stories;   -- prepend, so the array comes back in display order
  end loop;

  -- Consume the parent: a task keeps its history (completed, completed children still
  -- beneath it); a code inbox row has no completion, so it is deleted.
  if v_parent.item_type = 'task' then
    update items set status = 'completed', completed_at = now() where id = p_item;
  else
    delete from items where id = p_item;
  end if;

  return json_build_object('epic', to_json(v_epic), 'stories', to_json(v_stories));
end; $$;

grant execute on function convert_to_code_epic(uuid, uuid)
  to anon, authenticated, service_role;

The grant execute line is not optional — see the supabase / migration-lint skills. frontend/lib/database.types.ts must be regenerated (supabase gen types) and committed verbatim so the new function is typed; it is a generated file and must never be hand-edited.

4.4 · Stores

code-store — convertToCodeEpic

A new action beside convertTaskToCode, following the same optimistic recipe (runOptimisticMutation → insert → reconcile → rollback → error toast; see the data-flow skill):

  • Optimistic: insert a makeOptimisticEpic(projectId, parentTitle), then one makeOptimisticStory per child. Priorities mirror the server by folding the existing private topOfProjectPriority(stories, projectId) helper over the children in reverse display order, appending each pseudo-story to the local list as it goes — so the optimistic cards sort into the same slots the RPC will reconcile to.
  • Reconcile: replaceEpic by the temp epic id, then replaceStory per returned sidecar keyed by item_id (the child items already have real ids, like the gate — no temp-id swap needed).
  • Rollback: removeEpic + removeStory for everything it inserted; toast “Couldn't create epic”.
  • Signature: convertToCodeEpic(parent: { id; title; notes }, children: { id; title; notes; source_url }[], projectId: string): Promise<ConvertedEpic> — the caller passes the children already in display order.

tasks-store — settle the conversion locally

The converted children have left task_items (they now have sidecars) and the parent is either gone or completed. That is a pure client-side reconciliation, exactly like removeGatedItem — no API call, nothing to roll back: 

/**
 * Reflect a completed epic conversion: the converted children have left task_items, and the
 * parent is either completed (a task keeps its history + completed children) or removed (a
 * code inbox row, which the RPC deletes).
 */
settleEpicConversion: (input: {
  parentId: string;
  childIds: string[];
  parentOutcome: 'completed' | 'removed';
}) => void;

tasks-store — a child inherits its parent's family

addTask currently hard-codes item_type: parentId === undefined ? … : 'task'. Derive it from the parent already held in the flat list instead, so the code-child case needs no prop drilling through CaptureBox: 

const parent = parentId === undefined
  ? undefined

4.5 · Inbox UI

The “+” and the mobile menu item

  • useTaskRowFlags gains the shape flags the row and menu both need: canAddSubtask (isTask, or a code row with parent_id === null), isCodeParent, isCodeChild, canConvertToStory, canConvertToEpic. Centralising them here keeps the row and its menu in sync, which is the hook's stated job.
  • TaskRow renders the desktop + and passes the mobile Add subtask item when canAddSubtask (was isTask). On a code row the label and aria-label read “Add story”, and the inline CaptureBox takes a new optional placeholder prop ("Add story…"), defaulting to today's "Add subtask…".
  • A code child never shows the affordance, so the 1-deep rule has no UI path to violate.

Reordering code children

Gap strips, useSubtaskReorder, and reorderSubtask are all type-agnostic already — they key off parent_id + sort_order — so code children reorder with no change to those modules. What must change is the drop resolver, which currently ignores item types:

  • lib/dnd/reorder-subtask.ts → resolveReorder takes two new inputs, draggedItemType and gapParentItemType, and returns null when they don't match (a task into a code group, or a code child into a task group). Cross-parent reorder within the code family stays allowed — dragging a story from one epic-in-progress into another is useful and the resolver already handles the re-parent.
  • TaskDndProvider's re-parent branch bails when dragged.item_type === 'code' or target.item_type !== 'task', beside the existing completed/temp-id bail. This also fixes a latent bug: today a task dropped on a code inbox row is re-parented under it, because only the drop highlight (isValidDropTarget) checked the type.
  • Promote-to-root is left as-is: pulling a code child out to the top level makes it a plain code inbox row again, which is a legal state and a useful escape.

The row menu

  • Convert to Code Story… / Convert to Code Epic… — rendered adjacent for any convertible row, each with disabled + a title hint per §3.2. New props: canConvertToStory, canConvertToEpic, onOpenEpicGate.

5 · Out of scope / open questions

  • No epic construction inside the Code module. Epics there are still created by name via NewEpicDialog; this ticket only adds the inbox-side construction path.
  • No bulk epic conversion. The bulk bar disables rather than converting several parents at once (locked in §2).
  • No re-nesting a code item by drag. A code child is created with the + and can be reordered or promoted, but a code root can't be dragged into another code root to become a story of it. If that turns out to be wanted, it's a follow-up: the trigger already permits the shape, only the resolver would relax.
  • Folder view. Code rows have never been folder-filed in practice (folder_id stays null for inbox code items); this ticket doesn't change that, and a code parent constructed in a folder is not a supported flow.
  • Open: should an epic created this way carry the parent's source_url anywhere? Epics have no such column today; the value is dropped for the code path (the task path keeps it on the completed parent). Left as-is unless it proves annoying.

6 · Acceptance criteria

  • A code-classified inbox row at the root shows the inline + on desktop and an Add story item in the ⋯ menu on mobile; a code child shows neither.
  • Adding a child under a code row creates it as item_type = 'code', appended at the bottom of the group, and it renders under the parent with the Code badge and no checkbox.
  • Code children reorder by gap-drop and by Move up / Move down, and the order survives a reload.
  • A task cannot be dropped into a code group and a code child cannot be dropped into a task group (in either direction, including onto a row body); the database rejects it too.
  • The database rejects a code item nested more than one level deep, and rejects a code child whose parent is not a code root.
  • A code parent with children shows Send to Code module. With an intended_project_id it converts immediately with no dialog; without one it opens the project-only epic gate.
  • Conversion creates one epic named after the parent (carrying its notes) and one story per active child, all in the chosen project.
  • The new stories rank at the top of that project's Backlog in display order — first child highest — with the project's pre-existing stories below them and no other project's stories displaced.
  • After converting a code parent, the parent row is gone from the inbox and the children are gone from task_items; the board shows the new epic with its stories at Needs Refinement.
  • After Convert to Code Epic… on a task, the parent task is completed and appears in the Completed view with its previously-completed children still beneath it; its active children have become stories.
  • Convert to Code Story… is disabled for a row with children; Convert to Code Epic… is disabled for a row with no active children or with a child that has children of its own. Both are visible (not hidden) with a hint.
  • The Inbox bulk Send to Code… is disabled with a hint when any selected row has children.
  • A failed conversion rolls the optimistic epic and stories out of the code store, leaves the inbox rows untouched, and toasts the failure.
  • npm run check is green, and the change is captured in a demo doc.
