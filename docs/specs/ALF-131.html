ALF-131 — Add tool to measure PR ratios

Refinement Code module env · lib · API route · UI Spec only — no implementation. Build in a later session.

1 · Context & problem

Part of this quarter's goal-tracking is a simple weekly split: of the pull requests I merged this week, what share went to RealPlay and what share went to alfred? Today that question can only be answered by opening two GitHub tabs and counting by hand, which means it doesn't get asked. The number is small, the cadence is weekly, and the natural place to see it is the surface already used to decide what to work on next — the Backlog.

ALF-131 adds two things: a ratio component at the top of the Backlog view showing a split bar with a percentage label per repo, and the authenticated API endpoint that computes it, so the same number is reachable from a script, a Shortcut, or a future weekly-review surface without going through the UI.

Why this can't come from alfred's own data. The webhook Worker only reacts to PRs whose body carries an alfred frontmatter block, and code_items stores implementation_pr_url with no merge timestamp. So the existing tables can answer neither "was it merged this week" nor "what about the PRs the factory never saw" — and most RealPlay PRs are in that second bucket. The ratio is therefore computed from a live GitHub query, and reads nothing from Supabase.

2 · Decisions (locked during refinement)

Data source
Live GitHub Search API, server-side, one request per configured repo. The response's total_count is the count — no paging, no per-PR fetch.
Repo configuration
A server-side env var PR_RATIO_REPOS naming each repo and its display label. Deliberately not the projects table: RealPlay does not run through the Software Factory, and adding it as a project row would surface it in every project nav, board, and epic picker in the Code module.
Which PRs count
Merged PRs authored by the owner or by Claude on the owner's behalf — expressed as an author allowlist (PR_RATIO_AUTHORS). Verified against the real repo: agent-opened PRs in ac3charland/alfred are authored by ac3charland (opened via the Claude GitHub App), so one login covers both today, and the allowlist accommodates a future bot identity without a code change. Dependency bots are excluded by construction.
Week boundary
ISO week — Monday 00:00:00 inclusive → the following Monday 00:00:00 exclusive — evaluated in an IANA timezone supplied by the caller (?tz=). The in-app component sends the browser's resolved timezone; an external caller that sends nothing gets UTC. No timezone is baked into config or code.
API auth
Both — the browser session (cookie) for the in-app component, and the existing INGEST_API_KEY via x-api-key / Authorization: Bearer for scripts. Same dual posture as the capture ingress on POST /api/items.
Failure posture
The ratio is an ornament on the Backlog, never a gate. Missing config, a GitHub outage, a rate-limit, or an expired token must leave the Backlog fully usable — the component renders nothing (or a one-line muted note), and nothing throws.

3 · End-to-end flow

One read path, no writes, no Supabase. Every box below the fold is pure — the only I/O is the fan-out to GitHub.

  1. The Backlog mounts <PrRatio />. On mount the hook calls GET /api/code/pr-ratio?tz=<browser tz>; a skeleton renders meanwhile.
  2. The route authenticates (session or API key), resolves the repo config, and computes the ISO-week window in the requested timezone.
  3. One GitHub search per configured repo runs in parallel; each response's total_count is the repo's merged-PR count for the week.
  4. Counts become percentages via largest-remainder rounding (so the labels sum to exactly 100%), and the route returns the JSON envelope in §6.
  5. The component renders the split bar and its labels — or renders nothing at all if the endpoint reported that the feature is unconfigured.

4 · Configuration

Three new server-side env vars, added to frontend/.env.example with the same commented-template treatment the existing entries get. None are NEXT_PUBLIC_ — the token in particular must never reach the browser.

VariableRequiredFormatNotes
GITHUB_TOKEN Yes Fine-grained PAT Needs only Pull requests: read (plus Metadata: read) on the measured repos. Same name the Worker already uses for its own token, so the mental model is shared, but this is the frontend's own value in the frontend's own env.
PR_RATIO_REPOS Yes owner/name:Label,owner/name:Label Comma-separated, order preserved — that's the left-to-right order of the bar segments. The :Label suffix is optional; a missing label falls back to the repo name. e.g. ac3charland/realplay:RealPlay,ac3charland/alfred:Alfred
PR_RATIO_AUTHORS No login,login Comma-separated GitHub logins whose merged PRs count. Unset → no author: qualifier, and the known dependency bots are excluded instead (see §5.2).

Parsing lives in frontend/lib/github/config.ts and mirrors lib/instance.ts exactly: literal process.env.X reads (never a computed key), a blank-collapses-to-unset helper, and a total function that returns a typed object. Two or more repos must parse for the feature to be considered configured — a one-repo "ratio" is meaningless. 

frontend/lib/github/config.tsexport interface RatioRepo {
  /** GitHub owner, e.g. 'ac3charland'. */
  owner: string;
  /** GitHub repo name, e.g. 'realplay'. */
  name: string;
  /** Display label for the bar segment; defaults to `name` when the suffix is omitted. */
  label: string;
}

export interface PrRatioConfig {
  repos: RatioRepo[];
  authors: string[];
  token: string;
}

/**
 * Returns the parsed config, or `undefined` when the feature is not configured
 * (no token, or fewer than two well-formed repo entries). Never throws.
 */
export function getPrRatioConfig(): PrRatioConfig | undefined;

Malformed entries are skipped, not fatal: an entry that doesn't match owner/name (optionally :Label) is dropped, and if fewer than two survive, getPrRatioConfig() returns undefined and the feature is off.

5 · The computation

5.1 · The week window

frontend/lib/github/week.ts owns a single pure function. It is the one piece of logic here with real edge cases (DST, negative-UTC offsets, Sunday), so it is pure, exported, and directly unit-tested — no network, no clock reads beyond the injected now. 

frontend/lib/github/week.tsexport interface WeekWindow {
  /** ISO 8601 with offset, e.g. '2026-07-20T00:00:00-04:00' — inclusive. */
  start: string;
  /** ISO 8601 with offset — EXCLUSIVE (the following Monday's midnight). */
  end: string;
  /** The IANA timezone the window was computed in. */
  timezone: string;
}

/**
 * The ISO week (Monday 00:00 → next Monday 00:00) containing `now`, expressed in `timezone`.
 * Falls back to 'UTC' when `timezone` is not a valid IANA zone — never throws.
 */
export function isoWeekWindow(now: Date, timezone: string): WeekWindow;
  • Monday-start, matching ISO-8601 — so a Sunday-evening merge lands in the week that's ending, not the one about to begin.
  • Offsets are derived per-instant via Intl.DateTimeFormat with the target timezone, so a week spanning a DST change still starts and ends at local midnight.
  • An unknown/garbage tz silently degrades to UTC rather than 400-ing — the endpoint's job is a number, not timezone validation.

5.2 · The GitHub query

One GET https://api.github.com/search/issues per repo. GitHub's merged: qualifier accepts ISO timestamps with offset, which is exactly what §5.1 emits, so the window is enforced by GitHub rather than by post-filtering — important, because the search response's issue objects do not carry merged_at at the top level. 

repo:{owner}/{name} is:pr is:merged merged:{start}..{end}
  + for each configured author:  author:{login}          // GitHub ORs repeated author: qualifiers
  + when NO authors configured:  -author:app/dependabot -author:app/renovate -author:app/github-actions

Request shape, mirroring the Worker's existing GitHub call in workers/src/github.ts:

AspectValueWhy
Headers Authorization: Bearer $GITHUB_TOKEN, Accept: application/vnd.github+json, X-GitHub-Api-Version: 2022-11-28, User-Agent: alfred GitHub rejects API requests with no User-Agent — the gotcha already documented in the Worker's helper.
Query params q=<query>&per_page=1 Only total_count is read; asking for one item keeps the payload tiny.
Caching next: { revalidate: 300 } Search is capped at 30 req/min. A 5-minute revalidate makes repeated Backlog visits free while keeping the number current enough for a weekly metric.
Concurrency Promise.all across repos Two sequential round-trips would double the component's time-to-content for no reason.
Non-2xx Whole request fails (see §6) A partial ratio is a wrong ratio — better to show nothing than a bar whose segments were counted under different rules.

5.3 · Percentages

Percentages are integers that sum to exactly 100, via largest-remainder (Hamilton) rounding — floor each share, then hand the leftover points to the largest fractional remainders, ties broken by config order. Naive per-segment rounding produces the classic "33% / 66%" bar that visibly doesn't add up. Pure, exported, unit-tested: 

frontend/lib/github/pr-ratio.ts/** Integer percentages summing to exactly 100. All-zero input yields all zeros. */
export function toPercentages(counts: number[]): number[];

When every count is zero the total is zero: every percentage is 0 (not NaN, not an even split), and the UI shows its empty state (§7).

6.1 · Auth

Neither withSession nor validateApiKey alone covers the dual posture, and resolveIngestClient is the wrong shape here (it returns a Supabase client this route has no use for). Add a small sibling to lib/api/auth.ts so the pattern is named once rather than inlined:

 * something other than the database.

export function withSessionOrApiKey(
  handler: (request: Request) => Promise<Response>,
): (request: Request) => Promise<Response>;

6.2 · Request

ParamRequiredMeaning
tzNo IANA timezone the ISO week is evaluated in. Defaults to UTC; an unrecognized value also degrades to UTC.

Validated with a zod schema in lib/api/schemas.ts through the existing parseQueryParams helper, like every other query-taking route — not a hand-rolled searchParams.get.

6.3 · Responses

StatusWhenBody
200SuccessThe envelope below
401No session and no valid API key { "error": "Unauthorized" }
501Feature not configured (getPrRatioConfig() returned undefined) { "error": "PR ratio is not configured" }
502Any repo's GitHub request failed or rate-limited { "error": "GitHub request failed" }

The 200 envelope — 200 GET /api/code/pr-ratio?tz=America/New_York:

{
  "week": {
    "start": "2026-07-20T00:00:00-04:00",
    "end": "2026-07-27T00:00:00-04:00",
    "timezone": "America/New_York"
  },
  "total": 9,
  "repos": [
    { "repo": "ac3charland/realplay", "label": "RealPlay", "count": 3, "percentage": 33 },
    { "repo": "ac3charland/alfred",   "label": "Alfred",   "count": 6, "percentage": 67 }
  ]
}

repos preserves PR_RATIO_REPOS order. The response type (PrRatioResponse) lives in lib/types.ts and is what lib/api-client.ts's new getPrRatio(tz) resolves to — the client never re-declares the shape.

The distinction between 501 and 502 is load-bearing. 501 means "this deployment doesn't do PR ratios" → the component renders nothing, so a deployment without a token (or local dev) shows a clean Backlog. 502 means "configured but GitHub is unhappy right now" → the component renders a one-line muted note, because silence there would look like "zero PRs this week".

Per the frontend-architecture skill: the reusable primitive goes in atoms/, the compound is assembled in the feature directory, and the fetching behavior is a hook.

7.4 · States

StateRender
LoadingThe card with a muted skeleton bar — reserves the same height, so the Backlog list doesn't jump when data lands.
Ready, total > 0The bar + legend as mocked above.
Ready, total === 0Card with the muted line "No PRs merged yet this week." and no bar — a week genuinely starts at zero every Monday, so this is a normal state, not an error.
Unconfigured (501)Renders nothing — no card, no gap.
Error (502 / network)Card with the muted line "Couldn't load PR counts." No toast, no retry loop, nothing thrown.

7.5 · Styling

  • Segment tones come from the existing named-accent tokens in globals.css, cycled by index: accent-teal, accent-blue, accent-amber, accent-green. No new color tokens.
  • Card chrome matches the surrounding Code surfaces — rounded-lg border border-border bg-surface p-4 — so it reads as part of the Backlog rather than a widget bolted on.
  • The legend wraps on narrow viewports (the header row above it already does).
  • Accessibility: the bar carries role="img" with an aria-label spelling out the split ("RealPlay 33 percent, 3 pull requests; Alfred 67 percent, 6 pull requests"), since the visual split alone conveys the information. Each segment is aria-hidden; the legend text is the accessible detail.
  • Width transitions respect prefers-reduced-motion per the motion skill if the segments animate in at all.

11 · Acceptance criteria

  • The Backlog (/code and /code/backlog) shows a PR-ratio card between the "The Software Factory" header and the story list.
  • The card shows one segment per configured repo, in config order, with a percentage label and raw count per repo; the percentages sum to exactly 100.
  • Counts cover PRs merged in the current ISO week (Monday 00:00 → next Monday 00:00) in the viewer's local timezone.
  • Only PRs by the configured author logins are counted; with no authors configured, dependency bots are excluded.
  • GET /api/code/pr-ratio returns the documented envelope for an authenticated browser session.
  • The same endpoint returns the same envelope for a request bearing a valid INGEST_API_KEY via x-api-key or Authorization: Bearer.
  • The endpoint returns 401 when neither a session nor a valid API key is presented.
  • ?tz= changes which week is measured and is echoed in week.timezone; an absent or invalid value yields UTC without erroring.
  • With no GITHUB_TOKEN / PR_RATIO_REPOS, the endpoint returns 501 and the Backlog renders exactly as it does today, with no card and no error.
  • When GitHub fails or rate-limits, the endpoint returns 502 and the card shows a muted error line; the Backlog and its list stay fully usable.
  • A week with no merged PRs shows "No PRs merged yet this week" rather than an empty or NaN bar.
  • The GITHUB_TOKEN value never reaches the browser (no NEXT_PUBLIC_ prefix; no token in any client bundle or API response).
  • Every suite in §9 exists and passes; root check is green.
  • A demo doc per §10 exists and npm run demo -- verify passes.

12 · Out of scope

  • History and trends. Current week only — no previous-week comparison, no sparkline, no stored time series. (A future ticket wanting "vs last week" should add a ?week= offset param to this endpoint rather than a second one.)
  • Persisting PR data. No new table, no Worker change, no widening of the webhook beyond alfred-frontmatter PRs.
  • Anything but merged PRs. Open, draft, and closed-unmerged PRs are not counted; neither are commits, reviews, or lines changed.
  • Managing the config from the UI. Repos and authors are env-configured; no settings screen.
  • Goal targets. No "target ratio" line, no red/green judgement — the component reports, it doesn't grade.
  • Other surfaces. Project boards, the Tasks module, and the weekly-review flow don't show the ratio; the endpoint exists so a later ticket can add them cheaply.

13 · Open questions

  • The RealPlay repo's exact owner/name is not in this repo and wasn't needed to spec the behavior — it's a config value, set at deploy time in PR_RATIO_REPOS. The implementation session should use a placeholder in .env.example and let the real value be filled in on Vercel.
  • More than two repos. Everything above is written for N repos rather than exactly two (config order drives segments, largest-remainder handles N shares), so a third repo is a config change. Only the legend layout is designed against two; if a third is ever configured, the legend may want to stack rather than sit end-to-end.
