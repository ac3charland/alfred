ALF-132 — Add tasks view for weekly plan and endpoint to upload

Refinement Tasks module API · DB · UI Spec only — no implementation. Build in a later session.

1 · Context & problem

Every Friday the owner runs the weekly-review skill in Claude desktop. Its last step pipes a JSON plan through scripts/generate_plan.py, which emits a single self-contained HTML document — week-plan-<N>.html — carrying the week's theme, win conditions per rock, a day-by-day task breakdown, a timeline grid, success criteria, and open items.

That document currently lives wherever the desktop session dropped it. It is the single most referenced artifact of the week, and it is not in alfred — the app the owner actually has open all day. This ticket closes that gap: an upload endpoint so the plan can be posted into alfred the moment it's generated, and a tasks-module view that renders it, alongside By-Priority in the sidebar.

The rendering half already has a proven precedent in this repo: the code module's SpecBody (frontend/components/code/story-detail/spec-body.tsx) renders a snapshotted spec HTML document in a sandboxed <iframe srcDoc> so the document's own <style> can't leak into the app. This spec reuses that approach, with one deliberate deviation (§7.2) — the weekly plan needs its scripts to run, and the spec snapshot does not.

2 · Decisions locked during refinement

Three scope forks were resolved with the owner before writing this spec:

History
Archive + week picker. Every upload is kept as its own row; nothing is overwritten. The view renders the most recent plan by default and offers a picker to read earlier weeks.
Upload path
API-key endpoint only. No in-app file picker / drag-drop. The plan is POSTed with the existing INGEST_API_KEY ingress convention, the same shape POST /api/items already uses for the Siri capture path.
Metadata
None — store the HTML. No week number, no date range, no title parsing. A row is (id, html, uploaded_at). The picker labels entries by their upload date. Deriving richer labels is deferred (§12).

3 · What the uploaded artifact actually is

The implementation session should not have to guess at the payload. The generator emits, in one file with no external dependencies:

TraitDetailConsequence for this change
Doctype Starts <!DOCTYPE html> Passes the existing looksLikeHtmlDocument() sniff — reused as upload validation (§5.3).
Size ~30–50 KB (inline CSS + inline JS + content) Comfortably inside a 1 MB request cap; fine as a text column.
Styling Inline <style>, its own :root tokens and a prefers-color-scheme: dark block; body is max-width: 780px; margin: 0 auto; padding: 2rem Must render in an isolated frame (styles would otherwise collide with the app's). It brings its own dark mode and its own centering.
Scripts A trailing <script> block with PLAN_DATES and a per-day task map. It highlights today's column in the timeline and fills the “today” card. The frame must allow scripts, or the plan's most useful feature is inert. This is the deviation from SpecBody's sandbox="" (§7.2).
Interactivity Success criteria are <input type="checkbox"> with no persistence Ticks are frame-local and lost on reload/switch. Accepted — the plan is a read artifact here, not a task store (§12).
Title <title>Week 12: Jul 4 – Jul 11, 2026</title> Present, but deliberately not parsed per the locked metadata decision.

4 · Data flow

Write once a week through the keyed ingress; read from the shell-seeded store, with older plans' HTML pulled on demand rather than shipped in every page load.

5 · The upload endpoint

5.1 Route and contract

New Route Handler at frontend/app/api/weekly-plans/route.ts, plural to match /api/folders, /api/items, /api/epics.

MethodAuthRequestResponse
POST resolveIngestClient() Content-Type: text/html, raw body = the document 201 { id, uploaded_at }

Raw body, not JSON. Every other handler in the repo parses JSON via parseRequestBody, but the payload here is a file: the ergonomic call is --data-binary @week-plan-12.html, and JSON-escaping a 40 KB document from a shell is hostile. The handler reads await request.text() and validates the string (§5.3). Requests carrying any other Content-Type are rejected 415, so the contract stays unambiguous.

5.2 Auth

Use the existing resolveIngestClient(request) from frontend/lib/api/auth.ts — the same helper POST /api/items uses. A valid x-api-key / Authorization: Bearer matching INGEST_API_KEY resolves the service-role admin client; otherwise it falls back to the logged-in session; neither → 401. Nothing new is built here.

frontend/middleware.ts needs no change — it already treats all of /api as public so handlers self-authenticate with a JSON 401 rather than a 302 to /login.

5.3 Validation

ConditionStatusBody
No / wrong Content-Type (not text/html)415{ error: 'Expected Content-Type: text/html' }
Empty or whitespace-only body400{ error: 'Empty request body' }
Body > 1 MB413{ error: 'Weekly plan exceeds 1MB' }
Body is not an HTML document400{ error: 'Body must be an HTML document' }

The document sniff is the predicate SpecBody already uses. Extract it rather than copy it (see the frontend-architecture skill's shared-primitive rule): move looksLikeHtmlDocument out of spec-body.tsx into a new frontend/lib/html-document.ts, and import it from both spec-body.tsx and the new handler. Its behaviour is unchanged, so story-detail-modal.test.tsx must stay green untouched.

Error responses use the existing jsonError / jsonOk helpers from frontend/lib/api/responses.ts so the envelope matches every other route.

5.4 The call the owner will actually make

curl -sS -X POST https://<alfred-host>/api/weekly-plans \
  -H "x-api-key: $INGEST_API_KEY" \
  -H "Content-Type: text/html" \
  --data-binary @week-plan-12.html
# {"id":"7f3c…","uploaded_at":"2026-07-24T21:03:11.482Z"}

5.5 Reading one archived plan

New handler at frontend/app/api/weekly-plans/[id]/route.ts:

MethodAuthRequestResponse
GET withSession UUID path param (validated like the other [id] routes) 200 { id, html, uploaded_at }, 404 if unknown

This is the picker's on-demand fetch. It is deliberately session-only — the API key is a write credential for the ingress, and there is no reason to widen it to reads.

6 · Data model

New migration database/migrations/0020_weekly_plans.sql:

-- alfred — weekly plan archive (ALF-132).
--
-- The Friday `weekly-review` skill emits one self-contained HTML document per week. This
-- table is its archive: append-only, one row per upload, no derived metadata (that decision
-- is locked in the spec — the picker labels rows by uploaded_at). `html` is the whole
-- document verbatim, rendered in a sandboxed iframe by the /plan view.

create table weekly_plans (
  id          uuid primary key default gen_random_uuid(),
  html        text not null,
  uploaded_at timestamptz not null default now()
);

comment on column weekly_plans.html is
  'The uploaded week-plan document verbatim (inline CSS + inline JS). Never sanitized; rendered
   only inside a sandboxed iframe with an opaque origin (ALF-132 §7.2).';

-- The only query shape: newest first (latest plan + picker index).
create index weekly_plans_uploaded_at_idx on weekly_plans (uploaded_at desc);

-- ── RLS + privileges ─────────────────────────────────────────────────────────
-- Single-user: the authenticated owner gets full access; anon is denied (no policy).
alter table weekly_plans enable row level security;

create policy "authenticated full access" on weekly_plans
  for all to authenticated using (true) with check (true);

-- RLS gates which rows; GRANTs gate whether the role may touch the table at all. Raw `psql -f`
-- doesn't get Supabase's auto-grants, so grant DML explicitly (see the supabase skill).
grant select, insert, update, delete on weekly_plans
  to anon, authenticated, service_role;
Guardrails to respect here. (a) The explicit grant is not optional — this repo applies migrations with raw psql, so a missing grant is a shipped 500 (the 0005→0008 and 0014→0017 bugs). (b) After applying, regenerate frontend/lib/database.types.ts with the token-free path in the supabase skill (§“local typegen”) and commit the raw output — that file is generator-owned and excluded from ESLint/Prettier; never hand-edit it. (c) Append the apply line to database/migrations-applied.log per the existing ledger.

No sequence and no view is created, so migration-lint's sequence-grant / view-grant rules have nothing to fire on — but run npm run lint:migrations -w tools/migration-lint anyway; it's in check:fast.

7.2 Rendering — and the one deviation from SpecBody

frontend/components/tasks/weekly-plan-view.tsx renders the document exactly the way SpecBody renders a spec, with a single, deliberate difference:

AttributeSpecBody (code module)WeeklyPlanView (this change)Why
sandbox "" — every restriction on "allow-scripts" The plan's own <script> is what highlights today and fills the today card. Inert scripts would gut the feature.
allow-same-origin off off — must stay off Without it the frame gets an opaque origin: its script cannot read app cookies, localStorage, or reach the parent DOM. Adding allow-scripts allow-same-origin together would defeat the sandbox entirely.
srcDoc raw, unsanitized raw, unsanitized Same trust model: the content reaches the DB only through a credential the single owner holds. Sanitizing would strip the styling and scripting that are the artifact.
Height h-[28rem] (fits a modal) flex-1 min-h-[40rem] This is a full page, and ModuleRouter's tasks branch is already flex-1 flex flex-col — the frame fills the remaining viewport.
Background bg-white none — let the document paint The plan ships its own prefers-color-scheme: dark block, so forcing white would break its dark mode.

Not granted: allow-forms, allow-popups, allow-top-navigation, allow-modals. allow-scripts alone still lets the frame make network requests — accepted, since the document is authored by the owner's own tooling.

No layout change is needed. ModuleRouter wraps tasks views in mx-auto w-full max-w-3xl px-4 py-8 (≈736 px of usable width), and the plan document is max-width: 780px with an overflow-x: auto timeline that has a 600 px min-width. It fits and stays readable; leave the shared column alone.

7.3 Layout & states

Week Plan Jul 25 ▾

StateRender
≥ 1 plan Header row: an h1-scale “Week Plan” heading, and — only when there is more than one plan — a picker on the trailing edge listing uploads newest-first. Below it, the sandboxed frame.
Exactly 1 plan Same, with the picker hidden (nothing to pick).
No plans An empty state in the app's existing dashed-border card idiom (as SpecBody uses for a missing spec): one line of explanation plus the curl snippet from §5.4 with the host and key elided. No spinner, no error styling — “not uploaded yet” is a normal state.

Picker labels come from uploaded_at alone (locked decision §2): use formatMonthDay from frontend/lib/date-utils.ts, e.g. Jul 25. It already handles a full timestamptz.

8 · Read path & state

8.1 Server data module

New frontend/lib/data/weekly-plans.ts, mirroring lib/data/items.ts / lib/data/code.ts:

/** Picker index — newest first. Deliberately excludes `html` (see §8.2). */
export async function getWeeklyPlanIndex(): Promise<WeeklyPlanSummary[]>

/** The most recent plan, html included, or undefined when none has been uploaded. */
export async function getLatestWeeklyPlan(): Promise<WeeklyPlan | undefined>

Types WeeklyPlan (id, html, uploaded_at) and WeeklyPlanSummary (id, uploaded_at) go in frontend/lib/types.ts, derived from the regenerated database.types.ts row type like the existing aliases.

8.2 A deliberate exception to “fetch-all, seed-once”

The data-flow skill's house default is fetch everything at the shell layout and filter client-side. This change follows that for the index and breaks it for the documents: each plan is ~40 KB of HTML and the archive grows by one every week, so shipping all of them in the RSC payload would inflate every page load in the app — including the ones that never open /plan. The layout therefore seeds { index, latest }, and an older plan's HTML is pulled on demand and cached in the store. Record this exception in the data-flow skill while implementing.

8.3 Store

New frontend/lib/stores/weekly-plan-store.tsx exposing WeeklyPlanProvider (seeded with initialIndex + initialLatest) and hooks useWeeklyPlanIndex(), useSelectedWeeklyPlan(), useWeeklyPlanActions() (selectPlan(id)).

Build it on frontend/lib/stores/create-context-pair.ts like the other stores, but not on the optimistic-mutation machinery — there is no optimistic write here, only seeded data plus a read-through cache keyed by plan id. Registering the provider in frontend/app/(shell)/layout.tsx means adding the two fetches to the existing Promise.all and nesting one more provider; put it inside ToastProvider so a failed on-demand fetch can toast.

12 · Out of scope / deferred

  • Richer picker labels. The generator emits <title>Week 12: Jul 4 – Jul 11, 2026</title>, so a label like “Week 12” is derivable. The metadata decision (§2) deliberately excludes it. It can be added later with no breaking migration — either derived client-side from the stored html, or as added columns.
  • Persisting the plan's checkboxes. The success-criteria ticks live inside the sandboxed frame and are lost on reload. Making them durable would mean parsing and writing back into the document — a different, larger ticket.
  • Turning plan lines into alfred tasks. No extraction of the day-by-day tasks into items. The plan renders as a document; it does not sync.
  • In-app upload UI. Explicitly declined (§2) — the endpoint is the interface.
  • Deleting or editing an archived plan. Append-only for now; a bad upload is corrected by uploading again (the newest wins as the default view).
  • Automating the upload from the weekly-review skill. That skill lives outside this repo; wiring its final step to curl the new endpoint is a follow-up there, not here.

Open questions

None blocking. The three that mattered — history, upload path, metadata — were resolved with the owner during refinement and are recorded in §2.

13 · Acceptance criteria

  • POST /api/weekly-plans with a valid x-api-key and a text/html body stores the document verbatim and returns 201 with { id, uploaded_at }.
  • The same request with no credential returns 401; with a logged-in session instead of a key it succeeds (same dual path as POST /api/items).
  • A non-text/html content type returns 415; an empty body 400; a body over 1 MB 413; a body that isn't an HTML document 400.
  • GET /api/weekly-plans/[id] requires a session, returns the html for a known id and 404 for an unknown one.
  • Migration 0020_weekly_plans.sql creates the table with RLS enabled, the authenticated full access policy, the explicit DML grants, and the uploaded_at desc index; it is applied and logged in migrations-applied.log.
  • frontend/lib/database.types.ts is regenerated output, not hand-edited, and includes weekly_plans.
  • A Week Plan link sits directly under Priority in the tasks sidebar (and in the mobile drawer), navigates to /plan via ViewLink with no RSC round-trip, and highlights as active on that path.
  • /plan is reachable from the ⌘K palette and survives a hard reload / deep link (server-rendered by the route stub).
  • The view renders the most recent uploaded plan in an <iframe srcDoc> with sandbox="allow-scripts" and without allow-same-origin; the document's own styling and dark mode apply, and its today-highlighting script runs.
  • The plan's CSS does not leak into the app shell, and the app's CSS does not restyle the plan.
  • With more than one plan uploaded, a picker lists them newest-first labelled by upload date; choosing an older one fetches and renders it, and the choice is served from cache on a second visit.
  • With no plan uploaded, the view shows the empty state with the upload instruction — no error, no blank frame.
  • looksLikeHtmlDocument lives in one place and is imported by both spec-body.tsx and the upload handler; the code module's spec iframe still uses sandbox="" and its existing tests pass untouched.
  • Root npm run check is green (type-check, lint/format, unit, migration-lint, skill-lint, Storybook snapshots, Playwright, demo-lint).
  • A demo doc exists under docs/demos/, shows the upload and the rendered plan, passes npm run demo -- verify, and is linked live from the PR description.
