1 · What this story is

ALF-146 §8 splits the habit tracker into twelve slices. ALF-147 is the walking skeleton: the epic's own "earliest genuinely useful stopping point" — slices 1, 2, 3, 6, 7, 8, 10 — plus the minimum needed to make it self-contained (§2, S1). When it merges, the owner can define the reference habit, log a morning, and watch the chain grow. Nothing reads it from outside the app yet, and no statistics are rendered.

2 · Decisions locked during this refinement

These resolve questions the epic left to the story session. They do not reopen any epic decision; where one is load-bearing here it is cited as Dn.

S1POST /api/habits and a create dialog come along

The chosen slices contain no way to create a habit — slice 4 (the CRUD API) and slice 11 (the form) are both deferred. So the POST route and the create half of the form join this story. PATCH, DELETE, and the edit/archive UI stay out.

Why: without them /habits renders an empty state with no exit, slices 8 and 10 have nothing to draw, and no E2E can drive the loop — the skeleton would be unverifiable by the repo's own definition of done. Create is the minimum that closes the loop; editing a habit you just made is a real but separable need, and stopping there keeps this story from swallowing slice 11 whole.

S2The app reads through the shell seed, never through an API route

lib/data/habits.ts is read by the (shell) layout and seeded into HabitsProvider. No habits reader is added to lib/api-client.ts in this story, and GET /api/habits is not built.

Why: D8's read endpoint exists for the coach — a consumer that can't run the shell layout. The app itself follows the house data-flow exactly (server fetch → provider → optimistic writes), so building the endpoint now would ship a second read path with no caller. Slice 5 adds it when the coach needs it.

S3The only status a caller may state is skipped

PUT …/entries derives and freezes the status from results (D3, D12). A request body may carry status: 'skipped' — and nothing else. Any other explicit status is a 400.

Why: D12 freezes the status and stores the raw results beside it, so history stays chartable. Honouring a hand-typed met would let those two disagree permanently, with no way to tell later which was true. skipped is the one status the model genuinely cannot derive, which is exactly why it is the one exception. The epic's API table names only skipped; this makes that exhaustive rather than illustrative.

S4The browser always sends an explicit date

Every write from the app names the day it means. The tz-resolved "today" default (D11) stays in the route for the keyed callers — the coach and a Shortcut — that can't compute one.

Why: the client already knows which cell was tapped, so deriving it again server-side can only introduce disagreement. It also keeps the one genuinely awkward case — the shell renders on the server, which does not know the browser's zone — confined to a single highlight in the grid (§7.2) instead of leaking into the write path.

S5The streak engine ships whole, even though only part of it renders

lib/habits lands complete: the per-day calendar projection the grid draws and the scalar statistics (current / longest / average streak, allowance remaining, hit rate, cumulative met days, formation stage) that slice 9 will render later.

Why: the grid's connectors are the streak walk made visible — a link is drawn exactly where the walk continues, and greyed exactly where it spent allowance (D4, D5). Shipping "just enough walk to draw links" would mean writing the same rolling-window logic twice and risking the two disagreeing, which is the failure D8/D9 exist to prevent. One walk, one set of table-tests, two consumers — the second arriving a ticket later.

4 · Database

One migration, taking the next available number — never one pinned here. Apply it and append the row to database/migrations-applied.log the way 0021/0022 did, then regenerate database.types.ts against a local cluster built from database/migrations/, not prod introspection (the supabase skill records why).

4.1 The migration

create type habit_day_status as enum ('met', 'partial', 'missed', 'skipped');

create table habits (
  id           uuid primary key default gen_random_uuid(),
  name         text not null,
  notes        text,
  criteria     jsonb not null,
  active_days  smallint[] not null default '{1,2,3,4,5,6,7}',
  allowance    smallint not null default 0,
  started_on   date not null default current_date,
  archived_at  timestamptz,
  sort_order   int,
  created_at   timestamptz not null default now(),

  -- 1..n criteria, always an array (D3, D10). The per-criterion shape is validated by zod at
  -- the route, not here: a check constraint over jsonb would duplicate that rule in a second
  -- language and drift from it.
  constraint habits_criteria_non_empty
    check (jsonb_typeof(criteria) = 'array' and jsonb_array_length(criteria) >= 1),
  -- ISO weekdays only, at least one (D4).
  constraint habits_active_days_valid
    check (active_days <@ array[1,2,3,4,5,6,7]::smallint[] and array_length(active_days, 1) >= 1),
  -- A rolling window is 7 days, so forgiving 8 is meaningless rather than merely generous.
  constraint habits_allowance_range check (allowance between 0 and 7)
);

create table habit_entries (
  id          uuid primary key default gen_random_uuid(),
  habit_id    uuid not null references habits(id) on delete cascade,
  entry_date  date not null,
  status      habit_day_status not null,
  results     jsonb,
  note        text,
  created_at  timestamptz not null default now(),
  updated_at  timestamptz not null default now(),
  -- Load-bearing: this is what makes the write path a plain upsert, so logging is idempotent
  -- and correcting a day is the same call as making it.
  unique (habit_id, entry_date)
);

-- The only query shape: one habit's window, newest first.
create index habit_entries_habit_date_idx on habit_entries (habit_id, entry_date desc);

habits carries no index beyond its primary key — at a handful of rows the sequential scan is free, and D14's "no grouping" means there is no second access path to serve. updated_at has no trigger: this repo sets it from the writer (as code_items does), so the entries route stamps it explicitly.

4.2 RLS and grants

alter table habits        enable row level security;
alter table habit_entries enable row level security;

create policy "authenticated full access" on habits
  for all to authenticated using (true) with check (true);
create policy "authenticated full access" on habit_entries
  for all to authenticated using (true) with check (true);

grant select, insert, update, delete on habits        to anon, authenticated, service_role;
grant select, insert, update, delete on habit_entries to anon, authenticated, service_role;
RLS gates rows; grant gates whether the role may touch the table at all. Raw psql -f gets none of Supabase's auto-grants, so omitting these produces a runtime "permission denied" from the Data API — exactly what migration-lint catches at commit time. Both primary keys are gen_random_uuid(), so there is no sequence to grant.

4.3 The seed readers

frontend/lib/data/habits.ts, server-only, in the shape of lib/data/weekly-plans.ts — the closest precedent, because it too deliberately seeds a bounded slice rather than everything: 

/** Active habits in display order. Archived ones are excluded — nothing renders them yet. */
export async function getHabits(): Promise<Habit[]>

/**
 * Entries for every habit over a bounded trailing window (ALF-146 §4.3): ENTRY_WINDOW_DAYS
 * back from today, inclusive. A daily habit grows a few hundred rows per year per habit, which
 * is the point at which the shell's "fetch everything" default stops holding.
 */
export async function getHabitEntries(windowDays?: number): Promise<HabitEntry[]>

ENTRY_WINDOW_DAYS = 120, matching the epic. The window is computed in UTC on the server and deliberately generous, so whichever side of midnight the browser's zone is on, today's row is always inside it (§7.2). Both readers swallow the Supabase error and fall back to [], like getFolders — a seed failure must not blank the whole shell.

5 · lib/habits — the pure module

Dependency-free TypeScript beside lib/recurrence and lib/priority, with a barrel index.ts. Every export is a pure function of (habit definition, entries, today). No Date arithmetic on instants: all dates are YYYY-MM-DD strings, because a wake-time habit is precisely where an instant re-read in the wrong zone lands on the previous day (D11).

5.1 Types

export type CriterionKind = 'boolean' | 'time' | 'count' | 'duration';
export type Comparator    = 'lte' | 'gte' | 'eq';

export interface BooleanCriterion  { key: string; label: string; kind: 'boolean' }
export interface MeasuredCriterion {
  key: string; label: string;
  kind: 'time' | 'count' | 'duration';
  target: number;          // minutes after local midnight for 'time' (375 = 06:15)
  comparator: Comparator;
}
export type HabitCriterion = BooleanCriterion | MeasuredCriterion;

/** Keyed by criterion key (D10). A key with no entry is *unrecorded*, not false. */
export type HabitResults = Record<string, boolean | number>;

export type DerivedStatus = 'met' | 'partial' | 'missed';        // never 'skipped'
export type CellStatus    = HabitDayStatus | 'unknown' | 'not_applicable';

A time criterion stores minutes after local midnight as an integer, rendered HH:MM. A Postgres time column would drag zone semantics back into a model D11 keeps zone-free.

5.2 Criterion evaluation (slice 2)

/** 'unrecorded' when the key is absent or the stored value doesn't match the kind. */
export function evaluateCriterion(
  criterion: HabitCriterion,
  value: boolean | number | undefined,
): 'pass' | 'fail' | 'unrecorded';

/** Every criterion is required (D3), so an unrecorded one is simply not a pass. */
export function deriveDayStatus(
  criteria: HabitCriterion[],
  results: HabitResults,
): DerivedStatus;
KindPasses when
booleanthe stored value is true
time / count / durationlte: value ≤ target · gte: value ≥ target · eq: value === target

deriveDayStatus: all pass → met; at least one pass and at least one not → partial; none pass → missed. The three-way pass/fail/unrecorded return exists for the editor, which must render an empty field rather than a ✕ for a criterion the owner hasn't touched yet — the derivation itself folds unrecorded into "not a pass".

Orphaned keys are ignored, never fatal. D10 accepts no referential integrity between criteria and results: a criterion deleted later leaves stale keys in old rows. Evaluation iterates the criteria and looks each key up — so extra keys in results are simply never read.

5.3 The streak engine (slice 3)

Every rule below is ALF-146 §3.1 — read it there; this section says only what the module exposes. It is the riskiest logic in the epic and gets near-exhaustive table tests (§11). 

export interface HabitDay {

  allowanceRemaining: number;
  hitRate: number | null;                        // null when the denominator is 0
  metDaysTotal: number;
  stage: 'fully_deliberate' | 'gaining_momentum' | 'nearing_automaticity' | 'possibly_established';
  counts: { met: number; partial: number; missed: number; skipped: number; unknown: number };
}

/** The per-day projection the grid renders — one entry per date in [from, to]. */
export function buildHabitCalendar(
  habit: Habit,
  entries: HabitEntry[],
  range: { from: string; to: string; today: string },
): HabitDay[];

/** The scalars. `metDaysTotal` / `longestStreak` are all-history figures (§5.4). */
export function computeHabitStats(
  habit: Habit,
  entries: HabitEntry[],
  today: string,
): HabitStats;

link is the whole point of exposing a per-day projection. A day emits streak when the walk continues into the next applicable day on the strength of a met; bridge when it continues only because the rolling allowance absorbed a spent day (D4, D5); none when the run ends there. §8 renders those three values and invents nothing.

5.4 A note the store depends on

metDaysTotal and longestStreak are all-history figures and the seed is a 120-day window, so the module cannot derive them correctly from what the store holds. Nothing in this story renders them (slice 9 is deferred), so they are computed over the seeded window and the limitation is recorded in the module's doc comment. Slice 5 introduces the precomputed scalars the epic describes; that is the ticket where the distinction starts to matter. Do not build a second, unused scalar channel now.

5.5 Dates

export function todayIn(timezone: string): string;      // unknown zone → UTC, never a throw
export function isoWeekday(date: string): 1|2|3|4|5|6|7; // 1 = Monday
export function addDays(date: string, delta: number): string;
export function eachDay(from: string, to: string): string[];

todayIn uses the same Intl.DateTimeFormat validity probe as lib/github/week.ts (constructing the formatter throws on an unknown zone, which is the test) and degrades to UTC exactly as pr-ratio does. The two live in different modules on purpose — lib/github/week.ts resolves instants with offsets for a GitHub query string, this resolves a calendar date. Sharing one helper would couple a habit's day boundary to the PR-ratio window's, which is the coupling D11 warns about.

6.2 PUT /api/habits/[id]/entries — session or API key

The epic's D7 path, via resolveIngestClient (a valid key resolves the admin client; otherwise a session; otherwise 401). Body: 

{ "date"?: "2026-07-27", "tz"?: "America/New_York",
  "results"?: { "wake": 364, "light": true },
  "status"?: "skipped",
  "note"?: string | null }
  1. parseUUID the [id]; load the habit (its criteria, started_on, archived_at) or 404.
  2. Resolve the date: date if given, else todayIn(tz ?? 'UTC') (D11, S4).
  3. Reject 400 when the date is in the future relative to that same resolution, or precedes started_on — neither is a day this habit can have an outcome for.
  4. Resolve the status: skipped if stated (S3 — any other explicit status is 400), else deriveDayStatus(criteria, results). A body carrying neither results nor status is 400: there is nothing to record.
  5. Upsert on (habit_id, entry_date), stamping updated_at. Return the row.
The upsert is the correction path. Re-logging a day overwrites its results and re-freezes its status — that is D12 working as intended (the verdict is frozen against later criteria edits, not against the owner fixing what they typed). There is no delete-an-entry route in this story; §13 records the gap.

7 · Store & shell wiring (slice 7)

7.1 HabitsProvider

A createContextPair store in the house shape, with runOptimisticMutation doing the optimistic → reconcile → rollback dance and a toast on failure (see the data-flow skill). It sits inside ToastProvider like the other optimistic stores. 

interface HabitsState {
  habits: Habit[];
  /** habitId → (YYYY-MM-DD → entry). A map, not a list: every read is "this habit, this day". */
  entries: Record<string, Record<string, HabitEntry>>;
  /** The owner's local today, corrected on mount (§7.2). */
  today: string;
}

interface HabitsActions {
  addHabit: (input: CreateHabitInput) => Promise<Habit>;
  /** Log or correct a day. Derives the optimistic status locally with `deriveDayStatus`. */
  logDay: (habitId: string, date: string, results: HabitResults, note?: string | null) => Promise<void>;
  /** Excuse a day (D3) — the one status the model can't derive. */
  skipDay: (habitId: string, date: string) => Promise<void>;
}

Selectors: useHabits(), useHabitEntries(habitId), useHabitsToday(), useHabitActions(), and useUnloggedTodayCount() for the nav badge — habits where today isApplicableDay and no entry exists. The optimistic status the store writes uses the same deriveDayStatus the route will, so reconcile is a no-op in the normal case (S5).

7.2 The one genuinely awkward bit: whose "today"?

The shell renders on the server, which does not know the browser's zone, but the grid highlights today and the badge counts today's unlogged habits. Seeding a server-computed date and rendering it directly would be a hydration mismatch for any owner not on UTC.

So: the provider initializes today from the server's UTC date and corrects it in a mount effect from Intl.DateTimeFormat().resolvedOptions().timeZone. First paint matches the server, the correction lands before the owner can act, and the seeded 120-day window is generous enough that the corrected date is always already in hand (§4.3). Writes are unaffected — they always name their date explicitly (S4).

8 · The history grid (slice 8)

ALF-146 §6 settled this design; build it rather than re-deriving it. §6.1's two connector refinements are behavioural — each fixes a way the plain bar misstates §3 — so they are acceptance criteria, not polish.

8.1 Structure

A CSS grid, grid-auto-flow: column over grid-template-rows: repeat(7, …): weekdays down, ISO weeks across. The rendered range is the seeded window, padded forward to the end of the current week so today never sits on the trailing edge. Each cell is a relative wrapper holding the day square plus up to two absolutely-positioned connector spans, driven purely by HabitDay.link and the day's isoWeekday:

ConnectorRendered whenColour
down-barlink !== 'none' and the day is not Sundaystreak → met · bridge → bridge grey
wrap-out stublink !== 'none' and the day is Sundaysame
wrap-in stubthe day is Monday and the previous day's link is not nonesame as that previous day's link
A forgiven day's links are full-width and grey — never dashed (§6.1). Same weight, same geometry, colour only. A dash reads as weaker or uncertain; a run across a forgiven day is neither — it is unbroken, it simply wasn't earned.

8.2 What it looks like — pick the finish

The reference habit over five weeks — allowance: 1, criteria "up by 6:15" and "outside for light". Week two contains a forgiven partial (grey links either side, run survives). Week three is a real break: a forgiven missed on Thursday, then an unlogged Friday — two spent days in one rolling window exceeds the allowance, so no link leaves Thursday. The live run then goes from that Saturday to today.

9 · The remaining UI

9.1 /habits

A page header with a New habit button, then one card per habit — name, a cadence summary ("every day · 1 miss / rolling week"), and the grid. No stats rail: slice 9 owns it, and the card is laid out so the rail can be dropped in beside the grid without moving anything else.

9.2 The day editor (slice 10)

Tapping any applicable cell — today or a backfill — opens a Popover anchored to it. The verdict in the header is computed, never typed.

Thu 23 Jul Partial Up by 6:1506:04 Outside for light✕ Spends this week's allowance ⋯
  • One row per criterion. boolean → a tri-state CheckboxButton (unrecorded → ✓ → ✕); time → an <input type="time"> mapped to minutes after midnight; count / duration → a number field.
  • No Save button. Booleans commit on toggle; measured fields commit on blur or Enter, debounced through useDebouncedCallback so a typed time costs one request. Each commit is one logDay — the store's optimistic patch repaints the cell and the connectors around it immediately.
  • The header re-derives on every change via deriveDayStatus, so it cannot be made to disagree with the criteria beneath it — that is what "derived only" buys (D3).
  • The allowance line appears whenever the derived status isn't met, naming the consequence in the owner's terms (D5).
  • The ⋯ overflow holds Mark as skipped — the one status the model can't derive, kept out of the main flow so it isn't a fourth thing to tap past every morning.

9.3 The create dialog — a sentence builder

A FormDialog opened from the page header and from the empty state, collecting exactly what POST /api/habits takes: name, criteria (≥ 1; label + kind, and for a measured kind a comparator + target), the weekday set, and the allowance. Submitting calls addHabit; the habit appears in the list optimistically and the dialog closes.

Settled: the form is one editable sentence, not a stacked field list. Each underlined slot is a real control that opens a small popover and writes its result back inline:

Morning routine
Every day I will be up by 06:15 and get outside for light +
forgiving 1 miss a week.
Accessibility is the cost of this shape, and it is not optional. A sentence is not a form: every slot needs a genuine control with a programmatic label (not a <span onClick>), a visible focus ring, and a keyboard path that reaches it in reading order. The sentence must also reflow to two or three lines on a phone without the slots losing their inline meaning. Budget for this — it is the reason this shape was the most expensive of the three considered.

13 · Out of scope & open questions

Everything ALF-146 §7 rules out stays ruled out. Beyond the deferred slices listed in §1:

  1. Clearing an entry back to unknown. The editor can correct a day (re-upsert) and excuse it (skipped), but not un-log it — the epic's API surface has no delete-entry route, and inventing one here would pre-empt slice 4's shape. A mis-tap is recoverable by correcting or skipping the day. If that proves annoying in use, a DELETE on the entries route is a small additive change.
  2. Editing a habit after creation. Deliberate (S1) — PATCH and the edit/archive UI are slice 4/11's remainder. Until then a wrong allowance or target means creating the habit again. Worth watching: if the first week of real use hits this, that ticket jumps the queue.
  3. The window boundary is untested at scale. 120 days is the epic's number and this story honours it, but nothing here proves the "scroll further back is an on-demand fetch" story, because with a habit created today there is nothing behind the window to fetch. It becomes real around four months in.
  4. Does the partial rule feel right in practice? ALF-146 §9 already defers this; this story is what starts generating the data to answer it.

14 · Acceptance criteria

Database

  • Migration creates habit_day_status, habits and habit_entries with the checks, the unique constraint, the index, RLS policies and explicit grants — takes the next free number, is applied, and is recorded in migrations-applied.log.
  • database.types.ts is regenerated from the repo's own migrations and committed verbatim, with no unrelated tables swept in.

Pure logic

  • Criterion evaluation handles all four kinds and three comparators, and reports a missing or wrong-typed value as unrecorded rather than false.
  • Day status derives as all-pass → met, some-pass → partial, none-pass → missed, and is never derived as skipped.
  • The streak walk implements ALF-146 §3.1 exactly: applicable days only, the rolling allowance, skipped stepped over, today exempt, and a count of met days rather than elapsed days.
  • buildHabitCalendar returns a link per day distinguishing an earned continuation from a forgiven one, and the grid renders nothing the walk didn't say.

API

  • POST /api/habits creates a habit with ≥ 1 criterion, rejects every malformed criteria shape, and is session-only.
  • PUT /api/habits/[id]/entries upserts one day, derives and freezes its status, accepts skipped as the only explicit status, rejects a future date and one before started_on, and accepts either a session or the INGEST_API_KEY.
  • Logging the same day twice leaves one row, with the second write winning.

App

  • /habits exists in the Tasks module: reachable from the sidebar beneath Week Plan, from ⌘K, and by deep link / hard reload.
  • The nav badge counts today's applicable-but-unlogged habits and disappears at zero.
  • A habit can be created in the app — name, ≥ 1 criterion, weekday set, allowance — and appears without a page refresh.
  • The create form is the sentence builder (§9.3), and every slot is a real labelled control reachable by keyboard in reading order, with the sentence reflowing on a phone without a slot losing its inline meaning.
  • The grid renders weeks as columns, with earned links, full-width grey forgiven links, and stubs at both ends of a Sunday→Monday crossing.
  • Tapping a day opens the editor, whose status header is derived live and cannot be typed; skipped is reachable only from the overflow.
  • A logged day repaints immediately and survives a reload; a failed write rolls the cell back and toasts.
  • Every cell is keyboard-reachable with an accessible name carrying date, status and per-criterion results, and every state is distinguishable without colour.

Gates

  • npm run check is green — including migration-lint, the Storybook baselines and the E2E suite — with no config weakened and no ignore directive added.
  • A demo doc exercises every criterion above and passes npm run demo -- verify.
