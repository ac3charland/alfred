ALF-148 — Habit read endpoints for the productivity coach

Implementation spec. Epic context and every settled decision live in docs/specs/epics/ALF-146.html — read it first; this document does not restate it. The walking skeleton it builds on is specified in docs/specs/ALF-147.html.

Depends on ALF-147 having merged. The schema (habits, habit_entries), the pure lib/habits module, and PUT /api/habits/[id]/entries all ship there. ALF-148 adds no migration and no new UI: it is one GET handler, one paging read, two small additions to lib/habits, and the primer section that turns the whole thing into something the coach can actually call.

1 · What this story is

ALF-146 §8 splits the habit tracker into twelve slices. ALF-148 is slice 5 (the read API) and slice 12 (the coach integration), taken together — because slice 5 alone ships an endpoint nobody knows how to call, and slice 12 is the document the coach's alfred skill is generated from. The epic says as much: the primer gaining a third endpoint section is "part of the epic's definition of done — not a docs afterthought".

SliceWhat lands hereWhere it's specified
5GET /api/habits — definitions + a window of entries + every derived statistic, dual auth§4–§6
12docs/productivity-coach-primer.md — the read endpoint and the entry-upsert write path ALF-147 shipped, each with a reference script§7

On the ticket's plural "endpoints". There is one new route (§4, S1). The coach's surface grows by two endpoints, because ALF-148 is also what documents PUT /api/habits/[id]/entries — built in ALF-147, undocumented until now, and useless to the coach without the read (S7). Read + write is the loop the epic opened in D7/D8.

Unchanged and deliberately so: slice 9 (the stats rail), the rest of slice 4 (PATCH/DELETE) and slice 11 (edit/archive UI) stay deferred, and the app's own read path is untouched (S5).

2 · Decisions locked during this refinement

These resolve questions the epic left to the story session. They reopen no epic decision; where one is load-bearing it is cited as Dn, and ALF-147's as Sn (147).

S1One route, one payload — no per-habit and no digest endpoint

GET /api/habits returns every habit, its window of entries, and all of its derived numbers. There is no GET /api/habits/[id] and no summary/digest route.

Why: D8 exists to ship one authority for numbers whose rules (D4, D5) are subtle enough that a second derivation would disagree with the first — and a second route is a second place for that to happen. The precedent is /api/code/pr-ratio, which returns pre-rounded percentages "so they can be quoted directly". At the expected volume (a handful of habits, a few hundred entries each) one call answers the Friday review completely; a digest that saves the coach some JSON parsing is not worth a second contract to keep true.

S2resolveIngestClient, not withSessionOrApiKey

The handler resolves its Supabase client with resolveIngestClient(request) — the same wrapper PUT …/entries and POST /api/items use. A valid key yields the admin client; otherwise a session yields the session client; otherwise 401.

Why: withSessionOrApiKey is the obvious-looking choice (it is what pr-ratio — the existing dual-auth read — uses) and it is the wrong one here: it deliberately yields no Supabase client, because pr-ratio reads GitHub rather than the database. A keyed caller carries no cookie, so a route that reaches for createClient() under it gets an anonymous client and RLS-empty results — a 200 with habits: [], which reads as "no habits" rather than as a failure. This is the single easiest thing to get wrong in this story.

S3Scalars are all-history; the rate and counts are the window

The route reads every entry a habit has, computes the streak scalars over all of it, and uses the requested window only to (a) choose which entries the payload carries and (b) scope hit_rate and the five status counts. computeHabitStats gains an optional window argument for exactly that (§6.1).

Why: D6 makes met_days_total and the formation stage cumulative-forever figures, and D8 says the endpoint returns them — so anything less than full history is a wrong number, and ALF-147 §5.4 explicitly parks the problem here ("Slice 5 introduces the precomputed scalars … that is the ticket where the distinction starts to matter"). Hit rate is the one figure the epic scopes to the window (§3.1), because "how am I doing lately" is the question it answers. Both bases in one payload is fine as long as the contract says which is which — §4.4 and the primer table both do.

S4The entry read is paged, and truncation is a loud failure

habit_entries is read in pages of PAGE_SIZE = 1000 via .range() until a short page arrives. A run that never terminates within MAX_PAGES returns 500.

Why: PostgREST caps rows per response (Supabase's project-level Max rows, 1000 by default) and the cap silently truncates — a .limit(50000) does not lift it. One daily habit crosses 1000 entries at about two years nine months, and the symptom would be a quietly shrinking met_days_total and longest_streak: numbers the coach then states to the owner with full confidence. That is the worst failure this endpoint can have, so the loop is not an optimization to defer. The MAX_PAGES guard exists so the one remaining way to lose rows — a backend that never returns a short page — fails rather than truncating.

S5The app's read path does not change

The shell still seeds HabitsProvider from lib/data/habits.ts's 120-day window (ALF-147 S2). Nothing in the app calls this route, and no all-history scalar is plumbed into the store.

Why: nothing renders those scalars until slice 9 (the stats rail), and ALF-147 §5.4 is explicit — "do not build a second, unused scalar channel now". What ALF-148 does owe slice 9 is a reader it can reuse: getHabitsWithHistory (§5) takes an injected client and surfaces errors, so slice 9 wires it into the seed without writing new logic.

S6The payload is a projection, not a row dump

Entries carry { date, status, results, note }. Row id, habit_id, created_at and updated_at stay server-side. The habit object carries the epic's fields and no more.

Why: the payload is a published contract read by a consumer outside this repo, so every key in it is a key that can't change quietly. Row identity is internal — the coach addresses a day by (habit id, date), which is exactly what the upsert route takes — and at a few hundred entries per habit, dropping four columns is real bytes too. §4.3 is the shape; ALF-146 §5's sketch is where it comes from.

S7The primer documents the write path too, and says the key got wider

docs/productivity-coach-primer.md gains two endpoint sections — the read (this story) and PUT /api/habits/[id]/entries (ALF-147's) — plus a reference script each, and a plain statement that INGEST_API_KEY now also reads and writes habit data.

Why: the primer's own framing is "everything the coach needs is here", and a coach that can read a streak but can't log the morning it just heard about closes nothing. The two arrived in different tickets; the document has no reason to reflect that. The key's widened blast radius is called out because the primer currently tells the reader the key "cannot read tasks, plans, or anything else" — after this it can read and write habits, and ALF-146 §7 asks for that to be stated plainly rather than drifting.

S8A bad zone falls back; a future to clamps; both are echoed

An unrecognized tz resolves to UTC without erroring, and a to after today is pulled back to today. The response echoes the timezone and the window it actually used. Contradictory input — from after to, or a span over MAX_WINDOW_DAYS — is a 400.

Why: the fallback is the established convention (pr-ratio does it, and the primer already documents it, so a second rule would be a second thing to learn). Clamping rather than erroring on a future to keeps the obvious call — "give me this quarter" past quarter-end — working. Echoing is what makes both honest: a caller that got UTC or a shortened window can see it in the response instead of misreading the numbers. Erroring on from > to is different in kind — there is no sensible window to guess at.

4 · GET /api/habits

4.1 Auth

Session or INGEST_API_KEY, via resolveIngestClient (S2, D7). The precedence rules are validateApiKey's and are inherited, not re-implemented: a present x-api-key wins outright (so a wrong one fails even beside a correct bearer token), and an empty value is a mismatch rather than an absent header. Failure is 401 {"error":"Unauthorized"}.

4.2 Query parameters

ParamShapeDefault & rules
tzIANA zone string UTC. Unrecognized → UTC, never an error (S8). Decides today, which decides the default window, the future-clamp and the today-exemption in the streak walk.
fromz.iso.date() to − (DEFAULT_WINDOW_DAYS − 1), i.e. a trailing quarter. Bounds the entries returned and the hit_rate/counts window only.
toz.iso.date() today in tz. A later date clamps back to today (S8).
include_archived'true' | 'false' false. Anything else is a 400 — not z.coerce.boolean(), under which Boolean('false') === true and the caller silently gets the opposite of what they asked for. 
// lib/api/schemas.ts — beside prRatioQuerySchema
export const habitsQuerySchema = z
  .object({
    tz: z.string().optional(),
    from: z.iso.date().optional(),
    to: z.iso.date().optional(),
    include_archived: z.enum(['true', 'false']).optional(),
  })
  // Only the both-present case is decidable here; the rest of the window rules need `today`,
  // so they live in resolveWindow() where they can be table-tested (§6.2).
  .refine((q) => q.from === undefined || q.to === undefined || q.from <= q.to, {
    message: '`from` must not be after `to`',
  });

DEFAULT_WINDOW_DAYS = 90 — a quarter, matching the epic's own framing of a habit's horizon (§6.2's card shows one) and the review cadence that reads it. MAX_WINDOW_DAYS = 366 bounds the response; a longer span is a 400 naming the cap rather than a silently trimmed answer. Neither cap touches the scalars — those are always all-history (S3).

4.3 What the handler does, in order

  1. resolveIngestClient(request) → early-return the Response it may hand back.
  2. parseQueryParams(request, habitsQuerySchema) → early-return its 400.
  3. zone = resolveTimezone(query.tz ?? 'UTC'); today = todayIn(zone). The resolved zone — not the requested one — is what the payload echoes (S8).
  4. resolveWindow(query, today) → { from, to } or a validation failure → 400 (§6.2).
  5. getHabitsWithHistory(supabase, { includeArchived }) → habits in display order plus every entry, grouped by habit (§5). A PostgrestError goes through mapSupabaseError.
  6. Per habit: computeHabitStats(habit, entries, today, window), then project the entries inside the window, newest first.
  7. jsonOk(toHabitsPayload({ today, timezone: zone, window, habits })).

No caching layer, and no revalidate/dynamic export: the handler reads cookies or headers for auth on every call, which already makes it dynamic, and unlike pr-ratio there is no rate-limited upstream to protect — the numbers come from our own database and must be current the moment a day is logged.

Key names and layout follow ALF-146 §5's sketch verbatim — including the counts sitting flat inside stats — so the contract the epic advertised is the contract that ships. What the sketch could not say is which figure is measured over what, and mixing the two bases in one object is precisely where a consumer goes wrong:

FieldBasisNotes
current_streakall historyCounts met days, not elapsed days — a run bridged over a forgiven day reads one lower than the calendar span (ALF-146 §3.1).
longest_streakall history
average_streakall historyMean of completed runs, excluding the one in progress. null until a run has ended. Rounded to 1 dp.
allowance_remainingtrailing 7 daysIts own fixed window by definition (D4) — unaffected by from/to.
met_days_totalall historyWhat the formation stage is keyed to (D6). Never decreases.
stageall historyOne of fully_deliberate · gaining_momentum · nearing_automaticity · possibly_established.
hit_ratewindowmet / (met + partial + missed); unknown and skipped days are on neither side (D5). null when the denominator is 0. Rounded to 3 dp.
met … unknownwindowApplicable days only. unknown = applicable, in-window, no entry — so it is well-defined only because the window is explicit.
entrieswindowNewest first. Only days with a row; a day with no entry simply isn't there.

Rounding is the serializer's job, not the engine's (§6.3): computeHabitStats keeps full precision for the store, and the payload rounds so the coach can quote a figure without re-deriving it — the same reason pr-ratio pre-rounds its percentages.

Deliberately absent: the per-day calendar buildHabitCalendar produces. It exists to drive the grid's connectors, it inflates the payload by every non-applicable and unknown day in the range, and no consumer outside the UI can do anything with a link value.

4.5 Statuses

StatusMeaning
200The payload above. No habits is a 200 with habits: [] — a real answer, not an error.
400Unparseable from/to, from after to, a span over MAX_WINDOW_DAYS, or an include_archived that isn't true/false. Carries details from zod where zod rejected it.
401Missing, empty or wrong key, and no session.
500The database read failed, or paging hit MAX_PAGES (S4). Never an empty list standing in for a failure.

There is no 501/502 here — those exist on pr-ratio because it depends on configuration and on GitHub. This route depends on neither.

5 · The read layer

// frontend/lib/data/habits.ts — alongside ALF-147's getHabits() / getHabitEntries()

/**
 * Every habit (optionally including archived ones) plus its ENTIRE entry history.
 *
 * Takes the client rather than creating one: this serves a dual-auth route, where a keyed
 * caller has no cookie session and must read through the admin client (S2).
 *
 * Surfaces the error rather than falling back to `[]` like the shell seeders do: a seed
 * failure must not blank the app, but an API that answers "no habits" when the database is
 * unreachable tells the coach the owner did nothing this week.
 */
export async function getHabitsWithHistory(
  supabase: SupabaseClient<Database>,
  options: { includeArchived: boolean },
): Promise<{ habits: Habit[]; entriesByHabit: Map<string, HabitEntry[]>; error: PostgrestError | null }>;
  • Order: archived_at nulls first, then sort_order (nulls last), then created_at — so the active habits come back in exactly the order the app shows them, whether or not archived ones are included, and the coach lists them the way the owner sees them.
  • Entries: one query filtered by the habit ids just read, ordered (habit_id, entry_date desc) — a deterministic order is what makes paging safe — then grouped into the map. Skip the query entirely when there are no habits rather than sending an empty in.().
  • Paging (S4): .range(offset, offset + PAGE_SIZE - 1) in a loop; stop when a page comes back shorter than PAGE_SIZE; return an error after MAX_PAGES. Keep the loop in a small named helper so it can be unit-tested against a stub that returns a full page then a short one.
  • No window filter. The scalars need all of it (S3), and the route slices for the payload. Revisit only if entry volume ever makes the full read expensive — at which point the answer is a SQL rollup of the all-history scalars, not a truncated read.

6 · lib/habits additions

6.1 computeHabitStats takes an optional window

export interface StatsWindow { from: string; to: string }   // inclusive, YYYY-MM-DD

export function computeHabitStats(
  habit: Habit,
  entries: HabitEntry[],      // all history — order-independent
  today: string,
  window?: StatsWindow,       // NEW: scopes hitRate + counts only
): HabitStats;
  • currentStreak, longestStreak, averageStreak, allowanceRemaining, metDaysTotal, stage — computed over every entry passed, ignoring window.
  • counts and hitRate — over applicable days in window, intersected with [started_on, today] so a window reaching before the habit existed or past today adds no phantom unknown days.
  • Omitting window keeps ALF-147's behaviour exactly, so the store's 3-argument call sites are untouched.

If the implementation session finds ALF-147 shipped a different arity or an options object, adapt to what is there — the requirement is the semantics above, not the signature.

6.2 Two date helpers

/** The zone that will actually be used: the argument, or 'UTC' when it isn't a valid IANA zone. */
export function resolveTimezone(timezone: string): string;

/** Resolve + validate the requested window against `today`. */
export function resolveWindow(
  query: { from?: string; to?: string },
  today: string,
): { from: string; to: string } | { error: string };

todayIn is refactored to call resolveTimezone — no behaviour change, but the route can now report the zone it fell back to instead of echoing a bad one back at the caller (S8). resolveWindow owns the rules that need today: default to, clamp a future to, default from from DEFAULT_WINDOW_DAYS, reject from after the clamped to, reject a span over MAX_WINDOW_DAYS. It is pure and table-tested; the handler stays a list of early returns.

6.3 toHabitsPayload

The camelCase-to-snake_case, round, and project step (§4.4) in one pure function, so the published contract has a single place it is produced and a single place it is tested. It is the only code that knows the payload's key names; the route just calls it.

7 · The coach primer (slice 12)

docs/productivity-coach-primer.md is the contract the coach's alfred skill is generated from. Match its existing voice and structure exactly — numbered endpoint sections, a "Statuses to handle" table each, a reading-the-payload list, and a bundled script with hardcoded placeholders. Additions:

  • The intro list gains two capabilities: read habit data, and log a habit day.
  • Endpoint 3 — GET /api/habits. Request example with tz and a window; the payload from §4.4; the all-history vs window table (§4.4) restated in the primer's own terms, because that is the one thing a consumer cannot infer; the status table from §4.5.
  • Endpoint 4 — PUT /api/habits/[id]/entries (ALF-147, previously undocumented). The evidence-not-verdict rule (ALF-147 S3): send results and let the server derive the status; "skipped" is the only status a caller may state, and it requires a non-empty reason in note (S6 there). date omitted means today in tz; a future date or one before started_on is a 400; re-writing a day is the correction path.
  • Two reference scripts in the shape of the existing pair — hardcoded ALFRED_BASE_URL/ALFRED_API_KEY, set -euo pipefail, curl --fail-with-body --silent --show-error so a 4xx still prints alfred's error envelope: 
    habits.sh   [IANA timezone] [from] [to]    # GET /api/habits
log-habit.sh <habit-id> <results-json> [date]  # PUT /api/habits/<id>/entries
  • Reading notes the coach will otherwise get wrong. The streak counts met days, not elapsed days. unknown is a day never logged and costs allowance exactly like a miss (D5) — but sits in neither side of the hit rate. skipped is excused and costs nothing. stage is deliberately approximate: report "Possibly Established", never "Established" (D6).
  • The key's blast radius. The primer currently says the key "cannot read tasks, plans, or anything else". After this it reads and writes habit data — say so where the key is introduced (ALF-146 §7).
  • Out of scope, updated. Creating, editing or archiving a habit is session-only — the coach logs days against habits the owner defined in the app.

Regenerating the coach's own skill from the updated primer happens in the coach's chat, not in this repo — this story ships the document that makes it possible.

10 · Out of scope & open questions

Everything ALF-146 §7 rules out stays ruled out. Beyond that:

  • Habit CRUD by key. POST stays session-only and PATCH/DELETE remain unbuilt (slice 4). D7 widened the key for logging, not for defining entities.
  • The stats rail. Slice 9 still owns rendering these numbers in the app; this story only makes them correct over all history and reusable (S5).
  • Response pagination. The window caps the payload; there is no cursor. If a caller ever needs multi-year entry data in one response, that is a paging contract to design, not a cap to quietly raise.
  • Caching. None (§4.3). pr-ratio caches because GitHub rate-limits; our database doesn't.

Open questions

  • Is a windowed hit_rate the right default? The epic scopes it to the window (§3.1) and this ships that, but the coach's most natural question — "how has this gone since I started?" — is an all-history rate it must get by asking for a wide window. If real reviews keep widening the window just for that, add an all-history rate beside it rather than changing this one's meaning.
  • Does the coach eventually want a digest? S1 says one route now. The signal to revisit is the coach repeatedly fetching a quarter of entries to state three numbers.
  • Is 90 days the right default window? Chosen to match the epic's quarter framing. A weekly review arguably wants 7–14 days by default and a quarter on request; cheap to change, and the demo is where it will first feel wrong.

11 · Acceptance criteria

Endpoint

  • GET /api/habits returns definitions, a window of entries and every derived statistic in one payload, for a browser session or a valid INGEST_API_KEY; neither is 401 {"error":"Unauthorized"}.
  • A keyed call reads through the admin client — a key with no session returns the owner's real data, not an RLS-empty list (S2).
  • A present-but-wrong x-api-key fails even alongside a correct bearer token, and an empty value is a mismatch — the precedence the primer documents.
  • tz decides the day boundary; an unrecognized zone falls back to UTC without erroring, and the response echoes the zone actually used.
  • from/to bound the entries returned, to clamps to today, the default is the trailing DEFAULT_WINDOW_DAYS, and the effective window is echoed.
  • Contradictory or oversized windows are 400: from after to, or a span over MAX_WINDOW_DAYS — named in the message, never silently trimmed.
  • include_archived defaults to false, includes archived habits (with archived_at set) when true, and rejects any other value rather than coercing it.
  • Habits come back in the app's display order, and entries newest-first carrying only date, status, results, note.
  • No habits is a 200 with habits: []; a database failure is a 5xx through mapSupabaseError and never an empty list.
  • The route lives beside POST in app/api/habits/route.ts and adds no migration and no schema change.

The numbers

  • Streak scalars, met_days_total and stage are computed over all history — proved by two calls with different windows returning identical values.
  • hit_rate and the five counts are over the effective window, with unknown and skipped days on neither side of the rate, and no phantom unknown days outside [started_on, today].
  • The endpoint's numbers are the app's numbers — one lib/habits engine, no second derivation (D8).
  • A history longer than one PostgREST page comes back whole, and the paging guard fails loudly rather than truncating (S4).
  • hit_rate and average_streak are pre-rounded so a consumer can quote them directly, and the engine's own precision is unchanged.

Coach integration

  • The primer documents both endpoints — GET /api/habits and PUT /api/habits/[id]/entries — in its existing voice, each with a request example, payload, statuses table and reference script.
  • The primer states which figures are all-history and which are windowed, and the reading notes cover met-days-not-elapsed-days, unknown vs skipped, and the deliberately approximate stage label.
  • The primer states the key's widened blast radius — it now reads and writes habit data (ALF-146 §7).
  • Both scripts run as written, printing alfred's error envelope on failure and exiting non-zero.
