ALF-151 — Habit tracker: editing, archiving and deleting a habit

Story ALF-146 · slices 4 & 11 API · Store · UI Spec only — no implementation. Epic context: docs/specs/epics/ALF-146.html.

Two things in this document are still a choice, and the pick is the sign-off. §5 (the edit surface) and §6 (how a locked field reads) each offer three fully-drawn options behind a tab strip — click through them. Everything else is settled. Leave your pick as a PR comment; the implementation session builds exactly what is drawn in the selected tab.

1 · What this story is

The habit tracker works end to end — you can define a habit, log every day, watch the chain, and the coach can read and write through the keyed API. What you cannot do is change your mind. A habit today is write-once:

  • A typo in the name is permanent.
  • A criterion's target can't move — so the wind-down that ALF-146 was built for (wake ≤ 07:00 in month one, ≤ 06:15 by month three) has nowhere to happen.
  • A habit you've finished with can't be retired: archived_at exists in the schema, and nothing can set it.
  • A habit created by mistake sits on /habits forever.

The epic anticipated all of this — PATCH and DELETE /api/habits/[id] are in its API table (§5), and slice 11 is the edit form — but ALF-147 shipped only POST and the create dialog. This story closes both halves: the two missing route handlers, and an edit surface built out of the visual language the create sentence, the day editor and the folder menu already established.

In one line

In: PATCH + DELETE /api/habits/[id]; an edit surface for the name and the criteria; a frozen-cadence rule with an honest explanation on screen; archive + an Archived section with unarchive; hard delete behind a confirm. Out: anything that re-scores or re-shapes history (§11).

2 · Decisions locked during this refinement

S1Criteria are editable; cadence is frozen once a day is loggedowner

name, notes and criteria (labels, targets, comparators, adding and removing) can be changed at any time. active_days, allowance and started_on can be changed only while the habit has zero logged entries — after the first day is logged they are frozen for the habit's life.

Why the split isn't arbitrary — it's exactly where the retroactivity lives. Epic D12 freezes each day's status at write time, so editing a criterion is genuinely inert for history: a June day that was met against a 07:00 target stays met when the target tightens to 06:15, and every statistic reads back off those stored statuses. The other three fields are not stored per day — isApplicableDay() and the rolling walk read the habit's current active_days, allowance and started_on on every render. Dropping Saturday from the set, or raising the allowance, silently restates months of chain the owner already earned. Locking the three that restate, and leaving free the ones that don't, is the smallest rule that makes "edit your habit" safe.
Why zero-entries is the boundary: a habit you got wrong in the create dialog five minutes ago has no history to restate, and forcing a delete-and-recreate for a fat-fingered allowance would be silly. The moment there is one day to protect, the lock comes down.

S2The lock is enforced by the route, and only on a real change

PATCH reads the stored row first and compares. A locked field that arrives with the value it already has is a no-op, not an error; a locked field that arrives different on a habit with entries is a 409. active_days compares as a set, so [1,2,3] and [3,1,2] are the same cadence.

Why in the route and not only the form: the invariant protects stored history, so it belongs where the write happens — a form-only guard is one curl away from being bypassed, and the whole point of the rule is that the number on screen stays true. Why compare rather than reject on presence: whichever edit surface §5 picks, the form naturally submits the fields it rendered. Rejecting a mention of allowance would make every save fail; rejecting a change keeps PATCH idempotent and lets the client stay dumb.

S3Archived habits get a surface, and unarchive is one clickowner

A collapsed Archived disclosure at the bottom of /habits, listing each retired habit as one compact row with the span it ran and an Unarchive action (§7.3). The shell seed stops filtering archived rows; the view splits them.

Why: archive currently means "gone" — getHabits() filters archived_at is null and nothing renders the rest, so an accidental archive is unrecoverable without SQL. Making archiving reversible is what lets it be the safe default the epic wants it to be, and the cost is one line in the reader: entries are seeded by date window across all habits already, so no extra query appears.

S4Hard delete ships in the UI, behind a confirm that names the costowner

A destructive item in the habit's ⋯ menu opening a confirm dialog that names the habit, when it started and how many days go with it (§7.4). The row cascades to every habit_entries row.

Why: the epic's line is "archiving is the expected path; delete is for mistakes" — and a mistake is precisely the case a user hits five minutes after the create dialog, when going to the API is absurd. The confirm is what keeps it a deliberate act; it mirrors the existing destructive item in FolderNav's menu, with a confirm step added because a folder delete only re-homes its items while this one destroys data.

S5The wire says archived: boolean, not a timestamp

PATCH accepts { "archived": true | false }; the route stamps archived_at = now() or null. The column is never set directly by a caller.

Why: archived_at is not a preference, it is a fact about when something happened — and it is load-bearing, because isApplicableDay() stops scoring days on or after it. A caller free to post an arbitrary instant can retroactively un-score a fortnight by archiving "as of" a past date. A boolean removes that class of input entirely and keeps the "when" server-authoritative, the same way the entry route derives rather than accepts a status.

S6The create sentence is extracted and shared, never copied

NewHabitForm's body moves to components/habits/habit-sentence-form.tsx as HabitSentenceForm, taking optional initial values, a lockCadence flag and a submit label. NewHabitDialog and EditHabitDialog become thin wrappers around it.

Why: a second copy of the sentence is a second place criterion keys get minted, and key minting is the one piece of this form that history depends on (D10). The frontend-architecture skill's rule — extract on the second caller, not the third — lands exactly here, and CriterionEditor is already built this way ("adding a criterion and editing one are the same surface with different initial values").

S7Delete is optimistic, and its rollback restores position and entries

The card disappears on click and comes back in its old slot, with its logged days, if the request fails.

Why it needs saying: the store's existing removeHabit drops the habit and its whole entry bucket, and insertHabit appends. Reusing that pair as a rollback would silently resurrect the habit at the bottom of the list with an empty grid — which looks exactly like data loss. This story adds a restoreHabit action carrying the row, its index and its entries, following the position-aware rollback FoldersProvider already uses.

S8No field ships without a caller

sort_order stays off the update schema, and no reorder affordance ships. notes stays on the schema (it is on POST already) but gains no form field, because nothing renders it.

Why: the epic's slice-11 sketch lists "reorder" — but a manual-order drag with no ordering problem to solve (a handful of habits) is a feature looking for a user, and an endpoint field with no caller is untested surface area. Both are listed in §11 so the omission is a decision rather than an oversight.

4.1 PATCH /api/habits/[id] — session only

PATCH /api/habits/8f2a…  ·  Content-Type: application/json

{
  "name": "Morning routine",
  "criteria": [
    { "key": "wake",  "label": "be up by", "kind": "time",
      "target": 375, "comparator": "lte" },
    { "key": "light", "label": "get outside for light", "kind": "boolean" }
  ]
}

→ 200  the full updated habit row (same shape POST returns)

The schema sits beside createHabitSchema and reuses its pieces:

export const updateHabitSchema = z
  .object({
    name:        z.string().trim().min(1).optional(),
    notes:       z.string().nullable().optional(),
    criteria:    /* the same array + unique-key refine as create */.optional(),
    active_days: activeDays.optional(),
    allowance:   z.number().int().min(0).max(7).optional(),
    started_on:  z.iso.date().optional(),
    // S5: a boolean, never a timestamp. The route stamps the instant.
    archived:    z.boolean().optional(),
  })
  .refine((body) => Object.keys(body).length > 0, {
    message: 'No fields to update',
  });

The handler, in order

  1. parseUUID the segment → 400 on a malformed id.
  2. parseRequestBody(request, updateHabitSchema) → 400 on a bad body.
  3. Read the current row with .maybeSingle(). Null → 404. (Not .single(): mapSupabaseError has no PGRST116 case, so a missing row would surface as a 500. The shared mapper is deliberately left alone — widening it would change every other route's behaviour, which is not this story's business.)
  4. lockedFieldsChanged(current, input). If it returns nothing, skip to 6.
  5. Count this habit's entries (head: true, count: 'exact'). If > 0 → 409 naming the fields and the count.
  6. toUpdatePayload(input, ['name','notes','criteria','active_days','allowance','started_on']), plus archived_at derived from archived when present.
  7. .update(...).eq('id', id).select().single() → 200 with the row.
// lib/habits/edits.ts — pure, so the rule is table-tested, not route-tested.
export const LOCKED_FIELDS = ['active_days', 'allowance', 'started_on'] as const;

/** Which frozen fields this body actually CHANGES. Order-insensitive for active_days. */
export function lockedFieldsChanged(
  current: Habit,
  input: UpdateHabitInput,
): (typeof LOCKED_FIELDS)[number][]
The 409 is a real answer, not a failure. Its message is read by a human — it is what the §6 explanation quotes. Shape it as a sentence: "allowance is fixed once a habit has history — Morning routine has 63 logged days".

4.2 DELETE /api/habits/[id] — session only

DELETE /api/habits/8f2a…      →  200  { "success": true }

parseUUID, then .delete().eq('id', id). Entries go with it through the migration's on delete cascade — no second statement, and no orphan sweep. Deleting an id that doesn't exist is a successful no-op, matching DELETE /api/folders/[id].

6 · The locked slot — pick one

S1 freezes days, slack and start date once a habit has history. This is how that reads on screen. The stakes are specific: a control that simply doesn't respond gets clicked again, and then reported as a bug.

L1 · Static, with a footnote

The slot loses its dashed underline and its button role entirely: plain muted text on a faint plate with a padlock, out of the tab order. One line under the sentence explains the rule once.

Every day I will be up by 06:15 +
forgiving 1 miss a week.

Your days and slack are fixed — 63 days are already logged against them.

Cheapest and calmest. Nothing to build beyond a style branch. The footnote carries the whole explanation, so a screen-reader user meets it in document order rather than having to go looking. The risk: the footnote is easy to skim past, and then the slot looks broken.

L2 · Explains on click

The slot stays a real button with a padlock and a muted plate. Clicking opens a popover — the same popover the editable slots use — that states the rule, the count, and what to do instead. Its accessible name starts with "Locked", so the state is announced before the value. No footnote is needed.

Every day I will be up by 06:15 +
forgiving 1 miss a week.

Fixed for this habit

63 days are already logged. Changing your slack would rewrite what those days counted for, so the streak you earned stays the streak you see.

You can still change what counts as a good day — edit a criterion above.

Why this is the recommendation. The click is going to happen; the only question is whether it answers. It reuses the popover the sentence is already built from, so it is a content change rather than a new pattern, and it puts the reason next to the control instead of in a footnote — which is also where the 409's message can be quoted verbatim if the route ever refuses a save.

L3 · Explains, and offers a replacement

L2's popover, plus an action: Start a replacement habit opens the create dialog prefilled with this habit's name (suffixed), its criteria and its cadence, so the new terms begin today with a fresh chain — and offers to archive the old one on save.

Fixed for this habit

63 days are already logged. Changing your slack would rewrite what those days counted for, so the streak you earned stays the streak you see.

You can still change what counts as a good day — edit a criterion above.

Start a replacement habit

The replacement opens as a normal create sentence — every slot editable, because a habit with no history has nothing to protect.

The most useful, and the most build. It turns a dead end into a path: a genuine cadence change ("I need two misses now") gets an answer today rather than waiting for effective-dated goals (§11). It costs prefill plumbing through HabitSentenceForm, a naming rule for the copy, and an archive-the-old-one decision at save time — which is the part most likely to want its own conversation.

Whatever §6 picks, this holds: a locked field is locked only once the habit has an entry. A habit created two minutes ago and not yet logged shows all its slots normally and can be fixed freely — the create dialog's own behaviour, unchanged.

IconButton + DropdownMenu, accessible name Options for Morning routine — the same composition and naming FolderNav uses. Both trailing ellipses are load-bearing: those two items open a further step, Archive acts immediately.

Always visible, not hover-revealed. FolderNav reveals its menu on hover because a sidebar row is small and dense; a habit card is a large surface with one menu on it, and hover-only controls are a mobile dead end. The trigger is a muted icon button that gains contrast on hover / focus.

7.2 Archive is immediate, and reversible

Archive takes no confirm: it is the reversible action, and adding a dialog to it would put the same friction on the safe path as the destructive one. The card leaves the list, the Archived count next to the disclosure goes up by one, and a toast offers Undo.

Two consequences worth stating, because both are silent: archiving stops "today" being an applicable day for that habit, so the sidebar's unlogged badge drops — that is isApplicableDay() working as written, not a bug. And a habit archived by mistake and restored has lost nothing: archived_at going back to null restores every day exactly as it was.

One row per retired habit: name, the cadence summary the card already renders (habitSummary()), and the span it ran. Unarchive is a first-class button; the ⋯ carries Delete habit… only.

No grid and no statistics on an archived row, and that is deliberate rather than minimalism. The shell seeds a 120-day entry window, so a habit that ran last February has no entries in the store at all — a "longest streak" rendered here would read 0 and be a lie. The date span comes from started_on and archived_at, which are on the row itself and always true. Once ALF-150's server-seeded all-history baseline lands, enriching this row is a small additive follow-up — noted, not assumed.

Ordering and empty state: most-recently-archived first. With no archived habits the disclosure is not rendered at all. With only archived habits the existing "No habits yet" empty state still shows above it — which is accurate: there are no active ones.

7.4 The delete confirm

Delete “Morning routine”?

This destroys the habit and every day logged against it — 63 days since 12 June. It cannot be undone. Archive it instead to keep the record.

CancelDelete habit

FormDialog, focus on Cancel, Escape cancels. No typed confirmation — the named count and the destructive styling carry the weight, matching the skip flow's "second step, not a bigger button".

Getting the count right

The store only holds a 120-day window, so a blunt entries.length understates a habit older than that — and understating what you are about to destroy is the one direction this sentence must not be wrong in. deleteConfirmLine() therefore branches on whether the habit's started_on falls inside the seeded window:

Habit started…Reads
inside the window (the count is complete)“…every day logged against it — 63 days since 12 June.”
before the window (the count is partial)“…every day logged against it — at least 118 days, since 3 February.”
with nothing logged“…this habit. Nothing has been logged against it yet.”

Pure, and unit-tested beside the other habit strings.

8 · Store additions

The reducer already has almost everything: replaceHabit covers every update and both archive directions, and removeHabit covers delete. Only the delete rollback needs a new action (S7). 

type HabitsAction =
  | …existing…
  | { type: 'restoreHabit'; habit: Habit; index: number;
      entries: Record<string, HabitEntry> };   // NEW — rollback for delete

interface HabitsActions {
  addHabit:     (input: CreateHabitInput) => Promise<Habit>;      // unchanged
  logDay:       …;  skipDay: …;                                    // unchanged
  updateHabit:  (id: string, input: UpdateHabitInput) => Promise<Habit>;
  setArchived:  (id: string, archived: boolean) => Promise<Habit>;
  deleteHabit:  (id: string) => Promise<void>;
}
ActionOptimisticRollback · toast
updateHabit replaceHabit with applyHabitUpdate(habit, input, now) — the same pure merge the route's payload builder mirrors. Replace with the captured pre-mutation row · “Couldn't save that habit”.
setArchived replaceHabit with archived_at set or cleared — the card moves between the list and the Archived section on the click. Same restore · “Couldn't archive that habit” / “Couldn't restore that habit”.
deleteHabit removeHabit (drops the row and its entry bucket). restoreHabit with the captured row, its index and its entries · “Couldn't delete that habit”.

Selectors

useHabits()          // active only  — archived_at === null, memoized on state
useArchivedHabits()  // the rest, most recently archived first  (NEW)

Memoize, don't filter inline. useHabits() returns state.habits directly today; a bare .filter() would hand out a fresh array every render and re-run every memo downstream of it — including the grid's calendar build. Both selectors derive through React.useMemo over the state object, as useUnloggedTodayCount already does.

The badge needs no change. useUnloggedTodayCount reads the whole habit list, and isApplicableDay() already returns false for a habit archived on or before today — so archived habits entering the store cannot inflate it. Worth an explicit test rather than an assumption.

  1. The card ⋯ menu, and the edit surface open and prefilled.
  2. A criterion retargeted (07:00 → 06:15) — with the grid before and after in the same doc, unchanged. That screenshot pair is the whole argument for S1.
  3. The locked slot, and its explanation, as §6 draws it.
  4. An exec block: PATCH changing allowance on a habit with history returning 409, and the same call succeeding on a fresh habit.
  5. Archive → the Archived section → unarchive.
  6. The delete confirm, and the habit gone after a reload.

Open questions

  1. Should S1 be folded back into ALF-146 as a decision? The frozen-cadence rule is an epic-level constraint discovered while refining this story — it constrains every future habit story, not just this one. This spec deliberately does not edit the epic; the next revision of ALF-146 is where it belongs.
  2. Does an archived habit's entry data ever get cleaned up? Today it lives forever, invisible to the grid and outside the shell's 120-day window. That is fine at this volume, and the question only becomes real if the coach ever wants "everything I've ever tracked".
  3. If §6 picks L3, does saving a replacement archive the original? Offering it is friendly; doing it silently is not. Left open because the answer only matters if L3 is chosen.

12 · Acceptance criteria

  • API
  • PATCH /api/habits/[id] updates name, notes and criteria and returns the full updated row.
  • Sending a locked field (active_days / allowance / started_on) with the value it already has succeeds and changes nothing — including when active_days arrives in a different order.
  • Changing a locked field on a habit with no entries succeeds.
  • Changing a locked field on a habit with ≥ 1 entry returns 409, and the message names the field and the number of logged days.
  • { "archived": true } stamps archived_at server-side; false clears it. No caller can supply the timestamp.
  • An unknown id returns 404, a malformed id 400, an empty body 400.
  • DELETE /api/habits/[id] removes the habit and cascades every entry.
  • Both routes reject a request carrying a valid x-api-key but no session, with 401.
  • Editing
  • A habit can be renamed, and a criterion added, edited (label, target, comparator) and removed, through the surface §5 selects.
  • An existing criterion keeps its key across a label change, so logged history stays attached to it.
  • Retargeting a criterion leaves every already-logged day's status, and every statistic derived from it, unchanged.
  • The locked slots render and behave exactly as §6 draws, and no edit path can emit a cadence change for a habit with history.
  • A habit with no logged days shows every slot editable.
  • Archive & delete
  • The card carries a ⋯ menu with Edit, Archive and a destructive Delete, named Options for <habit>.
  • Archiving removes the card immediately, offers Undo, and drops the habit out of the sidebar's unlogged count.
  • Archived habits appear in a collapsed Archived section showing name, cadence and the span they ran; the section is absent when empty.
  • Unarchive returns the habit to the list with its full history intact.
  • Delete is gated by a confirm naming the habit and, accurately, how many logged days go with it — never overstating certainty for a habit older than the seeded window.
  • A failed delete restores the habit to its original position with its logged days, and shows a toast.
  • Repo rules
  • The create sentence exists in exactly one component, used by both dialogs.
  • Every new user-visible string is produced by a unit-tested pure helper in habit-format.ts.
  • The new visual state carries an image-snapshot baseline; no existing baseline changes.
  • A demo doc under docs/demos/alf-151-habit-editing/ passes npm run demo -- verify, and shows the grid unchanged either side of a criterion retarget.
  • npm run check is green, with no new lint suppressions and no config weakened.
