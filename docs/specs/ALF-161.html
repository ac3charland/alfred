ALF-161 — Add support for due times

StoryDatabase + frontend A due date can carry an optional time of day. Nothing changes for a task that doesn't have one.

A due date in alfred is a calendar day and nothing finer: lib/date-utils.ts deliberately reads YYYY-MM-DD as local midnight so day arithmetic never drifts across a timezone or a DST boundary, and every urgency rule in the app is built on that. This story adds the missing half — a task may also be due at a time, that time shows on its chip, and once it passes the task goes red.

1 · Context & problem

Today the due date is a whole-day fact, which makes the urgency colours coarse in exactly the way that matters most: everything due today is the same amber, all day. A 9am standup prep and an 11pm backup both read "due today" at 4pm, when only one of them is actually late.

The rules as they stand, and every place that depends on them:

There is also a latent capability already built and switched off for want of this feature. The recurrence engine implements an hourly frequency and formats its results as YYYY-MM-DDTHH:mm:ss, but lib/recurrence/types.ts says: 

/** A recurrence frequency. `hourly` is engine-only for now (no UI entry — needs a time anchor). */

A due time is that anchor. Exposing hourly repeats is deliberately not in this story (see §10), but this is the change that unblocks it, and the model below is chosen so that follow-up is small.

2 · Scope, as settled in refinement

QuestionAnswer
Does a due time change what counts as overdue? Yes. A task due today at 3pm turns red at 3:01pm. Date-only tasks keep the midnight rule exactly.
Where is the time set? In the existing due-date calendar popover — a time row under the month grid. No new chip, no new surface.
What rides along? Recurrence preserves the time — a daily task due 9am spawns its next occurrence at 9am.
How does a time render? Compact 12-hour: Today 3pm, Tomorrow 3:30pm, Aug 12 9am.
Explicitly out Reminders / notifications; the hourly repeat preset; time-aware ordering within a day; natural-language time capture. See §10.

4 · Decisions

D1A second column, due_time time — not a time folded into due_date

items.due_date is already a timestamptz, so folding a wall-clock time into it is possible. It is also a trap. The app has never used that column as an instant: parseDueDate reads YYYY-MM-DD and a midnight-UTC timestamp as local midnight, precisely so a date never drifts a day in a negative-UTC zone. 

// lib/date-utils.ts — the convention a folded-in time would have to break
if (/^\d{4}-\d{2}-\d{2}(T00:00:00|$)/.test(iso)) {
  return new Date(iso.slice(0, 10) + 'T00:00:00');
}

Under a folded model, "is this date-only?" becomes a question about the value — either a midnight sentinel or a companion boolean. The sentinel is outright wrong: 7:00pm CDT is midnight UTC, so that regex would silently read a real 7pm task as an untimed calendar date. A boolean avoids that but adds a flag that can drift out of sync with the value it describes.

A nullable time column has neither problem. null means "no time", every existing row already holds it, and due_date keeps its present meaning untouched.

The cost, stated: two fields now travel together through the schema, the route, the store and the optimistic patch — and anything that wants to order by instant has to compose them rather than parse one string. That is the direct reason ordering is deferred (D10, §10).

D2null is not a special case — it is today's behaviour, unmodified

Every predicate returns exactly what it returns now when due_time is null. That is the correctness bar for this story: the app must be indistinguishable from itself for a task without a time, in the chip, the folder badges, the subtask tally, the ordering and the recurrence spawn.

Concretely, the predicates take the time as a second argument rather than gaining separate variants, so no call site can accidentally keep using a date-only version: 

export function isDueDateOverdue(iso: string, time: string | null = null): boolean
export function isDueToday(iso: string, time: string | null = null): boolean
export function isDueTodayOrOverdue(iso: string, time: string | null = null): boolean

Why a default rather than a required parameter: the recurrence editor and the calendar call parseDueDate for pure calendar arithmetic where a time is meaningless. A defaulted parameter keeps those honest without threading a null through code that has no concept of one.

D3Clearing the date clears the time — the route does it, a CHECK proves it

A time with no date is meaningless, so the schema forbids it: 

alter table items add constraint items_due_time_needs_date check (
  due_time is null or due_date is not null
);

But a constraint alone would turn today's perfectly ordinary { due_date: null } PATCH — which task-row.tsx's clear handler sends — into a 500 for any task that had a time. So the route derives it: when the body sets due_date to null, the route forces due_time: null too, exactly as it already authors dispatched_at from the dispatched intent rather than trusting a caller to send a timestamp.

Why the server and not the client: Siri/service-role writes bypass the route's callers but not the route. Deriving it here means no ingress can create the orphan, and the CHECK is a backstop rather than a tripwire.

Deploy order — read before applying the migration. The supabase skill records that a new CHECK breaks the deployed frontend, because it writes without knowing the new invariant (items_dispatched_needs_folder did exactly this). These two constraints are safe: the deployed frontend has no concept of due_time, so every write it makes leaves the column null and satisfies both branches. The migration may therefore be applied ahead of the deploy. Say so in the PR body, with the alter table items drop constraint … escape hatch, so whoever picks it up knows the schema is ahead of the app.

D4Overdue becomes instant-aware, and the boundary instant is not overdue

At exactly 3:00pm a 3pm task has arrived, not lapsed. The existing rule already makes that choice — "today itself is NOT overdue" — so a timed task inherits it: overdue is now > dueInstant, strictly. 

/** The instant a task is due: local midnight when untimed, the local wall-clock time otherwise. */
export function dueInstant(iso: string, time: string | null): Date

// overdue
time === null
  ? parseDueDate(iso) < new Date(new Date().toDateString())   // unchanged
  : dueInstant(iso, time) < new Date()

dueInstant composes the calendar date and the wall-clock time in the viewer's local zone — new Date(y, m, d, hh, mm), never a UTC parse — which is the same invariant parseDueDate exists to protect, and which makes the value DST-correct for free.

D5A band that changes with no data change needs a clock — exactly one, at minute cadence

Every band change in the app today is either caused by a write or happens at midnight, so React re-renders whenever the answer could have moved. A 3pm due time breaks that: at 3:01pm the chip must be red, and nothing has happened. Without a clock, "turns red at 3:01pm" is really "turns red the next time you touch something", which is not the feature that was agreed.

So: lib/hooks/use-minute-tick.ts — a useSyncExternalStore hook over one shared interval aligned to the wall-clock minute (so the flip lands on :00, not 60s after mount), following the existing subscribe-once pattern in lib/hooks/use-media-query.ts and lib/use-prefers-reduced-motion.ts. Three consumers, which is every place a band is computed:

  • DueDateChip — its own band.
  • useFolderBadgeCounts — the sidebar red/amber tallies.
  • TaskRow — so countOverdueDescendants' roll-up doesn't lag the child chips that already updated beneath it.

Cost, and the alternative not taken: one re-render per visible row per minute. For a single-user list of tens-to-low-hundreds of rows that is far below the churn an ordinary keystroke in the capture box already causes. Threading the tick through TasksProvider instead would be fewer subscriptions but would change StateContext's value shape, which every useTasks() consumer reads — a much wider blast radius for the same result.

D6The time is set inside the existing picker, and is unavailable until a date is

One control owns "when is this due", so the popover gains a time row beneath the grid rather than the detail panel gaining a fourth chip. The row is disabled while no date is selected — which is D3's invariant made visible instead of enforced by a surprise, and removes the "user picks a time first" state entirely.

A No time control returns the task to date-only, mirroring the footer's existing Clear / Today pair.

What the control itself is, is deliberately still open. §5.1 draws four complete candidates and lets you drive them; the pick is a review comment. Everything else in this spec — the model, the urgency rules, the recurrence behaviour, the API — is independent of that choice, which is why it can stay open without blocking the rest.

D7Compact 12-hour, and the chip label is a plain join

formatTimeOfDay drops a zero minute and the space before the meridiem, because the compact row badge is already tight and 3:00 PM is four characters of nothing:

The label is formatDueDate(date) + a space + formatTimeOfDay(time) — so every existing label form composes without a new branch: Today 3pm, Yesterday 5pm, Tomorrow 9am, Aug 12 3:30pm.

Accessible name: the compact badge keeps announcing raw values — Due date: 2026-08-12 becomes Due date: 2026-08-12 15:00 when timed — so the existing test queries keep their shape and gain an unambiguous one for times. The comfortable chip's name stays the stable field label Due date, with the value on its visible text.

D8Recurrence carries the wall clock forward by copying it, never computing it

Because the time lives in its own column, "the next occurrence keeps the time" is a copy, not arithmetic. complete_and_spawn already selects the recurring root's own fields onto the spawned row; due_time joins that list, and joins the descendant deep-copy alongside c.due_date.

The TypeScript engine is not touched. nextOccurrence computes the next date; the time was never in the string it returns, and the complete route passes the same next_due it always did.

Why this is the DST-proof form: a 9am daily task stays 9am across the spring-forward boundary because nothing ever adds 24 hours to an instant. Had the time been folded into due_date, the spawn would have to do timezone-aware arithmetic to avoid becoming an 8am or 10am task twice a year.

The signature does not change — complete_and_spawn(uuid, timestamptz, int) stays as it is, so no grant execute has to be reissued.

D9due_time is a task-only field, like every other one

items_task_only_fields is the CHECK that makes a non-task row structurally incapable of holding a due date, a completion or a priority. A due time belongs in it, added by the drop-and-re-add its own history establishes (0010 did this for priority; 0019 last rewrote it). 

alter table items drop constraint items_task_only_fields;
alter table items add constraint items_task_only_fields check (
  item_type = 'task'
  or (due_date is null and due_time is null and status = 'active' and completed_at is null
      and (parent_id is null or item_type = 'code'))
);

Copy the predicate from 0019, the migration that last defined it, and add one conjunct. Re-deriving it from an older migration silently reverts the code-subtask relaxation — the trap 0025 and 0026 both document.

D10Ordering, grouping and filtering are untouched

lib/priority.ts keeps keying on Date.parse(due_date), i.e. day resolution. Two tasks due today at 9am and 5pm keep the ordering they have now, tie-broken by created_at. The Priority view's chips show their times and colour correctly; they just don't reorder. Deliberate — see §10.

D11The view and the RPC must both be re-expanded, or the column is invisible

Two documented traps apply to any column added to items, and neither is optional:

  • task_items is select i.*, and PostgreSQL freezes that column list at CREATE. It is the read path for every task in the app, so without a create or replace view the frontend simply never sees due_time. (0011, 0013, 0018 and 0026 each hit or document this.) Use create or replace, not a drop, so the grants and security_invoker survive.
  • get_subtree declares an explicit returns table (…), and create or replace cannot change a function's return type — it must be dropped first, as 0006 did when it added the recurrence columns.

get_subtree has no runtime caller today — only its generated type is referenced, via SubtreeRow in lib/types.ts. Update it anyway: a row type that omits a column of the row is a lie the next reader will believe, and it costs one paragraph of SQL.

5 · The surface

5.1 · The time control — an open pick between four

This section is a decision, not a description. Where the time lives is settled (inside the existing due-date popover, under the month grid — D6); what the control is is not. Below are four designs, each drawn in alfred's real design system and each complete — every one satisfies the whole requirement list, so picking any of them is a full sign-off and none leaves a gap for the implementation session to invent.

What every option must do

  • R1 — set a time on the selected day, saving immediately, leaving the popover open (only picking a day closes it).
  • R2 — reach any time it can express, not just a fixed menu, and state its granularity plainly.
  • R3 — clear back to date-only.
  • R4 — be wholly unavailable while no date is selected: dimmed, really disabled, out of tab order. (D3's invariant made visible.)
  • R5 — show the current value in the control itself, not only on the chip.
  • R6 — be built from treatments already in this popover — the day cell, the Input atom, the footer link — so it reads as part of the calendar rather than a bolt-on. This is the Repetition half of CRAP, and it is a requirement, not a preference.

Optimises for: being impossible to get wrong. Three short lists, no typing, no parsing, no meridiem ambiguity, and the value reads left-to-right in the order you say it — three · thirty · pm. Identical behaviour on desktop and phone, which none of the others quite manage.

Costs: three decisions to express one value, every time, including 9am. It is the tallest by a wide margin in a popover that already runs six rows of calendar. 6 · The change, layer by layer

6.1 · Database

One migration, database/migrations/<next>_due_times.sql — take whatever number is free when you build this, don't reserve one now. In this order: 

-- 1. The column
alter table items add column due_time time;

comment on column items.due_time is
  'Optional local wall-clock time of day for due_date. NULL = the task is due on that calendar '
  'day with no particular time, which is every task before ALF-161 and the app''s original '
  'behaviour. Deliberately a wall clock and not part of due_date: the app reads due_date as a '
  'LOCAL calendar date (lib/date-utils parseDueDate), and a recurring 9am task must stay 9am '
  'across a DST boundary.';

-- 2. A time cannot exist without a day
alter table items add constraint items_due_time_needs_date check (
  due_time is null or due_date is not null
);

-- 3. Task-only, like every other lifecycle field (predicate copied from 0019, one conjunct added)
alter table items drop constraint items_task_only_fields;
alter table items add constraint items_task_only_fields check ( … due_time is null … );

-- 4. Re-expand task_items — MANDATORY, `select i.*` froze its column list at CREATE
create or replace view task_items with (security_invoker = true) as
  select i.* from items i
  where not exists (select 1 from code_items c where c.item_id = i.id);

-- 5. get_subtree — DROP first (create or replace cannot change a return type), then recreate
--    with due_time in both the `returns table (…)` list and the final select.

-- 6. complete_and_spawn — add due_time to BOTH inserts: the spawned root selects the recurring
--    root's own due_time, and the descendant deep-copy carries c.due_time beside c.due_date.
--    Body copied verbatim from 0006; signature unchanged, so no grant is reissued.

No backfill: null is already the right value for every existing row.

  • seed.sql — give one seeded task a due_time, so a fresh dev database shows the feature without hand-editing a row.

9 · Acceptance criteria

  • Nothing regresses for a task without a time
  • A task with due_time = null renders the same label, the same band and the same accessible name as it does today, in all three of the row badge, the detail chip and the Priority view.
  • Folder badge counts, the overdue-subtask tally and priority ordering are unchanged for every untimed task.
  • Completing an untimed recurring task spawns the same next occurrence it does today.
  • Setting a time — R1–R6, and they hold whichever version §5.1 picks
  • The due-date popover shows a time row under the month grid, built as the picked version of §5.1 draws it, plus a No time control.
  • R1 — the control's quick path sets a time, saving immediately and leaving the popover open; choosing a day still closes it.
  • R2 — a time off the quick path is reachable, to the granularity that version states in §5.1's comparison table.
  • R3 — No time returns the task to date-only.
  • R4 — with no date selected every control in the row is dimmed, carries the real disabled attribute, is skipped by tab order, and is announced as unavailable.
  • R5 — the control reflects the current value, not just the chip above it.
  • R6 — the control's own cells reuse the day cell's treatment via the shared helper; no new pill geometry is introduced into the popover.
  • The chosen time survives a reload.
  • Showing a time
  • A timed chip reads <date label> <time> in compact 12-hour form — Today 3pm, Tomorrow 9am, Aug 12 3:30pm, Yesterday 5pm — with a zero minute dropped and no space before the meridiem.
  • The compact badge's accessible name is Due date: <YYYY-MM-DD> <HH:MM> when timed and Due date: <YYYY-MM-DD> when not.
  • Both chip sizes and the Priority view's display-only chip all show the time.
  • Urgency
  • A task due today at a time that has passed is red; one whose time is still ahead is amber; at exactly the due minute it is still amber.
  • Folder badges and the overdue-subtask tally agree with the chip for timed tasks.
  • A chip due at a time in the current minute flips to red without any interaction, within a minute of that time passing.
  • Recurrence
  • Completing a recurring task that is due at 9am spawns its next occurrence due at 9am.
  • The spawned occurrence's active descendants keep their own times.
  • Schema
  • A row with a due_time and no due_date is rejected by the database.
  • A non-task row carrying a due_time is rejected by the database.
  • task_items exposes due_time, and get_subtree returns it.
  • Clearing a task's due date through the API clears its time, even when the request never mentions the time.
  • Gates
  • npm run check is green, with no new ignore directive, no --no-verify, and no tooling-config edit made to get there.
  • lib/database.types.ts is regenerated output, not hand-edited.
  • A demo doc exists and npm run demo -- verify reproduces it.

10 · Out of scope

DeferredWhy, and what it would take
Reminders / notifications when a due time arrives The obvious next thought, and already routed elsewhere: epic ALF-146 puts notifications in their own epic, with the channel decision made (a Telegram bot from the existing Worker, docs/notifications-spike.md). This story gives that epic the timestamp it would fire on.
The hourly repeat preset lib/recurrence/types.ts blocks it on "needs a time anchor", which this story supplies. It stays off because the engine's hourly path returns a YYYY-MM-DDTHH:mm:ss string, i.e. it still assumes the time lives in due_date. Unblocking it means teaching nextOccurrence to advance due_time (and roll the date over midnight) and giving complete_and_spawn a next_due_time parameter — a signature change, and its own story.
Time-aware ordering within a day Two same-day tasks at 9am and 5pm keep today's ordering (D10). The sort key in lib/priority.ts is a single Date.parse(due_date); making it instant-aware means composing both columns in the comparator and re-baselining the Priority view's ordering tests. Worth doing — as a separate, visible change.
Natural-language capture ("call Bob tomorrow 3pm") The repo has no NL date parsing today, and adding one is a concern of its own size. Note that ALF-158's classifier is the natural home for it.
Timezones alfred is single-user and every date rule in it is local-wall-clock by design. due_time follows that convention. A task set to 3pm reads 3pm on any device; making it an absolute instant would be a change to the whole date model, not to this column.
A duration, or a start time A due time is one instant. Calendar-style time ranges are a different feature.

Open questions

One, and it blocks the build: which of §5.1's four time controls to build. Drive them and answer in a review comment — B if you want the recommendation, A if you want the cheapest thing that works. Nothing else in this spec depends on the answer, so it is the only sentence that has to be written before an implementation session can start.

Two sub-questions ride on the pick, and neither needs settling now — the implementation session can make the call and say so in its PR, because both are a handful of literals:

  • If A — which three preset times. 9am / 12pm / 5pm is a guess at someone's day.
  • If B — where the rail starts and ends. 7am–10pm fits two rows of eight; a 6am–9pm rail is the same size and a different bet about when this person works.

If C, one thing does need deciding up front rather than in flight, because it is behaviour rather than a literal: what a bare number means. §5.1's parser offers both readings and orders them 1–6 → pm, 7–11 → am, 12 → noon. Silently picking one instead would be the kind of guess that is wrong a few times a week.
