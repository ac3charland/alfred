Refinement spec · Tasks module

ALF-162 — Tasks: Add 3 dots to Priority view so tasks can be reprioritized/moved etc

Give every row in the By-Priority view the same “More actions” (⋯) menu the Inbox and Folder rows have — scoped to the actions that make sense while triaging a ranked list — so a task can be opened, re-dated, re-noted, re-filed, reordered or deleted without first navigating away to the view it lives in.

1 · Context & problem

By-Priority (/priority, ALF-37) is the one cross-cutting list of every top-level item across the Inbox and every folder, ranked by the best priority/urgency in each task’s active subtree. Since ALF-101 its rows are real, actionable task components — a completion checkbox, an expand chevron that reveals subtasks recursively, and a clickable PriorityChip — but the right-hand affordances were deliberately left out. The component says so in its own doc comment: 

// frontend/components/tasks/priority-view.tsx
 * The right-hand task-row affordances (add-subtask, the
 * ⋯ menu) are deliberately omitted here: the By-Priority list is for triaging and ticking off,
 * not for restructuring.

and a unit test pins the absence:

// frontend/components/tasks/priority-view.test.tsx:298
it('exposes neither the add-subtask nor the More actions affordance', () => { … })

That line held while the menu was mostly restructuring. It no longer does. The menu’s lead entry today is Open details — the only way to reach a task’s due date, repeat rule and notes — and it also carries Move to…, Move up / Move down, and Delete. In By-Priority all of those are unreachable: a task you have just decided is the most urgent thing you own can be ticked off or re-levelled, but not dated, noted, re-filed, reordered or deleted without clicking through to its folder and finding it again.

Priority itself is already editable here — the row’s PriorityChip (rendered with emptyLabel="Set priority") opens the shared picker in place. The ticket’s “reprioritized” is therefore already satisfied; the gap this spec closes is everything in the “/moved etc” half.

2 · Resolved scope from refinement Q&A

QuestionAnswer
Which entries should the By-Priority ⋯ menu carry? The triage subset. Open details, Move up / Move down (on expanded subtasks), Move to…, Delete. The code-module group — Classify as…, Send to Code module…, Convert to Code Story…/Epic… — stays out: that is Inbox triage, not priority triage.
Does the desktop add-subtask “+” come along too? No — ⋯ only. By-Priority stays a triage list; no new-work capture there. The menu therefore shows no “Add subtask” item at any breakpoint either.

3 · Decisions locked in this refinement

D1Reuse TaskRowMenu — do not grow a second dropdown

The By-Priority row renders the very same components/tasks/task-row/task-row-menu.tsx the Inbox and Folder rows render. Its internal structure (Open details → divider → reorder → move-to → divider → Delete) is already gated entry-by-entry on booleans, so the triage subset falls out of the flags the caller passes; no new menu markup, no copied item classes.

Why: the frontend-architecture skill’s one principle — a second copy of a dropdown drifts out of sync with the first. This also means the two menus keep identical keyboard, focus and portal behaviour for free.

D2The menu’s code-module and add-subtask props become optional

TaskRowMenuProperties today requires every code-module and add-subtask prop. The By-Priority caller has nothing true to say about any of them, and stubbing them with () => {} would fight @typescript-eslint/no-empty-function. So those props become optional, defaulting to false / absent; the required surface shrinks to what every caller genuinely has.

Why: the priority row then reads as what it is — a menu that simply doesn’t offer the code actions — instead of a menu lied to with a wall of false. TaskRow’s call site is untouched: it keeps passing every prop explicitly.

D3“Move to…” shows on depth-0 rows only

A By-Priority root row carries a folder/Inbox label and filing it is exactly what the label changes. A subtask row does not: moveTask re-files that subtask’s subtree without re-parenting it, so the row would keep rendering under a parent in a different bucket and nothing visible in this view would change. The priority row therefore passes folders only at depth 0 — and the menu’s existing folders.length > 0 guard drops the submenu on its own.

Why: costs no new conditional, and keeps every action in this view one the user can see the result of. TaskRow’s own behaviour (Move to… on every row) is deliberately unchanged — see §9.

D4The detail panel’s open state lives in the expansion store, not the row

“Open details” toggles ExpansionState.details (toggleDetails / closeDetails) — the same set TaskRow uses — and the panel is dismissed by Escape or an outside pointer press through the shared useDismiss hook, scoped to the row’s <li>.

Why: the store is already mounted around this view (app/(shell)/layout.tsx), is keyed by item id, and already knows how to be collapsed en masse. A row that opens its detail in the Folder view and then switches to By-Priority finds it open — one item, one state. (The row’s subtask expansion stays the local useState it is today; that asymmetry is pre-existing and out of scope.)

D5The five auto-saving detail callbacks move into a shared hook

task-row.tsx currently inlines handleSelectDueDate, handleClearDueDate, handleSaveRecurrence, handleSavePriority and handleCommitNotes — ~45 lines including the two fiddly rules (clearing a due date also clears the recurrence; setting a rule on an undated task stamps the anchor). Rather than paste them into the priority row, they become lib/hooks/use-task-detail-actions.ts, adopted by both call sites in the same change.

Why: “rule of two-or-three, earlier if the block is large or fiddly.” A second copy of the recurrence-anchor rule is exactly the kind that drifts. The hook also absorbs the priority row’s existing handlePriorityChange, so the row chip and the panel chip share one path.

D6Delete commits immediately here — no exit animation

TaskRow plays a fade + height-collapse before firing deleteTask (useAnimatedRowExit). By-Priority has no row exit animation today — completing a task already drops it from the ranked list the instant the store patches — so Delete follows suit and calls deleteTask(node.id) straight from the menu.

Why: consistency within the view beats consistency with another view, and the alternative means importing the collapse-wrapper chrome into a row that has none. Deletion stays optimistic and rolls back with a toast on failure, exactly as elsewhere.

D7The ⋯ is the row’s last child, revealed on hover at md+

The trailing actions cluster reuses rowActionsClass from task-row.styles.ts: always visible below md (touch has no hover), opacity-0 until the row is hovered at md+, and visible at every width under prefers-reduced-motion. Because it is opacity (not display), the column is reserved at rest and nothing shifts on hover. Since it is the last child of a row whose title is flex-1, the ⋯ lands on the row’s right edge at every depth even though only depth-0 rows carry a folder label.

Why: ALF-88 settled this behaviour for task rows; re-deriving it here would be a third copy of the same reveal.

4 · The behaviour

4.1 · What the menu offers, per row

By-Priority ranks every parentless item, so a code or still-unclassified inbox item can appear alongside tasks (they render without a checkbox today). The table is therefore keyed on what the row is, not on an assumption that it is a task.

Entry Shown when Does
Open details
teal, leads the menu		 Always — every row, every depth, every item type. Toggles the inline TaskDetailPanel between the row and its subtask list. Due + Priority chips on task rows; Repeat only on a depth-0 task; Notes always.
Move up / Move down Active subtask rows (depth ≥ 1) that are not already at the end of their sibling group — useSubtaskReorder, unchanged. Re-ranks the subtask among its active siblings via reorderSubtask; the expanded group reorders in place.
Move to… ▸ Depth-0 rows only (D3), and only when at least one folder exists. Submenu lists Inbox first, then every folder. moveTask — re-files the row and its whole subtree, and (per ALF-168) writes residency with it. The row’s folder label updates immediately.
Delete
destructive, below a divider		 Always — every row, every depth. deleteTask — removes the row and its whole subtree optimistically, no confirmation, exactly as in the Inbox / Folder views. Rolls back with a toast on failure.
Add subtask · Classify as… · Send to Code module… · Convert to Code Story…/Epic… Never rendered in this view — resolved in §2. The Inbox keeps them.

4.2 · Consequences worth stating

  • An edit can re-rank the row under your cursor. Changing priority (row chip or panel chip) or a due date re-sorts the list immediately — that is the view working as designed. The row keeps its React key, and its detail-open state lives in the store, so an open panel travels with the row to its new position rather than closing.
  • The row’s due-date chip stays display-only. Dates are edited in the panel; the row chip in this view is passed no onSelect/onClear and keeps today’s behaviour.
  • Completing from the checkbox is unchanged — including the cascade modal for a task hiding active subtasks.
  • Clicking the ⋯ must not navigate. The row title is a real <a href>, but the trigger is a sibling button, not a descendant of the anchor — no interception needed, and a unit test pins it (§7).

4.3 · Where an action goes once picked

Nothing new: every entry lands on an existing optimistic store action, which patches the in-memory list, calls the API, and reconciles or rolls back. No route, schema or store change.

6.2 · The extracted hook

// frontend/lib/hooks/use-task-detail-actions.ts
export interface TaskDetailActions {
  selectDueDate: (iso: string) => void;
  clearDueDate: () => void;
  changeRecurrence: (rule: RecurrenceRule | null, anchorDate: string) => void;
  changePriority: (next: TaskPriority | null) => void;
  commitNotes: (value: string) => void;
}

/**
 * The auto-saving detail mutations for one item — the callbacks TaskDetailPanel (and the row's
 * own chips) fire on every pick/blur. Each is fire-and-forget: the optimistic store already
 * rolls the row back and toasts on failure, so nothing is returned and nothing throws.
 */
export function useTaskDetailActions(node: ItemNode): TaskDetailActions

The two rules that must survive the move, verbatim in behaviour:

  • clearDueDate also clears recurrence when one is set — a rule has nowhere to anchor without a due date.
  • changeRecurrence stamps due_date: anchorDate in the same patch when a rule is being set on a task that has none.

Both call sites drop their void handleX() wrappers: the hook’s callbacks already return void, which is what TaskDetailPanel and PriorityChip want and what no-floating-promises is happy with.

6.3 · How the priority row composes the menu

// frontend/components/tasks/priority-view.tsx — inside PriorityRow
<div className={rowActionsClass}>
  <TaskRowMenu
    /* Depth-0 rows only: a subtask has nothing visible to re-file (D3). The menu's own
       `folders.length > 0` guard drops the submenu when this is empty. */
    folders={depth === 0 ? folders : []}
    canMoveUp={isActiveSubtask && canMoveUp}
    canMoveDown={isActiveSubtask && canMoveDown}
    onMoveUp={moveUp}
    onMoveDown={moveDown}
    onOpenDetails={() => { toggleDetails(node.id); }}
    onMoveToFolder={(targetFolderId) => { void moveTask(node.id, targetFolderId ?? null).catch(() => {}); }}
    onDelete={() => { void deleteTask(node.id).catch(() => {}); }}
  />
</div>

Everything the code-module group needs is simply not passed — that is the whole of D2 at the call site. The remaining wiring the row picks up:

  • useSubtaskReorder(node, isCompleted, false) — unchanged hook, supplies isActiveSubtask / canMoveUp / canMoveDown / the two moves.
  • useExpansion().details + toggleDetails / closeDetails, and useDismiss(rowRef, close, isDetailOpen) on the row’s <li> (D4).
  • useIndentation(depth) — already called for rowLeft; also take metaLeft for the panel.
  • group/row on the row’s flex line so rowActionsClass’s group-hover/row resolves to this row.
  • The panel renders between the row line and the AnimatedHeightCollapse subtask list, with showRepeat={isTask && depth === 0}.

6.4 · Accessibility

  • The trigger keeps aria-label="More actions" — the same accessible name the Inbox/Folder rows use, so existing queries and habits transfer.
  • Reorder stays reachable without a pointer: Move up/Move down are the keyboard path (By-Priority has no drag gesture at all).
  • Radix owns focus: the trigger regains focus when the menu closes, and the panel’s Escape dismiss defers to any open picker popover first (useDismiss).

9 · Out of scope

  • The code-module group and the add-subtask affordance in By-Priority — settled in §2.
  • Changing TaskRow’s own menu. It keeps Move to… on subtask rows; D3 is a By-Priority decision, not a repair of the Inbox/Folder behaviour.
  • An animated delete/complete exit in By-Priority (D6) — the view removes rows instantly today and continues to.
  • Making the row’s due-date chip clickable in this view; the detail panel is the editing surface.
  • Drag-and-drop reordering or re-parenting in By-Priority, and a Collapse all button for this view.
  • Moving the row’s subtask expansion into the expansion store — pre-existing local state, untouched (D4).
  • Inline title editing (double-click) in By-Priority — the task row has it, this view does not, and the ticket doesn’t ask for it.

Open questions

None. The two that mattered — how far the menu should reach, and whether the “+” comes with it — were resolved with the owner in this session (§2) and are locked in §3.

  • ☐ The menu on a depth-0 row contains exactly: Open details, divider, Move to… ▸ (Inbox + every folder), divider, Delete.
  • ☐ The menu on an active subtask row contains exactly: Open details, divider, Move up and/or Move down (hidden at the ends of the sibling group), divider, Delete — and no Move to….
