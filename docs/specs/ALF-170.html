ALF-170 — Apply all updates to inbox and classification

Story Epic ALF-158 · slices B + E + I Database + frontend. No cron, no Worker, no model call anywhere in this story.

The one-line shape. Everything the classifier needs on the other side of the wall, built by hand first. An item gains a pre-factory epic hint to sit beside its project hint; the Inbox row's detail panel becomes the one place every field a classifier would write is editable; and the bulk bar gains Dispatch, which sends a mixed selection to each item's own destination in one press. When it ships you can do by hand, for a batch, exactly what ALF-158 will later have a model pre-fill — and the story after this one has no UI or schema work left in it.

1 · What this story is

Epic ALF-158 splits into ten slices. This story takes the three that contain no model and no Worker — B (editing parity on the Inbox row), E (intended_epic_id + gate pre-selection) and I (the bulk Dispatch action) — and lands them together, because none of them is worth shipping without the others:

  • Dispatch (I) needs the epic hint (E). A code item can't be dispatched without an epic, and before this story it has nowhere to carry one before the gate.
  • Dispatch (I) needs editing parity (B). An action that routes a pre-filled batch is useless if filling those labels still means opening a dialog per item.
  • Editing parity (B) needs Dispatch (I). Setting a folder from the Inbox stops meaning "file it" (see S4), so without Dispatch there'd be a label you can set and no way to act on it.

Prerequisite: ALF-168 must land first

Slice A is already refined as ALF-168 and is not part of this story. It introduces items.dispatched_at, the backfill, the PATCH … { dispatched: boolean } intent, the lib/tasks/residency.ts helper, the store's residency-aware selectors and folder-badge guard, and the items_dispatched_needs_folder CHECK. Every one of those is assumed to exist here. This spec never re-specifies them; where it needs one it cites the ALF-168 decision by number.

If ALF-170 is picked up before ALF-168 has merged, stop and say so rather than building a reduced version. There is no dispatched_at for Dispatch to set, and S4's central distinction — that editing a label must not move the item — cannot even be expressed.

2 · Decisions

The epic hint

S1intended_epic_id, shaped exactly like intended_project_id

items gains a nullable intended_epic_id, following 0013_intended_project.sql line for line — the same FK behaviour, the same code-only CHECK, the same index, the same mandatory view recreation: 

alter table items
  add column intended_epic_id uuid references epics (id) on delete set null;

alter table items add constraint items_intended_epic_code_only check (
  intended_epic_id is null or item_type = 'code'
);

create index items_intended_epic_id_idx on items (intended_epic_id);

Why on delete set null: deleting an epic must not break an Inbox row — the item loses its hint, keeps its project, and simply stops being dispatch-ready until an epic is chosen. Deleting the project cascades its epics away (epics.project_id … on delete cascade) and nulls both hints, which is the coherent outcome with no extra code.
Why the CHECK: it mirrors items_intended_project_code_only so a task or unclassified row can never carry a stale epic. It is also what makes S6's clear-set mandatory rather than merely tidy.

S2A trigger keeps the epic inside its project — the one place this story is not a copy of the project hint

An epic belongs to a project, so intended_epic_id and intended_project_id can disagree. A CHECK can't see another table, so this is a trigger — the same reasoning that made enforce_subtask_shape a trigger in 0019 ("adjacency properties can't be a CHECK, hence the trigger"): 

create or replace function enforce_intended_epic_project() returns trigger
language plpgsql security invoker as $$
declare v_project uuid;
begin
  if new.intended_epic_id is null then return new; end if;
  select project_id into v_project from epics where id = new.intended_epic_id;
  if v_project is null then
    raise exception 'epic % not found', new.intended_epic_id;
  end if;
  if new.intended_project_id is distinct from v_project then
    raise exception 'intended epic % does not belong to intended project %',
      new.intended_epic_id, new.intended_project_id;
  end if;
  return new;
end; $$;

create trigger items_intended_epic_project
  before insert or update of intended_epic_id, intended_project_id on items
  for each row execute function enforce_intended_epic_project();

Why bother: enter_code_module(p_item, p_project, p_epic) validates neither argument against the other. Dispatch (S9) feeds it the two hints straight off the row, so an incoherent pair would create a story in one project filed under another project's epic — silent, cross-project corruption in the factory, discovered much later. The trigger makes it a loud immediate write error instead, which is ALF-168 S7's trade taken again.
It also removes a whole class of UI bug: the picker in S5 and the gate in S12 both clear the epic when the project changes, and this is what proves they do. An intended_epic_id with no intended_project_id is rejected by the same branch.

S3Neither hint is patchable today — both join the update schema and the route's field list

intended_project_id is accepted by createItemSchema (the capture box's ALF: prefix sets it at insert) but is absent from updateItemSchema and from the toUpdatePayload field list in app/api/items/[id]/route.ts. There is currently no way to change an item's project after capture except by going through the gate. Both hints become patchable: 

// lib/api/schemas.ts — updateItemSchema
intended_project_id: nullableUuid.optional(),
intended_epic_id:    nullableUuid.optional(),

// app/api/items/[id]/route.ts — toUpdatePayload field list
'intended_project_id', 'intended_epic_id',

Worth calling out because "add the epic beside the project" reads like a one-line symmetry and isn't: the project's write path is insert-only, so this story builds the update path for both fields, and S5's Project picker is a genuinely new capability rather than a second entry point to an existing one.
createItemSchema gains nothing. No capture path chooses an epic — the prefix parser resolves a project key and stops — so an insert-time epic would be an untested field with no caller.

Editing an Inbox item

S4Editing a label never moves the item. Filing does. One column, two verbs.

After ALF-168, folder_id is where an item will land and dispatched_at is whether it has landed. This story splits the actions that write them accordingly:

ActionWritesEffect on an Inbox row
Folder picker (detail panel, new) folder_id only, cascaded to the subtree The row stays exactly where it is, now labelled.
Move to… (row menu) · drag onto a folder · bulk Move to folder folder_id + dispatched_at (ALF-168 S3) The row leaves the Inbox and appears in the folder. Unchanged from today.
Dispatch (bulk bar, new — S9) dispatched_at only The row leaves the Inbox for whatever destination its labels already name.

A new store action, setFolder(id, folderId), cascades folder_id across the subtree and never touches residency — so it reads as "label this" on an undispatched row and as "move this between folders" on a dispatched one, from one rule. moveTask keeps its current meaning (file / un-file) untouched.

Why this is the load-bearing decision of the story: it is D6 applied to the human. The Inbox is a list you work down — correcting the folder on row three must not eject row three from the list you are working through. If the picker filed, the batch you were assembling would dissolve as you assembled it, and Dispatch would only ever be reachable for labels a machine wrote — which is precisely the thing that doesn't exist yet.
One constraint falls out of ALF-168's CHECK (dispatched_at is null or folder_id is not null or item_type = 'code'): a dispatched task must keep a folder. So the Folder picker offers its No folder entry only while the row is undispatched; on a dispatched task the entry is absent, and un-filing stays the row menu's Move to… → Inbox. Drawn in §3.

S5The detail panel becomes the one place every classifier-written field is editable

TaskDetailPanel's chip row is Due · Repeat · Priority today. It gains Type, Folder, Project and Epic, and the row shows the set relevant to the item's type — so the panel is complete for every field the epic's verdict schema can write:

ChipShown when Picker contentsWrites
Typealways (see S6 for when it's enabled) Task · Codeitem_type + the clear-set (S6)
Dueitem_type = 'task' (today) calendardue_date
Repeattop-level task (today) REPEAT_PRESETS + Custom…recurrence
Priorityitem_type = 'task' (today) High · Medium · Low · clearpriority
Folderitem_type = 'task' every folder, + No folder while undispatched (S4) folder_id, cascaded to the subtree
Projectitem_type = 'code' every project, + No project intended_project_id, and intended_epic_id → null whenever the project changes
Epicitem_type = 'code' the selected project's epics, + No epic; disabled with a hint while no project is set intended_epic_id

All four new chips are the same shape — a chip trigger opening a popover of single-select rows — so they are built on one shared primitive, components/atoms/picker-chip.tsx, which also absorbs the PickerListItem row currently private to detail-chips.tsx. Adopting it in RepeatChip is preferred (it is the same shape) but not required by this story.

Every chip here is a trigger whether or not it holds a value. Setting one never turns it into a label: the neutral "No folder" / "No project" state and the filled state are the same control wearing two tones, and pressing a filled chip reopens its picker with the current value ticked (drawn in §3.2). This is already true of Due, Repeat and Priority; the four new ones inherit it, and S7 extends the same property to the label chips on the row.

Why the panel owns the empty state: a rail of placeholder chips on every Inbox row would put six affordances on a surface whose job is to stay scannable, and most rows need none of them touched. The panel is one press away from the row menu, already auto-saves every control it hosts, and is where Due / Repeat / Priority already live — so this is the existing pattern extended, not a new one.
The split, stated once: a field with no value shows nothing on the row and is filled from the panel; a field with a value shows a chip on the row and is edited there (S7), with the panel offering the same control. So the row never grows an affordance for a label it isn't already carrying, and no label the owner can see is ever more than one press from being corrected.
Why Folder is task-only: "folders hold tasks" is already the rule moveTask encodes (ALF-72 classifies an unclassified item on filing it), and the epic's own verdict schema marks folder_id task-only. Offering it on an unclassified row would create a labelled row that can never be dispatched. Classify first, then file.
Why the project change clears the epic: S2's trigger would otherwise reject the write — and rightly. The gate already does exactly this (selectProject clears epicId); the picker matches it.

S6A type change is one coherent write, offered only on a childless root

Which way, and what it clears. Both directions violate a CHECK if written bare, so classifyItem stops being a lone item_type patch and becomes the single coherent PATCH D7 requires:

ChangeThe one PATCHWhy
→ Code { item_type: 'code', due_date: null, recurrence: null } items_task_only_fields forbids a due date on a non-task; recurrence is anchored to the due date (ruleFromPreset takes it as its anchor and complete_and_spawn needs it), so a rule without one is inert. They go together.
→ Task { item_type: 'task', intended_project_id: null, intended_epic_id: null } items_intended_project_code_only and S1's new twin both forbid a hint on a non-code row.

priority is deliberately not cleared in either direction: no constraint forbids it, the Priority chip simply stops rendering on a code row, and a mis-classification corrected straight back keeps the level the owner set.

Task and Code only. The picker never offers a return to unclassified. That value is what capture produces and what an abstention leaves behind — it is a starting state, not a destination, and nothing in the app reads it as somewhere to go back to.

Enabled only on a root with no children — parent_id === null && children.length === 0 — with the hint "Only a top-level item with no subtasks can change type". This gates the panel chip, the row menu's Classify as…, and the bulk bar's (S11).

Why the shape gate, precisely: enforce_subtask_shape fires before insert or update of parent_id, item_type and validates the updated row against its parent. Flipping a subtask's type is therefore caught by the database already (a code row under a task parent, or a task row under a code parent, both raise) — the UI just shouldn't offer it. Flipping a parent's type is the dangerous one: the trigger returns early on new.parent_id is null and the untouched children are never re-validated, so a code root would silently acquire task children. The database cannot catch that one, so the UI must.
This is not a regression. Today's gate is isUnclassified, and an unclassified item is always a leaf (canAddSubtask is isTask || isCodeRoot, so nothing can nest under one). Every row reachable today is already childless — the new gate only closes the hole that widening the control would otherwise open.
Changing a parent's family is already a supported action, with its own path: Convert to Code Epic…, which converts the parent and its children together through convert_to_code_epic. Nothing is lost.

What shows on the row

S7Two new row chips — the folder (Inbox only) and the epic. Shown only when set, editable whenever shown.

The row keeps its rule — a chip appears only when its field is set — and gains two:

  • Folder chip, rendered only on an undispatched row carrying a folder_id. In a folder view it would restate the view you are in.
  • Epic chip, rendered whenever intended_epic_id is set, beside the existing ProjectKeyChip and styled as its sibling (the epic's ref, in the project's colour).

All three label chips are clickable in place — the two new ones and the existing ProjectKeyChip, which stops being read-only. Each opens the same picker its panel twin does (S5), auto-saves, and writes through the same store action. A chip never goes inert once it holds a value: it is a trigger before and after.

They gain it the way DueDateChip and PriorityChip already do — an optional handler prop, present at the call site that wants editing and omitted for a display-only pill. ProjectKeyChip has exactly one call site (task-row.tsx), so the prop is additive with nothing else to migrate.

Two row elements stay read-only, deliberately. RecurrenceChip is unchanged (read-only on the row, edited in the panel — today's behaviour, untouched by this story), and the TypeBadge of S8 is a Badge, not a Chip: a type change carries S6's childless-root gate, and a badge that is silently inert on some rows reads worse than the ⋯ menu's Classify as…, which simply isn't offered where it doesn't apply.

Why they're not optional: after ALF-168 an Inbox row can carry a folder and show nothing for it, and after S1 the same is true of an epic. Both are inputs to Dispatch readiness (S9) — a label you cannot see is a label you cannot check, which makes the epic's "glance and move on" impossible and turns an unready row into a mystery.
Why clickable and not just visible: the row is where the owner reads the batch, so it is where they notice a wrong label. Sending them to the panel to fix the folder while the due date beside it takes one press would split the row into two classes of correction for no reason a user could infer. ALF-94 already settled this shape — the one chip, used in both places, clickable in both — and ProjectKeyChip's read-only note ("the project is chosen/changed through the gate") is a comment about a world where S3 hadn't made the field patchable yet.
This does not reopen the placeholder-rail question. The row still shows a chip only when its field is set; filling an empty field is still the panel's job. What changes is that a value already on screen is editable where it is shown.

S8The Task badge comes back — in the Inbox only

TypeBadge renders for task as well as code when the row is undispatched. Everywhere else — folder views, By Priority, Completed — a task keeps showing no badge, exactly as today.

Why reverse part of ALF-67: ALF-67 removed the "Task" pill because in a world where everything on screen is a task it carried no information. The Inbox stops being that world: it now holds unclassified, task and code rows side by side, and only two of the three can be dispatched. Without the badge an unclassified row and a bare task row are pixel-identical while behaving differently under Dispatch — the owner would press the button and be told something isn't ready with nothing on the row to explain it. Scoping the badge to undispatched rows keeps ALF-67's judgement intact everywhere it was made about.
This is a visible reversal of a deliberate past decision, so it is called out rather than slipped in: if the reviewer would rather mark the unclassified state instead, say so on the PR — the two are alternatives, not a pair.

Dispatching

S9Dispatch: one action over a mixed selection, gated per item, settling on partial

The bulk bar gains a Dispatch button — the primary action, first in the bar and the only one styled accent. It sends each ready selected item to its own destination regardless of type, in one press. Readiness is a pure predicate in a new frontend/lib/tasks/dispatch.ts, mirroring ALF-168's residency.ts:

ItemReady whenDispatch doesBlocker copy when not
Task item_type = 'task' and folder_id set PATCH { dispatched: true } on the row and its whole subtree (ALF-168 S3) needs a folder
Code item_type = 'code', both hints set, no children enter_code_module(item, intended_project_id, intended_epic_id) — the existing RPC, via the store's convertTaskToCode, then removeGatedItem needs a project · needs an epic · convert from its own row menu
Unclassified Never ready. needs a type
Unreconciled A row still carrying a temp id can't be PATCHed or passed to an RPC. still saving

Unready items are filtered out before the mutation runs — they are not "failures". The ready ones go, the unready ones stay selected so they're still in front of you, and the readiness line (S10) keeps saying what each is missing. A genuine save failure settles the way every other bulk action already does (applyBulkSettled: failed ids stay selected, N of M couldn't be dispatched). Success toasts Dispatched N items with no deep link — a mixed dispatch has no single destination to link to, and the existing Send-to-Code toast keeps its board link unchanged.

The button is enabled when at least one selected item is ready; at zero it is disabled with "Nothing in the selection is ready to dispatch".

One deliberate departure from D17. The epic's table excludes "anything with children" from Dispatch outright. That exclusion is kept for code items, where it is load-bearing — an epic-shaped row converts through convert_to_code_epic, not enter_code_module (ALF-129) — and relaxed for tasks: a task with subtasks is dispatchable, cascading dispatched: true across its subtree exactly as bulk Move to folder already cascades folder_id. Excluding it would make Dispatch strictly weaker than the action it exists to subsume, and would silently refuse every decomposed task in a batch. Flagged rather than assumed — if the reviewer wants D17 read literally, the readiness predicate is one clause.

Why a code dispatch opens no dialog: that is the feature. The gate exists to choose a project and epic; an item that already carries both has nothing left to ask. The consequence is that dispatching a code item is one-way (it enters the factory and leaves task_items), which is the same one-way step Send to Code… takes — from a confirm button instead of a picker.

S10The bar says what the selection is missing before you press

Whenever the selection contains ≥1 unready item, the bulk bar renders a second line beneath its actions, grouping the blockers by reason with counts:

2 not ready — 1 needs a folder, 1 needs an epic

It is derived live from the selection, so it updates as rows are selected, corrected in the panel, or dropped — and after a partial dispatch it is simply what remains.

Why in the bar and not on the rows: the epic names "telling you why an unready item didn't go" as the interesting half of this slice. Answering it on the rows means new per-row state that only ever appears mid-triage, on a surface S7 just worked to keep quiet; answering it in the bar puts it next to the button it is about, costs one line, and — the part that matters — arrives before the press rather than as a post-mortem.

S11The other three bulk actions get their gates re-derived

ActionGate todayGate afterWhy
Classify as every selected row unclassified every selected row is a childless root (S6) Correcting a type is now the common case, and the old gate disables the control on precisely the rows that carry a type to correct. The new gate is the one the database enforces.
Move to folder every selected row task every selected row is task or unclassified The smallest honest widening: moveTask already classifies an unclassified row to task as it files it (ALF-72), so those rows were always legal targets. A code row still can't be filed — folders hold tasks.
Send to Code… no selected row has children unchanged It stays the "choose the project and epic now" path. Dispatch is the "use what's already set" path. Neither subsumes the other.

Why keep all four buttons: the two survivors do things Dispatch can't — Move to folder files without a type decision and can also return a selection to the Inbox, and Send to Code… is the only way to reach an epic that doesn't exist yet (it hosts the "+ New epic…" row). Dropping either would trade a press for a dead end.

S12The gate pre-selects a unanimous epic, and never locks it

GateItem gains intendedEpicId. GateForm pre-selects it by the same unanimity rule it already applies to the project: when every item in the batch carries the same non-null epic, that epic starts selected. The project's lock behaviour on a bulk send is unchanged; the epic is never locked.

Why pre-select: without it, dispatching through the gate would discard a hint the item is already carrying and make the owner re-pick it — which would make S1 pointless anywhere except Dispatch.
Why not lock it too: the project lock exists because one project must apply to a whole batch and re-assigning it silently would be destructive. The epic list is right there in the dialog, and picking a different project already clears the epic, so a lock would only stop the owner changing their mind in the one place they came to change it.

4 · The change, layer by layer

One press, three outcomes. The split is a pure function, which is why every row of S9's table is a unit test and nothing about readiness lives inside a component.

Database — one migration, <next>_intended_epic.sql

Take whatever number is free when you build it; do not reuse the one that was free when this spec was written.

  • The column, the code-only CHECK and the index (S1), plus a comment on column naming it the pre-factory epic hint.
  • The coherence function + trigger (S2).
  • create or replace view task_items … — mandatory. A select i.* view freezes its column list at CREATE time, so intended_epic_id stays invisible to getAllItems() until the view is recreated. Documented by 0011 and 0013; recreate with create or replace (no drop, so grants and security_invoker survive).
  • notify pgrst, 'reload schema';

No RPC needs changing: enter_code_module leaves the hints alone and the row leaves task_items anyway, and ALF-168 S9 already handles the dispatched_at stamp. Apply with npm run migrate -w database <n>, commit the appended migrations-applied.log line, and regenerate frontend/lib/database.types.ts with supabase gen types — committed verbatim, never hand-edited.

API

  • lib/api/schemas.ts — updateItemSchema gains intended_project_id and intended_epic_id (S3). createItemSchema is untouched.
  • app/api/items/[id]/route.ts — both names join the toUpdatePayload field list.

Store — frontend/lib/stores/tasks-store.tsx

  • classifyItem(id, itemType) — becomes the coherent write of S6, choosing its clear-set from the row's current type. Same optimistic/reconcile/rollback shape.
  • bulkClassify(ids, itemType) — same, per row (each row's clear-set depends on its own current type, so the single shared patch object becomes a per-row one).
  • New setFolder(id, folderId) — cascades folder_id over the subtree (collectSubtree, as moveTask does) and never writes residency (S4).
  • New setIntendedProject(id, projectId) — writes { intended_project_id, intended_epic_id: null } in one PATCH when the project changes.
  • New setIntendedEpic(id, epicId).
  • New dispatchItems(ids) — filters by dispatchReadiness, runs the task PATCHes (subtree-wide) and the code RPCs through the existing applyBulkSettled machinery, drops gated rows from the store, and resolves with the ids that should stay selected (unready ∪ failed).
  • moveTask / bulkMove / removeGatedItem — unchanged.

Components

  • New components/atoms/picker-chip.tsx — the shared chip-plus-popover single-select primitive, absorbing PickerListItem from task-row/detail-chips.tsx.
  • task-row/detail-chips.tsx — gains TypeChip, FolderChip, IntendedProjectChip, IntendedEpicChip.
  • task-row/task-detail-panel.tsx — renders the per-type chip set of S5 and wires each to its store action.

6 · Acceptance criteria

Schema

  • items.intended_epic_id exists as a nullable uuid referencing epics(id) with on delete set null, carries a comment, and is indexed.
  • A non-code row carrying intended_epic_id is rejected by the database.
  • An intended_epic_id whose epic belongs to a different project than intended_project_id — or that is set with no project at all — is rejected, on insert and on update.
  • Deleting an epic nulls the hint and leaves the project hint intact; deleting a project nulls both.
  • task_items exposes intended_epic_id, with its grants and security_invoker intact.
  • frontend/lib/database.types.ts is regenerated (not hand-edited) and migrations-applied.log records the apply.

Editing

  • The detail panel shows Type · Due · Repeat · Priority · Folder for a task, Type · Project · Epic for a code item, and Type alone for an unclassified one — each auto-saving.
  • Setting a folder from the panel leaves the item in the Inbox; the folder chip appears on the row and the folder's badge count does not change.
  • The panel's Folder picker offers No folder only while the row is undispatched.
  • Changing a code item's project clears its epic in the same write, and the Epic picker is non-interactive while no project is set.
  • Changing an item's type is a single PATCH that clears exactly what the new type forbids and preserves priority; the control is offered only on a childless top-level row, and never offers unclassified.
  • Every field the epic's verdict schema can write — item_type, priority, due_date, folder_id, recurrence, intended_project_id, intended_epic_id — is settable from the Inbox without leaving it.

The row

  • An undispatched row with a folder shows a folder chip; a dispatched one does not.
  • A row with an intended_epic_id shows the epic's ref beside its project chip.
  • A task row shows the Task badge in the Inbox and nowhere else.
  • No chip renders for a field that is unset — an item with no folder, project or epic shows nothing in their place, on any view.
  • Every label chip that renders is editable where it renders: pressing the folder, project or epic chip opens its picker with the current value ticked, and picking auto-saves through the same store action the detail panel uses. The TypeBadge and the row's RecurrenceChip are the two documented exceptions.

Dispatch

  • A mixed selection of a ready task and a ready code item dispatches both in one press: the task appears in its folder, the code item on its project's board.
  • A task with subtasks dispatches with its whole subtree; a code item with children does not dispatch at all.
  • Unready items are not sent, stay selected, and are not reported as failures.
  • The bar names what the selection is missing, grouped by reason with counts, and updates live as the selection or its labels change.
  • Dispatch is disabled, with a hint, when nothing in the selection is ready.
  • Nothing leaves the Inbox without a human press — no code path in this story writes dispatched_at other than the three actions in S4's table.

The bulk bar and the gate

  • Classify as is enabled on a selection of childless top-level rows whatever their current type; Move to folder on a selection of tasks and unclassified rows; Send to Code… exactly as before.
  • The gate opens with a unanimous intended_epic_id already selected, still interactive, and clears it when a different project is chosen.

Guardrails

  • Every rule above is asserted by at least one test in the suite that owns it (§5), and check is green with no new ignore directives, config edits, or skipped tests.
  • The only image-snapshot baselines that moved are the ones S8 predicts, and each was approved by regenerating it, never by editing a PNG.
  • The E2E mock backend carries intended_epic_id, so no existing E2E body needed editing to stay green.
  • A demo doc exists, is linked from the PR as a live blob URL, and npm run demo -- verify reproduces it.

7 · Out of scope

  • Everything in ALF-168. dispatched_at, the backfill, the residency helper, the store selectors, the folder-badge guard, the insert and folder-delete triggers, the dispatched PATCH intent and the items_dispatched_needs_folder CHECK are that story's, and are assumed present.
  • Any classifier column. No classified_at, no provenance stamp, no classified_guess, no classification_corrections table, and no dispatch-time diff. Epic slices C, D and H add each one alongside the code that first writes it.
  • The Worker. No cron trigger, no scheduled handler, no sweep query, no Anthropic call, no prompt, no ANTHROPIC_API_KEY. The workers/ package is untouched by this story.
  • A rail of placeholder chips on the Inbox row. Decided against in S5: an unset field renders nothing on the row, and filling one is the panel's job. Note this is only about the empty state — a field that is set shows a chip and that chip is editable where it sits (S7). Revisit only if triage in practice proves the extra press to fill a blank expensive.
  • A single-row Dispatch entry in the ⋯ menu. Both single-item paths already exist — Move to… files a task, Send to Code module… gates a code item — and each already stamps residency. A third would be a synonym.
  • Un-dispatching in bulk. Move to folder → Inbox already returns a selection, and ALF-168 S8 defines what that clears.
  • Any rendering of when something was dispatched, or of who set a field. D4 holds: a machine-set value and a hand-set one are indistinguishable, and this story adds nothing that could tell them apart.
  • Creating a folder, project or epic from the detail panel. The pickers select from what exists; "+ New epic…" stays a gate affordance. The machine will never create one either (epic §5), so the panel matching that is deliberate.

8 · Open questions

  1. Does the Task badge earn its place, or should the unclassified state be marked instead? S8 proposes the badge because it reuses an existing component and needs no new vocabulary. The alternative — a dashed "Unclassified" chip — marks the rarer state and leaves classified rows quieter, at the cost of a chip that exists nowhere else in the app. Worth settling on this PR, since it is the one change here that reverses a previous deliberate decision.
  2. Should Dispatch confirm before sending code items? A code dispatch is one-way and dialog-free by design (S9). Proposed: no confirmation — the readiness line already states what will go, and adding a dialog re-introduces the per-batch friction the action exists to remove. Raised because it is the only irreversible thing in this story that happens on a single press.
  3. Does a folder chip on an Inbox row want a distinct treatment from a folder chip elsewhere? Proposed: no — S7 renders it in the row's existing muted badge tone, and D4 says a label is a label. Noted only because the folder chip is the first row element whose meaning is "will land here" rather than "is here", and a future reader may reasonably expect it to look different.
