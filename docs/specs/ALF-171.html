StoryEpic ALF-158 · slices C + D + H

ALF-171 — Create LLM classifier integration and cron worker

Database + Worker + deploy. No UI: this story renders nothing new and changes no component. The only frontend edit is a regenerated type file and the fixture builders that follow from it.

The one-line shape. A cron trigger wakes the existing Worker every two minutes. It selects the Inbox items nobody has touched yet, asks Claude Haiku 4.5 for a schema-constrained verdict about each one — type, priority, due date, folder, project, epic — and writes the guesses onto the item's real fields in a single coherent UPDATE. It never moves anything: dispatch stays a human act. And when you do dispatch, a database trigger diffs your final labels against what the machine guessed and appends every disagreement to a write-only log, which the next sweep reads back as worked examples.

Epic ALF-158 splits into ten slices, A–J. Three of them are already shipped: A (Inbox residency) as ALF-168, and B + E + I (editing parity, the epic hint, the Dispatch action) as ALF-170. 3 · Decisions

S1The sweep: one query, a hard item cap, sequential calls

The scheduled handler runs a single PostgREST read against items with the service-role key, then loops the results one at a time:

GET /rest/v1/items
  ?parent_id=is.null
  &dispatched_at=is.null
  &classified_at=is.null
  &classify_attempts=lt.5
  &select=id,title,notes,raw_capture,source_url,item_type,priority,due_date,
           folder_id,intended_project_id,intended_epic_id,classify_attempts
  &order=created_at.asc
  &limit=10
  • Zero eligible rows means zero API calls. A steady state where everything is triaged costs one database query per tick and nothing else.
  • The cap is 10 per tick (a module constant, SWEEP_LIMIT). Items over the cap are simply still unmarked on the next tick, so deferring them is free — which is why this is a more honest brake than a dollar meter (epic §7). At the epic's ~20 captures/day the cap is never reached in normal use; it exists so a bug cannot run away.
  • Oldest first (created_at.asc), so a burst drains in capture order rather than starving the earliest item.
  • Sequential, one item per request (D18). for … of with await inside, not Promise.all. Wall time is irrelevant — nobody is waiting on a tick — and parallel bursts only add 429 risk.
  • The handler awaits its own work. Return the promise from scheduled; do not fire-and-forget. A scheduled invocation is torn down when its returned promise settles, so unawaited work is silently killed mid-sweep.

Cron cadence: */2 * * * *. The epic asks for "order of every 1–2 minutes"; two minutes halves the idle query volume for latency nobody perceives, given the whole premise is capture-now-refine-later.

S2A human touch claims the item — enforced by a trigger, not by route code

The owner's answer in refinement: any human edit to a classifier-written field stamps classified_at, so the sweeper never revisits that row. This is implemented as a before update trigger on items, not in the PATCH route:

-- fires when a watched field changes, classified_at is still null, and the
-- statement is not itself the classifier stamping its own verdict
if new.classified_at is null and (
     new.title     is distinct from old.title
  or new.notes     is distinct from old.notes
  or new.item_type is distinct from old.item_type
  or new.priority  is distinct from old.priority
  or new.due_date  is distinct from old.due_date
  -- the three FK columns claim only when the new value is NOT NULL — see below
  or (new.folder_id           is distinct from old.folder_id
      and new.folder_id is not null)
  or (new.intended_project_id is distinct from old.intended_project_id
      and new.intended_project_id is not null)
  or (new.intended_epic_id    is distinct from old.intended_epic_id
      and new.intended_epic_id is not null)
) then
  new.classified_at := now();   -- provenance columns stay null: no model produced this
end if;
Why the three FK columns only claim in the non-null direction. All three are on delete set null, so a referential cascade writes them without any human stating anything. Deleting a folder is the case that bites: 0026's return_folder_items_to_inbox deliberately returns that folder's items to the Inbox, and the same delete nulls their folder_id — so a naive watch would claim every one of those items on its way back to the Inbox, permanently hiding from the sweeper exactly the rows that most need re-triaging. Excluding the to-null direction fixes it precisely, and costs only the vanishing case of a human hand-clearing a label on a never-classified item.

This is a cousin of the gotcha the supabase skill records from ALF-170 — a trigger that reads two columns is fine until a cascade writes them for you. It differs in shape (that one needed a deferred constraint trigger because it validates coherence and must judge the settled row; this one modifies NEW, so it must stay before update) but it has the same root cause, and the same moral: only the real-Postgres integration suite catches it — the JS mock has no cascades. §8 pins it there.

Why the database and not the route. There are already three ingresses that edit an item — the Next.js PATCH route, the two factory RPCs, and any service-role write (Siri, a future shortcut) — and only the database sits under all of them. The same argument ALF-168 made for putting inherit_dispatched_at in a trigger rather than the route applies unchanged, and it is why this story needs no frontend behaviour change at all.

Why classified_at rather than a separate "claimed" column. The sweep predicate is already classified_at is null; reusing it means there is exactly one way to be ineligible, so the two can never disagree. A row claimed by a human is distinguishable from one the model judged: its classified_provider is null (S3).

The accepted cost. A capture you deliberately rewrote to be clearer will never be guessed at. That is the trade the owner chose, and it is the conservative direction: it makes "the machine changed my answer back" structurally impossible, which is the failure D10 exists to prevent.

S3Provenance is three columns, and null provider means "no model ran"

The epic leaves the exact provenance columns to the story. They are:

ColumnShapePurpose
classified_attimestamptz, nullThe idempotency marker (D10). Null = eligible.
classified_providertext, null'anthropic'. Null = this row was claimed by a human edit (S2), not judged.
classified_modeltext, nullThe resolved model id, e.g. claude-haiku-4-5.
classified_prompt_versionint, nullA module constant in the Worker, bumped by hand whenever the prompt text or the schema changes.
classified_guessjsonb, nullThe verdict as written, so the dispatch diff has something to compare against (S12).
classify_attemptsint, not null, default 0Failed attempts. The ceiling (S11).

Why the provider is a column and not a constant. Straight from the epic: an override is the accuracy metric, so stamping the provider turns a future A/B into a query instead of a migration. It costs one text column now and keeps the option open for free. It is copied onto every corrections row too (S14).

Why the prompt version is hand-bumped. It is what makes a prompt change safely replayable over old captures — the reason story G can exist at all. A derived hash would change on whitespace; a hand-bumped integer changes when a human decides the prompt is meaningfully different.

S4task_items is recreated, and the new columns are visible to the frontend

The migration ends with create or replace view task_items … as select i.* from items i … and notify pgrst, 'reload schema', exactly as 0011, 0013 and 0026 do.

Why recreate, when D4 says the UI must never show the guess. It is tempting to leave the view stale as a free enforcement of invisibility. Don't. Item is Database['public']['Tables']['items']['Row'] — the table row type — and getAllItems() reads the view with .overrideTypes<Item[]>(). A column on the table but not the view produces a row whose runtime value is undefined where the type promises string | null. That exact mismatch is a documented past crash in this repo (lib/priority.ts carries the comment). Invisibility is D4's job and D4 achieves it by nobody rendering the field — the same way dispatched_at rides the view unrendered today.

The consequence to plan for: Item gains six fields, so the compiler will point at every fixture builder that constructs a whole item. See §7.

S5The call: the official SDK, Haiku 4.5 as a var, no thinking, no effort

One narrow module, workers/src/classifier.ts, owns the entire Anthropic surface: build the request, send it, return a parsed verdict or a typed failure. Nothing else in the Worker imports @anthropic-ai/sdk.

  • The SDK, not raw fetch. wrangler.toml already sets compatibility_flags = ["nodejs_compat"], and Cloudflare Workers is an officially supported runtime for @anthropic-ai/sdk. The SDK also brings the retry behaviour D13 leans on (S11). This is a deliberate departure from src/supabase.ts, which stays on raw fetch — that module's comment explains it keeps the Worker tiny and needs no compat flag, and it is not worth rewriting.
  • Model id from env.CLASSIFIER_MODEL, defaulting to claude-haiku-4-5 in [vars]. "Try Sonnet for a week" is then a deploy flag, not a story.
  • No thinking, no output_config.effort. Haiku 4.5 rejects effort outright, and classification needs no reasoning budget. Omit both.
  • max_tokens: 512. The verdict is ~100 tokens; this is headroom so stop_reason: "max_tokens" never fires in practice.
  • No prompt caching, and never pad the prompt to reach the cache floor. Haiku 4.5's minimum cacheable prefix is 4096 tokens and a compact classify prompt sits well under it, so cache_read_input_tokens: 0 is the expected reading, not a bug.

Cost, at the epic's ~20 items/day: ~$1.20/month before examples, ~$1.80 after the few-shot block's ~+50% input. The per-item verdict is ~1.5k in / ~100 out at $1/$5 per MTok. Every option in this tier is inside noise, so the choice is decided by fit — and the property that matters is structured-output support, which Haiku 4.5 has.

S6The schema carries the live ids as enums, rebuilt every sweep

This is D3's first layer, and it is why a hallucinated folder is not a case the Worker has to handle. The request carries output_config.format with a JSON Schema assembled per sweep from the live folder / project / epic lists:

output_config: {
  format: {
    type: 'json_schema',
    schema: {
      type: 'object',
      additionalProperties: false,
      required: ['item_type','priority','due_date','folder_id',
                 'intended_project_id','intended_epic_id'],
      properties: {
        item_type:           { anyOf: [{ enum: ['task','code'] },        { type: 'null' }] },
        priority:            { anyOf: [{ enum: ['high','medium','low'] },{ type: 'null' }] },
        due_date:            { anyOf: [{ type: 'string', format: 'date' }, { type: 'null' }] },
        folder_id:           { anyOf: [{ enum: [ ...live folder ids ] },   { type: 'null' }] },
        intended_project_id: { anyOf: [{ enum: [ ...live project ids ] },  { type: 'null' }] },
        intended_epic_id:    { anyOf: [{ enum: [ ...live epic ids ] },     { type: 'null' }] },
      },
    },
  },
}
  • Every field is required; nullability is an explicit {"type":"null"} branch. A strict schema wants every key present, and abstention has to be a value the model can emit rather than a key it can omit (D8).
  • additionalProperties: false on the object — required by structured outputs.
  • An empty id list collapses the field to {"type":"null"}. An empty enum is not a valid schema, so a fresh database with no folders must not produce one. The prompt-assembly function handles this and a unit test pins it.
  • Read the response as JSON from the single text block, guarding stop_reason first. messages.parse() is not usable here: it wants a static Zod schema, and this schema is rebuilt per sweep from live ids.

The per-request schema is not a cost problem. A new schema pays a one-time compilation and then caches for 24 hours; the id lists change only when a folder, project or epic is created, so in practice the schema is stable for days.

S7The closed world is described, not just named

The schema constrains which ids the model may emit; it says nothing about how it should choose between them. So the prompt's folder and project lists carry each row's description — the one-sentence standing statement of what belongs there that ALF-179 ships — alongside its name:

Folders (choose at most one, by id):
  7f3a…  Health   — Appointments, prescriptions, exercise, anything medical.
  b2c1…  House    — Repairs, maintenance, things to buy for the flat.
  9e04…  Someday  — Things I might do eventually. Nothing with a date.
  4d77…  Work                       ← undescribed: the name alone, no dash, no placeholder

Projects (choose at most one, by id):
  1a55…  ALF · alfred  — This app: the task system, the Inbox, the code factory.
  • Present when written, silently absent when not. A null description contributes nothing — not an empty dash, not "(no description)". ALF-179's D2 guarantees empty is stored as null and never '', which is what makes description ?? undefined a sufficient test; the renderer must treat both identically anyway, since the app's own readers do.
  • Epics are named, not described. They get their ref and title, and nothing more — epics.notes is deliberately not fed to the model. ALF-179's D1 draws that line explicitly: notes is a free scratchpad on a board card, "misc", while a description is a standing statement written to be read by something else. Feeding a scratchpad to the classifier as if it were a specification is how a prompt starts quietly encoding whatever the owner last jotted.
  • No fallback prose. If nothing has a description the block degrades to today's bare list of names, which is exactly what the prompt would have carried anyway.

Why this is the highest-value place to spend prompt tokens. S6 makes a hallucinated folder impossible, but the epic names the expensive failure as a confident-but-wrong pick from the real list — it gets rubber-stamped in review precisely because it looks legitimate. "Someday" versus "Work" is a judgement about how the owner uses their own system, and no amount of prompt engineering recovers it from a bare noun. This is the field that carries that judgement, and it is the only input here written by the owner specifically to be read by the model.

What it costs: descriptions are capped at 500 characters each (ALF-179 D3), so a fully described world of ~10 folders and ~3 projects is order +400 tokens on a ~1.5k prompt — comparable to the example block, and still inside D2's "under a dollar a month". No cap or truncation is applied here: the 500-character limit is already enforced at write time, and silently trimming the sentence the owner wrote to disambiguate two folders would defeat the point.

Descriptions are read, never written. Nothing in this story authors or edits one — that is ALF-179's whole contribution, and the two stories meet at this column.

S8Re-validate anyway — closed world plus cross-field coherence

D3's second layer, and the natural unit-test seam. A pure function validateVerdict(raw, world) takes the parsed response plus the id sets that were sent and returns a verdict where every surviving field is legal. Each rule drops a field to null; none rejects the whole verdict:

RuleDropped
An id is not in the set that was sent (deleted between prompt assembly and write-back)That id field
item_type is not 'task' — a task-only field is presentpriority, due_date, folder_id
item_type is not 'code' — a code-only field is presentintended_project_id, intended_epic_id
intended_epic_id names an epic that does not belong to intended_project_idintended_epic_id
intended_epic_id is set with no intended_project_idintended_epic_id
due_date does not parse as YYYY-MM-DDdue_date
A field the item already holds a non-null value forThat field — see below

The classifier fills gaps; it never overwrites. The last row is D10's third consequence. An ALF:-prefixed capture arrives already code with a project set and no classified_at, so it is eligible and should usefully gain an epic or a priority — but the project a human's prefix chose is not the classifier's to change. The merge is existing ?? guessed, per field.

Why this layer exists when the enum already closed the value space. The enum closes the values but not the time gap — a folder can be deleted between prompt assembly and write-back, and only this step notices. It is also where cross-field rules live, which an enum cannot express, and it is pure and deterministic, which makes it the seam D12 wants gated.

S9One coherent write, and dispatched_at is never in it

A validated verdict becomes exactly one PATCH /rest/v1/items?id=eq.<id> carrying the surviving guess fields and all six provenance columns together:

{ item_type, priority, due_date, folder_id,
  intended_project_id, intended_epic_id,          // only the fields that survived S7
  classified_at: <now>, classified_provider: 'anthropic',
  classified_model: env.CLASSIFIER_MODEL, classified_prompt_version: PROMPT_VERSION,
  classified_guess: <the validated verdict, as written> }

The database will reject anything else. items_task_only_fields requires due_date is null unless item_type = 'task', and items_intended_project_code_only requires item_type = 'code' for the project hint. Writing a due date before the type flips violates the CHECK and fails the row. This is not a style preference; it is the schema — which is also why S7's cross-field rules mirror the CHECKs exactly, so a validated verdict is always a legal write.

dispatched_at is absent by construction, and a unit test asserts the payload never contains that key. This is the invariant that makes D4 safe: because the machine cannot move anything anywhere, the worst a bad guess can do is show a wrong chip on a row you are already looking at.

An abstention is still a write. A verdict where every field came back null still PATCHes the provenance columns, marking the item. Eligibility is classified_at is null, not item_type = 'unclassified' — keying on the type would re-ask the same question about the same text forever, burning budget on exactly the items already known to be unjudgeable.

S10The reference date is America/Chicago, computed per sweep

"Friday" resolves against a wall clock the Worker does not have. The zone is CLASSIFIER_TIMEZONE in [vars], set to America/Chicago (the owner's answer). The prompt carries a reference date computed as:

new Intl.DateTimeFormat('en-CA', { timeZone: env.CLASSIFIER_TIMEZONE })
  .format(new Date())        // → 'YYYY-MM-DD'

The model emits due_date as a bare YYYY-MM-DD, written verbatim. items.due_date is timestamptz, so Postgres casts it to UTC midnight — which is exactly the shape parseDueDate() is written to read back as a local calendar date without an off-by-one in a negative-UTC zone.

Why a var rather than a constant: the zone is the one piece of this prompt that is about the owner rather than the domain, and it changes if they move. Why the zone is in the prompt at all: so a date is resolved once, deterministically, by the code — the model is given "today is 2026-08-08 (Saturday)" and asked for an absolute date, never asked to know what day it is.

S11Degrade per field, retry only transport, count every failure

Each classification is one stateless request. The Worker never opens a second turn to tell the model it got something wrong. Failures split two ways, and the full table is §5.

  • Transport — 429, 5xx, timeout, network. The SDK's own retry (maxRetries, default 2) absorbs the blip inside the request. If it still throws: nothing written, the attempt counter goes up, the next tick tries again. That is the entire retry mechanism — no queue, no backoff state, no dead-letter.
  • Content — a refusal, a truncation, an unparseable body. Nothing written, attempt counted. Re-sending the same prompt will not help, so it burns an attempt rather than looping.
  • The ceiling is 5 attempts, enforced in the sweep predicate (classify_attempts=lt.5) rather than by stamping a marker. A row that exhausts its attempts goes on being an ordinary unclassified Inbox item, forever if need be — the worst case equals today.
  • Incrementing costs no extra read. The sweep already selected classify_attempts, so a failure PATCHes n + 1 from the value in hand.
  • One carve-out: a credential failure aborts the sweep and counts nothing. A missing ANTHROPIC_API_KEY, or a 401/403 from the API, is a configuration fault rather than anything about the item. The handler checks the binding is present before the first call, and treats an auth rejection as fatal to the tick: log one distinct message, stop the loop, leave every item untouched — no PATCH, no attempt increment.
Why that carve-out is not optional. Without it, an unset key is indistinguishable from a transient outage: every eligible item burns an attempt per tick, and at a two-minute cadence the whole Inbox is past the ceiling of 5 in ten minutes — permanently, since nothing resets the counter. A single forgotten manual step would quietly and irreversibly opt every existing capture out of the feature, and the only symptom would be that nothing ever gets labelled. Failing the tick loudly instead makes the same mistake cost nothing but the ticks it takes to notice, and wrangler tail names the cause on the first one.

Why every failure counts, including transport. A taxonomy where transport failures retry freely is defensible, but it has no brake at all: a persistent misconfiguration would loop at 720 calls/day forever. Counting everything gives a uniform rule and, at a two-minute cadence, tolerates a ~10-minute outage before an item is set aside. Simplicity wins here; the alternative buys resilience against exactly the failure the owner would notice anyway.

Why no repair loop. The error a repair loop exists to fix is precisely the one S6 designs out — you cannot usefully say "that folder doesn't exist, try again" about an id the model was never able to emit. For everything else abstention is already the right answer, and a repair turn would spend a second call to convert a blank into a guess, moving in the opposite direction from the precision D8 optimises for.

S12classified_guess is the snapshot, not a second source of truth

The verdict as written is stored on the item as jsonb. It is written once, by the sweeper, and read by exactly one consumer: the dispatch trigger (S13). No UI, no API, no store field, no selector.

D4 costs the interface its ability to tell a guess from a decision. This is what buys it back — invisibly, which is the whole point. Storing the post-validation verdict (not the raw model output) means the diff compares like with like: a field S7 dropped was never presented to the owner, so it is not something they can be said to have corrected.

S13The dispatch diff is a database trigger, so every exit is covered

An after update trigger on items, firing when old.dispatched_at is null and new.dispatched_at is not null and old.classified_guess is not null. For each of the six guessed fields it compares the guess against the row as it now stands, and inserts one classification_corrections row per disagreement.

All three directions count as corrections, and the log records which:

DirectionGuessedChosenWhat it teaches
changednon-nullnon-null, differentThe label was wrong.
filled_innullnon-nullIt could have known.
blankednon-nullnullIt should have abstained — the most valuable of the three, because precision is what D8 optimises for.

Why a trigger rather than the PATCH route. Dispatch happens three ways: the bulk { dispatched: true } PATCH, enter_code_module, and convert_to_code_epic — two of which are RPCs the route never sees. The transition of dispatched_at from null is the single choke point all three pass through, and putting the diff there means no ingress can forget it. It also keeps this story out of the frontend entirely.

Why at dispatch rather than on every edit. An edit mid-triage may be revised twice before you're done; logging each would teach the model your hesitation rather than your conclusion. Dispatch is the commit point in this design and it fires exactly once per item.

A known, accepted quirk: enter_code_module nulls due_date in the same statement that stamps dispatched_at, so a task-shaped guess on an item the owner sent to the factory logs a blanked due-date correction. That is the correct lesson — the owner decided it was a code item, so the due date was wrong — and no special-casing is needed.

S14The log freezes the text and stores ids; names are resolved at read time

classification_corrections is append-only, one row per corrected field:

id                uuid primary key default gen_random_uuid()
item_id           uuid references items(id) on delete set null
captured_text     text not null          -- DENORMALISED copy of the title (+ notes)
field             text not null          -- check: one of the six
direction         text not null          -- check: changed | filled_in | blanked
guessed_value     text                   -- null = the model abstained
chosen_value      text                   -- null = the owner blanked it
provider          text not null
model             text not null
prompt_version    int  not null
created_at        timestamptz not null default now()
  • The captured text is copied, not referenced. A correction is a historical fact — this text, at that moment, got that label. Referencing would lose the text when the item is deleted, and would pair the current title with a label chosen for the old one when the item is edited, silently corrupting the example.
  • Ids are stored as ids (as text), and resolved to human names when the prompt is assembled. An example that says "→ 7f3a…" teaches the model nothing; an example that says "→ Health" teaches it the taxonomy. Resolving at read time also gives D16's closed-world filter for free: a correction naming a since-deleted folder simply fails to resolve and is dropped rather than taught.
  • item_id is on delete set null, so a lesson outlives its item.
  • RLS, policy and grants exactly as every other table: enable row level security, the authenticated full access policy, and explicit grants to anon, authenticated, service_role. The trigger is security invoker, so the inserting role must hold insert on the table — including the authenticated role that a browser dispatch runs as.

Why a table rather than columns on items: different cardinality (several corrections per item), different lifetime (outlives the item), append-only, and read by exactly one consumer. The same reasoning that kept habit_entries off items in ALF-146.

S15Example selection: round-robin across the three directions, 12 slots

The epic leaves the selection rule to this story and warns about its trap: a log dominated by "you left this blank and I filled it in" nudges the model toward guessing more, which is the failure D8 exists to prevent. So recency alone is not the rule.

The most recent 60 corrections are read, partitioned into the three direction buckets, and drawn round-robin — one from blanked, one from changed, one from filled_in, repeat — each bucket internally recency-ordered, skipping exhausted buckets, until 12 examples are collected or nothing is left. Examples whose ids no longer resolve are dropped before the draw, not after, so a dropped example does not cost a slot.

Why round-robin rather than a reserved fraction. It keeps blanking represented without a magic percentage, degrades to plain recency when a bucket is empty, and is a pure function of (rows, live world) — which makes it a clean unit-test seam rather than a behaviour you can only observe in production.

Why 12 and not "everything". Twenty examples at ~40 tokens is roughly +800 on a ~1.5k prompt; 12 keeps the block meaningful and the cost under a dollar a month. The number is the one thing here worth tuning later, and it is a module constant so tuning it is a one-line change.

What is not built: no distillation into standing rules, no embedding store, no second model call, no review surface. D16 stops at recency-ordered examples and so does this story.

S16The health check becomes the deploy's receipt for the classifier config too

GET / extends from alfred workers ok (build <sha>) to also name the resolved model and zone:

alfred workers ok (build 9b6e5f7; classifier claude-haiku-4-5 @ America/Chicago)

This is not decoration — it closes a real risk. The deploy workflow runs wrangler deploy --var WORKER_VERSION:"$GITHUB_SHA", and this story is the first to put anything else in [vars]. If a CLI --var ever shadows rather than merges the file's vars, the classifier would silently fall back to its defaults in production with no symptom. Reporting the resolved values makes that a one-curl check instead of a mystery — the same reasoning that made the build stamp exist after a Worker sat three phases behind main for days (ALF-149). The existing assertion on the health string in src/index.test.ts is updated alongside it.

4 · Architecture

The capture path is untouched; everything here hangs off the cron trigger, and all it does to an item is fill in fields. The dashed teal line is the learning half.

5 · What the model is asked, and what comes back

Input, per item

  • The item's title, notes, raw_capture and source_url.
  • The live folder list (id + name + description), project list (id + key + name + description), epic list (id + ref + title + project id — named, not described). Rendering and omission rules in S7.
  • The reference date, computed per S10, with its weekday spelled out.
  • The recent-corrections example block (S15), omitted entirely when the log is empty — an empty log is just today's prompt.

The abstention rules the prompt must state

FieldAnswer only when
item_typeThe text clearly reads as a task or as work on alfred itself. May stay null, which is simply the item behaving as it does today.
due_dateThe text actually states a date or a day. Never inferred from urgency.
priorityThe text signals it. No default guess.
folder_idOne existing folder is a clear fit. Never invent a folder.
intended_project_id / intended_epic_idOnly from the sets supplied. Never invent either.

Given D4, the cost of the two error modes is wildly asymmetric: a blank field is one the owner was going to fill anyway — zero regression — while a confident wrong label is worse than nothing, because a row that looks done gets skimmed past and dispatched. Optimise for precision and accept low recall.

Nothing here may block a capture, drop an item, or leave one in a state the UI can't render. The feature is strictly additive; the worst case is the status quo. One item's failure must not abort the sweep — the per-item body is wrapped so the loop continues.

6 · The correction loop, end to end

  1. The sweeper writes a verdict and stores it as classified_guess (S12).
  2. The owner scans the Inbox, overwrites what they disagree with using the row's ordinary editing controls, and presses Dispatch.
  3. The dispatched_at transition fires the trigger, which diffs guess against final and appends one row per disagreement, tagged with its direction (S13).
  4. The next sweep reads the log, resolves ids to names against the live world, drops what no longer resolves, and draws 12 examples round-robin across the three directions (S15).
  5. Those examples go into the prompt as worked pairs: this text → the label the owner actually chose.
Nothing about this is rendered. No badge, no "corrected" state, no diff view, no accuracy dashboard. D15 is a write-only substrate, and this story keeps it that way. The signal is collected for free from work the owner was going to do anyway — which is what turns D4's one genuine weakness into an asset.

9 · Acceptance criteria

The sweep

  • A cron trigger fires the Worker's scheduled export every two minutes, registered from wrangler.toml and live after a normal merge to main.
  • The sweep selects only top-level, undispatched, unclassified items under the attempt ceiling, oldest first, at most 10 per tick.
  • With no eligible items, a tick makes exactly one database query and zero API calls.
  • Items are classified one per request, sequentially; a failure on one item does not stop the others.

The verdict

  • The request constrains folder_id, intended_project_id and intended_epic_id to enums of the live ids, so an invented id cannot be emitted.
  • The folder and project lists shown to the model carry each row's owner-written description when one exists, and its name alone when it doesn't. Epics carry ref and title only — never notes.
  • Every field may come back null, and a fully-abstaining verdict still marks the item as classified.
  • Every id is re-checked against the sets that were sent, and cross-field incoherence drops the offending field rather than the whole verdict.
  • A field the item already holds a value for is never overwritten — an ALF:-prefixed capture keeps its project and may gain an epic or a priority.
  • A due date is written only when the text states one, resolved against America/Chicago.

The write

  • All of an item's guesses and all of its provenance land in a single UPDATE.
  • The classifier never writes dispatched_at; no item leaves the Inbox without a human act.
  • Each failure mode of §5 behaves as tabulated, and a run of failures sets an item aside rather than looping forever.
  • A missing or rejected API key aborts the tick with one distinct log line, costs zero requests when the binding is unset, and leaves every item's attempt counter untouched — so fixing the key later loses nothing.
  • Nothing in this story can block, slow, or fail a capture: POST /api/items gains no LLM call and no new dependency.

The claim rule

  • Editing any classifier-written field on an undispatched item stamps classified_at, and the sweeper never revisits it.
  • A human-claimed row is distinguishable from a model-judged one by its null classified_provider.
  • The rule holds for every ingress — the PATCH route, the factory RPCs, and a service-role write — because it lives in the database.
  • A referential cascade does not claim: deleting a folder returns its undispatched items to the Inbox and they remain eligible for the next sweep.

The correction loop

  • Dispatching an item whose guess disagrees with its final labels appends one correction row per field, tagged changed, filled_in or blanked.
  • Each row carries a frozen copy of the captured text plus the provider, model and prompt version that produced the guess.
  • Deleting the item leaves the lesson intact.
  • The next sweep's prompt carries up to 12 examples drawn round-robin across the three directions, with ids resolved to names and unresolvable examples dropped.
  • Nothing in the app renders any of it.

Guardrails

  • No test in check:fast or check:slow makes a live model call.
  • ANTHROPIC_API_KEY exists only as a Cloudflare Worker secret (plus, optionally, a developer's gitignored workers/.dev.vars) — not in Vercel, not a GitHub Actions secret, not a [vars] entry, not in the client bundle, not in the repo.
  • Setting the secret is a one-time manual step that can be completed before this story merges, and requires no redeploy to take effect.
  • task_items is recreated in the same migration, and reading the new columns through the view resolves.
  • GET / reports the running build alongside the resolved classifier model and timezone.
  • A demo doc reproduces a real sweep and a real correction, and npm run demo -- verify passes.

10 · Out of scope

Beyond slices F, G and J (§1), the epic's non-goals hold unchanged and none of them may be pulled in here:

  • Rewriting captured text. No de-rambling of voice input, no title tidying, no summarising. Titles and notes stay byte-for-byte as captured; this story writes metadata only.
  • Suggesting subtasks or structure. No proposing a breakdown of a capture into children.
  • Knowledge items. That destination type does not exist yet; the schema's item_type enum offers only task, code and null.
  • Any other LLM feature in the SPEC §13 roadmap — the Reader digest, the Communication Firewall, refinement generation inside the factory. This is Inbox triage only, even though it stands up the first Worker→LLM path they will all reuse.
  • Chat, or any conversational surface. One call, one item, no turns.
  • Distilling corrections into standing rules. D16 stops at recency-ordered examples, and so does this.
  • Any UI for the correction log. No diff view, no "the model got this wrong" affordance, no accuracy dashboard.
  • A second provider, or an A/B between providers. Nothing is built for it beyond D2's two cheap disciplines: the narrow call boundary (S5) and the provider stamp (S3).
  • Authoring, editing or backfilling a folder or project description. This story reads that column; ALF-179 creates it, writes it and builds its editor. Nothing here adds a description to an undescribed folder, and no default or generated text is ever substituted for one.
  • Retro-classifying the existing backlog. The sweeper takes new captures. A one-off backfill over historical items is a separate decision with a separate cost.
  • Prompt caching. Below Haiku 4.5's 4096-token floor, and the prompt must never be padded to reach it (S5).

11 · Open questions

  • Does the correction log ever forget? Recency ordering handles this implicitly while the log is small and stops handling it once it isn't — a lesson from a year ago about a folder you barely use still competes for a slot. No action now; S15's 60-row read window bounds the problem in the near term, and a session that later reaches for "just feed the whole table" should know this is why it won't stay fine.
  • Is 12 examples the right number? Chosen for cost, not measured. Story F's fixtures are what would settle it, which is the main reason F is worth doing next.
  • Does --var WORKER_VERSION merge with or shadow [vars]? S16 makes the answer observable rather than guessed. Confirm it on the first deploy — and if it shadows, the fix is to pass all three vars in the workflow's deploy command, which is a one-line change. Either way, record the answer in the cloudflare-workers skill.

Guidance for the implementing session, not a requirement of the spec. Skip it and build the thing in one pass if that reads better on the day.

  • The acceptance pass. §9's checklist is verified once, at the end, by one reader against the running system. An agent confirming its own slice is not the same evidence, and the failure this catches — a slice that is individually correct and collectively wrong — is exactly the one a split introduces.
