ALF-179 — Add support for folder and code project descriptions

Story spec Epic ALF-158 · LLM processing A nullable description on folders and projects, authored in place from each surface's own header. No LLM code in this story.

1 · Context & problem

Epic ALF-158 has the classifier choose a folder for a task and a project for a code item by picking an id from a closed list (epic decision D3: the live ids are the enum values of the response schema, so an invented folder is not something the model can emit). That design makes a wrong id impossible — but it says nothing about the model picking the wrong existing folder, which epic D8 names as the expensive failure, because a confident-but-wrong label gets rubber-stamped in review.

Today the only thing distinguishing one option from another in that list is its name. folders is (id, name, created_at, sort_order) and nothing more; projects carries a name, a 3-char key and a repo. So the prompt story D will assemble can say no more than "Health", "Work", "Someday", "House" — and "Someday" versus "Work" is a judgement about how the owner uses their own system, which no amount of prompt engineering recovers from a bare noun.

This story adds the field that carries that judgement: one sentence per folder and per project, written by the owner, saying what belongs there. It ships the column, the write path and the authoring surface — and stops before anything reads it. Two reasons that boundary is the right one: the classifier does not exist in the repo yet (epic stories C and D), and the descriptions are only worth reading once they have been written, so landing the authoring surface first means story D inherits real content on day one instead of a table of nulls.

Where this sits in the epic. It is not one of the epic's A–J slices — it is a small additional enabler discovered while refining them. It has no dependency on any of them and none of them depends on it to land: it makes story D's prompt better, not possible. It touches no file the residency work (story A, merged) or the sweeper (story C) touch, so it can ship at any point.

2 · Scope, as settled in refinement

QuestionSettled
Where is a description authored? In place, in each surface's own header — the folder's under the folder-view header, the project's under the board header. Both reuse the epic-notes inline editor (InlineEditTrigger → TextareaField). The sidebar folder menu's Edit keeps meaning rename, exactly as it does today.
Projects have no PATCH route at all — how wide should the new one be? Description only. PATCH /api/projects/[id] accepts description and nothing else. name, key, github_url and the repo fields stay as immutable as they are today.
Does anything read the description? No. Nothing in the app or the Worker consumes it in this story. Prompt assembly is story D's.

The shape of the change

Two writers, one column, no readers yet. The reads that already exist (select('*') in lib/data/folders.ts and lib/data/code.ts) carry the new field with no query change.

4 · Decisions

D1The column is description on both tables — not notes

text, nullable, no default. Null on every existing row, and null is a permanently legal value.

Why not notes, which epics already has: they are different fields with different jobs. epics.notes is a free scratchpad on a board card — anything the owner wants to jot. A description is a standing statement of what belongs here, written to be read by something else. The ticket names it, and one honest name beats reusing a word whose existing meaning is "misc".

D2Empty is stored as null, never ''

The editor trims and maps an empty result to null before writing (next === '' ? null : next), and every reader treats null and the empty string identically when deciding whether to show the placeholder.

Why: two representations of "no description" is one more than the prompt assembly in story D should have to think about — description ?? undefined must be enough to omit the folder's line entirely. The epic-notes save does exactly this today; copying it keeps one idiom.

D3500 characters, enforced at three layers, visible at none

  • A DB CHECK (description is null or char_length(description) <= 500) on each table.
  • z.string().max(500) in both schemas, so an API caller gets a 400 rather than a Postgres error mapped to a 500.
  • A native maxLength on the textarea, so the UI can never produce a body the other two reject.

Why a cap at all: every description is re-sent on every classify call (epic D18 — one item, one request, the folder list rebuilt each sweep), so an essay pasted into one folder is a permanent tax on every future item. The epic is explicit that prompt budget is the scarce thing and that padding the prompt is never a saving. Why no counter, no error state: 500 characters is several times what a real description needs, so hitting it is rare enough that a persistent counter would be chrome on every folder to serve a case that essentially never happens. Adding a counter would also mean a new prop on a shared atom used by the epic notes and the block-reason flow. The cap is a backstop, not a workflow.

D4The line is always rendered — an empty description shows its placeholder

Not hover-gated, not hidden until first use. Every folder view and every board shows either a description or Add ….

Why: it matches the epic-notes precedent, and a field nobody knows exists is a field that stays null — which is the one outcome that makes this whole story worthless. The cost is one muted line on surfaces that have no description yet, and the visible-consequence is real: it moves four committed Storybook baselines (§7).

D5updateFolderSchema's refine has to be loosened, not just extended

It currently reads "Either name or sort_order is required". Add description to the object and to the predicate — otherwise a description-only PATCH is rejected with a 400 before it reaches the route, and the failure looks like a store bug.

Why call it out: it is the one place in this change where adding a field without touching a second line silently breaks the feature, and both are in the same 8-line block. Prefer the updateHabitSchema idiom — Object.keys(body).length > 0 — so the next field added here can't repeat this.

D6No view to recreate, and no select to change

The task_items trap the epic spec warns about — select i.* freezing its column list at CREATE time — does not apply here. There is no view over folders at all, and v_code_stories names project columns explicitly (p.key, p.name, p.repo_owner, p.repo_name) — it has no p.*. The reads are already select('*') straight off the tables, so they pick the column up for free.

Why state a non-problem: the epic tells every story session in ALF-158 to recreate a view after adding a column. Following that instruction here would produce a pointless view recreation; a session that doesn't follow it should be able to see it checked rather than forgotten.

D7Creation stays name-only

POST /api/folders and POST /api/projects are unchanged. A new folder or project starts with description: null and is described afterwards from its own header.

Why: the sidebar's create form is a single inline field by design (type a name, Enter, done) and the new-project dialog is already a three-field form guarding a unique key. Describing is a second, unhurried thought — the same reason capture doesn't ask for a folder.

D8Both writes are optimistic, mirroring what each store already does

Folders: a new setFolderDescription(id, description) action, a line-for-line mirror of renameFolder — optimistic patch, PATCH, replace with the saved row, rollback to the previous value, toast on failure. Projects: a new patchProject reducer action (mirroring the existing patchEpic) plus an updateProjectDescription(id, description) action in the same shape.

Why optimistic rather than a refetch: it is the house pattern for every mutation in both stores (see the data-flow skill), and the write is a single scalar on a row already in memory — the cheapest possible case for it.

D9Nothing reads the description, and nothing is stubbed for a future reader

No prompt-assembly helper, no describeClosedWorld(), no Worker change, no placeholder module waiting to be filled in.

Why: story D owns the prompt and hasn't been specced yet; a seam guessed now would be a seam it has to delete. The column and the authoring surface are the whole contribution, and they are independently useful — a described folder is self-documenting for the human too.

5 · The change, layer by layer

5.1 · Database

One migration, database/migrations/<next>_entity_descriptions.sql — take whatever number is free when you build this; do not reserve one now. 

-- 1. The columns
alter table folders  add column description text;
alter table projects add column description text;

-- 2. The cap (D3) — a backstop against an essay pasted into a field that is re-sent
--    on every classify call once ALF-158 story D lands.
alter table folders  add constraint folders_description_length
  check (description is null or char_length(description) <= 500);
alter table projects add constraint projects_description_length
  check (description is null or char_length(description) <= 500);

comment on column folders.description is
  'Optional one-or-two-line statement of what belongs in this folder (ALF-179). NULL = undescribed, '
  'which is every folder before this migration. Written by the owner from the folder view header; '
  'destined for the ALF-158 classifier prompt, which needs more than a bare name to choose between '
  'folders. Capped at 500 chars because it is re-sent on every classification request.';
comment on column projects.description is
  'Optional one-or-two-line statement of what this project is and what work belongs in it (ALF-179). '
  'NULL = undescribed. Same purpose and same cap as folders.description.';

No backfill: null is already correct for every existing row. No view recreation and no re-grant (D6) — neither table is behind a view, and no function signature changes.

8 · Acceptance criteria

Authoring a folder description

  • A folder with no description shows Add folder description… on its own line under the folder-view header, at every viewport.
  • Clicking it opens a two-row textarea seeded with the current value, with Save and Cancel beneath it, and the tasks below do not move.
  • Saving persists immediately (optimistically) and survives a reload.
  • ⌘↵ / Ctrl+↵ saves; Escape and Cancel both restore the display without writing.
  • Saving an emptied field returns the folder to the placeholder and stores null, not ''.
  • Saving an unchanged value issues no request.
  • A failed save restores the previous text and shows Couldn't save the folder description.
  • A described folder shows its text wrapped, with a pencil that appears on hover.

Authoring a project description

  • Every criterion above holds for the project description on the board header, with the project copy, capped at max-w-2xl.
  • The BoardToolbar stays on its own row at every viewport, including the phone layout where the filters fold into the ⋯ menu.

API & schema

  • PATCH /api/folders/[id] accepts a body carrying only description.
  • PATCH /api/projects/[id] exists, updates the description, and returns the updated row.
  • That route ignores every field but description — a body naming name, key or github_url cannot change them.
  • An empty PATCH body is a 400 on both routes.
  • A description over 500 characters is a 400, not a 500.
  • The database rejects a description over 500 characters on both tables.
  • Both columns are nullable and null on every pre-existing row.

Nothing regresses

  • Folder rename from the sidebar, folder create, folder reorder and folder delete behave exactly as they do today; the sidebar row menu's Edit still opens the rename.
  • Project creation from the sidebar + and from the gate is unchanged.
  • The epic-notes editor and the story block-reason editor are byte-for-byte unchanged in behaviour.
  • No LLM code, no Worker change, and no prompt exists in the repo as a result of this story.

Gates

  • npm run check is green, with no new ignore directive, no --no-verify, and no tooling-config edit made to get there.
  • lib/database.types.ts is regenerated output, not hand-edited.
  • The four moved board baselines are regenerated by the updater and committed, with the diff image in the demo doc.
  • A demo doc exists and npm run demo -- verify reproduces it.

9 · Out of scope

DeferredWhy, and what it would take
Putting descriptions into the classifier prompt The whole point of the field, and explicitly ALF-158 story D's. There is no prompt assembly in the repo to add a line to, and story D has not been specced. This story ends at the column and the authoring surface (D9).
Descriptions on epics epics.notes already exists with a PATCH route and an inline editor on the board, so an epic has somewhere to say what it is. Whether the classifier should read notes or want a purpose-built description is story D's call, made with the prompt in front of it.
Renaming a project, or editing its key / repo Ruled out in refinement (§2). key is deliberately immutable — every ref, branch name and PR frontmatter carries it. A rename is a real feature with its own consequences; it is not a side effect of adding a text column.
Showing the description anywhere else — sidebar tooltip, project picker, gate dialog, backlog Each is a separate layout decision with its own truncation question, and none of them helps the owner write the description, which is what this story is for.
Searching descriptions from the command palette or global search Global search indexes items; folders appear only as a result's subtitle. Adding a second searchable entity type is its own change.
A character counter or a "too long" error state D3: the cap is a backstop three layers deep, not a workflow. A counter would be permanent chrome plus a new prop on an atom shared with two other flows, to serve a case that essentially never occurs.
Setting a description at creation time D7. The sidebar's create form is one inline field on purpose, and the new-project dialog is already three fields guarding a unique key.
Folding EpicHeaderActions into the extracted editor A pure refactor of working code that would drag the epic header — and its snapshots — into a story about a new column. Worth doing; not here.
