Working detail

Everything below is for the implementing agent. Approving needs only what’s above.

Context

ALF-188 asks for two things: the Code project title should glow in the project’s colour, and the owner should be able to choose that colour. The owner narrowed both in refinement: a palette pick, not any hex (D5), and the glow on the board title only (D6). The ticket also asked for the spec to offer several ways to open the picker (D1).

Today. Projects have no stored colour. frontend/lib/code/project-color.ts (ALF-50) assigns each one of five accents — blue, amber, green, red, teal — by its slot in creation order, round-robin (projectColorAt / projectColorFor). Every coloured project surface resolves through it with static Tailwind class maps: the sidebar glyph and key pill (project-nav.tsx), Backlog and Dashboard-queue badges (backlog-list.tsx, queue-widget.tsx), the PR-ratio bar (pr-ratio.tsx), the project filter menu (project-filter-menu.tsx), and the Tasks-side key chip, detail chips and project-suggest popover. The board header (components/code/board.tsx) renders the name as a plain font-serif text-2xl text-foreground h2 beside the mono key; it is the one place a project’s name appears uncoloured.

Builds on. ALF-179’s project description edit: PATCH /api/projects/[id], updateProjectSchema, and the store’s optimistic updateProjectDescription are the exact path the colour write reuses. The glow-* utilities in globals.css are box-shadows at 0.15 alpha — too faint for text, so the title gets its own text-shadow utilities (D10).

Decision records

D1Where do you open the colour picker? · settled

C · A palette button in the board toolbar (owner’s pick): an outline, icon-only Button size="sm" with lucide Palette, placed right after Create epic, the popover end-aligned beneath it. It sits with the board’s other controls rather than on the heading. Unlike the view filters (ALF-134) it does not fold into the ⋯ menu below md: a menu item would have to close the menu before opening a popover anchored to something no longer on screen, and one more 32px icon button still fits the phone row (Create epic · collapse glyph · palette · ⋯, Plate I). Accessible name: Project color: Green, or Project color: Blue (automatic); aria-expanded while open.

Considered: A, a swatch dot beside the key (recommended in the first draft); B, the title as the trigger; a button on each sidebar row (a button nested in a link is invalid HTML).

D2What does the glow look like? · settled

A · Tinted text with a soft glow (owner’s pick): color is the accent and text-shadow: 0 0 14px rgb(<accent> / 0.5). All five accents are the Tailwind -400 family on #0a0e17, so contrast stays well above AA for 24px text. The glow is static, so no reduced-motion variant is needed.

Considered: B, white text with a coloured halo.

D7Should the palette button show the colour? · proposed

The button’s Palette glyph takes projectTextClasses(color), so it shows the current colour, as the sidebar’s branch glyph already does. This recovers the one thing option A had and C lacks: you can see the colour without opening anything. Otherwise the toolbar, Plate I, is unchanged. Alternative: a muted glyph like the other toolbar icons, but then the only cue left would be the title itself.

D3Which colours are on offer? · proposed

Exactly PROJECT_COLORS (blue, amber, green, red, teal) plus Automatic. Adding violet (the sixth app accent) to the pickable set is tempting, but it would either have to join the round-robin — silently recolouring every automatic project, since slot n maps to n % 6 instead of n % 5 — or live in a separate pick-only list, splitting “the palette” in two. It is also the Wiki module’s hue. Left out; a later story can widen both lists together.

Automatic is the reset: it clears the override so the project returns to its slot colour, and it names that colour (“Automatic · Blue”) so the owner knows what they’ll get.

D4Where is the pick stored? · proposed

A nullable projects.color text column with a check constraint on the five keys; NULL = Automatic. Alternatives: localStorage (diverges between phone and desktop — rejected); a Postgres enum type (an extra type to regenerate and alter type … add value to extend; text + check matches the key column’s precedent). Consequence: existing rows are NULL, so nothing changes until the owner picks.

D5Any hex colour? · settled

Palette only (owner, refinement). Any-hex would move every project surface off static Tailwind classes onto inline CSS variables and allow unreadable picks on the dark background.

D6Which titles glow? · settled

The board title only (owner, refinement). The sidebar already carries the colour on its glyph and pill.

Implementation decisions

D8 · The override resolves inside projectColorFor

projectColorFor(projects, id) returns the project’s stored color when it is a palette key, else its creation-slot colour. Every call site already passes the creation-ordered list, so they all pick up the override with no change — except ProjectFilterMenu, which calls projectColorAt(index) directly and must switch to projectColorFor(projects, project.id). Automatic’s label uses projectColorAt(slot) (the colour it would revert to), exposed as projectSlotColorFor(projects, id).

D9 · Narrow the column with a guard

The generated Row.color is string | null. Add isProjectColor(value): value is ProjectColor; a value outside the palette (e.g. a future widened constraint read by an old client) falls back to the slot colour rather than throwing.

D10 · Title glow as static utilities

Five @utility text-glow-<colour> rules in globals.css, beside the existing glow-* block, carrying D2’s text-shadow; plus a PROJECT_TITLE_CLASS map and projectTitleClasses(color) in project-color.ts (e.g. 'text-accent-green text-glow-green'), written out in full so the Tailwind v4 scanner keeps every class — the same pattern as the four existing maps. The h2 drops text-foreground for it.

D11 · One ProjectColorPicker, trigger passed in

New components/code/project-color-picker.tsx composes the Popover atom: controlled open, the trigger passed as children through PopoverTrigger asChild, and the Plate I body. BoardToolbar renders it around its palette button (D1); keeping the trigger a child keeps the picker reusable if another surface wants it later. Picking closes the popover and fires onChange(color | null). UI copy spells “color”, as the ticket does (the app has no prior user-facing instance).

D12 · Store action mirrors the description write

updateProjectColor(projectId, color) uses runOptimisticMutation exactly as updateProjectDescription does: patch → api.updateProject(id, { color }) → reconcile from the saved row → roll back and toast Couldn't save the project color on failure.

D13 · Accessible picker

The six options are buttons with aria-pressed in a role="group" labelled Project color; swatches are named Blue … Teal, the reset Automatic (blue). The swatch colour is never the only cue: the pressed one carries the check glyph and ring. Radix supplies focus return and Escape.

Behaviour

  • Title. The board header resolves the colour with projectColorFor(useProjects(), projectId) — the creation-ordered list, not useProjectBoard’s project alone — and applies projectTitleClasses (P2, D10).
  • Opening. The toolbar’s palette button (D1) opens the picker end-aligned below it and shows a pressed state while open. Its glyph is in the project’s colour (D7). It is present at every width, never folded into the ⋯ menu (P1).
  • Picking a swatch closes the picker and recolours the project on every surface in the same frame (optimistic), P3. Picking the already-selected swatch just closes — no request.
  • Automatic sends color: null; it is the pressed option whenever the stored value is NULL (or invalid, D9). Picking it while already Automatic just closes.
  • Collisions are allowed. Two projects may share a colour — e.g. picking amber for project 1 while project 2 is automatically amber. No uniqueness check, no warning.
  • Failure. A rejected PATCH rolls the colour back everywhere and shows the toast (D12).
  • Unknown project. The board’s existing “could not be found” state renders no title and no trigger.

// lib/api/schemas.ts
export const updateProjectSchema = z
  .object({
    description: entityDescription.optional(),
    color: z.enum(PROJECT_COLORS).nullable().optional(),   // null = Automatic
  })
  .refine((body) => Object.keys(body).length > 0, { message: 'No fields to update' });

// app/api/projects/[id]/route.ts
const updates = toUpdatePayload<ProjectUpdate>(input, ['description', 'color']);

Acceptance criteria

  • The board title renders in its project’s colour with the D2 glow; no other surface gains a glow.
  • A palette button after Create epic, its glyph in the project colour, opens the picker. It is visible at desktop and phone widths, and its accessible name states the current colour and whether it is automatic.
  • The picker offers exactly blue, amber, green, red, teal and Automatic (naming the slot colour); the current choice is pressed, ringed and checked.
  • Picking a swatch recolours the title, sidebar glyph + pill, Backlog and Dashboard badges, PR-ratio segment + legend, filter-menu glyph and task key chips at once, and survives a reload.
  • Automatic clears the stored colour and the project returns to its creation-slot colour.
  • Existing projects render exactly as before the migration until a colour is picked.
  • The API rejects any color outside the five keys (and non-null non-strings) with 400.
  • A failed save rolls the colour back everywhere and shows Couldn't save the project color.
  • Picking the already-selected option closes the picker without a request.

Out of scope, risks & unknowns

  • Hex colours — D5. Sidebar glow — D6. Rename — the key is immutable by design (ALF-179); a name edit is its own story.
  • Auto-assignment skipping picked colours (to avoid collisions) is deliberately not done: it would recolour automatic projects whenever another project’s pick changes.
  • Confirm: lib/api/schemas.ts importing PROJECT_COLORS from lib/code/project-color.ts passes the lint import rules; if not, move the constant to a shared module both import.
