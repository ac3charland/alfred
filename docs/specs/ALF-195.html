ALF-195 — Endpoints for creating weekly-plan items and reading their status

Refinement Spec only — no implementation. Two keyed endpoints so the weekly-review coach can write a week's plan into alfred as real items, then read back what happened to them at the next review.

1 · Context & problem

The Friday review (the coach's weekly-review skill) already ends by generating a week-plan HTML document and posting it to POST /api/weekly-plans, where alfred's Week Plan view renders it in a sandboxed iframe. That document is a picture of the week: it is never diffed against what actually happened, and none of the work it describes exists in alfred unless the owner retypes it.

So the review loop has a hole at both ends. The plan's work never enters the system that tracks work, and at the next review the coach has to ask what got done — the least reliable possible source, a week later. What it wants instead is one call that answers: of the things we agreed to do last Friday, which are done, when were they done, and when were they scheduled for?

A week's plan is not homogeneous, either. It mixes shipping work that belongs in the Software Factory, ordinary scheduled chores, and half-formed intents that need a human's triage before they mean anything. The endpoint has to be able to say all three, and then get out of the way of the machinery alfred already has for sorting them out.

Everything needed to close that loop already exists except the two endpoints in this spec: the ingress key and its dual-auth helper, the item model (types, subtasks, due dates, priority, completion), the classifier that labels a fresh capture, and the plan archive to hang a cohort off.

2 · Scope, as settled in refinement

QuestionSettled
Does the title's “& projects” mean the Software Factory projects table? No. “Project” was meant in the to-do sense — an item with children. Nothing here creates a project, epic or story record.
Which item types may the coach create? All three — unclassified (the default), task and code — each stampable as part of the week's plan. Widened mid-refinement; it is the interesting decision in this spec, see D4.
How is an item stamped as belonging to a weekly plan? By the id of the plan document the coach posted — items.weekly_plan_id → weekly_plans.id. See D1.
One item per request, or a batch? Batch: one POST carries the whole week, roots with nested children, created atomically. See D3.
Where do the created items land? The Inbox, always — dispatched_at null, no folder. They are triaged by hand like every other capture. See D5.
Do they go through the LLM classifier? Yes, unchanged and deliberately. The sweeper fills only what the coach left blank. See D6 — it has one consequence the caller must know about.
How does the app show that an item came from the week plan? A Week plan badge in the row's metadata cluster, on the planned top-level row. Drawn in §6.

3 · Decisions

D1 The cohort key is the plan's id, not a date

New nullable column items.weekly_plan_id uuid references weekly_plans (id) on delete set null, written on every item the endpoint creates (roots and children).

Why the FK is available at all: POST /api/weekly-plans already answers with { id, uploaded_at }, and the review posts the plan (Step 9) before it would create items — so the id is in the coach's hand at exactly the moment it needs it. No new ordering constraint is introduced; the skill gains one step after the one it already runs.

Why not a weekly_plan_week date: a date is a second, parallel notion of “which week” that nothing else in the schema shares, and it is only as good as the caller's arithmetic — two calls a minute apart can disagree and silently split a cohort. The plan row is already the thing the review produced; joining to it also gives the read its uploaded_at for free, so the coach can quote the window it is reporting on.

on delete set null, not cascade: these are the owner's real items. Deleting an archived plan document must never delete work. (Nothing deletes a weekly_plans row today — the archive is append-only and has no DELETE route — so this is belt-and-braces.)

D2 Nested under the plan: /api/weekly-plans/[id]/items

One route file, both verbs. POST creates the cohort; GET reads it. The plan is in the path rather than the body, so the association can't be forgotten or contradicted. Items, not tasks: after D4 the endpoint writes all three types, and in this codebase “task” is one of them, not the family.

GET additionally accepts the literal segment latest — GET /api/weekly-plans/latest/items — resolving to the most recent plan that has at least one item attached. That is the coach's whole read: one URL, no arguments, no date arithmetic, correct whether the review is held on Friday, slipped to Sunday, or skipped a week.

Why “most recent with items” rather than “most recent”: re-posting a revised plan appends another archive row. If latest meant the newest row, one revision with no items attached would make the coach report an empty week. POST does not accept latest — a write names the plan it belongs to explicitly.

D3 The batch is one Postgres RPC, so a week lands whole or not at all

create_weekly_plan_items(p_plan uuid, p_items jsonb) returns setof items, security invoker, called from the route via supabase.rpc(...).

Why not two inserts from the route: roots and children can't go in one PostgREST insert (children need their parents' ids), and two round trips are two transactions — a failure on the second leaves a half-created week of childless roots that nobody can tell apart from a plan that really had no subtasks. A plpgsql function is one statement, so it is one transaction. This is also the repo's existing answer to “the client needs several related rows written together” — convert_to_code_epic and complete_and_spawn.

D4 Three item types, one discriminated union — the database already defines the three shapes

item_type is an optional field on each root, defaulting to unclassified exactly as POST /api/items and the capture box do. What a root may carry depends on it, because items_task_only_fields and enforce_subtask_shape already say so:

Field task code unclassified Enforced by
title, notes ✓✓✓—
due_date ✓✗✗ items_task_only_fields
priority ✓✗✗ items_task_only_fields (0010)
children ✓ any number ✓ one level ✗ items_task_only_fields (0019) + enforce_subtask_shape
child's own type inherited from the root — never stated enforce_subtask_shape forbids mixing families

So the request schema is a z.discriminatedUnion on item_type with three branches, and a child schema per branch. Every illegal combination becomes a 400 naming the field, instead of a 500 from a CHECK violation halfway through a batch.

Why children never state a type: the database permits exactly one answer (a code root's children are code stories-in-waiting; a task's are subtasks), so letting the caller state it only creates a way to be wrong. Making the illegal state unrepresentable is cheaper than validating it.

Why the default stays unclassified rather than becoming task: a plan line the coach hasn't typed is precisely the input the classifier exists to judge — see D6. Defaulting to task would decide the question on the coach's behalf and switch that machinery off. And it can't cause a silent loss: a due date or priority sent without "item_type": "task" is a 400 that says so, not a dropped field.

What is deliberately NOT accepted: folder_id, parent_id, status, completed_at, recurrence, source_url, and the pre-factory hints intended_project_id / intended_epic_id. The last pair is the interesting omission: a planned code item does need a project and an epic before it can enter the factory, but the coach has no way to discover project ids today, and both the classifier and Friday triage already fill them. Unknown keys are rejected rather than ignored, so a typo is loud.

D5 Created items land in the Inbox, untriaged

Every created row: status = 'active', dispatched_at = null, folder_id = null. The endpoint accepts no folder and does no dispatching.

Why: dispatch is a human act — that is the whole point of the dispatched_at column (0026), and the classifier was deliberately built to write labels without moving anything out of the Inbox. An agent filing twenty rows straight into folders would be the first thing in the system to bypass triage. The owner sees the week's work on Friday, in one place, and files it.

D6 The classifier sweeps these items like any other capture — nothing in the Worker changes

A created root matches the sweep predicate exactly (parent_id is null, dispatched_at is null, classified_at is null, classify_attempts < 5), so the cron picks it up within a couple of minutes — 10 items a tick, every 2 minutes, oldest first. A 21-item week is fully judged in about six minutes for ~21 Haiku calls.

It cannot contradict the coach, because mergeIntoItem writes only fields the item does not already hold. What that means per type:

The coach sentWhat the classifier may add
unclassified + a title Everything. decidedType treats unclassified as “nobody has decided”, so the model picks the type and then whatever fields that type allows — a folder for a task, a project/epic hint for a code item. This is the intended path for a vague plan line, and the reason the default is what it is.
task + due date + priority A folder, and nothing else. Every other field is already held. This is pure upside: it is the one label Friday triage has to supply by hand.
task + no due date A folder and a due date of its own choosing — see the warning below.
code intended_project_id and intended_epic_id: exactly the two hints a code item needs before it can be dispatched to the factory, which is why D4 doesn't accept them from the caller.
any child Nothing. The sweep is parent_id is null. A subtask keeps precisely what the coach sent it.
The one surprise, and it belongs in the primer: a task sent without a due_date can come back carrying one the model inferred from the title (“file taxes by the 15th”), and the read endpoint will then report it as the day the item was scheduled for — a date the coach never chose but will quote back as if it had. The fix is guidance, not code: a plan line with a day is a task and carries its due_date, and the review is planning day by day anyway. Suppressing the sweep instead would cost the folder suggestion on every item to prevent a guess on a few.

A quiet benefit: dispatching a classified item logs the diff between the model's guess and the labels the owner settled on (classification_corrections, 0029), which the next sweep reads back as worked examples. Twenty agent-authored items a week, each corrected by hand on Friday, is the richest training signal the classifier has ever had.

Rejected alternative: stamping classified_at = now() in the RPC to opt the cohort out. It saves ~20 cheap calls a week, loses the folder suggestions and the corrections log, and makes every planned row render the claimed provenance mark — the pencil that means “you labelled this”, which would be a small lie on every row. Honestly marking agent provenance would need a fourth origin and its own glyph: a real option, but a different ticket.

D7 The array's order is the order the Inbox shows — via explicit timestamps

The RPC writes created_at := v_now - (v_index * interval '1 millisecond') for the root at array position v_index. Children keep their parent's value and rely on sort_order (the sequence default increments per insert, so array order is preserved).

Why this is not incidental: buildTree sorts roots by created_at descending, and every row in one transaction gets the same now(). Twenty identical timestamps means the tie-break is whatever order Postgres happens to return — unstable across reloads and after any update. The offset makes array position 0 the newest row, so the week reads top-down in the Inbox in exactly the order the coach sent it, deterministically. The fabricated spread is ≤ 100 ms (the batch cap) and never in the future.

D8 The read answers with the tree, pre-counted, and follows a code item into the factory

GET returns the plan it resolved, a counts object and the items as a nested tree. Each node carries its item_type, status, completed_at, due_date, priority, created_at, its folder, whether it is still in the Inbox, and — when the item has entered the Software Factory — its code sidecar (ref, factory_state).

Why the sidecar is not optional: completion is task-only in this schema. A code item's status is always active and its completed_at is always null, because the CHECK forbids anything else — so reporting a shipped story as “active” would be the exact false answer this ticket exists to prevent. For a code item, “done” lives in code_items.factory_state, and ALF-201 · ready_for_review is a far better review line than a boolean anyway.

Why pre-counted: the same reason /api/habits pre-rounds its numbers — a figure the coach recomputes is a figure that can disagree with the app. Why no “overdue” count: overdue needs a timezone and a notion of today, which would put date policy in a payload whose consumer already has both. Why the folder: paired with in_inbox it distinguishes “done and filed” from “never triaged”, which is the more interesting review finding.

D9 Both verbs authenticate through resolveIngestClient

Valid INGEST_API_KEY (x-api-key or Authorization: Bearer) → the admin client; otherwise a browser session; otherwise 401. Same key the coach already holds for the plan archive, the PR ratio and habits.

Not withSessionOrApiKey: it yields no Supabase client, so a keyed caller — which carries no cookie — would fall through to an anonymous read and get a cheerful 200 with an empty list. The habits route documents this exact trap; a coach told “you created nothing last week” by an auth bug is worse than an error.

5 · The database change

One migration, database/migrations/<next>_weekly_plan_items.sql — take whatever number is free when you build it, not one written here.

5.1 The column

alter table items
  add column weekly_plan_id uuid references weekly_plans (id) on delete set null;

comment on column items.weekly_plan_id is
  'The archived week-plan document this item was created from (ALF-195). NULL = an ordinary '
  'capture. Written by create_weekly_plan_items on the root AND every child, so the cohort is '
  'one query. on delete set null: the item is real work and outlives the plan document.';

-- The only query shape: "every item belonging to this plan".
create index items_weekly_plan_id_idx on items (weekly_plan_id)
  where weekly_plan_id is not null;
Not added to items_task_only_fields. The column is provenance, and it must survive every type transition the app already performs — enter_code_module flips an item to code in place, and a CHECK naming the column would turn “I planned this and then sent it to the factory” into a write error on a legitimate flow.

5.2 Re-expand task_items — mandatory

create or replace view task_items with (security_invoker = true) as
  select i.* from items i
  where not exists (select 1 from code_items c where c.item_id = i.id);

select i.* freezes its column list at CREATE time, so without this the new column is invisible to the whole read path — getAllItems() reads this view and overrides the result to Item[], so the badge would read undefined where the type promises string | null. The bug 0011, 0013, 0018, 0026 and 0029 each document. create or replace (never drop) keeps the grants and security_invoker. v_code_stories is deliberately left alone — it enumerates its columns explicitly, and nothing in the code module reads the cohort (§10).

5.3 The batch RPC

create or replace function create_weekly_plan_items(p_plan uuid, p_items jsonb)
returns setof items
language plpgsql
security invoker
as $$
declare
  v_now   timestamptz := now();
  v_index int := 0;
  v_item  jsonb;
  v_child jsonb;
  v_type  item_type;
  v_root  items;
  v_kid   items;
begin
  if not exists (select 1 from weekly_plans where id = p_plan) then
    raise exception 'weekly plan % not found', p_plan;
  end if;

  for v_item in select * from jsonb_array_elements(p_items) loop
    -- The route's schema has already rejected every field this type may not carry, so the
    -- inserts below need no per-type branching: an absent key is simply NULL.
    v_type := coalesce(v_item ->> 'item_type', 'unclassified')::item_type;

    -- D7: one transaction shares a single now(), and buildTree sorts roots by created_at DESC.
    -- Descending offsets make array position 0 the newest row, so the Inbox reads top-down in
    -- the order the caller sent. Never in the future; ≤ 100ms of spread at the batch cap.
    insert into items (title, notes, item_type, due_date, priority, weekly_plan_id, created_at)
    values (
      v_item ->> 'title',
      v_item ->> 'notes',
      v_type,
      (v_item ->> 'due_date')::timestamptz,
      (v_item ->> 'priority')::task_priority,
      p_plan,
      v_now - (v_index * interval '1 millisecond')
    )
    returning * into v_root;
    return next v_root;

    -- Children inherit the root's type (enforce_subtask_shape forbids mixing families) and its
    -- created_at: a subtask group sorts by sort_order, whose sequence default increments per
    -- insert, so array order is preserved with nothing to compute.
    for v_child in
      select * from jsonb_array_elements(coalesce(v_item -> 'children', '[]'::jsonb))
    loop
      insert into items (title, notes, item_type, due_date, priority, weekly_plan_id,
                         parent_id, created_at)
      values (
        v_child ->> 'title',
        v_child ->> 'notes',
        v_type,
        (v_child ->> 'due_date')::timestamptz,
        (v_child ->> 'priority')::task_priority,
        p_plan,
        v_root.id,
        v_root.created_at
      )
      returning * into v_kid;
      return next v_kid;
    end loop;

    v_index := v_index + 1;
  end loop;
end; $$;

-- security invoker: the column defaults (sort_order's nextval) and the row inserts run as the
-- CALLING role, so all three need EXECUTE (the 0008 sequence-grant lesson's sibling).
grant execute on function create_weekly_plan_items(uuid, jsonb)
  to anon, authenticated, service_role;

notify pgrst, 'reload schema';

The database is the backstop, not the validator: items_task_only_fields rejects a due date on a non-task row and enforce_subtask_shape rejects a mixed family, so a schema bug fails loudly and atomically instead of writing an incoherent week. dispatched_at is never set, so inherit_dispatched_at (0026) leaves root and children alike in the Inbox and the pair can't be split across two views.

6 · The surface — the Week plan badge

One new chip in the row's metadata cluster: a muted pill reading Week plan behind the CalendarRange glyph — the same lucide icon the Week Plan nav item and view header already use, so the badge points at the place the plan document itself lives. Muted, not coloured: the row's five colours are spoken for (blue = due, amber = due today, red = overdue / high, teal = interactive, green = dispatch-ready), and this is a label like the Type badge, not a verdict.

6.3 The rule, in one line

RowMetaCluster renders <WeekPlanBadge /> when node.parent_id === null && node.weekly_plan_id !== null, positioned directly after the Type badge. Not isTopLevelTask — that term is isTask && parent_id === null, and after D4 a planned root may be any of the three types.

It is inert in both mounts (an always-span, like DispatchReadyMark) — there is nothing to click: the badge is provenance, and select mode's row is one <button> that forbids a nested control. hasMeta gains the same term, or the unclassified row drawn above renders no footer at all.

Where it deliberately does not appear. (a) On children — the badge marks the planned item, and a subtask sits under one. A completed subtask that buildTree lifts to a root in the Completed view still shows none, and that view already names its parent in the row's context label. (b) On the code board and backlog: once a planned code item is dispatched to the factory it gains a code_items sidecar and leaves the Tasks views entirely, and the code module reads v_code_stories, which enumerates its columns — badging it there is a one-line view change plus card work, deferred to §10. The API still reports it either way, which is what the review actually consumes.

No date on the badge. Resolving the plan's uploaded_at would make a task row depend on the weekly-plan store to render a chip, for a date that is one click away in the Week Plan view. The accessible name is the badge's own words (Week plan item).

10 · Out of scope, and known limits

  • Creating projects, epics or stories. The endpoint creates items, including code-typed ones; entering the factory stays a human act through the existing gate, which is also where the project and epic get chosen.
  • intended_project_id / intended_epic_id on create. The coach can't discover project ids today. The classifier fills both for a code item, and triage confirms them (D4). A GET /api/projects for the key list would be the enabler if we ever want the coach to state them.
  • The badge on the code board / backlog. A dispatched code item leaves the Tasks views, and v_code_stories doesn't carry the column. One line of view plus card work when it's wanted (§6.3).
  • Updating, deleting or re-pointing a cohort. No PATCH, no DELETE. A mis-created week is fixed at the keyboard, like any other item.
  • No de-duplication. Two identical POSTs create two sets of items. Appending is deliberate — it lets a mid-week check-in add to the same cohort — but the endpoint has no memory of what it wrote, so a retried call after a timeout duplicates. The coach creates the week once, after the plan is posted.
  • Deleted items leave no trace. The cohort is “rows that still exist”, so an item the owner deleted is indistinguishable from one that was never created. Tombstones would be a schema change for a case the review can just ask about.
  • A planned parent converted to an epic disappears from the cohort. convert_to_code_epic deletes a non-task parent (its children become stories and keep the column, so most of the cohort survives). Not worth special-casing: the stories carry the provenance, which is what the review reads.
  • No cohort surface in the app beyond the badge — no “week plan” filter, view or section, and no live status panel next to the plan document.
  • No timezone or overdue arithmetic in the payload (D8).
  • No paging. A cohort is tens of rows; the read takes a single 1000-row range, which the 100-node create cap keeps well clear of unless a plan is appended to ten times.
  • The coach's own skill lives outside this repo. In scope here is the primer it is generated from.

Open questions

  1. Should the Week Plan view show the cohort's live status beside the document? The plan says what was intended and the items say what happened; putting them on one screen is the obvious next move, but the review loop doesn't need it and it is a view's worth of design. Deferred, not rejected.
  2. What should happen when a revised plan is re-posted mid-week? Today the cohort stays attached to the id it was created against, and latest keeps resolving to it (it is the newest plan with items), so nothing breaks. If revisions become routine we may want a way to re-point a cohort at the new document — a small follow-up, not part of this.

11 · Acceptance criteria

  • Database
  • items.weekly_plan_id exists, nullable, FK to weekly_plans (id) with on delete set null, commented, and indexed by a partial index on the non-null set.
  • It is not named in items_task_only_fields, and survives enter_code_module.
  • task_items is re-created in the same migration and exposes the new column.
  • create_weekly_plan_items(uuid, jsonb) exists, is security invoker, is granted to anon, authenticated, service_role, and writes a whole batch or none of it.
  • Created rows carry the caller's type (defaulting to unclassified), children inherit their root's type, and every row is status = 'active', dispatched_at = null, folder_id = null, with weekly_plan_id set on roots and children alike.
  • Root created_at descends with array position, so the Inbox lists the week in the order it was sent.
  • migration-lint passes and frontend/lib/database.types.ts is regenerated by its generator and committed verbatim.
  • POST /api/weekly-plans/{planId}/items
  • Accepts the ingest key (x-api-key or bearer) or a browser session, and reads through the admin client on the keyed path; otherwise 401.
  • Creates task, code and unclassified roots, with children where the type allows them, and returns 201 with { plan, created, items }.
  • Enforces the D4 matrix at parse time: a due date or priority on a non-task root, children on an unclassified root, a child with its own item_type or its own children, an unknown key, a blank title, an empty batch or a batch over 100 nodes are each a 400 carrying zod details.
  • 404 for an unknown plan id and for the latest segment; nothing is written in either case.
  • GET /api/weekly-plans/{planId|latest}/items
  • Same auth rule as above.
  • latest resolves to the most recent plan that has at least one item — a newer item-less plan does not win.
  • Returns { plan, counts, items } with the tree nested and ordered as the app shows it, each node carrying item_type, status, completed_at, due_date, priority, created_at, folder, in_inbox and code.
  • A code item in the factory reports its ref and factory_state; one that never entered reports code: null.
  • counts.done + counts.open + counts.abandoned === counts.total, with done covering completed tasks and done code items; untriaged counted independently.
  • No cohort at all → 200 with plan: null, zeroed counts, empty items. An unknown explicit id → 404. A non-UUID, non-latest segment → 400.
  • The app
  • A top-level item of any type carrying weekly_plan_id shows the Week plan badge — muted pill, CalendarRange glyph — directly after the Type badge, in the Inbox, folder views, By-Priority, Completed and select mode.
  • Its children show no badge, and an item with no weekly_plan_id shows none.
  • A row whose only metadata is the badge still renders its metadata footer.
  • The badge is a non-interactive span in every mode and carries an accessible name.
  • No other row chrome moves: the drawings in §6 are the whole visual diff.
  • Docs & evidence
  • docs/productivity-coach-primer.md documents both endpoints in its existing format, carries the per-type matrix and the D6 due-date warning, ships a script for each, and no longer lists task creation as out of scope.
  • database/README.md summarises the migration.
  • A demo doc under docs/demos/ALF-195-weekly-plan-items/ shows create → badge → complete → read, and npm run demo -- verify is green.
  • Root check (fast + slow) is green, with no ignore directive, config relaxation or --no-verify anywhere in the change.
