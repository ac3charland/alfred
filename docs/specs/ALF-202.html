ALF-202 — Still run items classified as “Task” or “Code” through the LLM classifier

Refinement Spec only — no implementation. Giving a capture its type, or typing a description into it, stops counting as “this one’s mine”: the row stays eligible for the classifier sweep, and the answer you gave it is locked against the model exactly as a code item’s project already is.

1 · Context & problem

Since ALF-158 shipped its first stories, a cron sweep in workers/ reads the Inbox items nobody has touched yet, asks Haiku for a verdict, and writes the guesses straight onto the item’s real fields — type, priority, due date, folder for a task, project and epic for a code item. Eligibility is one column: items.classified_at is null.

Two things stamp that column. The sweep stamps it when it writes a verdict. And 0029_llm_classifier.sql’s claim rule stamps it — with the provenance columns left null — the moment a human edits a watched field on a row the sweeper hasn’t reached yet: 

-- database/migrations/0029_llm_classifier.sql, the claim trigger as it stands
if new.classified_at is null and (
     new.title     is distinct from old.title
  or new.notes     is distinct from old.notes
  or new.item_type is distinct from old.item_type
  or new.priority  is distinct from old.priority
  or new.due_date  is distinct from old.due_date
  or (new.folder_id           is distinct from old.folder_id           and new.folder_id           is not null)
  or (new.intended_project_id is distinct from old.intended_project_id and new.intended_project_id is not null)
  or (new.intended_epic_id    is distinct from old.intended_epic_id    and new.intended_epic_id    is not null)
) then
  new.classified_at := now();   -- provenance stays null: no model ran
end if;

The intent is right — “the machine must never change your answer back” (epic D10) — but the watch list is drawn around any edit rather than around the fields the machine actually writes, and that catches the two things you most often do to a fresh capture before it has been judged.

The type is the price of admission to everything else

An unclassified row is deliberately inert in the Inbox. It shows no chip row in the detail panel (“classify from the ⋯ menu first; the fields appear once there is a type to hang them on”), and it cannot take children at all — canAddSubtask = isTask || isCodeRoot in frontend/lib/hooks/use-task-row-flags.ts. So the natural shape of capturing a piece of work with parts —

  1. capture “Plan Mom’s birthday”,
  2. classify it Task so it can hold subtasks,
  3. type the two or three parts in under it,

— spends its second step opting the item out of the classifier permanently. And step 2 is exactly what makes the row need help: a task is dispatch-ready only once it carries a folder (dispatchReadiness in frontend/lib/tasks/dispatch.ts), and a folder guess is the one label the classifier is best at. The row that most wants a folder is the row guaranteed not to get one.

A description is the classifier’s input, and it disqualifies the row

buildUserMessage sends Title, Notes, Captured text and Source. Notes are read by the model on every single call. Under today’s rule, adding the sentence that would have made an ambiguous capture classifiable is the act that guarantees it is never classified.

The asymmetry that names the bug

The claim trigger is before update. An insert never claims. So the weekly-review endpoint from ALF-195 can already POST an item that arrives item_type = 'task' with a due date and a description, and the sweeper will happily add the folder it is missing — that is ALF-195’s D6, working as designed and documented.

Do the identical thing by hand, ten seconds after capture, and the item is dead to the classifier. Same row, same fields, same intent — different ingress. The API can hand the model a typed item; the UI cannot.

The epic left this open on purpose. ALF-158 §7, open question 2: “Does editing an item without dispatching it make it permanently yours? Proposed: yes — any human touch marks it and the sweeper never revisits.” This story is the owner’s answer, and it is no — not for content, and not for the type.

2 · Scope, as settled in refinement

QuestionSettled
Does setting item_type by hand claim the row? No. The row stays eligible and the type is locked against the model instead — the treatment intended_project_id already gets. See D2.
Does adding notes / a description claim the row? No, and neither does editing the title. Content is what the classifier reads; only labels are what it writes. See D1.
Do the remaining label edits still claim? Yes, unchanged — priority, due_date and the three FK hints in their existing non-null-only direction. That is the half of the rule that is doing real work. See D8.
Is the model told the type the owner already chose? Yes. Without it a disagreement is a guaranteed no-op that still marks the row forever. The prompt states the held type and the per-request schema pins it; PROMPT_VERSION goes 1 → 2. See D3.
What stops the sweep from overwriting a type set while it is mid-flight? The verdict write becomes a compare-and-set on the type it judged, alongside the marker check it already carries. See D4.
Does anything else break once a classified item can hold children? Yes, one thing, and it is fixed here: a dispatched subtask with no folder violates items_dispatched_needs_folder. A new trigger has it inherit its root’s folder. See D5.
Are rows already claimed by an edit re-opened? No backfill. The new rule applies from the migration forward. See D7.

3 · The rule, before and after

The claim trigger only ever fires while classified_at is still null — its own first condition. So this is not a rule about ownership in general; it is a rule about who wins the couple of minutes between capture and the sweep. Everything below concerns that window and nothing else. Once a row is judged (or claimed), no later edit re-stamps anything.

Edit, on an unjudged row Today After Why
title claims no claim The classifier reads the title; it never writes it. A rewritten capture is a better input, not a settled row.
notes claims no claim Same: it rides in the user message on every call.
item_type claims no claim — locked instead The one field the row needs before it can hold children or show a chip row. The model may not change it, which mergeIntoItem already guarantees.
priority claims claims (unchanged) Both are fields the classifier writes, and both claim in either direction. On an unjudged row a value can only have come from you or from the capture that created it, so emptying one says as much about the label as setting one does.
due_date claims claims (unchanged)
folder_id, intended_project_id, intended_epic_id claims when set to a non-null value unchanged The non-null-only carve-out is load-bearing and stays exactly as 0029 wrote it: all three are on delete set null, and a folder delete must not claim the rows it returns to the Inbox.
Any other column
(classify_attempts, dispatched_at, sort_order, status, …)		 no claim unchanged Never watched. The sweeper writes the attempt counter itself.

Both right-hand states are terminal for the sweeper: it never revisits either. The only thing this story moves is which edits keep a row on the left.

4 · Decisions

D1The claim rule covers what the classifier writes, not everything a human can touch. Title and notes come off the list.

The rule exists to stop the machine changing your answer back. That is only possible on a field the machine writes. title and notes are the classifier’s input: they ride in the user message, and nothing in the epic lets the Worker write either (ALF-158 §out of scope: “Titles and notes stay byte-for-byte as captured”).

Why it reads as a bug today: improving the text a classifier reads should improve its answer, not cancel it. The current rule turns “let me add a line so this makes sense next week” into “this item is now permanently unlabelled”, which is the opposite of what the owner intended by typing.

What it gives up: a capture you deliberately rewrote no longer counts as claimed on the strength of the rewrite alone. If you want a rewritten row to be yours, set a label on it — which is the same gesture that makes it dispatch-ready anyway.

D2item_type comes off the watch list and is locked instead — exactly like intended_project_id

The ticket’s own phrasing: “leave the classification field locked, like we do with code projects”. That lock already exists and needs no new code — mergeIntoItem in workers/src/verdict.ts reduces every verdict to the fields the item does not already hold: 

// workers/src/verdict.ts — the lock, already written
const existingType = decidedType(item);          // 'task' | 'code' | undefined ('unclassified')
const finalType    = existingType ?? verdict.item_type;
return {
  item_type: existingType === undefined ? verdict.item_type : undefined,   // never overwritten
  priority:  finalType === 'task' ? gap(item.priority, verdict.priority) : undefined,
  ...
};

Note finalType: the type the row will end up with decides which fields are legal, so a held task keeps a folder guess and discards a project guess, and vice versa. An ALF:-prefixed capture has relied on this since the sweep shipped — it arrives code with a project set and usefully gains an epic. All this story does is let a hand-set type reach the same code path an insert-set one already does.

Consequence worth naming: the sweep now judges rows the owner has already typed, so the dispatch-time diff has a new and honest lesson to record — item_type · changed · guessed code · chose task. That correction is fed back as a worked example on the next tick (selectExamples), so hand-classifying trains the classifier instead of hiding from it.

D3The model is told the type the owner already chose, and the schema pins it

Without this, D2 quietly fails half the time it matters. Consider a row the owner set to task where the model reads it as code:

  • validateVerdict drops priority / due_date / folder_id — they are task-only and the verdict says code;
  • mergeIntoItem drops intended_project_id / intended_epic_id — they are code-only and the row is a task.

Every field is dropped, the row is stamped classified_at, and it is never swept again. One wasted call, zero fields, no second chance — on precisely the workflow this story exists to serve.

So when the item already holds task or code:

  • The user message states it, e.g. Already classified by the owner: task. This is settled — judge only the fields that apply to a task.
  • The schema pins it. buildSchema is already rebuilt per request from live ids, so item_type becomes a single-value enum ({ enum: ['task'] }, no null branch) instead of nullableEnum(ITEM_TYPES). Structured output then makes echoing it the only legal response, and the parse path is unchanged.
  • PROMPT_VERSION goes 1 → 2 (0029’s column comment: bumped by hand when the prompt text or the output schema changes meaningfully).

Why pin the schema rather than only ask nicely: the echo keeps classified_guess.item_type equal to the row’s type, so the dispatch diff’s continue when v_guessed is not distinct from v_chosen skips it. Dropping the key instead would log a phantom filled_in correction on every hand-classified item and teach the example block a lesson the model was never asked to give.

Unpinned when there is no type. An unclassified row is unchanged in every respect: same prompt, same nullable enum, same abstention rule (“it may stay null”).

D4The verdict write becomes a compare-and-set on the type it judged

Today the claim rule doubles as the sweep’s concurrency guard: change anything mid-flight and the row gets classified_at, so the verdict’s onlyIfUnclassified filter matches nothing and the owner wins. Take item_type off the watch list and that guard disappears for exactly the field the owner is most likely to be setting while a tick runs — the window is real (a sweep is up to ten items at up to two attempts × 10 s each).

Two ways it goes wrong without a guard:

  • The sweep read unclassified, the owner set task, the verdict says code → the machine changes your answer back, the one outcome epic D10 exists to prevent.
  • The sweep read unclassified and is writing a task-shaped due date; the owner set code → items_task_only_fields rejects the whole PATCH, the coherent fields die with the incoherent one, and an attempt is burned.

So the write carries the type it judged as a precondition:

PATCH /rest/v1/items?id=eq.<id>&classified_at=is.null&item_type=eq.<the type as READ>

Zero rows back means the row was re-typed (or deleted, or judged by an overlapping tick) — the existing “gone or already classified” branch, which logs and counts no attempt. The row is simply still eligible on the next tick, and that tick re-reads the owner’s type and judges under it. The retry mechanism is the loop, exactly as everywhere else in the sweep.

Why always, not only when the verdict writes a type: the payload is derived from the read-time type either way — which fields are legal, which are gaps — so the precondition is “nothing about the type moved under me”, and that is true for both failure shapes above.

D5A subtask being dispatched with no folder inherits its root’s

This is the one consequence of the change that is not in the trigger, and it is not hypothetical — it lands on the exact workflow the ticket names.

  • items_dispatched_needs_folder (0026): a dispatched task must hold a folder.
  • Dispatch PATCHes every row of the subtree with { dispatched: true } — collectSubtree in dispatchItems.
  • Every existing folder writer cascades: setFolder, moveTask and bulkMove all write the folder across the subtree. The classifier does not — it PATCHes one row by id.

So a decomposed task whose folder came from the model has children with folder_id = null, and dispatching it fails their PATCHes on the CHECK. It is unreachable today only because classifying to add children claims the row; this story makes it reachable. Order matters and the likely order is the bad one — children are usually added within seconds of the classify, before the next tick. 

-- new in this migration: 0026's inherit_dispatched_at, one beat later in the life of a row
create or replace function inherit_folder_on_dispatch() returns trigger
language plpgsql security invoker as $$
declare v_root_folder uuid;
begin
  if new.parent_id is null                     then return new; end if;  -- roots carry their own
  if new.folder_id is not null                 then return new; end if;  -- already labelled
  if new.item_type = 'code'                    then return new; end if;  -- exempt from the CHECK
  if old.dispatched_at is not null
     or new.dispatched_at is null              then return new; end if;  -- only the transition
  with recursive ancestry as (
    select id, parent_id, folder_id from items where id = new.parent_id
    union all
    select i.id, i.parent_id, i.folder_id from items i join ancestry a on i.id = a.parent_id
  )
  select folder_id into v_root_folder from ancestry where parent_id is null;
  new.folder_id := v_root_folder;
  return new;
end; $$;

create trigger items_inherit_folder_on_dispatch
  before update on items
  for each row execute function inherit_folder_on_dispatch();

The ROOT’s folder, not the parent’s. The subtree’s PATCHes are issued together (Promise.all), so at depth ≥ 2 a middle row may not have been filled in yet when its child’s trigger runs. Walking to the root is the only reading that is order-independent, and it matches the app’s own invariant that a subtree shares one folder bucket.

The trigger name is load-bearing. Postgres fires before update row triggers in alphabetical order, and items_claim_from_classifier sorts before items_inherit_folder_on_dispatch. The claim trigger therefore sees folder_id still null and does not claim the child on the way through. A rename that reversed the order would silently start stamping children, so the ordering gets its own assertion.

In the database, not in dispatchItems, for 0026’s stated reason: three ingresses already dispatch (the bulk PATCH, enter_code_module, convert_to_code_epic) and only the database sits under all of them. The two RPCs are no-ops here — a code row is exempt by the guard above.

D6A row you typed and the model then judged reads “Labelled by the classifier”. No fourth provenance state.

classificationOrigin derives three states from two columns, and this story changes which rows land where: hand-classifying no longer flips a row to claimed immediately. It stays unjudged until the sweep reaches it, then becomes model — even though the type on it is yours.

That wording stays as it is. The mark answers “did a model touch this row?”, which is a fact about the past and is exactly true here; a per-field provenance display would be a different feature, and a mixed state would need a fourth glyph for a distinction the owner can already see (they set the type; they remember). claimed keeps its meaning and stays reachable — it is now what a label edit produces.

No code change: frontend/lib/tasks/classification.ts, ClassificationMark and their tests are untouched. This decision is recorded because the meaning of a rendered glyph shifts underneath them, not because anything is edited.

D7No backfill — the new rule applies from the migration forward

The sweeper has been live for weeks, so the Inbox holds rows claimed under the old rule. They are identifiable as a set (classified_at is not null and classified_provider is null) but not by which field claimed them — the trigger records no reason. Re-opening the set would also re-open rows claimed by a deliberate priority or folder edit.

Why that is the right trade here: the epic already put “retro-classifying the existing backlog” out of scope as a separate decision with a separate cost, and the honest fix for a row you want re-judged is the manual re-classify action the epic sketches (story K), reading from raw_capture. A migration that quietly spends model calls on the whole Inbox is not the same size of change as a trigger edit.

D8Clearing a label still claims — including the one awkward case

priority and due_date keep claiming in both directions. On an unjudged row the value being cleared can only have come from you or from the capture that created it, so emptying one is as much a statement about a label as setting one — and a rule where clearing did not claim would let the next tick put a value straight back into a field you had just emptied.

The awkward case: classifyPatch sends { item_type: 'code', due_date: null, recurrence: null } when a task becomes a code item. On an unjudged row that already carries a due date, that clear claims — so the type flip the owner made is accompanied by a claim after all.

Accepted, not fixed. Reaching it needs an unjudged row that already has a due date, which only an insert can produce (the weekly-plan endpoint, or a capture created with one). The ordinary paths are all clean: unclassified → task/code is a bare { item_type } patch, and code → task clears only the two FK hints, which claim in the non-null direction only. Widening the carve-out to cover it would weaken the half of the rule that works, for a case that is rare and whose outcome (the row is yours) is not harmful.

5 · The database change

One migration, database/migrations/<next>_classifier_claim_rule.sql — take the next free number at implementation time, don’t reserve one now. No columns, tables, views or grants change, which means:

  • No task_items recreation. The 0011 / 0013 / 0026 / 0029 view-freeze trap does not apply — nothing is added to items.
  • Nothing for migration-lint’s sequence-grant or view-grant rules to find, but the file still has to pass it (it runs in the global check:fast).
  • npm run gen-types -w database must still be run and its output committed: the integration suite’s freshness gate fires on any branch that touches database/migrations/, and expects the committed frontend/lib/database.types.ts to match. It should come back byte-identical here — commit it either way rather than discovering the gate at push time.

1 · The claim rule, narrowed

create or replace function claim_item_from_classifier() returns trigger
language plpgsql security invoker as $$
begin
  -- Only the fields the classifier WRITES claim the row (ALF-202). Title and notes are its
  -- INPUT — improving the text it reads must not cancel the reading — and item_type is locked
  -- against the model by mergeIntoItem rather than defended by opting the row out, so that
  -- classifying a capture (the only way to give it children) still leaves it eligible.
  if new.classified_at is null and (
       new.priority  is distinct from old.priority
    or new.due_date  is distinct from old.due_date
    or (new.folder_id           is distinct from old.folder_id           and new.folder_id           is not null)
    or (new.intended_project_id is distinct from old.intended_project_id and new.intended_project_id is not null)
    or (new.intended_epic_id    is distinct from old.intended_epic_id    and new.intended_epic_id    is not null)
  ) then
    new.classified_at := now();   -- provenance columns stay null: no model ran
  end if;
  return new;
end; $$;

The trigger itself (items_claim_from_classifier) is not re-created — the function body is replaced in place, so nothing about its firing order moves.

The sweep, walked through the case this story is for

  1. The owner captures “Plan Mom’s birthday”. Row: unclassified, classified_at null.
  2. They classify it Task from the ⋯ menu — a bare { item_type: 'task' } PATCH. No claim. They add two subtasks (children: parent_id set, so never eligible themselves).
  3. Within two minutes the sweep selects the root: parent_id is null, dispatched_at is null, classified_at is null, classify_attempts < 5.
  4. The request says the type is settled and pins the schema to task. The model answers a folder (Family), and abstains on priority and due date — the title signals neither.
  5. The verdict write lands on …&classified_at=is.null&item_type=eq.task. The row gains folder_id and the five provenance columns in one UPDATE.
  6. The Inbox row now shows a Family chip and the dispatch-ready pip. Dispatch sends the root and its two children; the children inherit Family from the root as the trigger writes their residency (D5).
  7. If the owner had overridden the folder before dispatching, the diff logs folder_id · changed · Family → <theirs>, and the next sweep carries it as a worked example.

A demo doc in its own folder — docs/demos/<feature-name>/<name>.md, the branch stamped into front matter by npm run demo -- init — authored with the showboat skill and reproducing under npm run demo -- verify. Follow that skill's evidence-matching rules rather than anything restated here, and note demo-lint's no-test-in-demo: a demo shows the new behaviour, it never runs the suites.

Extending it beats writing a second harness:

  • sweep, on a hand-classified row. The same row, typed task by hand, swept: show it selected as eligible, show the assembled request with item_type pinned to { enum: ['task'] } and the "already classified by the owner" line, and show the row after — the type still yours, the folder new.

No screenshot is required. Nothing new renders (§7), and the one visible effect — a folder chip appearing on a hand-classified row — needs a real sweep against a real model to produce, which is not reproducible in a demo.

10 · Out of scope, and known limits

  • No backfill. Rows already claimed stay claimed (D7).
  • No manual re-classify. The epic’s “re-classify from raw_capture” story is still the answer for a row you want judged again, and is still unbuilt.
  • The classifier still never writes title or notes. D1 changes what an edit to them means, not who may write them.
  • No change to which fields a verdict carries, to the abstention rules, to the sweep cadence, the item cap, or the attempt ceiling.
  • The type is pinned; the other held fields are not. A row that already holds a folder still gets a folder guess, which the merge then drops. Cheap, and it keeps the correction log’s reading of “what would the model have said?” honest for those fields. Only item_type earns the pin, because only it can invalidate the whole verdict (D3).
  • The children of an eligible root are still never swept (parent_id is null). A subtask keeps exactly what it was created with.
  • Known limit: a notes edit landing while a tick is in flight is not re-judged — the verdict was formed from the older text and marks the row. Harmless (the guess is merely made with less information), and the honest fix is the manual re-classify action above, not a second CAS on the captured text.

No open questions. The four that were open at the start of refinement — title edits, the backfill, whether the subtree-folder consequence belongs here, and whether to pin the type in the prompt — are settled above.

11 · Acceptance criteria

  • The claim rule
  • On an unjudged item, an UPDATE that changes only title leaves classified_at null.
  • Same for an UPDATE that changes only notes.
  • Same for an UPDATE that sets item_type to task or code (including the bulk bar’s Classify and the row menu’s Classify as…).
  • Setting priority or due_date, or clearing either, still stamps classified_at with the provenance columns left null.
  • Setting folder_id / intended_project_id / intended_epic_id to a non-null value still claims; a folder delete that nulls folder_id and returns items to the Inbox still does not.
  • An item whose classified_at is already set is never re-stamped by any later edit.
  • The sweep
  • An item holding task or code, undispatched and unmarked, is selected by fetchEligibleItems and classified.
  • The verdict never changes a held item_type, priority, due_date, folder_id, intended_project_id or intended_epic_id — only gaps are filled.
  • The request for a held-type item pins item_type to that single value in the output schema and states it in the user message; the request for an unclassified item is unchanged.
  • PROMPT_VERSION is 2, and is stamped onto the verdicts the new prompt produces.
  • The verdict write filters on both classified_at is null and the item_type that was read; a row re-typed in between matches nothing, is logged, is not counted as classified, burns no attempt, and is picked up again by the next tick.
  • Dispatch
  • Dispatching a task whose folder came from the classifier files the whole subtree into that folder — no items_dispatched_needs_folder violation, at any depth, in any PATCH order.
  • A dispatched child that already carries its own folder keeps it; a code child is unaffected; the inheriting child is not claimed by the claim trigger.
  • Everything else holds
  • Capture is unaffected: POST /api/items gains no LLM call and no new dependency.
  • No column, table, view or grant changes; frontend/lib/database.types.ts is regenerated and committed (expected: no diff).
  • The Inbox renders exactly as before — no new component, chip, glyph or state.
  • Root npm run check is green, with no config weakened and no ignore directive added.
  • A demo doc exists, is linked from the PR as a live blob URL (npm run demo -- pr-link), and reproduces under npm run demo -- verify.
