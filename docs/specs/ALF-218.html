Refinement spec · phase: refinement

ALF-218 — Create code dashboard for Alfred to display lines of code velocity and PR ratio

A new landing view for the Code module at /code: a lines-changed-per-week chart with a rolling-average trend line, the PR-ratio bar relocated from the Backlog, and two digest panes linking into the Needs-human-action and Backlog queues.

1 · Context & problem

The Code module has three destinations today — Needs human action (the default, ALF-174), the ranked Backlog, and a per-project Board. Two things are wrong with that shape:

  • There is no place that answers "how is the factory doing?". The one measurement the app takes — the merged-PR split (PrRatio, ALF-131/ALF-144) — is wedged above the Backlog list, where it competes with a re-ranking workspace for attention and is seen only when the owner goes to re-rank. Nothing measures output volume at all.
  • Entering the module lands on one queue, with the other invisible. Needs-human-action and the Backlog each answer half of "what now?", and whichever one you're on hides the other.

The change: a Dashboard becomes the module's landing view and its top nav item. It carries the new lines-changed-per-week chart, the relocated PR-ratio bar, and a digest pane per queue (top 5 stories each) whose heading links to the full page and whose rows open the story modal. The Backlog hands its "The Software Factory" hero title to the Dashboard and takes a plain, page-specific heading of its own — the same treatment Needs human action already has.

No schema change, no migration, no new environment variable. Everything new is read live from GitHub through one new Route Handler.

2 · Decisions taken up front

These four were open in the ticket and were settled with the owner before this spec was written. They are recorded here because the implementation session needs the reasons, not just the outcomes.

D1 The LoC metric is churn, author-scoped: additions + deletions, by the configured authors

Per week, sum additions + deletions over every commit authored by a login in PR_RATIO_AUTHORS, across every repo in PR_RATIO_REPOS. Source: GET /repos/{owner}/{repo}/stats/contributors — one request per repo, already bucketed by week, already split by author.

Why churn, not net growth. A week spent deleting a dead module or rewriting a component nets out near zero — or negative — while being the busiest week of the month. Net growth is an honest measure of codebase size and a misleading one of velocity. Why author-scoped. The PR-ratio bar already excludes Dependabot, Renovate and github-actions; if the chart beside it counted them, the two widgets on one page would disagree about whose work counts. stats/code_frequency is a smaller payload but cannot be filtered by author, so it was rejected. Note: commits Claude writes are authored by the owner in git, so factory output counts — which is the point.

D2 The Dashboard wears "The Software Factory"; the Backlog becomes "Backlog"

Dashboard ViewHeading: title The Software Factory, description "Your code module at a glance — what you're shipping, and what's waiting on you."
Backlog ViewHeading: title Backlog, description "Every story across your projects, ranked by priority." (its existing description, kept).

The module's hero name belongs on the module's landing page. Needs human action already names itself plainly and describes itself in one line; after this change all three cross-project views follow one rule — the landing page carries the product name, the queues carry their job.

D3 Bare /code renders the Dashboard — the default moves off Needs human action

/code and /code/dashboard both render the Dashboard. /code/needs-human-action keeps rendering its queue, and is no longer highlighted for the bare /code.

This reverses ALF-174's default, so the reason it was set that way has to be paid back: entering the module must still surface work blocked on the owner. It does — the Needs-human-action digest pane is on the Dashboard, showing the same ranked rows, each one click from its modal. The queue moves from "the whole screen" to "the pane you read first", and the Dashboard adds the two things the queue could never show.

D4 12 weeks of bars, 4-week trailing average

The chart shows the 12 most recent calendar weeks. The line is the mean of each week and the three before it.

Twelve bars stay wide enough to read at phone width, and a 4-week mean reacts inside a month, so the trend is actionable rather than decorative. 26 or 52 weeks turns the bars into slivers on mobile and hands all the signal to the line. Consequence that must be built: a true 4-week mean needs three weeks of history before the first drawn bar, so the server reads 15 weeks and returns 12 — see §4.3.

4 · The lines-changed data path

4.1 Shape

It mirrors the PR ratio exactly — that symmetry is the point, because the two widgets sit in the same card stack and must fail the same way:

lib/github/loc.ts is import 'server-only' for the same reason pr-ratio.ts is: it carries the fine-grained PAT, so importing it from a Client Component must be a build error rather than a leaked token.

4.2 Config: one shared repo set, two minimums

getPrRatioConfig() refuses fewer than two repos — "fewer than this many repos is not a ratio". The chart has no such constraint: one repo is a perfectly good velocity series. So split the reader and keep the ratio's guard where it belongs: 

// lib/github/config.ts
export interface GithubRepoConfig {
  repos: RatioRepo[];
  authors: string[];
  token: string;
}

/** Token + at least one well-formed repo. The shared base both widgets read. */
export function getGithubRepoConfig(): GithubRepoConfig | undefined { /* today's body, MINIMUM_REPOS → 1 */ }

/** The ratio's stricter view: a split needs at least two repos to be a split. */
export function getPrRatioConfig(): PrRatioConfig | undefined {
  const config = getGithubRepoConfig();
  if (config === undefined || config.repos.length < MINIMUM_RATIO_REPOS) return undefined;
  return config;
}

No new environment variables. PR_RATIO_REPOS / PR_RATIO_AUTHORS now feed both widgets — which is correct, not merely convenient: the two measurements on one page should share a denominator. Widen their doc comment in config.ts to say so.

Deliberately not renamed. PR_RATIO_* under-describes its new scope, but renaming it means a coordinated Vercel env change for zero functional gain, and a half-done rename leaves a deployment with an unconfigured dashboard. Out of scope — see §9.

4.3 Bucketing, and the three traps in it

stats/contributors returns, per contributor, a weeks array of { w, a, d, c } — w is the Unix-seconds timestamp of that week's Sunday 00:00 UTC, a additions, d deletions, c commits. Three things about it will bite:

TrapWhat happensWhat to do
d is positive here In stats/code_frequency deletions come back negative; in stats/contributors they are a positive count. Copying the sign convention from the wrong endpoint silently subtracts deletions from the churn. Sum a + Math.abs(d). A unit test pins the convention.
HTTP 202 with an empty body GitHub computes these statistics asynchronously. A cold cache returns 202 and no data, commonly on the first-ever request for a repo. Treating it as an error shows "couldn't load" for something that will work in a minute; treating it as success shows a chart of zeros — a lie. Its own outcome, surfaced as its own state. The Handler returns 202; the card says so and invites a refresh.
Weeks are Sunday-UTC, not negotiable GitHub does the bucketing. A local-timezone re-bucket is impossible without per-commit data, and formatting a UTC-anchored week in a local zone shifts labels by a day. No tz query param (unlike pr-ratio). Labels formatted in UTC, the way pr-ratio.tsx's formatDay already does.

Beyond that:

  • Read 15 weeks, return 12. HISTORY_WEEKS = 12, ROLLING_AVERAGE_WEEKS = 4; the reduce runs over the last HISTORY_WEEKS + ROLLING_AVERAGE_WEEKS - 1 = 15 buckets so the first drawn bar already has a true 4-week mean. Without this the line's first three points are means of 1, 2 and 3 weeks, which reads as a spurious ramp.
  • Zero-fill. A repo younger than 15 weeks simply has no entries for the weeks before it existed, and a quiet week has no entry either. Build the 15 buckets from the current Sunday backwards and fill missing weeks with 0 — true in both cases for the measured set.
  • The newest bucket is the week in progress. Draw it (it is real work), flag it partial: true, and give it average: null so the trend line stops at the last complete week rather than being dragged down by a Monday reading.
  • author can be null for commits GitHub can't map to an account. With an allowlist those rows can't match and drop out, which is correct. With an empty allowlist (the "anyone" case) count them, and exclude the three known bot logins by name — the same list pr-ratio.ts already keeps. Export DEPENDENCY_BOTS from there rather than re-typing it.
  • Any repo failing sinks the response (502), exactly as fetchPrRatio does: a velocity number missing one repo's lines is a wrong number, and showing nothing beats showing that. Any repo answering 202 makes the whole response 202.
  • Cache for an hour (next: { revalidate: 3600 }). These hit the 5 000/hr core limit rather than Search's 30/min, and the weekly buckets can't move faster than a push.

4.4 Contract

// lib/types.ts
/** One calendar week of the velocity series. */
export interface LocWeek {
  /** ISO date of the week's Sunday, in UTC — e.g. '2026-09-06'. */
  week: string;
  /** Lines added + removed that week by the measured authors, across every measured repo. */
  lines: number;
  /**
   * Trailing mean of `lines` over this week and the `averageWeeks - 1` before it, rounded.
   * `null` on the in-progress week, so the trend line stops at the last COMPLETE week.
   */
  average: number | null;
  /** True for the calendar week still in progress — its `lines` is a partial count. */
  partial: boolean;
}

/**
 * `GET /api/code/loc-velocity` — lines changed per week across the configured repos. Computed
 * live from GitHub, so it is neither persisted nor reconciled into any store.
 */
export interface LocVelocityResponse {
  /** Exactly `HISTORY_WEEKS` entries, oldest first; the last is the week in progress. */
  weeks: LocWeek[];
  /** `owner/name` of every repo counted, in configured order. */
  repos: string[];
  /** Logins counted; empty means "every contributor but the known bots". */
  authors: string[];
  /** The trailing window the `average` field was computed over. */
  averageWeeks: number;
}

The split is load-bearing, for the reason pr-ratio/route.ts already spells out: silence on a 502 would read as "you wrote no code for three months".

The client returns a discriminated union rather than undefined, because getPrRatio's two-outcome Response | undefined can't carry a third: 

// lib/api-client.ts
export type LocVelocityResult =
  | { status: 'ready'; velocity: LocVelocityResponse }
  | { status: 'unconfigured' }   // 501
  | { status: 'computing' };     // 202

export async function getLocVelocity(): Promise<LocVelocityResult> { /* throws on anything else */ }

useLocVelocity() then exposes the same five-state union the card switches on — loading | ready | computing | unconfigured | error — fetched once on mount, never retried, nothing thrown: the chart is an ornament, never a gate, the rule usePrRatio already states.

5.4 The chart primitive

No charting library. The repo has none, and pulling one in for a 12-bar chart is a disproportionate dependency. Add a presentation-only atom — components/atoms/bar-line-chart.tsx — modelled on RatioBar: no fetching, no arithmetic over domain values, no domain vocabulary (no "week", no "lines"), so it stays reusable for any bucketed series with a trend. 

export interface BarLinePoint {
  /** Short axis label, e.g. 'Sep 6'. */
  label: string;
  value: number;
  /** The trend value at this point, or null to BREAK the line here. */
  average: number | null;
  /** Dim the bar — a bucket that is still filling. */
  provisional?: boolean;
  /** Hover readout for this bucket, e.g. 'Sep 6 – Sep 12 · 1,980 lines (so far)'. */
  title: string;
}

interface BarLineChartProperties {
  points: readonly BarLinePoint[];
  /** What the chart conveys, spelled out for assistive tech — as RatioBar does. */
  ariaLabel: string;
  className?: string;
}

Mechanics, because two of them are easy to get subtly wrong:

  • Bars are HTML, not SVG — a flex row of equal-basis columns, each bar a div with style={{ height: 'n%' }} of the track, the way RatioBar sets widths. Labels are real text below the track, so they scale with the user's font size instead of being baked into a viewBox.
  • Only the trend line is SVG: one absolutely-positioned overlay at viewBox="0 0 100 100" preserveAspectRatio="none", so point coordinates are plain percentages. That non-uniform scale would distort the stroke, so the polyline carries vector-effect="non-scaling-stroke" — without it the line is visibly fat horizontally and thin vertically. For the same reason there are no point markers: a circle would scale into an ellipse.
  • A null average splits the series into separate <polyline> elements. One polyline with the gap dropped would draw a straight segment across it; a polyline that treats null as 0 would dive to the floor.
  • Axis maximum is a "nice" ceiling, not the raw max: round up to the next multiple of 10digits−1 (6 140 → 7 000; 420 → 500; 3 → 3). A pure unit-testable helper in the same file. All-zero input yields no bars and no line rather than a divide-by-zero.
  • Floor a non-zero bar at 2px so a quiet week is visible; a genuinely zero week draws nothing.
  • Accessibility follows RatioBar: role="img" on the plot plus the caller's ariaLabel (the visual carries the information, so it is an image with a label, not decoration). Per-bucket numbers are reachable by pointer through each bar's title.

8 · Notes for the implementation session

  • The card chrome is about to have a third copy. pr-ratio.tsx keeps private Card and Heading helpers; LocVelocity needs the same frame, and the digest panes need the card without the heading. That's the rule-of-three trigger from the frontend-architecture skill: extract the frame into an atom (a surface card with an optional title/detail header row), adopt it at every call site in this change, and delete the private copies. A half-adopted primitive is worse than none.
  • Read the skills first. frontend-architecture (where things live, the rule-of-three), data-flow (why this is a fetch-on-mount hook and not a store — nothing here is persisted, reconciled or mutated), nextjs (Route Handler + the revalidate fetch cache), react, storybook, playwright, tailwindcss.
  • No store involvement for the chart. The velocity series is derived, live, and never mutated; it does not belong in CodeProvider and must not be seeded at the shell layout — that would put a GitHub fan-out on the critical path of every page in the app.
  • The digest panes read the store the pages already read — useBacklog({ statuses }) with HUMAN_REVIEW_STATUSES and DEFAULT_BACKLOG_STATUSES respectively, both module constants and so referentially stable. Slice to 5 after the hook, and take the count from the full array. No project filter on either pane: the Dashboard is cross-project by definition.
  • Tailwind v4 scans for complete class names. Any per-state or per-tone class in the new components must be a full static string in a lookup table, never interpolated — the existing MODULE_ACCENT and PROJECT_BADGE_CLASS tables exist for exactly this. The bar heights are the exception: they're an inline style, like RatioBar's widths.
  • Demo doc. A user-visible change, so it needs one at docs/demos/<branch>/… per the showboat skill — which owns the evidence rules; follow them rather than anything restated here. Note only that this change has real journeys (pane header → page; row → story modal), so end-state stills alone won't do.
  • Hit friction with a lint rule? Make the code pass as the gate stands and drop a note in docs/lint-suggestions/ the same turn. Never an ignore directive, never --no-verify.

9 · Out of scope

  • Per-repo stacked LoC bars. One solid bar per week is the ticket's "each week's number", and the PR-ratio bar directly below already answers "which repo" for the current week. Stacking is a later call, and the atom's BarLinePoint shape doesn't foreclose it.
  • Any range control — no 12/26/52-week switch, no zoom, no date picker. One window (D4).
  • Renaming PR_RATIO_REPOS / PR_RATIO_AUTHORS (§4.2).
  • Persisting the series. No table, no migration, no Worker cron. Live reads with an hour-long fetch cache are adequate at single-user scale; persistence becomes interesting only if the owner wants history older than GitHub's stats window or per-repo backfill.
  • Excluding generated files, lockfiles or vendored code from the churn. GitHub's weekly statistics are pre-aggregated and cannot be filtered by path — doing so means per-commit diffs, which is a different (and far more expensive) feature.
  • Commits outside each repo's default branch, and the "Other" bucket's lines. The stats endpoint is per-repo and default-branch-only, so the chart measures the configured repos only — the PR-ratio bar's Other segment has no counterpart here.
  • Any Board, Backlog or Needs-human-action behaviour beyond the Backlog's heading and the removal of its ratio card. No change to filters, ranking, reorder controls or the story modal.

10 · Open questions

None blocking. The four that mattered were settled with the owner as D1–D4 before this spec was written. Two things are worth a look at review, and neither changes the build:

  • Does the churn number read as plausible once it's real? Author-scoped churn on a repo where most commits are Claude-authored-but-owner-committed should count fully, but the first real chart is the proof. If the numbers look wrong, the diagnosis is whether author.login matches the configured logins — not the arithmetic.
  • Card order. Chart above ratio, per the ticket's own "lines of code velocity and PR ratio". Trivially swappable if the owner would rather lead with the split.
