Refinement spec · Epic ALF-7 (Comms Module)

ALF-221 — Provide some sort of feedback when "Re-run classifier" button is pressed

After a re-run request, the row says it's waiting, and a toast reports the new verdict or the failure. The worker also stops retrying a re-run that can't succeed, so every re-run ends with an outcome.

1 · Context & problem

Ticket: "Right now there's no indication anything was sent, if the verdict changed or not, if something went wrong, etc."

Today a click on Re-run classifier (components/comms/row-verbs.tsx) calls requestReclassify in lib/stores/comms-store.tsx. That call POSTs /api/comms/messages/[id]/reclassify, which stamps reclassify_requested_at and resets classify_attempts. Then the UI says nothing. The flow is:

  1. The Worker's comms sweep (workers/src/comms/sweep.ts, cron */2) takes re-runs first, judges them, then clears reclassify_requested_at.
  2. The Comms store re-reads the snapshot every COMMS_POLL_MS (30s), so the new tier arrives 1–3 minutes after the click. If the tier changed, the row moves to another section with no explanation. If it didn't change, nothing visible happens.

Here is what the owner can see today for each part of the ticket:

The ticket asksTodayAfter this story
Was anything sent?Nothing, unless the POST fails. Then the store rolls back and toasts "Couldn't ask for a re-run".The button switches to Re-run requested with a spinner, and a Re-run pending chip appears on the row. The failure toast stays as it is.
Did the verdict change?The row might move sections, or might not.A toast names the sender and the before and after tiers, or says the tier stayed the same.
Did something go wrong?Nothing tells the owner. Worse, a re-run that keeps failing never ends (see below).After 5 attempts the Worker gives up and keeps the old verdict. A toast and a line in the detail panel say so.
A re-run that keeps failing retries forever. fetchReclassifyRequests (workers/src/comms/store.ts) does not filter on classify_attempts, and parkAtCeiling only picks up rows with tier IS NULL. So when a re-run of an already-judged row keeps failing with a bad model response (a content-shaped failure), the Worker re-sends the model call on every tick, bills it, counts attempts past the ceiling of 5, and never clears the request. The UI would show the row as pending forever. This story adds an end state for it (§3.3).

2 · What a re-run goes through

3 · Proposed change

3.1 Pending state (derived from the row, so it survives a reload)

The row counts as pending whenever message.reclassify_requested_at !== null. No new client state is needed. The existing optimistic patch in requestReclassify sets that field when the button is clicked, so the pending state shows at once, and a rollback removes it.

  • Button (RowVerbs): while pending it becomes a disabled ghost sm button with the Spinner atom (size 12, label "Re-run pending") in place of RefreshCw, and the text Re-run requested. It's disabled because a second request while one is pending would only reset the attempt count. RowVerbs gets a reclassifyPending prop, passed down through MessageDetail.
  • Chip (RowMarkers): a Badge variant="secondary" reading Re-run pending. It appears on queue and shelf rows, so the pending state is also visible when the row is collapsed. Like every other marker it's derived, not stored. It goes first in the chip order, because it describes the row's verdict as a whole.
  • A classifier outage keeps rows pending, and nothing new is added for that case. The existing module-level ClassifierBanner already explains why nothing is being judged.

3.2 Outcome toast (for re-runs requested in this tab)

The store remembers each re-run it asked for, and when the request clears it compares the before and after rows:

// comms-store.tsx: a ref, not reducer state, since nothing renders from it
const rerunsRef = useRef(new Map<string, { tier: CommTier | null; requestedAt: string }>());

// requestReclassify: record { tier, requestedAt } before the write; delete it on rollback.
// Each successful reconcile: resolve every tracked id against the snapshot's `watched` rows.
//   row absent (purged / expired)             → drop, no toast
//   row.reclassify_requested_at !== null      → still pending, keep waiting
//   otherwise                                 → toast outcomeMessage(before, row, people), drop

The watched rows come from the snapshot because a re-run can move a row somewhere the snapshot doesn't return. A demotion to FYI or a refusal files the row on the shelf, and the shelf is paged newest-first, so an older message can fall outside the loaded page. That is exactly the case that most needs a toast. So GET /api/comms/snapshot takes an optional watch parameter:

  • watch is a comma-separated list of UUIDs, at most 20. The route validates it the same way it validates shelf, and returns 400 on a malformed id.
  • The route returns those rows as seed.watched: CommMessage[], fetched with one extra .in('id', …) read, and only when the list is non-empty.
  • api.fetchCommsSnapshot(shelfLimit, watchIds) passes the list through. The store uses watched only to resolve outcomes. It is never rendered or merged into messages.

The toast text is built by a pure rerunOutcomeMessage(before, after, senderName) in lib/comms/. Tier names come from TIER_LABEL. The rules are checked top-down and the first match wins:

Resolved rowToast
reclassify_failed_at ≥ requestedAt (the Worker gave up, §3.3) Re-run failed · {sender}: kept {Tier}, or …: still unjudged if the row had no tier
judged_by = 'refusal'Re-run · {sender}: the model declined, moved to FYI
judged_by = 'unjudged'Re-run · {sender}: still couldn't judge it, on {Tier}
tier === before.tierRe-run · {sender}: still {Tier}
otherwiseRe-run · {sender}: {Old} → {New}

Toasts use the default variant and go through the existing showToastRef. The toast viewport's aria-live="polite" region announces them. The sender label comes from senderLabel(message, people), which tells two re-runs that land in the same tick apart. The owner's triage state is never touched: a cleared row stays cleared, as writeVerdict already guarantees.

3.3 Worker: a re-run that can't succeed gets an end state

  1. Migration <next>_comm_reclassify_failed.sql (use the next available number): ALTER TABLE comm_messages ADD COLUMN reclassify_failed_at timestamptz, nullable, no default. Run migration-lint. Regenerate frontend/lib/database.types.ts with supabase gen types. Add the field to the Worker's WireMessage/CommMessage and to lib/comms/fixtures.ts.
  2. A new first step in runCommsSweep, abandonStalledReruns, runs before parkAtCeiling and follows the same pattern. It reads rows with reclassify_requested_at NOT NULL AND classify_attempts >= COMMS_ATTEMPT_CEILING (limited to COMMS_SWEEP_LIMIT) and PATCHes each one to { reclassify_requested_at: null, reclassify_failed_at: now }. That PATCH is conditional on reclassify_requested_at still equalling the value it read, so it can't wipe out a newer request. It doesn't change tier, verdict or ask, so the old verdict stays. A row that never had a tier then goes to parkAtCeiling in the same tick, as it would today.
  3. fetchReclassifyRequests adds classify_attempts=lt.{ceiling}, so a stalled row is abandoned instead of being billed again.
  4. Subrequest budget: the new step adds one read to every tick, plus one PATCH for each abandoned row (rare). Recheck the arithmetic in the COMMS_SWEEP_LIMIT comment and keep a full tick under 50 subrequests. If the new step pushes it over, lower the cap on abandoned rows per tick; don't raise the budget.
  5. A new request clears the old failure. The reclassify route, and the optimistic patch in requestReclassify, also set reclassify_failed_at: null.

3.4 The failure line in the detail panel

While reclassify_failed_at is set, MessageDetail shows a line right after Why: (same text-[12.5px] text-muted-foreground, with an amber lead-in): Re-run failed {formatMessageTime(reclassify_failed_at)}. The classifier couldn't produce a verdict, so this one stands. This makes the failure visible after a reload, or when it happened in another tab. There's deliberately no chip on the collapsed row: the verdict still stands, so a failed re-run isn't a way the module is wrong about the row.

6 · Acceptance criteria

  • Clicking Re-run classifier immediately disables the button and replaces it with Re-run requested and a spinner. A Re-run pending chip, listed first, appears on the row whether it's expanded or collapsed, in the queue or on the shelf.
  • Reloading while a re-run is pending still shows both, because they're derived from reclassify_requested_at.
  • If the POST fails, the row rolls back (button and chip go back to normal) and the existing "Couldn't ask for a re-run" toast appears.
  • When the request clears, exactly one toast appears for each re-run requested in this tab, with the §3.2 wording for its outcome. That includes a row that moved to a shelf page that isn't loaded, via watch. A row that was purged or deleted is dropped without a toast.
  • rerunOutcomeMessage is unit-tested for every row of the §3.2 table, including the precedence order.
  • GET /api/comms/snapshot?watch=… returns the named rows in watched, returns 400 on a malformed id or more than 20 ids, and makes no extra read when watch is absent.
  • Worker: a re-run row at the attempt ceiling is abandoned without a model call. Its request is cleared, reclassify_failed_at is stamped, and its tier, verdict and ask are unchanged. fetchReclassifyRequests excludes rows at the ceiling. The abandoning PATCH doesn't match a row whose reclassify_requested_at has changed since it was read. A tier-null row that's abandoned is then parked by parkAtCeiling as it is today.
  • The reclassify route and the optimistic patch both set reclassify_failed_at to null.
  • The expanded row shows the Re-run failed line whenever reclassify_failed_at is set, and never on the collapsed row.
  • New Storybook stories on MessageRow: Re-run pending (expanded), Re-run pending (collapsed) and Re-run failed, with committed snapshot baselines.
  • The subrequest arithmetic in the COMMS_SWEEP_LIMIT comment is updated and stays under 50.
  • The demo doc's evidence follows the showboat skill's rules for a UI change that adds Storybook snapshots. This spec doesn't redefine them.

7 · Out of scope / open questions

  • Outcome toasts for re-runs requested in another tab or before a reload. The tracking lives in the tab's memory, so those re-runs get the pending state and the failure line (both stored on the row) but no toast. Accepted, since a re-run is a single deliberate click.
  • A keyboard shortcut for re-run. There isn't one today and this story doesn't add one.
  • Showing verdict history (the old reason next to the new one). The verdict rows are kept, but showing them is a separate audit feature.
  • The owner changes the tier while a re-run is pending. The re-run still overwrites the tier, as it does today (D19: it's an explicit act). The toast compares against the tier at the time of the request.
