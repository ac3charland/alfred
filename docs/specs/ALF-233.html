1 · Context & what this story delivers

The epic settled the shape: the Reader is alfred's fourth module, fed by the rows the Comms module already mirrors from the personal Gmail every three minutes (D2), re-fetching each newsletter for its full HTML (D3), matching senders against a publications roster (D4), summarising each post once with Sonnet 5 into a gist and a sectioned overview (D6–D8) on its own cron with a per-tick cap and a daily ceiling (D9), and showing an archive-or-open list (D11–D12). A claimed newsletter leaves the Comms FYI shelf (D14).

This story is the first of two (D15). Its single risk is a question no code review answers: does this extraction and this prompt work on real Substack mail? So it ships the minimum that lets the owner find out — the pipe, the list, the eval script — and ends at a checkpoint where the owner runs three things against a deployed Worker and a real mailbox (§12). What the checkpoint teaches is recorded for Story 2 (§11), which is refined only after this PR merges.

What exists that this builds on

  • workers/src/comms/gmail.ts polls gmail-personal over OAuth and mirrors inbound mail into comm_messages; newsletter.ts stamps has_list_header on every row. gmail-api.ts already exposes gmailClient(token).getMessage(id) at format=full, returning rejected/transport failures as values.
  • workers/src/comms/email-text.ts holds the MIME walk, base64url decoder and HTML stripper — module-private today (D14's first sanctioned comms edit exports them).
  • workers/src/classifier.ts is the structured-output call shape; the Anthropic SDK is mocked in tests via jest.spyOn(Anthropic.Messages.prototype, 'create').
  • The Worker talks to Supabase over raw PostgREST fetch (workers/src/supabase.ts), never a client library; every conditional write is a PostgREST filter, not a lock.
  • The frontend's module set is enumerated in six shell files (§7.1); the comms store, data layer, route helpers, fixtures and row chrome are the templates every reader file mirrors.

3 · Build decisions

The epic's decisions stand. These are the calls the code forced once the epic's sketch was laid against it — each with its why, so the implementation session doesn't re-derive them. Tagged diverges where the epic said otherwise; every such divergence is also named in the PR description.

B1Thinking is switched off explicitly, and the test asserts it. diverges from classifier.ts's shape

The summariser sends thinking: { type: 'disabled' }, output_config: { effort: 'medium', format: { type: 'json_schema', schema } }, max_tokens: 4096. summarize.test.ts asserts all three on the sent params.

Why: the epic's D8 already names thinking: { type: 'disabled' } and adds "like classifier.ts, no extended thinking" — but classifier.ts gets that by omitting the key, and its test asserts the key is absent, so a builder copying the classifier would drop the one line that matters. That works on Haiku 4.5, which has no thinking unless asked. On Sonnet 5, omitting thinking runs adaptive thinking (the Claude API reference is explicit), billed as output and counted against max_tokens — exactly the truncation-that-signals-nothing the epic's D8 exists to avoid. So the reader's call cannot copy the classifier's omission; it names the mode. Do not "fix" the classifier to match: Haiku rejects effort and the two modules must not couple. One prompt consequence: with thinking off, never add "do not think" or "answer without reasoning" lines to the system prompt — the API reference records that such lines make tag leakage more likely, and the JSON-schema constraint already shapes the output.

B2A 60-second request timeout, one SDK retry, and an eight-minute tick budget.

The client is built per call, as the classifier's is: new Anthropic({ apiKey, timeout: 60_000, maxRetries: 1 }). The tick records its start and stops starting posts once READER_TICK_BUDGET_MS = 8 * 60_000 has elapsed; rows already inserted stay pending for the next tick.

Why: the classifier's 10 s timeout fits a 512-token verdict; ~1 500 output tokens on Sonnet 5 takes 15–40 s. A scheduled invocation has a 15-minute wall clock: six posts at the worst case (60 s × 2 attempts + a Gmail read) is ~12.5 minutes, too close. The budget makes the worst case ~10 minutes. Note the SDK timeout is milliseconds in TypeScript.

B3Overlapping ticks are handled by a lease, not by hoping they don't overlap. adds a column

reader_posts.summarizing_since timestamptz. For a fresh post the insert is the claim: it carries summarizing_since = now, and a 409 on the (account_key, gmail_message_id) key means another tick owns it — skip, don't fail. For a retried pending post the claim is a CAS patch: PATCH …?id=eq.X&summary_state=eq.pending&or=(summarizing_since.is.null,summarizing_since.lt.<now−15m>), and zero rows affected means skip. Every terminal patch (§5) sets it back to null.

Why: the cron fires every five minutes and a tick may run ten (B2). Cloudflare does not serialise scheduled invocations — the comms judge already guards the same race with ifAttemptsEquals. That guard doesn't work here because attempts count only content failures (D10). A 15-minute staleness bound equals the runtime's own ceiling, so a tick that died mid-call releases its rows on the next tick after that.

B4The daily ceiling is derived from the posts, not counted on the health row. drops calls_today / calls_day

reader_posts.model_called_at timestamptz is stamped in the same terminal patch that records the outcome of every model attempt (done, refused, counted, transport). The tick reads calls_today once at its start — countRows(env, 'reader_posts', { model_called_at: 'gte.<UTC midnight>' }), a store.ts helper that sends GET …?select=id with Prefer: count=exact (overriding the return=representation that headers(env) sets) and Range: 0-0, ignores the body, and parses the total from Content-Range: 0-0/29 (*/0 → 0) — and adds the calls it makes itself. reader_health keeps only last_run_at, last_success_at, last_error, last_error_at.

Why: a counter on the singleton needs a write per model call (a subrequest the budget in B5 cannot spare) and a CAS against overlapping ticks; a stamp on the row is a column the terminal patch writes anyway. The crash window — a tick dying between the call and the patch — loses one count in either design. Transport failures are stamped too: a timeout may well have been billed, and the ceiling exists to bound money, so it counts conservatively.

B6Fixtures are Gmail messages.get JSON, not .eml. diverges from the epic's S1-B/S1-C wording

Committed under workers/src/reader/fixtures/ as TypeScript modules — each file exports one GmailMessage object in the shape gmail-api.ts already types (headers, MIME parts, base64url bodies), and fixtures/index.ts exports the set as READER_FIXTURES: readonly { name: string; message: GmailMessage }[]. Modules rather than .json because the Worker's tsconfig has no resolveJsonModule and no Node types, and enabling either to make a test pass is the config change CLAUDE.md forbids. Four fixtures, hand-built in the Substack shape and free of anything personal:

  • essay.ts — multipart/alternative, a long text/html part whose first /p/ link is the post, an author in From, a list header, and one javascript: anchor ahead of it that the scheme filter (B8) must skip.
  • roundup-view-in-browser.ts — no /p/ link; a "View in browser" anchor.
  • plain-text-only.ts — a text/plain body and no link at all (the Gmail-permalink path; html_extracted = false).
  • platform-mail.ts — from no-reply@substack.com with a list header, which discovery must ignore.

Why: the repo has no .eml anywhere, and nothing in the Worker parses RFC 822 — the intake's input is the Gmail API's JSON, so that is what the extractor is tested against and what the eval script can replay. The implementation session has no mailbox, so the fixtures are built from Substack's public email structure; the checkpoint's eval over real mail (§12) is where the extractor meets reality, and Story 2 starts by turning what that finds into fixtures (§11).

B7The eval script reads real mail from the mailbox, or replays fixtures. not "a folder of .eml files"

npm run eval:reader -w workers -- --ids 18f3a…,18f3b…
npm run eval:reader -w workers -- --fixtures            # replay the committed set, still billed
npm run eval:reader -w workers -- --fixtures --dry-run  # extraction only, no key, no bill, no results file
npm run eval:reader -w workers -- --query … --model claude-opus-5           # try another model

workers/scripts/reader-eval.ts, modelled on comms-eval.ts: reads workers/.dev.vars for GMAIL_OAUTH_CLIENT_ID, GMAIL_OAUTH_CLIENT_SECRET, GMAIL_PERSONAL_REFRESH_TOKEN and ANTHROPIC_API_KEY (falling back to process.env), mints a token with fetchAccessToken, lists and fetches with gmailClient, runs the same extractPost and summarizePost the tick runs, and prints per post: title, canonical URL (or "none → mailbox"), author, word count, then headline, gist and the four overview sections, then usage and an estimated cost. A billed run is written to workers/eval-results/<timestamp>.json (gitignored) and prints the path. --dry-run stops after extraction, needs no key, writes no file and prints no path — its stdout is a pure function of the fixtures, which is what lets it be the demo's Worker-side evidence under verify (§9). --fixtures imports READER_FIXTURES; no directory argument.

Why: the checkpoint asks the owner for "five real posts of different kinds"; pointing the script at the mailbox makes that a one-line command instead of an export chore, and every credential it needs is already in .dev.vars for gmail-probe. It lives under workers/scripts/, outside the Jest projects, because it spends money.

B8Title from the Subject; canonical URL is the first /p/ link on any host. refines D3 / D12

  • title — the Subject header, whitespace-collapsed; empty → the HTML <title>; empty → (untitled). Never the row's gist.
  • author — the From display name (parseAddress), else the publication name.
  • canonical_url — among anchors whose href parses as a URL with an http: or https: scheme (anything else — javascript:, mailto:, a relative path — is treated as no link), the first whose path matches ^/p/[^/?#]+, with query and fragment stripped; else the first whose text matches /view (this )?(in|on) (your )?browser|read online|view online/i; else undefined. Anchors are read from the raw HTML before stripping. The value is rendered as an href, so the scheme filter is a security rule, not a nicety.
  • publication name — the roster row's name.

Why: Substack puts the post title in the subject line; the HTML's <h1> markup changes between templates and a wrong pick puts a nav label on the row. D12 said "host is the publication's domain": a custom-domain publication mails from news@example.com and links to example.substack.com/p/… or www.example.com/p/…, and older templates wrap links in a tracking host. The /p/<slug> path is the Substack-specific signal; the host isn't.

B9Model input is capped at 150 000 characters; stored text at 400 000; word count from the full text.

READER_MODEL_INPUT_CHARS = 150_000 (≈ 37 000 tokens, ≈ $0.08 at Sonnet 5 list price — the pathological case, not the typical ~8 000-token post the epic's §6 costs). READER_TEXT_CHARS = 400_000 is D3's ceiling on what is stored. Both truncate on a code-point boundary via the exported truncateAtCodePointBoundary. word_count is computed on the stored text; the UI derives read minutes as max(1, ceil(word_count / 230)) and nothing stores them.

Why: the cost is the input, and a post that pathological is exactly what a cap should bound before the ceiling has to.

B10Roster seeding in Story 1: discovery for Substack, SQL for everything else. No publications route.

Discovery (§5 step 0) is the only automated way in. A non-Substack publication is added by one insert into reader_publications (handle, name, source) values (…, 'owner') in the Supabase SQL editor — the recipe lives in database/README.md's schema summary for the migration. Pausing one is update … set enabled = false.

Why: the epic allows "SQL / the route handler"; a route with no UI is a surface nobody exercises, and Story 2 owns the publications routes properly.

B11Vars fail closed.

READER_MODEL and READER_DAILY_CAP arrive as strings. Missing READER_MODEL, or a READER_DAILY_CAP that is not a positive integer, is a systemic failure: the tick writes reader_health.last_error and returns before touching Gmail. A missing READER_DAILY_CAP defaults to 30; a missing ANTHROPIC_API_KEY is the classifier's credentials outcome and is systemic too.

READER_MODEL may name any model that accepts thinking: { type: 'disabled' } — Sonnet 5, Opus 5 at effort medium, Haiku 4.5 only if effort is also dropped. Fable 5/5.1 reject disabled with a 400, which the tick would file as a systemic bad_request on every post; the var's comment in wrangler.toml says so.

Why: the ceiling is the money guard; an unparsable ceiling silently becoming "unlimited" is the one failure it must not have. wrangler.toml's own comments warn that a CLI --var can shadow a [vars] entry, so the Worker never trusts the shape.

B12A lost mailbox message claims the comms row and inserts nothing.

A Gmail 404 on messages.get (the owner deleted it for good between the poll and this tick) — and equally a 200 whose labelIds carry TRASH or SPAM, because Gmail keeps serving a binned message and only a hard delete 404s, which is why the comms poll checks labels after the fetch — stamps comm_messages.reader_claimed_at, logs one line, and moves on. The worklist view excludes claimed rows as well as rows with a post (§4), so it is never re-tried. The 404 is detected on status before the rejected/transport split, since gmail-api.ts files it under transport.

Why: the alternative — a permanently failed post with no text — puts mail the owner deleted on purpose into their reading list, which D5 says must not happen. And without the claim, the anti-join returns the message every tick forever and burns a Gmail read each time. Transport failures are different: they end the tick with nothing advanced (§5).

B13The list never carries text; one column list is shared by the seed, the route and the patch.

READER_POST_LIST_COLUMNS in frontend/lib/data/reader.ts is the explicit select — every reader_posts column except text — used by getReaderSeed, getReaderPosts and patchReaderPost. The frontend type is ReaderPostListItem = Omit<ReaderPost, 'text'>.

Why: a 30 KB body per row × 200 rows is a 6 MB shell seed for a body the UI never shows (the verb opens the original). One constant, so the three reads can't drift.

B14Three store actions, not four; "opened" stamps the latest open, silently. drops unarchive from §3.4

useReaderActions() → { archive(id), markOpened(id), refresh() }. archive is optimistic with rollback and a toast on failure. markOpened fires on the "Open" link's click without preventing navigation, sets opened_at locally, and a failed write neither rolls back nor toasts. No unarchive in the store until the archive view exists (S2); the PATCH route accepts { archived: false } anyway because the schema is a boolean.

Why: an action with no surface is untested code. A failed open-stamp is not worth interrupting reading for — the owner is already on the way to the post — and the next focus refetch corrects the row.

B15Three comms edits, not two — the store's realtime allowlist learns the column. D14 says two

Beside isShelved and the shelf branch of getCommMessagesByScope, messageUpdatePatch's column allowlist in comms-store.tsx gains reader_claimed_at, so the Worker's stamp reaches an open tab as a realtime UPDATE and the row leaves the shelf without a reload. isQueued stays untouched. All three are the session's own edits (§10), each with a test, each named in the PR.

Why: the allowlist exists precisely so unknown columns are dropped; a row that only leaves the shelf on the next page load would make the count under it wrong for the life of the tab. One line, and it keeps D14's "nothing vanishes silently" true live.

B16Four labels don't fit the 224 px sidebar: it widens to 256 px and the switcher's type drops to 13 px. not in the epic

The desktop <aside> in app-shell.tsx goes md:w-56 → md:w-64 — the width the mobile drawer already is. The switcher's segment class goes text-sm … px-1.5 → text-[13px] … px-1. Everything else about the control (flex-auto, min-w-0, truncate as the floor, gap-0.5, p-1) stays. The ViewSwitcher stories re-frame in the new geometry and their baselines move (the demo carries the diff). e2e/module-switcher.spec.ts's "no label is truncated" assertion is kept and now runs over four labels.

Why: measured in the bundled Geist at 14 px / 500, "Tasks Code Comms Reader" is 41 + 37 + 53 + 50 = 181 px of text; the sidebar offers 224 − 32 padding − 2 border − 8 inner padding − 6 gaps = 176 px for all four segments before any segment padding. No padding change fits it, and ALF-219 pinned that fitting by truncation is its own bug. At 256 px the budget is 208 px; 13 px labels measure 161 px (37 + 33 + 46 + 45 — measured in a browser with the bundled font, not scaled from 14 px) and px-1 adds 32, leaving 15 px of slack — enough that a font hinting difference can't tip it. The alternative that keeps w-56 — 12 px labels in a row with 8 px side padding — fits with 2 px to spare, which is a regression waiting for a browser update; it is the escape hatch in §14 if the owner would rather not move the sidebar.

B17headline is stored, not rendered, in this story. diverges from D6's "shown as the row's second line"

The model still produces it and the row stores it; the row draws eyebrow, meta, title, gist and verbs — no headline. Story 2 decides whether to show it and under what rule.

Why: D6 shows it "when the title is a teaser", and nobody has defined a teaser: "Open Thread 348" isn't one, "You won't believe what happened next" is, and the honest rule needs a week of real subjects to write. Drawing it now under a guessed rule would ship a second line the owner has never seen; storing it costs nothing and keeps the schema stable.

create view v_reader_worklist with (security_invoker = true) as
  select m.id           as comm_message_id,
         m.source_id    as gmail_message_id,
         a.key          as account_key,
         p.id           as publication_id,
         m.sender_handle, m.sender_name, m.subject, m.rfc822_message_id, m.received_at
    from comm_messages m
    join comm_accounts a on a.id = m.account_id and a.key = 'gmail-personal'
    join reader_publications p on p.handle = m.sender_handle and p.enabled
    left join reader_posts r on r.account_key = a.key and r.gmail_message_id = m.source_id
                                              -- the dedupe key, not comm_message_id: a purged and
                                              -- re-mirrored comms row gets a new id but the same source_id
   where m.direction = 'inbound'
     and m.reader_claimed_at is null          -- B12: a binned message claims without a post
     and r.id is null                         -- the anti-join PostgREST cannot express
     and m.received_at >= now() - interval '7 days';   -- D9's horizon
-- the tick orders by received_at asc and limits itself

create view v_reader_discovery with (security_invoker = true) as
  select m.sender_handle as handle,
         max(m.sender_name) as name,
         min(m.received_at) as first_seen_at,
         count(*)::int      as message_count
    from comm_messages m
    join comm_accounts a on a.id = m.account_id and a.key = 'gmail-personal'
   where m.direction = 'inbound'
     and m.has_list_header
     and m.sender_handle like '%@substack.com'
     and split_part(m.sender_handle, '@', 1) not in ('no-reply', 'noreply')
     and m.received_at >= now() - interval '7 days'
     and not exists (select 1 from reader_publications p where p.handle = m.sender_handle)
   group by m.sender_handle;

grant select on v_reader_worklist, v_reader_discovery to anon, authenticated, service_role;

The roster match is on the roster regardless of the header (D4): a publication whose mail lacks List-Unsubscribe still counts, and one that is also on the comms people roster still counts. Discovery's three conditions are what keep Substack's platform mail off the roster. sender_name is what comms parsed from From; the max is just a deterministic pick.

5.1 Extraction — extract.ts

  • Leaves via the exported flatten; the first decodable text/html leaf (exported decodePart) is the HTML; the first text/plain leaf is the fallback. Attachments (a filename) are skipped, as comms does.

  type: 'object', additionalProperties: false,
  required: ['headline', 'gist', 'overview'],
  properties: {
    headline: { type: 'string', description: 'What the post is about, in one line. ≤ 20 words.' },
    gist:     { type: 'string', description: 'The claim the post makes and whether it is a new take or a restatement — the "should I read this?" answer. ≤ 90 words.' },
    overview: {
      type: 'object', additionalProperties: false,
      required: ['novel_ideas', 'evidence', 'argument', 'who_should_read'],
      properties: {
        novel_ideas:     { type: 'array', items: { type: 'string' }, description: 'The genuinely new ideas. 0–6 bullets; empty is a valid answer.' },
        evidence:        { type: 'array', items: { type: 'string' }, description: 'The notable evidence, data or examples the post rests on. 0–6 bullets.' },
        argument:        { type: 'string', description: 'The argument in order — the one-page alternative to reading. ≤ 300 words.' },
        who_should_read: { type: 'string', description: 'Who the full post is worth the time for. ≤ 40 words.' },
      },
    },
  },
} as const;

Budgets live in the descriptions and the prompt, not as maxItems / maxLength: the structured-output grammar accepts a JSON-schema subset and a rejected keyword would be a 400 on every post. After parsing, the type guard trims each list to six.

6.2 The prompt — prompt.ts

READER_PROMPT_VERSION = 1, stamped on every summary beside the model id (D7). buildReaderRequest(post) returns { system, user, schema }. The system prompt is static and says, in the implementer's own words:

  • The reader subscribes to many newsletters and uses these summaries to decide what to read, not as a substitute for reading. Summarise this post only.
  • "Novel" means new against what a well-read person in the post's field already knows this season. An empty novel_ideas is the honest answer for a post that restates the consensus — say so in the gist rather than inventing novelty.
  • Be concrete: name the claim, the numbers, the examples. No padding, no praise, no editorialising about quality beyond the "should I read this?" verdict.
  • Ignore subscription boilerplate, footers, "share this post" chrome and comment digests.
  • A paywalled teaser is summarised as a teaser: the gist says what is behind the wall and the overview covers only what is present.

The user turn is the metadata block (publication, author, title, date, word count) followed by the text, truncated at READER_MODEL_INPUT_CHARS (B9). The exact wording is the implementation session's — S1-C in §10 — iterated against the fixtures until the eval's --dry-run and a mocked run read well; its quality is judged by the owner at the checkpoint, never by a test.
