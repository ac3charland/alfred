ALF-234 — Reader module: publications, health and retention (Half 2)

The second and last story of the Reader epic. Story 1 (the pipe and the reading list) proves that Substack mail can be fetched, summarised and skimmed; this story makes that pipe operable: the owner manages the roster without SQL, a dead summariser and a dead mailbox and an exhausted daily ceiling each read as a distinct state, a post can be re-summarised on demand, archived posts are browsable, the list is driven from the keyboard on desktop, and the 90-day text sweep runs.

1 · Context & problem

After Story 1 merges, the Reader works but is administered by SQL and diagnosed by wrangler tail:

  • The roster is invisible. Publications are auto-discovered (Substack senders with the list header) or seeded by hand. There is no way to pause one, rename one, or promote a non-Substack bulk sender without a database client — and the D5 Gmail filter the owner maintains by hand drifts from the roster silently.
  • An empty list is ambiguous. "Nothing new to read" is the module's resting state, but it is also what a dead summariser, a revoked Gmail token, or a tripped daily ceiling look like. Story 1 writes the health row and the per-post failure state; nothing reads them.
  • A summary can never change. Epic decision D7 says a prompt edit re-summarises nothing and an explicit per-post verb is the only way an existing summary changes — Story 1 ships without that verb, so a prompt fix after the checkpoint cannot reach a single existing row, and a post that failed three times is stuck.
  • Archived posts are gone from view (the list shows unarchived only) and the list is mouse-only.
  • The text column grows without bound. D13 keeps summaries forever and full text for 90 days; nothing sweeps it yet, because nothing is 90 days old until now.

Every item is operability layered on a pipe that, by the time this is built, has run against a week or more of real mail. The epic's §7 cut this as Story 2 for exactly that reason, and its "Done" line is this spec's acceptance list in §13.

3 · Decisions this story makes

The epic decided what (D4's UI half, D5's helper, D7's re-run verb, D10's surface, D11's archive view, D13). These are the choices the epic left to the story, each with its why. A departure tag marks a place this spec deliberately differs from the epic's sketch; the epic says the story's spec wins, and the PR description names each one.

S2-1The Worker stamps the cap it enforced onto the health row. departure

reader_health gains daily_cap int, written by the tick in the same health write that carries calls_today/calls_day (value: READER_DAILY_CAP as the Worker resolved it). The UI's "ceiling reached" state is calls_day = today (UTC) and calls_today ≥ daily_cap.

Why: the cap is a Worker deploy var and the frontend has no access to it; hard-coding 30 in the UI would lie the day the var changes. The epic's S2-B says "no Worker changes" — this is a one-line write in the tick and is owned by the session's foundations slice, not by S2-B. It is what lets the banner say "(30)" truthfully.

S2-2The text sweep stamps text_swept_at, and a swept post cannot be re-summarised. departure

reader_posts gains text_swept_at timestamptz, set by the sweep in the same UPDATE that nulls text. The list payload (which never carries text) carries text_swept_at, so the row can hide the re-summarise verb; the route refuses { resummarize: true } with 409 when text is null.

Why: D7's verb re-runs the model over the stored text; after D13 there is none. Without a stamp the UI would offer a verb that always fails, or the payload would have to ship the text to learn that it's absent. A stamp is also the audit trail the epic wants for anything that changes a row under the owner.

S2-3Re-summarise is one verb, offered on done, failed and refused rows; pending rows and swept rows don't get it.

PATCH /api/reader/posts/[id] { resummarize: true } sets summary_state = 'pending', summarize_attempts = 0, last_error = null and keeps the existing headline / gist / overview until the tick overwrites them. The row shows Story 1's pending marker over the old summary. The label is Retry summary on a failed or refused row and Re-summarise on a done row (a ghost verb under the overview, where comms puts "Re-run classifier").

Why on done rows: the checkpoint's whole point is that a prompt fix must be able to reach existing rows, and a "failed only" verb couldn't. Why keep the old summary: blanking it would show a judgment that has not happened yet — the same reason the comms reclassify verb runs no exit animation. Why reset attempts: a refused row is "no retry" by D10; the owner asking is the one thing that overrides that, and the tick's own retry order then picks it up — under the ceiling, so a re-summarise past the cap waits for tomorrow like any other pending row, which the ceiling banner's count includes.

S2-4One banner at a time, in a fixed precedence; the header carries two dots.

The header shows a summariser dot and the Gmail (personal) dot, each with a sentence beneath when not live. At most one banner renders, the first that applies: Gmail dead (red — needs a person) → summariser stalled (amber) → daily ceiling reached (amber, informational). §8 has the derivations.

Why one banner: three stacked banners on a phone push the list off screen, and the states are not equally actionable — a dead mailbox makes the other two moot (nothing new arrives), and a stall makes the ceiling moot (nothing is being summarised). The dots keep the suppressed states visible. Why red for Gmail: it is the one state the owner must act on (re-authorize) — the comms header already colours an erroring account sentence red for the same reason. Why amber, not the module green, for the others: a green banner reads as "fine", and neither is.

S2-5"Stalled" mirrors classifierStalled, with the ceiling as a third rule.

Two signals, either sufficient: the health row's last_error_at is newer than last_success_at; or a pending, retryable post has been waiting longer than READER_STALL_MINUTES = 15 (three tick cadences) while no post has summarized_at inside that window — unless the ceiling is reached, in which case waiting is by design. A health row that has never been written is a distinct never ran state (amber dot, "The summariser has never run").

Why: the comms module learned both rules the hard way (its docstring says so) and they transfer exactly: a backlog under a per-tick cap is draining, not stalled, and the proof of life is the last summary. The ceiling rule is the Reader's own: past the cap, pending rows waiting is the correct behaviour, and a banner calling it a stall would train the owner to ignore the banner.

S2-6The Gmail filter helper emits from:(a OR b OR …) over every enabled handle, sorted, through the shared clipboard helper.

A pure gmailFilterQuery(publications) in frontend/lib/reader/gmail-filter.ts; the button calls it, then copyToClipboard, then toasts "Gmail filter query copied" on success and "Couldn't copy — clipboard unavailable" on failure. Disabled (with a title saying why) when nothing is enabled.

Why handles, not domains: the epic's D5 says so, and a per-address term is exact — from:substack.com would also archive Substack's platform mail the roster deliberately excludes. Why only the term: the filter's actions (skip inbox, label) are the owner's; alfred never holds a write scope (D5). Why a toast either way: the code store's launch verbs confirm a copy with a toast; a silent failure on a phone (the likeliest place this is tapped) would leave the owner pasting nothing.

S2-7Candidates are bulk senders seen in the last 30 days, ranked by count.

v_reader_candidates aggregates inbound gmail-personal messages with has_list_header = true whose sender_handle is not on the roster: handle, the most recent sender_name, message_count, last_seen_at, over the last 30 days. "Add" promotes one as source = 'owner', enabled, with domain derived from the handle.

Why 30 days: the epic's mockup says "9 in 30 days"; a sender quiet for a month is not a candidate for a reading list. Why no exclusions: the Amazon row is the point of the mockup — it is a candidate and stays one. Filtering "obvious non-newsletters" would be a judgment nobody can audit; the roster stays deterministic.

S2-8Disabling a publication stops future claims and nothing else.

enabled = false drops the sender from v_reader_worklist (Story 1's view already joins on enabled). Existing posts stay in the list and the archive. Re-enabling resumes from now — the seven-day horizon still applies, so posts that arrived while paused and are older than seven days are never claimed.

Why: "paused" is the honest word for what the toggle does, and a pause that deleted or hid history would be a destructive verb dressed as a switch. The one thing to say in the UI is the horizon, and the toggle's title says it.

S2-9Keyboard: the reader's own key map, the comms blocked-target rule imported, hints on the selected row only. departure

frontend/lib/reader/hotkeys.ts exports readerHotkeyAction(event) with its own KEYS map (§10) and imports isHotkeyBlocked from @/lib/comms/hotkeys unchanged. <kbd> hints render beside the verbs of the selected row, hidden md:inline-flex, styled as the search box's ⌘P hint.

Why import rather than mirror or extract: the epic allows a shared helper "if one extracts cleanly without editing the comms files"; it doesn't (the blocked-target check sits in a comms file), but it is exported, and importing a pure function is not a comms edit. Copying fifteen lines would fork the one rule that keeps hotkeys from eating keystrokes in a dialog. Why the selected row only: the epic's picture drew hints on an unselected row; but hotkeys act on the selected row, so a hint beside a verb that a keystroke cannot reach misleads, and one row of hints is the whole affordance on a list that is otherwise quiet. Fidelity to comms, where nothing draws hints at all, is the other reason to be sparing.

S2-10The archive view reads its own scope on first visit, newest-received first.

/reader/archive asks GET /api/reader/posts?scope=archived&limit=200 when first shown and holds the result in the reader store beside the active list. Rows are ordered by received_at desc (the list's order and index), offer Open ↗ and Unarchive, and expand into the overview like the list. Unarchive is optimistic: the row leaves the archive and joins the active list. If 200 come back, a muted line beneath says "Showing the latest 200".

Why not seeded by the shell: the archive is unbounded — every post ever skimmed — and the shell seeds every module on every page load. A lazy read on first visit is the comms shelf's own trade (it mounts nothing until opened). Why 200 and no paging: the archive is browsed, not searched; a "load more" is a follow-up if the owner asks.

S2-11Realtime on reader_posts is built last and dropped first.

If the story is not running long: the migration adds reader_posts to supabase_realtime, and the store subscribes to UPDATE with a guard that applies only the summary columns (headline, gist, overview, summary_state, summarize_attempts, last_error, summarized_at, model, prompt_version) — never text, never triage columns the browser writes.

Why last: Story 1's focus refetch already covers the common case (open the tab, the gist is there). The gotcha that makes it droppable: Postgres change payloads carry the whole new row, so every UPDATE on reader_posts would stream the full text (up to 400 000 chars) over the socket, and Supabase Realtime drops payloads over its size limit — meaning exactly the posts most worth summarising might never stream. The guard strips it client-side but the wire still pays. If built, the PR says so; if dropped, the migration line is left out and §14 records it as the follow-up.

4 · Data model changes

One migration, database/migrations/<next>_reader_operability.sql — take the next free number at build time. Same RLS and grant pattern as 0034_comms.sql; migration-lint wants the view grant in the same file as the bare create view. Regenerate frontend/lib/database.types.ts with npm run gen-types -w database; never hand-edit it.

-- 1. The cap the tick enforced, so the UI can say "(30)" without knowing the deploy var.
alter table reader_health add column daily_cap int;

-- 2. When the text sweep took a post's body. Null = still holds its text.
alter table reader_posts add column text_swept_at timestamptz;

-- 3. Bulk senders not on the roster, for the publications view's candidates list.
--    Mirrors D4's signal exactly: the comms header filter's has_list_header, on the personal account,
--    inbound, inside 30 days. Ranked by volume; the most recent display name wins.
create view v_reader_candidates with (security_invoker = true) as
  select
    m.sender_handle                                        as handle,
    (array_agg(m.sender_name order by m.received_at desc))[1] as name,
    count(*)::int                                          as message_count,
    max(m.received_at)                                     as last_seen_at
  from comm_messages m
  join comm_accounts a on a.id = m.account_id and a.key = 'gmail-personal'
  where m.direction = 'inbound'
    and m.has_list_header
    and m.received_at >= now() - interval '30 days'
    and not exists (select 1 from reader_publications p where p.handle = m.sender_handle)
  group by m.sender_handle
  order by count(*) desc, max(m.received_at) desc;

grant select on v_reader_candidates to anon, authenticated, service_role;

-- 4. The D13 sweep: null the text of every post past the window, batched like comm_sweep_expired so a
--    catch-up run past a statement_timeout keeps the batches it finished. Cutoff computed here, never
--    from the Worker's clock.
create or replace function reader_sweep_text(p_days int default 90)
returns int language plpgsql security invoker as $$
declare v_count int := 0; v_batch int; v_cutoff timestamptz := now() - make_interval(days => p_days);
begin
  loop
    update reader_posts set text = null, text_swept_at = now()
    where id in (select id from reader_posts
                 where received_at < v_cutoff and text is not null
                 order by id limit 5000);
    get diagnostics v_batch = row_count;
    v_count := v_count + v_batch;
    exit when v_batch = 0;
  end loop;
  return v_count;
end; $$;
grant execute on function reader_sweep_text(int) to anon, authenticated, service_role;

-- 5. Only if S2-11 (realtime) is built — otherwise leave this line out.
-- alter publication supabase_realtime add table reader_posts;

Column names and exact SQL are the build's to finalise against Story 1's migration (the sender-name column may be called something else; comm_accounts.key is how the epic names the account). If Story 1's tick already writes a cap to the health row under another name, use that column and skip item 1.

8 · Health: what the UI derives

frontend/lib/reader/health.ts — pure functions over the snapshot, the active posts and a caller-supplied now (the view owns one ticking useNow() and hands the same instant to every reader, as the comms queue does). Nothing here reads the clock.

export const READER_STALL_MINUTES = 15;   // three tick cadences: well past "the next tick will get it"
export const RETRYABLE_ATTEMPTS = 3;      // mirrors the tick's "attempts < 3" — keep in step with the Worker

export type SummariserState = 'live' | 'stalled' | 'never';

/** Ceiling: the tick has spent today's calls. Read off the row the tick writes, never off a UI constant. */
export function ceilingReached(health: ReaderHealth | undefined, now: Date): boolean {
  if (health?.daily_cap == null || health.calls_day === null) return false;
  return health.calls_day === now.toISOString().slice(0, 10) && health.calls_today >= health.daily_cap;
}

/** Pending rows the tick will still try — what the ceiling banner counts as "wait for tomorrow". */
export function waitingPosts(posts: ReaderPost[]): ReaderPost[] {
  return posts.filter(p => p.summary_state === 'pending' && p.summarize_attempts < RETRYABLE_ATTEMPTS && p.text_swept_at === null);
}

/**
 * Stalled? Two signals, either sufficient (the comms classifier's rules, transplanted):
 *  1. the tick recorded a systemic failure more recently than a success;
 *  2. a retryable pending post has waited past the cadence while NO post was summarised inside it —
 *     unless the ceiling is reached, in which case waiting is by design.
 * `since` is the earlier of the two, so the banner names when summarising stopped, not when it was noticed.
 */
export function summariserStalled(
  health: ReaderHealth | undefined, posts: ReaderPost[], now: Date,
): { state: SummariserState; since: string | null } { /* … */ }

/** Which banner, if any — the S2-4 precedence, in one place so header and stories agree. */
export type ReaderBanner =
  | { kind: 'gmail'; state: 'stale' | 'erroring'; account: CommAccount }
  | { kind: 'stalled'; since: string }
  | { kind: 'ceiling'; cap: number; waiting: number };

export function readerBanner(snapshot: ReaderHealthSnapshot, posts: ReaderPost[], now: Date): ReaderBanner | null {
  const gmail = snapshot.account && accountHealth(snapshot.account, now);   // imported from '@/lib/comms' — no comms edit
  if (gmail && gmail !== 'live') return { kind: 'gmail', state: gmail, account: snapshot.account! };
  const stall = summariserStalled(snapshot.health, posts, now);
  if (stall.state === 'stalled') return { kind: 'stalled', since: stall.since! };
  if (ceilingReached(snapshot.health, now)) return { kind: 'ceiling', cap: snapshot.health!.daily_cap!, waiting: waitingPosts(posts).length };
  return null;
}

Sketch, not final code — non-null assertions are shown for brevity and the build narrows properly. The comms accountHealth already encodes "erroring beats stale" and "the expected interval is the account's own"; import it rather than restate it. The "never" state (no health row) renders the amber summariser dot and the sentence "The summariser has never run — check the Worker's cron" but no banner: before the first tick there is nothing to be stalled from.

14 · Out of scope & open questions

Out of scope (deliberately)

  • Adding a publication by typing a handle. Promotion is from the candidates list only; a sender who has never mailed has nothing to claim. If the owner wants to pre-register one, that is a small follow-up (the POST route already supports it; only the form is missing).
  • Deleting a publication. Pause is the verb. Deleting would orphan its posts' publication_id and re-discovery would re-add a Substack sender on the next tick anyway.
  • Archive paging / search. 200 newest and a line saying so.
  • A hotkey for re-summarise, and any hint on unselected rows.
  • Auto-enabling non-Substack platforms (epic Q1) — see below.
  • Any comms change, any prompt UI, any change to the summariser's schema or model.

Open questions (genuinely)

  • Epic Q1 — which platforms auto-enable? Story 1's discovery is Substack-only; after a week of candidates the owner can see whether beehiiv / Buttondown / Ghost senders dominate. If so, the auto-enable domain list grows by one constant in the discovery step — a one-line change this story could carry if the owner says so in review; otherwise it stays manual promotion.
  • S2-E (realtime) — ship or drop? Decided by the session's remaining appetite after batch 3, per S2-11. The PR says which.
  • Where does the Story 1 handoff live? Unknown at spec time (Story 1 is not yet specced). Step 0 lists the places to look; if there is none, the PR says "no handoff found" and the §2 diff is done against the code alone.
