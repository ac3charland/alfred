1 · Context

The wiki is Andrej Karpathy's LLM wiki pattern. A model compiles the sources you choose into an interlinked set of markdown pages once, then keeps those pages current as new sources arrive. This avoids re-deriving everything from raw documents on every question, which is how retrieval (RAG) works and why nothing builds up with it. Alex reads a lot: newsletters through Alfred's Reader, Instapaper, and books with notes in Obsidian. None of it compounds today.

The epic (ALF-259) ships in two tickets. This one, Day 1, is the wiki itself, entirely outside Alfred. Day 2 is a separate Alfred story. It wires Alfred in: sending Reader "Novel ideas" bullets, classifying captured ideas as knowledge, a read-only reading room, and global search. Day 2 writes folders into this repo's inbox/ and reads the pages this build produces. So the source-folder contract in §5 is the part other work depends on, and it has to be exact.

Day 1 delivers:

  • the repo skeleton, CLAUDE.md, and the source-type/file-kind registry;
  • a shared schema module every script imports;
  • the Obsidian book importer and the link resolver, tested against the real Brain Rules sample;
  • a web-source producer (add) and the pointer fetcher;
  • lint and the index generator;
  • the filing script and the ingest skill that every ingest follows;
  • the kickoff workflow: the lock branch, the Routine fire, and the claude -p fallback;
  • the repo's own check gate in CI;
  • a runbook, including Alex's setup checklist.

2 · Decisions this build rests on

Restated from the ALF-259 epic spec so this document stands alone. §3 records what this refinement changed.

storeA private GitHub repo of plain markdown

Git is the queue, the store, and the audit log. Nothing about the wiki lives in Alfred's database. The Mac clone sits beside Alex's Productivity Coach folder, never inside it. Links run coach → wiki only, and the wiki never ingests coach files.

Why: Alfred's storage sweeps by design (Reader text at 90 days, comms at 60). The coach folder holds private self-knowledge the wiki must never synthesize from.

envelopeEvery source is one folder: the contract is fixed, the files inside are open

Fixed: one folder per source; the path scheme (§5.1); YAML frontmatter on every file declaring its origin; the author's text is never edited. Open: which files a folder holds. A new file kind or source type is one registry row. Ingest, lint, and (later) Alfred's reading room keep working unchanged.

Why: the author's words, Alex's words, and the model's words have different provenance, which matters for trust, licensing, and any future public export. Every wiki page cites these paths, so changing the scheme later means rewriting citations across the whole tree.

immutabilityOnly the body is frozen

A frozen file's body is never edited. Scripts may amend frontmatter; the model never does. A later send for an already-filed source is merged into the existing folder by identity and never duplicates it. A materially revised source is a new capture that names the old one with supersedes:.

fidelityHow much of the source was captured

full-text (the whole source as markdown), excerpt (verbatim highlights only; books), pointer (metadata and a URL; to be fetched), notes-only (no author's text at all).

registryNew source types and file kinds are registry rows; there's no denylist

Every source reaches the wiki because Alex explicitly sent it, so no source type is banned. Producers must split mixed provenance (quotes into excerpts-…, commentary into notes-…) and must never put model-written text in source.md.

barSending is the bar for ingesting; filing is not ingesting

Nothing enters automatically. A producer may mark a send ingest: file-only: ingest moves it into raw/ and logs it, but writes no pages from it.

picksPicked bullets are model-derived and get checked against the source

A picks-… file holds summary bullets Alex chose (Day 2's Reader send). Their wording is the summarizer's, so they carry origin: model-derived. Ingest checks each pick against source.md. A pick the source doesn't support is flagged in the PR and not used to write pages.

booksA deterministic importer on the Mac converts Obsidian book notes; no model runs in it

It splits provenance per quote: the quote and any longer passage go to excerpts-… (third-party), and commentary goes to notes-… (mine). It is incremental: it files only quote notes that are new or changed. It flags what it can't classify instead of guessing. Books cap at excerpt fidelity, never the full text.

crosslinksAlex's own links are kept as written, resolved by script, and treated as synthesis cues

[[Wikilinks]] in Alex's notes stay in the body exactly as written. A script-maintained links: map in frontmatter records where each one points, or that it's unresolved. Ingest must reflect every resolved link: the two sources' pages link to each other, and a concept page for the shared idea cites both. Plain-text mentions ("See Outlive") are the model's to notice.

skillOne committed ingest skill guides every ingest

.claude/skills/ingest/SKILL.md is the whole procedure. The Routine prompt, the claude -p fallback, and an interactive session all just say "follow the ingest skill". Improving ingest is an ordinary reviewed commit.

autonomyAutomatic runs draft a PR; Alex's merge is the review

An automatic run works on its lock branch and opens a PR. It never pushes to main. An interactive ingest, with Alex present, may commit straight to main.

kickoffAn Action fires a Routine; a lock branch pins each batch; one batch in flight at a time

A push to main touching inbox/** runs an Action. Unless a batch is already in flight, the Action takes the lock (claude/ingest-… at main's head) and fires the Routine. The batch is exactly the inbox/ folders on the lock branch. Anything that arrives mid-run waits for the next batch. Merging the PR releases the lock. That merge is also a push, so the next batch starts if items are waiting.

Why a Routine: it runs in the cloud while the Mac sleeps, bills to the subscription, and leaves a real session Alex can open from the phone. Routine GitHub triggers only fire on PR and release events, not pushes, which is why an Action sits in between.

privacyRecord the inputs now; the sensitivity and visibility scripts ship with export

From the first ingest, lint enforces source_type and origin on every raw file and a non-empty sources: on every wiki page. The model never writes sensitivity or visibility. Those fields don't exist yet.

formatRelative markdown links, YAML frontmatter, no Obsidian-only syntax, in wiki/

Three consumers read the same files unconverted: Obsidian, Alfred's react-markdown, and a future static-site generator. Link syntax is woven into every page body, so it can't be migrated cheaply. The rule covers pages the model writes. Alex's words in raw/ keep their links as written.

5 · The source-folder contract

5.1 Folders and paths

  • Folder name: <YYYY-MM-DD>-<slug>. The date is the captured date of the send that created the folder. The slug is the title, lower-cased and ASCII-folded, with every run of non-alphanumerics turned into -, cut at a word boundary to at most 60 characters. If the name is taken in inbox/, add -2, -3, and so on.
  • Waiting: inbox/<folder>/. Filed: raw/<YYYY>/<folder>/. The year comes from the folder name's date. Filing is a git mv and never changes a file's contents.
  • Every send is a new inbox folder (§3 #9). A producer never adds files to an existing inbox folder, even one for the same source.
  • A folder must hold at least one file. Every file is optional on its own.
  • Dated file names (notes-2026-10-01.md) use the send's captured date. If that name already exists for the same source, in inbox/ or raw/, add -2 before .md.

5.5 Identity and later sends

7 · The book importer

This is scripts/import-books.ts, run on Alex's Mac against the Obsidian vault. It converts #book notes into new inbox/ folders and pushes them. It is deterministic: no model runs in it. It is designed from the one real sample (Appendix A), and older notes may drift from that format. So anything it can't classify, it flags and skips instead of guessing.

7.1 Input format (from the sample)

  • Book note: a note tagged #book. The tag is a whole token on any line, or book in a frontmatter tags: list. After the tag come Key: value metadata lines (Author, Published, Read), then one [[link]] per quote note, in reading order. The book note's file name is the book's title.
  • Quote note: named after the quote itself, including literal enclosing double quotes ("People who experience chronic stress….".md). The body is blank-line-separated paragraphs. It can include any of: a longer verbatim passage in quotes, a locator line (Ch. 3 - Stress, Ch 11 - Exploration, Introduction), and commentary. Commentary may contain [[links]] and plain-text mentions.
  • Vault layout isn't assumed. Links resolve by file name across the whole vault, which is Obsidian's own rule. .obsidian/ and .trash/ are skipped. If two files share a link target's name, that link is flagged.
  • Normalize before any comparison or hash: Unicode NFC (macOS can hand back decomposed file names), CRLF → LF, trailing whitespace trimmed from each line. A missing final newline doesn't matter.

7.2 Parsing rules

Paragraph in a quote noteClassified asGoes to
Starts with " or “ and ends with " or ”, possibly across several paragraphs (opening quote on the first, closing quote on the last), before any commentarypassageexcerpt entry, without the enclosing quote marks
A single line matching ^(ch(apter)?\.?\s*\d+\b.*|introduction|preface|foreword|prologue|epilogue|conclusion|afterword|appendix\b.*|part\s+\S+.*)$ (case-insensitive)locatorexcerpt entry, verbatim (Ch 11 stays Ch 11)
Anything elsecommentarynotes entry, verbatim, links included
YAML frontmatter at the topignored—

The quote itself is the note's file name without .md, with one pair of enclosing quote marks removed. It is always the first line of the excerpt entry. A note with an empty body files just the quote.

In the book note, other non-empty lines count as book-level commentary. That means lines other than the tag, the metadata lines, and lines that are only links. They go to the notes file under the id book. A quoted paragraph there is flagged.

Metadata: Author → author. Published → published as a year or ISO date string. Read is parsed as M/D/YYYY (the sample has 10/2/2024, which becomes 2024-10-02) or as ISO. An unparseable value is dropped and flagged. Other Key: value lines are ignored and listed in the report.

7.3 Quote ids

id = "q-" + slug(quote, ≤ 40 chars, cut at a word boundary) + "-" + sha256(NFC file name without .md).hex[0..4]. The file name hashed includes its enclosing quote marks, so the id is stable for as long as the note's name is. These are the sample's ids, computed with this rule. ## q-by-stabilizing-the-parents-gottman-and-3da3

Locator: Ch. 3 - Stress

> By stabilizing the parents, Gottman and Shapiro were able to change not only the marriage but the child.

Passage:

> It consisted of exposing expectant couples to the marital interventions whether their marriages were in trouble or not, and then assessing the development of the child. Gottman and Shapiro uncovered a gold mine of information. They found that babies raised in intervention households didn't look anything like the babies raised in the controls. Their nervous systems didn't develop the same way. Their behaviors weren't in the same emotional universe. Children in the intervention groups didn't cry as much. They had stronger attention-shifting behaviors. They responded to external stressors in remarkably stable ways. Physiologically, the intervention babies showed all the cardinal signs of healthy emotional regulation, while the controls showed all the signs of unhealthy, disorganized nervous systems. The differences were remarkable and revealed something hopeful and filled with common sense. By stabilizing the parents, Gottman and Shapiro were able to change not only the marriage but the child.

7.5 Incremental re-runs

The repo holds all the importer's state. There is no separate state file, so any clone gives the same answer.

  1. Split each quote note into its excerpt part {quote, passage, locator} and its notes part (the commentary). Each part's hash is sha256 of a canonical serialization of the normalized part, truncated to 12 hex characters.
  2. Gather every quotes and entries record from all files with the book's identity, in both inbox/ and raw/.
  3. File a part only if its (id, hash) isn't already recorded. A new quote note files both parts, or just the excerpt if there's no commentary. An edited comment files only a new notes entry. An edited locator or passage files only a new excerpt entry.
  4. New parts go into new dated files in a new inbox folder named <today>-<slug> (§5.1), even when the book already has a folder in inbox/ or raw/. Filing merges them by identity (§10.1).
  5. When several files hold entries with the same id, the latest dated file's entry wins. The ingest skill applies this rule.
  6. If the book has nothing new, the report says "up to date" and nothing is written. A quote note that has been filed but is no longer linked from the book note is reported and never deleted. If the book's metadata (Author/Published/Read) differs from what was filed, that is reported, not applied (§16).

7.6 Links: the map, the marker, and resolution

  • Kept as written. A [[Target]], [[Target|alias]], or [[Target#Heading]] in commentary stays in the notes body unchanged. The map key is the part before any | or #.
  • What a target resolves to:
    • A #book note resolves to that book's raw/ folder path.
    • A quote note resolves to raw/…/excerpts-….md#<id>, using the excerpt entry whose quotes[].note matches the target.
    • Anything else stays unresolved until a producer files it.
    Resolution looks only at raw/, since inbox paths are temporary.
  • Marker. At import time, an unresolved link gets <!-- unresolved-link --> right after it in the body. The marker is written once and never updated, because the body is frozen. The map is the only truth, and nothing reads the marker as state.
  • resolve-links scans every notes-*.md in raw/, fills unresolved entries whose target now exists, and rewrites only the frontmatter. The body stays byte-identical. The importer runs the same resolver at import time, and ingest runs it after filing (§10.2).

7.7 Clusters

--clusters helps Alex pick the calibration cluster (§14.2). Each #book note is a node. An undirected edge A–B is weighted by the number of [[links]] from A's book note or quote-note commentary to B's book note or any of B's quote notes. The output lists connected components, largest total weight first, showing each book's degree, then the count of isolated books. Plain-text mentions don't count.

7.9 Flags (skip and report, never guess)

A flagged quote note is not filed, so nothing is recorded for it and the next run retries once Alex fixes the note. The rest of the book still files. The exit code is 0 unless --strict is given. Flag reasons:

  • an opening quote with no closing one;
  • two locator lines;
  • a quoted paragraph after commentary (possibly Alex quoting someone else);
  • an embed (![[…]]);
  • a book-note link whose target is missing from the vault, or ambiguous;
  • an unparseable Read or Published value, which is flagged on the book rather than skipped.

8.2 npm run fetch-pointers: complete pointers

It takes folders as arguments, defaulting to every folder in inbox/. For each source.md with fidelity: pointer, a non-null source_url, an empty body, and no fetch.result: ok:

  1. GET the URL: follow redirects, 20 s timeout, 5 MB cap, and a plain browser-like User-Agent.
  2. Convert by content type:
    • HTML: @mozilla/readability on a jsdom document, then turndown with turndown-plugin-gfm.
    • text/markdown or text/plain: use it as it is.
    • Anything else: record the failure unsupported content-type <type>.
  3. On success (at least 150 words): write the body; set fidelity: full-text; fill title, author, and published if they were null; set fetch: {attempted, result: ok, final_url}. Filling an empty pointer body is the only time a frozen body is ever written after it's created. Lint allows exactly that transition (§9).
  4. On failure (HTTP error, timeout, fewer than 150 words, which is likely a paywall, or Readability returning nothing): leave the body empty and the fidelity at pointer, and set fetch: {attempted, result: "<reason>"}. The ingest session reports it in the PR.

It never throws on a per-source failure. It exits non-zero only on a bug. With --json, it prints what it did. It never calls a model. The HTTP client is injectable so tests run offline.

10 · Filing and the ingest skill

10.1 npm run file-batch

This moves inbox folders into raw/ mechanically, so the model only writes pages. It takes folders as arguments, defaulting to every folder in inbox/. --exclude-ref <branch> skips folders present in that ref's inbox/, which interactive mode uses to leave an in-flight batch alone. It also takes --dry-run and --json. For each folder:

  1. Compute the identity. If the files disagree, leave the folder in place and report it.
  2. No raw folder with that identity: git mv inbox/<f> raw/<YYYY>/<f>. If the name is taken by a different identity, add -2.
  3. A raw folder exists: git mv each file into it. If a same-named file exists with identical bytes, drop the inbox copy. If its bytes differ, rename the incoming file with -2 before .md. Then remove the emptied inbox folder.
  4. Never change a file's contents.

With --json, it prints one record per folder: {inbox, raw, action: "new" | "merged" | "left", files, fileOnly, notes}. The skill works from this list.

10.2 What .claude/skills/ingest/SKILL.md must say

Keep the skill lean (about 200 lines at most). It is read on every run, and it will be tuned during the seed. It needs YAML frontmatter (name: ingest, and a description that triggers on "ingest", "process the inbox", and "run the batch"), and this procedure:

  1. Pick the mode. PR mode when you were given a lock branch; interactive when Alex is in the session.
  2. Start. Run npm ci.
    • PR mode: git fetch origin <lock> && git checkout <lock>. Never pull or merge main.
    • Interactive: git pull --rebase, then list claude/ingest-* branches on the remote. If one exists, tell Alex that batch is in flight, that its folders will be left alone (--exclude-ref), and that page edits now may conflict with its PR.
  3. Pointers. Interactive mode runs npm run fetch-pointers. In PR mode the Action has already done it. Either way, never fill source.md from WebFetch or your own words, and list any pointer still unfetched as a failed fetch.
  4. File. Run npm run file-batch -- --json, then npm run resolve-links, and commit file: <n> sources. In PR mode, push the lock branch and open a draft PR into main right away, using the template (§10.3) with the sources listed and the rest marked in progress. Use gh pr create --draft, or the GitHub MCP tool in a cloud session. The draft and each later push are how kickoff knows the run is alive (§11.2).
  5. For each filed source, in order (skip steps a–e for file-only):
    1. Read the whole folder. For entries with the same id, the latest dated file wins.
    2. Verify picks against source.md. Mark each as supported, unsupported, or uncheckable (a pointer). Never write pages from an unsupported pick; list it in the PR.
    3. Follow cross-links. For each resolved links entry, make the two sources' pages link to each other, and create or update a concept page for the shared idea that cites both, with Alex's remark as the reason. List unresolved links in the PR.
    4. Write pages. Write the source page, then entity pages, then concept pages only for ideas Alex's quotes, notes, or picks touch. Search index.md and grep before creating a page, and update rather than duplicate. Where a new claim agrees or conflicts with an existing page, say so and cite both. Every page cites its sources.
    5. Keep attribution straight. Third-party quotes are the author's. Picks are the summarizer's wording of the author. Only notes-… are Alex's views.
    6. Commit ingest: <title> with the page edits that source caused. In PR mode, push right away.
  6. Finish. Run npm run index, append the log entries (§6.4), and run npm run check. Fix pages until it's green, and never weaken a check. Commit index: rebuild and log.
  7. Hand off.
    • PR mode: push, fill in the draft PR's description from the template, and mark it ready for review. Never push to main, never merge, and never create a different branch or a second PR.
    • Interactive: summarize for Alex, then push to main once Alex agrees.
  8. Never:
    • edit a raw body;
    • write sensitivity or visibility;
    • delete a raw file;
    • touch inbox/ folders outside the batch;
    • hand-edit index.md.

The lead reviews this file line by line against this section. Every future ingest copies what it says.

11.1 kickoff.yml

on:

  kickoff:
    if: github.event_name != 'pull_request' || startsWith(github.head_ref, 'claude/ingest-')
    timeout-minutes: 90
    steps:
      - checkout main (fetch-depth 0) · setup-node 24 · npm ci
      - id: decide  → node scripts/kickoff.ts decide     # outputs: action=none|run, lock, runner=routine|cli
      - if run:     git checkout the lock · npm run fetch-pointers · commit "fetch: pointers" + push if changed
      - if routine: node scripts/kickoff.ts fire --lock <lock>   # output fired=true|false
      - if cli, or fired == false:
                    anthropics/claude-code-action@v1 (claude_code_oauth_token, prompt, claude_args)
      - if that step failed: node scripts/kickoff.ts release --lock <lock> --if-no-work
  • Pending runs. A concurrency group keeps one run going and at most one pending, and a newer pending run replaces an older one. That's fine, because every run reads main's current head through the API, not the event's SHA.
  • Not configured yet. If neither ROUTINE_FIRE_TOKEN nor CLAUDE_CODE_OAUTH_TOKEN is set, decide writes a warning annotation and returns none before taking any lock. That keeps the implementation PR's own merge harmless.
  • Tokens. The Action's own writes (creating and deleting refs, the fetch commit, closing a dead draft PR) use GITHUB_TOKEN. Those don't trigger other workflows, which is what we want.
  • Cost. Sweeps and fires take seconds. A fallback run spends Actions minutes against the private repo's monthly allowance, which is one reason it is the fallback and not the default.

11.2 scripts/kickoff.ts decide

The decision is a pure function of the lock branches, their PRs, the files in inbox/ on main, the event, and the current time. A thin I/O layer (scripts/lib/github.ts, calling GitHub's REST API with fetch) feeds it, so tests drive the table below with fakes and a fixed clock.

  • Lock names look like claude/ingest-YYYYMMDD-HHMMSS (UTC), optionally followed by -retry. A lock's age comes from its name. A name under claude/ingest- that doesn't parse is treated as in flight, with a warning, so a hand-made branch can't wedge anything silently.
  • A lock's PR is the PR whose head is the lock, or failing that, a PR whose body's first line is lock: <lock>. Any state counts. A ready PR is open and not a draft.
  • A lock's last activity is the later of the time in its name and its head commit's committer date.
  • An empty inbox means inbox/ on main's head holds no folder. .gitkeep doesn't count.
What the sweep findsThen
A lock whose PR is closed or mergedDelete it (released) and continue.
A lock with no ready PR whose last activity is over 3 h agoClose its draft PR if it has one, with a comment saying the run went quiet. Delete the lock (dead) and continue. The next lock this run takes gets the -retry suffix. Exception: if the dead lock was already a -retry lock and the event is schedule, stop. A batch that died twice waits for the next push or a manual dispatch (it may be a poison batch).
A lock with a ready PR, or with last activity within 3 hStop. A batch is in flight, either awaiting review or still working.
No lock in flight; the event is pull_requestStop. Closing a PR releases the lock but never starts a batch.
No lock in flight; the inbox is emptyStop.
No lock in flight; the inbox is non-emptyCreate the lock at main's head. If creating it fails because it already exists, stop. Set runner to cli for a -retry lock and to routine otherwise.

13 · Subagent plan

Rules for dispatching. These are restated here because this repo has no skill for them.

  1. Build the foundation first, alone. Anything two slices need is built before the fan-out: shared types, the schema module, package.json with every dependency and script entry, the registry, and the CLI names. Two agents inventing the same helper is the default failure.
  2. Slice by behavior, not by layer. Each subagent owns one vertical slice and can test it on its own.
  3. Give each subagent its own files. No two subagents edit the same file. None of them edits scripts/lib/{frontmatter,schema,registry,sources,paths,git}.ts, package.json, the lockfile, tsconfig.json, registry.yaml, or CLAUDE.md. If one needs a change there, it stops and reports the exact change it needs.
  4. Brief each one as if it can't ask a question, because it can't. Each brief carries:
    • this spec's path;
    • the slice's behavior and acceptance criteria, in your own words;
    • its files and the files it must not touch;
    • the instruction to pin every behavior with node:test tests.
  5. Subagents write code and tests. They don't commit, push, or open PRs. The lead does that, once.
  6. A subagent's report is a draft. The lead reads every diff, reconciles the seams, and runs the full npm run check. A green subagent report is not a green repo.

Table-driven decide tests with a fake GitHub and a fixed clock: each row, a quiet lock with a draft PR (closed and swept), a draft PR with a recent commit (in flight), the -retry poison guard, a PR found by its lock: line, an unparseable lock name, and a .gitkeep-only inbox. fire with an injected fetch: 2xx, 429, 500, and a network error. release --if-no-work both ways.
E · Web sources scripts/add-source.ts, scripts/fetch-pointers.ts, scripts/lib/extract.ts, their tests, scripts/fixtures/html/** §8 in full. It never calls a model, and a per-source failure never throws. An article HTML fixture turns into the expected markdown, with a table (GFM) kept. A short page is recorded as a failure. HTTP 403, a timeout, and a PDF content type are recorded. Non-pointers and already-fetched pointers are skipped. add produces a pointer, a full-text source, and notes. A new folder is created even when the source already has one.

13.3 Order and seams

  1. Foundation, done by the lead, with npm run check green on an empty wiki.
  2. A to E in parallel. They depend only on the foundation.
  3. Integration, done by the lead. Reconcile these seams, each shared by two or more slices:
    • the identity lookup: B uses it for filed state, C for merging, and A for the duplicate check; all must call sources.ts;
    • the quote-id and ## <id> heading format: B writes it, and A and the skill read it;
    • the links map shape: B writes it, and A and the skill read it;
    • the fetch field: E writes it, and A and the skill read it;
    • the CLI flags: C's skill and D's workflow call B's, C's, and E's scripts;
    • the PR template's lock: line: C writes it and D matches on it.
  4. An end-to-end dry run on fixtures, done by the lead, in a scratch clone: import the sample, add a pointer with a stubbed fetch, run file-batch, resolve-links, index, and npm run check. This proves the pieces compose. It isn't an ingest; no pages are written.
  5. Review the skill line by line against §10.2, then write the README runbook (§14.1 as a checklist, plus troubleshooting: how to clear a stuck lock, re-run kickoff, and read a failed fetch). Then commit and open the PR.

13.4 What the lead keeps, and model tiers

  • The lead keeps: the foundation, integration, the skill review, the dry run, the full check, all commits, and the PR. Anything that needs Alex's accounts or Mac is written as a checklist, not attempted.
  • Tiers: the lead on the strongest model; the five implementer subagents on the mid tier; file lookups and searches on the fast tier.

14.2 The seed plan (manual, after setup)

A wiki page is about an idea, a person, or a question, and a book is only an input. So importing Brain Rules into an empty wiki should give:

  • one source page;
  • concept pages only for the ideas Alex's quotes touch;
  • entity pages for John Medina, John Gottman, and the Bringing Baby Home study;
  • an index line and a log entry.

For the first handful of sources, the wiki looks like book summaries with extra steps. It becomes a wiki once sources start sharing concepts.

  1. Smoke test, which is how Alex accepts Day 1. Send Karpathy's LLM-wiki document (Alfred's docs/knowledge-base/llm-wiki.md) in as a full-text article: npm run add -- --file <alfred clone>/docs/knowledge-base/llm-wiki.md --url <the gist URL> --title "LLM Wiki" --author "Andrej Karpathy" --push. Watch it go through the lock, the Routine, the PR, and the merge. Alex knows this document well enough to judge whether the pages are right, not just whether the pipeline ran. Check that the PR's head is the lock branch. Then check the fallback once: set ROUTINE_FIRE_TOKEN to a wrong value, add a small source, confirm the fallback opens the PR and that CI runs on it, then restore the token.
  2. A calibration cluster, one book per PR. Run --clusters and pick about five tightly linked books. Import one, review its PR closely, adjust the skill and CLAUDE.md, and merge before importing the next. A book imported while a PR is open joins the next batch, so importing ahead would merge two books into one PR and skip a round. The second and third books should visibly update pages the first one created. Look at:
    • page granularity;
    • page naming;
    • whether cross-links became links between pages;
    • whether each kind of text stayed attributed to its origin;
    • whether the index and log entries are useful.
  3. Bulk import once calibration settles. Books outside any cluster go in with --file-only.
  4. Optional: measure it. For the first sessions after the seed, log each question as query | … | hit|miss|wrong in log.md.

Why this order: the first ingests set the conventions every later ingest copies. Fixing them at source 5 is a CLAUDE.md edit; fixing them at source 150 is a reorganization. Starting cluster-first makes books compound from the second ingest.

16 · Out of scope & open questions

Out of scope

  • Every Alfred-side integration, which is Day 2: Reader send, knowledge classification, the snapshot, the reading room, and global search.
  • Instapaper in any form. The tag-sync follow-up covers it (§3 #3).
  • The sensitivity mapper, the visibility computer, public export, a static site, and a graph view. These stay deferred under the spike's triggers.
  • A search tool such as qmd, until index.md no longer reads in one pass.
  • Kindle and Readwise exports, PDFs, and other producers. Each is a registry row plus a producer, later.
  • Running the seed. It is Alex's manual work (§14.2).
  • Applying book-metadata changes after the first import. They're reported. Frontmatter could be amended by a script later if that's ever wanted.

Open questions

  • How far older book notes drift from the sample. Only running over the whole vault will tell. The importer flags instead of guessing, so the drift shows up as a report, not as mis-filed text. The parsing rules get extended during calibration.
  • The Routine's daily cap. It isn't shown until a Routine exists. The fallback makes it irrelevant to correctness. Record it once known.
  • A poison batch. A batch whose run dies twice waits for a push or a manual dispatch. Whether it should also open an issue can wait until it happens.
  • Renaming a note. Renaming a book or quote note in Obsidian changes its identity or id, so it files as new. If Alex renames notes often, a rename map is the fix.
  • merge=union on GitHub. Whether GitHub's merge button honors it is unverified. If an ingest PR conflicts on log.md because an interactive session appended to it, the fix is to keep both sides, which also works in GitHub's web conflict editor.
