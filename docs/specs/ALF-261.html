1 · Context

Day 1 built the wiki itself, outside Alfred. A private repo holds sources in inbox/ → raw/ and pages in wiki/. A push that touches inbox/** takes a lock branch and fires a Routine. The Routine follows the ingest skill and opens a PR, and Alex's merge is the review. Right now the only way in is npm run add or the book importer on the Mac, and the only way to read is Obsidian or GitHub.

Day 2 connects Alfred at both ends. In: the Reader has already done the expensive part, finding each newsletter's novel ideas, and that work expires with the post. Captured ideas are just Inbox rows. Both should flow into the wiki with one click. Out: Alfred is meant to be the one place Alex goes. A wiki he can only read elsewhere is a wiki he'll forget to read.

2 · What this refinement settled

D1 · One send is one commit, through the Git Data API departs from epic

The epic names the GitHub Contents API, but that API writes one file per commit. A Reader send has two files. Its first commit is a push to main touching inbox/**, which can start kickoff. Kickoff can then take the lock with only source.md in the batch, and the picks-… file lands in that same folder on main while the batch is moving it to raw/. That is exactly the conflict Day 1's "every send is a new folder" rule exists to prevent. So the writer builds one tree and one commit, then fast-forwards main (§4.4).

Cost: seven requests instead of two per send, plus a retry loop when main moved underneath us. Both are cheap on Vercel.

D2 · The module is called Wiki on screen Alex departs from epic

The switcher has about 47px spare at the sidebar's 256px width. "Wiki" fits and "Knowledge" does not. The module id is wiki, its URL is /wiki, its code lives in components/wiki/, and the switcher, heading, ⌘K and ⌘P all say "Wiki". The item type keeps the DB's reserved knowledge value: an Inbox row is classified as Knowledge and dispatched to the wiki.

D3 · The snapshot is pages only; raw citations open on GitHub Alex

Only wiki/*/*.md is snapshotted. A citation into raw/ (a quote, a notes file, a source folder) becomes a GitHub link in a new tab. Raw sources are large, never searched, and a bulk import can move hundreds of them in one merge, which would blow the Worker's budget (D4).

D4 · The snapshot reconciles to the repo's tree, in two GraphQL calls new

The epic's "fetchSpec pattern" fetches one file per REST call. The Worker runs on the Free plan: 50 subrequests and 10ms CPU per invocation. An ingest merge touches 10–30 pages. So the sync (a) asks GraphQL for the current tree's blob ids, (b) diffs them against the stored ids, and (c) fetches every changed page's text in one aliased GraphQL query. That is about six subrequests whatever the size, and each run is capped by CPU instead (60 pages, §7.3). A tree diff is self-healing: a missed webhook is repaired by the next push or by a daily safety-net run on the existing retention cron. No new cron slot is used; the Free plan's last one stays free.

D5 · The store seeds an index; bodies load on demand new

The shell layout seeds every module on every load, so wiki bodies must not ride along. The store seeds each page's path, section, title, summary, tags, dates and outbound links. A body is fetched when a page opens and cached by blob id. This is the weekly_plans precedent in the data-flow skill ("big documents seed lazily").

D6 · Search depth: the module searches bodies too; ⌘P stays titles Alex

Inside the Wiki module, typing gives instant title, summary and tag matches from the store, plus body matches from Postgres full-text search with highlighted snippets. ⌘P global search matches only title, summary and tags, instantly and client-side, the same way its other groups work.

D7 · A knowledge dispatch stamps, then deletes, in one RPC new

"Takes the item out of Alfred" is a hard delete, which is the epic's rule and ALF-7 D2. The classifier's learning loop (classification_corrections) only logs when dispatched_at goes from null to set. So the RPC send_items_to_wiki stamps dispatched_at first, which logs any correction such as "the classifier said task, Alex said knowledge", and only then deletes. convert_to_code_epic is the precedent for consume-and-delete. The items_dispatched_needs_folder CHECK is relaxed to exempt knowledge, as it already exempts code.

D8 · Sent state is stored as the bullet's text new

A novel_ideas bullet is a bare string with no id, and re-summarising a post rewrites the whole list. So reader_posts.wiki_sent_ideas text[] records the exact strings that were sent. A bullet shows as sent when its text is in that array. An index would point at the wrong bullet after a re-summarise.

D9 · Wiki writes are Personal-only new

Both instances run identical code. The write token is set only on the Personal Vercel project, and the snapshot Worker already writes only the Personal Supabase. When the writer isn't configured, the layout seeds writable: false, and every send affordance disappears: the Reader's controls and the Inbox's Classify as → Knowledge. The Work instance can never write into the personal wiki.

D10 · A fifth module hue: violet new

modules.ts requires one distinct hue per module. Teal, green, blue and amber are taken, and red means danger. The foundation adds --color-accent-violet: #a78bfa (Tailwind violet-400, from the same -400 family as green, blue and red) and glow-violet. The wiki's own marks wear violet, including inside the Reader: the sent checks, and the glyph on Send all. Selection and primary actions keep the app's standard teal, exactly as the Inbox's select-and-Dispatch does.

D11 · Reader posts get a producer-scoped identity new

external_id: "alfred:reader-post:<uuid>" keeps a post's sends stable even when canonical_url is null (email-only newsletters). It follows Day 1's alfred:item:<uuid> and the Instapaper follow-up's bookmark id. source_url still carries the canonical URL, so fetch-pointers can complete a swept post.

D12 · Reader send is a checklist: tick, then send once Alex

The epic's "send a single bullet or all of them" becomes tick any subset, then send it in one press, with Send all kept as the shortcut (§5.1). One ticked bullet still covers the single-bullet case. What goes away is sending bullets one press at a time.

Why: every send is a push to inbox/, and every push can take kickoff's lock. Per-bullet sends wouldn't start one Routine run per bullet, because the lock queues everything after the first send into one next batch. But they would still split an article: the first run ingests a lone bullet without its siblings, and Alex reviews two PRs for one article. Ticking first makes one article one send.

3 · Architecture

① A send commits one folder to main. ② Day 1's pipeline runs unchanged up to Alex's merge. ③ The merge's push reaches the Worker, which reconciles the page snapshot. ④ The Wiki module reads the snapshot. Dashed lines are reads, the safety net, or a human step.

What the architecture keeps from the epic:

  • Alfred only ever writes inbox/ folders. It never writes a page and never pushes anywhere else.
  • Git stays the queue. A failed send leaves nothing behind. A failed sync leaves the previous snapshot and a last_error.
  • No LLM runs in Alfred's path. The classifier only suggests knowledge; Alex's dispatch is the decision.

4.3 Folder names

writer/paths.ts mirrors the wiki's scripts/lib/paths.ts slugify / folderName / uniqueFolderName exactly: NFKD fold, lower-case, every run of non-alphanumerics becomes -, a word-boundary cut at 60 characters, and an empty slug becomes untitled. It carries a comment naming that file. Uniqueness is checked against the inbox/ names at the base commit and the other folders in the same commit.

4.4 The commit

commitEnvelopes(config, envelopes, { fetch?, now? }) in writer/commit.ts takes an injectable fetch. It returns { commitSha, folders } after seven requests:

  1. GET /repos/{o}/{r}/git/ref/heads/main gives the head commit.
  2. GET /repos/{o}/{r}/git/commits/{head} gives the base tree. Then GET /git/trees/{base} finds inbox, and GET /git/trees/{inbox} lists the names already taken.
  3. POST /git/trees sends { base_tree, tree: [{ path, mode: "100644", type: "blob", content }] }, one entry per file across every envelope.
  4. POST /git/commits sends { message, tree, parents: [head] }. The message is add: <title> for one folder, or add: <n> sources for several, matching npm run add.
  5. PATCH /git/refs/heads/main sends { sha, force: false }. A 422 from this PATCH means main moved, so the writer re-runs from step 1, at most 3 attempts in total. Any other non-2xx fails at once as rejected, and that includes a 422 from the tree or commit POST (a malformed path is never "busy").

Every request sends the headers workers/src/github.ts uses (Bearer, application/vnd.github+json, X-GitHub-Api-Version: 2022-11-28), with User-Agent: alfred-wiki. Failures throw a typed WikiWriteError (kind: 'unauthorized' | 'rejected' | 'busy' | 'unreachable'). Routes map the first, second and fourth to 502 {error: "Couldn't reach the wiki repo"}, and busy to 503 {error: "The wiki repo was busy — try again"} after the third 422. An unconfigured writer is 501, following the pr-ratio precedent. The token never appears in an error or a log line.

5.1 What Alex sees

The Novel ideas section becomes a checklist with one dispatch. Alex ticks the bullets worth keeping, then sends them together, so each article reaches the wiki as one send: one folder, one commit, and one kickoff trigger. It is the Inbox's select-then-Dispatch gesture in miniature, reusing its vocabulary. Send all stays as the one-press shortcut. None of this appears unless writable is true and the list is non-empty.

  • Each unsent bullet is a checklist row with role="checkbox" and aria-checked. A click or tap anywhere on the row toggles it, and so does Space when focused. The whole row is the hit target, so it works on a phone.

  • The selection bar appears under the list once one or more bullets are ticked. It reveals through AnimatedHeightCollapse, honoring reduced motion. It holds:
    • n selected in text-sm font-semibold text-accent-teal, the bulk bar's counter;
    • Button variant="accent" size="sm" with BookPlus + Send to wiki, which sends exactly the ticked bullets in one request;
    • Button variant="ghost" size="sm" Clear, which unticks everything.
    Selection and the primary action wear the app's standard teal, as the Inbox does. Violet is kept for the wiki's own marks: the sent checks and the BookPlus glyph on Send all.
  • Send all to wiki keeps its place on the section heading row: a ghost Button size="sm", violet BookPlus. It sends every unsent bullet whatever is ticked, and clears the selection on success. When every bullet is sent, it becomes muted text-xs "All sent to wiki" with the violet check.

    • On failure, a toast shows, and the ticks stay exactly as they were, so the retry is one press. This is the Inbox's "failed rows stay selected".
  • Selection is transient: it is the list's own useState, keyed by bullet text. Collapsing the overview drops it. There is no hotkey.

5.2 Behavior

  • Not optimistic, by design. A send is a commit to another system: it takes 1–2s and fails for reasons the store can't reconcile, such as a bad token or GitHub being down. So the pressed button reads Sending… until the server confirms, and only then do the ticked bullets flip to sent. It never claims success first and snaps back afterwards. The in-flight flag and the selection are the list's own useState. The write lives in the store action, so a row collapsed mid-send still lands, and its bullets read as sent when reopened.
  • Store action: sendIdeasToWiki(postId, ideas) in reader-store.tsx.
    • It calls beginWrite(postId), so a focus refresh keeps the local row.
    • It calls api.sendReaderIdeasToWiki, and on success reconciles with {type: 'replace', item: saved}.
    • On error it toasts the route's own sentence when the response carries one (the 409, 501, 502 and 503 bodies below), else Couldn't send to the wiki. It then rethrows, so the list re-enables its controls and keeps the ticks. The existing refusal() helper surfaces only a 409's detail, so this action reads ApiError.detail whatever the status.
    • endWrite runs in finally.
  • Route: POST /api/reader/posts/[id]/wiki, body { ideas: string[] } (1–6 non-empty strings, .strict()), through withSession.
    • It returns 501 if the writer isn't configured and 404 for an unknown post.
    • It returns 409 "That idea isn't in this post's overview any more" if any idea isn't in the current overview.novel_ideas. That happens when a re-summarise ran underneath.
    • It drops ideas already in wiki_sent_ideas. If none are left, it returns 200 with the row unchanged and makes no commit.
    • Otherwise it builds the envelope, commits, then appends the new ideas through the RPC append_wiki_sent_ideas(p_post, p_ideas) (§10). That RPC is one atomic update that adds only strings not already present. The UI allows one send per post at a time, but two tabs or devices can still race, and a read-modify-write here would let the later send erase the earlier one's bullets.
    • It returns the row with list columns only, so text never reaches the client.
  • Reading the row with text. The route uses a new getReaderPostForWiki(id) in lib/data/reader.ts, the only reader that selects text for this purpose.
  • If the append fails after the commit, the route returns 500 and the bullet reads unsent, although it reached the wiki.
    • A same-day retry commits a byte-identical picks file, which filing drops.
    • A retry on a later day commits picks-<later date>.md, so the ingest session sees that bullet twice. The cost is a repeated citation, never a lost idea.
    • Committing first is deliberate. Reserving the bullet first and un-reserving on failure risks the opposite: a bullet marked sent that never reached the wiki.
  • Re-summarise can reword bullets. A reworded bullet reads as unsent because its text isn't in the array. Old strings stay in the array harmlessly.

7.2 syncWiki(env, { fetch?, now? }): one run

  1. GraphQL #1 (POST https://api.github.com/graphql): ref(qualifiedName: "refs/heads/main") { target { oid } }, plus four aliased object(expression: "main:wiki/<section>") { ... on Tree { entries { name type oid } } }. Keep only type: "blob" and names ending .md. A response carrying an errors array, or a null ref, is a failure (step 7), never an empty tree. A partial or rate-limited answer must never read as "every page was deleted". A null section object counts as an empty section only in an error-free response.
  2. Supabase: select=path,blob_oid from wiki_pages.
  3. Diff. changed is every tree entry whose oid differs from, or is missing in, the table, sorted by path. removed is every row whose path left the tree. The first WIKI_SYNC_PAGE_CAP = 60 changed paths are taken, and pending is the remainder.
  4. GraphQL #2 (only if there are changes): one aliased p<i>: object(oid: "<blob oid>") { ... on Blob { text isBinary isTruncated } } per taken path. Fetching by oid means the text is exactly the blob that was diffed. A binary or truncated blob is stored with parse_error set and an empty body.
  5. Parse each page (§7.4).
  6. Upsert the parsed rows in one request (on_conflict=path, resolution=merge-duplicates). Delete the removed paths in one request (path=in.(…), each value double-quoted).
  7. State. Upsert wiki_sync row 1 with {commit_oid, synced_at, pending, last_error: null}. On any thrown failure, write {last_error, last_error_at} and leave the pages untouched.

That is at most six subrequests per run. The 60-page cap is the CPU ceiling: parsing a few-hundred-byte YAML block and scanning a page's links costs roughly 0.1ms per page, leaving headroom under the Free plan's 10ms. The arithmetic goes in the cap's doc comment, following the cloudflare-workers skill. Once more than 60 pages have changed, the rest converge on the next trigger, and the Wiki header says so (§8.4).

7.3 Why not fetchSpec

fetchSpec is one REST call per file, so the budget would cap a run at about 40 pages. It also depends on the push payload's file lists, which can be truncated. The tree diff needs neither. fetchSpec itself stays untouched. The Worker gains a yaml dependency (foundation).

7.4 Parsing a page (workers/src/wiki/page.ts, pure)

  • Frontmatter is split the way the wiki's parseFile does it (a leading ---\n, the next \n---, and CRLF normalized), then parsed with yaml. If the YAML is invalid, parse_error is set and the whole text becomes the body.
  • title: the frontmatter title, or the file stem when it is missing or blank (the wiki's titleFor). summary: a string, or ''. tags and sources: string lists, filtered to non-empty strings. created and updated: kept when they are real YYYY-MM-DD dates, else null.
  • links: extract link targets the way the wiki's extractLinks does, masking fenced and inline code. Resolve each relative to the page's folder literally, with no URL-decoding (the wiki's lint resolves targets the same way), strip the #anchor, and keep only wiki/<section>/<name>.md targets that don't escape the repo. Dedupe, drop the page itself, and sort. Missing targets are kept, since a backlink doesn't care whether the target exists.
  • section comes from the path.

11.4 Each slice's loop: implement → antagonize → fix

  1. Dispatch the implementer (Sonnet). Its brief carries:
    • this spec's path and its section numbers;
    • the slice's behavior and acceptance criteria in the lead's own words;
    • the exact file boundary and the foundation files it must not touch;
    • the relevant skills to read first (data-flow, frontend-architecture, react, storybook, playwright, jest, cloudflare-workers, supabase, as they apply);
    • "TDD; pin every behavior with a test; never commit; report what you needed outside your boundary".
  2. As soon as it reports, dispatch its reviewer (Opus, read-only). Pipeline, don't wait for the batch: slice C's review can run while D is still building. The reviewer's brief:
    • Posture: "Assume this slice is wrong and find out how. You are not here to approve. Every finding needs a concrete failure: a file:line, the input or state that breaks it, and what happens. Verify it by reading the code path or running the test before you report it. Mark each finding blocking (spec drift, a missing or toothless test, a bug, a guardrail bypass, a boundary breach, security) or non-blocking (naming, a clearer comment). If you find nothing blocking, say so in one line. Do not edit any file."
    • Hunt list:
      • Every acceptance line has a test that would fail if the behavior broke. Mutation thinking: delete the line, and see whether anything goes red.
      • The mockup's states are all drawn in stories.
      • No eslint-disable, @ts-*, .skip, or config edits.
      • No file outside the boundary.
      • The data-flow patterns: store actions through api-client, no router.refresh, no Supabase in components.
      • The token or text never reaches the client. The body route's path is validated.
      • The Worker's subrequest and CPU arithmetic holds.
      • Icon-only buttons have accessible names.
      • Mobile width.
      • Reduced motion.
      • §7.5 rows implemented identically.
  3. Fix round. The lead forwards the blocking findings to the same implementer via SendMessage, so its context survives. Non-blocking findings are the lead's call. The reviewer is resumed with the delta and re-checks each earlier blocker plus anything the fix touched.
  4. Exit: the reviewer reports no blocking findings. The cap is three rounds. After that the lead reads the dispute and decides, fixing it itself if the fix is small. A disagreement about intent goes to Alex in the tab, not into the code.

12 · Acceptance criteria

  • Writer
  • One send is one commit on main in a brand-new inbox/ folder, even when the post has an earlier send. A moved main is retried up to three times.
  • Golden envelopes pass the wiki repo's own npm run lint, and file as new, then merged, under file-batch --dry-run (§11.6).
  • The token is never sent to the client, logged, or echoed in an error. An unconfigured writer returns 501, and every send affordance is hidden.
  • Reader send
  • With the wiki connected, the Novel-ideas bullets are a checklist. Ticking any number and pressing Send to wiki sends exactly those bullets in one commit. Send all to wiki sends every unsent bullet in one commit.
  • The nothing-ticked, ticked, sending, all-sent and not-connected states render exactly as the mockup draws them. Only one send per post runs at a time. A failed send keeps the ticks. Concurrent sends from one post never lose a sent mark. When every bullet is sent the button becomes "All sent to wiki". The sent state survives a reload.
  • A swept post sends a pointer source.md (or picks alone when it has no URL). A reworded bullet reads as unsent. A failed send toasts and returns the bullet to unsent.
  • Without the wiki connected, and on a post with no novel ideas, the overview is pixel-identical to today.
  • Knowledge captures
  • The classifier can suggest knowledge (prompt v3). A held knowledge row is never retyped by the sweep, and a knowledge verdict carries no other labels.
  • An Inbox row can be classified as Knowledge from the ⋯ menu and the bulk bar. It shows the Lightbulb glyph and no label chips.
  • Dispatching knowledge rows commits one notes-… folder per row in one commit, deletes the rows, logs a classifier correction when Alex overrode the guess, and toasts "Sent to the wiki" or "Sent n ideas to the wiki". A knowledge row with subtasks is blocked with "has subtasks". Without the wiki connected, a knowledge row is blocked with "wiki not connected". A knowledge row can't be dragged into a folder, and classifying a row as Knowledge clears its folder label.
  • Snapshot
  • A push to the wiki's main updates wiki_pages to match its wiki/ tree: new, edited, renamed and deleted pages, at most 60 per run, with the remainder counted as pending. Pushes to other branches or repos are ignored.
  • A run makes at most six subrequests. A GraphQL failure records last_error and leaves the pages untouched. The daily retention cron also runs the sync.
  • Wiki module
  • A fifth switcher segment, Wiki, in violet, fits the sidebar without truncating any label. It has a sidebar nav with counts, mobile nav, ⌘K destinations, and deep links that survive a hard load.
  • The index, section, page, search, loading, error, not-found, empty and sync-failed states render as the mockups draw them.
  • Links behave per §7.5, including heading anchors that match the wiki's rule. Backlinks list every page linking in.
  • Module search shows instant title, summary and tag matches plus body matches with highlighted snippets. ⌘P shows a Wiki group matching title, summary and tags.
  • Process
  • Every slice passed its Opus review with no blocking findings. npm run check is green on the final tree. There is a demo doc (§13). This spec is archived in the implementation PR.

15 · Out of scope, risks, open questions

Deliberately out

  • Rendering raw/ files inside Alfred (D3). Revisit if following citations to GitHub on the phone proves annoying.
  • Body search in ⌘P (D6).
  • A graph view, and any write path to pages (epic non-goals).
  • Alex's own note attached to a Reader send (a notes-… file beside the picks). The contract already allows it, so it can be a small follow-up.
  • A keyboard shortcut for sending ideas.
  • Hiding the Wiki module on the Work instance, where it is always empty (both instances run identical code; Reader is the precedent).
  • Realtime push of snapshot changes. The navigation and tab-return refresh is enough at a few merges a day.
  • Instapaper tag sync (the epic's follow-up).

Risks

  • Size. The spike put Day 2 at about the Reader's whole build (≈14.6k lines with tests). One PR of that size is a long review. The per-slice Opus loop is there to make sure that review isn't where bugs are first found.
  • GraphQL with a fine-grained PAT. This spec assumes the Worker's fine-grained token can read the repo through GraphQL. If the smoke test shows an auth error that step 2 of §14 doesn't fix, graphql.ts falls back to REST (git/trees?recursive=1 plus one git/blobs/{sha} per page, capped at 40). That is a contained change behind syncWiki.
  • Worker CPU. The 60-page cap is an estimate. If a run hits the CPU limit, lower the constant; the remainder converges on later triggers.
  • Classifier drift. With no eval harness, knowledge may be over- or under-suggested at first. The corrections table (D7) is the signal to watch.

Open questions

None block the build. Alex settled the three scoping calls in the refinement session (D2, D3, D6). Everything else is decided above, where a reviewer can overturn it in PR comments.
