ALF-263 — Implement an Instapaper-to-Wiki pipeline

Refinement spec A story in epic ALF-259 · Wiki Module (docs/specs/epics/ALF-259.html, the "Instapaper tag sync" follow-up). Written 2026-09-26. Built in ac3charland/knowledge, not in Alfred. Alfred only gets this spec's archive commit.

In short. Alex moves an Instapaper article into a To Wiki folder. A new step at the top of the wiki repo's existing kickoff workflow reads that folder and commits one source folder per article into inbox/: the article text as source.md, his highlights as excerpts-<date>.md, and the notes he wrote on them as notes-<date>.md. From there the batch goes through the ordinary lock, ingest session, and PR. Once the PR is merged and the article sits filed in raw/ on main, the same step moves it into his existing Reference folder. There is no state store: git plus the To Wiki folder decide every action, so each run is idempotent and a failed run leaves nothing half-done.

1 · Context & problem

Alex reads in Instapaper, highlights what matters, and writes notes on some highlights. Today getting that into the wiki is manual. For example, raw/2026/2026-09-25-the-acceleration-of-addictiveness/ was sent with npm run add -- --url … --quote "…" --quote "…", with each highlight retyped as a --quote, and the notes he wrote on them were lost. The ticket asks for this flow:

  1. Mark an article in Instapaper.
  2. The body, the highlights, and Alex's notes on the highlights land in the wiki inbox.
  3. The wiki ingests it as normal and opens a PR.
  4. (Optional, but wanted.) On merge, Instapaper shows it as done.

The epic already settled the shape: a new producer and no new architecture. The kickoff lock, filing by identity, and the ingest skill are all reused unchanged. It left three things for this refinement: where the poller runs, tags versus folders, and API access. All three are now settled with Alex (§2).

Why folders, not tags. Instapaper's Full API can list bookmarks by tag (bookmarks/list?tag=), but it has no call to add, remove, or change a tag on a bookmark that already exists. Tags can only be set when a URL is first added (bookmarks/add). Every client library surveyed says so (e.g. vburojevic/instapaper-cli: "no tag management API"). A "To Wiki" → "In Wiki" tag swap is therefore impossible through the documented API. Folders can be listed and moved (bookmarks/list?folder_id=, bookmarks/move), so the pipeline uses folders.

2 · Decisions

Tagged changes epic where this differs from the epic's follow-up sketch, and changes ticket where it differs from the ticket text. Alex chose D1–D3 in this refinement session.

D1Folders both ways: To Wiki in, Reference out changes ticketchanges epic

An article is sent by moving it into the Instapaper folder To Wiki, from Unread, from Archive, or from Reference (a folder Alex already has). Once it is filed in the wiki, the poller moves it into Reference. Both names are exact-match constants (SEND_FOLDER = 'To Wiki', DONE_FOLDER = 'Reference') in the command. A missing folder is a setup error, and the script never creates one.

Why: tags can't be changed through the API (callout above). Reusing Reference keeps a filed article where Alex already keeps finished reading, instead of adding a parallel "In Wiki" folder.

D2The poller is a step in the wiki repo's kickoff.yml, before Decide

A new npm run instapaper script in knowledge/scripts/ runs as kickoff's first real step. Kickoff's triggers become the poller's triggers:

  • the existing 3-hour cron (17 */3 * * *): new articles reach inbox/ within about 3 hours;
  • every push to main touching inbox/**, which includes every ingest-PR merge (it moves folders out of inbox/). So an article moves to Reference within minutes of the merge;
  • Run workflow (workflow_dispatch): "send now" from the GitHub app.

Anything it commits lands on main before Decide reads main's head, so the same run's lock includes it.

Why here: the producer's output is a wiki-repo contract, and the wiki repo already has everything the job needs: htmlToMarkdown (Readability + turndown), frontmatter serialization, the quote-id and hash rules, git write helpers, node --test, and lint. Alfred stays out entirely: no fifth Worker cron, no Worker port of the writer, no write token on the Worker. Riding kickoff's cron costs about zero extra Actions minutes. Why not a separate workflow: a push made with the Actions GITHUB_TOKEN doesn't trigger other workflows, so a standalone poller would have to dispatch kickoff anyway.

D3Credentials: the same four OAuth values Alfred's Reader send uses

Repo secrets on ac3charland/knowledge: INSTAPAPER_CONSUMER_KEY, INSTAPAPER_CONSUMER_SECRET, INSTAPAPER_ACCESS_TOKEN, INSTAPAPER_ACCESS_TOKEN_SECRET. These are the names and values that frontend/lib/instapaper/config.ts (ALF-238, merged) reads from Vercel. A Full API token is bound to the consumer key that issued it, so all four travel together. Alex already has a key and Premium. No password is ever stored, and this repo gets no token-exchange script. If a token is ever re-minted, Alfred's npm run instapaper:token -w frontend does it, and both places get the new pair.

D4Git is the state; the plan is a pure function changes epic

For each bookmark in To Wiki, the next action is computed from two inputs: the bookmark and its highlights, and what main already holds for that source across inbox/ and raw/. §4 is the whole table. Nothing is recorded anywhere else, so re-running is always safe.

Why it changes the epic: the epic sketched "change the tag once the commit lands". Alex wants the done-state to mean filed, not sent, so the move waits for the merge. That needs a way to know an article is in flight without sending it twice, and inbox/ on main is exactly that record.

D5Identity is the article's URL, not the bookmark id changes epic

Every file carries source_url = the bookmark's url and external_id: null, so the folder's identity is the canonical URL (canonicalUrl in scripts/lib/sources.ts). Only a bookmark with no http(s) URL (a private/emailed bookmark) uses external_id: "instapaper:<bookmark_id>" with source_url: null.

Why: articles Alex already sent by hand with npm run add (the Paul Graham one above) are keyed by URL. A bookmark-id identity would open a second raw/ folder for the same article instead of merging into it.

D6Highlights → excerpts, highlight notes → notes, paired by one id

  • Each highlight becomes one excerpts-<date>.md record, with id webQuoteId(text): the rule npm run add --quote already uses (q-<slug(text, ≤40)>-<sha256(text)[0..4]>). A highlight Alex once sent by hand gets the same id and is never sent twice.
  • A highlight's non-blank note becomes an entry in notes-<date>.md under the same id. This is the book importer's convention for commentary on a quote, which the ingest skill already reads, so the skill doesn't change.
  • Records are written in article order: highlight position, then time.

D7source.md comes from Instapaper's own text, sent once

The body is bookmarks/get_text's HTML converted by the wiki's existing htmlToMarkdown, at fidelity: full-text. That is the text Alex actually read and highlighted, so excerpts match it. source.md is sent only when no full-text source.md is on file for the identity. If Instapaper can't produce text, a pointer (empty body) goes instead when there's a URL and no source.md on file at all. Kickoff's fetch-pointers then tries the web.

Why "only once": get_text can differ between calls, and a second full-text source.md whose body differs from the filed one makes file-batch leave the whole folder (action: "left"). The kickoff Gate would then park it.

D8At most 10 articles sent per run

--limit defaults to 10. Bookmarks are handled oldest-first (bookmark time). Anything over the cap is deferred: it stays in To Wiki for the next run. Waits and moves don't count toward the cap.

Why: it bounds one run's Instapaper calls (1 folders list + 1 bookmarks list + ≤10 get_text + moves) under unpublished rate limits, and keeps one ingest batch reviewable if Alex drops a backlog into To Wiki.

3 · How it flows

Blue-bold is the only new component. Orange lines are Alex. The merge moves the batch out of inbox/, so it re-runs kickoff. On that pass, step ① finds the article filed and moves it to Reference (dashed).

4 · Per-bookmark plan (the state machine)

Each run evaluates every bookmark in To Wiki against main's tree after a fresh pull. For one bookmark, with identity per D5 and on file meaning every folder on main (inbox/ and raw/) that declares that identity, the rules below apply in order and the first match wins:

#ConditionActionInstapaper calls
1Some inbox/ folder on main declares the identity wait. It's in flight: waiting for a lock, in a batch, or in an open or closed-unmerged PR.none
2The unsent set (below) is non-empty and the run's send count is under the cap send one new inbox/ folder holding exactly the unsent filesget_text only if source.md is unsent
3Unsent set non-empty, cap reacheddefer. It stays in To Wiki.none
4Unsent set empty, identity is in raw/move to Referencebookmarks/move
5Unsent set empty, nothing on file (URL-less, no text, no highlights) skip with a warning. It stays in To Wiki for Alex to look at.none

The unsent set, computed against every file on file for the identity:

  • source.md when no full-text source.md is on file (D7). If get_text yields no text, the pointer form is sent only when there's a URL and no source.md is on file.
  • Each highlight whose webQuoteId(text) isn't a quotes id in any excerpts-*.md on file.
  • Each highlight note (trimmed, non-blank) whose id isn't an entries id on file, or whose shortHash(notesHashInput([note])) differs from the latest-dated on-file entry with that id. An edited note is resent. A deleted note or highlight is never propagated, because raw/ is frozen.

Consequence worth knowing: an article already filed by hand with the same highlights has an empty unsent set, so on its first run it is simply moved to Reference, with nothing sent.

5 · What lands in inbox/

One folder per sent bookmark, inbox/<captured>-<slug(title)>, named with folderName/uniqueFolderName against the names already in inbox/ and those this run already used. source_type: web-article (an existing registry row, so registry.yaml doesn't change), via: instapaper, and captured = today UTC. title, author, and published are computed once per send and shared by every file:

  • title: the bookmark's title, else htmlToMarkdown's title, else defaultTitle(url), else Untitled.
  • author / published: from htmlToMarkdown when get_text ran, else null (the bookmark carries neither).

An illustrative first send (hashes and ids made up; key order is serializeFile's):

---

origin: third-party

author: Jane Doe
source_url: https://example.com/why-habits-stick

external_id: null            # "instapaper:<bookmark_id>" only when there's no http(s) URL

---

<get_text HTML → htmlToMarkdown>

# inbox/2026-09-26-why-habits-stick/excerpts-2026-09-26.md
---
source_type: web-article
origin: third-party
title: Why Habits Stick
…same core…
fidelity: excerpt
quotes:
  - id: q-habits-are-the-compound-interest-of-3f2a     # webQuoteId(highlight.text)
    note: Habits are the compound interest of self-improvement.
    hash: 7c1e0a9b2d44                                  # shortHash(excerptHashInput(text, null, null))
---

## q-habits-are-the-compound-interest-of-3f2a

> Habits are the compound interest of self-improvement.

# inbox/2026-09-26-why-habits-stick/notes-2026-09-26.md   (only when some highlight has a note)
---
source_type: web-article
origin: mine
title: Why Habits Stick
…same core…
entries:
  - id: q-habits-are-the-compound-interest-of-3f2a     # same id as the highlight it comments on
    hash: 1b9d0e77c3a2                                  # shortHash(notesHashInput([note]))
---

## q-habits-are-the-compound-interest-of-3f2a

Same point as Four Thousand Weeks: small repeated choices.

Rules: a body line of a multi-line highlight is quoted line by line (> ), exactly as add-source does. A note body is written verbatim. notes-… is omitted when no unsent note exists, and excerpts-… when no unsent highlight exists. A resend holds only the unsent files and records. Two distinct highlights with identical text collapse to one record (same id), keeping the first by position.

6 · The Instapaper client

Two new library modules, each with an injectable fetch (the scripts/lib/github.ts pattern), so tests never touch the network:

  • scripts/lib/oauth1.ts: a port of Alfred's frontend/lib/instapaper/oauth.ts (OAuth 1.0a HMAC-SHA1 per RFC 5849: percentEncode, signatureBaseString, hmacSha1Signature, newSigningMoment, signRequest). That file already imports only node:crypto and uses only erasable TypeScript, so the port is a copy minus its import 'server-only' line, with a header comment naming where it came from. The repos can't share code, and copying the RFC-pinned signer is safer than writing a second one. Its RFC 5849 vectors come across too (§10).
  • scripts/lib/instapaper.ts: instapaperConfig(env) (the four D3 values, or null if any is blank) and an InstapaperClient implementing an InstapaperApi interface that tests fake.

Every call is a signed POST to https://www.instapaper.com with an application/x-www-form-urlencoded body and a 20 s abort:

MethodEndpointParamsUsed for
listFolders()/api/1.1/folders/list— Resolve To Wiki and Reference to folder_ids by exact title
listBookmarks(folderId)/api/1.1/bookmarks/listfolder_id, limit=500 The To Wiki bookmarks (bookmark_id, url, title, time) and their highlights (highlight_id, bookmark_id, text, note (nullable), position, time)
getText(bookmarkId)/api/1.1/bookmarks/get_textbookmark_id The article HTML, or null when Instapaper can't generate text (error 1550)
move(bookmarkId, folderId)/api/1.1/bookmarks/movebookmark_id, folder_id To Wiki → Reference

Instapaper answers with a JSON array of typed objects ({"type":"error","error_code":…} among them). Read it the way Alfred's readAnswer in frontend/lib/instapaper/bookmark.ts does, codes included. Failures are typed, and no message ever includes a header, a body, or a secret:

Instapaper answerKindThe run
401/403, or error 1042 (app suspended)credentialsstops before writing anything; exit 1
error 1040 (rate limit)rate-limitedstops; whatever was already pushed stands; the next run resumes; exit 1
error 1041 (Premium required)premiumstops; exit 1
error 1550 on get_text—not an error: getText returns null (D7's pointer path)
any other error, a non-2xx, a network failure or timeout, or a body that isn't JSON (the docs say to treat it as a 503) unavailablestops; exit 1
Confirm the shapes against the docs first. This session couldn't reach instapaper.com (the cloud network policy blocks it). The error handling above comes from Alfred's working client, whose refiner read the docs. The four endpoints, their /api/1.1/ prefix, and the list response carrying highlights inline come from three client libraries (stve/instapaper, ieroNo47/gopaper, vburojevic/instapaper-cli). Alfred's own bookmarks/add call uses /api/1/. Before coding, read instapaper.com/developers/v1/full-api/ the way docs/specs/archive/ALF-238.html §6 describes: the pages are rendered client-side, and their markdown lives at /assets/<page>-<hash>.md. Take each endpoint's prefix from there. If bookmarks/list turns out not to return highlights, use /api/1.1/bookmarks/<id>/highlights per bookmark. If the implementing session can't reach the docs either, build to this table. Alex's --dry-run (§12) is the live check, and a mismatch there is a parser fix. GitHub's Actions runners have open egress, so production isn't affected.

7 · The instapaper command

npm run instapaper -- [--dry-run] [--limit <n>]      # package.json: "instapaper": "node scripts/instapaper.ts"
  1. Not configured (any D3 value blank) → print ::warning::instapaper is not configured and exit 0.
  2. prepareMainForWrite() (clean tree, on main, pull --rebase). This is skipped for --dry-run, which reads the working tree as-is.
  3. listFolders → both folder ids. If either is missing, print instapaper: no "<name>" folder and exit 1.
  4. listBookmarks(To Wiki); group highlights by bookmark_id; order bookmarks oldest-first.
  5. Scan main's sources (scanSources + foldersWithIdentity) and run the pure planBookmark (§4) for each bookmark. Call getText only for sends whose unsent set includes source.md.
  6. --dry-run: print the plan and exit 0. No files, commits, or moves.
  7. Write every send's folder; commitAndPushMain(['inbox'], msg) with msg = instapaper: <title> for one folder, instapaper: <n> sources for several. If the push is rejected (another producer pushed in between), reset to the pre-write commit, pull, and re-plan from step 5 (the Instapaper reads are reused), up to 3 attempts in total. It never rebases this run's folders onto someone else's, because the other writer may have created the same folder name.
  8. Only after the push succeeds (or when nothing was sent): perform every move. A failed move is reported and the rest continue, unless it's rate-limited or unauthorized, which stops the run. Every unmoved article is retried next run by rule 4.
  9. Print one line per bookmark, and append a summary line to $GITHUB_STEP_SUMMARY when set. Exit 1 if any step failed, else 0.
instapaper: send "Why Habits Stick" → inbox/2026-09-26-why-habits-stick (source.md, 3 excerpts, 1 note)
instapaper: wait "The Tail End" (in flight: inbox/2026-09-25-the-tail-end)
instapaper: move "Do Things That Don't Scale" → Reference
instapaper: defer "Some Other Article" (over the 10-per-run limit)
instapaper: skip "Private note 812" (no URL, no text, no highlights)
instapaper: sent 1, moved 1, waiting 1, deferred 1, skipped 1

Structure: planBookmark, the unsent-set computation, and the folder builder are exported pure functions. main(argv, ctx) takes { root, env, api, now } the way add-source's and kickoff's mains take their context, so the end-to-end tests drive it against a temp repo and a fake API. webQuoteId moves from scripts/add-source.ts into scripts/lib/obsidian.ts beside quoteId, exported, and both scripts import it, so the two producers can't drift.

8 · Kickoff wiring

One new step in .github/workflows/kickoff.yml, right after npm ci and before Decide. Nothing else in kickoff changes.

      - name: Send from Instapaper
        # Before Decide, so anything sent joins this run's batch. Its failure never blocks
        # ingest: the step shows red and kickoff carries on. Pushes with GITHUB_TOKEN don't
        # trigger workflows, so this commit doesn't start a second kickoff; Decide reads
        # main's new head over the API instead.
        continue-on-error: true
        timeout-minutes: 10
        env:
          INSTAPAPER_CONSUMER_KEY: ${{ secrets.INSTAPAPER_CONSUMER_KEY }}
          INSTAPAPER_CONSUMER_SECRET: ${{ secrets.INSTAPAPER_CONSUMER_SECRET }}
          INSTAPAPER_ACCESS_TOKEN: ${{ secrets.INSTAPAPER_ACCESS_TOKEN }}
          INSTAPAPER_ACCESS_TOKEN_SECRET: ${{ secrets.INSTAPAPER_ACCESS_TOKEN_SECRET }}
        run: |
          git config user.name "github-actions[bot]"
          git config user.email "github-actions[bot]@users.noreply.github.com"
          npm run instapaper
  • Kickoff already has contents: write, fetch-depth: 0, and a checkout of main for all three triggers, and main is unprotected (README setup checklist). Implementer: confirm actions/checkout leaves a local main branch (not a detached HEAD) for push, schedule, and dispatch, because prepareMainForWrite requires it. If it doesn't, add git checkout main to the step.
  • The step is independent of the Routine secrets: with Instapaper configured and the Routine not, it still sends, and Decide then logs "not configured" as today.
  • check.yml doesn't run on this bot push (GITHUB_TOKEN again). That is why the tests (§10) run lint and file-batch --dry-run over the produced folders. The ingest PR's check covers them later.

12 · Setup checklist (Alex)

Not agent work. It goes into the knowledge README's setup checklist.

  1. In Instapaper, create a folder named exactly To Wiki. Reference already exists.
  2. Add the four D3 secrets to ac3charland/knowledge (Settings → Secrets and variables → Actions), using the same values as Alfred's Vercel env (frontend/lib/instapaper/config.ts).
  3. Dry run on the Mac, from the clone on a clean main, with the four values exported and one highlighted, noted article in To Wiki: npm run instapaper -- --dry-run. Expect one send line with the right highlight and note counts. This is the live check of §6's shapes.
  4. Smoke test: Actions → kickoff → Run workflow. Check for an instapaper: … commit on main, then the lock, then the ingest PR. In the PR, check the source page quotes the highlights as the author's words and the notes as Alex's. Merge, and within minutes the article is in Reference.
  5. Resend test: add one highlight to that article and move it back to To Wiki. The next run sends a folder with only that excerpt, and after that PR merges the article returns to Reference.

13 · Acceptance criteria

  • An article in To Wiki with no identity on file is committed to inbox/ on main as one folder: source.md (full-text from get_text, else a pointer when it has a URL), excerpts-<date>.md (one record per highlight, webQuoteId ids, article order), and notes-<date>.md (one entry per non-blank note, same id as its highlight). All files carry source_type: web-article and via: instapaper, and identity per D5.
  • The folder passes npm run lint and files as new (first send) or merged (resend), never left.
  • An article whose identity is in inbox/ on main is neither resent nor moved.
  • An article filed in raw/ with nothing unsent is moved to Reference, with no Instapaper calls beyond the list and the move.
  • A resend holds only the unsent files and records. A full-text source.md is never sent twice.
  • At most --limit (default 10) articles are sent per run, oldest first. The rest are deferred.
  • Moves happen only after this run's push succeeded (or when it sent nothing). A rejected push re-plans against the new main, up to 3 attempts, and commits this run's folders exactly once.
  • --dry-run prints the plan and changes nothing locally, on the remote, or in Instapaper.
  • Unconfigured → warning plus exit 0. A missing folder, auth failure, rate limit, or network failure → a clear message plus exit 1, with nothing half-written. No output contains a credential.
  • kickoff.yml runs the step before Decide with continue-on-error: true, and the same run's lock includes anything it sent.
  • add-source uses the shared webQuoteId, and its tests are unchanged and green. npm run check is green.
  • The README documents the command, the step, the setup items, and the "stays in To Wiki" troubleshooting entry.
  • This spec is archived in Alfred by a PR carrying the phase: implementation block.

14 · Out of scope & open questions

Deliberately out

  • Tags. Not read and not written (D1).
  • Bulk backlog import. The epic's open "batching Instapaper" question stays open. This ships the per-article flow, and D8's cap is its only throttle. A later --file-only (marking sends ingest: file-only) would be the natural valve for "move the whole backlog into To Wiki".
  • Propagating deletions or edits of highlights after filing. raw/ is frozen, and only edited notes are resent (as a later-dated entry that wins).
  • The bookmark's description. It's the page's own summary, not Alex's words, so it isn't sent.
  • Anything in Alfred's UI. No status of Instapaper sends appears in Alfred.
  • An article sent both as a Reader pick and through Instapaper becomes two raw/ folders, because a Reader send's identity is alfred:reader-post:<id>. This is rare, and the ingest session sees both. Unifying identities is a separate decision.

Genuinely open (for the implementer to confirm, not to decide)

  • Whether bookmarks/list returns highlights inline. §6 names the fallback.
  • Instapaper's rate-limit numbers aren't published. D8 keeps a run to about a dozen calls. If 1040s ever appear in kickoff logs, lower the cap.
