ALF-268 — Unify PR ratio repos with actual projects in code module to synchronize name, color, etc.

Make the Code module's projects table the only list of measured repos. Both Dashboard widgets then measure exactly the project repos. On the PR-ratio card, each project's segment and dot use that project's own name and color, and its legend entry opens the project's board.

In one paragraph. Today the PR ratio and the lines-changed chart measure the repos listed in the PR_RATIO_REPOS env var, labelled by the var's :Label suffix and colored teal → blue → amber → green in env order. The rest of the Code module colors each project blue → amber → green → red → teal by creation order. The same repo can therefore show a different name and a different color on one screen. This change retires PR_RATIO_REPOS. Both routes read the repo set from projects (oldest first). Each ratio label is the project's name, and the card colors every segment with projectColorFor, the same rule that colors ProjectNav, the Backlog and the task chips. Each project's legend row also becomes a link to /code/<projectId>. The API response keeps its shape.

1 · Context & problem

The Dashboard (components/code/dashboard.tsx) shows two GitHub-derived ornaments above the queue digests: LocVelocity and PrRatio. Both get their repos from getGithubRepoConfig() in frontend/lib/github/config.ts, which parses PR_RATIO_REPOS (owner/name:Label,…). The header comment there says this was on purpose:

// config.ts, today
 * The measured repos are env-configured rather than read from the `projects` table on
 * purpose: not every repo the owner ships to runs through the Software Factory, and adding
 * one as a project row would surface it in every project nav, board and epic picker in the
 * Code module.

The drawback is two lists that describe the same repos and don't know about each other:

PR_RATIO_REPOS → PR ratio cardprojects → ProjectNav, Backlog, boards, task chips
Namethe :Label suffix, else the repo nameprojects.name
ColorTONES[index % 4] = teal, blue, amber, green by env order (pr-ratio.tsx)projectColorFor = blue, amber, green, red, teal by creation order (lib/code/project-color.ts)
Membershipedited in Vercel, needs a redeploycreated in the app (New Project dialog / inbox dispatch)

So on one screen, Alfred can show amber with an ALF pill in the sidebar and blue in the ratio bar just beside it (see the mockup). Adding a project doesn't add it to the ratio, and a renamed :Label doesn't match the project name. The ticket asks for one list.

2 · Decisions taken with the owner up front

QuestionDecisionConsequence
Where does the measured repo set come from? Projects only. Every row in projects is one measured repo. PR_RATIO_REPOS is deleted. This reverses the documented config.ts decision. A repo you ship to that isn't a project counts only toward Other, and only when PR_RATIO_AUTHORS is set.
Does the lines-changed chart follow the same set? Yes. Both widgets keep sharing one config. Both Dashboard measurements keep covering the same repos, as they do today.
How is a project's color decided? The existing rule: projectColorFor(projects, id), by creation order. No schema change. Colors reshuffle when a project is created or deleted, as they already do in ProjectNav and the Backlog.
What else ("etc.") is shared? Legend links to the project. Each project's legend row opens its board. Not chosen: matching ProjectNav's order, a key pill in the legend, and adding key/color to the API. See Out of scope.

Bar order follows from the color decision rather than being a new choice. Segments run left to right in project creation order, the same order projectColorFor indexes, so the bar always reads blue, amber, green, red, teal. This is not ProjectNav's order, which ranks projects by their best Backlog priority (useRankedProjects). It keeps the bar stable week to week while the ranking moves.

3 · Proposed change

3.1 Where names and colors come from, before and after

3.2 Server: the repo set comes from projects

lib/github/config.ts stops reading repos from env. It becomes a pure function of env (token, authors) plus the project rows it is given, so it stays DB-free and unit-testable. The REPO_ENTRY regex, parseRepo and every mention of PR_RATIO_REPOS are removed. RatioRepo keeps its shape, so pr-ratio.ts and loc.ts need no logic change.

/** The project columns a measurement needs, in the order the caller read them. */
export type MeasuredProject = Pick<Project, 'name' | 'repo_owner' | 'repo_name'>;

/** Token + ≥ 1 project, else undefined. Never throws. Repos keep the given order. */
export function getGithubRepoConfig(projects: readonly MeasuredProject[]): GithubRepoConfig | undefined {
  const token = envValue(process.env.GITHUB_TOKEN);
  if (token === undefined || projects.length < MINIMUM_REPOS) return undefined;
  const repos = projects.map((p) => ({ owner: p.repo_owner, name: p.repo_name, label: p.name }));
  return { repos, authors: splitList(envValue(process.env.PR_RATIO_AUTHORS)), token };
}

/** Same config under the ratio's stricter minimum (≥ 2 projects), unchanged in meaning. */
export function getPrRatioConfig(projects: readonly MeasuredProject[]): PrRatioConfig | undefined

Rewrite the header comment. The measured set is now the project set by definition; say that a repo which isn't a project lands in Other (when PR_RATIO_AUTHORS anchors it) and that GITHUB_TOKEN must be able to read every project's repo. Keep the note that PR_RATIO_AUTHORS under-describes its scope but isn't renamed.

A reader that takes the resolved client is added to lib/data/code.ts next to getProjectList. That file's readers build their own cookie client, which an API-key caller doesn't have, so this one takes the client as a parameter:

/** Every project's repo, oldest first: the order `projectColorFor` indexes, so bar order = color order. */
export async function listProjectRepos(supabase: SupabaseClient<Database>) {
  return supabase
    .from('projects')
    .select('name, repo_owner, repo_name')
    .order('created_at', { ascending: true });
}

Both routes switch from withSessionOrApiKey to resolveIngestClient, the way /api/habits does: a valid ingest key gets the admin client and a browser session gets its own RLS client. The API-key contract doesn't change for callers. Sketch for the ratio route (loc-velocity mirrors it with getGithubRepoConfig and no query params):

export async function GET(request: Request): Promise<Response> {

  if (client instanceof Response) return client;               // 401, as before

  const query = parseQueryParams(request, prRatioQuerySchema);

    const { status, message } = mapSupabaseError(error);       // NOT 501: the card must not go silent
    return jsonError(status, message);
  }

  const config = getPrRatioConfig(projects);
  if (!config) return jsonError(501, 'PR ratio is not configured');
  // …unchanged: rollingWeekWindow → fetchPrRatio → 502 | 200
}

3.4 Client: the card takes color and link from the project

lib/code/project-color.ts gains a solid-fill class map for the bar segment and legend dot. The existing badge, text and chip maps are all translucent or text-only. Write the strings out in full, as the file's own comment requires, so the Tailwind v4 scanner keeps them:

const PROJECT_FILL_CLASS: Record<ProjectColor, string> = {
  blue: 'bg-accent-blue',
  amber: 'bg-accent-amber',
  green: 'bg-accent-green',
  red: 'bg-accent-red',
  teal: 'bg-accent-teal',
};

/** Solid fill for a project's ratio-bar segment and legend dot. */
export function projectFillClasses(color: ProjectColor): string { return PROJECT_FILL_CLASS[color]; }

components/code/pr-ratio.tsx drops TONES/toneFor. It reads useProjects(); the Dashboard already mounts it under CodeProvider, and QueueWidget does the same. toEntries joins each response entry to its project by owner/name. This lookup can't collide: projects has unique (repo_owner, repo_name), and the server builds repo from those same columns, so the strings match exactly with no case folding.

function toEntries(ratio: PrRatioResponse, projects: Project[]): RatioEntry[] {
  const byRepo = new Map(projects.map((p) => [`${p.repo_owner}/${p.repo_name}`, p]));

  const entries: RatioEntry[] = ratio.repos.map((repo) => {
    const project = byRepo.get(repo.repo);
    return {
      key: repo.repo,
      label: repo.label,                                            // = project.name, server-side
      count: repo.count,
      percentage: repo.percentage,
      tone: projectFillClasses(projectColorFor(projects, project?.id ?? null)),
      href: project ? projectBoardHref(project.id) : undefined,
    };
  });
  // Other: unchanged — OTHER_TONE (bg-muted-foreground), dropped at zero, href undefined.
  return entries;
}
  • Legend rows with an href render their contents (dot, name, percent, count) inside a ViewLink to /code/<projectId>. It is a real <a href>, so a plain click navigates client-side and a modified click opens a new tab, as on the Dashboard's digest panes. Classes: group flex items-center gap-2 rounded-sm focus:outline-none focus-visible:ring-2 focus-visible:ring-accent-blue focus-visible:ring-offset-1 focus-visible:ring-offset-background. The label span adds group-hover:underline, the hover cue QueueWidget's header uses. The <li> and its layout are unchanged.
  • The Other row stays plain text. It isn't one place, so it has nowhere to link.
  • The bar is not interactive. RatioBar is unchanged: presentation only, one role="img" with its label.
  • Unmatched entry (a project created on another device after this page seeded its store): no link, and the color falls back to projectColorFor's documented default for an unknown id (blue). This is rare, and it fixes itself on the next full load. It's handled only so the card can't crash or show a dead link.
  • Accessible label (describeSplit), zero-total, loading, error and unconfigured states: unchanged.

4 · Consequences & deploy notes

Projects-only makes the project list a measurement setting too. Read these before merging.
  • The PAT must cover every project's repo. If a project's repo is private and GITHUB_TOKEN can't read it, that repo's search or stats call fails. The existing "a partial ratio is a wrong ratio" rule then turns both Dashboard cards into their error note until the PAT's repository list is widened. The README must say so next to GITHUB_TOKEN. Degrading per repo instead is out of scope.
  • Check the current PR_RATIO_REPOS before deploying. Any repo in it that isn't a project leaves its own segment. It moves into Other when PR_RATIO_AUTHORS is set and drops out of the bar when it isn't. If that repo should keep its own segment, create it as a project first.
  • Labels change. Env labels (e.g. RealPlay) are replaced by projects.name. Project names can't be edited (PATCH /api/projects/[id] accepts only description), so a label that reads badly stays that way until renaming projects becomes its own feature.
  • After deploying, delete PR_RATIO_REPOS from the Vercel project. Nothing reads it, so leaving it breaks nothing but misleads the next person who reads the env list.

8 · Out of scope

  • A stored per-project color or a color picker. The owner chose the existing creation-order rule.
  • Matching the bar to ProjectNav's order. Not chosen; the bar uses creation order (§2).
  • A key pill in the legend and adding key/color/projectId to the API. Not chosen.
  • Clickable bar segments. Only the legend links.
  • Excluding a project from measurement (e.g. a measured flag), or measuring a non-project repo as its own segment. With projects as the only source, neither exists.
  • Degrading per repo when the PAT can't read one project's repo, and checking PAT coverage in the New Project flow (§4).
  • A ratio for a one-project deployment (one project vs Other). The ≥ 2-repo minimum stays as it is.
  • Renaming PR_RATIO_AUTHORS / GITHUB_TOKEN, or renaming projects.

10 · Acceptance criteria

  • Nothing in frontend/ reads PR_RATIO_REPOS. It is gone from env.d.ts, config.ts, the README and the stories.
  • GET /api/code/pr-ratio measures exactly the repos in projects, in created_at ascending order, with label = the project's name and repo = repo_owner/repo_name. The response shape is unchanged.
  • GET /api/code/loc-velocity measures the same project repos, and its repos lists them in the same order.
  • Both routes accept a browser session or the ingest API key (401 with neither). The key path reads projects with the admin client.
  • 501 when GITHUB_TOKEN is unset, or with fewer than 2 projects (ratio) / 0 projects (velocity). A failed projects read returns a mapped error status, never 501.
  • The Other bucket, when PR_RATIO_AUTHORS is set, excludes every project's repo.
  • Each project's bar segment and legend dot use the same color projectColorFor gives that project in ProjectNav, via projectFillClasses. TONES is gone.
  • Each project's legend row is a link to /code/<projectId>. A plain click opens that board client-side; hover underlines the name; keyboard focus shows the blue focus ring.
  • The Other row is unchanged: muted tone, last, dropped at zero, not a link.
  • A response entry with no matching project in the store renders unlinked in the blue fallback and doesn't throw.
  • A project with zero merged PRs is still listed. The loading, zero-total, error and unconfigured states behave as before.
  • withSessionOrApiKey and its tests are removed, and no comment still names it.
  • The moved code-prratio--* baselines are regenerated through the approve flow, and the stories render inside CodeProvider.
  • The README documents that GITHUB_TOKEN must read every project's repo. The productivity-coach primer describes the repos as the Code module's projects.
  • A demo doc captures the change per the showboat skill, and npm run check is green.
