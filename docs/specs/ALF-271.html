ALF-271 — Be able to send Evidence bullet points to Wiki from Reader along with novel ideas

Written 2026-09-27. Builds on ALF-261 (Day 2 wiki setup, archived at docs/specs/archive/ALF-261.html), which made a post's Novel ideas a checklist that sends picked bullets into the wiki. Background: the Reader epic docs/specs/epics/ALF-232.html and the wiki epic docs/specs/epics/ALF-259.html.

In short. A post's Evidence section becomes a checklist like Novel ideas. Both sections share one selection: Alex can tick ideas and evidence together, and one Send to wiki press sends all of them as one commit. Each section heading has its own Send all to wiki, which sends only that section.

In the wiki, the send is still one picks-<date>.md file. Its body now has ## Novel ideas and ## Evidence headings, so ingest can tell a claim from its support. Sent evidence is recorded in its own column, wiki_sent_evidence. The Work instance, which has no wiki writer, stays exactly as it is today.

1 · Context & problem

The Reader summarises each newsletter into a gist plus a four-section overview: Novel ideas, Evidence, The argument, and Who should read it. ALF-232 D6 stored the first two as string arrays so a future knowledge base could index them. ALF-261 then built the path into the wiki, but only for Novel ideas. Evidence is still a plain list that nothing can send.

That leaves a gap. A claim without its support is the weaker half of what the post offered. When the ingest session writes a wiki page from a picked idea, the most useful thing to have beside it is the evidence the post gave for it: the study, the number, the example. Today Alex has to leave that behind or retype it.

2 · Decisions

D1 · One selection covers both sections, with one bar, one send and one commit Alex

Novel ideas and Evidence are both checklists over one selection. Ticks in either section add to it. A single selection bar sits under the last checklist section, and its Send to wiki sends every ticked bullet from both sections in one request. That request makes one folder, one commit and one kickoff.

Why: the reason for ALF-261 D12 still holds. A post's picks should reach the ingest session together. Evidence is support for a claim. If it went in a separate commit, it could land in a different ingest batch from the idea it supports, and the session would write about one without the other.

D2 · Send all stays per section Alex

Novel ideas' Send all to wiki does not change. Evidence's heading row gets its own button, which sends every unsent evidence bullet and nothing else. A section's Send all clears only that section's ticks, so ideas ticked while Evidence's Send all runs stay ticked.

Why: a button next to a list should send that list. Accepted cost: sending every bullet in the post takes two presses and makes two commits. Ticking everything and then pressing Send to wiki is still the one-commit way to do it.

D3 · Each send is still one picks file, now with headed sections Alex

A send still writes one picks-<captured>.md with origin: "model-derived", under the same registry row. The body changes:

  • The ideas in the send go under ## Novel ideas, and the evidence under ## Evidence.
  • A section with no bullets in this send is left out.
  • Every send has headings, including one with only ideas. That is a change from today's bare list.

Why: the summariser writes evidence bullets just as it writes ideas. They have the same provenance, so they belong in the same file kind, and ac3charland/knowledge needs no registry change. The headings let ingest tell a claim from its support. Always adding headings means every future picks file has one shape.

Unverified: nothing in this repo says whether the wiki's lint accepts headings in a picks body. The build's contract check (§8) is the gate. If the lint rejects them, the build stops and raises it (§11). It does not fall back to a flat list.

D4 · Sent evidence gets its own text-keyed column, and one RPC marks both lists atomically new

  • New column reader_posts.wiki_sent_evidence text[] not null default '{}'. It follows ALF-261 D8's rule: a bullet shows as sent when its exact text is in the array, and a reworded bullet reads as unsent.
  • New RPC append_wiki_sent_picks(p_post uuid, p_ideas text[], p_evidence text[]). It is one UPDATE that appends to both columns, with append_wiki_sent_ideas's rules for each: add only strings not already present, collapse duplicates, and keep first-occurrence order.
  • append_wiki_sent_ideas stays, because migrations here are expand-then-contract (supabase skill). The code still running during the deploy calls it. A later migration can drop it.

Why a separate column, not wiki_sent_ideas: an idea and an evidence bullet with the same text would mark each other as sent, and the column's name would no longer be true. Why one RPC: with two calls, a failure between them would leave half a send marked.

D5 · The route accepts both lists and still accepts today's body new

The body becomes { ideas?: string[]; evidence?: string[] }, with .strict(). Each list holds at most 6 non-blank strings, and the request must name at least one bullet overall. A tab still running today's bundle posts { ideas }, and that keeps working through the deploy.

D6 · A blank evidence bullet is treated as no bullet, in both views new

ALF-261's follow-up already does this for ideas. isIdea is renamed isBullet, since it now covers both sections. A blank evidence bullet is dropped from the checklist and from the plain list. An evidence list containing only blanks shows the empty line, "None — the post rests on assertion alone."

Why: the checklist needs it, because the route refuses a blank string and a drawn blank would make every Send all fail. The plain view gets the same rule so the two views never disagree.

4 · Behaviour

  • When a section is a checklist. Each of Novel ideas and Evidence is a checklist when writable is true and it has at least one non-blank bullet. Each section decides this on its own. With neither a checklist, the overview is exactly today's. The same rules apply wherever PostOverview renders, in the reading list and in the archive.
  • Evidence rows copy idea rows exactly. Each row has role="checkbox" and aria-checked, and the whole row is the hit target. Space toggles it; Enter does nothing. The tick box is 24 px on a phone and 16 px from md. A sent row can't be selected.
  • One selection. The selection is a set of (section, text) pairs, held in the overview's own useState. Collapsing the overview drops it. A bullet repeated within a section counts as one pick. The same text in both sections counts as two.
  • The bar reveals through AnimatedHeightCollapse (reduced motion honoured) under the last checklist section once anything is ticked. It keeps role="group", with its label changed from "Selected ideas" to "Selected bullets". The counter counts ticks in both sections. Send to wiki sends every ticked bullet in overview order, ideas first and then evidence. Clear unticks both sections.
  • Send all sends its own section's unsent bullets, whatever else is ticked. When it succeeds it clears its own section's ticks only. The heading row is 32 px tall only while that section's controls render.
  • In flight. A post can have only one send at a time (the store's wikiSendsInFlight, as today). While one runs, every tick box, both Send all buttons, Send to wiki and Clear are disabled. The pressed button shows the 14 px spinner and reads "Sending…". Sends are not optimistic.
  • Success. The sent bullets in both sections flip to their sent state. After a bar send, the selection empties and the bar folds away. If focus was lost, it moves to the first unsent tick row in either section, or to the heading row of the first checklist section if none is left. Focus Alex moved elsewhere stays where it is (today's rule).
  • Failure. A toast shows the route's own sentence, or "Couldn't send to the wiki" if it has none. Every tick stays as it was, so retrying takes one press.
  • No hotkey, as today.

5 · Data flow & contracts

5.1 Route · POST /api/reader/posts/[id]/wiki

This is the ALF-261 route, extended. Its checks run in this order:

  1. The writer isn't configured: 501, unchanged.
  2. The id doesn't parse, or the body fails sendReaderPicksSchema: 400. The schema is { ideas?: string[]; evidence?: string[] } with .strict(). Each list is 0–6 strings, each rejected when blank using the refine (not .trim()) as today, and a refine requires at least one bullet across the two lists.
  3. The post is unknown: 404. getReaderPostForWiki now also selects wiki_sent_evidence.
  4. An idea isn't in overview.novel_ideas: 409 with the existing sentence, "That idea isn't in this post's overview any more". This is checked first.
  5. An evidence bullet isn't in overview.evidence: 409, "That evidence isn't in this post's overview any more".
  6. Compute the fresh ideas (the request's ideas, deduplicated, minus wiki_sent_ideas) and the fresh evidence (the same, minus wiki_sent_evidence). If both are empty: 200 with the list row unchanged, and no commit.
  7. commitEnvelopes(config, [readerEnvelope(post, { ideas: freshIdeas, evidence: freshEvidence }, today)]). Writer errors map through wikiWriteErrorResponse, unchanged.
  8. appendWikiSentPicks. If it fails, answer 500, "Sent to the wiki, but couldn't mark the bullets as sent" (the word "ideas" becomes "bullets").
  9. 200 with the saved row through READER_POST_LIST_COLUMNS. text never reaches the client.

5.3 Migration · database/migrations/<next>_reader_wiki_evidence.sql

Use the next free number at build time. Don't pin one here.

-- Which Evidence bullets a post has sent — the exact text, as wiki_sent_ideas (0038) does for ideas.
alter table reader_posts add column wiki_sent_evidence text[] not null default '{}';
comment on column reader_posts.wiki_sent_evidence is '…';

-- One atomic append to both lists. Each array gets 0038's rules: only strings not already present,
-- duplicates collapsed, first-occurrence order (unnest … with ordinality / group by / order by min(ord)).
-- The subqueries read the row's pre-update arrays, so each list is checked against itself.
create or replace function append_wiki_sent_picks(p_post uuid, p_ideas text[], p_evidence text[])
returns setof reader_posts
language sql security invoker as $$
  update reader_posts
     set wiki_sent_ideas    = wiki_sent_ideas    || array(… p_ideas    … not (i = any(reader_posts.wiki_sent_ideas))    …),
         wiki_sent_evidence = wiki_sent_evidence || array(… p_evidence … not (i = any(reader_posts.wiki_sent_evidence)) …)
   where id = p_post
  returning *;
$$;
grant execute on function append_wiki_sent_picks(uuid, text[], text[]) to anon, authenticated, service_role;

A { ideas }-only body still commits exactly as today, apart from the heading.

  • Store. sendPicksToWiki sends both lists. It replaces the row with the server's on success, toasts the evidence 409's sentence, rethrows on failure, and refuses a second send while one is in flight.

10 · Acceptance criteria

  • Reader
  • With the wiki connected, a post's Evidence bullets form a checklist that looks and behaves like the Novel-ideas checklist, as frames A–F draw it.
  • Ticks in both sections form one selection. A single bar under the last checklist section counts them, and Send to wiki sends them all in one request and one commit.
  • Each section's Send all sends only that section's unsent bullets and clears only that section's ticks. A fully sent section reads "All sent to wiki".
  • While a send is in flight, every control in both sections is disabled. A failed send toasts and keeps every tick. Sent marks for both sections survive a reload, and concurrent sends never lose a mark.
  • A post with evidence but no novel ideas sends evidence alone (frame F). A reworded evidence bullet reads as unsent. A blank evidence bullet is drawn in neither view.
  • With the wiki not connected, the overview is pixel-identical to today (frame G; WikiNotConnected baseline unmoved).
  • Route & data
  • POST /api/reader/posts/[id]/wiki accepts { ideas?, evidence? }, still accepts today's { ideas }, answers 409 for a stale bullet in either list, and commits nothing when nothing is fresh.
  • reader_posts.wiki_sent_evidence exists, and append_wiki_sent_picks marks both lists in one atomic update. append_wiki_sent_ideas still exists. text never reaches the client.
  • Wiki
  • A send writes one picks-<date>.md whose body is headed ## Novel ideas and/or ## Evidence (§6), next to ALF-261's unchanged source.md.
  • The golden folders pass the wiki's own lint and file as new under file-batch --dry-run. If that couldn't be run, the PR says so.
  • Process
  • npm run check is green on the final tree, there is a demo doc (§9), and this spec is archived in the implementation PR.

After merge (Alex, not agent work)

  • From a real post, tick one idea and one evidence bullet and send them. Check that one folder appears in the wiki's inbox/ with a headed picks file, and that kickoff runs once.
  • Read the resulting ingest PR and check that it used the evidence as support for the idea, rather than as a free-standing claim. If it didn't, the fix is a line in the wiki repo's ingest skill (§11).

11 · Out of scope, risks & open questions

Deliberately out

  • Sending The argument or Who should read it. They are prose paragraphs, not bullets, and the epic stored them as such.
  • Linking each evidence bullet to the idea it supports. That is a prompt and schema change (a new READER_PROMPT_VERSION, with Worker edits) and would be its own story (see Risks).
  • Any edit to ac3charland/knowledge, whether its ingest skill or its registry. D3 needs neither, provided the contract check passes.
  • A single Send all for both sections (D2), a sticky selection bar, and hotkeys.
  • Dropping append_wiki_sent_ideas. That is a later contract-step migration once nothing calls it.

Risks

  • Evidence bullets aren't always self-contained. The prompt doesn't tie evidence to ideas, and some bullets only make sense next to their claim. For example, "An internal replication the author ran, n=1, flagged as such" doesn't say what was replicated. Two things soften this. source.md goes with every send, and the ## Evidence heading tells ingest these bullets are support. If ingest PRs still mishandle them, the lasting fix is to link evidence to ideas in the prompt, which is out of scope above.
  • The wiki's lint may reject a headed picks body. Nothing readable from this repo says either way. The contract check is the gate, and the fallback is a wiki-side change, not a flat list.
  • On a phone, the bar can sit below the fold. With six ideas and six evidence bullets, ticking the first idea shows a bar several screens down. The filled tick box is the immediate feedback. A sticky bar is the follow-up if this becomes a problem.
  • Deploy order. Vercel can go live a moment before the migration applies. During that gap, the list columns name a missing column, and the seed read returns an empty list. This is the same short window every additive list-column migration has had, including ALF-261's wiki_sent_ideas.

Open questions

None block the build. Alex made the two scoping calls in this session: D1 and D2 (one selection, per-section Send all) and D3 (one headed picks file). Everything else is decided above, and a reviewer can overturn any of it in PR comments.
