Refinement spec · a story in epic ALF-232 (Reader Module)

ALF-272 — Implement a “To Reader” folder pipeline in Instapaper à la “To Wiki”

Written 2026-09-28. Epic background: docs/specs/epics/ALF-232.html and its build notes docs/specs/epics/ALF-232-notes.md. Sibling pipeline: docs/specs/archive/ALF-263.html (To Wiki, built in ac3charland/knowledge). Built in alfred: the Worker, one migration, the Send route, and the Reader row and header.

In short. The owner moves an Instapaper article into a folder named To Reader. Within five minutes, the Reader's existing Worker tick lists that folder, takes the article's text from Instapaper, stores it as a reader_posts row, archives the bookmark in Instapaper, and summarises it with the same summariser, prompt, model and daily ceiling as a newsletter. In the reading list it is an ordinary row: the site's host as the eyebrow, and via Instapaper in the meta line. Send to Instapaper on that row moves the bookmark back to the top of Unread instead of saving a copy. Archive makes no Instapaper call. The owner chose both of those behaviours in this session, along with sharing the 30-a-day ceiling.

1 · Context & problem

The Reader summarises every newsletter that reaches the personal Gmail inbox. For each one it writes a gist that answers "should I read this?" and a one-page overview, and puts it in a list the owner skims. Anything the owner saves to Instapaper from the web gets none of that: to decide whether an article is worth the time, they have to open it and start reading.

The ticket asks for the same "move it into a folder" gesture that To Wiki (ALF-263) introduced, with a different destination. For To Wiki, an article in that Instapaper folder is committed to the wiki's inbox/ and moved to In Wiki once it has been filed. For To Reader, an article in the folder goes through the Reader's summariser and lands in the reading list.

2 · Decisions

Tagged owner where the owner chose it in this session.

D1The trigger is an Instapaper folder named exactly “To Reader”, and alfred never creates it

An article is sent by moving it into To Reader, from Unread, Archive or any other folder. The folder is found by exact title through folders/list (TO_READER_FOLDER = 'To Reader', a constant). If it doesn't exist, the leg records there is no “To Reader” folder in Instapaper on its health and does nothing else (D12).

Why: this is To Wiki's gesture (SEND_FOLDER) and uses the same folder mechanism, because Instapaper's API can't change tags on an existing bookmark (ALF-263 §1). The only thing alfred writes to Instapaper is the archive the owner asked for (D3). It never creates folders.

D2It runs in alfred's Worker, inside the Reader's five-minute tick

A To Reader leg is added to runReaderTick. It lists the folder, then its bookmarks become work items in the same sequential loop as newsletters (§5). There is no new cron trigger, no new Worker, and nothing in knowledge.

Why: To Wiki lives in the wiki repo because its output is a git commit and that repo already had every helper it needed. This leg's output is a reader_posts row plus a model call, and the summariser, lease, ceiling and health writes all live in the Worker. Running it anywhere else would mean a second summariser. It can't have a cron of its own either: this Worker registers four of the account's five cron triggers (the wrangler.toml comment), and the leg fits in a tick that already runs every five minutes. From the owner's side, an article reaches the list within about five minutes plus the summary call.

D3alfred archives the bookmark in Instapaper as it takes it owner

The order is get_text → insert the post → bookmarks/archive → summarise. The insert happens before the archive because the row is the floor. If the archive fails, the bookmark is still in To Reader next tick, the "already a post" read finds its row (D5), and the tick archives it without inserting or summarising again.

Why (the owner's choice over an "In Reader" folder, or putting it back in Unread): the Reader becomes the one undecided list, which is how newsletters already work, since the owner's Gmail filter archives them on arrival. To Reader empties by itself. Every later decision costs at most one Instapaper call, and archiving in the Reader costs none.

D4Send moves the bookmark back to Unread instead of saving a copy. Archive makes no Instapaper call. owner

For a post whose source is instapaper, the row's Send to Instapaper verb calls bookmarks/unarchive with the stored bookmark id, which moves that same bookmark to the top of Unread. It then stamps instapaper_sent_at and archives the Reader post, exactly as a newsletter send does today. If Instapaper says the bookmark no longer exists (the owner deleted it), the route falls back to bookmarks/add with the URL and title, and no content (§8). Archive and Unarchive in the Reader make no Instapaper calls. The verb keeps its label, hotkey (i) and exit animation.

Why: unarchive restores the owner's own bookmark, with its reading progress and any highlights, and uploads no body. add would resave by URL and, as built, carry the stored text as content. One label for one meaning ("put this in my reading queue") beats two labels for what is the same act to the owner.

D5Identity is Instapaper's bookmark id, checked across both sources

An Instapaper-sourced post stores the bookmark id in the existing instapaper_bookmark_id column. A partial unique index on it (where source = 'instapaper') is what makes the insert the claim: a 409 means another tick got there first, the same rule as Gmail's (account_key, gmail_message_id). Before inserting, the leg reads every post that already carries one of the bookmark ids it is about to handle, from either source:

  • An Instapaper post whose archive failed → archive the bookmark, nothing else.
  • A newsletter post the owner sent to Instapaper and has now moved into To Reader → no new post. Archive the bookmark, and if the post is archived in the Reader, put it back on the list (archived_at = null). It already has its summary.

Why the bookmark id and not the URL: it is what bookmarks/list hands back, it is stable, and a newsletter post already carries it after a Send. Matching Instapaper articles to newsletters by URL is out of scope (§15).

D6The text is Instapaper's own, run through the extractor's existing stripper

bookmarks/get_text returns the article's HTML as Instapaper's text view renders it. That HTML goes through htmlToText (from comms/email-text.ts, which extract.ts already imports), is cut at READER_TEXT_CHARS (400 000), and gives text and word_count, with html_extracted = true. html stays null because nothing reads it for these posts: Send uses unarchive, and the list never carries it. When Instapaper can't generate text (error 1550), the row is inserted and immediately filed failed with the existing NO_READABLE_BODY reason, and the bookmark is still archived. The title and the Original link are the floor, as for an empty newsletter.

Why: this is the text the owner would actually read in Instapaper, including for sites whose raw HTML is mostly chrome. A paywalled article's text is its teaser, which the prompt's existing Paywalls clause already covers.

The site name is the URL's hostname with a leading www. removed (paulgraham.com), or Instapaper when there is no URL. It is the model's Publication: line, both at intake and on a retry, and the row's eyebrow in the UI. The Worker and the frontend each implement this three-line rule, and each side has a test pinning it.

Why the intake instant: the list is ordered by received_at, newest first. An article saved in March and moved into To Reader today would otherwise land months down the list, out of sight, just after the owner asked for it. The 90-day text sweep then also counts from when the Reader got the article.

D8Same summariser, same prompt, same model, and READER_PROMPT_VERSION stays 1

summarizePost receives the usual SummaryInput, with the site as publication. The system prompt is not edited.

Why: every instruction in it ("novel" against the field, be concrete, ignore chrome, paywalls, the fields) applies unchanged to a web article, and its opening line about newsletters doesn't change an answer. Editing it would mean a version bump and two kinds of stamp in the list for no gain (epic D7).

D9One daily ceiling. On a capped day, articles wait in To Reader. owner

An article's model call is stamped on model_called_at like any other, so it counts against READER_DAILY_CAP (30, unchanged). The difference from a newsletter is what happens once the cap is spent: the To Reader leg doesn't run at all, and a bookmark whose turn comes after the tick has hit the cap is left alone (no get_text, no insert, no archive). It stays in To Reader until the next UTC day.

Why leave it there rather than take it in unsummarised, as Gmail intake does: a newsletter has to be claimed inside the seven-day horizon before comms' 60-day sweep removes it, but a bookmark waits safely. Taking it out of the folder only to show "summarising…" until tomorrow would move the backlog somewhere less useful. At the owner's volume a backlog of 40 clears over two or three days, next to newsletters, at about $0.03 an article.

D10The schema gets a source column, and Gmail's identity columns become required only for Gmail posts

reader_posts.source is 'gmail' | 'instapaper', defaulting to 'gmail', so every existing row and the untouched Gmail intake need no change. publication_id, account_key and gmail_message_id drop not null. One CHECK constraint states what each source requires (§6). source joins READER_POST_LIST_COLUMNS, and its pinning test enforces that.

Why a discriminator instead of a fake "Instapaper" publication: a roster row would appear in the publications view with an enable toggle that does nothing, and would claim to be a sender it isn't. The epic anticipated exactly this seam: "the dedupe key would grow a source discriminator" (epic §5).

D11The Worker gets its own Instapaper client, ported rather than shared

A new workers/src/instapaper/ directory holds the OAuth 1.0a signer, ported from frontend/lib/instapaper/oauth.ts (it imports only node:crypto, which the Worker's nodejs_compat flag provides) together with its RFC 5849 test vectors. It also holds a client ported from knowledge/scripts/lib/instapaper.ts — listFolders, listBookmarks, getText and its typed InstapaperError — plus archive(bookmarkId). Each file's header names where it was ported from. The four INSTAPAPER_* values become Worker secrets with the same names and values as on Vercel. ReaderEnv gains them as optional strings. If any is blank, the leg is off: no calls, no health stamp, and GET / reports instapaper unconfigured (it reports configured when all four are set). The Work instance's Worker has none of them.

Why port instead of sharing: alfred's workspaces share no code package, and the epic's rule for exactly this case is "duplicate the twenty lines rather than couple two modules". Copying a signer pinned to RFC 5849 test vectors is safer than writing a second one.

D12To Reader has its own health, shown as a third dot beside Gmail's

Three nullable columns on reader_health: instapaper_last_success_at, instapaper_last_error and instapaper_last_error_at. Success is stamped when the leg lists the folder and finishes every item it took without an Instapaper failure. Error is stamped for any Instapaper failure: credentials, Premium, rate limit, unavailable, or no folder. The message is written for the owner (§7), and the columns ride the tick's closing health write (§5). The header draws an Instapaper dot:

  • hidden when both timestamps are null (unconfigured, or not yet run),
  • live (green) when the last success is newer than the last error,
  • erroring (red) otherwise, with a red note underneath: “Instapaper stopped taking articles from To Reader {elapsed} — {error}. Articles wait there until it’s fixed.” Here {elapsed} is the time since instapaper_last_success_at, the same figure the dot shows. The error timestamp can't be used, because a failing leg re-stamps it every tick, so "3m ago" would always be what it said. If the leg has never succeeded, the note reads “Instapaper can’t take articles from To Reader — {error}. Articles wait there until it’s fixed.” and the dot shows no elapsed time.

An Instapaper failure never enters ReaderTickSummary.failures, so it never holds back last_success_at or makes the summariser read as stalled.

Why its own surface: the header already separates "the mailbox stopped" from "the summariser stopped", because they need different fixes. A dead Instapaper token is a third fix. Why transient failures go red too: the leg runs every five minutes, so a blip shows red for one cadence and clears itself. That is a deliberate trade, because until the API paths are verified live (§15), a wrongly wired path is the more likely failure, and it must be visible on the first day rather than silent. Staleness isn't tracked: the summariser dot already covers "the tick stopped running".

3 · How it flows

The green box is the only new component. The newsletter half of the tick, the summariser and the list are unchanged. The dashed bottom line is the bookmark's own journey: archived on intake, back to the top of Unread if the owner presses Send.

4 · Per-bookmark plan

Each bookmark the leg takes is evaluated against the "already a post" read (D5). The first matching row wins:

#ConditionActionFetches
1The ceiling is spent (before the leg or at this item's turn), or the tick had no free slot for it leave: it stays in To Readernone
2A post already carries this bookmark id and is archived in the Reader restore the post to the list (archived_at = null), then archive the bookmarkPATCH post · bookmarks/archive
3A post already carries this bookmark id and is on the list archive the bookmark onlybookmarks/archive
4No post, and get_text returns HTML take: insert (pending, leased), archive, summarise, terminal patchget_text · insert · archive · Anthropic ×2 · patch = 6
5No post, and get_text answers 1550 (no text) take as failed: insert, file failed / no readable body, archiveget_text · insert · patch · archive = 4
6The insert conflicts (another tick won the race) move on. The winning tick archives it.get_text · insert = 2

Instapaper failures part-way through an item:

  • get_text fails (anything but 1550): nothing is written. The leg stops for this tick, its later bookmarks wait, and the error is stamped (D12). Newsletter and retry items already done this tick are unaffected.
  • archive fails after the insert: the post stays and is still summarised this tick. The error is stamped, and next tick's row 3 archives the bookmark. A credentials, premium or rate-limited answer also stops the leg's later bookmarks.
  • archive answers "no such bookmark" (the owner deleted it after the list): treated as archived. That is not an error.

  health.end + the three instapaper_* columns                                     1

Rules the implementation has to keep:

  • Ordering stays retries → newsletters → To Reader. Newsletters are bound by a seven-day horizon, and articles can wait. At eight to ten newsletters a day, the six slots are almost always free.
  • A tick that stops for a Gmail reason (a token-mint failure, or a Gmail transport stop mid-loop) stops the To Reader items too, and they wait for the next tick, just as nothing is advanced means today. The leg still records what it learned: when the tick returns without a closing health write and the leg has an outcome to record (a failed list, or a finished leg), one PATCH of only the three instapaper_* columns goes out before the return. Every such path stops early, so that fetch always fits in the budget.
  • A capped retry or bookmark is not prepared. Preparing a bookmark means get_text and then the insert, which would take it out of the folder (D9).
  • ReaderTickSummary gains instapaper: { listed, taken, archived, restored, failures }. index.ts's logReaderTick prints one more line (reader instapaper: 3 listed, 2 taken in, 2 archived, 0 restored) and a console.error('reader: instapaper: …') for each failure.

6 · Schema

One migration, database/migrations/<next>_reader_instapaper_source.sql. Take whatever number is free at build time; don't pin one here. It creates no new table, view or sequence, so the existing RLS and grants on reader_posts and reader_health cover it. It only expands the schema, so the app keeps running while it applies.

alter table reader_posts
  add column source text not null default 'gmail',
  add constraint reader_posts_source_valid check (source in ('gmail', 'instapaper'));

alter table reader_posts
  alter column publication_id   drop not null,
  alter column account_key      drop not null,
  alter column gmail_message_id drop not null;

-- What each source needs in order to be a post at all. A Gmail post keeps every column it had;
-- an Instapaper post is identified by its bookmark and carries no mail identity.
alter table reader_posts add constraint reader_posts_source_identity check (
     (source = 'gmail'      and publication_id is not null and account_key is not null
                            and gmail_message_id is not null)
  or (source = 'instapaper' and instapaper_bookmark_id is not null
                            and publication_id is null and comm_message_id is null
                            and account_key is null and gmail_message_id is null)
);

-- The insert-is-the-claim key for the Instapaper intake, as (account_key, gmail_message_id) is Gmail's.
create unique index reader_posts_instapaper_source_key
  on reader_posts (instapaper_bookmark_id) where source = 'instapaper';
-- The per-tick "already a post?" read spans both sources (D5).
create index reader_posts_instapaper_bookmark_idx
  on reader_posts (instapaper_bookmark_id) where instapaper_bookmark_id is not null;

alter table reader_health
  add column instapaper_last_success_at timestamptz,
  add column instapaper_last_error      text,
  add column instapaper_last_error_at   timestamptz;

notify pgrst, 'reload schema';
  • Each new column and constraint gets a comment on, in the style of migrations 0035 and 0039. The comment on instapaper_bookmark_id is rewritten because it now has two meanings: the bookmark a Send created, or the bookmark an Instapaper post came from.
  • Unaffected: v_reader_worklist (inner joins on the mail side), v_reader_publications (a null publication_id joins nothing), and reader_sweep_text (it keys on received_at, which D7 sets to the intake instant).
  • frontend/lib/database.types.ts is regenerated, never hand-edited. database/README.md's schema summary gains the columns. database/src/assertions.ts gains the DB-level checks listed in §11.
  • Run migration-lint while drafting (see the migration-lint skill).

7 · The Worker's Instapaper client

workers/src/instapaper/client.ts implements an InstapaperApi interface that the tick's tests fake. fetch is injectable, so no suite touches the network. Every call is a signed POST with an application/x-www-form-urlencoded body and a 20-second abort. Every error message names the call, the error kind and Instapaper's code, and never includes a header, a request body or a secret.

MethodEndpointParamsAnswer
listFolders()/api/1.1/folders/list—{ folderId, title }[]

8 · Send restores

POST /api/reader/posts/[id]/instapaper keeps its order: config first, then the read, then Instapaper, and the write only on a confirmed save. getReaderPostForSend also selects source and instapaper_bookmark_id, and the call to Instapaper branches on the source:

// app/api/reader/posts/[id]/instapaper/route.ts — the one branch this story adds
const outcome =
  post.source === 'instapaper' && post.instapaper_bookmark_id !== null
    ? await restoreOrResave(config, post)   // bookmarks/unarchive; on "no such bookmark" → add by URL
    : await addBookmark(config, params);    // a newsletter, exactly as today
  • unarchiveBookmark(config, bookmarkId) in lib/instapaper/bookmark.ts uses the same readAnswer and returns the same outcomes (saved with the bookmark's id, or refused/unavailable), plus gone for the missing-bookmark code.
  • gone → addBookmark with url, title and the gist as description, and no content, so Instapaper fetches the page itself. Only a URL-less bookmark falls back to the stored text as content. The id returned then replaces instapaper_bookmark_id.
  • sendUnavailable (lib/reader/send.ts): an Instapaper-sourced post can always be sent when the deployment is configured, because the CHECK constraint guarantees a bookmark id. A newsletter's rule is unchanged.
  • The E2E mock (frontend/scripts/mock-supabase.mjs) answers bookmarks/unarchive as it answers bookmarks/add, records the request, and can be seeded with an error code.

12 · Build plan & evidence

  • One implementation session, one phase: implementation PR, which archives this spec (git mv to docs/specs/archive/) in the same PR.
  • Team. The lead writes the migration, the regenerated types and InstapaperApi first, alone. Then, optionally, one mid-tier subagent owns workers/src/instapaper/* and its tests, while the lead builds the leg against a fake of the interface. The file sets are disjoint and InstapaperApi is the only seam. The frontend half (send branch, row, header) is the lead's, because it shares fixtures with the Worker half's types. Subagents never commit.
  • Demo doc. Follow the showboat skill's evidence rules rather than inventing new ones here. This change has a visual surface (the row, the header, the empty state) and a non-visual one (the Worker leg, the Send branch), so the demo needs the evidence each kind calls for, covering every acceptance line below.
  • Egress. A cloud session can't reach instapaper.com, so everything is verified against fakes, and the live check is the owner's (§13). Never paste live credentials into a session.
  • PR description tells the owner the setup steps in §13 and notes that the Instapaper API paths were built to §7's table unless the docs could be read.

13 · Setup checklist (owner)

Not agent work. It goes into the PR description.

  • In Instapaper, create a folder named exactly To Reader.
  • Put the four values on the personal Worker: npx wrangler secret put INSTAPAPER_CONSUMER_KEY, and the same for _CONSUMER_SECRET, _ACCESS_TOKEN and _ACCESS_TOKEN_SECRET, using the same values as Vercel. A token is bound to the key that issued it. If one is ever re-minted (npm run instapaper:token -w frontend), update Vercel, the Worker and the knowledge repo's secrets together.
  • Live check before relying on it. With one article in To Reader, a local Anthropic key and the four values exported: npm run eval:reader -w workers -- --instapaper --limit 1. Expect its title, site and gist, and confirm that it archived nothing. This is the live test of §7's paths.
  • After the deploy: curl the Worker's / and look for instapaper configured. Move an article into To Reader. Within about five minutes it should be in the Reader, summarised, with via Instapaper; it should be in Instapaper's Archive; and the header's Instapaper dot should be green. Press Send, and it should be at the top of Unread.

14 · Acceptance criteria

  • With the four INSTAPAPER_* secrets set, an article moved into To Reader becomes one reader_posts row with source = 'instapaper', its bookmark id, the bookmark's title and URL, received_at = the tick's instant, the text from get_text via htmlToText, and no publication or mail identity.
  • It is summarised in the same tick by the unchanged summariser, prompt (READER_PROMPT_VERSION still 1) and model, with the site as Publication:, and its model call counts against READER_DAILY_CAP.
  • The bookmark is archived in Instapaper after the insert. If that archive fails, the next tick archives it without a second post or a second model call.
  • A bookmark id that an existing post already holds (from either source) gets no new post. The bookmark is archived, and an archived post returns to the reading list.
  • Error 1550 yields a failed / no readable body row with its Original link, and the bookmark is archived.
  • On a capped day the leg makes no Instapaper call, and nothing leaves To Reader. A bookmark whose turn comes after the cap is reached mid-tick is untouched.
  • The leg lists only when a slot is free and takes at most that many bookmarks, oldest first. A worst-case tick stays at or under 48 fetches, and READER_TICK_LIMIT stays 6.
  • An Instapaper failure stops only the leg, is stamped on instapaper_last_error(_at) in the owner-facing words from §7, and never blocks newsletters, retries or last_success_at. A clean leg stamps instapaper_last_success_at.
  • Unconfigured → no Instapaper call and no stamp, GET / says instapaper unconfigured, and the header draws no Instapaper dot.
  • The row's eyebrow is the site (with www. stripped), and its meta line ends · via Instapaper. Newsletter rows are unchanged.
  • The header's Instapaper dot is green when the last success is newer than the last error. Otherwise it is red, with the note “Instapaper stopped taking articles from To Reader {elapsed since the last success} — {error}. Articles wait there until it’s fixed.”, or “Instapaper can’t take articles from To Reader — {error}. …” if it has never succeeded.
  • Send to Instapaper on an Instapaper-sourced row calls bookmarks/unarchive with its bookmark id (no bookmarks/add), stamps instapaper_sent_at, and archives the post. If the bookmark is gone, it resaves by URL without content. Archive makes no Instapaper call.
  • The empty state reads “Newsletters from your publications, and articles you move to To Reader in Instapaper, land here summarised.”
  • The migration passes migration-lint, types are regenerated, existing rows read source = 'gmail', and the §11 DB assertions pass.
  • npm run eval:reader -w workers -- --instapaper reads To Reader and prints gists without archiving or writing anything.
  • check is green; there is a demo doc per the showboat skill; and this spec is archived by the implementation PR.

15 · Out of scope & open questions

Deliberately out

  • Highlights and notes. That is To Wiki's job. The leg ignores the highlights bookmarks/list returns.
  • Tags. They can't be written through the API (ALF-263 §1).
  • A separate daily cap, or a higher shared one. The owner chose to share 30 (D9). Raising it is a one-line var change if a backlog ever makes that worth it.
  • Matching by URL between an Instapaper article and a newsletter post that was never sent. Identity is the bookmark id only (D5).
  • Author extraction from the get_text HTML. The row shows the site, and author stays null.
  • Wiki picks' published date. For an Instapaper post it is the intake date (the envelope reads received_at), because the bookmark has no publish date.
  • An Instapaper article sent through both To Reader picks and To Wiki becomes two raw/ folders (reader-post identity vs URL identity), the same known gap ALF-263 §14 names.
  • Mirroring Reader decisions back to Instapaper beyond Send. Archive and Unarchive in the Reader make no call (D4).
  • A paywalled-teaser marker. It is still unbuilt for newsletters and isn't added here.

Genuinely open (for the implementer to confirm, not to decide)

  • The API prefixes and the missing-bookmark error code (§7). The knowledge client's /api/1.1/ paths haven't been run live yet (its README's dry-run and smoke-test items are unticked). The owner's eval:reader --instapaper run settles this before the leg is relied on.
  • Instapaper's rate limits aren't published. A configured, uncapped tick makes two listing calls every five minutes, about 576 a day. If rate-limited starts showing on the dot, the fix is to list on every other tick (a constant in to-reader.ts). No need to build that until it happens.
