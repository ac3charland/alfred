ALF-272 — Implement a “To Reader” folder pipeline in Instapaper à la “To Wiki”

Move an Instapaper article into a To Reader folder and, within five minutes, it’s summarised in the Reader like a newsletter.

Revised 2026-09-28: D1 → “Send to Instapaper” (your review).

Decisions

  1. D2Where does the pipeline run?

    In the Reader’s five-minute tick, not knowledge like To Wiki.

    The summariser, lease and cap live there; no new cron.

  2. D3How is an article stored?

    As a Reader post with a new source column, keyed by bookmark id.

    A fake “Instapaper” publication would appear in your roster.

  3. D4What marks an Instapaper row?

    Site as eyebrow, “via Instapaper” in meta, dated when alfred took it.

    Dated by when you saved it, it would sink out of sight.

  4. D5How does a broken Instapaper connection show?

    A third header dot, red, with a one-line note.

    Newsletters still flow; the summariser mustn’t read as stalled.

  5. D1What does Send say on these rows?

    “Send to Instapaper”, as on every row.

  6. D6Where does the bookmark go once taken?

    Archived in Instapaper; Send moves it back to Unread; Archive makes no call.

  7. D7How do articles count against the daily cap?

    They share the 30-a-day cap; on a capped day they wait in To Reader.

☞ open: your pick · → proposed: my call · ✓ settled: yours. Merging accepts every proposed row.

Not doing

Highlights or notes (To Wiki does those), tags, or a separate daily cap for articles.

Heads-up

  • Create a “To Reader” folder and add four Instapaper secrets to the Worker (steps).
  • The Instapaper API paths are unverified; run the live check first.
  • Each article costs about $0.03 of the same 30-a-day budget.

Working detail

Everything below is for the implementing agent. Approving needs only what’s above.

Context

The Reader (epic ALF-232, docs/specs/epics/ALF-232.html and its build notes ALF-232-notes.md) summarises every newsletter in the personal Gmail inbox into a gist and a one-page overview. Articles the owner saves to Instapaper from the web get neither, so deciding whether one is worth the time means opening it. The ticket asks for To Wiki’s “move it into a folder” gesture (ALF-263, docs/specs/archive/ALF-263.html, built in ac3charland/knowledge), with the Reader as the destination. The owner settled D6 and D7 in the refinement session.

Decision records

D1What does Send say on these rows? · settled

Considered: “Back to Unread” on Instapaper rows, which says literally what happens to an article already in Instapaper. The owner kept one label, hotkey (i) and exit animation for one meaning, “put this in my reading queue”. No label changes anywhere; the behaviour behind the verb on an Instapaper row is D6’s.

D2Where does the pipeline run? · proposed

Alternatives: a step in the knowledge repo’s kickoff Action (where To Wiki lives), or a fifth Worker cron. To Wiki lives in knowledge because its output is a git commit and that repo had every helper. This leg’s output is a reader_posts row plus a model call, and the summariser, lease, ceiling and health writes are all the Worker’s; running it elsewhere means a second summariser. A fifth cron would spend the account’s last trigger on a leg that fits in a tick that already runs every five minutes. Consequence: an article reaches the list within about five minutes plus the summary call. When newsletters fill every slot, articles wait for the next tick.

D3How is an article stored? · proposed

Alternative: a synthetic “Instapaper” publication row. That row would sit in the publications view with an enable toggle that does nothing and claim to be a sender it isn’t. A discriminator is the seam the epic anticipated (“the dedupe key would grow a source discriminator”, epic §5). Consequences: publication_id, account_key and gmail_message_id become nullable, a CHECK constraint states what each source requires, and a partial unique index on instapaper_bookmark_id makes the insert the claim, as (account_key, gmail_message_id) does for Gmail. Costly to reverse once rows exist.

D4What marks an Instapaper row? · proposed

Alternatives: an “Instapaper” eyebrow with no site, or an “from Instapaper” badge beside the state marker. The site is what a skimmer uses to judge a source, and the eyebrow is where the Reader already puts a newsletter’s publication. The existing “in Instapaper” badge already means sent, so a second Instapaper badge would read as the same claim. The date is the intake instant because the list sorts by received_at, newest first. An article saved in March and moved today would otherwise land months down, out of sight, just after the owner asked for it. The 90-day text sweep then also counts from intake.

D5How does a broken Instapaper connection show? · proposed

Alternative: stamp Instapaper failures on the summariser’s reader_health.last_error. That would read “summariser stalled” while newsletters summarise fine. The header already separates “the mailbox stopped” from “the summariser stopped” because they need different fixes, and a dead Instapaper token is a third. Transient failures go red too: a blip is red for one cadence and clears itself. That is deliberate, because until the API paths are verified live, a wrongly wired path is the likelier failure and must not be silent. Staleness isn’t tracked, since the summariser dot already covers “the tick stopped”. The mechanics are in D15.

D6Where does the bookmark go once taken? · settled

The owner chose this over moving the bookmark to an “In Reader” folder (To Wiki’s shape), or back to Unread (summary only). It matches how newsletters work, since the Gmail filter archives them on arrival: the Reader is the one undecided list, and To Reader empties by itself. unarchive restores the owner’s own bookmark, with its progress and highlights, and uploads no body. Archiving and unarchiving in the Reader make no Instapaper call. The fallback is in D14.

D7How do articles count against the daily cap? · settled

The owner chose sharing READER_DAILY_CAP (30, unchanged) over raising it to 60 or adding a separate article cap. An article’s model call is stamped on model_called_at like any other. What differs from a newsletter is the capped day: a newsletter must be claimed within its seven-day horizon, but a bookmark waits safely. So once the cap is spent, the leg doesn’t run at all, and a bookmark whose turn comes after the cap is reached mid-tick is left untouched. Consequence: a backlog of 40 clears over two or three days.

Implementation decisions

D8 · The folder is found by exact title and never created

TO_READER_FOLDER = 'To Reader', resolved through folders/list, as To Wiki’s SEND_FOLDER is. Folders rather than tags because Instapaper’s API can’t change a tag on an existing bookmark (ALF-263 §1). If the folder is missing, D15 stamps an error; the only write alfred makes to Instapaper is the archive the owner chose.

D9 · The text is Instapaper’s own

bookmarks/get_text HTML → htmlToText → cut at READER_TEXT_CHARS (400 000) → text and word_count, with html_extracted = true. html stays null, since nothing reads it for these posts. It is the text the owner would read in Instapaper, and a paywalled article’s teaser is covered by the prompt’s existing Paywalls clause. Error 1550 (no text) → the existing NO_READABLE_BODY path.

D10 · Same summariser, same prompt, READER_PROMPT_VERSION stays 1

Every instruction in the prompt applies unchanged to a web article, and its opening line about newsletters changes no answer. Editing it would mean a version bump and two stamps in the list for no gain (epic D7). The site goes in as publication.

D11 · The Worker gets its own Instapaper client, ported

workers/src/instapaper/ holds: the OAuth 1.0a signer, ported from frontend/lib/instapaper/oauth.ts without server-only (it needs only node:crypto, which nodejs_compat provides) and with its RFC 5849 vectors; and a client ported from knowledge/scripts/lib/instapaper.ts, plus archive. Each file’s header names its source. The workspaces share no package, and the epic’s rule is to duplicate rather than couple two modules. The four INSTAPAPER_* values become Worker secrets with Vercel’s names and values. If any is blank, the leg is off: no calls, no stamp, no dot.

D12 · “Already a post?” is checked across both sources

Before inserting, the leg reads every post holding one of the bookmark ids it is about to handle, whatever its source. This covers an Instapaper post whose archive failed (archive only), and a newsletter the owner sent to Instapaper and has now moved into To Reader. That one gets no new post: the bookmark is archived, and an archived post returns to the list with the summary it already has. URL matching between articles and never-sent newsletters is out of scope.

D13 · The leg takes only free slots, last in the tick

Order: retries → newsletters → To Reader. Newsletters are bound by a seven-day horizon; articles can wait. The leg lists only when 6 − retries − fresh > 0 and takes that many bookmarks, oldest time first. A new bookmark costs the same six fetches as a newsletter, so READER_TICK_LIMIT stays 6 and the worst tick is 48 of 50 (Behaviour).

D14 · Send falls back to resaving by URL when the bookmark is gone

If unarchive answers “no such bookmark” (the owner deleted it), the route calls bookmarks/add with the URL, title and gist but no content, so Instapaper fetches the page. Only a URL-less bookmark falls back to the stored text as content. The id that comes back replaces instapaper_bookmark_id.

D15 · The leg stamps its own health on the tick’s closing write

New columns: instapaper_last_success_at, instapaper_last_error, instapaper_last_error_at. Success is stamped when the leg lists and finishes every item it took without an Instapaper failure. Error is stamped on any Instapaper failure, in the owner’s words (Contracts). Both ride the tick’s closing health write. On the two paths with no closing write (a Gmail token or transport stop), one PATCH of only these columns goes out when the leg has an outcome to record; those paths stop early, so it fits the budget. Instapaper failures never enter ReaderTickSummary.failures, so they never hold back last_success_at.

Site name: the URL’s hostname with a leading www. removed, else Instapaper. It is the model’s Publication: line (at intake and on retry) and the row’s eyebrow. The Worker and the frontend each implement this three-line rule, and each side has a test pinning it.

The Instapaper dot (P1, P3)

  • Hidden when both instapaper timestamps are null (unconfigured, or not yet run).
  • Live when the last success is newer than the last error. Hover: Instapaper — To Reader last checked {elapsed}.
  • Erroring otherwise. The dot shows the time since the last success, and the note reads “Instapaper stopped taking articles from To Reader {elapsed} — {error}. Articles wait there until it’s fixed.”. With no success ever, the note reads “Instapaper can’t take articles from To Reader — {error}. …” and the dot shows no time. Elapsed counts from the last success, never the last error, because a failing leg re-stamps its error every tick. Hover: Instapaper — {error} ({elapsed since the error}), the Gmail dot’s form.

Acceptance criteria

  • With the secrets set, an article in To Reader becomes one reader_posts row: source = 'instapaper', its bookmark id, title and URL, received_at = the tick’s instant, text from get_text, and no publication or mail identity.
  • It is summarised in the same tick by the unchanged summariser and prompt (version 1), with the site as Publication:, and it counts against READER_DAILY_CAP.
  • The bookmark is archived after the insert. A failed archive is retried next tick with no second post and no second model call.
  • A bookmark id an existing post holds, from either source, gets no new post: the bookmark is archived and an archived post returns to the list.
  • Error 1550 yields a failed / no readable body row with Original, and the bookmark is archived.
  • On a capped day the leg makes no Instapaper call and nothing leaves To Reader. A bookmark after a mid-tick cap is untouched.
  • The leg lists only with a free slot and takes at most that many bookmarks, oldest first. A worst tick is ≤ 48 fetches, and READER_TICK_LIMIT stays 6.
  • An Instapaper failure stops only the leg and is stamped in the owner-facing words. Newsletters, retries and last_success_at are unaffected, and a clean leg stamps instapaper_last_success_at.
  • Unconfigured: no Instapaper call, no stamp, GET / says instapaper unconfigured, and no dot.
  • The eyebrow is the site (www. stripped) and the meta line ends “· via Instapaper”. Newsletter rows are unchanged.
  • Every row, article or newsletter, keeps the verb “Send to Instapaper” with hotkey i.
  • The Instapaper dot is hidden, live or erroring by the rules in Behaviour, with the note’s exact words.
  • Send on an Instapaper row calls bookmarks/unarchive (no add), stamps instapaper_sent_at and archives the post. If the bookmark is gone, it resaves by URL without content. Archive makes no Instapaper call.
  • The empty state reads “Newsletters from your publications, and articles you move to To Reader in Instapaper, land here summarised.”
  • The migration passes migration-lint, types are regenerated, and existing rows read source = 'gmail'.
  • eval:reader -- --instapaper prints gists without archiving or writing.

Out of scope, risks & unknowns

  • Highlights and notes are To Wiki’s job; the leg ignores the highlights bookmarks/list returns. Tags can’t be written through the API. A separate cap was declined (D7); raising the shared one is a one-line var change.
  • No author extraction from get_text. Wiki picks’ published date for an article is its intake date. An article sent both through Reader picks and To Wiki becomes two raw/ folders (the gap ALF-263 §14 already names). The paywalled-teaser marker is still unbuilt.
  • Unknown: the API paths and the missing-bookmark code. The knowledge client’s /api/1.1/ paths haven’t run live. Before coding, read Instapaper’s Full API docs as docs/specs/archive/ALF-238.html §6 describes; if they’re unreachable, build to Contracts. The owner’s eval:reader -- --instapaper run settles this.
  • Unknown: Instapaper’s rate limits aren’t published. The leg lists twice a tick, about 576 calls a day. If rate-limited starts showing, list on every other tick (a constant in to-reader.ts); don’t build that until it happens.
  • Never paste live credentials into a session. Cloud sessions can’t reach instapaper.com, so verification is against fakes.

After it ships (for you)

  1. In Instapaper, create a folder named exactly To Reader.
  2. Run npx wrangler secret put for INSTAPAPER_CONSUMER_KEY, _CONSUMER_SECRET, _ACCESS_TOKEN and _ACCESS_TOKEN_SECRET, using Vercel’s values. If a token is ever re-minted (npm run instapaper:token -w frontend), update Vercel, the Worker and knowledge’s secrets together.
  3. With one article in To Reader, a local Anthropic key and the four values exported, run npm run eval:reader -w workers -- --instapaper --limit 1. Expect its title, site and gist, with nothing archived.
  4. After deploy: curl the Worker’s / and look for instapaper configured. Move an article into To Reader. Within about five minutes it should be in the Reader with “via Instapaper”, archived in Instapaper, with a green dot. Press Send, and it should be at the top of Unread.
