alfred Reader · Refinement spec

ALF-280 — YouTube podcasts in the Reader

Paste a YouTube episode link into the capture box and dispatch it. It then shows up in the Reader summarised like an article, with every key idea and the best stretches timestamped, opening YouTube at that moment.

Decisions

  1. D1How is a podcast link recognised?

    A new Podcast type. A bare YouTube link gets it automatically.

    No model call; anything ambiguous you type yourself.

  2. D2Who fetches the transcript?

    Your Mac's daemon runs yt-dlp, fabric's way. Your API key supplies title and length.

    YouTube's API serves captions only to a video's owner. Episodes wait while the Mac sleeps.

  3. D3What gets timestamped?

    Every novel idea and evidence bullet, plus up to six “Worth a listen” stretches.

    Answers both “where's that idea?” and “what's worth hearing in full?”

  4. D4What changes on the row?

    Channel, running time, and Watch in place of Send to Instapaper.

    Instapaper can't play a video. Watch is how you listen.

  5. D5Which podcasts?

    YouTube videos you hand-pick, under ten hours a week. No audio transcription, no feeds.

  6. D6How does an episode arrive?

    Capture the link, then Dispatch the Inbox row to the Reader.

  7. D7Where does a timestamp play?

    In YouTube, at that second. No player inside alfred.

☞ open: your pick · → proposed: my call · ✓ settled: yours. Merging accepts every proposed row.

Not doing

Audio transcription, RSS/Apple podcasts, subscribing to channels, or an in-app player.

Heads-up

  • You install yt-dlp on the Mac and keep it updated. YouTube breaks it every few months (steps).
  • New: YOUTUBE_API_KEY on Vercel and a transcript secret shared by Worker and daemon.
  • Running cost ≈ $1–3 a month in summaries. Captions and the API are free.

Working detail

Everything below is for the implementing agent. Approving needs only what’s above.

Context

The ticket asked to "ingest new podcast episodes and transcribe them or get their transcripts", feed the transcript into the Reader like an article, and timestamp key ideas and interesting segments so the owner can listen to just those parts. In refinement the owner narrowed it. YouTube podcasts only, hand-picked (no subscriptions), under ten hours a week, arriving through the capture box → Inbox → Dispatch path, using YouTube's transcripts rather than running speech-to-text. Timestamps play in YouTube itself, so there is no player and no podcast-app deep link.

This departs from the epic. docs/specs/epics/ALF-232.html §5 lists "no podcasts" among its non-goals. That is a scope line for the epic's two stories, not a structural objection, and the epic also planned for a second source writing the same reader_posts row. Since then the Reader has gained two more sources: Instapaper's To Reader folder (ALF-272, source = 'instapaper') and research reports (ALF-298, source = 'research'). This story adds a fourth, youtube, using research's shape. An Inbox item type is dispatched by a route and an RPC into a post that waits for its body from outside, and the five-minute tick then summarises it like any other post.

Why not "the YouTube API" for transcripts. The YouTube Data API v3 captions.download endpoint returns 403 forbidden unless the request is authorised by the video's owner or the owner has enabled third-party contributions. It cannot read captions on someone else's podcast. fabric, which the owner pointed to, uses its API key only for metadata, duration and comments. Its transcripts come from shelling out to yt-dlp (internal/tools/youtube/youtube.go, tryMethodYtDlpInternal), which reads YouTube's internal caption tracks. That works on a home connection. YouTube routinely blocks the same requests from cloud and datacenter IPs, and a Cloudflare Worker cannot run yt-dlp anyway. Hence D2.

The research send route app/api/reader/research/route.ts plus RPC send_items_to_research (0047_research.sql) is the template for the route and RPC.
  • The classifier sweep (workers/src/sweep.ts, runSweep) classifies unclassified Inbox rows with Haiku. workers/src/verdict.ts lists the model-facing types.
  • The Reader tick. workers/src/reader/scheduled.ts. fetchRetries in worklist.ts picks pending posts, already gated by DELIVERED_OR_NOT_RESEARCH_FILTER so an undelivered research report is never summarised. prepareRetry files an empty-text post failed. prompt.ts (buildReaderRequest, READER_MODEL_INPUT_CHARS = 150_000), schema.ts (READER_SUMMARY_SCHEMA, normalizeReaderSummary) and summarize.ts.

Decision records

D1How is a podcast link recognised? · proposed

A fifth Inbox type, podcast (label "Podcast", lucide Headphones glyph). The sweep gives it deterministically, with no model call, to a capture whose trimmed title is exactly one YouTube video URL (forms in Behaviour). Every other capture goes to the model as today, and the model is not taught the new type. A link with words around it ("watch the Karpathy bit youtu.be/…") is classified as before, and the owner retypes it from the row menu.

Alternatives. (a) Teach the Haiku classifier the type. That is a prompt change and a billed judgment for something a regex decides exactly, and it would mistype "fix the YouTube embed https://youtube.com/…" captures. (b) No type, with Dispatch offered on any row that contains a YouTube URL. That breaks the rule that a row's labels name its destination (dispatch.ts's module doc). (c) A "Send to Reader" verb outside Dispatch. That gives two ways to leave the Inbox.

Consequence. A deterministic verdict is stored like a model verdict, so the row reads as classified, and the corrections trigger (0029) still logs an owner override at dispatch.

D2Who fetches the transcript? · proposed

Transcripts: a new job in the Mac daemon. Every few minutes it asks the Worker which episodes are waiting, runs yt-dlp for each to download the English caption track (manual if present, else auto-generated) as VTT without the video, parses and de-duplicates the cues, and posts the timed segments back, signed. Metadata: the owner's YouTube Data API key, called once by the Dispatch route (videos.list?part=snippet,contentDetails, 1 quota unit per call, up to 50 ids). That fills title, channel, duration, publish date and description chapters before the post exists, so the row reads correctly while the Mac sleeps, and a bad link is refused at dispatch rather than discovered later.

Alternatives, one line each:

  • Managed transcript API (e.g. Supadata, GET /v1/youtube/transcript, timed segments in ms, free tier 100 credits a month) called from the Worker. Always on and no Mac dependency. It adds a vendor and a secret, and the next-best choice if the Mac dependency chafes. The Worker-side seam (/reader/transcripts and the segment contract) is the same, so switching later replaces the daemon job with a tick leg and touches nothing else.
  • Unofficial caption endpoint from the Worker. Free, but cloud IPs are widely reported as blocked. It would fail on the first real episode.
  • Official captions.download. Owner-only (see Context). Not possible.

Consequences. Episodes wait while the Mac is asleep. The row says so and when the Mac was last seen (P2 b). yt-dlp is the maintenance cost: YouTube changes break it every few months and brew upgrade yt-dlp fixes it, so a systemic yt-dlp failure is reported as such and is never mistaken for "this video has no captions" (Behaviour). The daemon's credential grows from write-only to "read the ids of waiting episodes". That is low-sensitivity public video ids, through its own secret (D9).

D3What gets timestamped? · proposed

The episode keeps the post's two layers (headline, gist, overview) with three additions. Each Novel ideas and Evidence bullet carries the second where it is discussed. A new Worth a listen section lists 0–6 stretches worth hearing in full, each with a start time, a short title and why. "Who should read it" is drawn as Who should listen. Further reading is always empty, because a transcript has no links.

Alternatives. Chapters only, i.e. YouTube's own description chapters as the segments. Many episodes have none, and chapters are a table of contents, not a judgment of what's worth hearing (chapters are still passed to the model as hints). A timestamp only on ideas would answer "where" but not "what's worth the time".

Consequence. Stored bullets stay strings, so the wiki picks, the wiki envelope and the sent-marks keep working unchanged. Times ride in parallel arrays that the normaliser keeps aligned (D10).

D4What changes on the row? · proposed

Eyebrow = channel (stored in author, so postEyebrow needs no change). The meta line reads date · running time (2 h 14 min, from duration_s) · YouTube instead of read minutes. Watch ↗ (outline, hotkey o) takes Send to Instapaper's slot and is also the row's Original link, so the overview footer carries no Original. Two new markers: awaiting transcript (muted) and no transcript (alert, row dimmed like a failed one).

Alternative: keep Send to Instapaper. Instapaper saves a YouTube link as a bookmark with no readable text, and the owner reads there, so the verb would promise a read that isn't there.

D5Which podcasts? · settled

The owner's call in refinement: YouTube only, hand-picked, under ten hours a week, using YouTube's transcripts. RSS and audio podcasts, speech-to-text, and auto-ingesting a channel's new uploads are out (Out of scope).

D6How does an episode arrive? · settled

The owner chose capture → Inbox → Dispatch over a paste field in the Reader or Instapaper's To Reader folder. It is capture-first and reuses the one triage surface. The cost is two stops, which D1's auto-typing keeps to one tap on the ready row.

D7Where does a timestamp play? · settled

The owner said neither an in-app player nor a podcast app: YouTube itself. A chip links to https://www.youtube.com/watch?v=<id>&t=<s>s in a new tab. The YouTube app claims it on the phone and honours t.

Implementation decisions

D8 · A post waits for its transcript in its own state column

reader_posts.transcript_state (waiting | ready | unavailable, null off-source), alongside summary_state, the same way research_state sits alongside it. A youtube post is created summary_state = 'pending', transcript_state = 'waiting'. fetchRetries gains the guard transcript_state is null or transcript_state = 'ready' (folded into one PostgREST and with the research guard). Otherwise prepareRetry would file every waiting post failed for its empty text. No new cron and no new tick leg: a ready post is an ordinary retry row.

D9 · The daemon talks to a new signed Worker endpoint with its own secret

POST /reader/transcripts on the Worker, verified with verifyTimestampedSignature against READER_TRANSCRIPTS_HMAC_SECRET, not the comms secret, so each credential keeps its narrow power. One exchange both delivers results and asks for work. The request carries 0–3 results, and the response lists up to 3 waiting episodes. This mirrors how /comms/ingest answers with the cursor. It is a separate daemon job, not a comms Source: the Source interface is message-shaped.

D10 · Timestamps are produced by the model from a marked transcript and validated on the way in

The Worker formats segments into ~30-second blocks, each line opening [h:mm:ss]. The model returns at in integer seconds. normalizeReaderSummary drops any at outside [0, duration_s] (a bullet keeps its text with a null time, and a listen item is dropped). It sorts listen items by time, caps them at 6, and stores bullet times as novel_idea_at / evidence_at arrays aligned index-for-index with the stored bullets (trimmed together when the 6-bullet ceiling cuts). A model-facing schema with object bullets, normalised into string bullets plus parallel arrays, keeps every existing consumer on string[].

D11 · Episodes get the stored-text cap as their model-input cap

A 3-hour episode is ~30 000 words (~170 000 characters with markers), over today's READER_MODEL_INPUT_CHARS of 150 000. For source = 'youtube' the cap is READER_TEXT_CHARS (400 000), so the tail, with its timestamps, isn't silently cut. That is ~100k input tokens at most, about $0.20–0.30 for a pathological episode and ~$0.05 for an hour.

D12 · "No captions" waits 24 hours before it becomes "no transcript"

YouTube generates auto-captions some hours after upload, so a fresh episode's first answer is often "no subtitles". A post becomes unavailable only after the daemon has reported "no captions" across at least 24 hours (transcript_missing_since), with one attempt per hour. "Video unavailable" (private, removed, members-only) is final at once. A yt-dlp failure of any other kind is systemic: it touches no post and is recorded on reader_health.

D13 · Dispatch refuses what can never become an episode, and deduplicates

The route answers 409 naming the item for a title with no parsable video id, a video the API doesn't return (private or removed), or one whose liveBroadcastContent is live or upcoming. Nothing changes in that case, as with research. A video already in the Reader (any state, archived included) is consumed: the item is deleted, no second post is made, and the toast says "already in the Reader". A unique partial index on youtube_video_id makes that hold under a race.

Behaviour

Recognising a link (D1)

A capture is auto-typed podcast when its title, trimmed, is one URL matching any of these, with any extra query parameters ignored (t, si, list, feature):

  • https://(www.|m.)youtube.com/watch?v=<id>
  • https://youtu.be/<id>
  • https://(www.)youtube.com/live/<id>
  • https://(www.)youtube.com/shorts/<id>

The id is 11 characters, [A-Za-z0-9_-]. A channel, playlist or bare youtube.com URL does not match. One pure function, parseYouTubeVideoId(text), is shared by the sweep's pre-verdict and the Dispatch route (one copy per package, each tested on the same table of cases). The sweep's pre-verdict runs before any model call for that row and writes the verdict in the shape a model verdict takes.

Readiness and Dispatch (D6, D13)

  • dispatchReadiness: a podcast row is ready when it is childless and the deploy has YOUTUBE_API_KEY. Otherwise the blocker is youtube not connected, which wins over has subtasks, same reasoning as research. Classify as… → Podcast appears only when configured, as Research does.
  • The bulk bar and the row menu send podcast rows to POST /api/reader/youtube. Up to 10 ids per request, so one videos.list call suffices.
  • The route validates each item: root, undispatched, childless, item_type = 'podcast', and a parsable id. It then calls the API once, checks each video (D13), and calls send_items_to_youtube(p_episodes jsonb). The RPC, in one transaction, stamps dispatched_at, inserts one post per new video (on conflict do nothing on the partial unique index), deletes every item, and returns the inserted posts. The item's notes are not carried (Out of scope).
  • Toast: "Sent N episode(s) to the Reader", or "… N already in the Reader" when some were duplicates, linking /reader, via a youtubeSentToast(sent, duplicates) beside researchSentToast. A mixed bulk dispatch (podcast plus other types) runs each destination's send as the bar already does for research.

The exchange (D9, D12)

Every 5 minutes, and immediately after delivering results, the daemon POSTs { version: 1, results: [...] }. The Worker:

  1. Verifies the signature over the raw bytes (5-minute replay window, as ingest), then validates by hand, naming the failing field.
  2. Stamps reader_health.transcripts_last_seen_at = now. It sets or clears transcripts_last_error / _at from the request's systemic_error field.
  3. For each result, scoped by where id = $1 and transcript_state = 'waiting' (a stale result touches nothing):
    • ready: format the segments (D10) into text (capped at READER_TEXT_CHARS), set word_count, transcript_state = 'ready', transcript_checked_at = now. The next tick summarises it.
    • no_captions: set transcript_checked_at = now, transcript_missing_since = coalesce(transcript_missing_since, now). If that is ≥ 24 h ago, set unavailable plus summary_state = 'failed' plus last_error = 'YouTube has no English captions for this video'.
    • video_unavailable: set unavailable at once, with the daemon's reason (e.g. "the video is private or members-only").
  4. Answers { wanted: [{ post_id, video_id }] }: up to 3 waiting posts whose transcript_checked_at is null or older than 1 hour, oldest created_at first.

Subrequests per exchange: health stamp 1, one patch per result (≤ 3), wanted read 1. That is at most 5, far inside a fetch handler's 50.

The daemon job (D2)

  • Runs yt-dlp --skip-download --write-subs --write-auto-subs --sub-langs "en.*,en" --sub-format vtt -o <tmpdir>/%(id)s https://www.youtube.com/watch?v=<id> via execFile (no shell), 120 s timeout, preferring a manual track over an auto track when both arrive. It reads the VTT and removes the temp dir.
  • VTT parsing gotcha: auto-caption VTT repeats each line across rolling cues, and lines carry inline <00:00:01.234><c> word-timing tags. Strip the tags, drop a cue whose text is a repeat of the previous cue's tail, and collapse whitespace (fabric's readAndCleanVTTFile does the same). Output: [{ start_ms, text }].
  • Classifies the outcome. Exit 0 with no subtitle file → no_captions. A stderr line matching "Private video", "Video unavailable", "members-only", "This live event", "Sign in to confirm your age" → video_unavailable with a short reason. Anything else (non-zero exit, timeout, yt-dlp not found) is systemic: no result for that post, and the next exchange carries systemic_error with the last stderr line, e.g. "yt-dlp failed: … (try brew upgrade yt-dlp)".
  • Secrets come from the login keychain (alfred-reader-transcripts-hmac-secret). The endpoint URL comes from config.json (transcriptsUrl). The job is off when that key is absent, so the comms-only install keeps working. Logs name post ids and outcomes, never transcript text.

What the model is asked (D3, D10)

For source = 'youtube', buildReaderRequest builds the episode variant. A system-prompt addendum says: this is an auto-transcribed podcast episode, unpunctuated and without speaker labels; each line begins with its start time; give each novel idea and evidence bullet the start time of the block where it is discussed; choose 0–6 stretches worth hearing in full (≥ 2 minutes each, not the intro), each with a ≤ 8-word title and a ≤ 25-word note on why. "Who should read" becomes "who should listen". Chapters from the description, when present, are listed as hints. The user turn carries channel, title, date, duration, chapters, then the marked transcript. Bump READER_PROMPT_VERSION. A newsletter's request is unchanged apart from the version stamp.

Overview, stored (episode only; all keys optional on read)

overview: { novel_ideas: string[], evidence: string[], argument, who_should_read, further_reading: [],
            novel_idea_at: (int | null)[],   // seconds, aligned with novel_ideas

Model-facing schema (episode variant): novel_ideas / evidence are arrays of { text, at } and listen is an array of { at, title, note }, all required with additionalProperties: false. Acceptance criteria

  • A capture whose title is a bare YouTube video URL (each form in Behaviour) is typed Podcast by the sweep with no model call. A capture with other words, or a channel or playlist URL, goes to the model as before.
  • Podcast rows show the headphones glyph, and Classify as… offers Podcast only when YOUTUBE_API_KEY is set.
  • A childless podcast row is ready (green dot) and dispatches from the row menu and the bulk bar. Without the key its blocker reads youtube not connected.
  • Dispatch creates one waiting post per new video, deletes the items, and toasts "Sent N episode(s) to the Reader" linking /reader. A duplicate video is consumed without a second post and the toast says so.
  • A link with no video id, a private or removed video, or a live or upcoming stream is refused with a 409 naming the item, and nothing changes.
  • A waiting post shows the channel, running time, "YouTube", the awaiting transcript marker, Watch and Archive. It names the Mac's last-seen time once that is older than 30 minutes, and shows the Mac's error when the daemon reported one.
  • The daemon fetches English captions with yt-dlp, de-duplicates rolling auto-caption cues, and delivers them signed. The Worker stores the marked transcript and the next tick summarises it.
  • "No captions" becomes no transcript only after 24 h of hourly attempts. "Video unavailable" does so at once. A yt-dlp crash changes no post and is shown as the Mac's error.
  • A done episode's overview shows a timestamp chip on each bullet that has a valid time, a Worth a listen section of 0–6 items in time order, and "Who should listen". Times outside the episode never render.
  • Each chip and Watch link to youtube.com/watch?v=<id> (with &t=<s>s for a chip) in a new tab. Hotkey o opens Watch.
  • Wiki picks on an episode send bullet text exactly as on a post, and the chips sit outside the pick buttons.
  • An episode's model input is capped at READER_TEXT_CHARS, a newsletter's still at 150 000.
  • Newsletters, Instapaper articles and research posts render and summarise exactly as before, and all existing suites stay green.

Out of scope, risks & unknowns

  • Audio transcription, RSS and Apple podcasts, channel subscriptions, an in-app player: excluded by the owner (D5, D7). The /reader/transcripts contract would serve a future speech-to-text or managed-API producer unchanged.
  • The item's notes are dropped at dispatch. A post has no column for the owner's note, and personalising the prompt is an epic non-goal (ALF-232 D7). If the owner wants notes kept, that's a follow-up.
  • Non-English episodes come back "no transcript". Translation is not attempted.
  • Risk: yt-dlp breakage. YouTube's changes regularly break it until an update. Recent yt-dlp releases also want a JavaScript runtime (Deno) for full YouTube support, so check yt-dlp's current install notes at build time and document what's needed in daemon/README.md. The systemic-error path keeps this visible rather than silent.
  • Risk: YouTube rate-limits a home IP. At ≤ 3 videos per exchange and hand-picked volume this is unlikely. If it happens, it surfaces as a systemic error.
  • Unknown: whether videos.list's contentDetails.caption is worth using as an early hint. It reflects manual captions only, so it is not used to refuse a dispatch.
  • Unknown: the eval script (workers/scripts/reader-eval.ts) has no episode mode. Adding --episode <video-id> (it shells out to yt-dlp locally) is worthwhile if prompt iteration is needed, but it is not required for this story.

After it ships (for you)

  1. In the Google Cloud project you already use with fabric, make sure the YouTube Data API v3 is enabled. Create or reuse an API key restricted to that API, and set it as YOUTUBE_API_KEY in Vercel (Production), then redeploy.
  2. Generate one random secret. Set it on the Worker (wrangler secret put READER_TRANSCRIPTS_HMAC_SECRET) and in the Mac keychain: security add-generic-password -s alfred-reader-transcripts-hmac-secret -a alfred-daemon -w.
  3. On the Mac: brew install yt-dlp (plus whatever runtime its notes require). Add transcriptsUrl to the daemon's config.json, then reinstall the launchd agent (npm run install:launchd -w daemon).
  4. Capture one episode link, dispatch it, and confirm it reaches "summarising…" within ~10 minutes and then shows timestamps that open YouTube at the right moment.
  5. When a row says "Your Mac couldn't fetch it: yt-dlp failed", run brew upgrade yt-dlp.
