ALF-305 — Revamp the wiki landing page with a physics web and a concept of the day

/wiki opens on a concept of the day and a live physics web of your concepts and entities; sources and questions stay listed below it.

Decisions

  1. D1What the web opens on

    The concept of the day: pulled to the middle, glowing, its links and neighbours lit violet.

    One glance gives today’s idea and the ideas around it.

  2. D2How nodes and names look

    Dots sized by links (concepts filled, entities hollow); names only where lit or zoomed in.

    Up to 200 names can’t all be legible. Light what matters; zoom for the rest.

  3. D3What pointing and clicking do

    Hover lights a neighbourhood, click opens the page, drag pans, pinch or ⌘-scroll zooms.

    The landing gets you to a page. Plain scrolling still scrolls the page.

  4. D4Where the physics comes from

    Add d3-force; copy motivic’s sim, view and gestures into alfred, retuned for dots.

    Two repos, different nodes. A tuned copy beats a shared package.

  5. D5A graph view, despite ALF-259

    Yes. This ticket overrides the epic’s “no graph view”, and the epic doc stays as written.

  6. D6What /wiki shows

    Search, concept of the day, a web of concepts and entities, then the Sources and Questions lists.

  7. D7How the day’s concept is picked

    Rotation by date: the same concept all day, every concept before any repeat, no storage.

☞ open: your pick · → proposed: my call · ✓ settled: yours. Merging accepts every proposed row.

Not doing

Sources or questions in the web; a small graph on each page; remembering where you dragged nodes; picking or skipping the day’s concept.

  • Overrides ALF-259’s “no graph view” non-goal (D5). The epic document isn’t edited.

Working detail

Everything below is for the implementing agent. Approving needs only what’s above.

Context

The ticket. ALF-305, “Revamp the wiki landing page with a physics web and a concept of the day”, in epic ALF-259 (Wiki Module). The only note is “Borrow physics approach used in Motivic”. Alex answered four scoping questions in the refinement session:

  • Web nodes: concepts and entities. That option said sources and questions stay as lists below the web.
  • Today’s index: the web replaces the grouped lists; the search box stays on top, and typing swaps in today’s results. The full lists survive on the section views.
  • Daily pick: date-seeded rotation (D7).
  • Scale: 50–200 pages, today and in the coming months.

Read together, the first two answers give D6: the web takes the Concepts and Entities lists’ place on /wiki, and the Sources and Questions lists stay under it.

What exists today. The Wiki module is ALF-261’s read-only reading room (docs/specs/archive/ALF-261.html).

  • components/wiki/wiki-view.tsx routes by URL (wiki-route.ts). Both /wiki and /wiki/<section> render WikiIndexView: a search box over the pages grouped by section (WikiPageGroup + WikiPageRow). Typing swaps the groups for WikiSearchResults.
  • The store (lib/stores/wiki-store.tsx) seeds the index of every page: path, section, title, summary, tags, created/updated, and outbound links. That is enough to build the graph client-side, so no route, migration or Worker change is needed. Bodies load lazily and aren’t needed here.
  • The shell’s content column is max-w-3xl px-4 (components/shell/module-router.tsx): 736 px of content on desktop, 358 px on a 390 px phone.
  • There is no d3, no ResizeObserver hook, and no graph code in alfred. lib/use-prefers-reduced-motion.ts and lib/hooks/use-media-query.ts exist.

What motivic does (ac3charland/motivic, frontend/lib/web/*, frontend/app/web/*, docs/design-system/guidelines/10-motif-web.md):

  • simulation.ts builds a d3-force sim with link, many-body, a weak centring pull, a stronger focus pull (a force, not a pin, so a change of focus glides), collision, and bounds sized to the node count and shaped like the stage.
  • It draws from a seeded LCG via simulation.randomSource(), so the same input lands the same way every run.
  • It pre-rolls headless to α 0.3 before the first paint, then animates one tick per frame. Under reduced motion it settles fully before one paint. Its Storybook baselines rely on this: every story forces reduced motion.
  • A warm restart keeps positions by id. A new node starts beside what it links to.
  • The stage lives outside React (motif-web-stage.ts): each tick writes transforms and path data straight to registered DOM elements, so React renders nodes once.
  • view.ts fits all cards (never above 1:1); the view glides to its target until the player zooms or pans.
  • use-web-gestures.ts handles pointer and wheel: a press that moves over 4 px drags a card or pans empty stage, the click ending a drag never fires, and wheel or pinch zooms about the pointer.
  • Its nodes are 248×150 cards with a custom rectangle collision.

What the epic and spike said. ALF-259 §8 lists “No graph view (the spike’s reasons: an unseeded layout can’t pass the Storybook snapshot gate, and there aren’t enough pages yet)”. The spike (docs/spikes/llm-wiki-spike.html) deferred it with the trigger “≥30 pages, and a stated reason”. D5 records why both reasons are now answered. Per the launch prompt, the epic file is background and is not edited.

Decision records

D1What the web opens on · proposed

The concept of the day (D7) is the web’s focus, in motivic’s sense.

  • Pull: an extra centring force acts on it alone.
  • Bloom: its own links rest at about twice the normal length, and its collision radius is larger. Its neighbours sit out on a ring with room for their names. Without the bloom, a hub’s neighbours crowd within about 40 px, and their names overlap. The scratch runs behind Plate I showed this.
  • Paint: a violet halo and a bold name. Its edges and neighbours are violet and named at rest (P1 A).

The view fits every node (D10). So the focus lands near the middle, not exactly on it. Motivic’s fitViewAround centres the focus exactly, but it has to fit a box symmetric about the focus. For an off-centre focus that halves the zoom, and the whole-wiki overview is the point of a landing page.

Considered: a web with no focus, where the card and the web are unrelated. Also considered: exact centring via fitViewAround.

With no concept of the day (no concepts), the web has no focus, and nothing is lit at rest.

D2How nodes and names look · proposed

At 50–200 pages the fitted scale is about 0.5–0.8 on a 736 × 440 stage. Title cards (motivic’s treatment) would overlap, or shrink below legibility. So nodes are dots and names are shown selectively.

  • Constant screen size. Dots and names are not scaled by the view; only positions are. Zooming in spreads nodes apart while text stays 12 px, and a 358 px phone fit doesn’t shrink dots to specks.
  • Dot radius = clamp(3 + 1.5·√degree, 3, 9) px, where degree = distinct neighbours in the web (D8).
  • Kind: a concept is a filled dot and an entity is a 1.5 px ring. At rest both are muted-foreground. Violet belongs to the lit neighbourhood, so it keeps meaning “related to what you’re looking at”. A second hue for entities would clash with the module-colour system (MODULE_ACCENT).
  • Edges are straight 1 px muted-foreground lines at 28% opacity, trimmed 2 px short of each dot. Lit edges are 1.5 px violet at 70%. There are no arrows: wiki links are drawn undirected (D8).
  • Names are 12 px Geist, muted-foreground, drawn with a 3 px surface-coloured halo (paint-order: stroke) so a name stays legible over edges. The focus’s name is 13 px semibold foreground. The hovered node’s name is medium foreground. Which names show, and where, is D9.
  • One line under the stage, outside it so that nothing zoomed runs beneath it, holds the legend at left (“● Concept ○ Entity”, 12 px muted) and a hint at right (muted/70). The hint reads “Pinch or ⌘-scroll to zoom · drag to pan” on a fine pointer, “Pinch to zoom” on a coarse one.

Considered: title pills for every node (they don’t fit at this scale), and colour-coding entities (it clashes with module hues).

D3What pointing and clicking do · proposed

  • Hover (or keyboard focus, D12) lights a node’s neighbourhood (P1 B). The node gets a foreground fill or ring plus a 50% ring 5 px out. Its neighbours turn violet and show their names, and its edges turn violet. Everything else dims: dots to 30% opacity, edges to 10%. The day’s concept keeps its halo and name. Leaving the node restores the resting state.
  • Click opens the page through ViewLink (pushState). The node is a real <a href>, so ⌘/Ctrl-click and middle-click open a new tab.
  • Drag works like motivic’s: a press on a node that moves past 4 px drags it with a mouse or pen. Its neighbours follow, it isn’t pinned when released, and the click that ends a drag never navigates. A press on empty stage that moves pans the view. A click on empty stage does nothing, since there is no focus to clear.
  • Zoom with a trackpad pinch (browsers send it as wheel + ctrlKey), ⌘/Ctrl + wheel, or a two-finger touch pinch. It zooms about the pointer. A plain wheel is not captured: it scrolls the page, because /wiki scrolls. This departs from motivic, whose page never scrolls, and is the “cooperative gestures” pattern that embedded maps use.
  • Touch: the stage sets touch-action: pan-y. One finger scrolls the page through the web, a tap opens a node, and two fingers pinch and pan the web. Dragging a node is pointer-only.

Considered: motivic’s click-to-focus, which re-centres the web on the clicked node and swaps the card. It turns the landing page into an explorer, and each page already shows its own links and backlinks.

D4Where the physics comes from · proposed

Add d3-force@^3 and @types/d3-force to frontend/, the same versions motivic uses. d3-force pulls in d3-quadtree, d3-dispatch and d3-timer: about 17 kB minified, 7 kB gzipped. Nothing else from d3 is needed: zoom and pan are the ported gesture code, not d3-zoom.

Port motivic’s modules by copying and adapting them, keeping their structure, names and doc-comment voice so a reader of both repos recognises them:

  • The seeded LCG.
  • createWebSimulation / prerollSimulation / settleSimulation / positionsOf and the warm-start placement.
  • forceBounds (ported and made circle-aware).
  • fitView, glideTo, toWorld, zoomAt, wheelZoom, pinchView, movedPastThreshold, and revealCard as revealNode.
  • The stage object (outside React, writing to the DOM each tick).
  • The gesture hook.

Drop the rectangle collision: dots are circles, and d3’s own forceCollide fits (and is quadtree-backed, unlike the O(n²) rectangle pass). Drop the arrowed wirePath in favour of trimmed lines.

Considered: a shared npm package or a git dependency on motivic’s code. The repos have different stacks and release cadences, and their nodes differ (dots vs cards). Coupling two repos for about 600 lines isn’t worth it.

  • Size: at 50–200 pages the wiki is past the spike’s ≥30-page trigger.

The epic document is not edited (launch-prompt instruction). This record is where the override lives.

D6What /wiki shows · settled

Top to bottom:

  1. the header (unchanged);
  2. the search box (unchanged);
  3. the concept-of-the-day card (D7, D11);
  4. a “Concepts & entities” group, headed like the other groups with its node count, holding the web;

The Sources and Questions groups are today’s WikiPageGroup + WikiPageRow lists, unchanged. Typing in the search box replaces items 3–6 with WikiSearchResults, as it replaces the groups today (P1 D). The section views /wiki/concepts etc. and the nav are unchanged, so every concept and entity is still one click away as a list.

D7How the day’s concept is picked · settled

The rotation is least recently featured, replayed. It is a pure function of the page index and the local date, so it needs no storage, and every device agrees.

  • Candidates are the concept pages (section === 'concepts'). Entities are never picked.
  • A concept joins the rotation the day after its created date. So a page that syncs mid-day never changes that day’s pick. A concept with a missing or malformed created counts as having always existed.
  • Exception: on a day when no concept qualifies (the wiki’s first day, or every created is in the future), every concept qualifies.
  • Each day’s pick is the qualifying concept featured longest ago; one never featured goes first. Ties break on a 32-bit FNV-1a hash of `${date}|${path}`, lowest first.
  • The replay runs day by day from the earliest created date among the concepts to today, recording each day’s pick. Today’s pick is the answer.

Properties:

  • For a fixed set of n concepts, any n consecutive days show each exactly once.
  • A new concept is featured before any concept repeats. It usually appears the day after it syncs.
  • The pick is the same all day.

Accepted weakness: renaming or deleting a concept rewrites the replayed history, and can change the pick on the day it syncs.

“Today” is the local calendar date, alfred’s convention (todayISODate), read from the ticking useNow clock, so a tab left open rolls over at midnight. Implement the replay as a queue. Each day features exactly one concept, so featured dates are unique, and only never-featured concepts can tie. Keep the featured concepts oldest-first in a queue. Keep the qualifying never-featured ones in a set, fed from the concepts sorted by created. Each day, take the set’s lowest hash if the set is non-empty, otherwise the queue’s head, and push the pick to the tail. The refinement prototype matched a naive replay day for day and ran ten years × 200 concepts in about 17 ms; the naive pool-scan took about 550 ms. Memoise on (pages, date).

Considered, and rejected because it misses Alex’s pick: a per-cycle shuffle, shuffle(concepts, seed = ⌊day ÷ n⌋)[day mod n]. It is simpler, but any change in n reshuffles, so an ingest mid-day changes the day’s concept and can repeat one early.

Implementation decisions

D8 · The graph

  • Nodes: every page with section in {concepts, entities}, in index order (sortWikiPages). The order matters for determinism: d3 assigns initial spiral positions by array index.
  • Edges: for each node, each of its links that names another node. Self-links, links to pages not in the snapshot, and links to sources or questions are dropped.
  • Direction is discarded: A→B and B→A are one edge, keyed min(path)|max(path).
  • Degree is the number of distinct neighbours.
  • A node with no edges is still drawn. The bounds and centring pull keep it on the stage.

D9 · Which names show, and where

Candidates, highest priority first:

  1. the focus;
  2. the hovered or keyboard-focused node;
  3. the lit node’s neighbours;
  4. once the view scale is ≥ 1 (1:1 with the world), every node on the stage.

Placement:

  • A neighbour’s name sits outward from the lit node, just past its dot on the far side. It is anchored start when it lies to the right (unit x > 0.35), end to the left, and centred otherwise.
  • Every other name sits centred under its dot.
  • A name that would cross the stage’s side is nudged back inside.
  • Greedy culling: names are placed in priority order, then by degree (descending), then by path. A name whose box overlaps one already placed is hidden. The focus’s name is never hidden.

Name widths are measured once per node, since names are screen-constant. Culling reruns on each paint while a label set is showing. P1 A, C and E show culling at work: on the phone, “Retrieval practice” gives way to “Forgetting curve”. Names are truncated at 28 characters with “…”. The full title is the link’s accessible name.

View: screen = world × scale + (x, y), applied by writing each node’s translate() and each edge’s endpoints. The canvas is not CSS-scaled, because dots and names are screen-constant (D2).

  • The view follows the fit of all nodes, gliding by the glide share each frame and snapping on the first paint, until the user zooms or pans.
  • From then until the page set changes or the window resizes, it holds, and a Fit IconButton (neutral, md, lucide Maximize, aria-label="Fit the web") shows at the stage’s top-right (P1 C). Pressing it hands the view back to the fit.
  • Stage height: 440 px, or 320 px below the sm breakpoint.

D11 · The card

  • Frame: SurfaceCard’s frame (rounded-lg, border, bg-surface, p-4), with the border at accent-violet/30 and glow-violet.
  • Top row: the “Concept of the day” eyebrow (eyebrowClass) with the date right-aligned, e.g. “Wed, Sep 30”, text-xs muted.
  • Title: font-serif text-2xl. It is a ViewLink made a stretched link (after:absolute after:inset-0), so the whole card clicks through while the link’s name stays the title.
  • Summary: text-sm muted, omitted when empty.
  • Tags: Badge variant="muted", omitted when there are none.
  • The card is a <section aria-labelledby> named “Concept of the day”.
  • Hover: the border goes to accent-violet/60, with motion-reduce:transition-none.
  • No card is rendered when there are no concepts.

D12 · Keyboard and screen readers

The web is one tab stop, using a roving tabindex, so a 150-node web doesn’t put 150 stops before the Sources list.

  • Tabbing in lands on the focus, or on the first node when there is no focus.
  • Moving: ←/↑ go to the previous node and →/↓ to the next, in index order. Home and End go to the first and last. Enter opens the page (native link activation).
  • Focused node: it is lit like a hover (D3), wears the app’s focus-visible:ring-2 ring-ring round its dot, and is revealed if the view clips it (motivic’s reveal).
  • Structure: the stage is role="group", labelled by the group heading. A visually hidden hint follows it: “Use the arrow keys to move between pages.”
  • Names: each node is a link whose accessible name is the full title, plus a visually hidden “, concept” or “, entity”.
  • The legend and the gesture hint are aria-hidden.

D13 · Motion

  • First paint pre-rolls to α 0.3 headless, then the web relaxes into place, one tick per frame, until d3’s α floor.
  • A refresh that changes the node or edge set starts a warm sim from current positions (motivic’s startingPositions) and hands the view back to the fit.
  • Hover and dim changes are instant: no transition, because a 100-dot fade stutters.
  • Reduced motion (usePrefersReducedMotion, or a reducedMotion prop threaded WikiView → landing → web for stories and tests) settles the sim fully before a single paint, with no glide. A drag moves only the held node until release, then the rest jump. This is motivic’s reduced path unchanged.
  • While the search box holds a query, the web is unmounted. Clearing it re-lays the web from scratch, and because the sim is seeded it comes back identically, apart from any nodes you dragged.

Order of work and subagents

Follow the implement-spec skill. The lead (strongest model) builds the foundations alone: the dependency, graph.ts with its types, forces.ts, wikiWebFixtureSet, the WikiSearchable extraction, and the WikiView → WikiLandingView shell rendering placeholder slots. Then it dispatches mid-tier subagents on disjoint files:

  • Batch 1, in parallel.
    • A · Concept of the day: concept-of-the-day.ts and concept-of-the-day-card.tsx with tests. It must not touch lib/wiki/web/.
    • B · Web physics (pure): bounds.ts, simulation.ts, view.ts, labels.ts and use-element-size.ts, with tests. No React components.
  • Batch 2, after B. C · Web component: components/wiki/web/*, with tests and component stories, against B’s API.

Acceptance criteria

  • On /wiki, top to bottom: header, search box, concept-of-the-day card, “Concepts & entities” group with its count and the web, Sources list, Questions list. The Concepts and Entities lists are no longer on /wiki.
  • Typing a query replaces the card, web and lists with the existing search results. Clearing the query restores them.
  • The /wiki/concepts, /wiki/entities, /wiki/sources and /wiki/questions views, the nav, ⌘K and ⌘P behave as before.
  • For a given page index and local date, conceptOfTheDay always returns the same concept.
  • For a fixed set of n concepts, any n consecutive days feature each concept exactly once.
  • Adding a concept whose created is today doesn’t change today’s pick (except on the wiki’s first day), and it is featured before any concept repeats.
  • Entities are never picked. With no concepts, there is no card.
  • The card shows the eyebrow, the date, the title, the summary (if any) and the tags (if any). Clicking anywhere on it opens the page. Its link’s accessible name is the title.
  • The web draws exactly the concept and entity pages, and one undirected edge per linked pair among them. Links to sources, questions, missing pages or itself are not drawn.
  • At rest, the day’s concept wears the violet halo and its bold name. Its edges and neighbours are violet, and its neighbours are named. No other node is named at rest below 1:1.
  • Concepts are filled dots and entities are rings, sized by degree. Dots and names keep their screen size at every zoom.
  • Hovering a node lights it, its edges and its neighbours, names them, and dims everything else. Leaving restores the resting state.
  • Clicking a node opens its page in-app. ⌘/Ctrl-click opens it in a new tab. The click that ends a node drag does not navigate.
  • Dragging a node moves it and its neighbours follow. Dragging empty stage pans. A plain wheel scrolls the page and never zooms. Pinch and ⌘/Ctrl + wheel zoom about the pointer.
  • On touch, a one-finger vertical swipe over the web scrolls the page, a tap on a node opens it, and a two-finger pinch zooms the web.
  • From scale 1 up, every node on the stage is named. Overlapping names are culled by priority, and the focus’s name is never culled.
  • After a zoom or pan, a “Fit the web” button appears top-right. Pressing it returns the view to the fit, and the button disappears.
  • On first paint every node is inside the stage. The stage is 440 px tall, or 320 px on a phone, and nothing on the page is wider than a 390 px screen.
  • The web is a single tab stop. Arrow keys, Home and End move between nodes, lighting each like a hover and bringing it into view. Enter opens the page.
  • With reduced motion the web appears settled in one paint and never glides. Otherwise it relaxes into place after a near-settled first paint.
  • The same pages lay out identically on every run (seeded), so the Storybook baselines are stable in the Docker gate.

Out of scope, risks & unknowns

  • Sources and questions in the web: Alex chose concepts and entities. A concept linked only through a source can therefore look isolated. The cheap later fix is co-citation edges (two pages citing the same raw/ source), a derived edge type this spec deliberately doesn’t add.
  • A local graph on each page, stored positions, and skip or re-roll for the day’s concept are each a follow-up if wanted. D7 has no storage, so a skip would need some.
  • Risk: label legibility at 200 nodes. Culling keeps names from overlapping, but a dense core can still cull most neighbour names at rest. If that happens in the real wiki, raise focusLinkDistance before adding machinery.
  • Risk: cooperative touch gestures. If a finger starts a vertical pan before the second lands, the browser owns the gesture and the page scrolls. That is the accepted behaviour of the pattern. Verify on an iPhone, not only in Playwright’s emulation.
  • Risk: performance. 200 nodes and about 300 edges written each frame is within what motivic does per card. d3’s Barnes–Hut and quadtree collision are O(n log n). If frames drop, stop writing names that are hidden.
  • Unknown: whether the live pages carry created. Check with npm run psql -w database -- -c "select count(*) filter (where created is null), count(*) from wiki_pages where section = 'concepts'". If most are null, D7 degrades to “always existed” for them: still a full rotation, but a mid-day sync of such a page can change the pick. Say so in the PR if it applies.
  • Unknown: the real degree distribution. The sample’s hubs have 6–7 links. A wiki whose focus has 20 neighbours needs the bloom retuned. The constants live in one file for that reason.
