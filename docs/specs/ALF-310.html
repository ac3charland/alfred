ALF-310 — Record session metrics from hooks

Every alfred cloud session writes its own code_sessions row as it runs: the prompt exactly as sent, the commit it started on, tokens, subagents and cost.

Revised 2026-09-30: D1 → priced from Anthropic’s pricing page, folded in with a subagent plan; D5 → split out (your review).

Decisions

  1. D2Which sessions record themselves?

    Cloud sessions on alfred only. Local sessions silently skip.

    The ledger keys on session_… ids, and local sessions have none.

  2. D3When does the hook write?

    Once at session start (the starting commit), then at the end of every turn.

    Cloud containers are reclaimed, never ended; there’s no final moment.

  3. D4Who wins when hook and backfill disagree?

    The hook, for what it records; the backfill fills only what the hook can’t see.

    Extends ALF-309 D4’s recorded-wins rule from the prompt to the whole row.

  4. D1Where does a recorded row’s cost come from?

    alfred prices tokens from Anthropic’s pricing page, re-read on the Comms sweep’s daily tick.

  5. D5What fills PR outcome for new sessions?

    Not this story: a separate ticket tracks what happens after the session.

  6. D6Which prompt is stored?

    The first message exactly as sent. It permanently beats a rebuilt one.

  7. D7Which new metrics?

    Subagent count, plus tokens per model for the main thread and for subagents.

☞ open: your pick · → proposed: my call · ✓ settled: yours. Merging accepts every proposed row.

Not doing

No ledger screen, no local sessions, and nothing after the session idles: PR outcomes and bug tracing are a separate ticket.

Heads-up

  • Ships after ALF-309 is live and reuses its LEDGER_API_KEY credential; nothing new to mint.
  • Each turn’s end waits up to 5 s for one write; failures are only logged locally.
  • Costs appear at the first daily price fetch after deploy; earlier sessions are priced then.

Working detail

Context

The ask. ALF-309 (docs/specs/ALF-309.html, implementation in flight) seeds code_sessions from history and leaves forward recording to “a follow-up story, a Claude Code hook”. This is that story. Build on ALF-309 as merged. If its migration, routes or CLI landed under different names, follow what landed; the rules here still apply.

The owner’s answers in refinement:

  • Record the actual prompt sent, not a rebuilt one (D6).
  • Also record subagent count and tokens (D7).
  • On cost, the owner expected the transcript to carry it, as ALF-309’s hand-off said. It doesn’t (see below), so alfred prices the recorded tokens itself (D1).

Verified in this refinement session (a cloud session, CLI 2.1.x, Node 24.21):

  • Session id. CLAUDE_CODE_REMOTE_SESSION_ID=cse_01Sfqpa… and the session link session_01Sfqpa… share their suffix. The ledger id is "session_" + id.slice("cse_".length). CLAUDE_CODE_REMOTE=true is also set.
  • Transcript. The file is ~/.claude/projects/<cwd-slug>/<uuid>.jsonl, and the hook’s stdin carries its path as transcript_path. Each type:"assistant" entry carries message.model, message.id, requestId, effort, isSidechain:false and message.usage: input_tokens, output_tokens, cache_read_input_tokens, cache_creation_input_tokens, and cache_creation.{ephemeral_5m_input_tokens, ephemeral_1h_input_tokens}. One API response is written as several entries (one per content block), each repeating the same usage, so a naive sum overcounts.
  • No cost field. Across 27 assistant entries and one completed turn there was no totalCostUSD, costUSD or cost_usd. The only entry written at turn end was system/stop_hook_summary. ALF-309’s “cost-state entries” claim does not hold for this CLI. Hence D1.
  • Subagents. A subagent writes its own transcript at <transcript_path minus .jsonl>/subagents/agent-<id>.jsonl, with a .meta.json beside it. Its entries are isSidechain:true and carry their own model (claude-haiku-4-5-20251001 in the probe). The main transcript carries none of their usage.
  • Prompt. The first type:"user" entry is the launch prompt verbatim, starting with ALF-310: ….
  • Stop hooks fire in cloud sessions. The environment already runs a user-level ~/.claude/stop-hook-git-check.sh, and the project hook runs alongside it.
  • Proxy. Outbound HTTPS goes through HTTPS_PROXY, which Node’s built-in fetch ignores unless NODE_USE_ENV_PROXY=1 is set (Node ≥ 22.21). Without it, the proxy-injected credential never gets attached.
  • Clone. The clone is shallow (about 730 commits here). That’s enough to find the last links.ts change, but no hook may unshallow it.

Pricing, verified in refinement:

  • Precedent. The owner’s menu-bar usage widget (ac3charland/claude-usage-menu-bar, Sources/ClaudeUsageCore/PricingFetcher.swift and PriceHistory.swift, with Tests/…/PricingPageParserTests.swift) prices transcript tokens from Anthropic’s public pricing page. D1 and D14–D16 port it.
  • The page. https://platform.claude.com/docs/en/about-claude/pricing.md is served as markdown, and it’s reachable from a cloud session (200, 48 KB, 0.7 s). Its model table has six columns: base input, 5m and 1h cache writes, cache hits, and output, all in $n / MTok.
  • The cron. workers/wrangler.toml uses four of the account’s five cron triggers. The daily 17 9 * * * (RETENTION_CRON) already runs three isolated units in workers/src/index.ts, each awaited and logged on one line.
  • Hard-coded prices go stale. The anthropic-api skill lists Sonnet 5 at $3/$15 against the page’s $2/$10. workers/scripts/reader-eval.ts matches prices by prefix, so it bills Opus 5.5 at Opus 5’s rates.

What exists after ALF-309: code_sessions and upsert_code_sessions (recorded-wins for prompt, prompt_source, builder_sha and base_sha); POST /api/code/sessions; validateLedgerKey/resolveLedgerClient in frontend/lib/api/auth.ts; and the tools/session-ledger workspace with git.ts (blob lookup) and replay.ts (the skills regex). .claude/settings.json holds only enabledPlugins today.

Decision records

D1Where does a recorded row’s cost come from? · settled

Cost is computed in alfred: never in the hook, never from a committed table. The owner’s menu-bar widget is the model. It fetches Anthropic’s pricing page as markdown, parses its model table, keeps a dated history, and prices usage at the rates in effect when it happened. alfred ports that as D14 (the history), D15 (the parser) and D16 (the refresh and re-pricing). The hook sends tokens only, and record_code_session prices usage_by_model at session_created_at on every write.

Where this departs from the widget:

  • No built-in fallback table (the owner’s call). The history starts empty, and the first fetch’s rates apply back to every earlier session (D14’s launch-price rule), so nothing stays unpriced past the first tick.
  • Refresh on the Worker’s daily retention tick instead of a poll-driven isDue check. alfred has no poller, and the owner chose to share the tick rather than spend the last cron slot.
  • Only a -YYYYMMDD suffix is normalised away. Any other suffix, such as /fast, stays unpriced. The widget prices it at standard rates, but fast mode costs double.

Considered: a committed per-model table (it goes stale silently; see Context); fetching inside each session’s hook (it puts the fragile parser into silent code in every session); fetching from the record route when stale (no cron, but the owner preferred the shared tick).

D2Which sessions record themselves? · proposed

The hook runs only when CLAUDE_CODE_REMOTE_SESSION_ID starts with cse_ and ALFRED_BASE_URL is non-empty. ALFRED_BASE_URL is set only in the alfred cloud environment (ALF-309’s after-ship step), so it is the switch. Otherwise the hook exits 0 before reading anything. That covers local sessions, other environments, and forks that clone the public repo. The hook can’t tell whether the proxy credential exists, since it’s invisible by design; a 401 is logged like any other failure (D12). Considered: recording local sessions under a synthetic id. get_session can’t see them, the backfill could never join them, and they are not what the ledger evaluates.

D3When does the hook write? · proposed

SessionStart with matcher startup captures git rev-parse HEAD as base_sha before the session changes anything; that’s the real start commit, where ALF-309 D2 can only approximate it. It then writes the row’s first version. Stop fires at the end of every main-thread turn and rewrites the usage columns from the transcripts. Every write is the whole picture so far, so a missed write is healed by the next one. SessionEnd isn’t used because containers are reclaimed without ending. SubagentStop isn’t needed, because the next Stop re-reads every subagent transcript. The only thing that goes unrecorded is a background subagent that finishes after the last turn. Considered: UserPromptSubmit for the prompt. Its input carries prompt directly, but whether it fires for a cloud session’s launch prompt is unverified, while the transcript path is verified.

D4Who wins when hook and backfill disagree? · proposed

Columns fall into four ownership classes, listed in Behaviour. What the session observed first-hand beats what the backfill reconstructs: the prompt, the start commit, skills, usage, subagents and cost. The platform wins on what it owns: session_created_at, model, effort_level and ref (from the PR block). The hook fills those only while they’re null. Two RPCs enforce the split, so no client can bypass it: the new record_code_session, and an amended upsert_code_sessions. Without the amendment, ALF-309’s <every column> = excluded.<col> would null the hook’s new columns on every backfill run, because a backfill row doesn’t carry them. Considered: last-writer-wins (the two sources flip the row back and forth); a separate recorded_sessions table (every reader would join two tables and pick per column).

D5What fills PR outcome for new sessions? · settled

The owner’s scope rule: this story captures what’s hard to reconstruct later, meaning what only the running session can see. Everything that happens after the session goes idle is a separate ticket: PR merges, human rework, bugs traced back to the session that shipped them. The hook writes nothing about PRs. pr_*, launch_lane, spec_path/spec_blob_sha, human_commits_after_open, title, status and session_record stay class 4, filled by ALF-309’s backfill whenever it runs until that ticket ships. D4 makes that re-run safe against recorded data.

This corrects ALF-309’s “once it ships, this backfill is needed only for history”: that becomes true when the follow-up ticket lands, not with this story. A lead for that ticket: alfred’s webhook Worker (workers/src/index.ts, transitions.ts) already receives every pull_request event, including closed with merged, and parses the PR body. So it could write outcomes at merge time, through its own RPC following the same ownership table.

D6Which prompt is stored? · settled

The owner asked for the prompt as actually sent. It is the text of the first main-thread type:"user" entry that isn’t isMeta and isn’t a tool_result. That’s a string message.content, or its text blocks joined with \n. It is stored verbatim with prompt_source = 'recorded', and it includes any edits the owner made before sending. skills are derived from it with ALF-309 D12’s regex, with blobs at the recorded base_sha. ref is the prompt’s leading ^[A-Z]+-\d+, when the row has none. The first recorded write freezes prompt, prompt_source and skills; later user messages are never recorded.

D7Which new metrics? · settled

This story adds three columns. subagent_count is the number of subagents/agent-*.jsonl files. usage_by_model (jsonb) breaks usage down as {main: {<model>: U}, subagents: {<model>: U}}, where U = {requests, input, output, cache_read, cache_write_5m, cache_write_1h, web_search}. recorded_at holds the last hook write. The existing token columns hold whole-session totals, main thread plus subagents, and the subagent share is read from usage_by_model. Whether get_session’s totals include subagents (ALF-309’s open question) is settled for free after it ships: the two sit side by side in the same row.

Implementation decisions

D8 · The hook lives in tools/session-ledger/src/hook/ and imports only Node builtins

It shares ALF-309’s workspace, and with it the LedgerRow types, the skills regex and the blob lookup, so check:fast covers it without a new package. The hook runs from a session’s shell, where a missing node_modules must degrade to a silent no-op rather than a crash, so every module it reaches imports only node:* or relative paths. An ALF-309 module that imports an npm package gets its builtin-only half split into its own file. A unit test walks the import graph from hook/cli.ts and fails on any bare specifier. Node runs the .ts directly, as tools/showboat does.

D9 · Transcript reading

  • Parse the file line by line and skip unparseable lines; the file may be mid-write.
  • Usage: keep one usage per message.id (the last seen) among type:"assistant" entries. Do this separately for the main file and for each subagent file.
  • cache_write_tokens = cache_creation_input_tokens. Split it into 5m/1h from cache_creation when present, otherwise count it all as 5m.
  • web_search counts message.usage.server_tool_use.web_search_requests. It’s recorded but not priced, because the page’s model table has no search rate.
  • served_model is the last main-thread assistant message.model. model (filled only while null) is the first one.
  • effort_level (filled only while null) is the last main-thread entry’s effort, falling back to the CLAUDE_EFFORT env var.
  • session_created_at (filled only while null) is the first transcript entry’s timestamp.
  • A subagent file that can’t be read adds subagents_unreadable, and the rest still count.

D10 · Start capture and the state file

At SessionStart the hook resolves base_sha = git rev-parse HEAD, builder_sha = git log -1 --format=%H HEAD -- frontend/lib/code/links.ts (null if not in the shallow history), and repo from git remote get-url origin, normalised to owner/name. It writes them to os.tmpdir()/alfred-session-ledger/<session_id>.json, then posts {event: 'session-start', …}. Stop reads the state file to resolve skill blobs at base_sha. If the file is gone (a container re-provisioned mid-session), Stop sends no skills or base and adds start_unrecorded, and the backfill’s reconstruction fills them (D4, class 2).

D11 · The write path

POST /api/code/sessions/record takes one RecordedRow, zod-validated with unknown keys rejected. Auth is LEDGER_API_KEY or the owner’s session, via ALF-309’s resolveLedgerClient; INGEST_API_KEY is rejected. The route calls record_code_session(p_row jsonb). The hook reuses ALF-309’s key through the same proxy credential. Every alfred cloud session already carries that credential once ALF-309’s after-ship step is done, so this story widens no access; it only exercises it. The hook sends Authorization itself only when a LEDGER_API_KEY env var is set (ALF-309 D1’s fallback).

D12 · The hook never blocks, never talks

  • It always exits 0, including on a thrown error, and never exits 2, which would block a Stop.
  • It writes nothing to stdout or stderr. SessionStart stdout is injected into the session’s context.
  • The fetch gets AbortSignal.timeout(5000), and the settings timeout is 10 s for start and 15 s for stop.
  • A failure appends one line to os.tmpdir()/alfred-session-ledger/hook.log: ISO time · event · session_id · HTTP status or error name. Never headers, never bodies.
  • There are no retries; the next Stop is the retry.

D13 · Monotonic usage

If a resumed container ever restores a shorter transcript, the recount would go backwards. record_code_session updates the usage group (token columns, subagent_count, usage_by_model, served_model) only when the incoming output_tokens ≥ the stored one. Otherwise it keeps the stored group and adds transcript_regressed. cost_usd is then recomputed from whatever usage is stored.

D14 · The price history

model_price_history holds one row per distinct price table: effective_from (the fetch time, primary key), fetched_at, source (the page URL), and rates jsonb shaped {<model id>: {name, in, cw5m, cw1h, read, out}} in USD per MTok, the widget’s keys. Each row is the whole table: a fetch is merged over the latest entry, so a model missing from one fetch keeps its last rates and models are never dropped. A new row is written only when some rate changed.

Lookup. model_rates(model, t) first normalises the id by stripping a trailing -\d{8}. It then reads the entry in effect at t, meaning the last one with effective_from ≤ t. If that entry lacks the model, it takes the earliest later entry that has it, so a model’s launch price applies back to its first use. If no entry prices the model, the result is null, never a guess. code_session_cost(usage_by_model, t) sums in·input + cw5m·cache_write_5m + cw1h·cache_write_1h + read·cache_read + out·output ÷ 106 over every model in main and subagents, and is null if any model is unpriced.

D15 · The page parser

workers/src/pricing/page.ts ports PricingPageParser as a pure function of the markdown and the set of known ids:

  • Find the table whose header is exactly Model | Base input tokens | 5m cache writes | 1h cache writes | Cache hits and refreshes | Output tokens.
  • Clean each model cell: strip <sup> markers, reduce links to their text, and drop parentheticals such as “(retired, …)”. Derive the id by lowercasing and turning spaces and dots into hyphens, so “Claude Opus 5.5” becomes claude-opus-5-5.
  • Every price cell must match ^\$n(.n)? / MTok$ once footnotes are stripped.
  • Every row must satisfy cache read < input < 5m write < 1h write, and input < output.

A fetch is rejected on a missing header, a malformed cell, an ordering violation, fewer than 5 rows, or more than half the known models missing. A rejected fetch changes nothing. Port the widget’s fixture (the live table of 2026-09-24) verbatim as workers/src/pricing/__fixtures__/pricing-2026-09-24.md. It’s public data.

D16 · Refresh and re-pricing

runPriceRefresh(env, now) is a fourth isolated unit on RETENTION_CRON. It goes after the two retention units and before the wiki sync, with its own try/catch, awaited like the others. It works in four steps:

  1. Fetch the page with a plain GET: no Authorization header, no cookies, Accept: text/markdown, 10 s timeout.
  2. Read the latest entry’s model ids over Supabase REST as the known set.
  3. Parse (D15).
  4. Call append_model_prices(p_rates, p_source). It merges, appends if anything changed, then re-prices every recorded row (recorded_at is not null), setting cost_usd and adding or dropping price_unknown.

Re-pricing everything is deliberate: the cost is a pure function of stored usage and the history, so it’s idempotent and cheap at hundreds of rows. The unit logs exactly one line per run (Plate II). A failed day is not retried; the next tick is the retry.

Behaviour

Per event

  1. Gate (D2). No cse_ id, or no ALFRED_BASE_URL: exit 0.
  2. session-start (D10): capture the start state, write the state file, and post {event, session_id, repo, base_sha, builder_sha, session_created_at: now}.
  3. stop (D9): read stdin’s transcript_path, count the main and subagent transcripts, and post the usage group. Also post the prompt, skills and ref, frozen server-side after their first write. Never post a cost; alfred prices the usage (D1).
  4. Daily tick (D16): refresh the price history and re-price every recorded row.

Warnings. The recording codes are start_unrecorded and subagents_unreadable (sent by the hook), plus transcript_regressed and price_unknown (set by the RPCs). They are listed once in a SQL function code_session_hook_warnings(). Each RPC replaces only its own codes: record_code_session sets (stored − hook codes) ∪ incoming, and upsert_code_sessions sets incoming ∪ (stored ∩ hook codes), both sorted and deduplicated. transcript_regressed sticks once set.

Order independence. The final row is the same whether the backfill runs before, between or after hook writes. The SQL tests pin all three orders.

Acceptance criteria

  • Without a cse_ id or ALFRED_BASE_URL, the hook makes no fetch, reads no transcript, prints nothing and exits 0.
  • A thrown error, a network error, a timeout or a 401 each exit 0 with empty stdout/stderr and append one log line that holds no header or body.
  • The import-graph test passes: hook/cli.ts reaches only node:* and relative modules.
  • session-start posts HEAD as base_sha, the last links.ts commit as builder_sha (null when absent from the history), and repo as owner/name, and writes the state file.
  • The prompt is the first non-meta, non-tool-result main-thread user entry, verbatim, for both string and text-block content. skills and ref derive from it.
  • Usage dedupes by message.id. Totals include subagents; usage_by_model splits main from subagents by model; subagent_count counts agent files; an unreadable agent file adds subagents_unreadable.
  • The hook never sends a cost, and RecordedRow rejects cost_usd. record_code_session sets cost_usd = code_session_cost(usage_by_model, session_created_at); any unpriced model gives null plus price_unknown, with tokens intact.
  • The ported fixture parses to 18 models whose rates match the page. A missing header, a malformed price cell, an ordering violation, fewer than 5 rows, or more than half the known models missing each reject the fetch and leave the history unchanged.
  • Identical rates append nothing. One changed price appends one entry. A model absent from a fetch keeps its last rates.
  • A lookup uses the entry in effect at t. A model first priced later gets its launch price. claude-haiku-4-5-20251001 prices as claude-haiku-4-5, while claude-opus-5-9 (not claude-opus-5) and claude-opus-5-5/fast are unpriced. Cost matches a hand-computed fixture to 6 decimals across all five token classes.
  • After an append that adds a model, every recorded row using it is priced and loses price_unknown. Rows with recorded_at null (backfill-only) are never re-priced.
  • On RETENTION_CRON, a price unit that throws logs its line and the other three units still run, and vice versa. Each run prints exactly one model prices: line in Plate II’s form for appended, unchanged and rejected.
  • The page fetch is a GET with no Authorization header, no cookies and a 10 s timeout.
  • A missing state file at stop sends no base or skills and adds start_unrecorded.
  • The route accepts LEDGER_API_KEY and the owner session; it rejects INGEST_API_KEY, a wrong key and no auth with 401; it rejects unknown keys, a malformed id and a non-hook warning code with 400.
  • The final row is identical for backfill-before, -between and -after hook writes. The backfill never changes class 1 on a recorded row, nor class 2 once recorded; the hook never changes class 4 and fills class 3 only while null.
  • A second stop with a different first message leaves the stored prompt and skills unchanged.
  • A stop with fewer output_tokens than stored keeps the stored usage group and adds transcript_regressed.
  • Warnings merge per the rule. Neither RPC drops the other’s codes.
  • A settings test asserts both hooks point at an existing file, set NODE_USE_ENV_PROXY=1 and carry the timeouts, and that SessionStart matches startup only.
  • No transcript content, ledger data or key is committed. Fixtures are invented but shaped like the verified entries in Context.

Out of scope, risks & unknowns

  • Out:
    • A ledger screen.
    • Post-session tracking of PR outcomes, rework and escaped bugs (D5’s separate ticket).
    • Recording later user messages or steering counts.
    • Local sessions (D2).
    • Pricing web searches, which are counted in U.web_search but have no rate in the page’s model table.
    • Moving workers/scripts/reader-eval.ts onto the price history; it runs outside the database.
  • Page format can change without notice. D15’s guards reject a malformed table and keep the last good one, and Plate II’s line makes that visible in wrangler tail. A long-lived rejection shows up as price_unknown on sessions using new models only.
  • Price lag. A price change is picked up at the next tick, so up to a day of sessions is priced at the old rate. That’s accepted.
  • Transcript format is a CLI internal and can change. Tests pin today’s shape, and an unrecognised shape degrades to nulls, not a crash. If the prompt goes missing on some future CLI, the backfill’s reconstruction fills it (class 2).
  • Latency. Parsing a long transcript every turn costs time. If a real session’s stop hook exceeds about 1 s, the follow-up is an offset cache in the state file, not a weaker hook.
  • Resume behaviour. Whether a re-provisioned container restores the transcript and fires startup or resume is unverified. D10 and D13 cover both answers.
  • Injected sessions can write ledger rows. That is ALF-309 D1’s accepted blast radius: a session can only corrupt metrics, and a re-run doesn’t repair class 1–2 columns, so a suspect row is deleted and re-backfilled.
