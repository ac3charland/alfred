ALF-322 — Summarization types in the Reader

Each publication gets a type — Essay, Roundup or Alerts — and the summariser asks a different question of each: what's new, what's worth clicking, or is there anything I need to know.

Revised 2026-10-03: D2 → Highlights + Links (your review); Plate II redrawn.

Decisions

  1. D1Where does a type live?

    On the publication: Essay (default), Roundup, Alerts — chosen on its card, and when adding a candidate.

    A sender's mail is one kind; choosing per post would be a chore.

  2. D3What does an Alerts summary show?

    Findings on the row, tagged Sale · Security · Action · Change; no Send; Overview keeps only the stamp.

    The finding is the whole value; hiding it behind a click wastes it.

  3. D4Does changing a type re-summarise old posts?

    No. Posts keep the type they were summarised under; Retry summary uses the current type.

    Epic D7: a summary never changes under you silently.

  4. D2What does a Roundup summary contain?

    Highlights (what might make you read on) and Links (pieces worth reading, as the send checklist).

  5. D5An Alerts post with nothing notable?

    Auto-archived, and its archive row says "Nothing notable — filed automatically".

  6. D6What does Alerts look for?

    One fixed rubric for every Alerts publication — no per-publication "watch for".

  7. D7What does an Alerts post cost?

    Same model, same 30-a-day ceiling as every post.

☞ open: your pick · → proposed: my call · ✓ settled: yours. Merging accepts every proposed row.

Not doing

No per-publication criteria, no auto-detected type, no bulk re-summarise when a type changes.

Heads-up

  • Adding a promo sender as Alerts claims its mail off the Comms FYI shelf (epic D14).
  • Only bulk senders become candidates; most bank security mail has no list header.
  • Each Alerts post spends one of the 30 daily summaries (D7).

Working detail

Everything below is for the implementing agent. Approving needs only what’s above.

Context

The problem (ticket). The summariser is one size fits all: every post is read as an argumentative essay — novel ideas, evidence, the argument. Two other kinds of mail don't fit. A link roundup's value is which of its links are worth clicking, not the issue's own claims. A corporate newsletter or account notice is a needle-in-a-haystack: almost always noise, occasionally a sale or a security issue. The owner wants to classify publications by kind and have the summariser's prompt change accordingly.

What exists. The Reader epic (docs/specs/epics/ALF-232.html) shipped both stories plus follow-ons (Instapaper intake, Further reading, wiki picks, research reports). Relevant pieces:

  • workers/src/reader/prompt.ts — one static SYSTEM_PROMPT, READER_PROMPT_VERSION = 2, buildReaderRequest(post). Its Further reading clause already half-handles roundups ("in a roundup, pick the few items with real substance").
  • workers/src/reader/schema.ts — READER_SUMMARY_SCHEMA, the isReaderSummary guard, normalizeReaderSummary (caps, link-number → URL mapping).
  • workers/src/reader/summarize.ts — summarizePost(post, config), the outcome taxonomy (epic D10). Model/thinking/effort settings stay as they are (epic D8, this spec's D7).
  • workers/src/reader/scheduled.ts — the tick. readRoster reads id,name once per tick; prepareFresh / prepareRetry build the SummaryInput; applyOutcome writes the done patch.
  • reader_publications (migration 0035) and v_reader_publications (0036, an explicit column list — it must be recreated to expose a new column).
  • Frontend: components/reader/publications-card.tsx, publications-candidates.tsx, lib/stores/reader-settings-store.tsx, app/api/reader/publications/**; the row in components/reader/post-row.tsx, its panel post-overview.tsx, further-reading.tsx; the guards in lib/reader/overview.ts; the further-reading and wiki send routes, which read post.overview through isReaderOverview.

The owner's answers in refinement: a nothing-notable Alerts post is auto-archived (D5); Alerts uses one generic rubric, no per-publication criteria (D6); Alerts posts use the same model and the same daily ceiling (D7).

Where this departs from the epic. Epic §4's publications plate calls the Amazon candidate "the point: it is a candidate, and it stays one." This ticket deliberately makes promo senders legitimate roster members — as Alerts, which is cheap to read and auto-files the noise. Epic D7 (static prompt, no owner rubric) holds: the prompts are still static and versioned; the owner picks between three, not edits one.

Decision records

D1Where does a type live? · proposed

Considered: per-post auto-classification by the model (a billed judgment nobody can audit, and the epic's D4 reasoning against it applies verbatim); per-post owner override (a chore on fifty posts a day). A sender's mail is overwhelmingly one kind, and the roster is already the place the owner states intent about a sender. The candidate Add asks for the type because promotion claims the last seven days of that sender's mail on the very next tick — an Add that defaulted to Essay would spend summaries reading Amazon promos as essays before the owner could change it. Names: Essay (today's prompt; the default, so every existing publication keeps its behaviour), Roundup, Alerts.

D2What does a Roundup summary contain? · settled

Two sections, mirroring the Essay's shape. Highlights is the Roundup's analog of Novel ideas: up to six bullets of information or striking content in the issue itself — a number, a finding, a quote, a claim — that might make the owner want to read more. Links is the linked pieces worth reading in full, each with a title and a ≤ 20-word note on why; links that don't clear the bar are simply left out. Links are stored as overview.further_reading, so the existing checklist — send to Reader, send to Instapaper, sent marks in further_sent_reader / further_sent_instapaper — works unchanged; only its heading reads "Links". Highlights render as a plain bullet list (not wiki picks: the wiki route stays Essay-only). The gist says what the issue covers and what's worth opening it for.

Considered: every linked item judged, the losers listed collapsed as "Skipped" — the owner's review: the worth/skip categories didn't make sense, and an audit list is more reading, which the summary exists to save.

D3What does an Alerts summary show? · proposed

An Alerts post that survives (D5) exists only because something in it matters, so its findings are the row's body, each prefixed with a category tag. The panel machinery is kept, not special-cased: the row's done-state panel already holds the summary stamp, Original and Retry summary, and an Alerts row keeps that — it simply has no overview sections above the footer. Send to Instapaper is dropped for Alerts rows: there is nothing to read later in a sale notice. Category tags reuse Badge's alert variant (amber) and destructive for Security. The gist is still written (one line) and stored — the list never renders it for Alerts rows, but the eval script and the archive's screen-reader label use it.

D4Does changing a type re-summarise old posts? · proposed

Epic D7: "a summary that changes under the owner is indistinguishable from a bug." Each post records the kind it was summarised under (D8), and renders by that, not by its publication's current type. Retry summary is the explicit path: a re-run reads the publication's current type, so "switch Import AI to Roundup, then retry last week's issue" works. Considered: re-summarising the publication's last N posts on change — a burst against the 30/day ceiling triggered by a dropdown.

D5An Alerts post with nothing notable? · settled

The done patch for an Alerts post with zero findings also sets archived_at. It lands in /reader/archive, never on the reading list, and is recoverable there. Its row draws "Nothing notable — filed automatically." instead of a gist, derived from summary_kind = 'alerts' plus an empty findings list — no extra column. An Alerts post with findings leaves archived_at untouched, so a re-summarise from the archive that now finds something does not unarchive it (the owner is looking at it already).

D6What does Alerts look for? · settled

One static rubric (§Behaviour): a sale or discount on something specific, a security or account-access event, an action required (with its deadline when stated), a change to price, terms or service. Generic marketing ("new arrivals", "recommended for you", newsletters' editorial filler) is never a finding. Per-publication criteria were declined: they would make the prompt non-static and reopen epic D7.

D7What does an Alerts post cost? · settled

Same READER_MODEL, same summarizePost call shape, same READER_DAILY_CAP. An Alerts post is short, so it is cheaper per call than an essay anyway. If promoted senders start tripping the ceiling, that is the signal to revisit with data.

Implementation decisions

D8 · The kind is stamped on the post

reader_posts.summary_kind (nullable) is written in the done patch alongside prompt_version. Null means a summary written before this story — read as essay everywhere. Every overview reader (row, panel, further-reading route, wiki route) dispatches on it, never on the publication.

D9 · One static prompt and schema per kind; per-kind versions

prompt.ts holds three system prompts; the Essay prompt is byte-for-byte today's, so READER_PROMPT_VERSIONS.essay stays 2 and no existing summary looks stale. Roundup and Alerts start at 1. prompt_version is read together with summary_kind; the stamp reads e.g. "roundup prompt v1". Each kind's system prompt is still static, so prompt caching is unaffected (three cache entries instead of one). The user turn (metadata block, text, numbered links) is shared.

D10 · Posts without a typed publication are Essays

A research report is always essay. An Instapaper article uses its linked publication's type if it has one, else essay. A newsletter whose roster row has gone (retry path) falls back to essay.

D11 · Alerts has no separate "notable" flag

The schema asks only for findings; an empty list is "nothing notable". A separate boolean would let the model contradict itself (notable with no findings), which then needs a tie-break rule.

D12 · The tick's roster read carries the type

readRoster selects id,name,summary_kind and returns Map<id, {name, kind}>. No new fetch, so the subrequest table in READER_TICK_LIMIT's doc comment is unchanged.

Roundup prompt essentials. Highlights: concrete information or content in the issue's own text that would make a reader want more — a number, a result, a quote, a sharp claim, a surprising fact — each a self-contained bullet; not a table of contents of the issue, and empty when nothing stands out. Links: linked pieces the issue presents for the reader (never chrome, sponsors, or the author's back catalogue) that are substantive and likely new to a well-read person in the field; a press release, a listicle, a widely covered launch, or a link the issue already fully summarises is left out. Each names the linked piece itself (not the anchor text) with a ≤ 20-word note on why it's worth it. Link numbers come from the same numbered links block the Essay prompt uses.

Alerts prompt essentials. The reader only wants to know if this message requires or rewards attention. Findings are concrete: what, on what, by when. Categories: sale (a specific discount or offer), security (sign-in, password, breach, suspicious activity), action (something the reader must do, with its deadline in deadline when stated), change (price, terms, plan or service changes affecting the reader). Generic promotion, recommendations, brand storytelling and "new arrivals" are never findings; an empty list is the common, correct answer.

Rendering by stored kind. summary_kind null or essay → today's guard and panel. A stored overview that fails its kind's guard behaves as an Essay overview failing today: the gist (or, for Alerts, nothing) renders and the panel holds only the footer.

Publications. The card's type chip is a PickerChip (options with a one-line description, Plate I); a pick PATCHes immediately with the store's optimistic/rollback pattern, like the pause toggle. The candidate's Add becomes "Add as ▾" — a DropdownMenu with the three types; picking one POSTs { handle, summary_kind }. The auto-discovery upsert (Substack senders) inserts with the column default, Essay.

Hotkeys. Unchanged: v/enter toggles the panel where one exists (an Alerts row has one — its footer); the Instapaper send hotkey is a no-op on Alerts rows, as it is on any row without Send.

Acceptance criteria

  • Every publication has a type, Essay by default; existing publications read Essay after the migration.
  • The publication card shows a type chip that changes the type in one pick, optimistically with rollback.
  • A candidate is added with a chosen type via "Add as ▾"; auto-discovered Substack senders are added as Essay.
  • An Essay post's request (system prompt, schema, user turn) is identical to today's and is stamped prompt v2.
  • A Roundup post's overview shows Highlights as bullets, then Links as the send checklist (to Reader / Instapaper) under the heading "Links".
  • An Alerts post with findings appears on the reading list with one tagged line per finding, no Send, and an Overview that holds only the footer.
  • An Alerts post with no findings is archived by the tick in the same write as its summary and reads "Nothing notable — filed automatically." in the archive.
  • Changing a publication's type changes no existing post; Retry summary on one of its posts re-summarises under the new type.
  • Research reports and unlinked Instapaper articles are summarised as Essays.
  • Alerts and Roundup calls use READER_MODEL, count against READER_DAILY_CAP, and add no per-tick fetch.
  • npm run eval:reader -w workers -- --kind roundup|alerts prints that kind's summary.

Out of scope, risks & unknowns

  • Per-publication criteria — declined (D6); model-detected type — D1; bulk re-summarise on type change — D4.
  • Non-bulk senders can't become candidates. v_reader_candidates lists only has_list_header senders; transactional security mail often lacks it. Adding an arbitrary handle by UI is a separate story; the POST route already accepts any handle.
  • Comms overlap. A promoted sender's mail leaves the Comms FYI shelf (epic D14) but never the queue; a security notice the comms classifier queued stays queued as well as appearing here. Intended.
  • Prompt quality is the real risk. Roundup's bar for a highlight or a link and Alerts' noise rejection are judged by the owner with eval:reader --kind; expect a v2 of either prompt after a week of real mail.
  • Confirm while building: that the structured-output grammar accepts {"type": ["integer","null"]} / enum as used (the anthropic-api skill lists the supported subset); fall back to anyOf if not.
