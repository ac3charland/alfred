ALF-343 — A 7 AM Telegram digest: what’s due, the plan for today, comms and reader

Every morning at 7:00, one Telegram message: a short model-written opener, then fixed lists of what’s due, your ASAP/Today comms, and how many reader articles are waiting.

Decisions

  1. D5Where do today’s plan lines appear?

    Only in the opener; listed verbatim only if the model fails

    Plan lines are already due items: listing both repeats the week.

  2. D6Model call fails or is slow?

    Send on time without the opener; never hold the digest

    The lists are the point; the opener is garnish.

  3. D7What schedules it?

    The one-minute notify tick, as a third ping kind; sends 7:00–7:59 or not that day

    All five Free-plan cron triggers are taken.

  4. D1What does the model write?

    A whole-digest opener; every list below it is deterministic

  5. D2When?

    7:00 AM America/Chicago, every day

  6. D3How much comms?

    Tier counts, plus up to five ASAP/Today asks

  7. D4Which tasks are “due”?

    Exactly the Today view: due today or overdue, same order

Not doing

Calendar events (the morning brief’s job); reply buttons; a different time on weekends.

Heads-up

  • No new secrets or setup: it reuses the Telegram bot and the Worker’s Anthropic key.
  • Due titles and comms asks go to the model and sit on Telegram’s servers, as pings already do.
  • About one Sonnet call a day: well under $1 a month.

Working detail

Everything below is for the implementing agent. Approving needs only what’s above.

Context

The ask. ALF-343: a daily morning Telegram digest of due tasks and “the weekly plan’s instructions for the day”, plus outstanding comms and a count of reader articles waiting. Ticket note: “Make due tasks deterministic; generate summary via an LLM.” In refinement the owner picked a whole-digest opener (D1), 7:00 every day (D2), counts + ASAP/Today asks (D3), and the Today view’s due rule (D4).

What exists.

  • Telegram pings (ALF-333). workers/src/notify/: a one-minute tick (NOTIFY_CRON = '* * * * *') calls claim_notifications(p_now, p_zone, p_limit) (migration 0054_notifications.sql), sends each claim via sendTelegram (workers/src/telegram.ts), and stamps the outcome. Kinds today: comms_asap, task_due. Read the telegram skill first.
  • Cron budget. wrangler.toml holds five crons; index.ts’s NOTIFY_CRON comment says it is the account’s last Free-plan trigger and the next scheduled feature must share its budget. Hence D7.
  • Due tasks. The Today view’s rule is rankDueToday (frontend/lib/tasks/due-today.ts) over buildTree of every task_items row, ranked by rankNodes(…, compareKeyByDue) (frontend/lib/priority.ts). Due dates are floating (due_date is midnight UTC; read the date with at time zone 'UTC'); due_time is a floating wall-clock time (0053).
  • Weekly plan. weekly_plans.html (0022) stores the Friday review’s document verbatim. It is generated by the weekly-review skill’s generate_plan.py, which lives outside this repo. That generator embeds var DAILY_TASKS = {…};: JSON keyed by ISO date, each value an array of {pill, label, text}. It also emits <div class="theme-title">…</div>. The review also creates one item per plan line with that day’s due_date (0030), so plan lines and due tasks overlap heavily (D5). Lines with no item behind them are runs, habits and calendar events.
  • Comms queue. isQueued (frontend/lib/comms/queue.ts): inbound, cleared_at is null, tier in asap/today/whenever. The ask is comm_verdicts.ask; the sender is coalesce(comm_people.name, sender_name, sender_handle), exactly as claim_notifications builds it.
  • Reader. The reading list is reader_posts where archived_at is null (frontend/lib/reader/list.ts; Instapaper posts included).
  • Model calls from the Worker. workers/src/reader/summarize.ts is the pattern: @anthropic-ai/sdk, output_config.format JSON schema, typed error mapping. Read the anthropic-api skill.

Not the morning skill. The owner’s Claude-side morning skill renders a calendar-driven HTML brief. This digest is alfred’s own data, pushed; it does not read calendars.

Decision records

D1What does the model write? · settled

The owner chose the whole-digest briefing over a plan-only focus line. What makes it safe: the model writes only the opener. Every count, row and link is built in code from the same facts the model is shown. The prompt forbids stating counts or naming a task, person or article that isn’t in its input (see Behaviour). The deterministic lists are always authoritative, so the opener can frame them but never replace them. Considered: a plan-only focus line (less context, less risk); plan lines rewritten as instructions.

D2When? · settled

A [vars] entry DIGEST_TIME = "07:00", read in CLASSIFIER_TIMEZONE (the zone every floating time already uses), so moving it is a one-line deploy. An empty value turns the digest off.

D3How much comms? · settled

Counts for all three queued tiers. Up to five rows: ASAP first, then Today, each tier newest first (the queue’s own order). Whenever is a count only. Unjudged messages (tier null) are in neither the counts nor the rows, matching isQueued.

D4Which tasks are “due”? · settled

The digest’s list is rankDueToday(buildTree(active task_items), false), evaluated for the local date in CLASSIFIER_TIMEZONE at send time. A root shows if it, or an active descendant, is due on or before today. The order is the effective due moment, then priority rank, then created_at.

D5Where do today’s plan lines appear? · proposed

The review turns most plan lines into due items, so a verbatim “Plan” section would duplicate most of the Due list. The lines that aren’t items (runs, events, habits) are exactly the context the opener is for. So today’s lines and the theme go to the model, and the opener weaves them in. If there is no opener (D6), the plan section takes its place verbatim, as label · text bullets, so the plan never silently disappears. Considered: always list plan lines (duplication); list only the lines with no matching due item (title matching is brittle, and the review may rename items).

D6Model fails or is slow · proposed

Any opener failure is non-fatal: no key, a typed SDK error, a refusal, a schema-invalid reply, or a 20 s timeout. The digest sends at once in the no-model form (Plate I, “Model unavailable”) and logs digest: opener unavailable — <reason>. It counts no attempt and doesn’t retry the model. Holding a 7:00 message for a garnish would trade the point for the decoration.

D7What schedules it? · proposed

A third notifications kind, morning_digest, claimed by claim_notifications. The fire key is the local date (YYYY-MM-DD), so the unique index makes it once a day, whatever the overlapping ticks do. A new claim is made only while local time is in [DIGEST_TIME, DIGEST_TIME + 60 min). A deploy at noon therefore starts tomorrow, and an outage until 7:59 still delivers. Retries and abandonment follow the existing rules (3 attempts, 60 min since claim, 5-min lease). Considered: a sixth cron (needs the paid plan); a Worker-side clock check plus a separate claim RPC (splits retry handling across two paths).

Implementation decisions

D8 · One facts RPC, ranking in TypeScript

digest_facts(p_now, p_zone) returns everything in one subrequest: active task rows, comms counts and up to five asks, the reader count, and the newest plan’s html. The due ranking is ported to workers/src/digest/due.ts, not written in SQL. The rule being mirrored is TS, and a parity table copied from due-today.test.ts / priority.test.ts catches drift more readably than a recursive CTE would. Workers can’t import from frontend/; note the twin in both files’ doc comments.

D9 · Model: DIGEST_MODEL = "claude-sonnet-5"

A [vars] entry, like READER_MODEL, with the same call shape (thinking: {type:'disabled'}, output_config.effort: 'low', structured output). At one call a day the price is noise, and the opener is read daily, so the quality tier wins. The constraints in the wrangler.toml comment for READER_MODEL apply (no Fable).

D10 · Plan parsing degrades, never throws

alfred doesn’t own the generator. Extract DAILY_TASKS by taking the text after the literal var DAILY_TASKS = up to the first ;\n\nfunction initToday, then JSON.parse it and validate the shape (zod is not in workers; use a hand-written guard). Take the theme as the .theme-title div’s text, with tags stripped and the five basic entities decoded. On any failure: log digest: plan unreadable (<plan id>) and treat the day as “no plan”. A plan “covers today” iff DAILY_TASKS has today’s ISO key; an empty array means a planned rest day.

D11 · Retries regenerate the opener

notifications.text stays “what was sent”, NULL until sent, so a transient send failure rebuilds the facts and re-asks the model on the next tick. That is at most 3 model calls a day; not worth a draft column.

Behaviour

The tick

  • runNotifyTick passes DIGEST_TIME (normalised HH:MM, or null when blank or unset) to claim_notifications. A malformed value (anything not HH:MM, 00–23 : 00–59) is logged notify: DIGEST_TIME invalid — digest off and passed as null. It never aborts the other pings.
  • For a morning_digest claim, the tick builds the text (below), then sends and records it exactly like the other kinds. markSent stores the text Telegram received. The status handling is unchanged.
  • Budget: the per-claim worst case becomes per kind: 6 for a digest (facts 1 + model 2 with one SDK retry + send 2 + PATCH 1), 3 otherwise. The SUBREQUEST_CEILING check uses the claim’s own worst case. If digest_facts throws, count a failed attempt (digest facts failed: …) and carry on.

Building the digest (workers/src/digest/)

  1. Facts via digest_facts. Today = the local date of p_now in the zone.
  2. Due = D4 over the task rows. For each root, a label:
    • The effective due date is before today → N days late (1 day late when N is 1). When the late date comes from a subtask rather than the root itself → subtask late.
    • Due today with a time (its own) → formatTime, e.g. “3:00 PM”.
    • Due today via a subtask only → subtask due.
    • Otherwise no label.
    Show at most 8 rows. Past that, add a final row +N more on Today. Titles are capped at 100 graphemes (cap).
  3. Plan (D10): today’s lines as {label || default pill name, text}, and the theme title, or “no plan covers today”.
  4. Opener (D1, D6): one model call; input below. The output is capped at 600 graphemes and trimmed; if it is empty, there is no opener.
  5. Text: the sections in Plate I’s order. HTML and the plain-text twin are built by the same function, every interpolated value goes through escapeHtml, and links point to ALFRED_APP_URL + /today, /comms, /reader.

The model call

  • Input (user turn, JSON): { date: "Saturday, Nov 7", plan: { theme, lines:[{label,text}] } | null, due: [{title, label}], due_overflow, comms: { counts, asks:[{tier,sender,ask}] }, reader_waiting }. That is the same values the lists render, after capping.
  • System prompt, in substance: write 1–3 sentences (≤ 450 characters) that orient the owner to the shape of the day, using only the facts given. Lead with what’s late or who’s waiting when there is something; draw on today’s plan lines and theme for the why. Don’t restate counts or repeat the lists, and never name a task, person or article that isn’t in the input. Plain text, no markup, second person, no greeting (the headline is the greeting). With nothing due and no plan, say so plainly and briefly.
  • Output schema: { "opener": string }, via output_config.format, with max_tokens: 400. The opener renders in <i>.

Sections, edge cases

  • Nothing due → Due · nothing today. Empty queue → Comms · nothing waiting on you. The reader always shows its count, 0 included.
  • The headline is always Good morning · <Weekday>, <Mon> <D> in the zone.
  • Length: by the caps, the worst case is about 3,000 characters, under Telegram’s 4,096. As a backstop, assert in a test that a maximal fixture stays under 4,000 graphemes.
  • The digest still sends when there is nothing at all to report (Plate I “Quiet day”): its arrival is the signal that alfred is alive.

Acceptance criteria

  • With DIGEST_TIME="07:00", a tick at 07:00–07:59 Chicago claims exactly one morning_digest for that local date; ticks outside the window, or on a date already claimed, claim none.
  • A digest claim that fails to send is retried on later ticks under the existing attempt/lease/60-minute rules, and never sends twice for one date.
  • The sent text matches Plate I’s section order and wording; every count and row comes from digest_facts, not the model.
  • The Due list equals rankDueToday’s order and membership for the same rows (parity table), with the late, subtask and time labels.
  • Comms shows three tier counts and ≤ 5 rows, ASAP then Today, newest first; whenever, FYI, cleared, outbound and unjudged rows never appear as rows.
  • The reader count equals the number of unarchived reader_posts, and shows when it is 0.
  • When the newest plan covers today, its lines and theme are in the model input and not listed. With no plan, the opener input has plan: null and no plan section renders.
  • Model failure of any kind (no key, error, refusal, bad schema, timeout) sends the digest on the same tick, in the no-model form with today’s plan lines listed, without counting an attempt.
  • Quiet day: the digest still sends, reading “nothing today” / “nothing waiting on you” / “0 waiting”.
  • A blank DIGEST_TIME turns the digest off; a malformed one logs and turns it off; neither affects the other pings. GET / reports the digest’s state.

Review focus

  • A plan whose HTML has no DAILY_TASKS, or truncated or invalid JSON → digest sends as “no plan”, logs plan unreadable.
  • A task title or ask containing <, & or an emoji → renders literally, never cut mid-grapheme; Telegram never 400s on it.
  • 40 due tasks and 30 queued asks → 8 rows + “+32 more on Today”, 5 asks; total under 4,000 graphemes.
  • DST change day (spring forward skips 02:00, not 07:00; fall back repeats 01:00) → exactly one digest, at 07:00 local.
  • A transient send failure at 07:00 then success at 07:01 → one message; the recorded text is the one sent at 07:01.

Out of scope, risks & unknowns

  • Calendar: the Worker has no calendar access, and the morning skill covers it. Buttons/replies need an inbound webhook (the telegram skill’s “Deliberately left out”). Weekend time: not asked for; DIGEST_TIME is one value.
  • Generator coupling (D10): a change to generate_plan.py’s script block silently drops the plan to “unreadable”. A cleaner contract would be a <script type="application/json" id="plan-data"> block emitted by the generator. That change lives in the skill, outside this repo; file it as a follow-up rather than building it here.
  • Opener faithfulness: the prompt forbids inventing, but no suite runs the model. If the opener drifts in practice, an eval:digest script like eval:reader is the follow-up, not a check in this story.
  • Confirm the generated name of the kind CHECK in 0054 before dropping it (npm run describe -w database).
