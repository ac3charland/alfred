ALF-130 — Add ability to refine an epic in Claude Code

Refinement Code module DB · Worker · store · UI · skill Spec only — no implementation. Build in a later session.

1 · Context & problem

An epic is currently a naked bucket: name, an optional one-line notes field edited inline under the epic header, and an archived_at flag. Every decision that spans an epic — the architecture it assumes, the constraints, the things deliberately deferred, why the stories are cut the way they are — has nowhere to live. It gets re-derived, story by story, inside each story's refinement session, which is both wasteful and inconsistent: two stories in the same epic can be specced against two different mental models of the same feature.

Stories already have the machinery for exactly this. A story's Refine in Claude Code launch opens a prefilled claude.ai/code tab; the session writes a self-contained HTML spec and opens a PR carrying the machine-readable alfred block; the webhook Worker records spec_path on merge and snapshots the file into code_items.spec_markdown, which the story detail modal renders. ALF-130 lends that whole pipeline to epics:

  • a Refine epic in Claude Code action in the epic's 3-dot menu,
  • a new epic-refinement skill and launch prompt aimed at brainstorming and recording high-level context rather than a buildable change,
  • the resulting epic spec snapshotted onto the epics row, exactly like a story spec, and readable in a View spec modal,
  • and — the payoff — every story prompt in that epic (refine, implement, skip-to-dev) pointing at the epic spec file so each story session starts from the epic's settled context instead of re-inventing it.

2 · Decisions (locked during refinement)

Epic spec home
docs/specs/epics/<EPIC-REF>.html — its own folder, separate from the active story specs.
Never archived
A story spec is scaffolding and is git-moved to docs/specs/archive/ by its implementation PR. An epic spec is long-lived context that story prompts keep referencing, so it is never archived and never moves. Its own folder keeps it structurally clear of the archive rule.
Format
A self-contained HTML plan, same authoring rules as story specs (inline CSS, no external deps, htmlpreview link on the PR). The existing spec renderer already sniffs HTML-vs-markdown, so it renders an epic spec with no new rendering code.
PR contract
A third phase: phase: epic-refinement. The alfred-ticket is the epic's ref. Explicit routing beats "try code_items, fall back to epics" — refs are drawn from one shared per-project counter, so a silent fallback would make a typo'd story ref patch nothing while looking like it worked.
No epic lifecycle
Epics have no factory_state and gain none. An epic-refinement PR opening records refinement_pr_url; merging records spec_path and snapshots the file. A closed-unmerged epic-refinement PR is a no-op — there is no state to revert.
Re-refinement
The menu action is always available. When the epic already has a spec_path, the prompt tells the agent to update that file in place rather than write a second one, so an epic has at most one spec, refined as often as you like.
Reading it
A View spec item in the same 3-dot menu opens an Epic spec modal that reuses the story modal's spec rendering (sandboxed <iframe> for HTML, markdown fallback, sha-pinned View in repo link). The item is rendered only once a spec exists.
Column names
epics gains spec_path, spec_sha, spec_markdown, refinement_pr_url — the same names as code_items, so the Worker's snapshot writer and the frontend's spec renderer are shared, not forked. (spec_markdown holds HTML here exactly as it already does for stories; the name is historical and stays for symmetry.)
Which story prompts
All three — refinement, implementation, and skip-to-dev (bypass). Bypass deliberately carries no story spec reference (ALF-75), but an epic spec is background context for a build session, not a spec to consume or archive, so it belongs there too.
Writes are Worker-only
The four new columns are written only by the Worker (service_role). No API route, request schema, or store action lets the browser set them; PATCH /api/epics/[id] keeps its name / notes / archived_at allow-list unchanged.

5 · Data model

database/migrations/0019_epic_specs.sql

-- ALF-130 — Epic specs: an epic can carry its own refinement spec, snapshotted by the Worker
-- exactly like a code story's (§4 of the code-module schema). Epics have NO lifecycle state, so
-- there is no factory_state analogue here — only the spec columns and the PR url.

alter table epics
  add column spec_path         text,
  add column spec_sha          text,
  add column spec_markdown     text,
  add column refinement_pr_url text;

comment on column epics.spec_path is
  'Path the epic-refinement PR DECLARED for the epic spec; never inferred. Long-lived — unlike a '
  'story spec it is never archived, because story prompts keep referencing it.';
comment on column epics.spec_markdown is
  'Worker-written snapshot of the rendered epic spec; the epic spec modal reads this, not GitHub.';

-- The board read gains the epic's spec path so the story launch prompts can point at it.
-- `create or replace` (not drop/create) APPENDS the column and PRESERVES the view's grants —
-- the 0017 lesson. New columns must go LAST in the select list for the replace to be legal.
create or replace view v_code_stories with (security_invoker = true) as
  select
    c.item_id, c.project_id, c.epic_id, c.ref_number, c.ref, c.factory_state, c.lane,
    c.spec_path, c.spec_sha, c.spec_markdown, c.refinement_pr_url, c.implementation_pr_url,
    c.blocked_reason, c.created_at as code_created_at, c.updated_at as code_updated_at,
    i.title, i.notes, i.source_url, i.created_at as item_created_at,
    p.key as project_key, p.name as project_name, p.repo_owner, p.repo_name,
    e.name as epic_name, e.ref as epic_ref, e.archived_at as epic_archived_at,
    c.priority,
    e.spec_path as epic_spec_path
  from code_items c
  join items i on i.id = c.item_id
  join projects p on p.id = c.project_id
  join epics e on e.id = c.epic_id;

-- Idempotent re-assert (grants survive `create or replace`, but 0017 is the cautionary tale).
grant select on v_code_stories to anon, authenticated, service_role;

-- The Worker writes the snapshot out-of-band, so an open board needs a push channel to show it
-- without a reload — the epics analogue of 0003's code_items stream. RLS still governs it: epics
-- already has the `authenticated full access` policy from 0002.
alter publication supabase_realtime add table epics;

notify pgrst, 'reload schema';
Generated types. frontend/lib/database.types.ts is generated — regenerate it with supabase gen types and commit the raw output. Never hand-edit it, and never reformat it (it is excluded from ESLint/Prettier).

Epic and CodeStory pick the new columns up from the regenerated types automatically. Two knock-on edits: lib/tree.ts's makeOptimisticEpic seeds the four new fields as null, and every hand-built Epic fixture (unit tests, stories) gains them.

6.2 · Worker changes

FileChange
workers/src/frontmatter.ts CodePhase gains 'epic-refinement', and PHASE_RE becomes /phase:[ \t]*(epic-refinement|refinement|implementation)/. Alternation order matters — epic-refinement must come first or the engine can never reach it. (Today's regex simply fails to match phase: epic-refinement, so an old Worker ignores the PR rather than mis-routing it — the rollout is safe in either order.)
workers/src/transitions.ts TransitionPlan gains target: 'story' | 'epic' (existing plans set 'story'). planTransition grows the epic-refinement branch above. TicketUpdate is reused as-is: the epic branch only ever sets refinement_pr_url / spec_path, both of which exist on epics, so no new update type is needed.
workers/src/supabase.ts Generalize the PATCH over the table: an internal patchByRef(env, table, ref, updates) with patchCodeItem and a new patchEpic as the two thin exported wrappers. Same headers, same return=representation row count, same throw-on-non-2xx.
workers/src/index.ts Pick the patch function from plan.target, for both the main PATCH loop and the background snapshotSpec (which is otherwise unchanged — the snapshot columns are named identically on both tables, so SpecSnapshot is shared). The response JSON stays { ok, tickets, state }; state is simply undefined for an epic plan.

6.3 · The enforcing CI check

docs/code-module/repo-setup/alfred-frontmatter.yml — the copy-ready artifact each project repo installs:

const phase = /phase:\s*(epic-refinement|refinement|implementation)/.exec(blk);   ← accepts the new phase
…
if ((phase[1] === "refinement" || phase[1] === "epic-refinement") && !specPath) { ← spec-path required for both
  console.error("refinement PRs need spec-path"); process.exit(1);
}
// Archive rule — implementation PRs only, and never an epic spec:
if (phase[1] === "implementation" && specPath
    && specPath.startsWith("docs/specs/")
    && !specPath.startsWith("docs/specs/archive/")
    && !specPath.startsWith("docs/specs/epics/")                                ← epic specs are never archived
    && fs.existsSync(specPath)) { … }

The epics/ exclusion is belt-and-braces: the rule already only fires on phase: implementation, whose spec-path is the story spec. It exists so that pointing an implementation block at an epic spec can never demand that a long-lived document be archived. The repo-setup/README.md contract table and phase list are updated to match, and its copy-checklist gains the epic-refinement skill.

The prompt it produces (an epic that already has a spec shown in green):

ALF-12: Communication Firewall

You are refining the EPIC ALF-12. Produce an EPIC SPEC ONLY — a high-level context and
decisions document for the epic as a whole. Do NOT implement anything, and do NOT write
per-story specs (individual stories are refined in their own sessions).

1. Ground yourself first: skim the repo and honor its own conventions — read any CONTRIBUTING
   or CLAUDE.md — and base the epic spec on the code that already exists.
2. If the epic name and context below don't pin down the problem space and the decisions worth
   recording, ASK ME HERE before writing — you don't need to guess, I'm in this tab.
   Brainstorming the epic with me is the point of this session.
3. Write the epic spec following the epic-refinement skill at
   `.claude/skills/epic-refinement/SKILL.md` (it auto-loads in an epic-refinement session) — it
   defines this repo's epic-spec format, structure, and where the spec lives. If the skill is
   absent, write it as a single self-contained HTML document under the repo's specs directory.
   This epic already has a spec committed at `docs/specs/epics/ALF-12.html` — UPDATE that file
   in place rather than adding a second one.
4. Open a pull request whose description carries this machine-readable block — the orchestrator
   (alfred) reads it to attach the spec to the epic and a CI check enforces it. Reproduce the
   `alfred-ticket` and `phase` lines exactly, and set `spec-path` to where you saved the spec:

```alfred
alfred-ticket: ALF-12
phase: epic-refinement
spec-path: <path-or-folder-of-the-spec>
```

5. Before opening the PR, confirm the spec is saved, `spec-path` above names that spec (not the
   placeholder), and the block is reproduced exactly.

Context (from the epic notes):
Everything about how alfred talks to me: notifications, Siri capture, the morning brief.

Same shape as the story refinement prompt, deliberately: ref + name lead so the new browser tab is scannable; the format/location stays the skill's job (a placeholder spec-path, not a hardcoded path); the clarification gate and the verbatim-block self-check are kept.

7.2 · The epic-spec reference in the three story prompts

buildRefinementUrl, buildImplementationUrl and buildBypassUrl each emit one extra paragraph when story.epic_spec_path is non-null, placed immediately after the opening "You are …" line and before the numbered steps — so the existing step numbering and the block position are untouched: 

Epic context: this story belongs to epic ALF-12 (Communication Firewall), whose epic spec is
committed at `docs/specs/epics/ALF-12.html`. Read it first — it carries the high-level decisions
and constraints for the whole epic. It is background, NOT this story's spec: don't edit, archive,
or move it.

No line at all when the epic has no spec — nothing is worse than pointing an agent at a file that isn't there. The "don't archive it" clause matters because the implementation prompt in the very same message tells the agent to git-move its spec into docs/specs/archive/.

7.3 · The new skill

.claude/skills/epic-refinement/SKILL.md — a sibling of refinement, aimed one altitude higher. It must cover:

  • What an epic spec is — durable context and decisions for a body of work, not a buildable change and not a story breakdown to implement from. It is read by every later story session in the epic.
  • Where it goes — docs/specs/epics/<EPIC-REF>.html, a self-contained HTML document (inline CSS, no external deps, no JS required), same authoring rules as the story-spec skill.
  • Sections — problem space & why now; the decisions taken, each with its rationale; architecture / data model the epic assumes; constraints and non-goals; a sketch of how the work splits into stories (a sketch, not specs); open questions.
  • Refining again updates the same file — one spec per epic, revised in place; record what changed and why rather than starting a second document.
  • The PR — the alfred block with phase: epic-refinement and the epic's ref, plus the htmlpreview.github.io link on the head branch (the same rendering trick the refinement skill documents, and the same reason).
  • Never archived — an implementation PR retires a story spec; the epic spec stays put.
  • No implementation and ask when context is thin — the same two guardrails, since this session is even more open-ended.
Skill work is high-leverage. Read skill-creator before writing it, walk its "Writing a description that triggers" checklist line by line against the draft, and run npm run lint:skills -w tools/skill-lint while drafting. Cross-reference the refinement skill for the shared HTML/PR conventions instead of restating them — the two skills must not drift.

10 · Acceptance criteria

  • An epic's 3-dot menu has Refine epic in Claude Code; selecting it opens a claude.ai/code tab prefilled with the epic-refinement prompt and copies that prompt to the clipboard, changing no epic state.
  • The prompt leads with <EPIC-REF>: <name>, forbids implementation and per-story specs, points at .claude/skills/epic-refinement/SKILL.md, inlines the epic notes (clipped at 1000 chars with the truncation warning), and carries an alfred block with phase: epic-refinement and a placeholder spec-path.
  • When the epic already has a spec_path, the prompt tells the agent to update that file in place; when it doesn't, no such line appears.
  • .claude/skills/epic-refinement/SKILL.md exists, covers everything in §7.3, and passes npm run lint:skills -w tools/skill-lint.
  • epics has spec_path, spec_sha, spec_markdown, refinement_pr_url; v_code_stories exposes epic_spec_path and keeps its SELECT grant.
  • The Worker parses phase: epic-refinement, records refinement_pr_url on open, records spec_path and snapshots the file into the epics row on merge, and no-ops on close-without-merge — never touching code_items for that phase.
  • Existing refinement / implementation transitions are byte-for-byte unchanged.
  • The copy-ready alfred-frontmatter.yml accepts epic-refinement, requires spec-path on it, and never applies the archive rule to a docs/specs/epics/ path; repo-setup/README.md documents the phase and lists the new skill as a per-repo artifact.
  • Once a spec is snapshotted, the epic menu offers View spec and the modal renders it (HTML in a sandboxed frame, markdown as prose) with a sha-pinned View in repo link; with no spec, the item is absent.
  • The merged snapshot reaches an already-open board over realtime, without a reload.
  • A story whose epic has a spec gets the epic-context paragraph in all three launch prompts, telling the agent to read it and not to edit, move, or archive it; a story whose epic has no spec gets no such paragraph.
  • No API route, request schema, or store action lets the browser write the epic spec columns.
  • npm run check is green; the demo doc at docs/demos/alf-130-epic-refinement/ reproduces via npm run demo -- verify.

11 · Out of scope

  • Any epic lifecycle state — no in_refinement equivalent, no state chip on the epic header, no "needs refinement" nudge.
  • Backfilling existing epics — the columns start null; an epic gets a spec the first time you refine it.
  • Feeding the epic's story list into the epic prompt. The prompt is built from the epic's own fields; the session can read the repo, and the ~14k prompt cap makes inlining a story list a bad trade.
  • Editing the epic spec from alfred. The modal is read-only; edits go through a new refinement session and its PR, exactly like story specs.
  • An epic-spec indicator on the board (a badge, an icon on the epic header). Worth revisiting once epic specs are common; the menu item is the discovery path for now.
  • Installing alfred-frontmatter.yml into this repo's .github/workflows/ — it stays a copy-ready artifact, as today.
