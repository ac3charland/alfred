ALF-137 — Mark stories as not needing refinement

Refinement Code module DB · API · Store · UI Spec only — no implementation. Build in a later session.

1 · Context & problem

A code story enters the factory at needs_refinement and the only way out today, short of actually refining it, is the “Skip to Development” chip (frontend/lib/code/launch.ts, the bypass phase). That chip is a launch action: it writes factory_state = 'in_development' and opens a Claude Code tab in the same click.

So the decision “this one doesn't need a spec” is welded to the act “start building it right now.” You cannot triage a batch of small stories as dev-ready on Sunday and pick them up on Tuesday — every skip drags a browser tab with it. Worse, the judgement leaves no trace: nothing on the row distinguishes “deliberately skipped” from “not refined yet”, so a future automated dispatcher has no column to query and, on any state revert, the intent is simply gone.

This ticket separates the two. A story gains a persisted requires_refinement flag that can be set at creation or flipped later; clearing it parks the story in Ready for Dev with no tab opened. The “Skip to Development” chip stays exactly as it is for the impulse path — it just also records the flag now, so both routes leave the same durable mark.

1.1 The latent bug this also fixes

ready_for_dev currently assumes a merged spec — its launch builds buildImplementationUrl, whose prompt opens with “Implement the merged spec committed at <path> — read it first”, falling back to a conventional path when spec_path is null (frontend/lib/code/links.ts:272–299). That assumption is already false today: the Worker reverts a closed-unmerged implementation PR to ready_for_dev (workers/src/transitions.ts:122), so a story that was bypassed and whose PR got closed lands in a state it never passed through, with no spec — and its next launch tells the agent to read a file that does not exist.

Making the mark land stories in ready_for_dev would multiply that bug, so the fix is in scope: the development launch picks its prompt from whether a spec actually exists, not from the state alone (§7).

2 · Decisions locked during refinement

What the mark does
Moves the story to ready_for_dev, opens nothing. It sits in the Ready for Dev lane showing the normal Implement in Claude Code button, fired whenever the human (or, later, the factory) is ready.
Persistence
A real column — code_items.requires_refinement boolean not null default true. Survives state reverts, is queryable by a future dispatcher, and is what the UI and the prompt-selection read.
Entry points
Two: a Needs refinement checkbox in the New Story dialog (checked by default), and a toggle on an existing story in the detail modal.
Prompt selection
Fixed here. A ready_for_dev story with no committed spec launches the existing SKIP-REFINEMENT (bypass) prompt instead of the spec-reading implementation prompt.
Not doing
The gate dialog (Send to Code module / Convert to Code Story) does not get the toggle — those items land at needs_refinement as they do today and can be marked afterwards from the modal (§12).

4 · Database

One migration, at the next available migration number (take whatever is free when you build this — do not reuse a number from this document), named <next>_story_requires_refinement.sql. Follow the conventions in 0002/0020: comment on for the non-obvious column, explicit grants, notify pgrst at the end.

4.1 The column

alter table code_items
  add column requires_refinement boolean not null default true;

comment on column code_items.requires_refinement is
  'False = a human judged this story small/clear enough to build with no spec. Independent of '
  'factory_state so the intent survives a PR-close revert, and queryable by a future automated '
  'dispatcher. Cleared by the New Story checkbox, the detail-modal toggle, and the '
  'Skip to Development launch.';

Default true so every existing row keeps today's meaning with no backfill, and so the column reads the same way as the UI label (“Needs refinement”, checked by default).

4.2 The board read

Append the column to v_code_stories. Use create or replace — not drop/create — so the view's grants survive (the 0017 lesson recorded in 0020), which means the new column must go last in the select list. Re-assert the grant idempotently anyway; migration-lint's view-grant rule expects it. 

create or replace view v_code_stories with (security_invoker = true) as
  select
    …every existing column, in its existing order…,
    c.priority,
    e.spec_path as epic_spec_path,
    c.requires_refinement;          -- new column LAST

grant select on v_code_stories to anon, authenticated, service_role;

4.3 The creation RPC

create_code_story (added in 0004) must accept the flag and land the sidecar in the matching state.

Do not just add a defaulted 5th parameter. That creates a second function rather than replacing the first, and PostgREST's existing 4-named-arg call (p_project, p_epic, p_title, p_notes) then matches both candidates — Postgres answers function public.create_code_story(…) is not unique and story creation 500s. Drop the old signature first, then create the new one, and re-issue grant execute (grants do not carry across signatures). 
drop function if exists create_code_story(uuid, uuid, text, text);

create or replace function create_code_story(
  p_project uuid, p_epic uuid, p_title text, p_notes text default null,
  p_requires_refinement boolean default true
) returns code_items language plpgsql security invoker as $$
declare n int; k text; v_item uuid; row code_items;
begin
  select key into k from projects where id = p_project;
  n := next_code_ref(p_project);
  insert into items (title, notes, item_type)
  values (p_title, p_notes, 'code')
  returning id into v_item;
  insert into code_items (item_id, project_id, epic_id, ref_number, ref,
                          requires_refinement, factory_state)
  values (v_item, p_project, p_epic, n, k || '-' || n,
          p_requires_refinement,
          case when p_requires_refinement then 'needs_refinement'
               else 'ready_for_dev' end::code_factory_state)
  returning * into row;
  return row;
end; $$;

grant execute on function create_code_story(uuid, uuid, text, text, boolean)
  to anon, authenticated, service_role;

Only the last two insert columns and the new parameter differ from 0004; keep the rest of that body byte-for-byte.

enter_code_module and convert_to_code_epic are unchanged — the column defaults to true, which is the behaviour the gate already has.

6 · Store & the pure helper

6.1 Where a mark lands the story

The state consequence of flipping the flag is small, conditional, and worth unit-testing on its own, so it lives as a pure module beside launch.ts and status.ts: frontend/lib/code/refinement-mark.ts. 

/**
 * The factory state a refinement-mark change should land the story in — often the state it is
 * already in. Clearing the mark only fast-forwards a story still sitting at the front of the
 * lifecycle; re-setting it only undoes that fast-forward, and only while no spec exists.
 */
export function refinementMarkTarget(
  story: Pick<CodeStory, 'factory_state' | 'spec_path'>,
  requiresRefinement: boolean,
): CodeFactoryState { … }
Current statespec_pathMark → falseMark → true
needs_refinement—→ ready_for_devunchanged
ready_for_devnullunchanged→ needs_refinement (undo)
ready_for_devsetunchangedunchanged — a spec exists; do not rewind past it
anything else—unchanged — the flag is recorded, the story does not move

Marking a story mid-flight (say, in ready_for_review) is therefore harmless: it records the judgement without yanking the card across the board.

6.2 The store action

Add setRefinementRequired(ref: string, requiresRefinement: boolean): Promise<void> to CodeActions. It reuses the existing private transitionState helper (code-store.tsx:635) rather than growing a parallel write path: 

await transitionState(
  ref,
  refinementMarkTarget(story, requiresRefinement),   // often === story.factory_state
  { requires_refinement: requiresRefinement },
  "Couldn't update refinement",
);

transitionState needs three small extensions so the new field rides the existing optimistic machinery: include requires_refinement in the captured rollback, set it on the optimistic patch when extra.requires_refinement !== undefined, and read it back in the reconcile patch alongside factory_state. Sending an unchanged factory_state is a deliberate no-op write — it keeps one code path for both the moving and non-moving cases.

6.3 Carrying the column everywhere a story is projected

Four projections define what a CodeStory is made of; the new column has to appear in all four or it will silently vanish on some path:

ProjectionWhy it matters
codeItemToStoryPatch (code-store.tsx:415) The single sidecar→story mapping shared by optimistic reconcile and the code_items realtime subscription. Omit it and a Worker/second-device write never reaches the board.
makeOptimisticStory (lib/tree.ts:285) Must default to requires_refinement: true. createStory overrides it — and overrides factory_state to ready_for_dev when the box is unchecked — so the optimistic card appears in the right lane immediately, exactly as it already overrides priority.
codeStoryStatusPatch (lib/code/status.ts) The navigation-refetch reconcile. Add the flag to CodeStoryStatus so a mark set elsewhere lands on a story already in the store.
createStory signature createStory(epicId, title, notes, requiresRefinement); the call site is components/code/board/epic-block.tsx:339.

6.4 The existing skip chip also records the mark

In openClaudeSession, the bypass phase writes the flag with its transition — pressing “Skip to Development” is declaring that no refinement is needed, so the two routes must leave identical rows: 

await transitionState(
  ref,
  LAUNCH_TARGET_STATE[phase],
  phase === 'bypass' ? { requires_refinement: false } : {},
  "Couldn't start session",
);

7 · Launch-prompt selection

Keep launchPhasesFor and LAUNCH_LABELS untouched: a ready_for_dev story still offers one primary Implement in Claude Code button, whether or not a spec exists. Only the prompt behind it changes, so add a dispatcher to frontend/lib/code/links.ts: 

/**
 * The development-launch prompt for a story in `ready_for_dev`: the spec-reading implementation
 * prompt when a refinement PR actually recorded one, and the SKIP-REFINEMENT prompt when it did
 * not. `spec_path` is the only honest test — the Worker sets it on refinement-PR merge, so a null
 * means no committed spec exists, however the story reached this lane (the ALF-137 mark, or the
 * closed-unmerged revert in workers/src/transitions.ts).
 */
export function buildDevelopmentUrl(project: Project, story: CodeStory): string {
  return story.spec_path === null
    ? buildBypassUrl(project, story)
    : buildImplementationUrl(project, story);
}

openClaudeSession's buildUrlForPhase map then reads implementation: () => buildDevelopmentUrl(project, story). The bypass entry keeps calling buildBypassUrl directly.

buildImplementationUrl itself is left alone. Its conventional-path fallback for a null spec_path becomes unreachable through the launch path, which is the point — it stays as belt-and-braces for any direct caller.

8 · The Worker needs no change

workers/src/transitions.ts stays exactly as it is, and that is a decision, not an omission:

  • A marked story's PR still carries phase: implementation and no spec-path, which the frontmatter parser already accepts (workers/src/frontmatter.ts:43) and the committed alfred-frontmatter check already tolerates.
  • The closed-unmerged → ready_for_dev revert (transitions.ts:122) becomes correct under this model: Ready for Dev is precisely where a no-spec story belongs, and §7 now gives it the right prompt.
  • The Worker never writes requires_refinement. The flag is a human judgement; PR events describe progress, not intent.

9.2 Story detail modal

A new sub-component frontend/components/code/story-detail/refinement-mark.tsx, rendered in the modal's header action row next to PrimaryAction and the PR links (story-detail-modal.tsx:218–228). Same control as the dialog — a “Needs refinement” checkbox — wired to setRefinementRequired, with the pending/rollback handling the sibling ManualControls already models.

  • Unchecking it on a needs_refinement story moves the card to Ready for Dev behind the modal and swaps the primary button from Refine in Claude Code to Implement in Claude Code — no tab opens.
  • Re-checking it on a spec-less ready_for_dev story undoes that.
  • It is a plain checkbox in every other state, and disabled while a write is in flight.
  • It does not go in ManualControls (“Move this story”) — that section is the linear advance/revert stepper, and this is a property of the story, not a hop.

9.3 The story card is unchanged

No third chip. A needs_refinement card keeps its two launch chips; a marked story is visible by virtue of sitting in the Ready for Dev lane, which is the whole point of the mark. A card-level menu is deferred (§12).

12 · Out of scope

  • The gate dialog. Send to Code module / Convert to Code Story keep landing items at needs_refinement; mark them from the modal afterwards.
  • Project- or epic-level defaults (“this epic never needs refinement”).
  • Automated dispatch. This ticket only creates the column the future factory will query; nothing consumes it automatically yet.
  • A card-level mark affordance (a story 3-dot menu). No such menu exists on a story card today, and adding one is its own change.
  • Backfilling the flag for stories bypassed before this ships. They keep requires_refinement = true; the history is not worth a data migration.
  • Renaming the “Skip to Development” chip. It keeps its label and its subordinate styling — only its write changes (§6.4).
