ALF-165 — Add ability to create task from folder view

StoryTasks moduleFrontend only Capture a task straight into the folder you are looking at, instead of capturing to the Inbox and dragging it in afterwards.

1 · What this story is

Every task in alfred is born in the Inbox. The hero CaptureBox lives on /, and a folder view (/folders/[id]) is read-only: it renders an eyebrow with the folder name, a Collapse-all button, and the folder's TaskList (frontend/components/tasks/folder-view.tsx). So filing a thought you already know belongs in Work costs a trip to /, a capture, a return to the folder, and a drag — or a triage pass later.

This story gives the folder view its own capture affordance. Nothing about the Inbox flow changes; this is the second door into the same store action.

The pieces already exist. This is mostly wiring:

  • CaptureBox already takes a folderId prop and already has a compact single-line mode — that is exactly what the row-level "Add subtask" affordance renders.
  • AnimatedHeightReveal already owns the grow-in / shrink-out motion for that box.
  • ActiveEditorProvider already owns the "only one inline input open at a time" invariant.
  • useScopedTasks({ type: 'folder', folderId }) already picks up an optimistic insert, so the new row appears with no refetch.

Two small gaps have to be closed for the wiring to be correct rather than merely present: a top-level capture that carries a folder currently saves as item_type: 'unclassified' (§6), and the shared empty state has nowhere to put an action (§5.3).

2 · Decisions locked during this refinement

S1The affordance is a "+" in the folder header, revealing the compact capture boxowner

An IconButton sits in the header's right cluster, left of Collapse-all, in the same grey treatment as Collapse-all — the atom's default neutral tone, not the teal accent one. Pressing it reveals a compact CaptureBox between the header and the list; pressing it again closes it. Drawn in §4.

Why not an always-visible input: the folder view is a reading surface — a second permanent textbox competes with the Inbox hero for "the place you type". Why not the full hero box: it would re-frame a folder as a capture screen and duplicate the one surface that is deliberately singular. The toggle mirrors the row-level "Add subtask" +, and the epic block's "New story" +, so it is the third instance of a pattern rather than a new one.

S2Open/closed lives in the ActiveEditorProvider, keyed by folder id

ActiveEditor['kind'] gains 'folder-capture', and the folder box is identified by { itemId: folderId, kind: 'folder-capture' }.

Why not local useState: the store exists precisely to keep one inline input open at a time. With local state the folder box and a row's title edit (or another row's add-subtask box) could be open simultaneously, each with its own draft — the exact thing that store was introduced to prevent. Registering it also inherits the correct close semantics for free (closeEditor no-ops when something else already took over). The Inbox hero box stays exempt, as its store doc says: it is always-on and has no toggle.

S3A new task lands wherever the folder's ranking puts itowner

No pinning, no re-sort, no scroll. A folder ranks by priority → due date → created_at (ALF-37), so a fresh task with neither priority nor due date appears at the end of the unprioritised group.

Why: pinning would introduce a second ordering rule that contradicts the one the view advertises, and it would have to expire on some ill-defined event ("until you navigate away"). The capture box stays open and focused after each capture, so the feedback that the capture landed is the box clearing and the count/badges updating — the same feedback the Inbox gives.

S4A top-level capture into a folder is created as a task, not unclassified

addTask resolves item_type to 'task' when a parentless capture carries a folderId. Today it would resolve to 'unclassified'.

Why this is a bug, not a preference: the store already encodes the rule — moveTask classifies any still-unclassified item as a task when filing it into a folder, because "folders hold tasks". An unclassified row rendered in a folder has no completion checkbox (completion is task-only) and offers a Classify gate instead, so a task created from the folder view could not be ticked off. Creating into a folder is filing; it classifies for the same reason.

S5An empty folder gets an "Add task" action inside its empty stateowner

EmptyState gains an optional action slot; TaskList gains emptyDescription / emptyAction passthroughs. The folder view fills both.

Why: an empty folder's description reads "Capture something above." — copy that is true on the Inbox and false in a folder, where there is nothing above. And an empty folder is exactly when the header "+" is hardest to find, because the eye is on the centred empty state. The action is only rendered while the box is closed, so it never sits under an open box as a dead control.

S6No API, schema, or migration change

POST /api/items already accepts folder_id and an explicit item_type. The classification rule of S4 is applied client-side in the store, where the identical moveTask rule already lives. No migration is added by this story.

Why not enforce it in the route: the route is a generic item factory shared with the Siri ingest path (which never sends a folder); pushing a tasks-module product rule into it would split the rule across two layers. items_task_only_fields does not constrain folder_id, so nothing at the DB level is being worked around.

5.3 The component, in outline

// components/tasks/folder-view.tsx
const editor = { itemId: folderId, kind: 'folder-capture' } as const;
const showCapture = sameEditor(useActiveEditor(), editor);
const { openEditor, closeEditor } = useActiveEditorActions();
const prefersReducedMotion = usePrefersReducedMotion();

// Keep the box mounted through its exit; drop it on the reveal's onExited — or during
// render when there is no animation to wait for (the motion skill's reduced-motion rule).
const [captureRendered, setCaptureRendered] = React.useState(showCapture);
if (showCapture && !captureRendered) setCaptureRendered(true);
else if (!showCapture && captureRendered && prefersReducedMotion) setCaptureRendered(false);

// header: eyebrow · [ + ] [ collapse-all ]
<IconButton size="md" aria-label={`Add task to ${folder.name}`} title="Add task"
  aria-expanded={showCapture}
  onMouseDown={(e) => { if (showCapture) e.preventDefault(); }}
  onClick={() => { showCapture ? closeEditor(editor) : openEditor(editor); }}>
  <Plus size={16} />
</IconButton>

{captureRendered && (
  <AnimatedHeightReveal open={showCapture} onExited={() => { setCaptureRendered(false); }}
    className={captureRevealClass}>
    <CaptureBox compact folderId={folderId} placeholder="Add task…"
      onDismiss={() => { closeEditor(editor); }} />
  </AnimatedHeightReveal>
)}

<TaskList
  scope={{ type: 'folder', folderId }}
  emptyMessage={`No tasks in ${folder.name}`}
  emptyDescription="Add your first task to this folder."
  {...(showCapture ? {} : { emptyAction: /* the ghostAccent "Add task" button */ })}
/>
exactOptionalPropertyTypes is on: spread an optional prop conditionally (as above) rather than passing undefined, the pattern folder-nav.tsx already uses.

parseProjectPrefix stays off here, as it is for the subtask box: a <project>: prefix classifies a capture as Code and strips the folder, which is the opposite of what this affordance is for. The Inbox box remains the only place it runs.

The store's item_type expression is the only line of logic this story adds: 

item_type:
  parentId === undefined
    ? (input.itemType ?? (folderId === undefined ? 'unclassified' : 'task'))  // ← S4
    : parent?.item_type === 'code'
      ? 'code'
      : 'task',
Captureitem_typeWhy
Inbox hero boxunclassified Unchanged — no folderId is passed (folderId: null normalises to undefined, so an explicit "Inbox" is still unclassified).
Inbox hero box, <project>: prefix matchedcode Unchanged — an explicit itemType still wins over the folder rule.
Folder box (new)task S4 — filing classifies, exactly as moveTask does.
Add-subtask boxtask / code Unchanged — the parent branch already decides, and it is evaluated first.

Everything else about the created row is today's behaviour: sort_order one past the largest root, raw_capture = the typed text, no due date, no priority, and the folder's sidebar badges recompute from the same store (a new task with no due date and no priority moves neither tally).

9 · Out of scope

Not in this storyWhy / what instead
The same affordance on Priority, Completed, or the weekly plan Priority is a cross-folder ranking with no single destination folder; Completed is an archive. Neither has an unambiguous "create here" target.
Setting a due date / priority / notes while capturing Capture stays one line, as everywhere else in alfred. The row's detail panel is one click away once it exists.
Creating a subtask from the folder header Already exists per-row; a folder-level box only ever creates top-level tasks.
Project-prefix parsing in the folder box Deliberately Inbox-only (§5.3) — it strips a capture out of the folder into the Code module.
A keyboard shortcut to open the box No shortcut vocabulary exists for view-scoped affordances yet; the command palette is the established fast path.
Returning focus to the "+" when the box dismisses The row-level add-subtask box behaves the same way today. Worth fixing — for both boxes, in CaptureBox, in its own change — rather than making the two diverge here.
Moving CaptureBox's compact dismiss from blur to outside-pointerdown Same reason: it is shared with add-subtask, so changing it is a change to that feature too.

Open questions

None. The three decisions this story turned on — the affordance's shape, where a new task lands, and what an empty folder offers — were settled with the owner during refinement and are recorded as S1, S3 and S5.

10 · Acceptance criteria

  • The affordance
  • A folder view header shows a "+" button named Add task to <folder>, left of Collapse-all, at every viewport width.
  • It carries the same grey icon-button treatment as Collapse-all — the IconButton default tone, at rest and on hover — so the pair reads as one cluster.
  • Pressing it reveals a compact capture box between the header and the list, focused, placeholder Add task…; pressing it again closes it, with no re-open flicker.
  • Escape, or focus leaving the box, dismisses it; opening any other inline editor (a row title edit, a row's add-subtask box) closes it, and opening it closes them.
  • Under prefers-reduced-motion the box appears and disappears with no animation and is not stranded on screen.
  • The "Folder not found" view has no capture affordance.
  • Capturing
  • Enter (or Add) creates a task in that folder; the row appears immediately, in the position the folder's priority → due → created_at ranking gives it.
  • The box clears and stays open and focused, so several tasks can be captured in a row.
  • The created item is persisted with item_type = 'task', the folder's folder_id, and no parent — it has a completion checkbox and can be ticked off immediately.
  • It does not appear in the Inbox.
  • A failed save restores the text into the box, removes the optimistic row, and toasts — unchanged CaptureBox / store behaviour.
  • An Inbox capture is still created as unclassified, and a <project>:-prefixed one still as code.
  • The empty folder
  • An empty folder reads "No tasks in <folder>" over "Add your first task to this folder." — never "Capture something above."
  • It offers an Add task action that opens the same box; the action is not rendered while the box is open.
  • The Inbox's empty state is unchanged, and so is "Folder not found".
  • Repo rules
  • No new capture input, reveal, or open/close state machine is hand-rolled — the box, the reveal, the button, and the single-open invariant all come from the existing shared layer.
  • The reveal padding class exists once and is used by both the subtask box and the folder box.
  • No API route, schema, or migration change.
  • No image-snapshot baseline is added or changed.
  • A demo doc built with npm run demo passes npm run demo -- verify and shows both the populated and the empty-folder path.
  • npm run check is green, with no new lint suppressions, no --no-verify, and no config weakened.
