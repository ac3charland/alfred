ALF-168 — Implement inbox dispatch (slice A)

StoryEpic ALF-158 · slice A Database + frontend. No LLM anywhere in this story.

Make Inbox residency an explicit fact on the row instead of something inferred from folder_id. An item is in the Inbox while dispatched_at is null, and only a human act stamps it. Nothing about the app looks or behaves differently when this ships — which is the point: it is the enabling change the rest of ALF-158 stands on, landed on its own so the risky part is proven before anything non-deterministic exists.

1 · Context & problem

Today "in the Inbox" is a derived fact, computed in two places from one column:

SurfaceRule todayWhere
Inbox listitem.folder_id === null useScopedTasks — frontend/lib/stores/tasks-store.tsx
Folder viewitem.folder_id === folderId same
Folder badgesitem.folder_id !== null useFolderBadgeCounts — same file
"Where does this live" labelsroot.folder_id !== null ? folderName : 'Inbox' lib/tasks/task-location.ts, components/shell/search-results.ts, components/tasks/priority-view.tsx, components/tasks/task-row.tsx
Keyed list endpoint.is('folder_id', null) lib/data/items.ts (GET /api/items?inbox=true)

That identity — having no folder ≡ waiting for triage — holds only while nothing but a human can write folder_id. Epic decision D4 breaks it: the classifier writes its guesses onto the item's real fields, folder_id included. Under today's rule the moment a guess lands the item disappears from the Inbox into a folder before the owner has ever seen it — the exact opposite of "waiting for me to look at", and it would happen silently.

So residency and location have to become two different facts (D5), and only a human act may change residency (D6). This story does exactly that and stops. It ships with the classifier still non-existent, so every user-visible behaviour is identical before and after: nothing in the app writes folder_id without also dispatching, so the two rules agree on every row.

The invariant this story must not break: every item is reachable from exactly one view. Today a folder deletion (on delete set null) returns its items to the Inbox for free, because losing the folder is returning to the Inbox. Once residency is its own column that stops being free — see S6, which is the one place this refactor can strand data.

2 · The rule, drawn

Residency (dispatched_at) is what moves an item between views. Location (folder_id) only says which folder it will land in.

3 · Decisions

S1The column, and what reads it

items gains dispatched_at timestamptz, nullable, no default. null = still in the Inbox. Every rule in §1's table is rewritten in terms of it: Inbox is dispatched_at === null, a folder view is folder_id === folderId && dispatched_at !== null, and a folder badge counts a row only when it is dispatched.

Why a timestamp, not a boolean: it matches the repo's existing idiom (completed_at, archived_at) and records when triage happened, which is free here and is what slice H's correction diff hangs off later.

S2Backfill: everything currently in a folder is dispatched

update items set dispatched_at = now() where folder_id is not null;

Every other row keeps null. No item changes view, which is the migration's whole acceptance test.

Why now() rather than created_at: the real dispatch time is unknown for historical rows, and created_at would assert something false (that the item was triaged the instant it was captured). The migration timestamp is honest — it means "dispatched at or before this migration" — and nothing reads the value, only its null-ness.

S3Residency travels with the subtree, exactly like folder_id

A subtree shares one folder bucket, and the client filters flat before buildTree — so if a root and its children disagreed about residency the subtree would be split across two views and the orphaned half would vanish. dispatched_at is therefore written to every row a folder_id write touches, in the same request. That covers moveTask, bulkMove, and the folderCascade shared by reparentTask / reorderSubtask.

Consequence for the cascade helper: folderCascade currently skips descendant writes when the folder is unchanged. It must now cascade when either the folder or the residency differs from the new parent's — dragging an Inbox subtask under a filed task changes residency even when folder_id happens to match.

S4The API takes an intent, and the server authors the timestamp

PATCH /api/items/[id] accepts a new optional boolean dispatched — not a raw timestamp. The route maps it: true → dispatched_at = new Date().toISOString(), false → null, absent → the column is untouched (PATCH semantics, as today). 

// filing a task, as one coherent write
PATCH /api/items/:id  { "folder_id": "…uuid…", "item_type": "task", "dispatched": true }

// returning it to the Inbox
PATCH /api/items/:id  { "folder_id": null, "dispatched": false }

Why a virtual field: no caller has a reason to choose when an item was dispatched, and letting one backdate the column would quietly corrupt slice H's diff. A boolean also reads as what it is — "this is a dispatch" — so the intent survives in the request rather than living only in a comment. Why one PATCH and not two: the DB CHECK constraints already force item_type and its type-specific fields to move together (epic D7); residency joins that same coherent write, and a half-applied move can't leave an item unreachable.

S5A new item inherits residency at insert, in the database

A before insert trigger on items fills dispatched_at when the caller left it null:

  • has a parent_id → inherit the parent's residency (dispatched if the parent is).
  • otherwise, has a folder_id → now().
  • otherwise → stays null, an ordinary Inbox capture.

Why the database and not the route: two ingresses already create filed items — the folder view's capture box (ALF-165) and the inline "add subtask" field, which passes its parent's folder_id — and Siri/service-role writes bypass the route entirely. Why parent inheritance rather than "a folder means dispatched": once the classifier can put a folder_id on an undispatched item, adding a subtask to it would create a dispatched child under an undispatched parent — the split subtree S3 exists to prevent. Inheriting is correct in both worlds, so it is written once, now.

The optimistic store must predict the same value or the new row flashes into the wrong view before reconciling: makeOptimisticItem takes the residency the row will get, and addTask computes it from the parent (which it already looks up) or the folder.

S6Deleting a folder returns its items to the Inbox — explicitly now

items.folder_id is on delete set null, so deleting a folder currently drops its items straight back into the Inbox. Once the Inbox is dispatched_at is null that stops happening by itself: the rows would keep a non-null dispatched_at with no folder and render nowhere at all. A before delete trigger on folders clears dispatched_at for every item in that folder, so today's behaviour survives.

This is the one data-loss path in the story. The behaviour it protects is already asserted end-to-end — frontend/e2e/folders.spec.ts's "Homeless task" case — but that test runs against the in-memory mock, which emulates on delete set null itself (deleteRows in frontend/scripts/mock-supabase.mjs). So the red/green pair that actually catches a missing trigger is a DB integration assertion; the E2E case only stays honest if the mock learns the same rule. Write both, in that order.

S7A CHECK makes "dispatched but nowhere" impossible

alter table items add constraint items_dispatched_needs_folder check (
  dispatched_at is null or folder_id is not null or item_type = 'code'
);

A dispatched task must hold a folder. A dispatched code item is the deliberate exception: it leaves for the factory, which has no folders.

Why enforce it at all: this is epic D17's "a task with no folder cannot be dispatched" turned into something the database will refuse rather than something each future story must remember. The failure mode it replaces is silent and unrecoverable-looking (an item that exists but renders in no view); the failure mode it introduces is a loud, immediate write error. Loud wins. It does not constrain the classifier: a guessed folder_id on an undispatched row satisfies the first disjunct.

S8Move-to-Inbox clears both fields

moveToInbox keeps meaning what it means today: folder_id → null and dispatched_at → null.

Why not keep the folder as a hint: the item would sit in the Inbox pre-filled with the very folder the owner just pulled it out of, and one press of the future bulk Dispatch would send it straight back. "Un-file" should undo the filing, not remember it.

S9The two factory RPCs stamp dispatched_at as they consume an item

enter_code_module (the gate) and convert_to_code_epic (ALF-129) each already run an update items set item_type = 'code', … on the row(s) they admit; each gains dispatched_at = now() in that same statement.

Why bother, when a gated item leaves task_items anyway: so "dispatched_at is null" means "still in the Inbox" for every row rather than "every row except the ones that took the other exit" — the sweeper (slice C) keys on that predicate, and slice H reads the dispatch event. One column, no new query.

Copy each function body verbatim from the migration that last defined it — enter_code_module from 0014_project_scoped_priority.sql, convert_to_code_epic from 0019_code_epics.sql — and change only that one assignment. Re-deriving a body from an older migration silently reverts later fixes; migration 0025 documents this exact trap.

S10One shared residency helper; no site re-derives the rule

A new pure module frontend/lib/tasks/residency.ts holds the two predicates every read site needs, and every site in §1's table calls it: 

/** An item is in the Inbox until a human dispatch stamps it. */
export function isDispatched(item: Pick<Item, 'dispatched_at'>): boolean;

/**
 * The folder an item actually LIVES in — null while it is still in the Inbox, whatever
 * `folder_id` holds. The one function that turns location into residency.
 */
export function residentFolderId(item: Pick<Item, 'dispatched_at' | 'folder_id'>): string | null;

Why extract it: the rule is about to be read from a store selector, a badge tally, three location labels and a route handler. Six copies of dispatched_at !== null && … is six places for slice D to be half-applied — and the shared-primitive layer is where this repo already puts logic with more than one caller.

S11Nothing new appears on screen in this story

No new control, chip, badge or copy. The bulk Dispatch button is slice I; showing a guessed folder on an Inbox row is slice B. The dispatch actions in this story are the ones that already exist — drag-to-folder, the row menu's Move to, the bulk bar's Move to folder, and the code gate — which now write residency alongside location.

4 · The change, layer by layer

Database — one migration, <next>_inbox_dispatch.sql

Take whatever number is free when you build it; do not reuse the one that was free when this spec was written.

  1. alter table items add column dispatched_at timestamptz; + a comment on column stating the rule (null = in the Inbox, regardless of folder_id).
  2. The backfill (S2).
  3. The CHECK (S7) — added after the backfill, or it rejects the existing rows.
  4. A partial index on (dispatched_at) where dispatched_at is null: the Inbox read and the sweeper's predicate (slice C) both select exactly that set.
  5. The insert trigger (S5) and the folder-delete trigger (S6).
  6. create or replace view task_items … — mandatory. A select i.* view freezes its column list at CREATE time, so dispatched_at is invisible to getAllItems() until the view is recreated. This is the ALF-62 bug that 0011 and 0013 both document; recreate with create or replace (no drop, so grants and security_invoker survive).
  7. The two RPC replacements (S9), then notify pgrst, 'reload schema';.

Then apply it (npm run migrate -w database <n>), commit the appended migrations-applied.log line, and regenerate frontend/lib/database.types.ts with supabase gen types — committed verbatim, never hand-edited.

API

  • lib/api/schemas.ts — updateItemSchema gains dispatched: z.boolean().optional(). createItemSchema gains nothing: the trigger owns insert-time residency.
  • app/api/items/[id]/route.ts — map dispatched onto dispatched_at after toUpdatePayload (it is not a column, so it cannot ride the field list).
  • lib/data/items.ts — getItems's inbox: true branch becomes .is('dispatched_at', null); update the doc comment that names the old rule.
  • lib/api-client.ts — moveToInbox sends { folder_id: null, dispatched: false } (S8).

Store — frontend/lib/stores/tasks-store.tsx

  • useScopedTasks: inbox → !isDispatched(item); folder → isDispatched(item) && item.folder_id === folderId. Completed is unchanged.
  • useFolderBadgeCounts: skip undispatched rows (replace the folder_id === null guard with residentFolderId(item)). Without this an undispatched item carrying a guessed folder inflates that folder's badge from inside the Inbox.
  • moveTask / bulkMove: send dispatched: folderId !== null alongside folder_id on every row of the subtree, and patch dispatched_at optimistically in the same dispatch as folder_id.
  • folderCascade + its two callers: cascade on a residency change as well as a folder change (S3), adopting the new parent's dispatched_at.
  • addTask: pass the predicted residency into makeOptimisticItem (S5).
  • removeGatedItem / settleEpicConversion: unchanged — those rows leave the store entirely.

Read sites

  • lib/tasks/task-location.ts — taskDestination routes an undispatched root to /?view=inbox even when it carries a folder.
  • components/shell/search-results.ts — the result subtitle says Inbox for an undispatched root.
  • components/tasks/priority-view.tsx — the right-hand location label, same rule.
  • components/tasks/task-row.tsx — the Completed view's context label, same rule.
  • lib/tree.ts — makeOptimisticItem carries the new field.

The E2E mock backend — frontend/scripts/mock-supabase.mjs

The Playwright suite talks to an in-memory Supabase stand-in that re-implements the database's own rules: deleteRows reproduces on delete set null, and the factory RPCs are hand-written. Every server-side rule this story adds has to land there too, or the E2E suite will keep asserting the old world and pass against a schema that no longer matches:

  • deleting a folder clears its items' dispatched_at as well as their folder_id (S6);
  • an insert inherits residency from its parent, else from its folder (S5);
  • enter_code_module / convert_to_code_epic stamp dispatched_at (S9);
  • the PATCH path passes dispatched_at through like any other column — the dispatched → timestamp mapping happens in the Next.js route, above the mock.

The CHECK (S7) is deliberately not worth reproducing in the mock: it guards against a write the app should never make, and the DB integration suite is where that is proven.

Fixtures

Item gains a field, so the compiler will point at every builder. Give the builders a derived default rather than a flat null, so the ~20 existing fixtures that say folder_id: 'f1' keep meaning "filed in f1" with no edit: 

dispatched_at: overrides.dispatched_at ?? (overrides.folder_id == null ? null : DISPATCHED_AT),

A fixed ISO constant, never new Date() — fixtures pin the clock rather than read it. Applies to e2e/support/constants.ts's makeItem and the per-file task() helpers in the Storybook stories (folder-nav.stories.tsx above all: its badge counts are seeded entirely from foldered rows, and a flat null default would silently zero them).

7 · Acceptance criteria

  • Schema
  • items.dispatched_at timestamptz exists, is nullable, has no default, and carries a comment stating that null means "in the Inbox".
  • Every pre-existing item with a folder has a non-null dispatched_at; every other item has null. No item changed which view it renders in.
  • task_items exposes dispatched_at, and its grants and security_invoker are intact.
  • A dispatched task with no folder is rejected by the database; a dispatched code item is accepted.
  • Deleting a folder returns its items to the Inbox (both folder_id and dispatched_at end null).
  • An item created with a folder, or under a dispatched parent, is dispatched on insert; an item created under an undispatched parent is not.
  • enter_code_module and convert_to_code_epic stamp dispatched_at, and neither loses any behaviour from its previous definition.
  • frontend/lib/database.types.ts is regenerated (not hand-edited) and migrations-applied.log records the apply.
  • Behaviour
  • The Inbox lists exactly the undispatched top-level items, whatever their folder_id.
  • A folder view lists exactly the dispatched items in that folder.
  • Folder attention/overdue badges count only dispatched items.
  • Filing an item (drag, row menu, bulk Move) removes it from the Inbox and shows it in the folder, exactly as before — and it, plus its whole subtree, is dispatched in one coherent write.
  • Moving an item back to the Inbox clears both fields, and its subtree comes with it.
  • Re-parenting a row under a task in another folder — or in the same folder but a different residency — cascades both fields to the subtree.
  • Search results, the By-Priority location label, the Completed context label and "jump to task" all say Inbox for an undispatched item, even one carrying a folder.
  • GET /api/items?inbox=true returns undispatched items.
  • No new control, chip or copy appears anywhere in the app.
  • Guardrails
  • Every rule above is asserted by at least one test in the suite that owns it (§6), and check is green with no new ignore directives, config edits, or skipped tests.
  • No existing image snapshot baseline moved.
  • The E2E mock backend enforces the same insert-, delete- and RPC-side rules as the migration, so no E2E test body needed editing to stay green.
  • A demo doc exists, is linked from the PR as a live blob URL, and npm run demo -- verify reproduces it.

8 · Out of scope

  • The bulk Dispatch action (epic D17, slice I) — mixed selections, per-item readiness and partial settle. This story only makes the column it will write exist.
  • Showing a folder / priority / due chip on an Inbox row, and re-deriving the bulk bar's enablement gates — slice B.
  • Anything that writes a guess: no cron, no scheduled handler, no Anthropic call, no classified_at, no intended_epic_id. Slices C, D, E.
  • Retro-dispatching or re-triaging the existing backlog. The backfill preserves the current view of every row and asserts nothing else.
  • Any UI for when something was dispatched. The timestamp is stored and never rendered.

9 · Open questions

  • Should a dispatched item ever be un-dispatched in bulk? Single-item "move to Inbox" exists (S8) and the bulk bar's Move to folder → Inbox covers a selection, so nothing is missing today. If slice I later wants an explicit "return to Inbox" action, it is that story's call — the column already supports it.
  • Does an undispatched item with a folder need a visible cue before slice B lands? Proposed no — the state is unreachable through the UI until the classifier exists, so a cue would have nothing to describe. Raised only so slice B knows it inherits the question rather than discovers it.
