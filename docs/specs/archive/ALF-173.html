Refinement spec · Code module (Software Factory)

ALF-173 — Make spikes a first-class item

Give a story titled Spike: … its own factory phase — its own launch prompt, its own committed skill, its own phase: value in the machine-readable alfred block, and its own rows in the Worker's transition table — whose deliverable is a self-contained HTML findings document in docs/spikes/ rather than a feature spec or code changes.

1 · Context & problem

The Software Factory recognises exactly three phases today. Each one is the same four things wired together:

PhaseLaunch promptCommitted skillDeliverableWorker rows
epic-refinement buildEpicRefinementUrl .claude/skills/epic-refinement/ docs/specs/epics/<EPIC-REF>.html epic: record PR / spec
refinement buildRefinementUrl .claude/skills/refinement/ docs/specs/<REF>.html → ready_for_dev on merge
implementation buildImplementationUrl .claude/skills/implement-spec/ code + the archived spec → ready_for_review / done

Research doesn't fit any of them. A story called “Spike: outbound notifications via Telegram” has only two doors out of needs_refinement: Refine in Claude Code, which writes an implementation spec for work nobody has yet decided to do; or Skip to Development, which tells the agent to build something when the whole point was to find out what to build. The code-module spec already records the gap in its own words — §5.2's manual-fallback note opens “Spikes, research, and abandoned items have no PR signal”, so today the only honest way to run a spike is to drive the card by hand.

Meanwhile the repo already contains two spike findings documents, both written outside the factory: docs/notifications-spike.md and docs/scheduled-cloud-backups.md. They independently converged on the same shape — Where we landed (the decision, up front) → Why → Technical shape (for the implementation spec to expand) → Sidebars: appealing alternatives we're not taking → Cost & open questions → Sources. That is the house spike form, waiting to be named and made repeatable.

ALF-173 makes the spike the factory's fourth phase, built the same way as the other three, and gives its output a home at docs/spikes/.

2 · Resolved scope from refinement Q&A

Question askedAnswer
Where does a phase: spike PR land the story? Spike replaces both phases. Launch → in_development; PR opened → ready_for_review; merged → done; closed-unmerged → ready_for_dev. No new states, no migration. Follow-up work becomes new stories.
Which launch buttons does a spike show? Only “Run spike in Claude Code”. It replaces Refine / Skip to Development / Implement in every launch-eligible state.
How are the merged findings recorded and displayed? Reuse spec_path / spec_sha / spec_markdown and the block's spec-path key; the detail modal renders them in the existing sandboxed frame under a Findings heading.
Is a spike visually marked on the board? Yes — a muted “Spike” badge on the story card and the detail-modal header, derived from the title prefix.

3 · Decisions locked in this refinement

D1“Spike-ness” is derived from the title. Nothing is persisted.

One new pure module, frontend/lib/code/spike.ts, exports isSpike(story): true when the title, left-trimmed and lower-cased, starts with spike:.

Why: the ticket names the title prefix as the signal, and it costs no migration, no view change, and no new column to keep in sync. Renaming a story re-classifies it instantly — which is the right behaviour for a judgement the human makes in the title anyway.

D2A spike offers exactly one launch action, in both pre-work states.

launchPhasesFor takes the story instead of the bare state. For a spike it returns ['spike'] in needs_refinement and in ready_for_dev, and [] everywhere else. Non-spike stories keep today's behaviour exactly.

Why: Refine and Implement are both wrong for a spike, so offering them invites the wrong session. Covering both pre-work states matters because a story reaches ready_for_dev by several routes (the “Needs refinement” toggle, a closed-unmerged PR revert) — a spike must stay launchable however it got there, and it is also the state a closed-unmerged spike PR reverts into (D3).

D3The lifecycle reuses the existing states — no enum value, no migration.

Launching writes in_development (LAUNCH_TARGET_STATE.spike); the Worker moves the story to ready_for_review when the spike PR opens, done when it merges, and back to ready_for_dev when it closes unmerged.

Why: a new in_spike state would mean a migration, a seventh swimlane, new labels, and a wider laneStateFor — for a story that occupies it for one session. The existing lanes already read correctly: the spike is being worked, then its PR is waiting on you, then it's done. The Review PR chip (reviewPrUrlFor) already links implementation_pr_url in ready_for_review, so the spike PR surfaces on the card with no change at all.

D4Findings reuse the spec columns and the spec-path key.

The spike PR carries spec-path: docs/spikes/<file>. On merge the Worker records it into spec_path and snapshots the file into spec_sha / spec_markdown — the same snapshotSpec path the two refinement phases use. The detail modal renders it through the existing SpecView, which already sniffs HTML and frames it sandboxed.

Why: those three columns mean “the long-form document this ticket produced”, and a spike produces exactly one. New findings_* columns would buy a nicer name at the cost of a migration, a view replace, a second parser field, a second snapshot path and a second render branch. The only visible difference is the label, and a label is cheap (D7).

D5A findings document is never archived.

The enforcing check's archive rule stays scoped to phase: implementation and paths under docs/specs/. docs/spikes/ is outside it, so nothing to exclude. The spike prompt and skill both say so explicitly.

Why: a spec is scaffolding consumed by its implementation; findings are the durable answer later sessions keep reading — the same reasoning that exempts epic specs. The prompt has to state it, because the implementation prompt in the same family does tell the agent to git-move its document.

D6Findings live in docs/spikes/; the skill owns the exact filename.

The prompt names no path — it carries the same <path-or-folder-of-the-spec> placeholder the refinement prompt does and tells the agent to follow the skill, with a one-line fallback (“a self-contained HTML findings document under the repo's spikes directory”) for a repo that has no skill. The skill pins alfred's convention: docs/spikes/<REF>-<short-slug>.html, e.g. docs/spikes/ALF-173-spike-phase.html.

Why: prompt-thin / skill-thick is the existing division of labour, and it's what lets another project put its findings somewhere else. The slug (unlike docs/specs/'s bare ref) earns its keep because findings are browsed as a library long after the ticket is closed — the ref alone is opaque a year later, and the two hand-written spikes already in the repo are named for their subject.

D7A spike's detail modal drops the refinement toggle and relabels two things.

On a spike story: the Needs refinement checkbox is not rendered; the implementation_pr_url link reads Spike PR rather than Implementation PR; and the document section's heading reads Findings (empty copy: “No findings yet. The spike PR writes them when it merges.”). Launching a spike also records requires_refinement: false, exactly as “Skip to Development” does.

Why: a spike is never refined, so a toggle promising refinement is a control that can only mislead — and the flag it writes is the one a future dispatcher would query, so the launch should set it honestly. The two label swaps are the whole cost of reusing the spec columns (D4).

D8The two hand-written spike docs move into docs/spikes/.

git mv docs/notifications-spike.md docs/spikes/ and git mv docs/scheduled-cloud-backups.md docs/spikes/, fixing the four relative links the move breaks (listed in §6.1). Filenames are unchanged, so the two documents' links to each other keep working untouched.

Why: it creates the directory the new skill points at (git tracks no empty folder) and puts real content in it, so the first agent to open docs/spikes/ sees the house form rather than a promise. Severable: this is two moves and four link edits and touches nothing else in the change — drop it if you'd rather the folder start empty.

D9The spike skill is a per-repo setup artifact, like the refinement skills.

.claude/skills/spike/SKILL.md is written here and listed in docs/code-module/repo-setup/README.md as a file to copy into each project repo, alongside the two refinement skills. The enforcing check (docs/code-module/repo-setup/alfred-frontmatter.yml) learns the new phase in the same commit.

Why: the launch prompt references the skill by path in whatever repo the session opens in, so a phase whose skill only exists here would degrade to the one-line fallback everywhere else. Actually installing it into other repos stays the credentialed per-repo step it already is (§9).

4.1 · What counts as a spike

// frontend/lib/code/spike.ts
/** The title prefix that marks a story as a spike — matched case-insensitively. */
const SPIKE_PREFIX = 'spike:';

/**
 * Is this story a spike? Derived from the title alone (nothing is persisted), so renaming a
 * story re-classifies it. Matched on the left-trimmed, lower-cased title so "Spike: ",
 * "spike:" and a stray leading space all read the same.
 */
export function isSpike(story: Pick<CodeStory, 'title'>): boolean {
  return (story.title ?? '').trimStart().toLowerCase().startsWith(SPIKE_PREFIX);
}

4.2 · The lifecycle

Teal boxes are the states a spike passes through; the two on the left are where the launch button lives. No new state, no new swimlane — the six happy-path lanes are unchanged.

The Worker's transition table gains three rows (and only three):

PhaseActionTargetColumns patchedSnapshot?
spike opened story factory_state: 'ready_for_review', implementation_pr_url no
closed & merged story factory_state: 'done', spec_path (when the block carries one) yes
closed & !merged story factory_state: 'ready_for_dev' no
Merge is the snapshot point, not open. Unlike implementation (whose spec was recorded a phase earlier) a spike's document only exists on its own PR, so spec_path is written and the file snapshotted when the PR merges. While the story sits in ready_for_review the modal's Findings section is empty and the card's Review PR chip is how you read the draft — which is exactly what a review state is for.

4.3 · The launch prompt

buildSpikeUrl(project, story) joins buildRefinementUrl's family and reuses its shared pieces verbatim: epicContextLines, htmlPreviewStep, notesContext, frontmatterBlock, SPEC_PATH_PLACEHOLDER, and the ref-plus-title first line that makes the new tab scannable. The numbered body: 

ALF-173: Spike: make spikes a first-class item

You are running a SPIKE for the ticket ALF-173. Produce a FINDINGS DOCUMENT ONLY — answer the
question and record what you found, in enough detail that a later refinement or implementation
session can act on it. Do NOT implement anything (no app or source changes) and do NOT write a
feature spec.

1. Ground yourself first: skim the repo and honor its own conventions — read any CONTRIBUTING or
   CLAUDE.md — and base your findings on the code that already exists.
2. If the title and context below don't pin down the question this spike has to answer, ASK ME
   HERE before investigating — you don't need to guess, I'm in this tab. Otherwise go ahead.
3. Investigate, then write the findings following the spike skill at
   `.claude/skills/spike/SKILL.md` (it auto-loads in a spike session) — it defines this repo's
   findings format, structure, and where the document lives. If the skill is absent, write a
   single self-contained HTML findings document under the repo's spikes directory.
4. The findings document is LONG-LIVED reference material — later sessions keep reading it. Do
   not archive or move it, and do not add it to the specs directory.
5. Open a pull request whose description carries this machine-readable block — the orchestrator
   (alfred) reads it to advance the ticket and a CI check enforces it. Reproduce the
   `alfred-ticket` and `phase` lines exactly, and set `spec-path` to where you saved the findings
   document:

```alfred
alfred-ticket: ALF-173
phase: spike
spec-path: <path-or-folder-of-the-spec>
```

6. <the shared htmlPreviewStep sentence>
7. Before opening the PR, confirm the findings document is saved, `spec-path` above names that
   document (not the placeholder), the preview link is there, and the block is reproduced exactly.

Context (from the ticket):
<notes>

Step 4 is the one line with no analogue in the other prompts, and it is load-bearing: the implementation prompt in the same module tells the agent to git-move its document into an archive, and a model that has internalised that family resemblance will helpfully do the same here. Step 6 is htmlPreviewStep(project) unchanged — the findings document is always HTML, so the “if the spec is an HTML file” conditional in the shared sentence is simply always true.

4.4 · The block and the enforcing check

phase gains a fourth legal value in three places that must stay in lockstep — the Worker's parser, the enforcing Action, and the repo-setup contract table: 

// workers/src/frontmatter.ts
export type CodePhase = 'epic-refinement' | 'refinement' | 'implementation' | 'spike';

// Alternation order still matters for the epic-/refinement pair; `spike` shares no

In alfred-frontmatter.yml the same alternation change, plus spike joins the phases that require spec-path (a spike PR with no findings path would merge into a story with nothing to snapshot): 

const SPEC_PATH_PHASES = ["refinement", "epic-refinement", "spike"];

6.2 · The launch layer

// frontend/lib/code/launch.ts
export type LaunchPhase = 'refinement' | 'implementation' | 'bypass' | 'spike';

/**
 * The ordered list of launch phases a story offers. A SPIKE offers exactly one — its own
 * session — from either pre-work state: `needs_refinement` and `ready_for_dev` are both
 * reachable before the spike runs (the refinement mark, a reverted PR), and neither
 * `refinement` nor `implementation` is the session a spike wants.
 */
export function launchPhasesFor(story: Pick<CodeStory, 'factory_state' | 'title'>): LaunchPhase[] {
  const state = story.factory_state;
  if (isSpike(story)) {
    return state === 'needs_refinement' || state === 'ready_for_dev' ? ['spike'] : [];
  }
  if (state === 'needs_refinement') return ['refinement', 'bypass'];
  if (state === 'ready_for_dev') return ['implementation'];
  return [];
}

export const LAUNCH_LABELS: Record<LaunchPhase, { idle: string; busy: string }> = {
  // …unchanged…
  spike: { idle: 'Run spike in Claude Code', busy: 'Opening spike' },
};

export const LAUNCH_TARGET_STATE: Record<LaunchPhase, CodeFactoryState> = {
  // …unchanged…
  spike: 'in_development', // one session produces the findings; there is no separate build phase
};

In the store, the spike launch joins bypass in recording the judgement that this story will never get a spec:

6.3 · The spike skill

.claude/skills/spike/SKILL.md is the highest-leverage file in this change: it steers every future spike session in every repo it is copied into. Per CLAUDE.md, read the skill-creator skill before writing it, walk its “Writing a description that triggers” checklist against the draft, and run npm run lint:skills -w tools/skill-lint while drafting. It must cover:

  • The deliverable: one self-contained HTML findings document — inline <style>, no build step, no external dependencies, opens in a browser, mobile-friendly — at docs/spikes/<REF>-<short-slug>.html, with a <title>/<h1> of <REF> — <spike title>.
  • The document's shape, which is the form the repo's two existing spike documents already converged on: Where we landed (the recommendation stated first, not buried) → Why, with the evidence → Technical shape for a later spec to expand → Sidebars: appealing alternatives we're not taking → Cost & open questions → Sources, with real links.
  • Findings must be grounded. Read the code, run the command, hit the endpoint, check the version — record what was actually observed and cite it (file paths, command output, source links). A spike that only reasons from memory is the failure mode this skill exists to prevent.
  • No implementation in the PR. Throwaway experimentation is encouraged locally; the PR contains the findings document (and, under D8's convention, nothing else). Do not write a feature spec either — a spike answers a question; the answer may or may not become one.
  • Never archived, never moved — the mirror of the implement-spec archive rule, stated because the sibling convention pulls the other way.
  • The alfred block with phase: spike and spec-path pointing at the findings document; one story per spike PR; iteration happens in PR comments.
  • Say so when it isn't a spike. If the question is already answered in the repo, or the story is really an implementation ticket wearing a Spike: prefix, stop and tell the human rather than manufacturing findings — the counterpart of the refinement skill's “not a clean one-story spec? say so”.

9 · Out of scope

  • Installing anything into other project repos. Copying the new skill and the updated alfred-frontmatter.yml into each project repo stays the credentialed, per-repo Phase-C step the repo-setup README already describes. This ticket writes the artifacts and documents the step.
  • Creating follow-up stories from findings. A merged spike lands at done; turning its recommendation into a refinement ticket is a human action in the board's New Story dialog. No auto-creation, no linkage column.
  • A “Spike” option in the New Story dialog. Typing the prefix in the title is the whole interface (D1); a checkbox that types it for you is a separate, later convenience.
  • Converting the two moved documents to HTML. D8 moves notifications-spike.md and scheduled-cloud-backups.md as they are. They predate the convention and stay markdown; only new findings are HTML.
  • A spikes index or browse surface. docs/spikes/ is a directory, not a view in the app. The detail modal renders the one findings document attached to its story.
  • An in_spike state, lane, or filter — explicitly rejected in D3.

Open questions

  • Does a spike ever want a second session? Today a closed-unmerged spike PR reverts to ready_for_dev, where the button is offered again — that is the retry path. If it turns out spikes routinely need a follow-up run after merging, the answer is a new story, not a new state; revisit only if that proves wrong in practice.
  • Nothing in the app enforces that a spike's findings landed in docs/spikes/ — the skill says so and the reviewer sees the path in the PR, but the enforcing check only requires that some spec-path is present. Deliberate: the path convention is per-repo (D6), so the check stays path-agnostic.
