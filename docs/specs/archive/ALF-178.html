Refinement spec · Tasks module · Inbox

ALF-178 — Somehow visually distinguish inbox items which are ready for dispatch

A cue on the Inbox row that says this one will go when you press Dispatch — derived from the readiness rule that already exists. Four treatments were drawn; the owner picked option 2, the ready pip. Subtle enough not to clutter a triage list, glanceable enough to read the whole Inbox in one pass.

1 · Context & problem

ALF-170 shipped Dispatch: in the Inbox's select mode, one press sends every ready selected item to its own destination — a task to its labelled folder, a code item through the factory gate — and leaves the unready ones selected with a line naming what each is missing. The rule behind "ready" lives in one pure function, frontend/lib/tasks/dispatch.ts, and is already fully unit-tested.

The problem is when you learn the verdict. Today readiness is invisible until you have already entered select mode and chosen a set — the readiness line renders inside InboxBulkBar, which only mounts once at least one row is selected. So the ordinary Inbox — the list you actually triage in, the one you scan to decide what to fix and what to send — shows the inputs to the decision (the Type badge, the Folder chip, the Project and Epic chips, all put there by ALF-170 precisely because "a label you cannot see is a label you cannot check") but never the verdict. You re-derive it per row, in your head, every pass.

What the row is missing is one bit, not a new fact. Every input to dispatchReadiness is already on screen. The row can therefore say "ready" without any new column, endpoint, store field or fetch — this story is a rendering change and nothing else. That is what keeps it small enough to be worth doing, and it is the constraint the whole spec is written against.

The ticket's refinement note sets the bar for the cue itself: subtle enough to not clutter the inbox or distract, but clear enough to be glanceable. §4 offers four treatments against that bar, each drawn in the app's real palette, in every row state it has to survive.

Where the verdict is computed today, and what this story adds

Three callers of one pure function, which is the whole point: the cue on the row and the items the press actually sends can never disagree, because they ask the same question of the same code. A cue derived any other way — a second predicate, a stored flag, a "looks filled in" heuristic — could drift, and a cue that lies about what Dispatch will do is worse than no cue.

3 · Decisions

These hold whichever treatment §4's pick lands on. They are the part of the story that is not a matter of taste.

D1Derived per render from dispatchReadiness — never stored, never fetched

The row calls the same pure function the bulk bar and the store already call. No column, no view change, no API field, no store selector, no memo cache.

Why: readiness is a function of fields already on the row, and it changes the instant one of them does. Anything persisted would need invalidating on every label edit — the exact class of bug the residency and readiness modules were both built to make impossible by staying pure. It also means this story adds zero migration, route or store surface; see §5.

D2Mark the ready rows, not the gaps

The cue appears on rows that will dispatch. An unready row gets nothing added (option 4 in §4 is the deliberate exception — it de-emphasises the unready rows instead, and is offered precisely so the owner can weigh that inversion).

Why: the ticket asks to distinguish the ready ones, and the two framings are not equivalent in cost. Marking gaps means the majority of a fresh Inbox carries chrome, and it duplicates a job the bulk bar already does better — the readiness line names which gap, in words, where marking a row could only say "something's missing". Marking readiness says the one thing the row cannot otherwise say and the bulk bar cannot say early enough.
Consequence: if in practice nearly every row is ready — a plausible end state once the classifier is good — the cue stops discriminating and the inverse becomes the better read. That is a real risk, not a hypothetical; it is logged as the one open question in §9 and is a one-line flip if it materialises.

D3The same gate as the provenance mark: top-level, undispatched, outside Completed

The cue renders only where isInboxRow is already true in task-row.tsx — parent_id === null && !isCompletedView && !isDispatched(node) — and then only when readiness says yes. No cue in a folder view, the priority view, the weekly plan, the Completed view, or on a subtask.

Why: Dispatch is an Inbox action over top-level rows. A "ready to dispatch" cue on a row that has already been dispatched is a contradiction; on a subtask it promises an action that row will never be offered. Reusing the existing constant rather than writing a second condition is what keeps the Type badge, the provenance mark and this cue from ever gating differently.

D4Binary. The row says ready; the bulk bar still owns why not

One state, present or absent. The row never renders needs a folder / needs an epic / still saving.

Why: six blockers rendered per row is a second metadata cluster, and the row already carries the answer — a task with no Folder chip is missing a folder, visibly. The blocker strings exist to summarise a selection ("2 not ready — 1 needs a type, 1 needs a folder"), which is a sentence only the bulk bar is positioned to write. Splitting the labour this way also keeps the cue's whole visual budget at one bit, which is what lets it be as small as §4's treatments are.

D5Inert, and present in both the ordinary row and select mode

A <span> in every mode — no click, no popover, no menu — carrying an accessible name and a native title of “Ready to dispatch”. It renders in the ordinary row and in the select-mode branch.

Why inert: the only action it could offer is Dispatch, which is the bulk bar's, and select mode's row is one <button> — a nested control there is invalid HTML with undefined activation behaviour. Being inert by construction means one component works in both branches, exactly as ClassificationMark does.
Why both modes: the ordinary row is where you decide what to select; select mode is where you watch the set you are about to send. A cue that vanished on entering select mode would disappear at the moment of the press. The wording matches the bulk bar's own disabled hint (“Nothing in the selection is ready to dispatch”) so the row and the bar speak one vocabulary.

D6Green is the only free row-state colour — and presence, not hue, carries the signal

Where a treatment needs a colour it takes --color-accent-green (#34d399). Teal, blue, amber and red are all spoken for as row states (interactive / selected / drop target / search highlight; due; due today; overdue and high priority), and grey is now the provenance register.

Why green survives the audit: it appears on a task row today only inside a chip's own fill — a project whose palette slot is green (project-color.ts) — and in Habits. It has no row-state meaning to collide with. The residual collision is honest and worth naming: a code row whose project is the green one shows a green chip near a green cue. It is tolerable because the two differ in shape, size and position, and because the cue is drawn once per row while the chip is a label.
Why this passes WCAG 1.4.1 rather than leaning on colour: the cue is binary presence or absence, never green-versus-another-hue, so no hue discrimination is required to read it; and D5's accessible name makes the state available to a screen reader outright. Option 4 is the one treatment that encodes by contrast instead of presence, which is the weakest channel for low-vision reading — stated in its costs rather than buried here.

D7The cue is not the provenance mark's second job

It is a separate element with its own name, never a fourth state of ClassificationMark, and never a recolouring of it.

Why: ALF-180's D4 is explicit that the mark answers "where did these labels come from?", a fact about the past — never "do you accept these?", a task in the present. Readiness is a fact about the future ("what will happen when you press Dispatch"), and the two are independent: a classifier-labelled row can be unready and a hand-claimed row can be ready. One glyph cannot carry two orthogonal axes without meaning neither. Options 1 and 2 place the cue next to the mark, which is a layout adjacency, not a merge.

D8It flips live, with no new plumbing — and it costs no mobile row height

Picking a folder from the row's Folder chip flips the cue on when the PATCH reconciles, through the store update the row already re-renders on. Nothing is subscribed to, nothing polls.

Why it's free: the row re-renders from the tasks store on every optimistic patch, and D1 re-derives readiness during that render.
And the mobile footer is safe: RowMetaCluster renders nothing at all when a row has no metadata, so on a phone a bare capture stays one line. A ready row always carries at least one chip already (a ready task has its Folder chip; a ready code item has its Project and Epic chips; both carry a Type badge), so hasMeta is already true wherever the cue can appear. Adding the cue to that cluster therefore cannot grow a second line on any row — the cost ALF-180 declined to pay for the provenance chip is simply not incurred here. This is the strongest argument for option 2 and it applies to no other element that could be added to that cluster.

4 · The pick — four treatments, drawn decided · option 2

All four carry the same rule (§2), the same gate (D3), the same single state (D4), the same inertness and accessible name (D5), and the same live flip (D8). They differ only in where the cue lives and how much chrome it costs, running from most explicit to most ambient. Flip between them below; the same four rows are drawn each time, and they are the four rows of the existing InboxScreen · MidTriage story fixture — two ready, two not.

The owner picked option 2, the ready pip, which is also the option this document argued for. All four stay drawn: the rejected three are why the chosen one is the chosen one, and a later session asking “why not just put it on the title?” should be able to see the answer rather than re-derive it. The demo opens on option 2, which is also what a reader with scripting off sees.

The design question underneath the pick. "Glanceable" in a list has a specific meaning: a cue you can read without reading the rows. That needs alignment — a cue at the same x on every row forms a column the eye resolves in one saccade, while a cue whose position depends on the title length has to be hunted row by row. Set against that is proximity: a cue next to the title annotates the item, while one out at the row's edge annotates the row. The four options trade these against each other, and that trade — not the prettiness of the glyph — is what the pick was really choosing between.

An 11px lucide CircleArrowRight in text-accent-green/90, set immediately after the provenance mark at the end of the title, joined to it the same way the mark is joined to the text. No pill, no border, no fill.

No element at all, and the one treatment that inverts D2: a ready row is drawn exactly as today, and an unready row steps down a level of contrast — its title to text-muted-foreground and its chip cluster to opacity-55 — plus an sr-only span so the state is still announced.

And it is the one treatment that encodes by contrast rather than presence, which is the channel that fails first for low-vision reading (D6).

The decision: option 2, the ready pip. It is the only treatment that gets alignment — the property that makes a list cue glanceable rather than merely present — without spending the row's contested leading edge (option 3) or its contrast channel (option 4). It mounts once instead of twice, in the cluster that already holds every label readiness is computed from, so the verdict reads as the last word of the evidence rather than as a sixth independent fact. And D8's argument is uniquely available to it: because a ready row always already renders a chip, adding the pip to that cluster cannot cost a mobile row a second line — the exact price ALF-180 declined to pay for a provenance chip.

What the pick costs, and what §5 and §6 therefore carry: a bare dot is a symbol rather than a word, so its accessible name and title are load-bearing and get their own assertions; and its column property is a desktop property, so the phone drawing below is part of what was signed off, not an afterthought.

Written for the chosen treatment (option 2). The rule, the gate, the wording and the tests would have been the same under any of the four; the mount is the part that is option-specific, so §5.3 keeps a record of what each rejected treatment would have moved instead — history for a later reader, not work for this story.

Add showReadyPip to hasMeta even though it is provably redundant. The cluster returns null when a row carries no metadata, and by D8 a ready row always carries a chip — so the term can never be the one that flips hasMeta true, and therefore can never cost a phone a second line. 8 · Acceptance criteria

Written against §4's pick. Where a criterion says "the cue", read it as option 2, the ready pip — a 6px bg-accent-green/80 dot as the last child of RowMetaCluster, drawn in §4.

  • An Inbox row that dispatchReadiness calls ready shows the pip, drawn as §4's option 2; a row it calls unready does not.
  • Readiness on the row is computed by calling dispatchReadiness itself — no second predicate, no stored flag, no new column, route, store field or fetch.
  • Every row of §2's table is honoured on screen: a task with a folder and a childless code item with both hints are marked; a task with no folder, a code item missing either hint, a code item with children, an unclassified row and a temp-id row are not.
  • The pip is the last child of the metadata cluster, after the subtask and overdue counts, so it lands at a fixed offset from the row's right edge — the alignment the pick was made for.
  • The cue appears only on top-level, undispatched rows outside the Completed view — no cue in a folder view, the priority view, the weekly plan, the Completed view, or on a subtask — and the gate is the existing isInboxRow constant, not a second expression.
  • The cue renders in both the ordinary row and the select-mode row, and is never interactive in either: not a button, no click handler, opens nothing.
  • It carries the accessible name “Ready to dispatch”, from the same exported constant the bulk bar's disabled hint reads, so the row and the bar can't drift apart in wording.
  • The row never renders a blocker reason; naming what is missing stays the bulk bar's readiness line (D4).
  • Setting a folder on an unready Inbox row from the row's own Folder chip makes the cue appear once the PATCH reconciles — no reload, no remount, no new subscription.
  • The metadata footer's height is unchanged on mobile: no row that did not render a footer before renders one now.
  • The provenance mark is untouched — same glyphs, same three states, same greys, same placement — and the readiness cue is a separate element with its own name (D7).
  • The rows the Inbox marks are exactly the rows a subsequent Dispatch press sends, asserted end to end in inbox-dispatch.spec.ts.
  • Story fixtures show both states side by side, and the image snapshots the change moves are regenerated with the repo's own tooling and committed alongside the demo doc that shows their diff.
  • check is green; no guardrail config was edited and no ignore directive added.

9 · Out of scope & open questions

Deliberately not in this story

  • Any per-row Dispatch affordance. The cue reports readiness; it does not become a button, and no “Dispatch this one” entry is added to the row menu. Dispatch stays the bulk bar's, which is where partial-settle behaviour lives.
  • Sorting or filtering the Inbox by readiness. Floating ready rows to the top, or a “ready only” filter, is a different story with its own argument — and it would fight the capture-order reading the Inbox depends on.
  • A count anywhere. No “3 ready” in the Inbox header, no folder-style badge. The bulk bar already counts the selection; counting the whole Inbox is a separate claim about what the header is for.
  • Blocker reasons on the row — D4. The words stay in the bulk bar.
  • Any animation. The cue appears on the reconcile like any other chip; a row you have just given a folder should not flash. If a transition is ever wanted it is a motion-token question, and the motion skill owns it.
  • Touching dispatchReadiness's rules. If a rule is wrong (say, a code item with only completed children ought to be dispatchable) that is its own ticket — this story renders the rule as it stands.
  • A row wash. Not offered, on purpose: ALF-180 measured that treatment and it lost to the row's own state channel — hover (bg-secondary/30), the selected row (bg-accent-teal/5) and the drop target all paint over a background tint, so the row you point at is the one that loses its cue. Re-offering it here would ask the owner to re-decide a settled question.

Open

  • Nothing blocking. §4's one decision is settled — option 2, the ready pip — so the spec is ready to build. The other three treatments stay drawn as the record of why.
  • Does positive marking survive a good classifier? D2's consequence. If most Inbox rows arrive ready, a cue on nearly every row stops discriminating and the informative signal becomes its absence — at which point option 4's inversion is the better read. Worth revisiting after a fortnight of real use rather than guessing now; the predicate and the gate are shared either way, so the flip is small.
