Story spec · epic ALF-158 (LLM processing)

ALF-180 — Add subtle visual indicators for AI-classified vs human claimed

An Inbox row already knows who filled in its labels — the classifier, or you. Nothing shows it. This story renders that one bit (well, one-of-three) on the row, and nothing else: no accept, no reject, no confidence, no diff.

The whole change in a sentence. Derive a three-way ClassificationOrigin from two columns that already reach the browser (classified_at, classified_provider), and draw a small monochrome mark for it on Inbox rows only. No migration, no API change, no store change, no new query.

Treatment — decided: option 2, the title glyph. An 11px monochrome glyph set immediately after the title text, no pill. §4 keeps all four drawings as the record of what it was chosen against; §5 builds only this one.

1 · Why this exists, and why it doesn't contradict the epic

Epic ALF-158's D4 is blunt: guesses are written to the item's real fields, and “a machine-set chip is visually indistinguishable from one the owner set.” It rules out a suggestion sidecar, a confidence badge, ghosted styling and an accept/reject affordance. This story adds a mark to the row. That looks like a reversal, so it is worth being exact about what D4 was actually protecting, because the answer constrains the design.

D4's argument has two halves, and only one of them is about pixels:

What D4 rules outWhyStill holds?
A “suggested” state with an approve/reject step It creates a second thing to do on top of the thing you wanted, which was to glance and move on. Yes — untouched
A proposed-vs-real split in the data Every store, selector, filter, count and view would have to know about it. Yes — untouched
Ghosting / dimming the guessed values A label you're meant to act on shouldn't read as provisional. Yes — the chips are drawn exactly as today
Any mark at all saying who filled the row in Assumed to imply the three above. No — this is the amendment

The distinction this story rests on is provenance is not a proposal. A provenance mark answers “where did these labels come from?”, which is a fact about the past; a suggestion asks “do you accept these?”, which is a task in the present. The first adds nothing to the queue of things you must do — you can ignore it forever and the Inbox behaves exactly as it does today. D4's real invariant is no second job, and this story keeps it: the mark has no click target, no menu, no state of its own, and is derived from columns that already exist.

What the mark buys, concretely, during a triage sitting:

  • It calibrates how hard you read a row. A row you labelled yourself last Tuesday doesn't need re-checking; a row the model labelled does. Today both look identical, so every row gets the same suspicious second look — which is exactly the review tax D4 wanted to avoid.
  • It tells a blank row apart from a blank row. Under D8 abstention is a first-class answer, so a bare Inbox row is ambiguous today: the model looked and had nothing to say, or the sweeper simply hasn't reached it yet. Those call for different behaviour (fill it in vs. wait ten seconds and reload), and the data already distinguishes them.
  • It makes the correction loop legible. D15 logs your overrides at dispatch, invisibly. Seeing “this one is the model's, that one is mine” is the only place the loop surfaces at all — still write-only, still no diff view.
Guard rail for the implementation session. If a change here would make any store, selector, filter, count, sort or query read the classification columns, it has left this story's scope and re-opened D4's second half. The columns are for rendering one mark, nothing else.

2 · The data already says all of this

Migration 0029_llm_classifier.sql shipped the provenance this story renders, and the frontend already receives it: getAllItems() reads task_items with select('*'), the view was re-expanded in 0029 §5 so the new columns ride along, and Item (the generated row type) carries them. Nothing needs fetching, storing or migrating.

Two columns, read together, give four data states:

classified_at classified_provider What happened Rendered as
null null The sweeper hasn't judged this row (it is eligible, or it exhausted its attempts). Not yet classified
set set ('anthropic') The classifier wrote a verdict — including a verdict that abstained on every field. Labelled by the classifier
set null The items_claim_from_classifier trigger stamped it: a human edited a classifier-written field, so the row is yours and the sweeper will never revisit it. Labelled by you
set set, then edited Not a state. The trigger's first condition is new.classified_at is null, so once the classifier has stamped a row your later edits do not clear the provider. Labelled by the classifier (see D5)

The mapping is therefore a two-line pure function, and the fourth row above is the reason it must be written in exactly this order: 

// frontend/lib/tasks/classification.ts
export type ClassificationOrigin = 'model' | 'claimed' | 'unjudged';

export function classificationOrigin(
  item: Pick<Item, 'classified_at' | 'classified_provider'>,
): ClassificationOrigin {
  if (item.classified_at === null) return 'unjudged';
  return item.classified_provider === null ? 'claimed' : 'model';
}

How a row moves between the three

Three destinations, and the only one you can leave is the first. Once a row is marked — by the classifier or by your own hand — it never changes mark again.

3 · Decisions

D1Item-level provenance, never per-field owner

One mark per row, meaning “these labels came from …”. Not one mark per chip.

Why: per-chip marking needs classified_guess parsed in the browser and diffed against the live fields — a jsonb column 0029 documents as “Never rendered, never read by the app”, whose one consumer is the dispatch-time diff trigger. Reading it in the UI would put a second, drifting copy of the diff rule in the frontend and drag the marking into the per-field chrome D4 rejected. Item-level costs two nullable columns already on the row.

D2Three states, including “not yet classified” owner

model · claimed · unjudged. All three get a mark; the vocabulary is identical across every option in §4.

Why the third: without it a bare row is ambiguous between “the model abstained” (D8's designed-for outcome — fill it in yourself) and “the sweeper hasn't run yet” (wait). D10 makes those genuinely different rows, and the cron interval means the second is common for the minute after a capture.

D3Inbox rows only — top-level, undispatched, outside Completed owner

The gate is node.parent_id === null && !isCompletedView && !isDispatched(node) — byte-for-byte the condition task-row.tsx already uses for the Task half of showTypeBadge. Extract it once as a local isInboxRow and let both read it.

Why each clause: top-level because the sweeper's predicate is parent_id is null — a subtask is never eligible, so marking one “not yet classified” would be a promise nothing intends to keep (and the claim trigger fires on subtask edits too, stamping a meaningless classified_at). Not dispatched because provenance is a triage aid; once the item is filed the question is settled. Not Completed view because an Inbox item can be completed in place and the Completed view's rows are a history list, not a queue. Together the three clauses are exactly “an Inbox row”, which is why folder, priority and completed views need no change at all.

D4The mark is inert — no click, no popover, no menu

It renders as a <span> in every mode. Its accessible name comes from aria-label (or an sr-only span where the treatment has no element of its own), plus a native title so a pointer hover reveals the same words.

Why: two reasons that point the same way. The moment it is clickable it is an affordance, and the only actions it could offer — accept, reject, re-run — are precisely the second job D4 forbids. And the select-mode row is a single <button>: a nested interactive element there is invalid HTML with undefined activation behaviour, which is why every chip in RowMetaCluster already has an inert form. An always-inert mark needs no such fork. The repo has no tooltip primitive; title= is the established fallback (collapse-all-button.tsx).

D5“Not yet classified” means not judged, not judging now

The frontend never mirrors the Worker's ATTEMPT_CEILING. A row that burned its five attempts keeps the unjudged mark forever, and that is correct rather than tolerated.

Why: the alternative is a fourth state whose only input is a constant that lives in workers/src/sweep.ts, in a different npm workspace with no import path to the frontend. Copying it buys a distinction the owner sees perhaps twice a year and creates a number that can silently drift out of step with the sweeper. Wording the state as not judged rather than queued makes the copy honest for both cases and deletes the whole question. Same reasoning covers the once-classified-then-edited row in §2's fourth line: the mark says where the labels came from, and they came from the model.

D6Monochrome — the shape carries the state, not the colour

Every mark is drawn in the muted-foreground family at three weights. No new colour token, and no reuse of an existing accent. (Option 4 is the single exception, and that is counted against it in §4.)

Why: the row's colour language is already fully spoken for — blue is due/low/links/focus, amber is due-today, red is overdue/high, teal is interactive, selected and drop-target, and the project palette cycles through all five. A sixth meaning in any of those colours reads as one of the five it borrowed. Grey is the only unclaimed register, and “subtle” is the word in the title.

D7The mark flips live when you claim a row, with no new plumbing

Edit a label on a model-classified row and the mark stays classifier (D5). Edit one on an unjudged row and it becomes yours as soon as the PATCH settles — no reload.

Why it already works: the claim happens in a database trigger, the route returns the updated row (.select().single()), and optimistic-mutation upserts what comes back. The stamped classified_at arrives on reconcile and the mark re-derives from it. Worth a test precisely because nothing had to be built for it — an optimistic-patch shortcut added later could quietly break it.

D8No live update when the classifier writes — accepted

items has no realtime subscription (only code_items and epics do). A verdict written by the cron Worker while the tab is open appears on the next load or router.refresh(), so an unjudged mark can sit stale for a while.

Why not fix it here: subscribing items to realtime is a data-flow change affecting every view that reads the store — a bigger and independently valuable story. Shipping the mark without it is strictly better than today, and the failure mode is a mark that is momentarily pessimistic, never wrong in the other direction. Listed in §9.

4 · The pick — four treatments, drawn decided · option 2

All four carry the same three states (D2), the same gate (D3), the same inertness (D4) and the same wording. They differ only in where the mark lives and how much chrome it costs, running from most explicit to most ambient. Flip between them below; the same four rows are drawn each time.

The owner picked option 2, the title glyph, over the chip this document originally recommended. All four stay drawn: the rejected three are why the chosen one is the chosen one, and a later session asking “why not just a pill?” should be able to see the answer rather than re-derive it. Option 1 — Provenance chip not picked

A glyph-only Badge variant="muted" in the first slot of RowMetaCluster, before the Type badge: an 11px lucide glyph (Sparkle / Pencil / CircleDashed) with tightened padding and no text. Reading order becomes provenance → type → folder → project → epic → due → repeat → priority → counts.

Mounts in row-meta-cluster.tsx, one new element, no row-level change.

Buys the existing pill vocabulary, the footer's mobile wrap and the display:contents desktop inlining for free; an unambiguous test target (getByLabelText); zero collision with any existing colour or state treatment.

Costs a real element in the densest part of the row, and the mobile second line on a bare capture drawn above — hasMeta must now include the mark, so every Inbox row renders the footer.

Option 2 — Title glyph chosen

The three glyphs at 11px, set immediately after the title text, at text-muted-foreground/60. No pill, no border, no fill.

Mounts in task-row.tsx — the ordinary row's title span and the select-mode branch's title, which are not the same mount (see below).

Buys the lightest visible chrome of the three glyph treatments; anchors provenance to the text, which is the thing that was classified, rather than to the labels, which are its output; no change to hasMeta, so a bare capture keeps its single line on every viewport; and no collision with any existing colour or state treatment, since it is grey and sits nowhere near the row's edges.

Costs two mount sites rather than one, and a glyph living inside running text — both of which have a specific consequence, resolved below rather than left for the build to discover.

Two structural details the drawing hides

Setting a glyph after the title is not one change made twice: the two branches treat the title differently, and each treats it in a way that would swallow a naive mount.

BranchWhat the title does thereWhere the mark goes, and why
Ordinary row The title span carries titleTextClass, which includes break-words — a long title wraps across lines. Inside the title span, after the text, joined to it by a non-breaking space. Appended as a plain sibling the glyph is a separate inline box with a break opportunity in front of it, so a title that fills its last line to the edge pushes the glyph onto a line of its own — a lone mark floating under the row, which nothing else in the app does. The   removes that break opportunity, so the glyph travels with the final word instead.
Select mode The title is min-w-0 flex-1 truncate — one nowrap line, clipped with an ellipsis. Outside the title span, as its next sibling with shrink-0. Inside, the mark is part of the overflowing content, so on any title long enough to truncate the ellipsis eats it and the row silently loses its provenance — in the one mode where you are choosing what to dispatch. As a sibling it always renders, immediately after the clipped text.

Both are worth an explicit test (§6): a long-title row in each branch, asserting the mark is still found. They are also the reason the mark stays a self-contained component rather than two inline snippets — the placement differs, the component does not.

Option 3 — Edge rail not picked

A 2px full-height bar pinned to the row's leading edge, inside the row's paddingLeft so nothing shifts: solid grey for the classifier, faint grey for yours, near-invisible border-toned for unjudged. Plus an sr-only span for the name.

Mounts in task-row.tsx's row wrapper, as an absolutely-positioned span (both branches).

Buys zero horizontal space and, uniquely, a column you can scan down the whole list at once rather than reading row by row.

Costs three states that must stay legible as three widths of the same grey — the weakest discrimination of the four. It also lands in the row's most crowded state channel: the search highlight (ring-2 ring-inset ring-accent-teal), the drop-target ring, and select mode's ring all draw on that same edge, so the rail is hidden or ambiguous in exactly the states where the row is being acted on. On mobile it sits inside the card's own border, 4px from it.

Option 4 — Row wash not picked

No element at all: a whole-row background tint — bg-accent-teal/[0.05] for the classifier, none for yours, bg-muted-foreground/[0.045] for unjudged — plus an sr-only span for the name.

Mounts in task-row.tsx's row class list.

Buys the least chrome possible; the Inbox reads as banded groups at a glance with nothing added to any row.

Costs D6 — it cannot be monochrome and still separate three states, so it spends the teal. And the teal it spends is already taken: hover (bg-secondary/30) paints over the wash, so the row you are pointing at is the one that loses its provenance; select mode's selected row is bg-accent-teal/5, one hundredth of an alpha from the classifier wash, so in select mode a classified row reads as selected; and the drop-target wash is teal again. Flip the demo to Hover row 1 and Select mode with treatment 4 picked to see both.

The decision. Option 2, the title glyph. This document originally recommended option 1 on reuse grounds — it borrows the existing pill vocabulary and needs one mount site instead of two. The owner picked option 2, and the trade it makes is the better one for a mark whose whole brief is the word subtle: a pill is a label, and the row already carries four of them, so a fifth reads as a fifth fact about the item rather than as a note about where the other four came from. A bare glyph beside the text reads as an annotation, which is what it is. It also keeps the badge footer untouched, so a bare capture stays one line on a phone — option 1's one real cost, avoided rather than accepted.

What the pick costs, and what §5 and §6 therefore carry: two mount sites instead of one, each with a specific failure mode (the wrap orphan and the truncate clip) that is now specified and tested rather than left to be found.

8 · Acceptance criteria

  • A pure classificationOrigin() maps classified_at + classified_provider to model / claimed / unjudged, checking classified_at first.
  • An Inbox row whose classifier verdict was written shows the Labelled by the classifier mark as an 11px monochrome glyph immediately after the title text — option 2, drawn in §4.
  • An Inbox row claimed by a human edit shows Labelled by you.
  • An Inbox row the sweeper has not judged shows Not yet classified — including a row that has exhausted its attempts.
  • The mark appears only on top-level, undispatched rows outside the Completed view: no mark on a subtask, a dispatched row, a folder-view row, a priority-view row or a completed row.
  • The mark is never interactive: it is not a button, has no click handler and opens nothing, in both the ordinary row and the select-mode row.
  • Every mark carries an accessible name matching its legend copy, and the same words as a title.
  • A row with a long, wrapping title keeps its mark attached to the title text rather than dropped onto a line of its own; the same row in select mode keeps its mark rather than having it clipped by the title's ellipsis.
  • The badge cluster is untouched: a bare unjudged capture renders no metadata footer, so it stays a single line on a phone exactly as today.
  • Editing a label on an unjudged Inbox row flips its mark to Labelled by you once the PATCH reconciles, with no reload; editing one on a classifier-marked row leaves the mark alone.
  • No store, selector, filter, count, sort, query, API route or migration changed.
  • Inbox story fixtures carry a realistic provenance mix, and the regenerated image snapshots are committed alongside the demo doc that shows their diff.
  • check is green; no guardrail config was edited and no ignore directive added.

9 · Out of scope & open questions

Deliberately not in this story

  • Per-field marking. Which individual chip the model guessed vs. you set — D1. It needs classified_guess read in the browser and is a separate decision.
  • Any accept / reject / re-run affordance. D4 of the epic stands; manual re-classify is epic story G.
  • Any surface outside the Inbox row — no detail-panel provenance line, no folder or priority view treatment, no correction-log view (the epic's D15 keeps that write-only).
  • Realtime for items. D8 — a classifier write still needs a reload to show. Worth its own story if the staleness ever grates; it touches every view that reads the tasks store.
  • Showing the model or prompt version. classified_model and classified_prompt_version stay unrendered; they exist for the future A/B query the epic's D2 describes.

Open

  • Nothing blocking. The treatment — §4's one decision — is settled: option 2, the title glyph. The spec is ready to build.
  • Does the “not yet classified” mark earn its place once the sweeper is fast and reliable? It is the state you see most often and care about least. Worth revisiting after a fortnight of real use — if it reads as noise, dropping it is a two-line change and the other two states stand on their own.
