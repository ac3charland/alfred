Refinement spec · Tasks module

ALF-191 — Contextually show dropdowns in the three-dots menu to set epic (for code stories) and priority / folder / due date (for tasks)

Give the task row's ⋯ “More actions” menu a set of type-contextual label submenus, so an Inbox row can be made dispatch-ready without opening the detail panel — and retire “Classify as…” the moment a row has a type, because a type change after the fields are filled is not worth supporting.

1 · Context & problem

Two independent frictions in the same menu, which is why they land in one ticket.

1.1 · Setting an empty field costs a detour

The row's metadata chips (RowMetaCluster) are editable in place — but only once a field is set. Its own doc comment states the rule: “A chip appears only when its field is set — filling an empty field is the detail panel's job.” So the exact rows that need attention are the ones with no affordance: an Inbox row with no folder shows no folder chip, a code story with no epic shows no epic chip.

That is precisely the state dispatchReadiness calls not ready. Its blockers — needs a folder, needs a project, needs an epic — name the empty fields, the row's Dispatch entry sits disabled with that blocker as its hint, and the only way to clear it is ⋯ → Open details → click the chip → pick → ⋯ → Dispatch. Triaging a full Inbox means paying that detour per row.

1.2 · “Classify as…” outlived its usefulness

Today Classify as… renders on every childless root, so a typed row can be re-typed. That was a deliberate widening (“correcting a type is an ordinary act now”), and classifyPatch exists to make each flip coherent by clearing the fields the new type forbids. But a flip after the fields are filled silently destroys work — a task→code flip drops due_date and recurrence; a code→task flip drops both pre-factory hints — and it is the one entry in the menu that can lose data without saying so.

The ticket's call: “If other fields have been set, it's too complicated to handle converting once type is set, so just remove the option. Users can delete and start over if need be.” The menu's own Delete is the escape hatch.

Be honest about whose type it is. A type does not only arrive from a human press: the classifier sweep writes item_type as part of its verdict (0029_llm_classifier.sql, ClassifiedRow in lib/tasks/classification.ts), classificationOrigin distinguishes 'model' from 'claimed', and ClassificationMark draws a Sparkle on a model-labelled row precisely so a human can see a machine chose it. So “a mis-typed row is rare and cheap to re-capture” is only true of hand-typed rows. After this change a wrong machine guess is corrected the same way as a wrong human one — Delete and re-capture — and the provenance mark stays the only signal that a type wasn't chosen by hand. That is the accepted trade (see §8), not an oversight.

1.3 · The two halves are the same change

Both edits act on the same slot in the menu. An unclassified row has no fields to set (the detail panel renders no chip row at all for one — “classify from the ⋯ menu first; the fields appear once there is a type to hang them on”), and a typed row has no type left to change. So one group replaces the other, and the menu carries exactly one of them at any time.

1.4 · This deliberately reverses part of ALF-67

ALF-67 removed flat Set due date / Set priority / Add notes entries from this menu, and left a test standing to keep them out — task-row.test.tsx › “no longer offers Set due date / Set priority / Add notes”. This ticket reinstates due date and priority as submenus, so that test is superseded and must be narrowed, not deleted wholesale: Add notes stays out (a textarea is not a menu — see §8), and that half of the assertion still holds.

The distinction that makes the reversal coherent: ALF-67 removed entries that each opened somewhere else; these set a value in place, in one press, from a list. Say it here so the next reader doesn't think the reinstatement was an accident.

3 · Decisions

D1The label group and “Classify as…” are mutually exclusive, and occupy one slot

An unclassified row shows Classify as… and no label submenus. A typed row shows its label submenus and no Classify as…. They render in the same position — where Classify as… sits today, between the reorder items and Dispatch.

Why: the menu's own doc comment already frames this pair as “the order the Inbox is worked: Classify as… sets the labels, Dispatch acts on them.” The label submenus are the label-setting step now, so they inherit that slot and that sentence. It also mirrors the detail panel exactly: no chip row for an unclassified row, a per-type chip set once there is a type to hang the fields on.

D2Each submenu's gate is the field's own domain rule, not a blanket isTask/isCode

EntryRenders whenWhy that gate
Due date ▸ isTask Due dates are task-only (the DB CHECK) — the same gate the panel's Due chip uses.
Priority ▸ isTask Same gate as the panel's Priority chip.
Folder ▸ isTask && parent_id === null && !isDispatched(node) && !isCompletedView This is the folder-as-label case — exactly dispatchReadiness's needs a folder. Once dispatched, Move to… in this same menu owns the folder (it is a move, not a label) and two folder entries would be a puzzle. A subtask's residency travels with its root, so it has no folder of its own to label. !isCompletedView is load-bearing: useScopedTasks({ type: 'completed' }) returns completed items regardless of residency, so a completed never-dispatched root would otherwise match — and RowMetaCluster refuses to draw the folder chip there on purpose (“the context label owns ‘where this lives’”), so the write would succeed and render nowhere.
Project ▸ isCode && parent_id === null Both code dispatch paths need a project: a story's factory gate, and an epic-shaped row's convert_to_code_epic (whose opensDialog is literally “no project set”). Setting it here removes that dialog step.
Epic ▸ isCode && parent_id === null && children.length === 0 Only a code story carries an epic hint — the ticket's own wording. A code row with children is an epic-in-waiting: the conversion creates its epic. A code child becomes a story under its parent-turned-epic and inherits it.
Classify as… ▸ isUnclassified && canChangeType The ticket's rule (§1.2), keeping the existing structural guard as a conjunct — see D3.

Why not just “the panel's chip set”: the panel is laxer about Folder (it offers the chip on any task row). The menu can afford to be stricter because it already carries Move to…, and because tying each gate to dispatch.ts's blockers keeps the cue, the disabled hint and the fix in one vocabulary.

Every row above also carries a leading !isTempId(node.id) conjunct — including Classify as…. dispatch.ts already names this state ('still saving'), and every other write path guards it: isValidDropTarget, canDrag, groupHasTempIds. Without it the feature misfires on precisely the row it targets — a just-captured item, in the window before reconcile. setFolder('temp-…') hits a route that validates the id as a UUID, 400s, rolls back, and leaves a bare “Couldn't save changes” toast after a pick that looked fine. (The affordance cannot misfire today, because a chip renders only for a field that is already set.) The window is milliseconds; hiding the entries through it is correct, and the entries are absent rather than disabled, like every other gate here.

D3Absent, not disabled — and canChangeType survives as a structural guard

Delete CLASSIFY_DISABLED_HINT and the disabled/title pair on the sub-trigger. Classify as… is either offered or not there. Keep the canChangeType prop and useTaskRowFlags.canChangeType, now as a render conjunct rather than a disabled gate.

Why keep canChangeType at all? Not for the subtask half — that one the database does enforce: items_task_only_fields permits a non-task type only on a row with parent_id is null (or on a code row), so a child inserted with the unclassified column default is rejected outright by the CHECK. The flag earns its place on the parent half, which nothing below the UI catches: enforce_subtask_shape returns early on a parentless row and never re-validates the untouched children, so a code root could silently acquire task children — “the database cannot catch that one, so the UI must.” A one-token conjunct is cheaper than re-deriving that argument later.

D4Due date is presets + Custom…, not a calendar grid inside the menu

The submenu lists, in order:

  • Today · Tomorrow · Next week — todayISODate(), +1, +7, ticked when they equal the row's current calendar date (see the callout)
  • a separator (always after the third preset), then No due date (only when a date is set)
  • Custom…, which closes the menu and opens the existing Calendar in a popover anchored to the ⋯ button
due_date is a timestamptz, not a YYYY-MM-DD string — normalise before you compare or add. The column is timestamptz (0001_initial_schema.sql) and the write schema says so outright: “Accept a date-only string … Postgres coerces the date to a timestamptz at midnight” (lib/api/schemas.ts). A reconciled row therefore carries 2026-09-04T00:00:00+00:00, so preset.value === node.due_date is always false and no preset would ever tick. Derive the calendar date once and use it for both the tick and any arithmetic: 
const currentDue = node.due_date === null ? null : node.due_date.slice(0, 10);
currentDue is what the submenu passes as its value. Never hand node.due_date raw to addDays: it splits on -, so Number('04T00:00:00+00:00') is NaN and new Date(NaN).toISOString() throws.

This defect is invisible to the obvious test. Every due-date fixture in the repo uses a date-only string (due_date: '2099-12-31'), so a test written from those fixtures passes while the shipped feature never ticks. §6.2 therefore requires a fixture with a full timestamptz due date.

Why: a 7-column button grid inside DropdownMenuSubContent breaks Radix's roving-focus model (arrow keys move between menu items, not grid cells) and is a cramped touch target on mobile. Presets cover the overwhelmingly common picks in one keystroke and stay keyboard-navigable like every other entry; Custom… keeps every other date one step away through the component that already owns that job.

Clearing: route No due date through onClearDueDate, not onSelectDueDate(null) — clearing a due date also clears any recurrence rule (a rule has nowhere to anchor without one). That's why the entry hides when no date is set: the handler already no-ops there.

D5Every submenu always renders for its type, with the current value check-marked

A task row always carries Due date / Priority (and Folder while it qualifies); a code story always carries Project / Epic — set or unset. The active option wears the trailing teal Check, exactly as PriorityMenu and PickerListItem do.

Why not hide a submenu once its field is set (“the row chip is clickable now”)? Because a menu whose shape shifts as you fill fields in is a menu you have to re-read every time, and the row chips are hover-revealed and tiny — on mobile the ⋯ menu is the reliable surface. A fixed per-type shape is learnable in one sitting; it is also what the detail panel does.

D6Epic disables — with the chip's exact words — until a project is set

With intended_project_id === null the Epic ▸ sub-trigger renders disabled, carrying title="Pick a project first" — IntendedEpicChip's verbatim hint, so the two surfaces never drift — and the same words as a trailing muted span in its visible label: Epic…  Pick a project first.

The title alone would never be readable. DropdownMenuSubTrigger carries data-[disabled]:pointer-events-none, so a disabled sub-trigger is not a hover target and the browser never renders its tooltip — and on touch, where §4.3 argues this menu matters most, title shows nothing at all. (IntendedEpicChip's comfortable trigger is a plain <button disabled title> with pointer events intact, which is why the chip's hint does appear and the menu's would not.) Hence the visible span: title stays for assistive tech and for the test assertion, but the sighted, mouse-free reader is who the hint is actually for. Drawn in §4.1.

Why disabled rather than absent (the opposite of D3)? Here the entry's absence would be unexplained — the field exists and the row needs it — whereas Classify as… is gone because the action itself no longer exists. The visible hint teaches the dependency: pick the project directly above, and Epic lights up.

Consequence to expect: picking a project always clears the epic hint in the same PATCH (setIntendedProject sends { intended_project_id, intended_epic_id: null }, matching the DB trigger). So changing a project from the menu resets Epic to “No epic” — the same behaviour the panel's Project chip has.

D7One new atom for the submenu; the menu keeps RowMetaCluster's prop shape

Five submenus of check-marked single-select options is the rule-of-three, twice over. Add DropdownMenuSelectSub to components/atoms/ — a DropdownMenuSub whose content is a list of options with a trailing Check on the active one. It takes the repo's existing single-select option shape, PickerChipOption, so the menu and the popover pickers describe their choices identically.

TaskRowMenu already takes 17 props; five more fields plus five more handlers would double it. Instead it takes node: ItemNode and the editing: RowMetaEditing bundle — exactly what RowMetaCluster does, with the same handler bundle TaskRow.metaEditing already builds.

Where the flags come from: the type flags stay useTaskRowFlags's and are passed in (isTask, isUnclassified, alongside today's isCode / canChangeType), together with isCompletedView, which the row already holds. The menu derives from node only what is pure shape — parent_id === null, children.length === 0, isDispatched(node), isTempId(node.id). One derivation of “what type is this row”, in the hook, exactly as the row and the cluster already share it.

Why not read the stores inside the menu for folders/projects/epics? Folders already arrive as a prop and the row is the composition root — but note FolderChip and IntendedEpicChip do read them via useFolders / useEpics. Either is defensible; keep folders as the prop it already is and read useProjects() / useEpics() inside the menu, matching detail-chips.tsx, so no new plumbing crosses TaskRow.

D8The bulk bar narrows to match — one rule for “can this be classified?”

allChildlessRoots becomes allUnclassified: count > 0 && every(i => i.item_type === 'unclassified' && i.parent_id === null && i.children.length === 0). The hint becomes a single sentence: Only unclassified items can be classified.

Why include the bulk bar: the ticket's reasoning — a type change after the fields are filled destroys them — is about the write, not the surface. Leaving the bulk bar able to re-type a filled row would leave the hole open behind a second door, and bulkClassify runs the same classifyPatch. The childless-root terms stay as the same structural guard as D3.

5.2 · The new atom

components/atoms/dropdown-menu-select-sub.tsx — the menu twin of PickerChip. Sketch: 

import type { PickerChipOption } from '@/components/atoms/picker-chip';

interface DropdownMenuSelectSubProperties {
  /** The sub-trigger's label, e.g. "Priority…". */
  label: string;
  /** The current value, ticked in the list. `null` matches a clear entry. */
  value: string | null;
  options: readonly PickerChipOption[];
  onSelect: (value: string | null) => void;
  /** Disable the trigger; `hint` becomes its `title` (e.g. "Pick a project first"). */
  disabled?: boolean;
  hint?: string;
  /**
   * Draw a `DropdownMenuSeparator` after this option index. Priority: 0 (after "No priority").
   * Due date: 2 — after the third preset, in BOTH shapes, so the divider doesn't move when
   * "No due date" appears. Omit for Folder / Project / Epic.
   */
  separatorAfter?: number;
}

It renders DropdownMenuSub → DropdownMenuSubTrigger (label + ChevronRight size={12}, matching the existing sub-triggers) → DropdownMenuSubContent of DropdownMenuItems, each className="justify-between" with a trailing <Check size={12} className="text-accent-teal" /> when active — the convention PriorityMenu and PickerListItem already share. Give it its own *.test.tsx: renders options, ticks the active one, calls back with the picked value, respects disabled.

Custom… is a sentinel, not a value. The atom's onSelect is (value: string | null), and “open a calendar” is neither. Use the repo's existing idiom rather than inventing a second prop: RepeatChip already ships a { value: 'custom', label: 'Custom…' } option and branches on it in onSelect (detail-chips.tsx). Do the same here — the Due-date submenu's handler checks value === 'custom' first and opens the popover, and only then treats the value as a date.

Adopt it everywhere in the same change. The five submenus are its call sites. Do not also rewrite PriorityMenu, PickerChip or Move to… to use it — those are a top-level menu, a popover and a bespoke list respectively. This atom is for submenus.

5.3 · Shared option builders

epicOptions is private to detail-chips.tsx today, and the project and folder lists are built inline there too. The menu needs all three, so extract them to lib/tasks/label-options.tsx and adopt them in detail-chips.tsx in the same change (per the frontend-architecture rule: a half-adopted primitive is worse than none):

One shape for all three — today they disagree (epicOptions excludes the clear entry and callers prepend it; FolderChip prepends conditionally; IntendedProjectChip hard-codes No project inline). Unify on an optional clear label: pass one and the builder prepends { value: null, label: clearLabel }; omit it and there is no clear entry. 

export function folderOptions(folders: readonly Folder[], clearLabel?: string): PickerChipOption[]
export function projectOptions(projects: readonly Project[], clearLabel?: string): PickerChipOption[]  // name · KEY
export function epicOptions(epics: readonly Epic[], clearLabel?: string): PickerChipOption[]           // name · REF

Call sites: Folder passes 'No folder' only while the row is undispatched (today's allowClear); Project always passes 'No project'; Epic always passes 'No epic'. A .tsx because the labels are two-column ReactNodes. Pure functions of their inputs, so they unit-test without rendering. Behaviour must be identical — the existing chip tests stay green with no assertion changes.

5.4 · Due-date presets

lib/habits/dates.ts already exports a correct addDays(iso: string, days: number): string over YYYY-MM-DD strings. Don't write a second one — but it is not self-contained: it is built on the module-private MS_PER_DAY, toUtcMillis and fromUtcMillis, which isoWeekday, daysBetween and eachDay also use and which cannot all move with it. So move the trio with it:

  • Move MS_PER_DAY, toUtcMillis, fromUtcMillis and addDays into lib/date-utils.ts, exporting the two converters.
  • lib/habits/dates.ts imports the converters back for its remaining helpers and re-exports addDays, so lib/habits/index.ts's barrel and every habits call site are untouched and their tests stay green.

Not a duplicate: lib/recurrence/engine.ts has a module-private addDays(date: Date, days: number): Date. Different type, different module, unrelated — it stays exactly where it is. §7's criterion is about the string helper only. 

// Inside the component — NOT module scope. At module scope `today` freezes at first
// import, so the presets go stale after midnight in a long-lived tab and any test that
// pins a clock after import gets the wrong dates.
const duePresets = React.useMemo(() => {
  const today = todayISODate();
  return [
    { value: today,             label: 'Today'     },
    { value: addDays(today, 1), label: 'Tomorrow'  },
    { value: addDays(today, 7), label: 'Next week' },

}, []);

5.5 · The Custom… popover

Selecting a DropdownMenuItem closes the menu, so the calendar cannot live inside it. Wrap the trigger in a PopoverAnchor (already exported from atoms/popover.tsx) and hold the popover's open state in TaskRowMenu: 

<Popover open={calendarOpen} onOpenChange={setCalendarOpen}>
  <DropdownMenu>
    <DropdownMenuTrigger asChild>
      <PopoverAnchor asChild>
        <IconButton size="md" aria-label="More actions">…</IconButton>
      </PopoverAnchor>
    </DropdownMenuTrigger>
    <DropdownMenuContent align="end">…</DropdownMenuContent>
  </DropdownMenu>
  <PopoverContent align="end">
    <Calendar selected={node.due_date} onSelect={…} onClear={…} />
  </PopoverContent>
</Popover>
Radix focus trap to watch for. The menu returns focus to its trigger on close while the popover is mounting. If the popover flickers shut or the calendar never takes focus, defer the open by one frame from the item's onSelect rather than reaching for event.preventDefault() (which would keep the menu open on top of it). Whichever way it lands, record the finding in the shadcn-ui skill — read compounding-learning first for the house style.

5.7 · Accessible names

Every entry is a plain menuitem whose accessible name is its visible text, so tests query by role and name. Two collisions to avoid:

  • Today appears both as a Due-date preset and in the Calendar footer, so a test with both open must scope its query to the menu or the popover.
  • The Classify as… submenu's Code already needs exact: true in the e2e specs (a longer entry contains the word); keep that, and prefer exact: true for the new short entries — Today, Work, Alfred — for the same reason.

7 · Acceptance criteria

  • The label group
  • A task row's ⋯ menu shows Due date… and Priority… submenus.
  • An undispatched top-level task also shows Folder…; a dispatched task and a subtask do not (a dispatched task still shows Move to…).
  • A code root shows Project…; a childless code root also shows Epic…. A code root with children shows Project but not Epic; a code child shows neither.
  • An unclassified row shows none of the five. A row still carrying a temp id shows none of them either — nor Classify as… — until it reconciles.
  • A row in the Completed view shows no Folder… (the context label owns "where this lives" there), whatever its residency.
  • Each submenu marks the row's current value with the teal check, including the clear entry (“No folder” / “No project” / “No epic” / “No priority”).
  • The submenus render at every breakpoint — no md:hidden on the label group, asserted as an explicit class check (jsdom ignores media queries).
  • Writes
  • Due date offers Today / Tomorrow / Next week / Custom…, plus No due date only when a date is set; each preset persists that exact calendar date.
  • The tick lands on the matching preset for a row whose due_date is a full timestamptz (not just a date-only fixture), and no code path passes a raw due_date to addDays.
  • No due date goes through the clear path, so a task with a recurrence rule loses the rule too.
  • Custom… closes the menu and opens the Calendar popover anchored to the ⋯ button; picking a day persists it, “Clear” clears it, Escape dismisses without a write.
  • Priority offers “No priority” + High / Medium / Low with their glyphs, matching PriorityMenu.
  • Folder lists the folders plus “No folder”, and writes through setFolder — a label, not a move: the row stays in the Inbox.
  • Epic is disabled while intended_project_id is null, showing "Pick a project first" as visible text in the sub-trigger as well as in title — a disabled sub-trigger is pointer-events-none, so the tooltip alone can never be read. It lists only the selected project's epics otherwise.
  • Changing the project from the menu clears the epic hint in the same write (Epic falls back to “No epic”).
  • Every pick auto-saves optimistically and rolls back with the store's existing failure toast — no new error handling.
  • Dispatch readiness
  • Setting the missing label from the menu flips the row's ready pip on immediately, and re-opening the ⋯ menu shows Dispatch enabled — with no page reload and no detail panel. (Picking closes the menu: Radix closes on onSelect, and §5.5 depends on that, so "in the same menu-open session" is not a state that exists.)
  • A label set from the row menu is reflected in the bulk bar's readiness line the next time select mode is entered — both read the same dispatchReadiness off the same store. (They are never on screen together: TaskRow renders no ⋯ menu in select mode, and InboxBulkBar renders null outside it.)
  • Classify
  • Classify as… is absent — not disabled — on any row whose item_type is task or code.
  • It still appears, enabled, on an unclassified row, and both Task and Code still work from it.
  • No “Only a top-level item with no subtasks can change type” hint remains anywhere in the row menu.
  • The bulk bar's Classify as button is enabled only when every selected row is unclassified, and its disabled hint reads “Only unclassified items can be classified”.
  • Structure & guardrails
  • The five submenus are built from one shared atom, not five copies of the sub-trigger + item markup.
  • detail-chips.tsx uses the extracted option builders, and its existing tests pass with no assertion changes.
  • Exactly one string-based addDays exists in the frontend, in lib/date-utils.ts, with lib/habits/dates.ts re-exporting it; habits call sites and the barrel are unchanged. (lib/recurrence/engine.ts's private Date-based helper is unrelated and stays.)
  • npm run check is green, with no new eslint-disable, @ts-expect-error, .skip, or tooling-config edit.
  • A demo doc reproduces via npm run demo -- verify, and the PR description links it as a live blob URL (npm run demo -- pr-link).

8 · Out of scope

  • Repeat stays panel-only. It is not in the ticket, and its “Custom…” opens a full modal editor — a heavier detour than the calendar popover, for a field that is set far less often.
  • Notes stay panel-only (a textarea is not a menu).
  • Creating a project, epic or folder from the menu. The pickers select from what exists — creation stays the gate's and the sidebar's affordance, exactly as the detail chips have it.
  • The Code module's own surfaces (board, backlog, story detail, epic-block's ⋯). This ticket is the Tasks row menu; a code story's epic after it reaches the factory is a different field on a different table.
  • The By-Priority view's rows. The view itself is built and routed (PriorityView, wired in task-views.tsx) — what it lacks is a ⋯ menu on its rows, and its PriorityRow is a bespoke component that shares nothing with TaskRow (its own checkbox, chevron, priority chip and cascade modal). Giving it a menu is ALF-162's job, and would need its own decision about which submenus make sense outside the Inbox. It will not inherit this change for free.
  • The Calendar atom's selected-day highlight. Pre-existing and out of scope: isSelected = cell.iso === selected compares a YYYY-MM-DD cell to a raw due_date, so against real (timestamptz) data no day ever reads as selected. §5.4's normalisation fixes the menu; the calendar keeps its own bug until someone fixes it deliberately. Do not let §7's "picking a day persists it" be read as a claim that the calendar shows the current value.
  • A confirmation or undo for the removed re-classify path. Delete + re-capture is the accepted recovery, per the ticket.
