ALF-276 — Exclude projects from the PR ratio

The Dashboard’s PR-ratio card gets a ⋯ menu where ticking a project excludes it, stored on its row; knowledge ships ticked, so its PRs drop out.

Revised 2026-09-29: an “all projects excluded” line replaces the card body when every project is ticked (your review) — Plate II gains the state; D11 added.

    No — the velocity chart keeps counting every project.

  2. D5How does knowledge get excluded?

    The migration ticks it for ac3charland/knowledge, if that project exists.

    Ships configured, as the ticket asks; a no-op anywhere else.

  3. D6What does the PR-ratio API return?

    Excluded projects are omitted from repos; total and percentages ignore them.

Working detail

Everything below is for the implementing agent. Approving needs only what’s above.

Context

The Dashboard’s PR-ratio card (frontend/components/code/pr-ratio.tsx) splits the last seven days’ merged PRs across the Code module’s projects, plus an Other bucket when PR_RATIO_AUTHORS is set. Since ALF-268 the measured repos are the projects rows (frontend/lib/github/config.ts → getPrRatioConfig), read by listProjectRepos in frontend/lib/data/code.ts; frontend/lib/github/pr-ratio.ts issues one Search query per project plus one for Other (which subtracts every project repo with -repo:), and toPercentages shares 100 across them. The same route serves GET /api/code/pr-ratio, which the weekly-review-prep skill reads (docs/productivity-coach-primer.md, Endpoint 2).

The ticket asks for an exclude list, configured to drop the knowledge repo (ac3charland/knowledge, also WIKI_REPO). In refinement the owner redirected it: the list should be dynamic, a column on projects, and knowledge should behave like every other project unless excluded by this switch — i.e. it is (or will be) a Code project, and exclusion is a per-project property, not an env list and not a special case for the wiki repo. Excluded PRs should vanish silently.

Precedent for a per-project owner setting: ALF-188’s projects.color (database/migrations/0041_project_color.sql), editable through PATCH /api/projects/[id] (updateProjectSchema in frontend/lib/api/schemas.ts), the store’s optimistic updateProjectColor (frontend/lib/stores/code-store.tsx), and the board toolbar’s palette popover. This spec reuses that pipe (PATCH → optimistic store action → rollback toast) but puts the control on the ratio card itself.

Decision records

D1Where do you flip the switch? · settled

A ⋯ menu on the Dashboard card, ticks meaning “exclude”. An IconButton (size md, neutral tone, lucide MoreHorizontal 14px) at the end of the card header opens a DropdownMenu headed “Exclude from PR ratio”: one DropdownMenuCheckboxItem per project, creation order, each with its colour dot, checked = exclude_from_pr_ratio. The ticked set is the exclude list, matching the column and the ticket’s wording. It sits beside its effect and shows every project at once. It costs a header-action slot on SurfaceCard, a refetch after each toggle (D9), and D7’s all-projects minimum so an exclusion can’t make the card, and its menu, disappear.

Considered: a “PR ratio” group in the board’s palette popover; a popover on the card whose ticks meant “count” — the owner chose the menu with exclude-ticks.

D2Where does the exclude list live? · settled

projects.exclude_from_pr_ratio boolean not null default false. The owner chose a column over an env list so it changes without a redeploy. Default false means every existing and new project keeps counting — no backfill. Considered: PR_RATIO_EXCLUDE_REPOS env list (reaches non-project repos, needs a deploy); auto-excluding WIKI_REPO (couples two features).

D3What happens to an excluded project’s PRs? · settled

No Search query is issued for an excluded project, so it has no segment, no legend row, and adds nothing to total or the percentage base. Its repo is still subtracted from the Other query with -repo:, so its PRs don’t reappear as Other. Nothing on the card says anything was excluded. Side effect: one fewer Search request per excluded project against the 30/min cap. Considered: a muted “N excluded” detail — declined by the owner.

D4Does the lines-changed chart honour it? · proposed

getGithubRepoConfig (shared with loc.ts) is unchanged; only getPrRatioConfig applies the flag. This knowingly departs from DEPENDENCY_BOTS’ “two widgets, same ground” principle, because the ticket and the column name are about the ratio. Considered: honour it in both (rename the column exclude_from_measurement) — a one-line filter if the owner wants it later.

D5How does knowledge get excluded? · proposed

The same migration that adds the column ends with update projects set exclude_from_pr_ratio = true where repo_owner = 'ac3charland' and repo_name = 'knowledge'; — idempotent, and a no-op locally, in CI and anywhere the row doesn’t exist. The ticket asks for the configuration to ship; this keeps that without an env var. Considered: leave it to the owner to tick after merge (the fallback when the row is absent — see after-merge).

D6What does the PR-ratio API return? · proposed

The response shape is unchanged; excluded projects simply aren’t in repos, and total/percentage are computed without them. The skill that reads it keeps working and now agrees with the card. Considered: include them with an excluded: true flag and zero counts — a shape change for a reader that has no use for it.

D11All excluded, but Other has PRs? · proposed

The owner asked for a muted “all projects excluded” line in place of the misleading quiet-week line. The card decides it from the store alone — every useProjects() row has exclude_from_pr_ratio — so the line shows immediately, with no loading pulse and no date range, and it wins over every fetch state (loading, error, empty, ready). It wins even when Other has merged PRs: a bar that is 100% Other isn’t a split between projects. The API is not special-cased: with no counted repos it returns repos: [] and whatever Other counts, which is an honest answer for a script. Considered: only replacing the total: 0 case, leaving an Other-only bar when Other is non-zero.

Implementation decisions

D7 · The two-repo minimum counts all projects, before exclusion

MINIMUM_RATIO_REPOS keeps gating on every project row, so exclusions never turn the route into a 501: the card, and with it the only control that un-excludes (D1), stays on screen. Two projects with one excluded therefore draw a single-project bar (plus Other when measured). Considered: gating on counted projects only — cleaner semantics, but ticking the second-to-last project would hide the menu you’d need to undo it.

D8 · Colours don’t shift

toEntries already colours by projectColorFor(projects, id) over the store’s full creation-ordered list, so excluding knowledge leaves every other project’s colour as it is (Plate II). Don’t filter the store list before colouring.

D9 · Menu mechanics

  • Trigger aria-label="PR ratio options"; it renders in every state the card renders — loading, error, empty, ready and all-excluded (D11) — so the header never jumps, and so a repo the token can’t read (which fails the whole fan-out as a 502) can be excluded from the error state.
  • Each item’s onSelect calls event.preventDefault() so the menu stays open (precedent: board-toolbar.tsx’s checkbox items).
  • The heading is a non-interactive label: add a DropdownMenuLabel (Radix Label, px-2 py-1.5 text-xs text-muted-foreground) to atoms/dropdown-menu.tsx rather than a bare <p>.
  • The items read the store’s useProjects() (already select('*'), so the column arrives with the type regen); the toggle is the store action updateProjectPrRatioExclusion (optimistic tick, rollback + toast on failure).
  • usePrRatio gains refetch(), called after the PATCH resolves (the server reads the DB, so an optimistic refetch would race it). While it refetches the card keeps the previous ratio rather than flashing the loading bar.

D10 · Config shape

PrRatioConfig stops being an alias: GithubRepoConfig & { excludedRepos: RatioRepo[] }, where repos holds only counted projects. buildOtherQuery subtracts [...repos, ...excludedRepos]. MeasuredProject gains exclude_from_pr_ratio and listProjectRepos selects it; getGithubRepoConfig ignores it (D4).

Acceptance criteria

  • A migration adds projects.exclude_from_pr_ratio (boolean, not null, default false) and regenerated types include it.
  • The same migration sets it true for ac3charland/knowledge and is a no-op when that row is absent.
  • With a project excluded, the card shows no segment or legend row for it and its PRs are in neither total nor Other.
  • No Search request is made for an excluded project; the Other query still carries -repo: for it.
  • Excluding a project leaves every other project’s colour unchanged.
  • GET /api/code/pr-ratio omits excluded projects from repos; percentages sum to 100 over the rest.
  • Exclusions never produce a 501: the route gates on two projects before exclusion.
  • The lines-changed chart still measures excluded projects.
  • The card’s ⋯ menu lists every project with a tick for each excluded one; ticking or unticking persists across reload and the bar updates without a page load.
  • The ⋯ shows in the loading, error, empty, ready and all-excluded states, and the menu stays open between ticks.
  • With every project excluded, the card shows only its title, the ⋯ and the muted line “All projects excluded from the PR ratio.” — no range, bar or legend — even when Other has PRs; unticking one brings the bar back.
  • PATCH accepts a boolean exclude_from_pr_ratio, rejects other types with 400, and a failed PATCH rolls the UI back.
  • With no project flagged, the card and API behave exactly as before.
