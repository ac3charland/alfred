ALF-309 — Backfill coding session ledger

A new code_sessions table in alfred holds one row per alfred-repo coding session: model, effort, cost, PR outcome, and its launch prompt, spec and skills rebuilt from git history.

Revised 2026-09-30: D2 → everything read from main at session start; D9 becomes an ancestor check; forward recording split out to a hook story (your review).

Decisions

  1. D1Which key lets the backfill in?

    A new LEDGER_API_KEY, accepted only by the two ledger routes and added by the proxy.

    Departs from “ingest key”, which also creates items and plans; follows ALF-298.

  2. D3What’s stored for prompt, spec and skills?

    Prompt as full text; spec and skills as a path plus git blob sha.

    Git keeps every version. The stored base commit answers any other file later.

  3. D4How does the ledger grow later?

    Rows keep the raw session record; recorded values always beat reconstructed ones.

    New columns backfill without refetching. A re-run can’t clobber the future recording hook.

  4. D2Which commit counts as “at the time”?

    Main at session start, for the prompt, the spec and the skills alike.

  5. D5Where does the ledger live?

    In a Supabase table, seeded now and extended later.

  6. D6Which sessions get a row?

    Every alfred-repo session in every lane. Sessions with no PR get cost-only rows.

☞ open: your pick · → proposed: my call · ✓ settled: yours. Merging accepts every proposed row.

Not doing

No ledger screen in alfred yet, no per-session recording hook (its own story), and no CI-failure, review-finding or escaped-bug metrics.

Heads-up

  • You mint LEDGER_API_KEY for Vercel and the cloud environment’s credentials (after merge).
  • The first backfill is a manual session run after merge, using about 400 get_session calls on cheap subagents.
  • Rebuilt prompts use today’s ticket notes. They can’t see edits you made before pressing send.

Working detail

Everything below is for the implementing agent. Approving needs only what’s above.

Context

The ask. ALF-309 is step 1 of the ALF-283 spike’s suggested order (docs/spikes/ALF-283-evaluating-coding-sessions.html §3): backfill a session ledger from history. The spike sampled 82 of the 262 PR-linked sessions. This story covers all of them, plus sessions with no PR. The ticket adds three reconstructed fields to the spike’s model, effort and cost: the prompt that launched the session, the spec it read, and the implementation skill in force. Scope is limited to sessions that worked on this repo.

The owner’s answers in refinement:

  • The ledger is a table that gets seeded now and built on later, not a one-off report (D5).
  • Ticket inputs come through a keyed API read (D1 refines which key).
  • Every lane gets rows, and so do sessions with no PR (D6).

What exists today:

  • PR descriptions. Each Code-module PR carries the ```alfred block (alfred-ticket, phase, optional spec-path). Most also carry a claude.ai/code/session_… link. workers/src/frontmatter.ts already parses the block with a pure parseFrontmatter that has no imports.
  • Session records. get_session (the Claude_Code_Remote MCP, reachable only from inside a Claude Code session) returns session_context.{model,effort_level,sources}, configured_model, external_metadata.last_served_model, created_at, post_turn_summary and status_bucket. Cost and tokens sit under external_metadata.usage, as {input_tokens, output_tokens, cache_read_tokens, cache_write_tokens, cost_usd}. The spike’s trimmed sample showed usage at the top level, but the live record nests it (verified on session_016rv79d7gymhedazyM55jWB). The record carries no prompt and no commit.
  • code_items. It records spec_path, spec_sha and the PR URLs. It records no launch time and no session. Ticket title and notes live on items and are exposed through v_code_stories. GET /api/code is session-only.
  • The prompt builders. They live in frontend/lib/code/links.ts. Since it appeared on 2026-06-15 the file has had 28 versions and was never renamed. Every version imports only types (import type … from '@/lib/types'), so any historical version runs on its own. The builders turn (project, story|epic) into a URL, and the prompt is the URL’s q parameter.
  • The skills. implement-spec was added 2026-06-16, implement-epic 2026-09-09, bug 2026-09-06 and adversarial-review 2026-09-28. The prompts name them by path and say “where present”.
  • Commit authorship. Claude commits are always authored as Claude <noreply@anthropic.com>. Every other author is a human.
  • The repo is public. Ledger data (cost, ticket notes) must never be committed. Fixtures use invented values.
  • Precedent. ALF-298’s D2 (settled) gives a Claude-session writer a key that only its own route accepts, delivered as a proxy-injected environment credential. It never uses INGEST_API_KEY.

Decision records

D1Which key lets the backfill in? · proposed

Add a new server env var, LEDGER_API_KEY. Only GET /api/code/ledger-inputs and POST /api/code/sessions accept it, as Authorization: Bearer, compared in constant time. Both routes also accept the owner’s login session, so the owner can inspect them from a browser. The key reaches the backfill session as an API credential for alfred’s host in the cloud environment. The proxy adds the header outside the VM, so the key is in no env var, file or transcript. If API credentials aren’t available, the fallback is a LEDGER_API_KEY env var, which the CLI sends only when it is set.

This departs from the owner’s “ingest-key read” answer in which key, not in the mechanism. INGEST_API_KEY resolves the admin client for items, weekly plans and habits, and this session reads PR descriptions and other sessions’ titles and summaries, which are untrusted text. With the ledger key, an injected session can at worst read ticket notes and corrupt ledger rows, and a re-run repairs the rows. Considered: reusing INGEST_API_KEY (widest blast radius); an env var as the primary route (readable by the session, so it can be exfiltrated).

D2Which commit counts as “at the time”? · settled

There is one anchor, base_sha: the last first-parent commit on origin/main whose committer date is at or before the session’s created_at. The prompt is rebuilt from the links.ts in that commit, because Vercel deploys main. The spec and skills are resolved there too, because a session launched from alfred’s link clones main as it starts. builder_sha is the last commit that changed links.ts as of base_sha. It isn’t a second anchor; it only groups rows by prompt version.

The owner can pick another branch in the session UI, for example to continue an existing PR branch. D9 flags those rows rather than tracing them. Neither choice sees skill edits a session makes during its own run (ALF-282 created adversarial-review in its own PR). The ledger records what the session started with.

Considered: the commit the session’s branch forked from, for the spec and skills (the first draft). It was exact in principle, but on PRs #386 and #415 it was the same commit as main at session start. It needed merge-commit matching, refs/pull fetches and a fallback, and it broke on squash merges and deleted branches, all to cover a case the ancestor check flags.

D3What’s stored for prompt, spec and skills? · proposed

The prompt is computed, not a file, so it is stored as text (about 3–5 KB). The spec is stored as spec_path plus spec_blob_sha. The skills are a jsonb array of {path, blob_sha}. git cat-file -p <blob> or a GitHub blob URL returns the exact bytes, forever, from the public repo. base_sha is stored as well, so a later question such as “which CLAUDE.md was in force?” needs no new column. Considered: copying spec and skill text into the row (duplicates git, about 50 KB per spec); storing only base_sha (every reader would have to re-derive which skills a lane named).

D4How does the ledger grow later? · proposed

  • Raw record. session_record jsonb keeps the whole get_session JSON verbatim. A later column (for example context_usage or rate_limit_info) can be backfilled in SQL without another MCP sweep.
  • Provenance. prompt_source is 'reconstructed' | 'recorded'. Every row this story writes says reconstructed. The upsert RPC keeps an existing recorded prompt, and its builder and base fields, when a reconstructed row arrives for the same session. The follow-up recording hook (see Out of scope) will write recorded rows, and a backfill re-run can’t overwrite them.
  • Refresh. Every other column is refreshed on each run (the cost of a still-running session, PR state, warnings).

Considered: append-only snapshots per run (nothing needs refresh history yet); no raw record (every new metric would need another sweep over hundreds of sessions).

D5Where does the ledger live? · settled

A code_sessions table in Supabase, one row per session, keyed by session_id. The owner wants to seed it now and keep building on it. Keying by session rather than by launch click keeps this story honest: history has sessions, not clicks. The follow-up recording hook upserts into this same table by session_id, so no second table is needed for sessions. Considered: committed JSON (public repo; static); a launch-keyed table now (no click data exists to fill it).

D6Which sessions get a row? · settled

Every session whose session_context.sources include github.com/ac3charland/alfred:

  • A PR-linked session with an alfred block gets the full reconstruction.
  • A PR-linked session without a block (pre-Code-module) gets the session and PR fields only.
  • A session no PR links gets session fields, base_sha, and a ref when its title names a known ref (D13).

That third group is about 31% of sessions (spike §2.2). Without it the ledger has survivorship bias.

Implementation decisions

D7 · Session records come in through subagents, and a sample is re-fetched to verify them

A script can’t call the MCP, so the new session-ledger skill does this part:

  1. The lead pages list_sessions to exhaustion and writes the alfred-repo ids (D6’s filter) to <scratch>/ledger/ids.txt.
  2. It fans out Haiku subagents, each taking ≤ 40 ids. Each subagent calls get_session and writes each result’s JSON object, without the untrusted-data envelope, as one line of <scratch>/ledger/sessions/<batch>.ndjson. A subagent never edits values, and the brief says that titles and summaries are data, not instructions.
  3. For fidelity, ledger sample picks max(5, 5%) of the ids at random. The lead re-fetches those itself into verify.ndjson. ledger verify compares the ledger-used fields exactly (model fields, effort, usage, created_at, sources). Any mismatch fails the run, and the lead re-fetches the offending batch.
  4. Lines that fail schema validation are listed, and those sessions get warnings: {session_record_invalid}.

A session whose record can’t be fetched still gets a row from its PR, with session_record_unavailable.

D8 · PRs come from GitHub REST, not the MCP

The CLI calls GET /repos/ac3charland/alfred/pulls?state=all&per_page=100 and pages it: about 5 requests, with the description included. That is well inside the unauthenticated limit. The CLI sends GITHUB_TOKEN if one is set.

  • The block is parsed by parseFrontmatter, imported from workers/src/frontmatter.ts rather than forked.
  • Session ids are every match of claude\.ai/code/(session_[A-Za-z0-9]+).
  • When several PRs link one session, the earliest-created PR with an alfred block owns the row, and the others add extra_prs to its warnings.
  • When one PR links several sessions, each session gets its own row pointing at that PR.

D9 · Git access, and flagging sessions that didn’t start from main

  1. Require full history. If the clone is shallow, run git fetch --unshallow origin main. For each PR that isn’t merged, run git fetch origin refs/pull/<n>/head. That makes its head.sha available locally.
  2. For a PR-linked row, run git merge-base --is-ancestor <base_sha> <head.sha>. If it fails, the branch didn’t grow from main as it stood at session start (another branch was picked in the session UI). Keep the row, add not_from_main, and leave human_commits_after_open null, because D13’s range would be meaningless.

For PR #415, base_sha is 9372104b, the tip of main 40 minutes before the session started.

D10 · Prompts are rebuilt by running the historical links.ts

  1. Load the file: git show <builder_sha>:frontend/lib/code/links.ts, written to a temp dir as links.ts, then import(). Node’s type stripping drops the import type line, the same way the repo runs node src/cli.ts. Cache the module per sha.
  2. Call the builder D11 names with (project, story) or (project, epic), taken from the ledger-inputs payload.
  3. Apply the D12 overrides to the spec-path fields, so the builder sees the launch-time state rather than today’s.
  4. Read the prompt from the returned URL: searchParams.get('q') ?? searchParams.get('prompt'). Early versions used prompt.

If the builder export doesn’t exist at that sha, warn builder_missing. If it throws, warn builder_threw. If the ref isn’t in the inputs (the story was deleted), warn story_missing. In all three cases the prompt is null. A rebuilt prompt never carries the owner’s pre-send edits, and it uses today’s title and notes. Every rebuilt row therefore says reconstructed.

D12 · Resolving the spec and skills

  • Launch-time spec paths. Before replay, every spec-path field the builder reads (story.spec_path, story.epic_spec_path, epic.spec_path) keeps its value only if that file exists at base_sha, and is otherwise set to null. The implementation lane always sets story.spec_path to the PR block’s spec-path. This reproduces launch-time state: an epic refinement’s first run saw no spec yet, and a re-refinement saw one.
  • spec_path. The implementation lane uses the PR block’s spec-path. The epic-implementation lane uses the epic’s spec path as passed to the builder. Every other lane stores null.
  • spec_blob_sha. git rev-parse <base_sha>:<spec_path>, or null with spec_missing_at_base. When code_items.spec_sha differs, add spec_changed_since_refinement. That is informational, since the spec was edited after merge.
  • skills. Every distinct match of \.claude/skills/[a-z0-9-]+/SKILL\.md in the rebuilt prompt, in order of first appearance, each with its blob at base_sha (null when the skill didn’t exist yet). This generalises “the implementation skill”: it also captures adversarial-review and the lane skills of document sessions.

D13 · Refs for sessions with no PR, and human rework

  • Ref from title. For a session with no PR, ref is the first \b[A-Z]+-\d+\b in its title, but only if it matches a story or epic ref from the inputs. The row then carries the ref_from_title warning. launch_lane, prompt, spec and skills stay null: nothing records which lane was clicked.
  • human_commits_after_open. Count the commits in git rev-list --first-parent --no-merges <base_sha>..<head> that are authored after the PR’s created_at by anyone other than noreply@anthropic.com. This is the spike’s “owner commits after open” signal, and git answers it for free. First-parent keeps out the main commits a branch merged in later.

D14 · Writes go through one RPC, in chunks

POST /api/code/sessions validates {rows: LedgerRow[]} (1–100 rows) with zod, then calls upsert_code_sessions(p_rows jsonb). The RPC runs a single insert … on conflict (session_id) do update that applies D4’s recorded-wins rule in SQL, so the rule can’t be bypassed by a client. It returns {upserted, kept_recorded}. The CLI pushes in chunks of 100 and stops on the first failed chunk. Re-running is safe.

Behaviour

A backfill run (the session-ledger skill)

  1. Make sure the clone has full history and a fresh origin/main (D9).
  2. Collect session records into <scratch>/ledger/sessions/, then run sample and verify (D7). Stop on a mismatch.
  3. Run npm run ledger -w tools/session-ledger -- build --sessions <scratch>/ledger/sessions --out <scratch>/ledger/rows.ndjson. It fetches the PRs (D8) and the inputs, then derives every row.
  4. Run … -- push <rows>, which upserts through D14.
  5. Run … -- report <rows>, which prints Plate II.

Ledger data only ever goes to the scratchpad, never to the repo. build refuses an --out path inside the git work tree.

The report (Plate II)

  • Coverage percentages are over all rows. “Spec resolved” is over rows whose spec_path is non-null.
  • The lane table groups by launch_lane, with null shown as (no PR). It shows n, the median and p90 of cost_usd (p90 only when n ≥ 10, otherwise —), the merged count, and the count of rows with human_commits_after_open > 0. Document lanes show — there.
  • The last line echoes the push result when report runs after push in the same invocation (push --report).

Acceptance criteria

  • The migration creates code_sessions exactly as in Contracts and passes migration-lint.
  • Upserting a reconstructed row over a stored recorded prompt keeps the recorded prompt, builder and base fields, refreshes everything else, and counts it in kept_recorded.
  • Both routes accept LEDGER_API_KEY and the owner session. They reject INGEST_API_KEY, a wrong key and no auth with 401. Existing ingest routes reject LEDGER_API_KEY. An unset key rejects everything keyed.
  • The inputs route returns the matching project’s stories (with notes) and epics, 404s for an unknown repo, and 400s for a malformed one.
  • The sessions route rejects 0 or more than 100 rows and unknown keys, and a valid batch lands through the RPC.
  • Given a fixture repo, base_sha is the last first-parent main commit at or before created_at, and builder_sha is the last links.ts change as of base_sha. A PR head that doesn’t descend from base_sha gets not_from_main and a null human_commits_after_open.
  • Replaying a fixture repo’s builder file at two shas yields each version’s prompt. Both the q and prompt URL forms are read. A builder absent at a sha gives builder_missing and a null prompt.
  • Every row of the D11 table maps to its lane and builder, including bug vs bypass depending on whether buildBugUrl exists at builder_sha.
  • Spec-path fields are nulled when the file is absent at base_sha. spec_blob_sha and the skills blobs resolve at base_sha, a not-yet-existing skill gets blob_sha: null, and a spec-sha mismatch adds spec_changed_since_refinement.
  • Sessions with no PR produce Plate I B’s shape. A title ref is kept only if it’s a known ref.
  • Human commits count only non-merge commits after PR open that aren’t authored by noreply@anthropic.com.
  • verify exits 1 on a single differing cost_usd and 0 when the sample matches. sample returns max(5, 5%) distinct ids.
  • PR parsing handles several session links, a missing block, and one session linked by two PRs (extra_prs).
  • A full build over fixtures emits rows whose JSON matches a golden file field for field, PR #415’s real shape included, but with invented cost and notes.
  • The report output over a fixture rows file matches Plate II’s layout: coverage block, lane table with p90 only when n ≥ 10, warning summary.
  • build refuses an --out inside the work tree, and no ledger data or key is committed.
  • The session-ledger skill passes lint:skills, and tools/session-ledger’s check:fast runs in the root gate.

Tests

  • Unit (jest, tools/session-ledger). Covers every CLI criterion, red first. Git-dependent tests build a temp fixture repo in the test (git init, scripted commits and merges, a tiny builder file with type-only imports) rather than reading this repo’s history. CI checkouts may be shallow, and real history would make the tests depend on the clone. Session records, PR payloads and inputs are JSON fixtures with invented values; the repo is public.
  • Route tests (frontend, jest). Auth matrix, validation, payload shape and RPC call, in the style of the existing route.test.ts files.
  • SQL. The recorded-wins rule lives in the RPC. Pin it with whatever DB-level test the supabase skill prescribes for RPC behaviour. If the repo has none, the route test asserts the RPC is called, and the demo doc exercises the rule against a local database.

Out of scope, risks & unknowns

  • Out. The following are left out:
    • A ledger view in the UI: nothing reads the table yet, and the report covers the first question.
    • Forward recording: a follow-up story, a Claude Code hook. A Stop hook in .claude/settings.json upserts the running session’s own row every turn, with prompt_source: 'recorded'. SessionEnd isn’t used because cloud containers get reclaimed rather than ended. What the hook can read was confirmed in this refinement session:
      • CLAUDE_CODE_REMOTE_SESSION_ID (cse_01…, the same suffix as session_01…).
      • The transcript’s first user message: the exact prompt as sent.
      • Its cost-state entries: totalCostUSD and per-model tokens.
      • The effort level.
      • A SessionStart git rev-parse HEAD for the real base_sha.
      That story must settle three things:
      • Whether cost-state cost matches get_session’s cost_usd (subagents included or not).
      • No-op and never block a turn when the key is absent: locally, and in sessions not launched from alfred.
      • Every coding session gains write access to ledger rows through the proxy credential.
      Arms and prompt versions (spike step 3) can ride on it. Once it ships, this backfill is needed only for history.
    • Red-CI counts, review-finding parsing and escaped-bug tracing: later columns, derivable from pr_number and session_record.
  • Fidelity. Rebuilt prompts use today’s title and notes, can’t see the owner’s edits before sending, assume the launch came from alfred’s link, and read skills as they were at session start, before any edits the session made itself. Every rebuilt row is therefore marked reconstructed and should be treated as “very likely”, not observed.
  • Old sessions. Whether June sessions’ records are still readable is unconfirmed; the spike only fetched sessions from August onward. A missing record degrades to session_record_unavailable and doesn’t fail the run.
  • Subagent cost. Whether usage includes subagent tokens is still unconfirmed (spike §5). The ledger stores what the record says.
  • Transcription. Subagents copying JSON is the one non-deterministic step. D7’s sampled verification bounds the risk; it doesn’t eliminate it.
  • Node type stripping. It rejects non-erasable TypeScript (enums, parameter properties). No historical links.ts uses any today. If one ever does, fall back to typescript.transpileModule for that sha.

After it ships (for you)

  1. Generate a random key and set it as LEDGER_API_KEY in Vercel’s production env, then redeploy.
  2. In the alfred cloud environment’s settings, add an API credential for alfred’s host that sends Authorization: Bearer <key>. If that section isn’t offered, add a LEDGER_API_KEY env var instead. Also set ALFRED_BASE_URL to the app’s URL. Never paste the key into a chat.
  3. Start a new session on alfred and ask it to “run the session-ledger backfill”. It is a one-time seed: once the recording hook ships, new sessions record themselves. Until then, re-running refreshes rows safely.
