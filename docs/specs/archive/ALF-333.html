ALF-333 — Send ASAP comms and task due-times to Telegram

Your phone buzzes from a private alfred bot on Telegram in two cases: alfred judges a message ASAP, or a task's due time arrives.

Decisions

  1. D4What never pings?

    Tier changes you make, verdicts over 30 minutes old, and due times over 15 minutes past.

    Otherwise deploy day and every outage would replay a backlog as a burst.

  2. D5How fast does a ping arrive?

    Within a minute, from a new cron that uses the account's last free slot.

    Every existing tick is already at its 50-subrequest ceiling.

  3. D6Which time zone are due times read in?

    America/Chicago (the Worker's existing zone), whatever the phone's zone.

    The Worker can't know where you are. If you travel, pings still fire on Chicago time.

  4. D7Is each ping recorded?

    Yes, one row per ping in a new notifications table.

    It dedupes across ticks, and lets the Firewall show alfred's stream later.

  5. D1How does alfred reach you?

    A dedicated Telegram bot, send-only: no buttons, no replies.

  6. D2What does an ASAP ping say?

    The sender, the account and alfred's one-line ask, never the message body.

  7. D3When does a timed task ping?

    Once, at its due minute. Tasks with only a date never ping.

☞ open: your pick · → proposed: my call · ✓ settled: yours. Merging accepts every proposed row.

Not doing

Buttons or replies; a morning digest of date-only tasks; quiet hours (Telegram's and iOS's own settings handle that).

Heads-up

  • A one-time phone and BotFather setup, plus two Worker secrets: see After it ships.
  • Bot chats aren't end-to-end encrypted, so every ask sits on Telegram's servers.
  • This uses the Cloudflare account's fifth and last free cron trigger.

Working detail

Everything below is for the implementing agent. Approving needs only what’s above.

Context

The problem. Today alfred can't reach the owner at all. An ASAP comms row only exists for someone who opens /comms and looks, and a timed task (ALF-161's due_time) is past due without anyone saying so. The ticket asks for both to land on the owner's phone through Telegram.

What this departs from. The comms epic (ALF-7, revision R6) removed an outbound ASAP notification (D16 and story M) because the owner had never decided on one, and it left Q0 open: "whether alfred should be able to reach out, and how". This ticket is the owner's answer: yes, via Telegram, for ASAP. D16 and M stay retired identifiers, so this is a new decision rather than their revival.

What it builds on.

  • docs/spikes/notifications-spike.md chose the channel: a dedicated BotFather bot, a plain fetch to the Bot API from the existing Worker, and the secrets TELEGRAM_BOT_TOKEN and TELEGRAM_CHAT_ID. It also asked for each send to be recorded so the Firewall can later show alfred's stream (realized by D7).
  • workers/src/index.ts dispatches four cron expressions on event.cron. Each existing tick is budgeted against the Free plan's 50 subrequests per invocation and sits near the ceiling: TICK at about 49, READER at 48, RETENTION at exactly 50. wrangler.toml notes that the account allows five triggers and four are in use.
  • The comms judge writes a comm_verdicts row (with ask, a one-line statement of what the sender wants, and person_id), then points comm_messages.verdict_id/tier at it, with judged_by = 'model'. When the owner retiers a row, judged_by becomes 'owner'. Messages are deleted at 60 days.
  • items.due_date is a calendar date stored as UTC midnight, and items.due_time is a floating time (migration 0053_due_time.sql). task_items excludes code-module rows. The Worker already resolves dates in CLASSIFIER_TIMEZONE = "America/Chicago".

The owner's answers in this session, now D1–D3:

  • Ping at the due minute only.
  • Sender plus ask, never the body.
  • Send-only for v1.

Network. During this session the owner added api.telegram.org and core.telegram.org to the cloud environment's allowlist. D9's facts were checked against the live docs (Bot API 10.3, 2026-08-24), and an unauthenticated getMe returned {"ok":false,"error_code":401,"description":"Unauthorized"}. An authorized send still can't happen from a cloud session. The token sits in the URL path, where the proxy can't inject it, and secrets never go in the sandbox. So the first real send is the owner's (After it ships, step 8).

Decision records

D1How does alfred reach you? · settled

The channel is the spike's: a private bot that messages one chat. It is send-only, because inline buttons need an inbound Telegram webhook on the Worker (secret-token header, chat_id authorization, callback handling), which would roughly double the scope and add an attack surface. Considered: buttons (deferred to a follow-up ticket); SMS or iMessage and Pushover (both rejected in the spike).

D2What does an ASAP ping say? · settled

The ping carries the sender label, the account label, the verdict's ask, and a link to /comms. It never carries the body, the subject or the handle. Bot chats are Telegram "cloud chats", stored server-side without end-to-end encryption. The ask is alfred's paraphrase, so it exposes less than the body while still telling the owner whether to look. Considered: sender only (too little to act on), and a body excerpt (the most exposure).

D3When does a timed task ping? · settled

One ping per (task, date, time) at the due minute. A task with only a date has no minute to fire on. A morning digest of those tasks would be a separate feature. Considered: a lead-time ping, ping-before plus ping-at, and a digest.

D4What never pings? · proposed

A ping means "this just became true". Three rules keep every ping about something that just happened:

  • Only the model's ASAP pings. The row's judged_by is 'model'. A move the owner made to ASAP is something they already know, and filter, unjudged and refusal rows never reach ASAP anyway.
  • Only a fresh verdict pings. The current verdict's created_at is within 30 minutes. Without this, the first deploy would ping every ASAP row still open. A re-run that moves a row Today → ASAP does ping, because it writes a fresh verdict and the row has never pinged. ASAP → ASAP doesn't ping again, because the dedupe key is the message (D7).
  • Only a recent due moment pings. The due moment must fall in (now − 15 min, now]. That excludes the backlog of already-overdue timed tasks on deploy day, a task created with a time already past, and catching up after a Worker or Supabase outage longer than 15 minutes. A retry of an existing claim is governed by D11, not by this window.

A message the Mac daemon delivers hours late (ALF-7 D17, Mac asleep) still pings, because the clock starts when the verdict is written, not when the message was sent. That is deliberate: it's the case where the owner most needs to hear.

Considered: no windows (a burst of stale pings on deploy) and a launch-time watermark (it handles deploy day but not outages).

D5How fast does a ping arrive? · proposed

A new NOTIFY_CRON = '* * * * *' gives due pings ≤ 1 minute late and ASAP pings ≤ 1 minute after the judge tick, so ≤ 3 minutes from ingest. It can't share a tick, because each existing one is at its subrequest ceiling (Context). This uses the fifth and last trigger the account allows on the Free plan, so the next scheduled feature has to share NOTIFY's budget (its idle cost is one RPC) or move to the paid plan.

The expression has no step, so it can't collapse onto another schedule (the POLL_CRON trap). It does coincide with every other tick, which is harmless because each invocation has its own budget.

Considered:

  • Piggybacking on */2 (it busts that tick's budget).
  • A Durable Object alarm per task (a new binding type and the exact-minute firing it buys isn't needed).
  • The Workers Paid plan (worth having, but not this story's call).

D6Which time zone are due times read in? · proposed

The due moment is ((due_date at time zone 'UTC')::date + due_time) at time zone CLASSIFIER_TIMEZONE. due_time floats on the device, but a server has no device, so it reuses the one zone the Worker already treats as "where the owner is". When the owner travels, the app shows 3 PM local while the ping fires at 3 PM Chicago. A var rename (for example to OWNER_TIMEZONE) is out of scope. The notify tick reads the existing var and does the same missing-var abort the sweeps do.

On a DST spring-forward day, a time that doesn't exist that day (02:30) resolves the way Postgres resolves it, an hour later. That's acceptable at single-user volume.

D7Is each ping recorded? · proposed

The new notifications table (§Contracts) has three jobs:

  • Dedupe and claim across overlapping ticks. A unique index on (kind, fire_key) lets a claim be one atomic insert … on conflict do nothing.
  • Retry state. See D11.
  • The spike's Firewall forward-compatibility. The Bot API can't read a bot's own history back, so recording at send time is the only record. The row stores the sent text and Telegram's message_id.

Retention follows the subject: on delete cascade from comm_messages (so the 60-day sweep takes the stored ask with it) and from items.

Considered: a notified_at column on each source table. That needs two migrations to the busiest tables, can't re-arm a rescheduled task, and records nothing the Firewall could show.

Implementation decisions

D8 · One claim RPC per tick, built text in the Worker

claim_notifications(p_now, p_zone, p_limit) does both the eligibility (D4) and the claim in SQL, and returns every field the message needs, which costs one subrequest. The Worker builds and escapes the text (Jest-tested), sends it, then makes one PATCH to stamp the outcome. Worst case per tick is 1 + 2 × NOTIFY_LIMIT (20), so 41 of 50 subrequests.

D9 · The minimal Bot API surface

The only Bot API call is POST https://api.telegram.org/bot<TOKEN>/sendMessage with a JSON body of chat_id, text, parse_mode: "HTML" and link_preview_options: { is_disabled: true }. The response is read as { ok, result?: { message_id }, error_code?, description?, parameters?: { retry_after? } }. HTML rather than MarkdownV2 because the docs require escaping only <, > and & outside tags, while MarkdownV2 escapes about 18 characters. All of this is checked against Bot API 10.3 (Context).

If a send gets 400, the Worker retries it once immediately as plain text, with parse_mode and link_preview_options removed and the tags stripped. An escaping bug ("can't parse entities") then degrades the ping instead of dropping it. That retry costs one extra subrequest, which is inside D8's headroom.

D10 · Text caps

The ask is capped at 300 characters and a task title at 200, ending in "…". The total stays far under Telegram's 4096-character message limit. Sender label: comm_people.name via the verdict's person_id, else sender_name, else sender_handle. The handle is the one D2 field allowed, and only when there is no name. Account label: comm_accounts.label. Time: h:mm AM/PM, with no leading zero.

D11 · Failure handling

Branch on the HTTP status, not the body's error_code, which the docs say "is subject to change". Read parameters.retry_after on a 429 for the log line.

OutcomeWhat happens
ok: trueStamp sent_at, telegram_message_id and text.
429Stop sending this tick. The claim stays unsent and no attempt is counted. The next tick retries.
5xx, network or timeoutCount the attempt (attempts + 1, last_error) and retry next tick.
400 after the plain-text retryCount the attempt.
401 or 403Systemic: a bad token, or the bot was never started or was blocked. Abort the tick with a distinct log banner and count no attempts.

The RPC re-returns an unsent claim while attempts < 3, claimed_at > now − 60 min and its subject is still eligible: the task is active with the same date and time, or the message is still ASAP and uncleared. Otherwise it stamps abandoned_at. So a systemic outage that's fixed within the hour still delivers.

D12 · Configuration gating and health

If either secret or ALFRED_APP_URL is missing, the tick logs notify: telegram unconfigured and returns without calling the RPC, so nothing is claimed while it's off. GET / gains telegram configured|unconfigured, reporting presence only and never probing Telegram, the same policy as the Anthropic key. ALFRED_APP_URL is a committed [vars] entry (https://alfred-six-gamma.vercel.app, the public origin, not a secret).

D13 · Keep the token out of logs and commits

The token travels in the URL path. Never log the request URL, and never let a caught error's message (which some runtimes build from the URL) reach console unredacted: log error_code and description only. Add a secretlint pattern for bot tokens to /.secretlintrc.json (/\b\d{8,10}:[A-Za-z0-9_-]{35}\b/; check it against a fabricated token in the test fixture). This is a deliberate rule addition, which CLAUDE.md permits, not a weakening.

Behaviour

Eligibility (evaluated by claim_notifications at p_now)

KindPings when all holdfire_key
comms_asapThe message's direction = 'inbound', tier = 'asap', judged_by = 'model' and cleared_at is null; its current verdict (verdict_id) has created_at > p_now − 30 min; and no notifications row exists with that key.message id
task_dueThe task_items row has status = 'active' and due_time is not null; its due moment (D6) is in (p_now − 15 min, p_now]; and no row exists with that key.item_id|YYYY-MM-DD|HH:MM
  • A rescheduled task changes its key, so it re-arms. A recurring task's next occurrence is a new item.
  • A subtask with its own time pings like any task. A completed task never pings, and a retry of a claim for one is abandoned (D11).
  • New claims are ordered by due moment or verdict time ascending, and retries come first. At most p_limit rows are returned. Overflow waits a tick, still inside the windows, because 20 per minute is far above single-user volume.
  • Sends go one at a time in claim order. Telegram's per-chat rate (about 1 message a second, sustained) is handled by the 429 rule (D11), not by sleeping.

Message text (verbatim, P1)

comms_asap:  <b>ASAP</b> · {sender} · {account}\n{ask}\n<a href="{ALFRED_APP_URL}/comms">Open comms</a>
task_due:    <b>Due {h:mm AM}</b>\n{title}\n<a href="{ALFRED_APP_URL}/today">Open Today</a>

Every interpolated value is HTML-escaped (& first). The plain-text fallback (D9) is the same text with the tags removed and the link written as a bare URL on line 3. Messages are sent with sound: disable_notification is not set, so how quiet a ping is gets decided on the phone.

Contracts

Migration <next>_notifications.sql

create table notifications (
  id                  uuid primary key default gen_random_uuid(),
  kind                text not null check (kind in ('comms_asap', 'task_due')),
  fire_key            text not null,
  comm_message_id     uuid references comm_messages (id) on delete cascade,
  item_id             uuid references items (id) on delete cascade,
  claimed_at          timestamptz not null default now(),
  sent_at             timestamptz,
  telegram_message_id bigint,
  text                text,          -- what was actually sent; null until sent
  attempts            int not null default 0,
  last_error          text,
  abandoned_at        timestamptz,
  constraint notifications_subject check (
    (kind = 'comms_asap' and comm_message_id is not null and item_id is null) or
    (kind = 'task_due'   and item_id is not null and comm_message_id is null))
);
create unique index notifications_key_idx on notifications (kind, fire_key);
create index notifications_pending_idx on notifications (claimed_at)
  where sent_at is null and abandoned_at is null;
-- RLS on + the "authenticated full access" policy + explicit grants, as 0034 does;
-- migration-lint's rules apply.

create function claim_notifications(p_now timestamptz, p_zone text, p_limit int)
returns table (id uuid, kind text, attempts int,
               sender text, account text, ask text,      -- comms_asap
               title text, due_time time)                -- task_due
-- 1. abandon unsent claims that fail D11's retry test;
-- 2. insert new claims per §Behaviour (on conflict (kind, fire_key) do nothing);
-- 3. return retryable + newly inserted, retries first, limit p_limit.
-- security invoker; grant execute to service_role (and the usual roles, as 0034 does).

Acceptance criteria

  • A model-judged ASAP verdict written in the last 30 minutes, on an uncleared inbound row, produces exactly one sendMessage whose text is the verbatim comms_asap format, with sender, account, ask and the /comms link, and no body or subject.
  • An active task due at D T (Chicago) produces exactly one task_due send on the first tick at or after that minute, with the Due h:mm AM line, the title and the /today link.
  • A task with a due_date but no due_time never produces a send.
  • No send for: an owner-set ASAP; a verdict older than 30 minutes (including every ASAP row present at first deploy); a due moment more than 15 minutes past; a completed task; a cleared message.
  • An ASAP → ASAP re-run doesn't send again. A Today → ASAP re-run sends once. Rescheduling a task that already pinged re-arms it for the new time.
  • The Worker dispatches * * * * * to the notify tick, and no other unit runs on it.
  • The due moment is computed in CLASSIFIER_TIMEZONE. A missing zone aborts the tick and claims nothing.
  • Every successful send leaves a row with sent_at, telegram_message_id and the sent text. Deleting the message or task deletes its rows.
  • 429 stops the tick with no attempt counted. A 5xx is retried on later ticks up to 3 attempts. 401/403 aborts with a banner. A claim past 60 minutes, or whose subject is no longer eligible, is abandoned and never sent.
  • A 400 triggers exactly one plain-text resend, with no parse_mode and no tags.
  • If any of the two secrets or ALFRED_APP_URL is missing, the tick makes no RPC and no send, and GET / reports telegram unconfigured. With all three set, it reports configured and never calls Telegram.
  • No log line or thrown message contains the bot token. secretlint flags a fabricated bot token in a fixture.

Review focus

  • An ask or title containing <, &, > or an emoji → rendered literally, never as markup or a 400.
  • A 2,000-character ask, or a sender with no name → capped with "…"; the sender falls back to the handle.
  • Two ticks overlapping on one due minute → one claim, one send (the unique index arbitrates).
  • A task edited from 3:00 to 2:50 at 2:58 → pings once for 2:50 (inside the window) and never for 3:00.
  • A due time of 23:30 Chicago, which is the next UTC day → pings at 23:30 Chicago on the right date.

Out of scope, risks & unknowns

  • Buttons or replies need an inbound webhook (D1), so they belong in a follow-up ticket. The same goes for a date-only digest (D3) and operational alerts such as a failed backup, which the spike names as the obvious next sender on this channel.
  • Quiet hours are left to Telegram's per-chat settings and iOS Focus (After it ships). ASAP means "break focus", so alfred doesn't decide when to stay quiet.
  • Still unverified. Which 403 descriptions cover a never-started bot and a blocked bot, and the exact bot-token length (D13's pattern). The docs' example token is not real-shaped. An unauthenticated call can't show either. The owner's first live ping confirms the happy path, and wrangler tail shows the status and description if it fails.
  • The cron slot. Confirm in the Cloudflare dashboard that no other Worker on the account uses a trigger. If one does, wrangler deploy fails on the trigger count, and the fix is moving to the paid plan or dropping a schedule, not this story's call.
  • Telegram-side retention. Sent pings stay in the chat until deleted. alfred's own copy cascades away (D7). If the client offers it, enable the chat's auto-delete timer on the phone.

After it ships (for you)

  1. Install Telegram on the iPhone from the App Store and sign up or log in with your phone number.
  2. Create the bot. Search @BotFather (blue verified check) and send /newbot. Name it alfred; the username must be unique and end in bot (for example ac3_alfred_bot). BotFather replies with the token. Treat it like a password: never paste it into a Claude chat, a commit or a demo doc.
  3. Lock it down. In BotFather send /setjoingroups, pick the bot and choose Disable, so nobody can add it to a group.
  4. Start the chat. Open the t.me/<username> link from BotFather's reply and tap Start. A bot can't message you until you've started it; without this step sends fail with 403.
  5. Find your chat id on the Mac, not in a cloud session: run read -rs TOKEN and paste the token (it stays out of shell history), then curl -s "https://api.telegram.org/bot$TOKEN/getUpdates". The number at result[0].message.chat.id is your chat id. If result is empty, send the bot "hi" and run it again.
  6. Set the secrets from workers/: run npx wrangler secret put TELEGRAM_BOT_TOKEN, then npx wrangler secret put TELEGRAM_CHAT_ID, pasting each value when prompted. No redeploy is needed.
  7. Check it's configured: curl -s https://alfred-workers.alfred-six-gamma.workers.dev/ should include telegram configured.
  8. Live check: give a task a time two minutes from now. Within about a minute of that time, the ping should arrive looking like Plate I. If it doesn't, run npx wrangler tail to see the notify line and any error_code.
  9. Tune the alerts on the phone:
    • In the alfred chat, tap the bot's name, then Notifications, to set its own sound and make sure it isn't muted.
    • In iOS Settings → Notifications → Telegram, allow notifications and the lock screen.
    • If you don't want the ask on your lock screen, turn off Telegram → Settings → Notifications and Sounds → Show Previews.
    • To let ASAP break through a Focus, add Telegram under Focus → Allowed Apps. iOS allows apps, not chats, so mute any other Telegram chats.
    • Mute the chat in Telegram on the Mac, if you install it there, to avoid double alerts.
  10. If the token ever leaks: send /revoke in BotFather, then run wrangler secret put TELEGRAM_BOT_TOKEN with the new token.
