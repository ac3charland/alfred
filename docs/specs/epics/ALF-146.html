ALF-146 — Habit Tracker

Epic Tasks module DB · API · Store · UI · Coach Epic spec — durable context and decisions for the whole body of work. No implementation, and no per-story specs; each story is refined in its own session.

Read this before refining any ALF-146 story. Every decision below is settled with the owner unless it appears in §9 Open questions. If a story session finds one inconvenient, that is a conversation to have — not a decision to quietly re-take. Decisions carrying a revised tag were reopened after the first refinement round; the text shown is the current one.

1 · Problem space & why now

The owner's goal this quarter is to get up at 6:00 AM consistently — and, as part of the same morning, to get outside for light exposure. That is not a task. It has no completion, no due date, and no meaningful "done" — it is a standing commitment whose only real measure is a run of days. alfred currently has nowhere honest to put it:

  • A task is the wrong shape. Recurring tasks already exist (items.recurrence, complete_and_spawn), and a daily "get up at 6" recurring task almost works — except that the only outcome a task can record is completion. A day you failed and a day you never looked at the app are the same row in the same state. Habit tracking is precisely the thing that needs to record a miss as a first-class event, and tasks structurally cannot.
  • The volume is wrong too. A daily habit generates ~90 rows a quarter. Routed through items, those land in the Inbox, the Priority list, the Completed view, the folder counts, the search index, and the getAllItems() seed the whole shell loads on every request. One habit would drown the task system it is supposed to sit beside.
  • The coach has no signal. The Friday productivity-coach review already reads alfred for the merged-PR ratio (GET /api/code/pr-ratio) and writes back the week plan (POST /api/weekly-plans) — see docs/productivity-coach-primer.md. "Did you actually get up at 6 this week?" is exactly the kind of question that review exists to ask, and right now the answer lives only in the owner's memory.

So this epic introduces a new entity (a habit, its criteria, and its daily log), a new view, and a third entry in the coach's API surface. The unit of value is a single loop: define a habit → record each day's outcome → see the chain and how it's consolidating → have the coach read it on Friday.

The reference habit. Every decision below was pressure-tested against the owner's real one, which is more demanding than "daily checkbox" in three specific ways — and each of those drove a decision:
  • It has two parts — up by ~6:15, and outside for light — that succeed or fail as one day, not as two habits. → D3
  • It aims at every day, but one miss a week shouldn't kill the run. → D4
  • One part is a measured time, the other a yes/no. → D3

2 · Decisions

Each decision carries its rationale. D1–D8 were settled with the owner across two refinement rounds; D9–D14 follow from those plus existing repo convention.

D1Habits are their own tables, not a new item_type

New tables — habits and habit_entries — with no relationship to items. There is no item_type = 'habit'.

Why: the generic-item core exists so a captured thought can be converted between task / code / knowledge destinations (SPEC §3.1). A habit is never any of those and never converts into one — it is a definition plus a dense daily log, a fundamentally different cardinality. Reusing items would buy the recurrence engine and pay for it with habit rows leaking into every task view, store, count and search path in the app. Keeping the tables separate also means the entry log can carry the one thing tasks can't: an explicit miss.

D2Habits are a view inside the Tasks module, at /habits

A sidebar entry beneath Week Plan in FolderNav, a branch in TaskViews, a page under app/(shell)/(tasks)/habits/, and a go-habits destination in the ⌘K palette. Not a third segment in the Tasks ⇄ Code switcher.

Why: this is the same shape as /priority and /plan — a cross-cutting personal-productivity surface, not a peer module with its own sidebar. The switcher is a deliberate two-up segmented control, and the named accents are already pencilled in for the SPEC §13 modules (Tasks = teal, Code/Factory = amber, Knowledge = green, Firewall = blue); habits would have to squat on one. Promotion to a module later is cheap — the data model doesn't change, only the navigation — so start at the cheaper altitude.

D3A habit is a list of criteria; a day is met / partial / missed / skippedrevised

A habit holds 1..n criteria, each either boolean ("got outside for light") or measured with a unit, target and comparator ("wake time ≤ 06:15"). Every criterion is required. An entry records a result per criterion, and the day's status is derived:

metevery criterion passed
partialat least one passed, at least one didn't
missedno criterion passed
skippedexcused by hand — illness, travel (never derived)

Why: the reference habit is one commitment with two parts, and the owner experiences it that way — splitting it into "Up at 6" and "Morning light" would produce two chains for one morning and make neither answer "did I do my morning routine?". A single metric field could hold the wake time or the boolean, never both. Partial exists because the distinction is real and actionable: "up on time but skipped the light" is a different failure from sleeping through, and flattening them to missed throws away exactly the signal the Friday review wants. Making every criterion required (rather than adding an optional/bonus flag) keeps the derivation a single rule; if a criterion shouldn't be able to fail your day, it doesn't belong on the habit.

D4Weekday set, plus a rolling miss allowancerevised

Two independent fields:

  • active_days — ISO weekday numbers the habit applies to (default all seven). A day outside the set is not applicable: neutral, never scored, invisible to every statistic.
  • allowance — at most N non-met days in any trailing 7-day window before the streak breaks (default 0 = strict; the reference habit uses 1).

Why the weekday set: "up at 6 on weekdays" is a real shape, and without it every Saturday reads as a failure.
Why the allowance, and why it is not an N-per-week quota: a quota ("gym 3×/week") makes the week the unit of success — a different entity with a different visualization. The owner's habit keeps the day as the unit and merely tolerates a bounded number of failures. That is one parameter on the streak walk, not a second mode. Quotas remain out (§7).
Why rolling rather than calendar-week: a Mon–Sun reset lets you miss Sunday and then Monday — two misses in two days, each "the only one that week" — and keep an unbroken streak. That is plainly against the intent. The rolling window costs a slightly fussier explanation and buys a number that can't be gamed.

D5One rule: anything that isn't met or skipped spends allowancerevised

missed, partial, and an unlogged (unknown) day all consume one unit of the rolling allowance. skipped is transparent — it neither extends the streak nor spends anything. Unknown and skipped days remain excluded from both sides of the hit rate, so a day you never logged still never counts as a failure in the statistics.

Why: the first round set "unknown ends the streak" while a logged miss was unforgiven too, so the two were consistent. Adding the allowance (D4) broke that: had unknown kept hard-breaking, forgetting to log would be punished more harshly than failing — the app would quietly train the owner to stay silent about bad mornings, corrupting the very data the coach reads. Charging both the same is the only coherent option, and it collapses four cases into one sentence. Keeping unknown out of the hit rate preserves the original point: statistics stay truthful even though the chain is unforgiving.

D6No quarter entity — but a formation stage from cumulative met daysrevised

A habit has started_on and, once retired, archived_at. There is no quarter table, no rollover, no renewal. Alongside the streak, each habit shows a formation stage derived from its total met days ever — not its current streak:

Fully Deliberate0–13 met days
Gaining Momentum14–41
Nearing Automaticity42–65
Possibly Established66+

Why no quarter: "quarterly habit" describes intent, not a lifecycle the software must enforce. A quarter boundary is derivable from dates by the one consumer that cares (the coach), and modelling it would add rollover, an expired state, and a renewal ritual to express what started_on already implies.
Why cumulative days and not the streak: automaticity accrues from repetitions. Keyed to the streak, a single miss would demote the habit from "Nearing Automaticity" back to "Fully Deliberate" — demoralising, and not what the evidence says. Banked progress should not be confiscated by one bad morning. The streak already answers "how consistent am I right now"; the stage answers "how much have I banked". Two questions, two numbers.
On the thresholds: 66 is the median from Lally et al. (2010), whose observed range was 18–254 days. The ladder is therefore deliberately approximate and must be labelled as such in the UI ("Possibly Established", not "Established"). Hard-coded rather than configurable — a per-habit target is an easy additive change if the fixed ladder proves wrong, and guessing at configurability now would add a form field nobody has asked to fill in.

D7Two logging paths: the app, and a keyed API write

In-app logging from /habits is the primary path. In addition, the entry-upsert endpoint accepts the existing INGEST_API_KEY (x-api-key), so the productivity coach can log "I got up at 6:05 and went outside" from chat and a Siri Shortcut can log by voice — the same dual-auth pattern as POST /api/items and GET /api/code/pr-ratio.

Why: the friction that kills habit tracking is remembering to open the app at 6 AM. The keyed ingress already exists, is already documented for the coach, and costs one wrapper (withSessionOrApiKey / resolveIngestClient) to reuse. Note this widens the key from write-only-to-the-archive to also readable for habits (D8) — called out explicitly in §7 so it is a considered change, not a drift.

D8The read endpoint returns definitions, entries and derived stats

GET /api/habits returns each habit's definition, its entries over a requested window, and every derived number the UI shows — current / longest / average streak, allowance remaining, hit rate, cumulative met days and formation stage.

Why: the streak rules (D4, D5) are subtle enough that a consumer re-deriving them would get a different answer than the UI shows, and the coach quoting a different streak than the app displays is a trust bug. Ship one authority. The precedent is /api/code/pr-ratio, which returns pre-rounded percentages "so they can be quoted directly without re-deriving them".

D9Streaks are computed in TypeScript, not SQL

A pure, dependency-free module under frontend/lib/habits/ owns applicable-day logic, criterion evaluation, the allowance-aware streak walk, and the formation ladder. The API route and the client store both call it.

Why: it matches lib/recurrence, lib/priority and lib/tree — pure logic in TS, exhaustively unit-tested, so the optimistic client store and the server produce identical numbers with no round-trip. A Postgres function would force a network call to answer "what's my streak?" after every optimistic click — and the rolling-window walk is exactly the kind of logic that deserves table-driven unit tests rather than SQL.

D10Criteria and results are jsonb, keyed by a stable criterion key

habits.criteria is a jsonb array, each entry carrying a stable key. habit_entries.results is a jsonb object keyed by those same keys. No child tables.

Why: criteria are a small, rarely-edited config blob that is always read as a unit with its habit — the same shape as items.recurrence, which is the house precedent. Two child tables would add a join to every read and a migration to every criterion tweak. The stable key is what makes it safe: renaming or reordering a criterion leaves history intact, and a deleted criterion simply leaves orphaned keys in old results, which the reader ignores rather than failing on. The tradeoff accepted: no referential integrity between the two blobs, so lib/habits must treat a missing key as "not recorded" rather than assuming presence.

D11Dates are plain date, resolved in a caller-named timezone

habit_entries.entry_date is a Postgres date — never a timestamptz. "Today" is resolved from a tz query parameter (IANA zone, falling back to UTC on an unrecognized value, exactly as pr-ratio does); the browser passes its own zone, and a write may name date explicitly to backfill.

Why: for a wake-up-time habit the day boundary is the whole game — a 6:04 AM log stored as an instant and re-read in the wrong zone lands on the previous day and silently corrupts a streak. A calendar date has no such ambiguity. alfred has no user-timezone setting and this epic does not add one; the caller naming its zone is the established convention.

D12A derived status is frozen at write time

The resolved day status is stored alongside the per-criterion results. Editing a habit's criteria or targets later does not retroactively re-score history.

Why: a chain you already earned should not break because you tightened the goal in month three or added a third criterion in month four. The stored status is the historical verdict; the stored results keep the raw truth for charting. Re-scoring would also make the coach's Friday numbers non-reproducible week to week.

D13The stats surface is a first-class part of the view

Every habit shows, next to its history: current streak, longest streak, average streak, allowance remaining, hit rate, and the formation stage. They render in a rail beside the history grid (§6); that they exist at all is not optional.

Why: "how long has this been going" is a headline outcome of the feature, not a caption. The first draft left the streak as a number in a card header, which under-served it. Naming the six figures here stops a UI story from shipping a chart with the answer buried.

D14One quiet badge; no other view changes

The /habits nav link carries a count of today's applicable-but-unlogged habits, reusing the FolderCountBadge pattern. Nothing is added to Priority, the Inbox, the capture screen, or the Week Plan.

Why: discoverability without interruption, and it keeps this epic's blast radius to one new view plus one nav link. The heavier option — a check-off card on /priority — stays available as a follow-up once there is real usage data on whether the badge is enough.

3 · The streak engine

This is the epic's highest-risk logic and the reason lib/habits exists. Everything here is a pure function of (habit definition, entries, today).

3.1 Definitions

ConceptRule
Applicable day A date d where d ≥ started_on, archived_at is null or d precedes it, and isoWeekday(d) ∈ active_days. Non-applicable days are never scored and appear in no denominator.
Day status Derived from the per-criterion results and frozen (D3, D12): all pass → met; some pass → partial; none pass → missed. skipped is only ever set by hand.
Spent day Any applicable day that is missed, partial, or unknown (no row). These consume allowance (D5).
Allowance remaining allowance − (spent days in the trailing 7 calendar days), floored at 0. This is the number the UI shows as "1 miss left".
Current streak Walk backwards from the start point over applicable days. met extends the run and increments the count; skipped is stepped over transparently; a spent day does not increment the count but only ends the run if the trailing-7-day spent count at that day exceeds allowance. Today is exempt: if today is applicable and unlogged, the walk starts at the previous applicable day — otherwise every streak would read 0 each morning until logged.
Longest streak The maximum such run over the habit's whole history, under the same rules.
Average streak Mean length of completed runs — the in-progress current run is excluded, so a long healthy streak doesn't drag the average down while it's still growing. Undefined (shown as —) until at least one run has ended.
Hit rate met / (met + partial + missed) over the requested window. Unknown and skipped days appear on neither side (D5).
Formation stage From the count of met days over all history, against the D6 ladder. Never decreases.
The streak counts met days, not elapsed days. A run of 10 days containing one forgiven miss reads 9, not 10 — the run is unbroken, but a forgiven day was not earned. The history visualization shows the bridge (§6, connector) so the two numbers reconcile visually instead of looking like an off-by-one.

3.2 Worked example — the reference habit

Mon–Sun, allowance: 1 per rolling 7 days. Criteria: wake ≤ 06:15, got outside.

MTWTFSS

Wednesday was partial — up at 06:02 but no light. It spends the week's one allowance, so the run survives (dashed bridge) but does not count: current streak 6, allowance remaining 0 until Wednesday rolls out of the trailing window.

4 · Architecture & data model

4.1 Data flow

Both the view and the coach reach the same routes; the same pure lib/habits module derives stats on the server and in the optimistic store, so the two never disagree.

4.2 Schema shape

Illustrative, not final DDL — the story session writes the migration and takes the next available migration number (never a number pinned here). RLS is mandatory and explicit grants are required on both tables (and on any sequence) or the Data API returns "permission denied" — see the supabase skill and migration-lint. 

-- habits ────────────────────────────────────────────────────────────
id           uuid  pk
name         text  not null
notes        text
criteria     jsonb not null                                  -- 1..n, all required  (D3, D10)
             -- [{ key: 'wake', label: 'Up by 6:15', kind: 'time',
             --    target: 375, comparator: 'lte' },
             --  { key: 'light', label: 'Outside for light', kind: 'boolean' }]
active_days  smallint[] not null default '{1,2,3,4,5,6,7}'   -- ISO 1=Mon .. 7=Sun  (D4)
allowance    smallint   not null default 0                   -- non-met days per rolling 7  (D4)
started_on   date  not null default current_date             -- (D6)
archived_at  timestamptz                                     -- retire, never delete
sort_order   int
created_at   timestamptz not null default now()

-- habit_entries ─────────────────────────────────────────────────────
id          uuid pk
habit_id    uuid not null references habits(id) on delete cascade
entry_date  date not null                                    -- plain date  (D11)
status      habit_day_status not null  -- 'met'|'partial'|'missed'|'skipped', frozen  (D12)
results     jsonb                                            -- { wake: 364, light: true }  (D10)
note        text
created_at  timestamptz not null default now()
updated_at  timestamptz not null default now()
unique (habit_id, entry_date)                                -- one row per habit per day

The unique (habit_id, entry_date) constraint is load-bearing: it is what makes the write path a plain upsert — logging is idempotent, and correcting a day is the same call as making it.

Time criteria store minutes after local midnight (integer, e.g. 364 = 06:04), rendered as HH:MM from kind: 'time'. A Postgres time column would drag zone semantics back into a model D11 deliberately keeps zone-free. A boolean criterion stores true/false; a count or duration criterion stores a plain number.

4.3 Frontend wiring

Habits follow the established data-flow architecture exactly (see the data-flow and frontend-architecture skills): a server-side lib/data/habits.ts fetch seeded once by the (shell) layout into a HabitsProvider optimistic store with reconcile/rollback and a toast on failure; the view reads from the store and never calls router.refresh().

One deviation from "fetch everything": the shell seeds a bounded window of entries (the last ~120 days) rather than all history. The existing eager-fetch tradeoff is accepted at hundreds of rows; a daily habit is a few hundred rows per habit per year and grows without bound, so the window is the point at which that tradeoff stops holding. Scrolling further back is an on-demand fetch, the same shape as pulling an older week's plan HTML.

Note for the store: cumulative met days and longest streak (D6, §3.1) are all-history figures that a 120-day window cannot derive. The read endpoint returns them as precomputed scalars alongside the windowed entries, and the optimistic store adjusts them locally on a write rather than recomputing from the window.

5 · API surface

RouteAuthPurpose
GET /api/habits session or API key Definitions + entries in a window + all derived stats (D8). Query: tz, from, to, include_archived.
POST /api/habits session Create a habit, with its criteria.
PATCH /api/habits/[id] session Rename, edit criteria / active_days / allowance / notes, archive, reorder.
DELETE /api/habits/[id] session Hard delete, cascading entries. Archiving is the expected path; delete is for mistakes.
PUT /api/habits/[id]/entries session or API key Upsert one day (D7). Body: { date?, results?, status?, note? }. date omitted ⇒ today in tz. status omitted ⇒ derived from results and frozen (D3, D12); passing status: 'skipped' explicitly is how a day is excused.

Errors use alfred's standard { "error": "…" } envelope. Auth follows the existing precedence rule the primer documents: a present x-api-key wins outright and an empty value is a mismatch, not an absent header.

6.1 Two refinements to the connector

Both were raised by the owner against the round-two mockups and are part of the spec, not polish — each fixes a way the plain gap bar misrepresents the streak rules in §3.

  1. A forgiven day's links are full-width and grey — never dashed. The bar keeps exactly the weight and geometry of a normal link and changes only colour. A dashed line reads as weaker or uncertain; the run across a forgiven day is neither. It is unbroken — it simply wasn't earned, and grey says that without implying the chain is fraying.
  2. A streak crossing a column boundary grows a stub at each end. Sunday sits at the bottom of one column and the next Monday at the top of the next, so no bar can join them. Each therefore renders a half-stub pointing outward — down from the Sunday, up into the Monday. Without it the chain appears to break every week, which is the one thing this visualization exists to communicate correctly.

6.2 The habit card

The reference habit: every day, allowance: 1, criteria "up by 6:15" and "outside for light". The window is a full quarter — which fits without scrolling at this cell size — and the habit itself started partway through it, in mid-June. Every number in the rail is derived from the grid beside it, so the two can be checked against each other.

Four things in that grid are worth reading carefully, because they are the §3 rules made visible:

  • Two weeks contain a partial (the second and the sixth tracked weeks). The links either side go grey, the run continues through, and the streak count skips the day — it was forgiven, not earned. That is why the current streak reads 33 rather than the 35 elapsed days of the run.
  • The third tracked week is a real break. Thursday was missed — grey link in, so it was forgiven on its own — and then Friday was never logged. Two spent days inside the same rolling window exceeds the allowance, so the chain stops dead: no link out of Thursday at all. Saturday begins the run that is still going.
  • Every column boundary carries a stub where the streak survived the Sunday→Monday hop, so one 33-day run reads as a single chain instead of eight weekly fragments.
  • The first five columns are before started_on and render with the same "not tracked" treatment as the three future days at the end. They are not misses, and they are in no denominator — the 94% hit rate is over the 50 logged days only.

6.3 The day editor

Opens on tapping any cell — today or a backfill. The verdict in the header is computed, never typed.

Thu 23 Jul Partial Up by 6:1506:04 Outside for light✕ Spends this week's allowance ⋯

Two properties this shape has to preserve. The header status is a consequence of the criteria and cannot be made to disagree with them — which is what "derived only" buys. And because skipped is the one status the model can't derive, it lives behind the ⋯ overflow rather than as a fourth thing to tap past on every edit.

Accessibility floor for this design. Four day states plus future and n/a is a lot to carry on hue alone, and the cells are small. Met / partial / missed must stay distinguishable without colour — a glyph, border treatment, or fill pattern — and every cell needs an accessible name giving the date, status and criteria results, since the grid is the only way to reach the editor.

7 · Constraints & non-goals

Deliberately outWhy / what to do instead
Reusing items No item_type = 'habit', no recurrence-engine reuse, no habit rows in any task view, store, count or search path (D1). A story that finds itself reaching into items has taken a wrong turn.
N-times-per-week quotas Still out — but note the distinction the allowance draws. A quota ("gym 3×/week") makes the week the unit of success and needs its own week-shaped visualization; D4's allowance keeps the day as the unit and only forgives a bounded number of failures. The second is in; the first is not.
Optional / bonus criteria Every criterion is required (D3). "Track it but never let it fail my day" is a real idea and an easy additive flag later; adding it now would mean two derivation rules before either has been used in anger.
Configurable formation thresholds The four stages are hard-coded (D6). A per-habit goal length is additive if the fixed ladder proves wrong.
Quarters, rollover, renewal No quarter entity of any kind (D6). Date ranges express everything needed.
Reminders & notifications A 6 AM nudge is the obvious next thought and is out of this epic. The channel decision is already made and documented in docs/notifications-spike.md (Telegram bot from the existing Worker) — it becomes its own epic that can consume the habits API, not a story here.
Automatic data capture No Apple Health / sleep-tracker / calendar ingestion. Entries are typed by a human or written by the coach through the keyed endpoint (D7).
Gamification No points, badges, levels, or streak-freeze tokens. The allowance (D4) is a rule, not a currency you earn or spend deliberately.
Retroactive re-scoring Backfilling and correcting a day are in scope; re-scoring history when criteria or targets change is not (D12).
Habit folders / tags / grouping Manual sort_order only. At the expected volume (a handful of active habits) grouping is premature.
Multi-user anything Single-user, role-based RLS as everywhere else — authenticated full access, no user_id column (SPEC §7).

Constraints inherited from the repo

  • RLS + explicit grants are mandatory on both new tables (and any sequence) — omitting a grant produces a "permission denied" the Data API surfaces at runtime, which is exactly what migration-lint exists to catch at commit time.
  • Every behavioral change lands with a test (unit, Storybook, or E2E) and a demo doc under docs/demos/<branch>/ per the showboat skill. §3 is pure functions and should be near-exhaustively table-tested — the rolling-window walk with four statuses, an allowance, a today exemption and transparent skips has more edge cases than the rest of the epic combined.
  • The API key's blast radius widens with D7/D8: it currently writes the plan archive and reads the PR ratio; after this epic it also reads and writes habit data. Worth stating plainly in the primer when the endpoints are documented.
  • Visual work must respect prefers-reduced-motion and the dark-canvas contrast floor (SPEC §5.4). The grid's colour and accessible-name floor is stated with the design in §6.3 — it is a requirement, not a nice-to-have.

9 · Open questions

  1. Should a partial cost the same as a full missed? D5 charges both one unit of allowance, which keeps the rule to a single sentence — but "up on time, forgot the light" arguably isn't as bad as sleeping through. A fractional or separate partial allowance is the obvious refinement and is deliberately deferred until there's real data on how often partials actually occur.
  2. Does the coach get a writeback ritual, or only ad-hoc logging? D7 gives it the ability to write an entry. Whether the Friday review should routinely reconcile the week ("you told me Tuesday was a 6:40 — want me to log it?") is a coach-skill design question, not an alfred one, and can be answered after the endpoint exists.
  3. Is skipped enough of an escape hatch, or will a vacation want a date-range pause on the habit itself? Deferred deliberately — one skipped entry per day is workable for a week away, and a paused_from/paused_to pair is a cheap additive change if it turns out not to be.
