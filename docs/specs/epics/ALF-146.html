ALF-146 — Habit Tracker

Epic Tasks module DB · API · Store · UI · Coach Epic spec — durable context and decisions for the whole body of work. No implementation, and no per-story specs; each story is refined in its own session.

Read this before refining any ALF-146 story. Every decision below is settled with the owner unless it appears in §8 Open questions. If a story session finds one inconvenient, that is a conversation to have — not a decision to quietly re-take.

1 · Problem space & why now

The owner's goal this quarter is to get up at 6:00 AM consistently. That is not a task. It has no completion, no due date, and no meaningful "done" — it is a standing commitment whose only real measure is a run of days. alfred currently has nowhere honest to put it:

  • A task is the wrong shape. Recurring tasks already exist (items.recurrence, complete_and_spawn), and a daily "get up at 6" recurring task almost works — except that the only outcome a task can record is completion. A day you failed and a day you never looked at the app are the same row in the same state. Habit tracking is precisely the thing that needs to record a miss as a first-class event, and tasks structurally cannot.
  • The volume is wrong too. A daily habit generates ~90 rows a quarter. Routed through items, those land in the Inbox, the Priority list, the Completed view, the folder counts, the search index, and the getAllItems() seed the whole shell loads on every request. One habit would drown the task system it is supposed to sit beside.
  • The coach has no signal. The Friday productivity-coach review already reads alfred for the merged-PR ratio (GET /api/code/pr-ratio) and writes back the week plan (POST /api/weekly-plans) — see docs/productivity-coach-primer.md. "Did you actually get up at 6 this week?" is exactly the kind of question that review exists to ask, and right now the answer lives only in the owner's memory.

So this epic introduces a new entity (a habit, and its daily log), a new view, and a third entry in the coach's API surface. The unit of value is a single loop: define a habit → record each day's outcome → see the chain → have the coach read it on Friday.

2 · Decisions

Each decision carries its rationale. Decisions D1–D6 were settled with the owner in the refinement session; D7–D12 follow from them plus existing repo convention.

D1Habits are their own tables, not a new item_type

Two new tables — habits and habit_entries — with no relationship to items. There is no item_type = 'habit'.

Why: the generic-item core exists so a captured thought can be converted between task / code / knowledge destinations (SPEC §3.1). A habit is never any of those and never converts into one — it is a definition plus a dense daily log, a fundamentally different cardinality. Reusing items would buy the recurrence engine and pay for it with habit rows leaking into every task view, store, count and search path in the app. Keeping the tables separate also means the entry log can carry the one thing tasks can't: an explicit miss.

D2Habits are a view inside the Tasks module, at /habits

A sidebar entry beneath Week Plan in FolderNav, a branch in TaskViews, a page under app/(shell)/(tasks)/habits/, and a go-habits destination in the ⌘K palette. Not a third segment in the Tasks ⇄ Code switcher.

Why: this is the same shape as /priority and /plan — a cross-cutting personal-productivity surface, not a peer module with its own sidebar. The switcher is a deliberate two-up segmented control, and the named accents are already pencilled in for the SPEC §13 modules (Tasks = teal, Code/Factory = amber, Knowledge = green, Firewall = blue); habits would have to squat on one. Promotion to a module later is cheap — the data model doesn't change, only the navigation — so start at the cheaper altitude.

D3An entry is met / missed / skipped, with an optional measurement

Every habit is scoreable as a binary. A habit may additionally declare a metric — a label, a unit, a target and a comparator (e.g. wake time ≤ 06:15) — in which case an entry may carry a numeric value and the status is derived from it.

Why: "up at 6" is naturally quantitative — 06:04 and 07:40 are both misses against a 6:15 target but they are not the same morning, and the trend is the interesting part. Forcing every habit to declare a metric would be worse: "no phone in bed" has nothing to measure. Binary is the floor; measurement is opt-in enrichment on top of it.

D4Each habit declares the weekdays it applies to

active_days is a set of ISO weekday numbers (1 = Mon … 7 = Sun), defaulting to all seven. A day outside the set is not applicable: it renders neutral, is never scored, and is invisible to streaks and rates.

Why: "up at 6 on weekdays" is the actual goal, and without this every Saturday reads as a failure — the chain metaphor collapses if the app is wrong about which days counted. N-times-per-week quotas are explicitly out (see §6): a quota is a per-week bar, not a chain, and mixing the two would mean two incompatible visualizations in one view.

D5An unlogged past day is unknown, not a miss

No row means no data. Unknown renders as an empty cell, visually distinct from a logged miss. It ends the current streak (a streak is a run of days you actually met) but is never counted as a failure — it is excluded from the numerator and the denominator of the hit rate.

Why: auto-missing would conflate "I failed" with "I forgot to open the app", and that noise would flow straight into the coach's Friday review as a false signal. Backfill exists precisely so an unknown day can be resolved honestly after the fact. The cost is accepted: a chain can be broken by forgetfulness — but the statistics stay truthful, which is what the coach reads.

D6No quarter entity — habits are open-ended

A habit has started_on and, once retired, archived_at. There is no quarter table, no quarter field, no rollover or renewal action, and the app never groups habits by quarter.

Why: "quarterly habit" describes the owner's intent, not a lifecycle the software needs to enforce. A quarter boundary is derivable from dates by anything that cares — and the one consumer that cares is the coach, which already slices by date range. Modelling quarters would add a rollover concept, an "expired habit" state, and a renewal ritual, all to express something a started_on date already implies.

D7Two logging paths: the app, and a keyed API write

In-app logging from /habits is the primary path. In addition, the entry-upsert endpoint accepts the existing INGEST_API_KEY (x-api-key), so the productivity coach can log "I got up at 6:05" from chat and a Siri Shortcut can log by voice — the same dual-auth pattern as POST /api/items and GET /api/code/pr-ratio.

Why: the friction that kills habit tracking is remembering to open the app at 6 AM. The keyed ingress already exists, is already documented for the coach, and costs one wrapper (withSessionOrApiKey / resolveIngestClient) to reuse. Note this widens the key from write-only-to-the-archive to also readable for habits (D8) — called out explicitly in §6 so it is a considered change, not a drift.

D8The read endpoint returns definitions, entries and derived stats

GET /api/habits returns each habit's definition, its entries over a requested window, and the computed current_streak / longest_streak / hit_rate.

Why: the streak rules (D4, D5, D9) are subtle enough that a consumer re-deriving them would get a different answer than the UI shows, and the coach quoting a different streak than the app displays is a trust bug. Ship one authority. The precedent is /api/code/pr-ratio, which returns pre-rounded percentages "so they can be quoted directly without re-deriving them".

D9Streaks are computed in TypeScript, not SQL

A pure, dependency-free module under frontend/lib/habits/ owns applicable-day logic, streak walking, hit rate, and metric evaluation. The API route and the client store both call it.

Why: it matches lib/recurrence, lib/priority and lib/tree — pure logic in TS, exhaustively unit-tested, so the optimistic client store and the server produce identical numbers with no round-trip. A Postgres function would force a network call to answer "what's my streak?" after every optimistic click.

D10Dates are plain date, resolved in a caller-named timezone

habit_entries.entry_date is a Postgres date — never a timestamptz. "Today" is resolved from a tz query parameter (IANA zone, falling back to UTC on an unrecognized value, exactly as pr-ratio does); the browser passes its own zone, and a write may name date explicitly to backfill.

Why: for a wake-up-time habit the day boundary is the whole game — a 6:04 AM log stored as an instant and re-read in the wrong zone lands on the previous day and silently corrupts a streak. A calendar date has no such ambiguity. alfred has no user-timezone setting and this epic does not add one; the caller naming its zone is the established convention.

D11A derived status is frozen at write time

When a metric habit records a value, the resolved status is stored alongside the value. Editing a habit's target later does not retroactively re-score history.

Why: a chain you already earned should not break because you tightened the goal in month three. The stored status is the historical verdict; the stored value keeps the raw truth for charting. Re-scoring would also make the coach's Friday numbers non-reproducible week to week.

D12One quiet badge; no other view changes

The /habits nav link carries a count of today's applicable-but-unlogged habits, reusing the FolderCountBadge pattern. Nothing is added to Priority, the Inbox, the capture screen, or the Week Plan.

Why: discoverability without interruption, and it keeps this epic's blast radius to one new view plus one nav link. The heavier option — a check-off card on /priority — stays available as a follow-up once there is real usage data on whether the badge is enough.

3 · Architecture & data model

3.1 Data flow

Both the view and the coach reach the same routes; the same pure lib/habits module derives stats on the server and in the optimistic store, so the two never disagree.

3.2 Schema shape

Illustrative, not final DDL — the story session writes the migration and takes the next available migration number (never a number pinned here). RLS is mandatory and explicit grants are required on both tables (and on any sequence) or the Data API returns "permission denied" — see the supabase skill and migration-lint. 

-- habits ────────────────────────────────────────────────────────────
id           uuid  pk
name         text  not null
notes        text
active_days  smallint[]  not null default '{1,2,3,4,5,6,7}'   -- ISO 1=Mon .. 7=Sun  (D4)
metric       jsonb                                            -- null = binary habit (D3)
             -- { kind: 'time'|'count'|'duration', label, unit,
             --   target: number, comparator: 'lte'|'gte' }
started_on   date  not null default current_date              -- (D6)
archived_at  timestamptz                                      -- retire, never delete
sort_order   int                                              -- manual display order
created_at   timestamptz not null default now()

-- habit_entries ─────────────────────────────────────────────────────
id          uuid pk
habit_id    uuid not null references habits(id) on delete cascade
entry_date  date not null                                     -- plain date (D10)
status      habit_entry_status not null                       -- 'met' | 'missed' | 'skipped'
value       numeric                                           -- optional measurement (D3)
note        text
created_at  timestamptz not null default now()
updated_at  timestamptz not null default now()
unique (habit_id, entry_date)                                 -- one row per habit per day

The unique (habit_id, entry_date) constraint is load-bearing: it is what makes the write path a plain upsert — logging is idempotent, and correcting a day is the same call as making it.

Time metrics are stored as minutes after local midnight (integer value, e.g. 364 = 06:04), rendered as HH:MM from metric.kind === 'time'. A Postgres time column would drag zone semantics back into a model D10 deliberately keeps zone-free.

3.3 The rules lib/habits owns

ConceptRule
Applicable day A date d is applicable to a habit when d ≥ started_on, archived_at is null or d precedes it, and isoWeekday(d) ∈ active_days. Non-applicable days are never scored and never appear in any denominator.
met Entered directly, or derived from value against metric.target via the comparator and frozen at write time (D11).
missed An explicit, logged failure. The only thing that counts against you.
skipped Transparent by design — a legitimately excused day (illness, travel). Neither extends nor breaks a streak; excluded from the hit rate entirely. This is how a day gets excused after the fact, since active_days is a fixed rule.
unknown No row (D5). Ends the current streak; excluded from both sides of the hit rate.
Current streak Walk backwards over applicable days counting consecutive met, stopping at the first missed or unknown, stepping transparently over skipped. Today is exempt: if today is applicable and unlogged, the walk starts at the previous applicable day — otherwise every streak would read 0 each morning until you logged.
Longest streak The maximum such run over the habit's whole history.
Hit rate met / (met + missed) over the requested window. Unknown and skipped days appear on neither side, so forgetting to log never depresses the rate (D5).

3.4 Frontend wiring

Habits follow the established data-flow architecture exactly (see the data-flow and frontend-architecture skills): a server-side lib/data/habits.ts fetch seeded once by the (shell) layout into a HabitsProvider optimistic store with reconcile/rollback and a toast on failure; the view reads from the store and never calls router.refresh().

One deviation from "fetch everything": the shell seeds a bounded window of entries (the last ~120 days) rather than all history. The existing eager-fetch tradeoff is accepted at hundreds of rows; a daily habit is a few hundred rows per habit per year and grows without bound, so the window is the point at which that tradeoff stops holding. Scrolling further back is an on-demand fetch, the same shape as pulling an older week's plan HTML.

4 · API surface

RouteAuthPurpose
GET /api/habits session or API key Definitions + entries in a window + derived stats (D8). Query: tz, from, to, include_archived.
POST /api/habits session Create a habit.
PATCH /api/habits/[id] session Rename, edit active_days / metric / notes, archive (set archived_at), reorder.
DELETE /api/habits/[id] session Hard delete, cascading entries. Archiving is the expected path; delete is for mistakes.
PUT /api/habits/[id]/entries session or API key Upsert one day (D7). Body: { date?, status?, value?, note? }. date omitted ⇒ today in tz. status omitted with a value on a metric habit ⇒ derived (D3, D11).

Errors use alfred's standard { "error": "…" } envelope. Auth follows the existing precedence rule the primer documents: a present x-api-key wins outright and an empty value is a mismatch, not an absent header.

6 · Constraints & non-goals

Deliberately outWhy / what to do instead
Reusing items No item_type = 'habit', no recurrence-engine reuse, no habit rows in any task view, store, count or search path (D1). A story that finds itself reaching into items has taken a wrong turn.
N-times-per-week quotas "Gym 3× a week" is a per-week bar, not a chain (D4). Revisit only if a real habit demands it — it is a second visualization, not a field.
Quarters, rollover, renewal No quarter entity of any kind (D6). Date ranges express everything needed.
Reminders & notifications A 6 AM nudge is the obvious next thought and is out of this epic. The channel decision is already made and documented in docs/notifications-spike.md (Telegram bot from the existing Worker) — it becomes its own epic that can consume the habits API, not a story here.
Automatic data capture No Apple Health / sleep-tracker / calendar ingestion. Entries are typed by a human or written by the coach through the keyed endpoint (D7).
Gamification No points, badges, levels, or freeze tokens. The streak number and the chain are the reward.
Editing history semantics beyond backfill Backfilling and correcting a day are in scope; retroactive re-scoring when a target changes is not (D11).
Habit folders / tags / grouping Manual sort_order only. At the expected volume (a handful of active habits) grouping is premature.
Multi-user anything Single-user, role-based RLS as everywhere else — authenticated full access, no user_id column (SPEC §7).

Constraints inherited from the repo

  • RLS + explicit grants are mandatory on both new tables (and any sequence) — omitting a grant produces a "permission denied" the Data API surfaces at runtime, which is exactly what migration-lint exists to catch at commit time.
  • Every behavioral change lands with a test (unit, Storybook, or E2E) and a demo doc under docs/demos/<branch>/ per the showboat skill. The streak rules in §3.3 are pure functions and should be near-exhaustively unit-tested — they are the epic's highest-risk logic and its cheapest to cover.
  • The API key's blast radius widens with D7/D8: it currently writes the plan archive and reads the PR ratio; after this epic it also reads and writes habit data. Worth stating plainly in the primer when the endpoints are documented.
  • Visual work must respect prefers-reduced-motion and the dark-canvas contrast floor (SPEC §5.4); habit cells are small, so the met/missed/unknown/n-a distinction has to survive a colour-blind reader — shape or border, not hue alone.

8 · Open questions

  1. The §5 selections. The one intentionally-open decision. Paste the metadata block back and it becomes settled context recorded in this file.
  2. Does the coach get a writeback ritual, or only ad-hoc logging? D7 gives it the ability to write an entry. Whether the Friday review should routinely reconcile the week ("you told me Tuesday was a 6:40 — want me to log it?") is a coach-skill design question, not an alfred one, and can be answered after the endpoint exists.
  3. Is skipped enough of an escape hatch, or will a vacation want a date-range pause on the habit itself? Deferred deliberately — one skipped entry per day is workable for a week away, and a paused_from/paused_to pair is a cheap additive change if it turns out not to be.
