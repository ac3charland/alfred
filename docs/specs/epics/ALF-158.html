ALF-158 — LLM processing

Epic spec Durable context for the epic. Read this before refining any story inside it.

The one-line shape. A small model reads each item as it lands in the Inbox and fills in the labels that are manual today — task or code, priority, a due date if the text states one, a folder for a task, a project and epic for code. The guesses are written straight onto the item's real fields and wait in the Inbox, unmarked. The owner scans, overwrites anything wrong, multi-selects, and dispatches. The machine never routes anything; it only pre-fills — and every override the owner makes is remembered and fed back, so the next batch guesses a little better.

1 · Problem space & why now

SPEC.md has planned for this from the start. §2 names Cloudflare Workers as the home for "LLM pre/post-processing", §4.2 sketches an LLM cleanup layer in front of capture, §6 says POST /api/items is "the seam where the future LLM capture-processing Worker slots in", and §11 Phase 6 is literally (Future) LLM processing layer. This epic is that phase — narrowed to the highest-value slice.

The system is capture-first by design: an item lands with a title and nothing else, and the owner is never ambushed with triage at capture time. That is the right trade, and it works — but it pushes 100% of the classification cost into a later sitting. Every Inbox item currently needs the owner to decide, by hand, up to five things that are usually obvious from the text itself:

FieldSet today by
item_typethe bulk bar's Classify, a row menu, or the ALF: capture prefix
priorityPrioritySelect, by hand, per item
due_datethe calendar popover, by hand — even when the title says "friday"
folder_idbulk Move, drag-to-folder, or a row menu
project / epic (code)the ALF: prefix for the project; the epic only at the gate dialog

Most of these are not judgement calls. "Call the dentist friday" is a high-signal string: it is a task, it has a date, and if there is a Health folder it belongs there. The owner is doing work a small model does well and does instantly. Meanwhile the multi-select machinery to act on a batch already exists — InboxBulkBar ships Classify / Move / Send-to-Code over a selection. The missing half is that the items arrive blank, so a "batch" is still five decisions per row.

Why now: the Inbox is the one surface where the owner still pays a per-item tax, the destination surfaces it feeds (folders, the priority view, the code factory) are all built, and the Worker package already exists with a deployed entrypoint and a Supabase service-role write path. There is nothing left to build around this.

What this epic builds on

Three pieces of existing behaviour are load-bearing, and each is precedent for a decision below.

  • The ALF: capture prefix (lib/code/project-prefix.ts, ALF-62). A capture starting with a known project key or name is classified code, has intended_project_id set, and stays in the Inbox. A deterministic pre-classifier writing straight to the real fields already exists and is already trusted; this epic generalises it, it does not invent it.
  • Filing already classifies (moveTask, ALF-72). Dropping an unclassified item into a folder flips it to task in the same mutation, because "folders hold tasks" and a bare move would strand it. Coupled multi-field writes are the house pattern.
  • The task_items view excludes only items that have a code_items sidecar. Its own comment says it covers "code-classified-but-not-yet-sent items" — the Inbox is already a place where a classified item waits.

2 · Decisions

D1, D2, D4, D5, D9 were settled with the owner in this session. The rest follow from those plus what the repo already does. Each carries its rationale so a story session doesn't re-litigate it.

Provider & model

D1The Anthropic API with a pay-as-you-go key — not the Claude subscription, not a self-hosted OSS model

The Worker calls POST /v1/messages with an ANTHROPIC_API_KEY held as a Worker secret (wrangler secret put), alongside the secrets already declared in wrangler.toml.

Why not the subscription + claude -p: two independent blockers. Mechanically, -p runs the Claude Code CLI — a Node process with a filesystem and an OAuth credential on disk. A Worker is a V8 isolate: no subprocess, no filesystem, no way to invoke a CLI. And separately, a Pro/Max subscription credential is for using Claude Code, not a substitute API credential for a hosted service. There is no version of this that works from inside a Worker.
Why not a cheaper open-source model: the cost this would save is real but tiny (D2), and a second provider costs a second key, a second SDK, a second failure mode, and — the part that actually matters — a materially weaker guarantee on constrained JSON and on picking correctly from a closed list. A wrong-but-plausible folder is the expensive failure here, because it gets rubber-stamped in review. Re-open if monthly spend ever exceeds ~$25, which at these rates means volume has grown ~20×.

D2Claude Haiku 4.5 by default; the model id is a Worker var, not a constant

Default claude-haiku-4-5, injected as a [vars] entry so it can be changed at deploy without a code change. Escalation path is claude-sonnet-5.

ModelRatePer item (~1.5k in / ~100 out)Per month @ 20/day
claude-haiku-4-5$1 / $5 per MTok~$0.002~$1.20
claude-sonnet-5$3 / $15 ($2 / $10 intro to 2026-08-31)~$0.006~$3.60
claude-opus-5$5 / $25 per MTok~$0.010~$6.00

Why: at this volume every option is inside noise, so the choice is decided by fit, not price — and Haiku 4.5 supports structured outputs (D3), which is the property that matters. Making the id a var rather than a constant means "try Sonnet for a week" is a deploy flag, not a story.
Two facts worth not rediscovering: Haiku 4.5's prompt-cache minimum is 4096 tokens, so a compact classify prompt will silently never cache — do not build a caching story around it and do not read cache_read_input_tokens: 0 as a bug. Haiku 4.5 also does not accept the effort parameter; classification needs no thinking, so this costs nothing, but a copied-in output_config.effort will error.

D3Constrain the values in the schema, re-validate in code, let the database have the last word

Three layers, deliberately redundant:

  1. The schema carries the ids. output_config.format is assembled per sweep with the live folder / project / epic ids as enum values, not merely typed as strings. Structured outputs constrain generation, so an id that isn't on the list is not something the model can emit — a hallucinated folder becomes impossible rather than caught.
  2. The Worker re-validates anyway. Every id is rechecked against the sets that were sent, plus cross-field coherence (a code verdict carrying a due date, a task verdict carrying a project). Anything failing drops to null.
  3. The database rejects whatever survives. The foreign keys and the CHECK constraints of D7 will fail the write rather than store an incoherent row.

Why layer 2 when layer 1 exists: the enum closes the value space at generation time but not the time gap — a folder can be deleted between prompt assembly and write-back, and only the validation step notices. It is also where cross-field rules live, which an enum can't express cleanly, and it is pure and deterministic, so it is the natural unit-test seam (D12).
Why not just prompt for it: "only choose from this list" is a request, not a constraint. Layer 1 is the same instruction expressed somewhere it is actually enforced.
The cost of a per-request schema: a new schema pays a one-time compilation cost and then caches for 24 hours. The id lists change only when a folder, project or epic is created, so in practice the schema is stable for days and recompiles on the rare change — not a reason to hand the model a free-text field.

The write-through model — the heart of this epic

D4Guesses are written to the item's real fields, with no "suggested" marking

There is no suggestion sidecar, no confidence badge, no ghosted styling, no accept/reject affordance. The classifier writes item_type, priority, due_date, folder_id, intended_project_id exactly as a human edit would, and a machine-set chip is visually indistinguishable from one the owner set. The owner overwrites what they disagree with, using the editing controls already on the row.

Why (owner's call, and it holds up): the point of the epic is that the labels are waiting when you get there. A "suggested" state creates a second thing to do — approve — on top of the thing you actually wanted, which is to glance and move on. It also doubles every read path in the app: every store, selector, filter, count and view would need to know about proposed-vs-real. The repo already write-throughs a machine guess in exactly this way (the ALF: prefix), and nobody has wanted a badge for it.
What this costs: the interface can no longer tell a guess from a decision, so if the guess is ever to be learned from it has to be recorded somewhere invisible — which is exactly what D15 does. Accepted, because the risk that remains — a confident wrong label that gets rubber-stamped — is attacked by abstention (D8) rather than by badging.

D5The Inbox stops meaning "no folder" and starts meaning "not yet dispatched"

Today Inbox membership is computed client-side as item.folder_id === null (lib/stores/tasks-store.tsx), and a folder view is item.folder_id === folderId. This epic introduces an explicit residency marker on items — a nullable dispatched_at timestamptz, null meaning still in the Inbox — and every Inbox / folder / count query reads it instead of inferring residency from folder_id.

  • Inbox = dispatched_at is null (top-level items), whatever folder_id holds.
  • Folder view = folder_id = X and dispatched_at is not null.
  • Folder attention / overdue badges must adopt the same dispatched_at guard, or an undispatched item with a pre-filled folder will inflate that folder's counts from inside the Inbox.
  • Backfill: every existing item with a non-null folder_id gets a non-null dispatched_at; everything else stays null. No item changes view.

Why this is unavoidable: it is the direct consequence of D4. The moment the classifier can write folder_id, the current rule files the item away — it disappears from the Inbox into a folder before the owner has ever seen the guess. That is the exact opposite of "waiting for me to look at". Residency and location have to become two different facts.
Why a timestamp rather than a boolean: matches the repo's existing idiom (completed_at, archived_at, ref conventions) and records when triage happened, which is free and occasionally useful.

D6Dispatch is a human action. The classifier never sets dispatched_at.

Only an explicit human act leaves the Inbox: the bulk bar's Move / Send-to-Code, a drag onto a folder, a row-menu file, or entering the code factory via the gate. The classifier writes labels and stops.

Why: this is the invariant that makes D4 safe to live with. Because the machine cannot move anything anywhere, the worst a bad guess can do is show you a wrong chip on a row you are already looking at. Nothing is silently routed, nothing goes missing, and there is no "where did that go?" failure mode. Every story in this epic should be checked against it.

D7One coherent write per item — item_type and its type-specific fields go together

The classifier applies all of an item's guesses in a single UPDATE, never field-by-field.

Why — the database will reject anything else. items_task_only_fields (last redefined in 0019_code_epics.sql) requires due_date is null unless item_type = 'task', and items_intended_project_code_only (0013_intended_project.sql) requires item_type = 'code' for intended_project_id. Writing a due date before the type flips violates the CHECK and fails the row. This isn't a style preference; it is the schema.

D8Abstention is a first-class answer — every field may come back null

The schema makes every field nullable and the prompt makes abstaining explicitly correct:

  • due_date — only when the text actually states a date or a day. Never inferred from urgency.
  • folder_id — only when one existing folder is a clear fit. Never invent a folder.
  • priority — only when the text signals it. No default guess.
  • item_type — may stay unclassified, which is simply the item behaving as it does today.
  • project / epic — only from the sets supplied. Never invent either.

Why: given D4, the cost of the two error modes is wildly asymmetric. A blank field is a field the owner was going to fill anyway — zero regression. A confident wrong label is worse than nothing, because a row that looks done gets skimmed past and dispatched. Optimise the prompt and the schema for precision, and accept low recall; the fallback for a blank is the status quo, and the status quo is fine.

How and when it runs

D9A scheduled Worker sweeps; capture is never coupled to the model

A cron trigger (order of every 1–2 minutes) fires a scheduled handler in the existing workers/ package. It selects undispatched, not-yet-classified Inbox items, classifies them, and writes back with the service-role key it already holds. wrangler.toml gains a [triggers] crons block — it has none today — and src/index.ts gains a scheduled export beside its existing fetch.

Why a sweeper rather than firing from the capture route: one code path covers every ingress that exists or will exist — the in-app box, the Siri shortcut, anything later — instead of each one having to remember to trigger it. Retry is free: a failed item is simply still unclassified on the next tick, with no queue, no dead-letter, and no bespoke retry code. And capture stays structurally incapable of being slowed down or broken by the model, which is the SPEC's first guiding principle rather than an implementation detail.
Why the latency is fine: the entire premise is capture-now-refine-later. Nobody is watching a row waiting for a chip to appear.

D10A processed marker — the sweeper is idempotent and never re-guesses over you

items gains a marker recording that the classifier has run (classified_at, plus enough provenance to tell which prompt/model version produced it — and, per D15, the verdict itself). Re-classification is possible but always explicit — a manual action, never automatic — and reads from raw_capture, which SPEC §3.2 preserves for exactly this.

The sweep predicate is roughly parent_id is null and dispatched_at is null and classified_at is null, which carries three consequences worth stating outright:

  • No eligible rows means no API call at all. The tick costs one database query and nothing else. A steady state where everything is triaged is a steady state where the model is never invoked.
  • Eligibility is classified_at is null, not item_type = 'unclassified'. These come apart precisely on abstentions: an item the model declined to judge (D8) keeps item_type = 'unclassified' but is marked, so it is never swept again. Keying on the type instead would re-ask the same question about the same text forever, burning budget on exactly the items already known to be unjudgeable.
  • An item may arrive already partly populated, and the classifier fills gaps rather than overwriting. The ALF: prefix (live today) creates an item with item_type = 'code' and a project already set but no classified_at — so it is eligible, and should usefully gain an epic or priority guess. A field that already holds a value was set by a human and is not the classifier's to change.

Why: without a marker the sweeper re-runs on every tick, burning budget and — far worse — silently overwriting an edit the owner just made. "The machine changed my answer back" would end trust in the feature immediately. The version stamp is what makes a future prompt change safely replayable over old captures.

D11Suggesting an epic requires a pre-factory epic hint, mirroring intended_project_id

Projects already have a pre-factory home on items: intended_project_id (ALF-62) — nullable, on delete set null, CHECK-gated to item_type = 'code'. Epics have no equivalent; the epic is chosen only in the gate dialog at send time. Suggesting one means adding intended_epic_id with the same shape, and having GateDialog pre-select it.

Why record this here: "suggest the epic too" reads like the same size of change as "suggest the project", and it isn't — it is a migration, a constraint, a view recreation (see the 0013 note: task_items freezes its column list at CREATE time and must be recreated when a column is added to items), a store field, and a gate-dialog change. It deserves its own story, and a story session that assumes parity with the project hint will be surprised.

Quality, safety, cost

D12The model's judgement is not a back-pressure gate; everything around it is

Draw the line at the model boundary:

  • Deterministic, and therefore gated — prompt assembly from live folder/project/epic lists; response-schema validation; the closed-world id check (D3); the coherent write (D7); the sweep query and its marker (D10); the Inbox residency rule and every count that reads it (D5); the dispatch-time diff and the example-block assembly (D15, D16); every failure path (D13). All tested against a stubbed model response.
  • Non-deterministic, and therefore not gated — whether the model picks the right folder. Measured by a separate fixture set of real captures with expected labels, run on demand.

Why: CLAUDE.md's rule is that every behaviour change touches at least one test, and the obvious-but-wrong reading of that is to put a live API call in the suite. That would make check:fast flaky, slow, network-dependent, and billable on every commit — and the guardrails would lose their teeth within a week. Naming the boundary once, here, stops each story session from re-deriving it and reaching a different answer.

D13Degrade per field, retry only transport — and there is no conversational repair loop

Each classification is one stateless request. The Worker never opens a second turn to tell the model it got something wrong, never sends an error message back for another attempt, and never holds a conversation. What happens instead depends on what failed:

What went wrongWhat the Worker does
An id fails validation — deleted between prompt and write-back (D3 layer 2) That field drops to null. The rest of the verdict is written and the item is marked classified. No retry.
Cross-field incoherence — a code verdict carrying a due date The offending field is dropped, the coherent core is written. No retry.
stop_reason: "max_tokens" — response truncated mid-JSON Nothing written, item left unmarked, next tick retries. Genuinely a config bug rather than model behaviour: the verdict is ~100 tokens, so max_tokens should be set with room to spare and this should never fire.
stop_reason: "refusal" Nothing written; the attempt is counted. Re-sending the same prompt will not help, so it burns an attempt rather than looping.
429 / 5xx / timeout / network Nothing written, unmarked, next tick. Transient blips are absorbed by the SDK's own retry inside the request.
Attempt or budget ceiling reached The item is marked attempted and left alone — it goes on being an ordinary unclassified Inbox item, forever if need be.

Why no repair loop: the error a repair loop exists to fix is precisely the one D3's first layer designs out — you cannot usefully say "that folder doesn't exist, try again" about an id the model was never able to emit. And for everything else, abstention is already the right answer (D8): a dropped field yields a blank the owner fills in, which this epic already treats as a perfectly good outcome. A repair turn would spend a second call, more latency and a retry budget to convert that blank into a guess — moving in the exact opposite direction from the precision D8 optimises for.
Why transport failures need no code either: D9's sweeper already retries them for free. An item that failed is simply still unclassified on the next tick. That is the entire retry mechanism — no queue, no backoff state, no dead-letter, nothing to test beyond the attempt counter.
What this buys: cost stays flatly predictable at one call per item per attempt, with no path where a bad response multiplies spend. And the worst case is the status quo — the feature is strictly additive, so nothing here may block a capture, drop an item, or leave one in a state the UI can't render.

D14The key lives only in the Worker; captures leave the box, and that is a deliberate choice

ANTHROPIC_API_KEY is a Worker secret. It never reaches the browser, a Vercel env var, or the Next.js layer — the frontend has no LLM code path at all. The Worker reads and writes Supabase with the service-role key it already holds.

Why say it out loud: captures are the owner's unfiltered personal thoughts, and this epic sends every one of them to a third-party API. That is an accepted trade for a single-user system, but it is a new property of the app and should be a recorded decision rather than something rediscovered later. It is also the reason the capture path stays clean: adding an LLM call to POST /api/items would put the key one refactor away from the client bundle.

Learning from corrections

D15Every override is recorded — the diff is taken at dispatch, and it is never shown in the UI

The classifier stores its own verdict as an invisible snapshot on the item alongside classified_at (D10). At dispatch — the one unambiguous "these labels are final" event (D6) — the snapshot is diffed against the fields as they now stand, and each disagreement is appended to a classification_corrections log: the captured text, which field, what was guessed, what the owner actually chose.

  • All three directions count as corrections — the owner changed a value, filled in one the model left null (it could have known), or blanked one the model filled (it should have abstained). The third is the most valuable, because precision is what D8 is optimising for.
  • The captured text is copied into the log (denormalised), not referenced by id. A correction is a historical fact — this text, at that moment, got that label — so the copy has to be frozen. Referencing would lose the text when the item is deleted, and would pair the current title with a label chosen for the old one when the item is edited, silently corrupting the example.
  • Nothing about this is rendered. D4 is unchanged: no badge, no "corrected" state, no diff view. This is a write-only substrate.

Why at dispatch rather than on every edit: an edit mid-triage may itself be revised twice before you're done, and logging each keystroke's worth of intent would teach the model your hesitation rather than your conclusion. Dispatch is already the commit point in this design, it already exists as a distinct action, and it fires exactly once per item.
Why a separate table rather than columns on items: different cardinality (several corrections per item), different lifetime (outlives the item), append-only, and read by exactly one consumer. The same reasoning that kept habit_entries off items in ALF-146.
What this buys: it turns the one genuine weakness of D4 into an asset. Because the guesses live in the real fields, correcting one is just using the app — there's no separate feedback gesture to remember, no thumbs-down button to ignore. The signal is collected for free from work the owner was going to do anyway.

D16Corrections feed back as few-shot examples in the prompt — nothing more clever than that

Each sweep reads the most recent N corrections and injects them into the classify prompt as worked examples: this text → the label the owner actually chose. Bounded by count, ordered by recency, and filtered through the same closed world as the output (D3) so a correction naming a since-deleted folder is dropped rather than taught.

Why this and not something smarter: it is the whole loop in one deterministic step — no fine-tuning, no embedding store, no separate review surface, no second model call, and no human in the loop. Prompt assembly is already a tested seam (D12), so an example block is a change of input, not of architecture. It also degrades gracefully: an empty log is just today's prompt.
What it costs: input tokens per item. Twenty examples at ~40 tokens each is roughly +800 on a ~1.5k prompt — call it +50% input, which on D2's numbers is under a dollar a month. A side effect worth knowing rather than chasing: a large enough example block could push the prompt past Haiku 4.5's 4096-token cache floor and start caching, which would claw most of that back.
The trap to avoid: examples must not be allowed to teach away abstention. A log dominated by "you left this blank and I filled it in" nudges the model toward guessing more, which is the failure D8 exists to prevent. Whatever selection rule story H lands on needs to keep blanking corrections represented, not drown them.

Distilling corrections into durable rules is a later epic, not this one. The obvious next move — compact the log into standing instructions ("anything mentioning the dentist goes in Health") and keep them in a prompt document or skill — needs judgement, probably its own model call, a review surface so bad rules can be retired, and an answer for how a rule and an example disagree. That is a body of work. This epic builds the substrate that makes it possible and stops at recency-ordered examples.

3 · Architecture

The capture path is untouched. Everything this epic adds hangs off the cron trigger, and the only thing it does to an item is fill in fields. The loop on the right is the learning half: dispatching records what you overrode, and the next sweep reads it back as examples.

Data model additions

Column on itemsShapePurpose
dispatched_at timestamptz, null Inbox residency (D5). Null = in the Inbox regardless of folder_id. Set only by a human dispatch (D6). Backfilled non-null for every item that currently has a folder.
classified_at (+ version/provenance) timestamptz, null The sweeper's idempotency marker (D10). Null = not yet attempted. The exact provenance columns are a story-level call.
intended_epic_id uuid → epics(id), on delete set null, CHECK code-only Pre-factory epic hint (D11), mirroring intended_project_id. Only needed by the epic-suggestion story.
classified_guess jsonb, null The classifier's own verdict, kept so the dispatch-time diff has something to compare against (D15). Never read by the UI.

Plus one new table, classification_corrections — append-only, one row per corrected field: the denormalised captured text, the field, the guessed value, the chosen value, the model/prompt version, and a nullable item_id (on delete set null) so a lesson survives its item. Like every other table it needs enable row level security plus the authenticated full access policy and explicit grants — the Worker writes it with the service-role key, which bypasses RLS by design (SPEC §7).

Migration gotcha, already paid for once. task_items is select i.* from items i …, and a view freezes its column list at CREATE time — a column added to items afterwards never appears in the view until it is recreated. 0013 hit this and documents the fix: create or replace view in the same migration (no drop, so grants and security_invoker survive). Every migration in this epic that adds an items column must do the same, or the frontend will read the row and find the field missing.

What the model is asked for

One call per item. Input: the item's title, notes, raw_capture, and source_url; the current folder list; the current project list; the current epic list; a reference date; and the recent-corrections example block (D16). Output, schema-constrained, every field nullable: 

{
  "item_type":            "task" | "code" | null,
  "priority":             "high" | "medium" | "low" | null,   // task only
  "due_date":             "YYYY-MM-DD" | null,                // task only, only if stated
  "folder_id":            enum(<live folder ids>)  | null,     // task only
  "intended_project_id":  enum(<live project ids>) | null,     // code only
  "intended_epic_id":     enum(<live epic ids>)    | null      // code only
}

The three id fields are enums of the actual ids, rebuilt each sweep — that is D3's first layer, and it is why an invented folder isn't a case the Worker has to handle. null for item_type means "leave it unclassified", not an error. The shape mirrors the CHECK constraints deliberately: a code verdict can never carry a due date, so the coherent write in D7 is always legal.

5 · Constraints & non-goals

Hard constraints

  • Capture is never blocked, slowed, or made failable by anything in this epic. POST /api/items gains no LLM call and no new dependency.
  • The machine never dispatches. No item leaves the Inbox without a human act (D6).
  • The machine never creates. No new folders, projects, or epics — it selects from what exists or abstains (D8).
  • No live model call in check:fast or check:slow (D12).
  • The API key never leaves the Worker (D14).
  • Worst case equals today. Any failure leaves an ordinary unclassified Inbox item (D13).

Deliberately out of scope — do not pull these in

  • Rewriting captured text. No de-rambling of voice input, no title tidying, no summarising. Titles and notes stay byte-for-byte as captured. SPEC §4.2 anticipates a cleanup layer and raw_capture is preserved for it, but it edits content rather than metadata, needs its own undo story and its own accuracy bar, and belongs in its own epic.
  • Suggesting subtasks or structure. No proposing a breakdown of a capture into children.
  • Recurrence. The recurrence engine is not driven from captured text here.
  • Anything about knowledge items. That destination type does not exist yet; the model must never return it.
  • Any other LLM feature in the SPEC §13 roadmap — the Reader digest, the Communication Firewall, refinement generation inside the factory. This epic is Inbox triage only, even though it stands up the first Worker→LLM path they will all reuse.
  • Chat, or any conversational surface. One call, one item, no turns.
  • Distilling corrections into standing rules. D16 stops at recency-ordered examples. Compacting the log into durable instructions in a prompt document or skill — and the review surface, conflict resolution and extra model call that needs — is a later epic built on this one's substrate.
  • Any UI for the correction log. No diff view, no "the model got this wrong" affordance, no accuracy dashboard. D15 is write-only by design.
  • Retro-classifying the existing backlog. The sweeper takes new captures. A one-off backfill over historical items is a separate decision with a separate cost.

6 · How the work splits into stories

A sketch of the slices and why they cut where they do — not specs. Each is refined in its own session. The ordering matters: A is the enabling change and has no LLM in it at all, so it can ship and be lived with before a single token is spent.

#SliceWhy it's its own story
A Inbox residency — dispatched_at, migration + backfill, store selectors, folder counts, dispatch actions The load-bearing change (D5), and entirely independent of the model. Touches the store, every task view, the folder badges, and the E2E suite. Shipping it alone means the risky part is proven before anything non-deterministic exists.
B Editing parity on the Inbox row — every field the classifier will write is editable in place from the Inbox D4 only works if overwriting is as cheap as glancing. Some of these controls exist on Inbox rows today and some may not; the audit and the gaps are one story. Also the natural home for reworking the bulk bar's now-inverted enablement gates.
C The sweeper skeleton — cron trigger, scheduled handler, sweep query, classified_at marker, service-role write, no model call Proves the whole loop end to end with a deterministic stand-in (e.g. reuse the ALF: prefix rule as the "classifier"). First cron in the repo, so it carries the wrangler and deploy learning on its own.
D The Anthropic call — prompt assembly, the enum'd output schema, re-validation, the coherent write, and the per-failure degradation table The actual model integration. Lands behind everything above, so its blast radius is one swapped function. Note D13 leaves it with no retry code of its own beyond an attempt counter — the sweeper is the retry.
E intended_epic_id + gate pre-selection A migration, a constraint, a view recreation, a store field and a dialog change (D11) — genuinely not the same size as the project hint it resembles.
F Evaluation fixtures + an on-demand accuracy run The non-gating half of D12. Needs real captures with expected labels, and is what makes "try Sonnet for a week" a measurable experiment rather than a vibe.
G Manual re-classify from raw_capture The escape hatch once a prompt improves, and the reason D10 stamps a version. Small.
H The correction loop — classified_guess, the dispatch-time diff, the classification_corrections table, and the few-shot block in the prompt D15 + D16. Depends on A for the dispatch hook and D for a prompt to inject into, so it lands late — but it is the slice that makes the feature improve rather than plateau, and story F's fixtures are how you tell whether it did. The selection rule (how many examples, how to keep blanking corrections represented) is the interesting decision inside it.

A → B are shippable and useful with no LLM in the repo at all. C → D is the feature. E, F, G, H are independent of each other and can be ordered by appetite.

7 · Open questions

  1. Reference timezone for date parsing. "Friday" resolves against a wall clock the Worker doesn't have. The architecture is settled — an IANA zone as a [vars] entry in wrangler.toml — but the value needs the owner's answer, and story D can't land without it.
  2. Does editing an item without dispatching it make it permanently yours? Proposed: yes — any human touch marks it and the sweeper never revisits. The alternative (re-run when the title changes) is defensible for a capture you deliberately rewrote, but it reintroduces the "the machine changed my answer back" failure D10 exists to prevent. Worth confirming before story C fixes the sweep predicate.
  3. Is a spend ceiling worth building? At ~$1–2/month the volume is self-limiting and a budget guard is arguably ceremony. But a bug that loops the sweeper has no natural brake. Cheapest honest answer is probably a hard per-sweep item cap rather than a dollar meter — decide in story C.
  4. Which corrections earn their tokens as examples? D15 records the whole diff, including the fields the owner left alone. Feeding every correction is the obvious v1, but the prompt budget is the scarce thing and the mix matters: examples are also the mechanism by which the model could be taught to guess more and abstain less (D16's trap). Open: recency alone, or recency balanced across fields and across the change / fill-in / blank directions? Confirmations almost certainly aren't worth their tokens, but that's an assumption, not a measurement — story F's fixtures are what would settle it. Decide in story H.
  5. Does the correction log ever forget? A lesson from a year ago about a folder you barely use is still in the table competing for a slot, and a habit you've since changed your mind about is worse than no example at all. Recency ordering handles this implicitly while the log is small and stops handling it once it isn't. No action needed now — but a story session that reaches for "just feed the whole table" should know this is why it won't stay fine.
