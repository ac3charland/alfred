ALF-259 — Wiki Module

Epic spec The shared context for the wiki epic: what the wiki is, how primary sources are shaped and how new kinds get added, how something moves from Alfred into the wiki, and what starts an ingest session. The Day 1 and Day 2 refinement sessions read this before writing their own specs.

First refinement, 2026-09-24. Built on the spike docs/spikes/llm-wiki-spike.html. The spike's overall shape is kept: a private git repo of markdown, written by a Claude session, fed by Alfred, and read in Alfred. Where this spec settles something differently from the spike, the decision is tagged changes spike and this document wins. Decisions this session added are tagged new.

One-paragraph version. The wiki is Karpathy's LLM-wiki pattern: a private GitHub repo of plain markdown that a Claude session keeps compiling from the sources Alex chooses to send it. Every source is one folder. Today a folder can hold the frozen original text, Alex's own notes, and the summary bullets Alex picked, but the set of files is open by design: a new kind of file, like a new kind of source, only needs a registry row. The folder's contract doesn't care where the source came from. Alfred feeds the wiki by committing those folders into the wiki repo's inbox/: bullets picked in the Reader's "Novel ideas" section, and captured ideas the classifier marks as knowledge. Book notes come from a script on the Mac that converts Alex's Obsidian notes into the same folders. A push that touches inbox/ starts a Claude Code Routine. The Routine takes everything in the inbox at that moment as one batch following a committed ingest skill and opens a PR, and Alex merging the PR is the review. Day 2 also gives Alfred a read-only reading room and puts wiki pages in its global search.

1. Problem space & why now

Alex reads a lot, through the Reader, Instapaper, and books, and has ideas worth keeping. Today none of it compounds. A Reader post's text is swept after 90 days, Instapaper highlights sit in Instapaper, book notes sit in Obsidian, and a captured idea is just an inbox item. Asking Claude about any of it means rediscovering it from scratch each time, which is RAG's failure mode. The LLM-wiki pattern fixes this by having a model compile sources into an interlinked set of pages once, then keep those pages current.

Why now: the Reader already does the expensive part, reading every newsletter and extracting its novel ideas. That compute currently expires with the post. Sending Alex's picks from it into a wiki turns a disposable summary into lasting knowledge. The spike settled the high-level shape; this epic settles primary sources and the ingestion workflow, which the spike left thin.

3. Architecture

Solid lines are the automatic path; dashed lines are Alex, a re-trigger, or Alfred's read path. Git is the only queue.

What the architecture commits to:

  • Git is the queue, the store, and the audit log. Nothing about the wiki lives in Supabase. A write that fails or a run that gets rejected leaves its folder sitting in inbox/, and nothing is lost.
  • Alfred is a producer and, eventually, a reader, never a writer of wiki pages. The only thing Alfred writes into the wiki repo is inbox/ folders. The model writes pages, and only through git.
  • Every way of running an ingest does the same job. A Routine, claude -p, and an interactive session all follow one committed ingest skill, so swapping the runner doesn't touch the wiki.

4. Decisions — primary sources

envelopeEvery source is one folder: the contract is fixed, the files inside it are open changes spike costly to reverse

Fixed (the contract): one folder per source; the path scheme below; every file in the folder carries frontmatter declaring its origin; the author's text is never edited. Open (by design): which files a folder holds. The kinds below are the ones this epic needs. A new kind (a transcript.md, an audio asset) is added the way a new source type is: one entry in the registry naming the file kind and its origin. Ingest, lint, and the reading room keep working unchanged.

A folder lands in inbox/; ingest moves it (git mv, contents unchanged) into raw/, sorted by year:

inbox/2026-09-24-why-habits-stick/            ← waiting
raw/2026/2026-09-24-why-habits-stick/         ← after ingest; permanent
    source.md               the author's words as markdown; body frozen   (optional)
    excerpts-2026-09-24.md  quotes Alex chose (books); frozen, one per send (optional)
    notes-2026-09-24.md     Alex's own words, one file per send           (optional)
    picks-2026-09-24.md     summary bullets Alex picked, model-worded     (optional)
    assets/                 original binary the text was extracted from   (optional)
    …                       any file kind the registry adds later

Every file is optional, but a folder must contain at least one of them. Different kinds of source use the same contract with different files:

  • Reader post: source.md (the post text) plus picks-… (the bullets Alex sent).
  • Book: excerpts-… (the quotes Alex chose, with their chapter) plus notes-… (his commentary on them), both accumulating as he reads. Never the book's full text (books).
  • Captured idea: a single notes-… file.
  • PDF: source.md holds the extracted text; the PDF itself goes in assets/.

Every file carries YAML frontmatter with a small fixed core: source_type, origin, title, author, source_url, published, captured, via, external_id. Every file holding the author's words (source.md, excerpts-…) also carries fidelity (see fidelity). origin is one of:

  • third-party: someone else's words
  • mine: Alex's words
  • model-derived: the model's words, picked by Alex

Why a folder: the author's words, Alex's words, and the model's words have different provenance. That matters for trust (a pick can misquote), for licensing (a paid Substack post), and for any later public export. Separate files let a wiki page cite exactly the kind of material it used. A folder also gives notes that grow over time (a book read across six weeks) somewhere to accumulate.
Why costly to reverse: every wiki page's sources: list points at these paths. Changing the scheme later means rewriting citations across the whole tree, the same class of cost as the spike's link-syntax rule.

immutabilityOnly the body is frozen; frontmatter can be amended by script, and a source can keep growing new

  • The body of source.md is never edited. It is the record of what Alex read. Frontmatter may be amended by scripts (a backfilled field, a later sensitivity label), never by the model's judgment.
  • Identity is external_id, or the canonical URL when there is no id. A later send for a source that's already filed arrives as an inbox/ folder holding only the new files (say, one more picks-…). Ingest merges those files into the existing raw/ folder and never creates a duplicate.
  • A materially revised source is a new capture, whose frontmatter names the earlier folder with supersedes: <path>.

Why: the spike's "raw is write-once" rule conflicts with its own script setting sensitivity on raw files. Scoping "write-once" to the body resolves that, and it is also what lets a source type add fields later without breaking the rule.

fidelityA fidelity field records how much of the source was captured new

fidelityMeaningTypical case
full-textThe whole source, converted to markdownReader post, web article, extracted PDF
excerptVerbatim highlights onlyBook quotes; Instapaper / Kindle highlights
pointerMetadata and a URL only; the ingest session should try to fetch itA Reader post whose text has already been swept; a bare link
notes-onlyNo author's text at all; only Alex's wordsCaptured ideas

Given a pointer, the ingest session tries to fetch the text and upgrades the folder to full-text. If it can't (a paywall, a network block), it leaves the folder at pointer and says so in the PR.

Why: pointer is what keeps adding a source type cheap. A producer that only has a URL can still hand one off, and the hard part (fetching) happens in one place.

registryNew source types and new file kinds are registry rows; there's no denylist changes spike

A registry file in the wiki repo has two lists. Source types: each source_type with its highest allowed fidelity (books cap at excerpt), its default origin, and, once export exists, its default sensitivity. File kinds: each file name pattern a folder may hold (source.md, excerpts-*.md, notes-*.md, picks-*.md, assets/, …) with its origin and whether its body is frozen. Lint checks every folder against both. Adding a source type means writing a producer and adding a row; adding a file kind means adding a row. The ingest skill, lint, and reading room don't change.

Producers can live in three places:

Producer lives inSuitsIn this epicLater, for example
Alfred (it already holds the content)Things Alfred capturesReader picks; captured ideasNon-Reader newsletters; Instapaper tag sync (follow-up)
The ingest session (completes a pointer)Anything reachable by URLSwept Reader postsArticles, arXiv, transcripts
Alex's Mac (a script, or a dropped folder)Local files and exportsThe Obsidian book importer (books); Instapaper highlightsKindle / Readwise exports, PDFs

Why no denylist: Alex is the only builder and the only sender, and every source reaches the wiki through an explicit act of sending. A standing ban (the spike's "comms are never a source") would only be friction. Sending a message to the wiki is a deliberate choice to keep it, and it doesn't change the fact that Alfred's own copy of comms is still swept at 60 days.

Two things producers must do: split mixed provenance (Kindle quotes go in source.md at excerpt; Alex's comments go in notes-…), and never put an LLM summary in source.md. Model-written text only ever enters as picks.

barSending is the ingest bar; filing is not ingesting new

Nothing reaches the wiki automatically. A source enters only because Alex sent it, dispatched it, or dropped it in. There's no "ingest everything I saved". A producer may mark a folder ingest: file-only: ingest moves it into raw/ and logs it, but doesn't synthesize pages from it. Those pages get written later, when a question or a newer source touches it.

Why: this keeps the wiki about what was new to Alex (the spike's first anti-goal) while still letting bulk imports get archived without a synthesis session per item. Whether this valve is also the right way to batch Instapaper is open.

picksPicked bullets are model-derived, and ingest checks them against the source new

A picks-… file holds the "Novel ideas" bullets Alex chose, word for word, with origin: model-derived. The signal is that Alex found these insightful; the wording is the summarizer's. Before building on a pick, the ingest session checks it against source.md. A pick the source doesn't support gets flagged in the PR, not synthesized.

Why not origin: mine: a summarizer can misstate an article, and a paraphrase of a paid post is still derived from that post. Labelling the picks as Alex's own words would launder both problems. The source text sitting next to the picks is what makes the check cheap.

booksBook notes come in through a deterministic importer on the Mac, then auto-ingest changes spike

Alex's book notes live in his Obsidian vault in a regular format (the Brain Rules sample):

  • A book note tagged #book, with Author / Published / Read lines and a link to one note per quote.
  • A quote note per quote, named after the quote. Its body holds some of: a longer verbatim passage, a chapter locator (Ch. 3 - Stress), Alex's commentary, and links to other notes.

A book importer script in the wiki repo's scripts/, run on the Mac against the vault, turns one #book note into a folder and pushes it to inbox/. Auto-ingest takes it from there; Alex doesn't need to be in a session.

  • It splits provenance per quote. The quote and any longer passage go in excerpts-<date>.md (origin: third-party, frozen) under a stable id taken from the quote note's name, with the chapter locator. The commentary goes in notes-<date>.md (origin: mine) under the same id. Anything it can't classify, it flags rather than guesses.
  • It is incremental. It records which quote notes, and which versions of them, it has filed. Re-running it on a book still being read files only the new or changed quote notes, as new dated files in the same folder. That handles "a book note is a living document" without a model deciding what's new.
  • No model runs in the importer. Conversion is mechanical; synthesis is ingest's job.
  • The seed is the same importer run over every #book note. How it walks the vault and the exact splitting rules belong to the Day 1 spec.

Why a script, not a session: the format is regular enough to convert mechanically, and a script can tell what's new by quote-note identity, which a model can only approximate.
Why books can hold quotes: the spike's "his own notes, never the book text" assumed the notes were only Alex's words. The sample shows they are built from verbatim quotes. So books cap at excerpt (the quotes Alex chose, never the full text), and the quotes are labelled third-party so they never pass for his words.

crosslinksAlex's own links are kept as written, resolved by script, and treated by ingest as synthesis cues new

  • Kept as written. A link Alex wrote (Same as Chesterton! [[The Everlasting Man]]) stays in his notes file exactly as he wrote it. The relative-links-only rule (format) covers the wiki pages the model writes, not Alex's words in raw/.
  • Resolved in frontmatter. A script-maintained links: map in the notes file's frontmatter records where each link points (The Everlasting Man: raw/…/the-everlasting-man/). If the target isn't in the wiki yet, the map records the link as unresolved and the importer tags it in the body with a comment marker to address later. When the target arrives, a script fills in the map entry without editing the body (immutability). The map is the current truth, and lint lists whatever is still unresolved. The same treatment applies to a link to a note that isn't a book.
  • Treated as synthesis cues. Every link in Alex's notes is a connection he made himself, the most valuable thing in the folder. Ingest must reflect each one: the two sources' pages link to each other, and a concept page for the shared idea cites both, with Alex's remark as the reason.
  • Plain-text mentions are the model's job. "See Outlive" isn't a link. Ingest treats it like any mention in the text, and the importer doesn't try to resolve it.

Why: Alex wants his backlinks preserved and reflected in what the wiki writes. Rewriting them to relative paths at import time would break for any book imported before its target, because the body can't be edited later. Resolving them in script-owned frontmatter means the order of imports doesn't matter.

5. Decisions — the path into the wiki

handoffAlfred commits folders to inbox/ through the GitHub API changes spike

Alfred writes each envelope straight into the wiki repo's inbox/ on main, as a commit made through the GitHub Contents API. It uses a separate fine-grained token with Contents:write on the wiki repo only; the existing read-only GITHUB_TOKEN stays read-only. There's no Supabase queue and no keyed inbox endpoint.

Why: the queue then lives in git, with no sweep and no expiry, and it's visible as ls inbox/. Ingest sessions need no Alfred API key and no network route to Alfred, and they behave the same on the Mac and in the cloud. The commit is also the event that starts kickoff. The cost is a write token, kept to the smallest scope that works.

readerReader → wiki sends picked "Novel ideas" bullets, and the post text rides along changes spike

In a post's "Novel ideas" section (overview.novel_ideas), Alex can send a single bullet or all of them. A send produces an envelope containing:

  • source.md, built from reader_posts.text (fidelity: full-text), plus the post's metadata; and
  • a picks-… file with the chosen bullets.

Sending more bullets from the same post later adds only a new picks file (immutability). Once the 90-day sweep has nulled the text, a send still works: source.md becomes a pointer at canonical_url. Paywalled posts may fail to fetch at that point, and the PR will say so.

Why: Alex doesn't want the whole article dumped into the wiki. The summarizer has already done the work of finding what's new, and Alex's pick is the strongest signal of what mattered. The full text rides along so the picks can be checked and so later synthesis has the original to go back to.

How the picker looks (per-bullet affordance, "send all", sent state) belongs to the Day 2 spec, which draws it in the Reader's own design system. This spec only fixes the behavior.

ideasCaptured ideas: the classifier suggests knowledge, and Alex dispatches

The ALF-158 classifier gains knowledge as a third item_type (today it only picks task and code). The enum value has been reserved since 0001_initial_schema.sql. It's still only a suggestion. Dispatching a knowledge item from the Inbox commits a notes-only envelope (origin: mine) to inbox/ and takes the item out of Alfred. From then on the wiki is the record, consistent with ALF-7 D2: Alfred mirrors, it is never the store of record.

Why not auto-send: it would break bar. The click is the decision to keep something.

6. Decisions — ingest sessions

skillOne committed ingest skill guides every ingest new

The wiki repo carries an ingest skill (.claude/skills/ingest/SKILL.md, referenced from its CLAUDE.md). It is the step-by-step ingest procedure:

  1. Pull.
  2. Take the batch: the inbox/ folders at the lock branch's commit. Complete any pointers.
  3. Merge folders into existing raw/ folders by identity.
  4. Verify picks.
  5. Write and update pages.
  6. Update index.md and log.md.
  7. Lint.
  8. Commit, one commit per source.
  9. Push and open the PR, whose description lists the pages touched, flagged picks, failed fetches, and questions for Alex.

The Routine's saved prompt, a claude -p invocation, and an interactive session all just say "follow the ingest skill".

Why: the procedure is the part that will keep getting tuned, and it needs one home. With the procedure in the repo, changing runners never changes behavior, and improving ingest is an ordinary reviewed commit.

autonomyAutomatic sessions draft a PR; Alex's merge is the review changes spike

An automatically started session works on the claude/ingest-<timestamp> lock branch the Action created for it (kickoff) and opens a PR in the wiki repo. It never pushes to main. An interactive ingest, with Alex in the session, may commit straight to main, because he is reviewing as it happens (Karpathy's "stay involved" mode). The interactive session checks for a lock branch first. If a batch is in flight, it leaves that batch's inbox/ items alone and warns Alex that its page edits may conflict with the batch's PR.

Why: this keeps the reason behind the spike's "no autonomous ingest before a month of reviewed ingests" (every change is reviewed) without the delay. The review moves from "Alex starts the session" to "Alex merges the PR", which he can do from the GitHub app. claude/ branches are also the ones a Routine can always push to.

kickoffAn Action in the wiki repo fires a Routine; a lock branch makes each run's batch exact, and only one batch is in flight at a time

  • Trigger: a GitHub Action in the wiki repo runs on pushes to main that touch inbox/**. It POSTs to the Routine's /fire endpoint; the Routine's token lives only in the wiki repo's secrets. Any writer triggers it: Alfred, the book importer, a folder dropped from the Mac, or an interactive session. Alfred never needs to know Routines exist.
  • The lock is a branch, taken before the Routine starts. Before firing, the Action creates the run's branch, claude/ingest-<timestamp>, at main's current commit. If any claude/ingest-* branch already exists, a run is in flight (still working, or its PR awaits review), and the Action does nothing. Creating a branch that already exists fails, so two Actions can't both take the lock. The Action also runs in a single concurrency group.
  • The batch is exactly what was in inbox/ at the lock's commit. The session checks out the lock branch and ingests those folders, all of them and only them. It never pulls newer items from main. The Action passes the branch name in the fire payload. One run takes every waiting item, so a burst of sends becomes one PR.
  • Items that arrive mid-run wait for the next batch. They sit in inbox/ on main, untouched by the running session. Merging the PR moves that batch's folders out of inbox/, deletes the branch (which releases the lock), and is itself a push to main. The Action runs again, finds the waiting items, and starts the next batch. No item is ever in two runs.
  • The lock can't wedge. If /fire is rejected (a cap, an outage), the Action deletes the branch it just made. A lock branch that has no PR after a few hours is treated as a dead run: the next Action deletes it and proceeds. Closing an ingest PR without merging releases the lock but doesn't re-fire. That batch's items stay in inbox/ for the next run, and Alex removes any he doesn't want redone.
  • Fallback runner: if the Routine's daily cap ever bites, the Action's one step switches to claude -p (claude-code-action with the subscription OAuth token). Nothing on the wiki side changes (skill).

Why a Routine: it runs in the cloud whether or not the Mac is awake, it bills to the subscription like any interactive session (not per token), and it leaves a real claude.ai/code session Alex can open and continue from his phone. Routine GitHub triggers only fire on PR and release events, not pushes, which is why the Action sits in between.
Why not a local model: an ingest revises 10–15 interlinked pages without contradicting earlier ones. That is exactly where small models are weakest, and a wiki quietly degraded by its model is worse than none. The cheap steps (moving files, checking links) are scripts that need no model. Batching, which the one-batch-in-flight rule provides, is the cost lever that actually works.
Why the caps don't threaten correctness: Routines have a daily run cap per account (the number isn't published) and preview-era rate limits. A rejected fire leaves the folders in inbox/, and the next push or merge retries.
Why a lock taken before firing: "Skip while an ingest PR is open" alone leaves a gap. A session runs for many minutes before its PR exists, and an item arriving in that window would fire a second session, which would re-ingest the first batch (still in inbox/ on main) and open a conflicting PR. Taking the lock before firing closes the gap. Pinning the batch to the lock's commit means a session never sees items that arrive mid-run.
Why queue rather than stack onto an open PR: the PR Alex is reviewing never changes under him, and each merge is one coherent batch. The cost is latency: an item sent while a PR awaits review waits for that merge plus one more run.

7. Decisions — privacy, format, reading

storeA private GitHub repo of plain markdown, separate from the coach folder

As the spike decided (§2.2–2.4): a new private repo, cloned on the Mac as a sibling of the Productivity Coach folder, with links running coach → wiki only. The layout is CLAUDE.md, index.md, log.md (merge=union), inbox/, raw/, wiki/{concepts,entities,sources,questions}/, scripts/, .claude/skills/ingest/, and the source-types registry. The repo's name is open.

privacyRecord the inputs now; the sensitivity and visibility scripts ship with export changes spike

From the first ingest, the schema requires, and lint enforces, source_type and origin on every raw file and a non-empty sources: list on every wiki page. The sensitivity mapper and the visibility computer ship together with the (still deferred) public export step. The model never writes sensitivity or visibility; until those scripts exist, the fields simply don't exist.

Why: both scripts are deterministic functions of data we record anyway, so running them the day export arrives gives the same result as running them now. The spike's core principle survives intact: the model that saw the sources never decides what is safe to publish.

formatRelative markdown links, YAML frontmatter, no Obsidian-only syntax costly to reverse

As the spike decided (§2.5). Three consumers read the same files unconverted: Obsidian, the Reading room's react-markdown, and a future static site generator. Link syntax is written into every page body, so it can't be migrated cheaply. The rule covers the pages the model writes in wiki/. Alex's own words in raw/ keep his links as written (crosslinks).

readingThe reading room is read-only, and wiki pages join Alfred's global search

A thin Knowledge module in Alfred, using the spike's shape (§3.7): a snapshot of main taken on push (the fetchSpec pattern), rendered with react-markdown with relative links resolved inside Alfred, plus search and backlinks computed from the snapshot. Wiki pages also appear as their own group in ⌘P global search, and Knowledge is a ⌘K destination. There's no write path through Alfred and no graph view. It ships on Day 2; until then, Alex reads in Obsidian or the GitHub app.

Why in Alfred at all: Alfred is meant to be the single place Alex goes (spike §2.3). A wiki he can only read somewhere else is a wiki he'll forget to read.

8. Constraints & non-goals

  • No LLM writes through Alfred. Alfred only ever writes inbox/ folders; pages are written in git by a session.
  • No automatic merges. Automatic sessions stop at an open PR.
  • No automatic sending. Every source gets there through Alex's explicit act (bar).
  • No wiki storage in Supabase, and no Supabase queue.
  • No public export, static site, or garden in this epic. That stays deferred with the spike's triggers, and the privacy scripts ship with it.
  • No graph view (the spike's reasons: an unseeded layout can't pass the Storybook snapshot gate, and there aren't enough pages yet).
  • No local model for synthesis (kickoff).
  • Live data isn't a source. The wiki compiles documents. A spreadsheet, a calendar, or Alfred's own history gets in only as a dated snapshot document that a producer writes.
  • No changes to Alfred's retention. The Reader's 90-day and comms' 60-day sweeps stay as they are. The wiki's copy of anything is deliberate and separate.
  • No tasks or habits in the wiki. Alfred owns anything with a date. Coach files are never ingested.

9. The two-day split

The epic ships as two tickets, one per day. Each gets its own refinement session and spec, and each is built by one implementer session that dispatches subagents. The split is by where the code lives. Day 1 is the wiki itself, entirely outside Alfred. Day 2 is every Alfred-side integration. Day 2 depends on Day 1: it writes into the inbox contract and reads the pages Day 1 creates.

To the refiner of the Day 1 and Day 2 tickets: your spec must contain an explicit subagent plan for the implementer. The breakdowns below are a starting point, not that plan. Check them against the code (for Day 2) or the empty repo (for Day 1), then write a plan the implementer can follow without re-deriving it. It must say:
  1. Foundations the lead builds first, alone: the shared types, contracts, migrations, and shell wiring that more than one subagent needs, so the fan-out starts from a repo that already has them.
  2. Each subagent: the behavior it owns (a vertical slice, not a layer), its file boundary (the files it may touch and the neighbours it must not), its acceptance criteria, and the tests that pin them.
  3. Order: which subagents run in parallel (disjoint files), which wait for another, and why.
  4. The seams the lead reconciles after each batch: names, types, or files two subagents both depend on.
  5. What the lead keeps: integration, the full check run, commits, and the PR. On Day 1 it also keeps anything that needs Alex's accounts or his Mac.
  6. Model tier per role, following Alfred's CLAUDE.md: the lead on the strongest model, implementer subagents on the mid tier, lookups on the fast tier.
Alfred's implement-epic skill already covers how to dispatch well: build foundations first, give each subagent its own files, brief each one as if it can't ask a question, and don't let subagents commit. The Day 2 plan should point the implementer at that skill. The Day 1 plan must restate those rules inline, because the wiki repo won't have the skill.

Day 1 — the wiki itself, outside Alfred

Caveats: this ticket is built outside Alfred.
  • Refined in Alfred, built in the new wiki repo. Alex creates the empty private repo and pastes the spec into a session there. That session has none of Alfred's CLAUDE.md, skills, hooks, check gates, or demo docs, and it can't read this epic spec.
  • So the Day 1 spec must be self-contained. It restates every decision it depends on (envelope, immutability, fidelity, registry, picks, books, crosslinks, skill, autonomy, kickoff, format, store) and the subagent-dispatch rules. It also includes the Brain Rules sample, which Alex supplies because it isn't committed here, as the importer's reference input. It leaves out Alfred's PR machinery: the alfred block and spec archiving.
  • Its guardrails are its own. Alfred's back-pressure doesn't exist in the wiki repo. The spec sets up the repo's own lightweight gate, the scripts' tests plus lint, so the scripts aren't unguarded.
  • Some steps need Alex and can't be delegated:
    • creating the repo;
    • creating the Routine on claude.ai and putting its token into the repo's secrets;
    • cloning the repo on the Mac;
    • running the importer against the real vault. A cloud session can't reach the vault, so it builds and tests the importer against the sample, and Alex runs it.
    The spec lists these as a checklist for Alex, not as agent work.

Follow-ups outside this build

instapaperInstapaper tag sync: tag an article and it files itself follow-up

The goal: Alex tags an article in Instapaper. Its body and his highlights land in the wiki, the tag changes so the article isn't sent twice, and an ingest of it starts. No Mac, no session, and no click in Alfred.

It needs nothing new from this epic's architecture, only a new producer:

  • A poller checks Instapaper on a schedule for bookmarks carrying the "send" tag, fetches each article's text and highlights through Instapaper's API, and commits one folder per article to inbox/.
  • The folder:
    • source.md: the article body (full-text, with source_url).
    • excerpts-<date>.md: the highlights, verbatim. They are the author's words, but Alex chose them, so they carry the same signal as a Reader pick.
    • notes-<date>.md: any note Alex attached to a highlight, if the API returns them.
    Identity is the Instapaper bookmark id. Re-tagging an article after highlighting more adds only the new highlights (immutability).
  • The tag changes only after the commit lands. The "send" tag is swapped for a "filed" one. If the commit fails, the tag stays, and the next poll retries.
  • Kickoff is the existing one. The commit to inbox/ is an ordinary push, so the article joins the next batch under the lock (kickoff).
Left for its own refinement:
  • Where the poller runs: an Alfred Worker cron beside the Reader's, or a scheduled Action in the wiki repo, which would keep Alfred out of it entirely.
  • Whether Instapaper's API exposes tags or only folders. If only folders, the fallback is a "To wiki" folder whose items move to "Filed".
  • API access: the Full API needs an approved consumer key and xAuth.
This replaces the spike's deferred "Instapaper sync script" row. Once it exists, the Instapaper part of the seed could become "tag the backlog".

10. Open questions

  • Batching Instapaper, for the Day 1 spec. This is about the one-time seed; ongoing Instapaper is the follow-up. Is ingest: file-only the right valve for a bulk Instapaper import, or is it better to group several highlights into one synthesis pass? Batching may not save much, since the synthesis cost scales with pages touched rather than sessions started.
  • Email other than Reader posts, for a later spec. Reader posts are covered by reader_posts.text (90 days). Other mail sits in comm_messages.body for 60 days, so Alfred already stores the text. Still open: whether that body's extraction quality is good enough to serve as source.md, and what the send affordance looks like.
  • Variation in older book notes, for the Day 1 spec. The importer is designed from one sample. Running the seed over the whole vault will show how far older notes drift from that format; the importer flags what it can't classify rather than guessing.
  • The repo's name. It will show up in URLs if a public export ever happens.
  • Media that isn't a document. The design assumes every source reduces to markdown with a stable identity. Audio kept as audio, or a dataset, would break that. Revisit when one comes up; R2 for large binaries stays deferred under the spike's trigger.
  • The Routine's actual daily cap (shown at claude.ai/code/routines, not published). Check it when Day 1 is refined.
  • Network policy for pointer fetches. The default Trusted environment blocks arbitrary hosts, so the Routine's environment needs custom or full network access. Decide which in the Day 1 spec.
