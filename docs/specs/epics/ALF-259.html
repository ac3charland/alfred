ALF-259 — Wiki Module

Epic spec The shared context for the wiki epic: what the wiki is, how primary sources are shaped and how new kinds get added, how something moves from Alfred into the wiki, and what starts an ingest session. Story sessions read this before refining their own slice.

First refinement, 2026-09-24. Built on the spike docs/spikes/llm-wiki-spike.html. The spike's overall shape is kept: a private git repo of markdown, written by a Claude session, fed by Alfred, and read in Alfred. Where this spec settles something differently from the spike, the decision is tagged changes spike and this document wins. Decisions this session added are tagged new.

One-paragraph version. The wiki is Karpathy's LLM-wiki pattern: a private GitHub repo of plain markdown that a Claude session keeps compiling from the sources Alex chooses to send it. Every source is one folder with a fixed shape: the frozen original text, Alex's own notes, and the summary bullets Alex picked. That shape doesn't care where the source came from, so a new kind of source only needs a producer and one registry row. Alfred feeds the wiki by committing those folders into the wiki repo's inbox/: bullets picked in the Reader's "Novel ideas" section, and captured ideas the classifier marks as knowledge. A push that touches inbox/ starts a Claude Code Routine. The Routine drains the whole inbox following a committed ingest skill and opens a PR, and Alex merging the PR is the review. Alfred's read-only reading room comes last.

1. Problem space & why now

Alex reads a lot, through the Reader, Instapaper, and books, and has ideas worth keeping. Today none of it compounds. A Reader post's text is swept after 90 days, Instapaper highlights sit in Instapaper, book notes sit in Obsidian, and a captured idea is just an inbox item. Asking Claude about any of it means rediscovering it from scratch each time, which is RAG's failure mode. The LLM-wiki pattern fixes this by having a model compile sources into an interlinked set of pages once, then keep those pages current.

Why now: the Reader already does the expensive part, reading every newsletter and extracting its novel ideas. That compute currently expires with the post. Sending Alex's picks from it into a wiki turns a disposable summary into lasting knowledge. The spike settled the high-level shape; this epic settles primary sources and the ingestion workflow, which the spike left thin.

3. Architecture

Solid lines are the automatic path; dashed lines are Alex, a re-trigger, or the later reading room. Git is the only queue.

What the architecture commits to:

  • Git is the queue, the store, and the audit log. Nothing about the wiki lives in Supabase. A write that fails or a run that gets rejected leaves its folder sitting in inbox/, and nothing is lost.
  • Alfred is a producer and, eventually, a reader, never a writer of wiki pages. The only thing Alfred writes into the wiki repo is inbox/ folders. The model writes pages, and only through git.
  • Every way of running an ingest does the same job. A Routine, claude -p, and an interactive session all follow one committed ingest skill, so swapping the runner doesn't touch the wiki.

4. Decisions — primary sources

envelopeEvery source is one folder with a fixed shape changes spike costly to reverse

A source is a folder, not a file. It lands in inbox/; ingest moves it (git mv, contents unchanged) into raw/, sorted by year:

inbox/2026-09-24-why-habits-stick/            ← waiting
raw/2026/2026-09-24-why-habits-stick/         ← after ingest; permanent
    source.md               the author's words as markdown; body frozen   (optional)
    notes-2026-09-24.md     Alex's own words, one file per sitting        (optional)
    picks-2026-09-24.md     summary bullets Alex picked, model-worded     (optional)
    assets/                 original binary the text was extracted from   (optional)

Every file is optional, but a folder must contain at least one of them. Different kinds of source use the same shape and leave pieces out:

  • Reader post: source.md (the post text) plus picks-… (the bullets Alex sent).
  • Book: notes-… files only, which keep accumulating as he reads. The book's text is never stored.
  • Captured idea: a single notes-… file.
  • PDF: source.md holds the extracted text; the PDF itself goes in assets/.

Every file carries YAML frontmatter with a small fixed core: source_type, origin, title, author, source_url, published, captured, via, external_id. A source.md also carries fidelity (see fidelity). origin is one of:

  • third-party: someone else's words
  • mine: Alex's words
  • model-derived: the model's words, picked by Alex

Why a folder: the author's words, Alex's words, and the model's words have different provenance. That matters for trust (a pick can misquote), for licensing (a paid Substack post), and for any later public export. Separate files let a wiki page cite exactly the kind of material it used. A folder also gives notes that grow over time (a book read across six weeks) somewhere to accumulate.
Why costly to reverse: every wiki page's sources: list points at these paths. Changing the scheme later means rewriting citations across the whole tree, the same class of cost as the spike's link-syntax rule.

immutabilityOnly the body is frozen; frontmatter can be amended by script, and a source can keep growing new

  • The body of source.md is never edited. It is the record of what Alex read. Frontmatter may be amended by scripts (a backfilled field, a later sensitivity label), never by the model's judgment.
  • Identity is external_id, or the canonical URL when there is no id. A later send for a source that's already filed arrives as an inbox/ folder holding only the new files (say, one more picks-…). Ingest merges those files into the existing raw/ folder and never creates a duplicate.
  • A materially revised source is a new capture, whose frontmatter names the earlier folder with supersedes: <path>.

Why: the spike's "raw is write-once" rule conflicts with its own script setting sensitivity on raw files. Scoping "write-once" to the body resolves that, and it is also what lets a source type add fields later without breaking the rule.

fidelityA fidelity field records how much of the source was captured new

fidelityMeaningTypical case
full-textThe whole source, converted to markdownReader post, web article, extracted PDF
excerptVerbatim highlights onlyInstapaper / Kindle highlights
pointerMetadata and a URL only; the ingest session should try to fetch itA Reader post whose text has already been swept; a bare link
notes-onlyNo source.md by ruleBooks, captured ideas

Given a pointer, the ingest session tries to fetch the text and upgrades the folder to full-text. If it can't (a paywall, a network block), it leaves the folder at pointer and says so in the PR.

Why: pointer is what keeps adding a source type cheap. A producer that only has a URL can still hand one off, and the hard part (fetching) happens in one place.

registryA new source type is a producer plus one registry row; there's no denylist changes spike

A source-types registry file in the wiki repo lists each source_type with its highest allowed fidelity (books cap at notes-only), its default origin, and, once export exists, its default sensitivity. Lint checks every folder against its row. Adding a source type means writing a producer and adding a row; the ingest skill, lint, and reading room don't change.

Producers can live in three places:

Producer lives inSuitsIn this epicLater, for example
Alfred (it already holds the content)Things Alfred capturesReader picks; captured ideasNon-Reader newsletters
The ingest session (completes a pointer)Anything reachable by URLSwept Reader postsArticles, arXiv, transcripts
Alex / the Mac (drops a folder)Exports and one-offsThe seed: Obsidian book notes and Instapaper highlightsKindle / Readwise exports, PDFs

Why no denylist: Alex is the only builder and the only sender, and every source reaches the wiki through an explicit act of sending. A standing ban (the spike's "comms are never a source") would only be friction. Sending a message to the wiki is a deliberate choice to keep it, and it doesn't change the fact that Alfred's own copy of comms is still swept at 60 days.

Two things producers must do: split mixed provenance (Kindle quotes go in source.md at excerpt; Alex's comments go in notes-…), and never put an LLM summary in source.md. Model-written text only ever enters as picks.

barSending is the ingest bar; filing is not ingesting new

Nothing reaches the wiki automatically. A source enters only because Alex sent it, dispatched it, or dropped it in. There's no "ingest everything I saved". A producer may mark a folder ingest: file-only: ingest moves it into raw/ and logs it, but doesn't synthesize pages from it. Those pages get written later, when a question or a newer source touches it.

Why: this keeps the wiki about what was new to Alex (the spike's first anti-goal) while still letting bulk imports get archived without a synthesis session per item. Whether this valve is also the right way to batch Instapaper is open.

picksPicked bullets are model-derived, and ingest checks them against the source new

A picks-… file holds the "Novel ideas" bullets Alex chose, word for word, with origin: model-derived. The signal is that Alex found these insightful; the wording is the summarizer's. Before building on a pick, the ingest session checks it against source.md. A pick the source doesn't support gets flagged in the PR, not synthesized.

Why not origin: mine: a summarizer can misstate an article, and a paraphrase of a paid post is still derived from that post. Labelling the picks as Alex's own words would launder both problems. The source text sitting next to the picks is what makes the check cheap.

5. Decisions — the path into the wiki

handoffAlfred commits folders to inbox/ through the GitHub API changes spike

Alfred writes each envelope straight into the wiki repo's inbox/ on main, as a commit made through the GitHub Contents API. It uses a separate fine-grained token with Contents:write on the wiki repo only; the existing read-only GITHUB_TOKEN stays read-only. There's no Supabase queue and no keyed inbox endpoint.

Why: the queue then lives in git, with no sweep and no expiry, and it's visible as ls inbox/. Ingest sessions need no Alfred API key and no network route to Alfred, and they behave the same on the Mac and in the cloud. The commit is also the event that starts kickoff. The cost is a write token, kept to the smallest scope that works.

readerReader → wiki sends picked "Novel ideas" bullets, and the post text rides along changes spike

In a post's "Novel ideas" section (overview.novel_ideas), Alex can send a single bullet or all of them. A send produces an envelope containing:

  • source.md, built from reader_posts.text (fidelity: full-text), plus the post's metadata; and
  • a picks-… file with the chosen bullets.

Sending more bullets from the same post later adds only a new picks file (immutability). Once the 90-day sweep has nulled the text, a send still works: source.md becomes a pointer at canonical_url. Paywalled posts may fail to fetch at that point, and the PR will say so.

Why: Alex doesn't want the whole article dumped into the wiki. The summarizer has already done the work of finding what's new, and Alex's pick is the strongest signal of what mattered. The full text rides along so the picks can be checked and so later synthesis has the original to go back to.

How the picker looks (per-bullet affordance, "send all", sent state) belongs to the handoff story, which draws it in the Reader's own design system. This spec only fixes the behavior.

ideasCaptured ideas: the classifier suggests knowledge, and Alex dispatches

The ALF-158 classifier gains knowledge as a third item_type (today it only picks task and code). The enum value has been reserved since 0001_initial_schema.sql. It's still only a suggestion. Dispatching a knowledge item from the Inbox commits a notes-only envelope (origin: mine) to inbox/ and takes the item out of Alfred. From then on the wiki is the record, consistent with ALF-7 D2: Alfred mirrors, it is never the store of record.

Why not auto-send: it would break bar. The click is the decision to keep something.

6. Decisions — ingest sessions

skillOne committed ingest skill guides every ingest new

The wiki repo carries an ingest skill (.claude/skills/ingest/SKILL.md, referenced from its CLAUDE.md). It is the step-by-step ingest procedure:

  1. Pull.
  2. Drain inbox/ and complete any pointers.
  3. Merge folders into existing raw/ folders by identity.
  4. Verify picks.
  5. Write and update pages.
  6. Update index.md and log.md.
  7. Lint.
  8. Commit, one commit per source.
  9. Push and open the PR, whose description lists the pages touched, flagged picks, failed fetches, and questions for Alex.

The Routine's saved prompt, a claude -p invocation, and an interactive session all just say "follow the ingest skill".

Why: the procedure is the part that will keep getting tuned, and it needs one home. With the procedure in the repo, changing runners never changes behavior, and improving ingest is an ordinary reviewed commit.

autonomyAutomatic sessions draft a PR; Alex's merge is the review changes spike

An automatically started session works on a claude/ingest-<date> branch and opens a PR in the wiki repo. It never pushes to main. An interactive ingest, with Alex in the session, may commit straight to main, because he is reviewing as it happens (Karpathy's "stay involved" mode).

Why: this keeps the reason behind the spike's "no autonomous ingest before a month of reviewed ingests" (every change is reviewed) without the delay. The review moves from "Alex starts the session" to "Alex merges the PR", which he can do from the GitHub app. claude/ branches are also the ones a Routine can always push to.

kickoffAn Action in the wiki repo fires a Routine; each run drains the whole inbox, and only one ingest is in flight at a time

  • Trigger: a GitHub Action in the wiki repo runs on pushes to main that touch inbox/**. It POSTs to the Routine's /fire endpoint; the Routine's token lives only in the wiki repo's secrets. Any writer triggers it: Alfred, a folder dropped from the Mac, or an interactive session. Alfred never needs to know Routines exist.
  • One run in flight at a time: the Action does nothing while an ingest PR is open. Merging that PR is itself a push to main, so if items arrived during review, the merge starts the next run.
  • Drain everything: each run processes all of inbox/, not only the item that triggered it. The result is at most about one run per merged PR, and a burst of sends becomes one PR.
  • Fallback runner: if the Routine's daily cap ever bites, the Action's one step switches to claude -p (claude-code-action with the subscription OAuth token). Nothing on the wiki side changes (skill).

Why a Routine: it runs in the cloud whether or not the Mac is awake, it bills to the subscription like any interactive session (not per token), and it leaves a real claude.ai/code session Alex can open and continue from his phone. Routine GitHub triggers only fire on PR and release events, not pushes, which is why the Action sits in between.
Why not a local model: an ingest revises 10–15 interlinked pages without contradicting earlier ones. That is exactly where small models are weakest, and a wiki quietly degraded by its model is worse than none. The cheap steps (moving files, checking links) are scripts that need no model. Batching, which the drain rule provides, is the cost lever that actually works.
Why the caps don't threaten correctness: Routines have a daily run cap per account (the number isn't published) and preview-era rate limits. A rejected fire leaves the folders in inbox/, and the next push or merge retries.

7. Decisions — privacy, format, reading

storeA private GitHub repo of plain markdown, separate from the coach folder

As the spike decided (§2.2–2.4): a new private repo, cloned on the Mac as a sibling of the Productivity Coach folder, with links running coach → wiki only. The layout is CLAUDE.md, index.md, log.md (merge=union), inbox/, raw/, wiki/{concepts,entities,sources,questions}/, scripts/, .claude/skills/ingest/, and the source-types registry. The repo's name is open.

privacyRecord the inputs now; the sensitivity and visibility scripts ship with export changes spike

From the first ingest, the schema requires, and lint enforces, source_type and origin on every raw file and a non-empty sources: list on every wiki page. The sensitivity mapper and the visibility computer ship together with the (still deferred) public export step. The model never writes sensitivity or visibility; until those scripts exist, the fields simply don't exist.

Why: both scripts are deterministic functions of data we record anyway, so running them the day export arrives gives the same result as running them now. The spike's core principle survives intact: the model that saw the sources never decides what is safe to publish.

formatRelative markdown links, YAML frontmatter, no Obsidian-only syntax costly to reverse

As the spike decided (§2.5). Three consumers read the same files unconverted: Obsidian, the Reading room's react-markdown, and a future static site generator. Link syntax is written into every page body, so it can't be migrated cheaply.

readingThe reading room is read-only and built last

A thin Knowledge module in Alfred, using the spike's shape (§3.7): a snapshot of main taken on push (the fetchSpec pattern), rendered with react-markdown with relative links resolved inside Alfred, plus search and backlinks computed from the snapshot. There's no write path through Alfred and no graph view. Until it exists, Alex reads in Obsidian or the GitHub app.

Why last: ingestion is this epic's center of gravity, and reading already works without it. It is still in scope, but it's the first slice to move to a follow-up epic if the others run long.

8. Constraints & non-goals

  • No LLM writes through Alfred. Alfred only ever writes inbox/ folders; pages are written in git by a session.
  • No automatic merges. Automatic sessions stop at an open PR.
  • No automatic sending. Every source gets there through Alex's explicit act (bar).
  • No wiki storage in Supabase, and no Supabase queue.
  • No public export, static site, or garden in this epic. That stays deferred with the spike's triggers, and the privacy scripts ship with it.
  • No graph view (the spike's reasons: an unseeded layout can't pass the Storybook snapshot gate, and there aren't enough pages yet).
  • No local model for synthesis (kickoff).
  • Live data isn't a source. The wiki compiles documents. A spreadsheet, a calendar, or Alfred's own history gets in only as a dated snapshot document that a producer writes.
  • No changes to Alfred's retention. The Reader's 90-day and comms' 60-day sweeps stay as they are. The wiki's copy of anything is deliberate and separate.
  • No tasks or habits in the wiki. Alfred owns anything with a date. Coach files are never ingested.

The Wiki repo slice's spec is written for a different reader. It will be refined in Alfred, like any story, but built by a session in the new, empty wiki repo, where it will be pasted in by hand. That session won't have Alfred's CLAUDE.md, skills, hooks, check gates, demo docs, or this epic spec. So that spec must be self-contained: it inlines every decision it depends on from this document (envelope, immutability, fidelity, registry, picks, skill, format, store), assumes no Alfred conventions or tooling, and doesn't carry Alfred's implementation-PR machinery (the alfred block, spec archiving) into the wiki repo.

10. Open questions

  • Batching Instapaper, for the Wiki repo spec. Is ingest: file-only the right valve for a bulk Instapaper import, or is it better to group several highlights into one synthesis pass? Batching may not save much, since the synthesis cost scales with pages touched rather than sessions started.
  • Email other than Reader posts, for a later handoff spec. Reader posts are covered by reader_posts.text (90 days). Other mail sits in comm_messages.body for 60 days, so Alfred already stores the text. Still open: whether that body's extraction quality is good enough to serve as source.md, and what the send affordance looks like.
  • The repo's name. It will show up in URLs if a public export ever happens.
  • Media that isn't a document. The design assumes every source reduces to markdown with a stable identity. Audio kept as audio, or a dataset, would break that. Revisit when one comes up; R2 for large binaries stays deferred under the spike's trigger.
  • The Routine's actual daily cap (shown at claude.ai/code/routines, not published). Check it when the auto-ingest slice is refined.
  • Network policy for pointer fetches. The default Trusted environment blocks arbitrary hosts, so the Routine's environment needs custom or full network access. Decide which in the auto-ingest story.
  • Carried over from the spike: whether Rock 2's "LLM-wiki implemented in Alfred" needs rewording, and whether the Motivic/Chad reference docs migrate out of the coach folder. Both are Alex's decisions and don't block any slice.
