ALF-240 — Spike: Instagram message integration to comms

Can the owner's Instagram DMs feed the Comms module (epic ALF-7)? If so, by which read path, and how does it fit the epic's invariants: dedupe key, cursor, health, the reply-detection drain, and Open in source? The owner's account is a personal account. The owner would consider switching it to Creator if that turned out to be the clean path. It isn't clean (§2).

1 · Where we landed

There is no official, terms-clean way to read a personal account's DMs. Meta's messaging API serves Professional (Business/Creator) accounts only. Converting has three problems:

  • The account goes public. A Professional account can't be set to private.
  • The API still can't see group DMs. For D18 that's a missed obligation that leaves no trace.
  • Meta's docs contradict each other on whether a single-owner app receives webhooks for DMs from ordinary senders.

If Instagram is built, build it as a third Mac-daemon source that reads the Beeper Desktop API on localhost. Beeper Desktop runs the open-source mautrix Instagram bridge on the Mac. Its first-party local REST API supplies what the epic needs:

  • message ids for source_id
  • chat ids for thread_key
  • an isSender flag for direction, and so for D18's reply-detection drain
  • group chats

It slots into the daemon's existing Source contract the same way iMessage and WorkMail do, and it inherits the same limit: the Mac sleeps.

But gate the build on a zero-code trial, and on the owner accepting one real risk. Every non-official path, Beeper included, is automated access under Instagram's Terms §4.2. Users of the bridge report checkpoints ("we suspect automated behaviour"), and one reported a disabled account.

  • The trial: install Beeper Desktop, connect Instagram on-device, and use it for two weeks with no alfred code.
  • What it answers: whether this account gets checkpointed, and the four API questions in §6.
  • If it gets checkpointed: the answer is "no Instagram source", not the official API.

This amends the epic, so it's the owner's decision. ALF-7 §5 lists "the owner's four actual channels" as a non-goal boundary, and D9's table has no fifth row. An Instagram story needs an epic revision first. It can only land after the daemon stories E (skeleton) and Q (ingest endpoint).

2 · Why

The official API is built for businesses talking to customers, not for a person's inbox

  • Professional accounts only. "Your app users must have an Instagram professional account. An Instagram professional account can represent a business or creator" (Platform overview). The Basic Display API, the last consumer-account surface, shut down on 2024-12-04 and never exposed DMs anyway.
  • Converting makes the account public. "Professional accounts can't be set to private" (Instagram Help, verified this session). That applies to Creator as well as Business, and pending follow requests are auto-accepted. For a personal account that is a real cost unrelated to alfred.
  • Group DMs are out of reach. "Group messaging is not supported. An Instagram professional account can only converse with one customer per conversation" (Messaging API, verified). A group thread asking the owner something would never reach alfred. That breaks D24's rule that a message is never silently skipped, and it is §1's failure 1 (a missed obligation) with no trace anywhere. Keeping the account private is a preference. The group-DM gap is a correctness problem.
  • Delivery to a single-owner app is contradictory in the docs.
    • Webhooks require the app to be Live (Webhooks setup).
    • The setup page's requirements table lists "Advanced Access" and business verification "for production access".
    • The Messenger-Platform overview says "Apps with Standard Access can only interact with people who have a role on the app". A friend DMing the owner has no app role.
    • The App Review page says an app "only for a business I own or manage" needs Standard Access and no review.
    • Community reports (n8n, Aug 2025) say DM webhooks fired only for tester accounts.
    Only a hands-on test would settle it, and it's moot unless the owner goes public.
  • Smaller costs if it were built anyway:
    • A 60-day token that must be refreshed before it lapses, the same trap as D23.
    • Only the 20 most recent messages per thread are readable, so D21's backfill is shallow.
    • Request-folder threads inactive for 30 days are hidden.
    • GIFs and stickers fire no webhook.
    • It needs a new webhook route in the Worker, a third "home" the schema doesn't allow today (§3.4).

Beeper's local API maps onto the epic almost field for field

  • First-party, documented and local. "Local API & MCP for Beeper Desktop … requires Beeper Desktop to be running", covering "WhatsApp, Instagram, Telegram …" (Desktop API, verified). It listens on localhost:23373 with a bearer token created in Settings → Integrations (auth). It has been open to all stable-app users since v4.1.169 (2025-09-02). Reads are "not subject to" Beeper's sending restrictions (Beeper help).
  • Reply detection is built in. Search takes sender=me|others, and every message carries isSender, "True if the authenticated user sent the message" (messages/search, verified). That is the iMessage is_from_me pattern the daemon already normalizes (daemon/src/sources/imessage/normalize.ts:153). The existing comm_record_reply drain (database/migrations/0034_comms.sql:393) works unchanged once thread_key is the chat id.
  • On-device, open-source bridge. Beeper runs Instagram through the mautrix bridge, "the same bridges we run with On-Device Connections and also on Beeper Cloud" (open source). The on-device option means "messages never touch our servers" (FAQ). So Beeper adds no new party holding the owner's DMs. The bridge is very actively maintained: releases on 2026-08-16, 09-10 and 09-16, and a commit on 2026-09-24 (mautrix/meta releases). That matters, because Instagram changed its DM protocol in mid-2026 and bridges broke and were fixed within weeks (mau.fi, 2026-07). With Beeper, that maintenance is Beeper's job, not alfred's.
  • Encryption is no longer an obstacle. "End-to-end encrypted messaging on Instagram is no longer supported as of May 8, 2026" (Instagram Help, verified). It had been opt-in only. Any server-side reader now sees every DM except vanish-mode ones.
  • Free. Beeper's free tier covers up to 5 accounts, one per network (FAQ).

The risk that doesn't go away

Instagram's Terms §4.2 forbid "accessing or collecting information in an automated way without our express permission". Beeper, mautrix and instagrapi are all that. The documented consequence is checkpoints: Meta may block you "until you do some tasks like completing a captcha, adding a phone number or resetting your password" (mautrix docs). mautrix/meta#44 ("We suspect automated behaviour") has open reports through 2026:

  • a flag after about an hour of use, on a home IP with 2FA on (2025-12)
  • cookie sessions dying after about 7 days (2026-08)
  • one "account is disabled" report, which another user attributed to the bridge's token rather than the account

Other users report months without incident. The risk falls on the owner's personal account, not on alfred. It's worth taking only if the trial shows this account is left alone.

3 · Technical shape

The daemon pulls from Beeper; nothing pushes into the daemon. The link from Beeper to Instagram is Beeper's concern. Everything to the right of the daemon already exists.

3.1 · The source

A third directory, daemon/src/sources/instagram/, implementing the existing Source contract (daemon/src/sources/types.ts:35-42: key, kind, label, check(), poll(ctx)). The runner, batching, backoff, HMAC signing and heartbeat are already source-agnostic (daemon/src/runner.ts). The plug-in steps are the ones daemon/src/sources/index.ts:7-12 already lists:

  • a config section in config.ts
  • a factory under sources/instagram/
  • one branch in createSources()

The Beeper token is a Keychain item reached through createSecretResolver (daemon/src/keychain.ts:82-98), never the config file (the same rule as the WorkMail password).

Poll: the daemon polls, it doesn't watch (D10 holds)

GET http://localhost:23373/v1/messages/search
    ?accountIDs=<the Instagram account id from GET /v1/accounts>
    &dateAfter=<cursor.after − overlap>
    &excludeLowPriority=false      ← the default is true, which hides chats the owner marked low-priority
    &limit=20  (the max)  … then page with cursor + direction=after while hasMore
Authorization: Bearer <token from Keychain>
  • Cursor (comm_accounts.cursor is opaque jsonb, so no migration is needed): { "after": "<ISO timestamp of the newest message ingested>" }. Re-read with a small overlap. The dedupe key makes overlap free: unique (account_id, source_id) (0034_comms.sql:108), and the store counts replays as duplicates (workers/src/comms/store.ts:52). D21's rules apply unchanged: seed from 7 days on first run, and re-seed from last_seen_at, never the window.
  • excludeLowPriority=false is binding. Beeper's default silently drops chats the owner has marked low-priority. That's §1's failure 1 arriving through a default.
  • Don't use the WebSocket (ws://…/v1/ws). Beeper labels it "experimental and may change between desktop releases" and documents no replay, so it's the FSEvents trap again.

Health: D17 without new machinery

check() calls GET /v1/info and confirms the Instagram account is listed and connected.

  • Beeper not running (connection refused) → erroring, with that reason, not stale. The daemon is up and the source is dead.
  • A checkpointed or logged-out bridge → erroring "reconnect Instagram in Beeper". This is the likeliest failure, and D17 exists so it isn't a green dot over a dead source.
  • The Mac asleep → stale, exactly as for iMessage. The ASAP latency promise (D17) doesn't extend to Instagram.

3.2 · Open in source (D20)

frontend/lib/comms/deep-link.ts:64 branches only on 'imessage', and every other kind falls through to the Mail branch. An 'instagram' account would build a broken message:// link, so it needs its own branch.

  • Safe floor: https://www.instagram.com/direct/inbox/.
  • Better, if it can be sourced: https://www.instagram.com/direct/t/<thread id>/.

Whether Beeper exposes Instagram's native thread id is unknown (§6 Q4). Open in source is D24's recovery path, so the inbox-level link is the minimum, not a nice-to-have.

3.3 · People and handles (D12)

"Anything from my wife is ASAP" only works on Instagram if an Instagram username resolves to a person. That needs three changes:

  • a third handle kind: comm_handles_kind_valid is kind in ('email', 'phone') (0034_comms.sql:227)
  • a username branch in all four copies of handle canonicalization: SQL comm_canonical_handle (0037_comms_etiquette.sql:129-146), whose else branch strips non-digits and would turn a username into an empty string; frontend/lib/comms/people.ts:30; workers/src/comms/prompt.ts:232; and daemon/src/sources/imessage/normalize.ts:49
  • the people editor learning the new kind

3.5 · Inherited limitations

  • Edits and unsends: a forward poll doesn't see them, the same blind spot as D28, accepted for the same reason. Beeper's WebSocket does emit message.upserted and message.deleted, which a later story could use once it's out of "experimental".
  • Vanish-mode chats don't bridge (mautrix/meta#319, "a bug on the instagram side"). They're invisible, and that should be stated as a limitation, as D28 does.
  • No sending, ever. The API can send, and Beeper warns that sending is what gets accounts suspended. The epic's non-goal already forbids it, which also keeps the risk surface to reads.

4 · Sidebars: appealing alternatives we're not taking

Convert to Creator and use Meta's official Instagram API

It's the only terms-clean path, and it is well documented:

  • Instagram Login, with no Facebook Page needed
  • messages webhooks with is_echo for the owner's own replies
  • signing via X-Hub-Signature-256 with the App Secret
  • a Conversations API for catch-up

What rules it out:

  • The account becomes public.
  • Group DMs are unsupported. That's a silent false negative the epic's invariants forbid.
  • The Live mode and Standard vs Advanced Access conflict (§2).
  • A 60-day token to keep alive.
  • A 20-message backfill cap.
  • A new webhook route in the Worker plus a third home.

Revisit ifthe account becomes Professional for other reasons and the owner accepts that group DMs never arrive. Even then, test webhook delivery from a non-role sender before writing a spec.

Self-host the mautrix-instagram bridge

It removes the Beeper dependency, and it's the same code. But it needs a Matrix homeserver (Synapse plus appservice registration plus a database) or Beeper's bbctl, and an Instagram login alfred would have to manage. The login is cookie-based, and sessions die after about 7 days in some reports. The terms risk is identical. Beeper Desktop is the same bridge with someone else doing the upkeep.

Revisit ifBeeper Desktop's API is withdrawn, paywalled, or its breaking changes (about twice a year per its changelog) become a burden.

instagrapi or a Node private-API client inside the daemon

This path has no dependency on another app, and instagrapi has DM, pending-inbox and realtime reads. What rules it out:

  • It's Python in a Node daemon.
  • 3.0.0 (2026-09-12) changed login with no fallback, and login-breakage issues pile up monthly (e.g. #2807, 2026-09-18).
  • Its own README steers production users to a paid service.
  • The Node libraries are dead: instagram-private-api was last published in 2024-03.

It has the highest checkpoint risk of any option, with alfred holding the owner's raw Instagram password.

Read Instagram web notifications from the Notification Center database

This is tempting because the daemon already holds Full Disk Access. On this Mac (macOS 26.6.2) ~/Library/Group Containers/group.com.apple.usernoted/db2/db exists. Its record.data blob carries the notification, and web push from instagram.com would land under the browser's app_id.

What rules it out:

  • It sees incoming messages only, so there's nothing for D18's reply detection. A source with no drain "honours two of the three exits, which is not enough", and the epic forbids shipping one.
  • There's no thread id.
  • Truncation and retention are unknown.
  • Dismissing the notification may drop the record.

Email notifications through the existing Gmail path

This would need zero new code, since Gmail is already ingested. But no source shows Instagram sending a per-DM email with the message text. What exists are "message reminder" digests about a day after an unanswered DM. That's too late for Today, carries no reply signal, and is unreliable as a channel. Worth one Gmail search (from:instagram.com) to confirm, but not a design.

"Download your information" exports

This path is official and terms-clean, and includes group threads as JSON. But it's manual, generation takes minutes to 48 hours, and the link expires in 4 days. Useful for one-off backfill or for building story K's eval fixtures from real Instagram DMs. Not an ingestion path.

5 · Cost

  • Effort: one story, about the size of story G (WorkMail): a daemon source with fixture tests, one migration, a regenerated types file, and a deep-link and handle-kind branch in the frontend. It depends on E and Q (daemon skeleton, ingest endpoint), and it's cheaper after F because the iMessage source is the closest template. It needs an epic revision before refinement.
  • Money: $0. Beeper's free tier (5 accounts, one per network) covers it. There's no Meta app, no App Review and no business verification.
  • Risk, in order:
    1. A checkpoint or suspension of the owner's personal Instagram account (terms §4.2). This is the gate.
    2. Beeper or Instagram breaking the bridge for days to weeks. The mid-2026 protocol switch broke it, and D17's erroring state is the answer.
    3. Beeper changing or paywalling the local API.
    4. The Mac being a single point of failure for three of five sources.

6 · Open questions

Q1–Q4 are answerable in an afternoon with curl during the trial. Q5–Q7 are the owner's.

  1. Does /v1/messages/search with no query return every message in the account after dateAfter? The docs list query as a filter, not as required. If it isn't enough, the fallback is GET /v1/chats ordered by lastActivity, then /v1/chats/{id}/messages?direction=after per active chat.
  2. Are Beeper message ids stable across a re-login or bridge reconnect? This is the dedupe key. If they change, a checkpoint recovery re-ingests the whole window as new rows, the corruption D21 warns about. If they're unstable, a composite of chat id, timestamp and sender is the fallback key.
  3. Does the on-device Instagram connection backfill? Beeper's Instagram help page says "only new messages sent after setup may appear". The page is undated and mautrix supports backfill. This decides whether D21's 7-day seed means anything for this source.
  4. Can the native Instagram thread id be recovered for a /direct/t/<id>/ deep link, and do message requests from non-followers come through at all?
  5. Is Instagram DM volume worth a fifth channel? The epic's premise is a small, honest count. If Instagram carries a handful of real asks a month, "tell those people to text" costs less than a source.
  6. Does the owner accept the terms risk on their personal account, once the two-week trial is in? This is the go/no-go.
  7. Notifications (the epic's Q0). If Instagram notifications stay on, as the epic asks of Gmail and Messages, the Instagram source is a ledger, not a firewall. That's the same trade the epic already names.
