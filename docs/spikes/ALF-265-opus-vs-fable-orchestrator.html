ALF-265 — Single Opus agent vs. a Fable orchestrator with Sonnet implementers

On one replayed story (ALF-289), the Fable orchestrator cost 2.1× as much ($39.48 vs $19.09) and took 30% longer. All four blind judge verdicts preferred the single Opus agent’s patch.

Where we landed

Keep a single Opus agent for story-sized implementation. Don’t launch stories as a Fable orchestrator with Sonnet implementers. The bet behind the architecture was that an expensive model which only plans and integrates stays cheap while cheap models do the typing. It didn’t hold. The orchestrator’s own thread produced as much output as the single agent writing all the code, and it accounts for 80% of its arm’s cost. Delegation also lost things at the seams.

This is one ticket, so it’s a case study, not a rate. The one uncontrolled difference, effort, ran in Fable’s favour. Next, I’d cut two stories: an Opus medium vs high effort trial on the implementation lane, and a replay of the epic lane, the only place orchestration has a structural case.

The evidence

Everything below is for whoever builds on this. Acting on the answer needs only what’s above.

The experiment

The ticket said to compare the same prompt on output and cost, with an LLM judge choosing a winner or calling it even. The owner settled four design questions before anything ran:

  • Arms. Add a fresh single-Opus replay rather than compare against the historical session alone.
  • PRs. Push branches and open no PRs.
  • Ticket. A multi-layer story, so the orchestrator has slices to dispatch.
  • Judges. Opus and Fable, each in both orders.

The ticket

ALF-289 (Reader “Further reading”) was chosen from the 61 merged implementation PRs in #330–#428. It is a single-model Opus 5.5 session at high effort that cost $32.47, with no human commits. It spans a migration, a Worker prompt and schema change, an API route, a store, a component, Storybook and Playwright: about 70 files. That gives an orchestrator real, separable slices.

Held equal

  • Base commit. 80f0d0d: main when the original session started, not the PR’s base.sha (4013e36), which the original reached by rebasing.
  • Prompt. The launch prompt, verbatim from the original session’s first user event, behind one shared preamble. The preamble: no PR; review the branch diff; no human answers; don’t read the merged solution; report to the parent. The arms differ only by one architecture paragraph in B.
  • Review. One Opus adversarial review round, the same gates (pre-commit check:fast, pre-push check:slow), and no human turns.

Not held equal

  • Effort. create_session takes a model but no effort, so each child ran its model’s default: Opus 5.5 at medium, Fable 5.1 at high. The difference favours B, since more effort is more thought for the same task, so it strengthens rather than explains the result.
  • A’s single-agent rule reached it as a send_message a minute after launch, not in its prompt. It complied: its one subagent is the reviewer.

The counterfactual

B’s orchestrator thread priced at Opus 5.5 rates is $18.00. Add B’s subagents and an Opus orchestrator with Sonnet implementers would still cost about $25, more than A’s $19.09. Most of the gap is Fable’s price: $50 against $20 per million output tokens, and $0.25 against $0.20 for cache reads. The rest is orchestration itself, which didn’t shrink the lead’s thread.

The historical session cost $32.47 at high against A’s $19.09 at medium. That comparison is confounded: it includes a rebase turn, a Q&A turn and a Sonnet UI subagent. But it is consistent with ALF-283’s point that effort is the cheapest lever.

Output quality

The judges

Four blind pairwise verdicts:

  • Inputs. Anonymised diffs against 80f0d0d, with binary snapshots excluded. Model names, branches and session ids were masked, and the patch files had neutral names.
  • Brief. Grade the spec’s checklist item by item, with file:line citations; hunt for defects; score five criteria; then give an overall verdict, where “about the same” is allowed and a tie on fidelity goes to the smaller patch.

What separated them

All points below were named by at least three judges. Those marked ✓ I re-checked on the branches.

  • ✓ B deviates from a settled decision (D7). It reserves a quarter of the model-input cap for the links block first (LINKS_BLOCK_SHARE = 4 in workers/src/reader/prompt.ts). The spec settles text first, then the list cut whole-line, which A implements.
  • ✓ B leaves two committed demo docs broken. It changed reader-eval’s output and the summary schema without refreshing the demos that record them. npm run demo -- verify on B’s branch changes 1 of 2 blocks in reader-pipe-and-list and 4 of 9 in alf-272-to-reader, whose stand-in summary now fails the schema. On A’s branch both pass. No gate runs verify on untouched demos, so nothing caught it.
  • B reuses post-centric failure copy for links. Example: “Instapaper didn’t accept this post’s link”. A reworded it for links.
  • ✓ Shared styles. A extracted reader-checklist.styles.ts as D14 prefers; B imports WikiPicks’ exports and copies a class.
  • B duplicates the anchor parsing in extract.ts rather than sharing one reader.
  • B adds about 600–900 lines of demo-only tooling.

Where B was better

  • It stops saving after an account-wide Instapaper refusal.
  • Its partial-send toast counts only links the route confirmed. A declined that finding as a rare race.
  • ✓ It kept frontend/scripts/mock-supabase.mjs in sync (+95 lines). A didn’t, and its E2E passes only because the spec’s plan stubs the route.

Size and gates

Production lines added: A 1,428, B 1,431, historical 1,546. New test cases: 101, 121 and 115. Both arms pushed through the pre-push check:slow: 344 Playwright tests, every Storybook snapshot and 102 database integration tests. Both review rounds returned “ship it”. A’s raised 5 findings (2 fixed, 1 raised, 2 declined); B’s raised 7, all fixed, plus one regression that the push gate caught.

Why the orchestrator didn’t save money

  • The lead does most of the reading anyway. To slice a spec and brief agents that can’t ask questions, it reads the spec and the code. To integrate, it reads every returned diff, runs the full gates, reconciles seams and fixes what the gates find. B’s lead made 188 requests, against A’s 187, and its context grew to 480k tokens, against A’s 452k. Writing the code was the part that moved to Sonnet, and on this ticket that wasn’t the expensive part.
  • Cheaper implementers save only on output. Sonnet 5.5’s cache reads cost the same as Opus 5.5’s ($0.20 per million). Long sessions are dominated by cache reads: 54M of A’s main-thread tokens. So “Sonnet does the typing” discounts only the smallest line item. This matches ALF-283’s §5 reprice.
  • Seams are where defects hide. B’s distinctive defects all sit between slices rather than inside one: stale demos two directories away, a design rule one slice re-decided, and parsing duplicated across files. That fits the prior evidence that multi-agent coding works when “writes stay single-threaded” and loses on dependent work.

How much to trust it

  • n = 1. At ALF-283’s observed per-session cost spread (log sd 1.13), one pair can’t estimate a cost ratio with an interval. A 2× gap with a matching mechanism is a strong hint, not a measurement. Quality differences this marginal would need dozens of pairs.
  • Effort. B ran at high and A at medium. If anything this flatters B’s quality and inflates its cost. An effort-matched rerun would likely narrow the cost gap somewhat and the quality gap not at all.
  • The orchestration brief. B followed the implement-epic skill, written for epics. A brief tuned for stories, or one telling the lead not to re-read diffs, might be cheaper. Nobody has written one, and today’s epic lane uses this one.
  • LLM judges. They were controlled for position and family, and their key claims were spot-checked against the branches. They still read diffs, not running software. Both arms passed the same real gates.
  • Contamination. Both arms were told not to read the merged solution. Both needed origin/main locally for the pre-push branch secret scan: B fetched it, and A pointed the ref at the base instead. Neither report shows the solution being read. I didn’t audit their transcripts.

What this settled about measuring sessions

  • get_session → usage.cost_usd includes subagents, with their real output. This was ALF-283’s open question. B’s server total had 279k output tokens; its main thread wrote 131k, and the transcripts recorded only 3.1k of subagent output (placeholders, flagged subagent_usage_partial). The hook leaves such rows unpriced, which is correct. The backfill’s session-record cost is the one to trust for multi-agent sessions.
  • usage refreshes only at a turn’s end, so a mid-run read is stale.
  • A replay on a pre-ALF-310 base has no recording hook. Running the hook’s dry-run from a worktree of main recovers the per-model split.
  • The procedure and its gotchas now live in the llm-evaluation skill, references/replay.md. They cover the base commit, launch prompt, create_session’s missing effort, why every rule goes in the prompt, reporting to the parent and blinding the judge.

Alternatives we’re not taking

An Opus orchestrator with Sonnet implementers for stories

The counterfactual reprice puts it near $25 against $19 for a single agent, before any quality cost from the seams. The architecture doesn’t pay on a story at any lead price we have. It might pay where one context can’t hold the work: an epic.

Run more replays now to get an interval

Each pair costs about $60 plus judging. ALF-283’s power figures say about 20 pairs are needed for a 2× cost ratio, and far more for quality at this margin. The ledger’s production data, an effort trial with arms by ref hash, answers the cost question for free.

Judge the Fable arm against the historical PR

This was the ticket’s first idea. The historical diff sits on a different base, 4013e36, after a rebase onto #399’s migrations. It also carries owner turns and a Sonnet UI subagent, so the judge would be comparing more than the architecture. The fresh Opus replay replaced it as the control. The historical cost stays as a reference row only.

Cost & open questions

  • What this spike spent. About $59 on the two replays. The four judges used 202k, 234k, 375k and 366k subagent tokens. Then this session’s own cost.
  • Does the result hold at matched effort? create_session can’t set effort. Matching it needs the owner to launch from the UI, or a CLI flag the tool doesn’t expose.
  • Does orchestration pay on an epic? Epics are where one context struggles, and that is the only setting with a structural case for it. ALF-283’s structured case review of epic sessions is the instrument.
  • Should check:slow run demo verify on demos a branch’s changes affect? B’s stale demos passed every gate. This is a lint suggestion, not part of this spike.
