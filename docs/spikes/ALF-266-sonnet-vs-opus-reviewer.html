ALF-266 — Sonnet vs. Opus as the adversarial reviewer

Sonnet reviews for a third of Opus’s cost. Replayed on three past PRs, it missed the bug-fix root cause both times, rated down what it found, and added noise.

Where we landed

Keep the adversarial reviewer on Opus. Switching saves about $1 a review. That is real money on small PRs: the original Opus reviews were 8–25% of their sessions’ cost. But most of the saving is Sonnet doing less, not Sonnet being cheaper. It made a third as many requests, and two of its six runs ran no tests. What it gave up was the catch a review exists for. On the bug fix, both Sonnet runs called the fix “correct and complete” while Dispatch still filed work into an archived epic. Every Opus run found that path. One escaped defect like it costs a bug-fix session, which is more than a month of the saving.

This is three PRs with two runs per arm: a case study, not a rate. The recall intervals overlap. If the reviewer’s cost needs cutting, pin its effort before changing its model. Next I’d cut one story: turn these three cases into ALF-283’s defect-recall bench, so the next reviewer question is a rerun rather than a spike.

  1. Catches

    Key defects: Opus 71%, Sonnet 61%. Bug-fix root cause: Opus 2/2, Sonnet 0/2.

    Two blind graders from two model families, scored against what each PR’s author verified. §3

  2. Labels

    Four of six Sonnet verdicts read as “ship it”, both bug-fix runs included.

    Triage acts on severity. Sonnet called the Backlog miss minor; Opus called it major both times. §4

  3. Precision

    Sonnet: two false findings (one major) and 7–10 noise items. Opus: one false sub-claim.

The evidence

Everything below is for whoever builds on this. Acting on the answer needs only what’s above.

The experiment

The ticket asked for three things: find PRs where an Opus review caught real issues, have Sonnet review the code as it stood before that review, and compare catches and cost. For consistent prompting, the reviews should come from after the adversarial-review skill was committed. The owner made two design calls before anything ran:

  • Brief. Each case reuses its original brief verbatim, rather than one rebuilt on today’s skill.
  • Budget. Three cases, two runs per arm: 12 sessions. The account’s seven-day usage was at its warning level.

Arms

  • Sonnet 5.5 × 2 per case: the arm under test.
  • Opus 5.5 × 2 per case, fresh: the control. Without it, a Sonnet miss can’t be told from run-to-run luck, because the historical Opus review is one sample from a different setup.
  • The original Opus review is a reference, not an arm. It produced the ground truth, so it scores near-perfect by construction.

Held equal

  • Code. Each child session started on the PR head as it was when the original reviewer was spawned. Its origin/main was pinned to that review’s base with git update-ref, because today’s main holds the PR’s fix commits.
  • Prompt. One shared preamble, then the original brief verbatim, then the PR description as GitHub stored it at review time. The preamble said: review this commit, don’t read the PR on GitHub, fetch nothing but the base, report only, nobody answers questions, send the report to the parent. For #408 the brief withheld the description, so the replay did too.
  • Environment. The same cloud environment as the originals, with the same tools, so every arm could run the suites.
  • Contamination. An audit of all 12 transcripts found no GitHub tool calls, no WebFetch and no fetch beyond the base. Two Opus runs fetched the review commit itself, which the preamble allows.

Not held equal

  • Effort. create_session takes a model but no effort, so each child ran its model’s default. No tool reports the effort that actually ran. The API defaults are medium for Opus 5.5 and high for Sonnet 5.5, so if anything this favours Sonnet. The original reviewers were subagents, and probably inherited their parent session’s effort: xhigh for #402 and #408, high for #418.
  • Session shape. In production the reviewer is a subagent; each replay was a top-level session. That adds a larger system prompt to both arms equally, and it changes the cache TTL, which §5 reprices.

The cases

The pool was the 22 implementation and bug-fix PRs merged after the review skill landed (PR #386, 2026-09-28) that carry an Adversarial review section. Six were extracted from their session transcripts: #402, #408, #414, #418, #419 and #420. Three were kept. Each has real, author-verified defects, they span the feature, bug and skip-refinement lanes, and their size keeps a review in minutes. #419 and #420 were 1.3–3k code lines. #414 had a single behavioural defect.

Their input side alone, at 7.6M, 7.7M and 4.2M cache-read tokens, comes to at least $2.41, $2.38 and $1.44. Those sessions cost $11.05, $9.46 and $17.99, so the review was at least 22%, 25% and 8% of each.

The briefs were not the skill’s brief

The ticket assumed that once the skill was committed, review prompts would be consistent. They aren’t. Every brief in these cases was written by hand per PR, in the skill’s earlier “be adversarial, hunt for…” style with blocker / major / minor / nit labels. Several also name the edge cases to look at. #418’s brief, for example, lists “items reparented or type-changed… non-task items”, which points at K2 and K3. The current skill text (PR #413) tells the brief to make “nothing blocking” a full answer. No case here used it. The prompt is identical across the arms of each case, so the model comparison is fair. Whether the gap changes under today’s brief is open.

What each run caught

Two graders scored the twelve reports blind against each case’s rubric, as catch, partial or miss, with a quote for each grade. Reports were relabelled R1–R4 in a seeded random order per case, and the key file sat outside the graders’ folder. Grader A ran on Opus 5.5 and grader B on Fable 5.1. Both checked every major claim and every image claim against the commit. They agreed on every key item but one, H2, where A applied the rubric’s rule: a multi-part item with only some sub-points found is partial. No report named H2’s empty popover, so the reconciled grade is partial for all four. ✓ catch · ½ partial · ✗ miss.

Intervals are Wilson 95%. They overlap, and the items aren’t independent: three PRs, each run twice. The H1 split, 3/3 against 0/2, has a Fisher exact p of 0.10. On recall alone, this sample can’t separate the models. §4 is where they differ in kind.

Run-to-run variance is large in both arms. One Opus run missed K2 and K5, both of which the original found, and the other run caught K2. One Sonnet run caught K5, which both fresh Opus runs missed. A single review round is a sample, not a sweep.

Beyond recall: labels, precision, new finds

Severity and verdicts

The author triages on the reviewer’s labels. The skill asks for a failure scenario before anything counts as blocking. So a correct catch rated minor tends to be declined, while one rated major gets fixed.

  • #402. Both Opus runs called the Backlog row major. Sonnet run 1 called it minor, and its verdict was “approve with minor follow-ups. No blockers and no correctness bugs.” The PR description had already scoped the row out, so a minor label would likely have been declined. In production it was labelled major and fixed.
  • #408. Sonnet: “the fix is correct and complete for the reported bug” and “nothing blocker or major”. Opus led both reports with the Dispatch major.
  • #418. Sonnet run 1 said “No blockers found.” Sonnet run 2’s only major was false (below).

Four of six Sonnet verdicts read as “ship it”. In two of them, #408’s, a real major remained. No Opus verdict read as “ship it”, and every major Opus raised was real.

False findings

  • Sonnet, #418, rated major: “the GIF never shows the expanded 80vh frame”. False. All 69 frames were extracted with ffmpeg: frames 20–38 show the frame expanded, and 21–22 show “Collapse plan”. The run had sampled about 12 frames. Acting on it would have meant re-recording a correct demo.
  • Sonnet, #402, minor: “a test that forgot the colour would still type-check”. False, because the prop is required.
  • Opus, #418, inside a correct major: the sub-claim that the GIF “never shows Collapse plan”. False, for the same frames.

Both graders also marked findings as noise: true, but restating the PR or of trivial value. Grader A counted 10 in the Sonnet reports and grader B 7; neither counted any in the Opus reports. The count of valid findings outside the rubric was a wash: A counted Opus 17 and Sonnet 13, B counted Opus 15 and Sonnet 19.

New valid finds

  • Both fresh Opus runs, #418, major: a mid-week plan revision empties the default view. Re-posting a revised plan adds a new weekly_plans row, and the cohort stays on the original id. The midweek-checkin skill posts exactly such revisions. The picker defaults to the newest row, so the view opens on “Nothing has been created from this plan yet”. ALF-195’s spec names the trap (“re-posting a revised plan appends another archive row”), and the API’s latest already routes around it. One run proved it with a scratch test. The original review missed it.
  • Sonnet, #418, minor: the expanded state persists across week switches. Plausible, and not on the rubric.

Neither the #418 revision gap nor the remaining #408 Dispatch story is fixed on main as of this spike. That is the owner’s call, not this spike’s.

Where the gap comes from

Opus costs $1.03 more per review. Priced at Sonnet’s rates, Opus’s own tokens would cost $1.08, so price explains $0.39 of the gap (38%). Priced at Opus’s rates, Sonnet’s tokens would cost $0.68, so behaviour explains $0.79 (77%) measured that way. Either way, most of the saving is Sonnet reading and running less: 3.5× fewer cache-read tokens, 2.4× less output and a third of the requests. Cache reads cost the same on both models, at $0.20 per million, and a long review is mostly cache reads. That is the same depth that found H1.

Against the originals

The production reviews on #402 and #408 read 7.6M and 7.7M cache tokens, about 2.7× the fresh Opus replays. Their parents ran at xhigh. On #418, with a parent at high, the original read 4.2M, within the replays’ range. That fits subagents inheriting their parent’s effort. If so, today’s reviewer costs more than these replays suggest, and the effort a reviewer runs at is a lever we don’t yet set. Claude Code’s subagent docs confirm the mechanism. A subagent whose definition sets no effort “inherits from session”, and the Agent tool takes no effort argument. A .claude/agents/<name>.md definition can pin effort (low to max) next to model. A reviewer agent definition is how the review’s cost becomes a setting, not a side effect of the implementer’s effort.

What a switch would save

About $1 a review at replay volumes, and perhaps $1.5–2 at production’s inherited effort. ALF-283 counted about 45 implementation launches a month, and bug fixes add more, so the saving is roughly $45–90 a month. The bug-fix session behind #408 cost $9.46 on its own. A single escaped root-cause defect, plus the owner’s time to find it, erases about a month of savings. Sonnet missed one in three cases here.

How much to trust it

  • n. Three PRs and two runs per arm. The recall intervals overlap, and the H1 split’s p is 0.10. The direction of every quality signal agrees, but each is a handful of events.
  • The rubric comes from Opus. Ground truth is what one Opus review found and the author verified, so it can’t contain a defect Opus systematically misses and Sonnet finds. Two things temper this. The fresh Opus runs also missed rubric items (K2, K5), so the rubric isn’t simply “what Opus sees”. And Sonnet’s one unique catch, K5, is counted.
  • Effort. Not controlled, and not observable. The defaults favour Sonnet. An effort-matched rerun would need agent definitions that pin effort (§5).
  • Graders. Blind, from two model families, quoting each grade, with every major and image claim checked against the commit. They agreed on all key items but one, reconciled by the rubric’s own rule. Grader A is Opus. Grader B, on Fable, gave the Opus reports slightly more credit than A did, not less.
  • Old brief. Every brief predates the current skill text. A “nothing blocking is a full answer” brief might pull both models’ verdicts toward “ship it”. If it does, Sonnet’s under-labelling would likely get worse, not better.

Alternatives we’re not taking

Switch the reviewer to Sonnet

It saves about a dollar a review and loses root-cause catches, severity calibration and precision. §4 has the evidence.

Two Sonnet reviewers for the price of most of one Opus

Two Sonnet runs cost $0.88, against $1.47 for one Opus. On #408 the union of both Sonnet runs still missed H1, and both called the fix complete. Sonnet’s misses here repeat rather than vary, so a second run doesn’t cover the first.

Sonnet first, escalate to Opus when it finds something

The failure mode is a confident clean verdict on a PR with a real major. That gives escalation nothing to fire on.

Sonnet for small or low-risk PRs

#408 was the smallest case, a 141-line bug fix. It is also where the root cause hid in a path the diff never touched. Diff size didn’t predict where the risk was.

More replays now, to narrow the intervals

A pair of runs is cheap, about $2. The expensive part is building each case: extracting the brief, finding the commit and writing the rubric. That is exactly what a defect-recall bench automates. Build it once (ALF-283’s plan), then rerun.

Cost & open questions

  • What this spike spent. $13.85 on the 12 replays, plus one setup that stalled before the model ran. On top of that: two graders, six transcript-extraction subagents, a transcript audit, and this session.
  • What does the reviewer cost in production? ALF-310’s ledger rows now split tokens by model and by subagent. Reviewer input and cache tokens can be read from them; output can’t (subagent_usage_partial).
  • Does the gap hold at matched effort, or under today’s brief? That is a bench run, not another hand-built spike.
  • Should a single review round be the default? Variance between two Opus runs on one PR was as large as the gap between models. That is outside this ticket, but it is a question for the review skill.
