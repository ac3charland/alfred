ALF-267 — Explore Jev for communication/inbox triage

Jev can’t replace alfred’s classifiers, but as a scorer or gate it fits the Inbox and, plausibly, ranking best; each can be tested cheaply before anything is built.

Revised 2026-09-29: adds ranking of the code backlog and folder tasks, and puts the Inbox and the two-stage Comms gate on firmer ground.

Where we landed

Don’t swap Haiku out for Jev; test Jev beside it, cheapest test first. Ranking is where Jev’s shape fits best and its price edge first clears rounding error: one call can carry a whole list and hundreds of pairwise questions, each answered with a probability. The code backlog is already a curated total order, so a ranker can be scored against it offline in an afternoon (§6). The Inbox comes next: it already logs every override per provider, so a paired shadow run needs no fixtures. For Comms, a gate (Jev shelves only the confident “nothing owed”, Haiku judges the rest) is stronger than I first allowed, since ALF-7 D13 accepts shelving before the model; but it can only lose recall, so score first and replay offline. Begin by reading Haiku’s current override rates. Caveats: I have not seen the ranking tickets, and TypeSafe’s docs were unreachable from this sandbox.

From the official SDK (@typesafe-ai/sdk, 0.6.0 per npm and the J-Mail pin — pre-1.0):

  usage:   { input_tokens, output_tokens }

  • Fit for the Worker. The client uses only globalThis.fetch, AbortController and setTimeout, takes an injectable fetch, and its runtime probe names cloudflare-workers explicitly. nodejs_compat is already on in workers/wrangler.toml. A plain-fetch call is also possible, but the body shape is documented only through these types, so the SDK is the safer contract.
  • Retries. SDK default: 2 retries, 500 ms → 5 s backoff with 25% jitter, on 408/429/5xx and connection errors, honouring Retry-After up to 60 s. alfred deliberately runs Anthropic at a 10 s timeout and 1 retry (workers/src/classifier.ts: REQUEST_TIMEOUT_MS, MAX_RETRIES), sized so two cron ticks cannot pile up; a Jev client would have to be configured to the same arithmetic, not left on defaults.
  • A decision model has fewer ways to fail. ClassifyFailure today has refusal, truncated and unparseable beside the transport and credential classes. A model that generates no text has nothing to refuse, truncate or mis-format, so those three plausibly disappear. Unconfirmed: whether the API can reject content.

Why the Inbox, not Comms, is the better first test

My first draft set the Inbox aside because “there is nothing to measure a swap against”. That confused “no fixtures” with “no instrument”, and it was wrong.

  • The instrument is built. Migration 0029_llm_classifier.sql adds classified_provider, classified_model, classified_prompt_version and classified_guess to items, plus a classification_corrections table with the same provider/model/version columns. A trigger, log_classification_corrections, fires on the first dispatch and diffs the guess against the fields the owner finally chose, in three directions (changed, filled in, blanked). ALF-158 §3 says of the provider stamp that a future comparison “stops needing a fixture harness at all: run both for a fortnight and compare corrections per item”. A Jev arm is exactly that.
  • Free labels, on the same items. Unlike Comms, where a false negative sits unseen on the shelf, an Inbox guess is always in front of the owner, so the final field values are the label. A Jev guess kept in a side column instead of the real fields can be diffed against those same final values offline: both providers scored on identical items, with no live risk. (Needs a column, and the task_items view recreation ALF-158 warns about.)
  • The downstream is already provider-neutral. validateVerdict, mergeIntoItem and the write all operate on a Verdict, and classify() returns a ClassifyOutcome. Only buildRequest and classifyJson are chat-shaped, so a Jev path is one builder that turns the ClosedWorld into questions and one adapter that turns probabilities into a Verdict. That is a smaller change than the Comms one, and a held item_type is simply a question not asked, rather than a schema pin.
  • Lower privacy stakes. Inbox captures are the owner’s own words, which ALF-158 D14 already accepted sending to a third-party API. Comms holds other people’s messages.
  • The objective matches. ALF-158 D8 optimises for precision — a confident wrong label is the failure — and enforces it with a paragraph of prompt (ABSTENTION_RULES). Per-field thresholds on probabilities are that abstention made explicit, and the correction log is where they would be fitted.

What I have not checked: how often Haiku is overridden today. That number decides whether there is anything for Jev to improve (§9, Step 0). One cost to count first: the Inbox sweep shares the two-minute tick, and therefore the 50-fetch budget, with the Comms judge, and SWEEP_LIMIT is 10 items.

The seam

classifier.ts opens by claiming to be “the only module allowed to import @anthropic-ai/sdk, so swapping providers later touches this file and nothing else”, and ALF-158 D2 tells story sessions to keep the swap “a contained change”. That holds for another chat-completions provider. It does not hold for Jev: classifyJson(env, request: ClassifyRequest) takes { system, user, schema }, and Jev takes neither a system prompt nor a JSON Schema. Both request builders (prompt.ts buildRequest, comms/prompt.ts buildCommsRequest) would need Jev-shaped siblings built from the same ClosedWorld, roster, rubric and thread. The provenance half is ready: both sweeps stamp PROVIDER = 'anthropic' on every verdict “so a future provider comparison is a query, not a migration”. For Comms, what has no home yet is the probability distribution (the Inbox’s classified_guess jsonb could hold one); J-Mail (a community Jev integration) stores “full probability distributions and the model version” for exactly the reason that thresholds can then change without re-inference.

What Jev would add, and what it would cost

The real upside

  1. Thresholds instead of prose. ALF-158 D8 (abstain unless the text is clear) and ALF-7 D7 (“uncertainty resolves into the queue and down to Today”, never ASAP; prompt rules 4 and 5) are requests made in words, enforced by nothing but the model’s compliance. With noul and confidence they become numbers: queue iff P(owes reply) ≥ t, asap iff P(asap) ≥ thi. Stored distributions let those thresholds be tuned offline against the correction log with no re-inference.
  2. A second, differently built opinion on the failure nothing else sees. ALF-7 §6 is explicit that the correction rate “measures the demotion rate” and is “structurally blind” to false negatives, and that the re-run fixtures are “the only instrument in this epic that ever measures a false negative”. ALF-7 Q8 asks whether the FYI shelf needs a forcing function and floats “a small periodic sample in the existing weekly review”. Disagreement sampling is a principled version of that: the set where Haiku said fyi and Jev says P(owes) is high is small and worth an adjudication. The premise that the two models’ errors are independent is an assumption; both may miss the same ambiguous personal text.
  3. Structural separation of instructions from sender text — rules live in question definitions, the message lives in state. Plausibly helpful against injection, but third-party reviewers list adversarial input as a weakness and alfred’s current defences (stripForgedLiterals, the message fences, prompt rule 10) are prompt-level and would not carry across. Unproven either way.

The costs beyond dollars

  • A second processor for the most sensitive data. ALF-158 D14 accepted that captures leave the box. Comms mirrors other people’s texts and mail. Whether a direct-API account gets any retention commitment at all is unverified; the only statement found is that zero data retention is an enterprise option obtained through a DPA. This is the owner’s call, not a technical one.
  • The subrequest budget. COMMS_SWEEP_LIMIT = 6 was sized to spend “~42” of the Free plan’s 50 outbound fetches per invocation. A shadow call per message adds six, landing at about 48 — too close to a ceiling whose breach “throws part-way, and a half-swept tick bills model calls for verdicts it never managed to store”. The shadow would need a limit of 5 or its own trigger; wrangler.toml notes the plan allows five cron triggers and four are used.
  • An alias that floats. The SDK default model is jev-latest. If provenance stamps the requested alias, the stamp stays constant while the weights change. Stamp SystemOneResult.model, the resolved name.
  • Housekeeping. A new Worker secret (TYPESAFE_API_KEY) beside the list in the wrangler.toml header, set by hand with wrangler secret put like ANTHROPIC_API_KEY, and a pre-1.0 SDK dependency.

Comms: the two-stage gate

The proposal: Jev scores each message first, and only messages it thinks likely need a response go on to Haiku. There are three designs hiding in that, and they behave differently.

DesignJev decidesHaiku decidesVerdict
Gate (the proposal)Shelve only when P(owes a response) < ε; otherwise pass onEverything passed on, in full: tier, ask, reasonViable; see below
Tier by Jev, words by HaikuThe tierAsk and reason for queued messagesRejected (§10): the reason explains a decision Haiku did not make
OR-check (shadow)Nothing yet; scores in the backgroundEverything, as todayA high P(owes) on a shelved message is flagged for review

My first draft dismissed the second design and called it “the cascade”. That is not what was proposed. In the gate, Haiku still makes and explains every decision it makes, so the audit-trail objection does not apply to it. And the gate has a precedent I should have weighed: ALF-7 D13 already files header-detected bulk mail on the shelf before any model call, because “a model call to decide that is pure waste”.

D13’s three conditions carry over

  • Strong signals only. Shelve only in the confident tail, P(owes) < ε with ε small and fitted on data; anything ambiguous goes on to Haiku. That is ALF-7 D7’s rule — uncertainty resolves into the queue — written as a number.
  • Record that the filter, not the model, shelved it. A gate-shelved row has no verdict and no reason and must say so. The mechanism exists: ingest.ts writes judged_by: 'filter' with a filtered_reason, and frontend/lib/comms/markers.ts flags any row whose reason is set. But FilteredReason is 'newsletter' alone (types.ts), so a second value needs a type change and, very likely, a migration for its CHECK constraint (not confirmed).
  • Never filter a sender on the people list. Check the roster in code before calling Jev, which also saves the call. D13’s own filter already builds rosterHandles for this.

What the gate buys, and what it risks

  • It can only lose recall. A gate removes messages from Haiku’s consideration and can never add one to the queue. ALF-7 D7 says recall is the number that decides, and D13 calls a wrongly filtered real message “the expensive one” — it “never reaches the classifier”, “where no amount of tuning the rubric can reach it”. The OR-check goes the other way: it can only add. Neither is free, but they are not symmetric, and the spec sides with the second.
  • The saving is small. Comms is about $3.30 a month on Haiku. If a third to a half of messages are confidently “nothing owed” (28 of the 68 fixtures are fyi, but the header filter has already removed newsletters, so real traffic will differ — this is an assumption, not a measurement), the saving is roughly $1.10–1.65 a month. Subrequests are roughly neutral: a gated message skips Haiku and the verdict insert, so it is cheaper than today’s ~5, while a passed one costs one more. Count against the store calls before touching COMMS_SWEEP_LIMIT.
  • The boundary is where Jev is reported to be weakest. “Silence would be a lapse” (rule 1(b), the ALF-244 fix) is an indirect ask, and “just landed, flight was brutal” is the kind of text a “does this need a response” question is most likely to score low. This is the specific case the Step 3 screen tests.

One dataset settles all three designs

A shadow run that stores Jev’s P(owes) for every message lets the gate, the OR-check and a future tier-by-Jev design be replayed offline at any ε: how many Haiku calls the gate would have saved, and how many messages Haiku queued — or the owner later corrected — that it would have shelved.

It also offers a false-negative proxy the spec does not mention. Outbound messages are stored with their thread_key, and comm_record_reply drains only queued rows, so an owner reply after a shelved message leaves no mark today. But the rows are in comm_messages for 60 days, so a query can find shelved inbound messages followed by an owner reply in the same thread. That is my inference from store.ts and the schema, not something I ran, and a reply may answer something else in the thread: a lead, not a label. If it holds, it contradicts the spec’s claim that fixtures are the only false-negative instrument.

Ranking the backlog and folder tasks

What I could and couldn’t read. The ranking spikes are unmerged tickets, so I have not seen their criteria, comparison method or list sizes. This section covers how Jev would apply to the designs a ranker could take, using what the repo shows about ordering today. It should be re-checked against the tickets’ choices when they land.

What is ranked today

  • The code backlog is a curated total order. code_items.priority is a double precision rank, “lower = higher priority”, unique. Project-scoped moves insert at the midpoint of two neighbours (0014), and a respace runs when the floats run out (0031, which fixed an outage where every code dispatch failed). A new story lands at the top by default (0012), and the owner moves stories with swap and jump-to-top/bottom (0009). The whole order is the owner’s own judgment, one number per story.
  • Folder tasks have three buckets, not an order. priority is a nullable enum, high < medium < low (0010). A folder sorts by priority or by due date, each falling back on the other and then on created_at, oldest first (frontend/lib/tasks/task-sort.ts). sort_order (0018) orders subtasks only — its comment says roots ignore it — so within a bucket and a due date, top-level tasks are ordered by age alone.

Those are two different jobs. On the backlog a ranker either slots a new story where it belongs instead of at the top, or re-ranks the list; a full re-rank would overwrite the owner’s curated order, so slotting is the natural job. For folders, the bucket is what the Inbox classifier already guesses per item (the score row in §3), so what is left is ordering within a (priority, due date) tie — usually a small group.

Why Jev’s API shape suits ranking

A chat model compares items either one pair per request, which costs a call each, or many in one prompt, where the answers contaminate one another — the objection ALF-158 D18 makes to batching classifications. Jev takes one shared state and any number of named questions and answers them together, a probability each. If that holds at scale, comparisons cost rounds rather than calls:

DesignJev questionsCallsWatch for
Score in contextOne score per item over a state holding the whole list; rank by expected score Σ s·P(s)1 per listScores are absolute and may drift between calls; test stability
Pairwise in contextA choice between two ids per pair; aggregate client-side by expected wins or a Bradley–Terry fitpairs × ~30 tokens ÷ the limitPosition bias, so ask both orders (double the questions). The aggregation is deterministic and therefore testable in ALF-158 D12’s sense
InsertionA new item against ~8 evenly spaced anchors in one call; place by wins, then one refining call1–2 per new itemBinary search is sequential for a chat model; here it takes two rounds

Soft preferences are the other real gain. Jev returns P(A over B). The Anthropic Messages API returns text, so a Haiku comparison arrives as a hard choice (I found no token-probability output in the repo’s anthropic-api skill; I did not check the API reference). With probabilities, an intransitive cycle is a weak preference to average out rather than a contradiction to break arbitrarily.

Untested, and it is the crux: whether a pair’s answer changes with the number of other questions in the call. The most questions per call in any source read is six (J-Mail), and the 64k-token limit is a third-party figure. Test a pair asked alone against the same pair among 400 others, in both orders.

  • Volume is real under exactly one design: refreshing a large list by pairwise comparison. Merge-sorting 500 items daily is about $60 a month on Haiku against $2.26 on Jev with a call per comparison — the first place in this document where Haiku’s cost is not a rounding error against the ~$4.50 the whole app spends now. The Workers Free plan’s 50-fetch cap would also need ~90 invocations for 4,483 standalone calls; in-context batching is what lets a full refresh fit in a few calls at all.
  • The cheaper way round volume is to compare less. One listwise Haiku prompt ranks 100 items for under a cent, and inserting a new item takes ~10 comparisons: about half a cent on Haiku ($3.24 a month at 20 new items a day) against $0.12 on Jev. Whether listwise ranking stays reliable past ~100 items is commonly reported to degrade; I did not measure it. So Jev’s price case rests on the ranking spikes choosing a full-refresh pairwise design. If they choose slotting or listwise, the case is soft preferences and rounds, not price.

Where Jev is weaker for ranking

  • The criterion is the hard part, and it is the owner’s. What comes next mixes deadline, dependency, effort, epic context and whatever the week’s plan says. Jev sees only what is put in its state, and “X must precede Y” is a multi-step inference where its reviewers say it decides in single steps.
  • Don’t ask Jev to compare dates. Priority and due date are structured fields the app already sorts on, and date comparison is a reported weak spot. Let code order on the structured keys and use Jev only for the residual — the ties.
  • No reason for an order. The backlog already has direct override (swap, jump to top), but a ranker gives the owner nothing to argue with.
  • Stability. Reruns shift confidences, so a ranker that recomputes daily can reshuffle a backlog the owner curated. It needs hysteresis (move an item only past a margin) or pairwise probabilities cached per item version.
  • No move history to learn from. Every manual swap is a preference a ranker could learn, but I found no history table and the swap and move RPCs (0007, 0009) contain no insert; only the resulting rank persists.

How to test it: the backlog is its own ground truth

Because the backlog is a curated total order, any ranker can be scored against it offline — Kendall’s τ or plain pairwise agreement — with no shadow period, no live writes and no fixtures to hand-write, using only the owner’s own story titles. Baselines to beat: random, and creation order; new stories start at the top, so recency is already baked into the order and will be a stronger baseline than it looks. The score is capped by how stale and recency-shaped the order is, so the informative number is Jev against Haiku on the same items, not either against 1.0. Cost at 100 stories: about a cent on Jev, about $2 on Haiku with a call per pair. Folders have thinner ground truth — three buckets and a due date — so their test is agreement with the existing priority labels, which is the Inbox problem again.

Verdict

Ranking is the best structural fit for Jev in alfred: decisions under a rubric over given items, no text to write, probabilities that matter, and a call shape that turns comparisons into rounds. It is also the only place Jev’s price advantage clears rounding error, and only under a full-refresh pairwise design. But the designs are unwritten, and the two natural jobs in this codebase — slot a new story, break ties inside a folder bucket — need few comparisons, where Haiku is already cheap. The offline backlog replay is the cheapest experiment in this document, and it settles quality before any volume argument matters.

A test plan, if the owner wants one

Not a spec — the shape of the cheapest experiments, in order of cost, with stop conditions proposed rather than settled.

Step 0 — read the incumbent’s baseline (free, no Jev)

Group classification_corrections by field, direction and provider, and comm_corrections by kind, over the weeks since each shipped. If Haiku’s override rate on a field is already low there is little for Jev to improve; if folder_id or item_type is overridden often, that is the opening. I could not query production from this sandbox, so this number is missing from the findings.

Step 1 — replay a ranker against the backlog (offline, own data)

Once the ranking spikes fix a criterion, score Jev and Haiku against the current backlog order for one project (§6): all pairs in both orders for Jev, a listwise prompt and a merge sort for Haiku, with random and creation order as baselines. About two cents of Jev and a couple of dollars of Haiku at 100 stories. Stop if Jev does not beat creation order, or if a pair’s answer changes with the number of other questions in the call.

Step 2 — the Inbox paired shadow (first live test)

A Jev guess stored in a side column, never written to the fields; questions built from the live ClosedWorld, one choice per id field with the owner’s folder descriptions as criteria, a score for priority, no question for a held type. Two to four weeks; at 20 captures a day that is 280–560 paired items. Compare per field: agreement with the value the owner finally chose, and whether Jev’s probabilities separate right from wrong (precision at each threshold). due_date is excluded. Stop if Jev’s confident answers are overridden as often as Haiku’s, or if its probabilities do not separate right from wrong.

Step 3 — a one-afternoon Comms screen, no personal data

workers/scripts/comms-eval.ts already runs every fixture through classifyJson and scores it with scoreRun (queue recall, asap precision, Wilson intervals). Add a Jev path: state = account, sender with roster marker, received stamp, today’s date, thread and message; three questions — noul “does the owner owe this person a response”, noul “is someone blocked or is a deadline inside a few hours”, and score 0–3 for the tier. Run each fixture twice. Cost: pennies, on synthetic messages. Stop if queue recall falls below Haiku’s, or if it misses the priority-roster, deadline-hours and thread fixtures (spouse-call-me, the text-* family).

What that screen cannot tell you

I counted the fixtures with node --experimental-strip-types over fixtures.ts: 68 in all — asap 10, today 25, whenever 5, fyi 28 — of which 40 are queued, 4 carry a thread, and the longest body is 161 characters. No adversarial cases and nothing email-length. With five whenever cases it cannot rank two models; it can only catch a gross failure, which is what it is for. (ALF-7 §6 budgets roughly 200–400 tokens for a real email body.)

Step 4 — the Comms shadow, only if Step 3 passes, and only with the owner’s privacy sign-off

Four weeks of real traffic, Jev scoring alongside Haiku with P(owes) and P(asap) stored, nothing user-visible except a short weekly list of disagreements. Then replay offline (§5): the gate at several ε, the OR-check, and the shelved-then-replied query. The owner adjudicates the disagreement list; that is labelled false-negative data nothing else produces.

Alternatives we’re not taking

Replace the Comms judge with Jev

Ruled out by ask and reason, both of which the UI shows and the spec treats as load-bearing.

Tier by Jev, then Haiku writes ask and reason for the queued

The reason would be written after the fact for a tier Haiku did not choose: a confabulated audit trail, which defeats the purpose ALF-7 D11 versions everything for. It puts two vendors in the hot path for a saving of about $1.40 a month. This is not the gate in §5, which stays open.

Swap the Inbox classifier outright

The best field fit, but due_date is a gap, Haiku’s baseline has not been read, and the saving is about $1.16 a month. The paired shadow in §9 comes first; a swap is what its result would justify, not a starting point.

Reach Jev through a gateway (Vercel AI Gateway, Cloudflare, OpenRouter)

Adds a hop and a second data policy that applies on top of TypeSafe’s. The jevmail README records a gateway free tier of 5 calls per 5 minutes, so real use needs the paid tier. Cloudflare’s catalogue listing was seen only as a search-result title. Worth a look only if one billing or logging surface matters more than one fewer hop.

Use Jev for the deterministic newsletter header filter

ALF-7 D13’s filter is free, deterministic and explainable already.

Cost & open questions

Effort. Step 0 is two queries. Steps 1 and 3 are each a script and an afternoon. Step 2 is a migration for the side column (with the task_items view recreation), one Jev request builder and adapter, a second secret and a tick-budget check. Step 4 adds a migration for the distribution, a UI list and, if a gate follows, a new filtered_reason. Each is a real story, and none should be cut before the step before it passes.

  1. What is the two-stage design for? If the goal is cost, the ceiling is about $1.40 a month. If it is fewer noisy rows, or keeping machine mail away from Haiku, the correction log should show that first; the motive sets ε.
  2. Does Jev use a long prose policy at all? The owner’s rubric, the people roster and the corrections-as-examples loop (ALF-7 D11, ALF-158 D16) all assume in-context adaptation. Jev’s weights are reportedly identical for every customer, so putting text in instructions or state is the only personalization route, and whether it moves the answer is untested. This decides whether the learning loop can live on Jev.
  3. Is a second processor acceptable for message bodies, other people’s included? And what are default retention terms for a direct-API account? Needs TypeSafe’s DPA and privacy page, which this sandbox could not reach.
  4. The unchecked vendor claims. Limits, rate limits, pricing for output tokens, whether state handles JSON well, what jev-latest resolves to. A session with normal network access should read docs.typesafe.ai (in particular /models and the SDK page) before the first step that calls it.
  5. Calibration on this owner’s traffic. The 98.2%-above-0.6 figure is one person’s synthetic support inbox. Thresholds should be fitted on alfred’s own correction log and disagreement list, not borrowed.
  6. Where the shadow call runs. Inside the existing judge tick at a lower per-tick limit, or on the last free cron slot. Both have costs (§4).
  7. Haiku’s current override rates. Step 0 above; not read here.
  8. Which comparison design will the ranking spikes pick, and at what list sizes? Full refresh by pairwise comparison is the only design where Jev’s price matters; slotting and listwise make Haiku cheap enough (§6).
  9. Does a pair’s answer depend on the other questions in the call? The whole in-context idea rests on it, and no source read tried more than six questions.
  10. Where would a within-bucket folder order live? Top-level tasks have no order column beyond priority, due date and age (0010, 0018); a ranker that produces one needs a home for it.
