Spike · findings · ALF-283

ALF-283 — Research existing frameworks/techniques for evaluating model performance

For the Code module's coding sessions, how should alfred decide with evidence rather than impressions which subagent architectures the launch prompts ask for, and which models and effort levels to default to? Can we reuse an existing framework, or should we hand-spin one from the field's practice?

Scope. The primary subject is the Claude Code on the web sessions that alfred's Code module launches. Every session starts from a prefilled link that frontend/lib/code/links.ts builds for one of eight lanes, and every session ends in a PR carrying the alfred block. "Model performance" here means one of the following changes to such a session:

  • the session's model
  • its effort level
  • the subagent architecture its prompt asks for
  • the prompt's wording

The Worker's own LLM features (Inbox classifier, Comms triage, Reader summaries) are secondary. §6 condenses what this spike found about them.

1 · Where we landed

Don't adopt an eval framework as the foundation. alfred already produces most of the data an evaluation needs:

  • Every Code-module PR links its session.
  • Every session record carries its model, effort level, token usage and an API-equivalent cost_usd, and it is still readable after the session is archived.

So first build a thin session ledger that joins ticket, launch, session and PR outcome. Then answer each question with the cheapest instrument that can actually resolve it at alfred's volume:

  1. Effort and model defaults. Use the ledger. Cost differences show up within weeks. For quality, run a non-inferiority check (the cheaper arm is acceptable unless the guardrails show it is clearly worse), not a superiority test.
  2. Launch-prompt instructions, such as the review round or the clarification gate. Use randomised arms in the launcher, assigned per ticket and recorded at launch. It stays free and ToS-clean, because a human still clicks every launch.
  3. The adversarial reviewer: keep it, which model runs it, and how it is briefed. Use an offline defect-recall bench made of real escaped bugs traced back to the PRs that introduced them, plus seeded bugs the gates provably miss. This is the one place an existing tool fits: claude plugin eval.
  4. Epic orchestration. Epics are too rare to test statistically. Review each epic session as a structured case study against the prior evidence, which is unusually one-sided here.

Reserve a full ticket-replay bench (SWE-bench-style, Harbor-run) for a single high-stakes decision the cheaper instruments leave open. It costs real money and months of setup.

Three things the question takes for granted that the evidence doesn't support:
  1. Today's default is itself an untested choice. Every session sampled runs Opus 5.5 at xhigh effort. Anthropic documents medium as Opus 5.5's default and says "tuning effort is often a better lever than switching models". The cheapest, highest-leverage first experiment is effort, not the model or the architecture.
  2. The review round's findings are not evidence of its value. Claude Code's own docs warn that "a reviewer prompted to find gaps will usually report some, even when the work is sound". A count of findings measures diligence. What would show value is recall (seeded and real bugs caught) and precision (findings you agree were real).
  3. Most quality questions can't be settled at this volume. Only large gaps are detectable, around 85% vs 50% success with 20 sessions per arm (§2.3). So the realistic decision rule is "take the cheaper option unless a guardrail trips", backed by reading transcripts. Proving the better option better is out of reach.

2.2 · The history, measured

  • Volume. About 390 PRs since the repo was created on 9 June 2026, or roughly 100 a month across every lane and phase. Implementation, bug and bypass launches are a fraction of that.
  • Model mix. All three sessions sampled ran claude-opus-5-5 at xhigh, including this one, and cost $9.15–9.70 at API-equivalent prices. If that holds across the history, the past offers no natural variation to compare against: every arm has to be created on purpose.
  • The review round is recorded in 14 merged PR descriptions (search: "Adversarial review" in the description). Some predate ALF-282 as ad-hoc reviews. On the two ALF-281 PRs (#389 and #390), the round came back after merge with 1 major, 9 minor and 4 nit findings. All were fixed, except that one was only partly fixed, and a separate aside was declined. That is one real bug the gates had passed, and an anecdote, not a rate.
  • Escaped bugs. There are 67 merged PRs titled fix(…), the raw material for the reviewer bench's real-defect cases.

A full backfill joins every PR to its session record (model, effort and cost by lane) and is being added to this section.

Read it this way: at alfred's volume, cost is measurable and quality mostly is not. A 2× cost difference is visible within a few weeks. A 20-point quality difference needs roughly 80 sessions per arm in production, or about 180 replayed sessions. Hence the cost-first, non-inferiority decision rule.

The ledger still earns its keep on quality in two ways:

  • It bounds how much worse the cheaper arm can plausibly be.
  • It points you at the transcripts worth reading.

2.4 · The prior evidence on the two questions

Evaluation budget should go where the prior is uncertain. For architecture it mostly isn't:

PatternWhat the evidence saysSo evaluate…
A fresh-context reviewer subagent (the ALF-282 step) Supported.
  • Claude Code's best-practices docs: "A fresh context improves code review since Claude won't be biased toward code it just wrote."
  • Self-correction without external feedback is unreliable (Huang et al. 2023).
  • LLM judges favour their own generations (Panickssery et al. 2024).
  • A trained critic caught inserted bugs better than paid human reviewers (CriticGPT, 2024).
Caveats: reviewers over-report, and an Opus reviewer of an Opus-written PR is a same-family check, not a cross-model one.		 Which reviewer, and briefed how, measured by recall and precision. Whether to have one at all is the less open question.
Orchestrator plus parallel implementer subagents (the epic lane) Weak for coding.
  • Anthropic's multi-agent research post: "most coding tasks involve fewer truly parallelizable tasks than research". Multi-agent systems use about 15× the tokens of chat.
  • Cognition's revised view: multi-agent works "when writes stay single-threaded".
  • Claude Code's agent-teams docs: for "sequential tasks, same-file edits, or work with many dependencies, a single session or subagents are more effective".
  • MAST (Cemri et al. 2025): gains over single agents are "often minimal".
 The case review below, especially slice independence (shared files, integration fixes) and cost. Don't spend a replay budget here.
Cheaper implementer subagents (CLAUDE.md's tier rule) Anthropic frames an orchestrator with lower-cost workers as a cost pattern. In its research-system post, an Opus 4 lead with Sonnet 4 subagents beat Opus 4 alone by 90.2%, but that is a research eval, not coding. Only if the epic lane survives its case review. Then use the ledger's cost with a rework guardrail.
Effort level Anthropic's docs describe xhigh as "deeper reasoning at higher token spend". Opus 5.5 defaults to medium, and max is "prone to overthinking; test before adoption". First. It is a one-click, per-session change, and the ledger shows its cost at once.
Model: Opus 5.5, Sonnet 5 or Fable 5.1 Public leaderboards rank the model plus scaffold on someone else's tasks, and Terminal-Bench submissions show the scaffold moves results as well as the model. Routing and cascade work (FrugalGPT, RouteLLM) argues against a flat "always the strongest". Per lane. Refinement, spike and bug differ in how much judgement they need.

2.6 · The practices worth taking

fetched means the primary page was read in this session. snippet means the claim rests on search-result text, because this container's proxy blocks the domain (arxiv, metr.org, cognition.com).

P1 · Randomise per ticket, and don't trust felt speed.

In METR's 2025 randomised trial, each of 246 real issues was randomly assigned AI or no AI. Developers expected a 24% speed-up and reported a 20% one afterwards, but were measured 19% slower. Impressions of "this setup feels better" are exactly what randomisation exists to overrule.

METR, 2025 snippet

P2 · Grade mergeability, not only tests.

In METR's 2026 study, maintainers' acceptance of test-passing agent PRs ran about 24 points below the automated score. Roughly half of the passing PRs would not have been merged. For alfred, the PR's actual fate (merged, reworked, reverted, bug filed) is the grade.

METR, "Many SWE-bench-passing PRs would not be merged" snippet

P3 · Build a bench from your own history, SWE-bench-style.

A task is a base commit, a problem statement and hidden tests. The tests are split into FAIL_TO_PASS (fail before the fix, pass after) and PASS_TO_PASS (must keep passing). alfred's merged implementation PRs already carry the spec (the problem statement) and the tests that pinned it. Prefer tickets merged after a model's training cutoff: this repo is public, so older solutions may already be in the training data (SWE-rebench, SWE-bench Live).

SWE-bench repository fetched; SWE-rebench and SWE-bench Live snippet

P4 · Isolate trials, run several, and choose pass^k where consistency matters.

"Each trial should be 'isolated' by starting from a clean environment". Use pass^k ("all k trials succeed") "for agents where consistency is essential". Start from "20–50 simple tasks drawn from real failures", and "read the transcripts".

Anthropic, Demystifying evals for AI agents fetched

P5 · Measure a reviewer on bugs you know are there.

CriticGPT was evaluated on code into which people had deliberately inserted subtle bugs ("tampering"). The software-engineering version with real bugs is SZZ: trace the lines a fix deleted back to the change that last touched them, which is the change that introduced the bug. alfred has 67 merged fix(…) PRs to trace, and Stryker is already set up to generate mutants that survive the test suite. Those are, by definition, bugs the gates miss.

OpenAI, LLM Critics Help Catch LLM Bugs; Śliwerski, Zimmermann & Zeller 2005 snippet; the stryker skill in this repo

P6 · Pay only for complexity that demonstrably helps.

"Consider adding complexity only when it demonstrably improves outcomes." Multi-agent token cost is about 15× that of chat, and "token usage by itself explains 80% of the variance" in Anthropic's research eval. An architecture that costs more has to beat simply spending those tokens on one agent.

Anthropic, Building effective agents and multi-agent research system fetched

P7 · Small n means intervals and paired tests on every number.

Report the standard error or interval with each score. When two arms answer the same items, test the paired difference. The Anthropic statistics post and the Wilson and McNemar machinery in §6 apply unchanged.

Anthropic, A statistical approach to model evaluations fetched

The defect-recall bench (sketch)

  • Cases (target 15–20).
    • Real: for a merged fix(…) PR, find the PR that introduced the bug (SZZ, then an owner check). The case is that PR's head, with the bug still present.
    • Seeded: take a merged PR and apply one Stryker mutant that survives the package's tests, inside the diff. Such a mutant is invisible to the gates by construction.
    • Add a few requirement misreads that you write by hand, because mutants never model misreading the spec.
  • Runner. The adversarial-review skill, packaged as a plugin with the repo's review-relevant conventions inside it (plugin runs don't load CLAUDE.md). A scaffold_script checks out the case, and --model selects each arm. Run 3 times; ablation none, since a "no reviewer" baseline is meaningless.
  • Graders. Did the report name the planted or real defect at its file, and give a correct cause? Use an llm grader with a stronger --judge-model, plus regex on the path. Estimate false positives by owner labelling of a sample of findings on clean PRs.
  • Arms worth testing.
    • Reviewer model: Opus 5.5, Sonnet 5 or Fable 5.1.
    • Briefing: cold, versus with the implementer's summary.
    • One reviewer, versus two cheaper ones with different focus areas.
  • Cost. A review run is a bounded task, minutes rather than hours. 20 cases × 3 runs × 3 arms is 180 runs. The docs say plugin eval counts against plan usage, and --max-cost-usd caps the list-price estimate.

Files a later story would touch

  • frontend/lib/code/links.ts: a prompt-version constant per lane, an arm registry, and armFor(ref), a stable hash. The launcher shows "launch with model · effort" when an arm names one.
  • database/migrations/: a code_launches table, one row per launch click (ref, lane, arm, prompt version, launched_at). It is append-only, so relaunches keep their history.
  • lib/stores/code-store.tsx openClaudeSession: insert the launch row next to the state write it already awaits.
  • tools/session-ledger/: a TypeScript CLI run from a Claude Code session, which has the session MCP. It joins launches, PRs and session records into JSON, and prints per-arm cost and outcome with Wilson intervals, reusing the §6 statistics.
  • evals/reviewer/, or a plugin directory: the defect-recall cases, graders and scaffold scripts.

Suggested order (each step pays for itself)

  1. Backfill the ledger from history. It is read-only and needs no product change. It answers "what does each lane cost today, and how often is it reworked?"
  2. Run an effort trial on one lane: xhigh against the model's default medium or high, alternated by ref hash. Implementation and bug fixes have the most volume.
  3. Record launches (the table and the prompt versions) so future arms are clean.
  4. Build the defect-recall bench, then decide the reviewer's model and brief.
  5. Review each epic session as a case study as epics come up. Revisit the orchestrator only if the case reviews disagree with the prior.
  6. A replay bench, only if a model-default change is on the table that the ledger cannot bound.

4 · Sidebars: appealing alternatives we're not taking

Build the replay bench first (Harbor, or Inspect with inspect_swe)

It is the most rigorous option. It gives paired comparisons on the same tickets, hidden tests and clean isolation, and Harbor runs Claude Code on private task sets.

Why not first:

  • alfred's gates need Docker, a Postgres cluster and Playwright's Chromium inside every task image.
  • Runs are API-billed. At the API-equivalent cost of the sessions sampled here (about $9–10 each), 180 sessions is about $1,700 for about 75% power on a 20-point gap.
  • The interactive gates ("ASK ME HERE") have to be stubbed, which changes the very prompt under test.

Revisit if a model-default change is proposed that the ledger's guardrails can't settle. Harbor is Apache-2.0 and runs Claude Code natively.

Use claude plugin eval for whole tickets

It is first-party, counts against plan usage, gives multiple runs and a baseline, and publishes an HTML report.

Why not:

  • Each run is capped at 200 turns and one hour. The sampled implementation sessions ran for hours of wall clock and used about 300k tokens of context.
  • The Bash sandbox blocks the network unless you grant domains.
  • CLAUDE.md and skills don't load, so it isn't testing the real launch.

It fits the bounded reviewer task, so that is where it's used.

Pick the default model from public leaderboards

Why not: SWE-bench and Terminal-Bench rank a model plus a scaffold on other people's repositories, and the scaffold changes move the results. They say nothing about alfred's conventions, gates, or the clarification gate that tells a session to stop and ask. They are a prior, not a decision.

A METR-style randomised trial with a no-AI control

Why not: the question is which agent setup to use, not whether to use one. Randomising between arms keeps P1's protection against felt speed without the cost of a control group.

Score PRs with an LLM judge instead of real outcomes

Why not: the real outcome (merged, reworked, a bug filed) is free and is ground truth. A judge adds bias (position, verbosity, self-preference) and cost. Judges belong where there is no ground truth: the bench's grader, validated on your labels.

Agent teams for epics

Why not: it is still experimental and off by default. The docs themselves say teams cost "significantly more tokens" and lose to a single session on dependent work, which describes an epic.

Automating launches to raise n

Why not: automated use of the subscription is off the table (code-module spec §1). The honest ways to get more n are time, or API-billed offline benches.

Open questions

  • Can plan usage, rather than dollars, be observed? Anthropic publishes no per-model plan multiplier. cost_usd is the best proxy, but a Max plan's real constraint is its limit window. Watch rate_limit_info in the session record.
  • Does usage include subagents? The evidence here is only an inference. If it doesn't, the review round and epic implementers are under-counted.
  • Is the session-record API reachable outside a Claude Code session? Today the ledger has to run where the session MCP exists. That's fine for a manual instrument, but it blocks a Worker cron.
  • How is owner intervention counted? The number of your turns mid-session is the clearest "needed a human" signal, but it isn't in the session record. The transcript events may carry it; that needs checking.
  • Is running claude plugin eval on the subscription sanctioned? The docs say plan usage. Spec §1's constraint concerns third-party automation of the subscription, and this is Anthropic's own CLI, run by you. It still needs your confirmation before any bench is built on it.

6 · Secondary: the Worker's own LLM features

The first version of this spike covered these, and its findings stand:

  • Keep the hand-built harness and adopt no framework. npm run eval:comms -w workers already reports its directional metrics (queue recall, asap precision) with Wilson intervals, which the TypeScript frameworks don't. A prototype showed that promptfoo 0.123.1 (2.0 GB installed) and Evalite 1.0.0-beta.16 can both drive alfred's real buildCommsRequest, but neither computes a paired comparison.
  • Add four things.
    • Variants × fixtures × k = 5 trials. temperature is deprecated, models after Opus 4.6 reject anything but 1.0, and the SDK exposes no logprobs.
    • Paired statistics: exact McNemar, and a fixture-clustered bootstrap.
    • A dev/holdout split.
    • A first Inbox classifier suite, seeded from classification_corrections.
  • Labels are the constraint. At 68 comms fixtures, a prompt change must flip 6 fixtures one way and break none to clear p < 0.05. That argues for growing the set past 150 from real traffic.
  • The Reader's free text: blind pairwise review by the owner first. Add an LLM judge only once it has been validated on TPR/TNR.

The statistics layer (Wilson intervals, exact McNemar, paired bootstrap) is the same code the session ledger needs. Build it once in a shared place.
