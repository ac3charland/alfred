Spike · findings · ALF-283

ALF-283 — Research existing frameworks/techniques for evaluating model performance

How should alfred compare prompts on the same model and task, and models on the same prompt and task? Adopt an existing framework, or hand-spin one from the field's best practices?

Scope. Model performance means alfred's three single-call LLM features in workers/:

  • the Inbox classifier (claude-haiku-4-5, six nullable fields, PROMPT_VERSION = 3)
  • Comms triage (claude-haiku-4-5, four tiers, COMMS_PROMPT_VERSION = 4)
  • the Reader summariser (claude-sonnet-5, free text, READER_PROMPT_VERSION = 1)

Evaluating the Claude Code agent sessions that the Code module launches is a different problem. It gets a sidebar in §4, not a recommendation.

1 · Where we landed

Hand-spin. Extend the harness alfred already has, and adopt no framework. eval:comms is already ahead of every TypeScript framework surveyed on the part that matters most: domain metrics (queue recall, asap precision) with Wilson intervals. It is behind on four practices that the field agrees on. Take those four ideas from the frameworks and leave their code:

  1. Variants × fixtures × trials as the unit of a run. A variant is a prompt builder plus a model plus that model's call parameters.
  2. Repeated trials (k = 5), with a reported noise floor: the fixtures that flip between identical runs.
  3. Paired comparison of variant A against variant B on the same fixtures, never two independent confidence intervals set side by side.
  4. A dev / held-out split, so a prompt tuned against the fixtures is not also graded on them.

For the free-text Reader summaries, use blind pairwise review by the owner first. Add an LLM judge only after it has been validated against those human labels.

The pushback: the framework is the least important decision in this ticket. The binding constraints are statistical:
  • The comms set has 68 fixtures, of which 40 should be queued and 10 are asap.
  • At that size a prompt change has to flip six fixtures one way and break none before it clears p < 0.05 (§2.2).
  • Sampling noise cannot be configured away. Production runs at the default temperature of 1.0, and models released after Opus 4.6 reject any other value.
Installing promptfoo changes none of that. Growing the labelled data does, and so does running every fixture more than once. If one of the two gets the time, put it into labels.

2.2 · The statistics bind before the tooling does

The table below is exact two-sided McNemar over the 68 comms fixtures. "Fixes" are fixtures that A got wrong and B got right, and "breaks" are the reverse. The numbers were computed in this session (§6, command 4).

  • Power is low even for large effects. Suppose the errors of A and B were independent and the true accuracy moved from 85% to 92%. A 2,000-run simulation detects that change about 16% of the time at n = 68, 35% at n = 150, and 67% at n = 300. Real prompt edits have correlated errors (the hard fixtures stay hard), which helps, but the direction of the conclusion holds.
  • The per-tier intervals are wide. A perfect asap run over 10 fixtures has a Wilson interval of 72–100%, and 9 of 10 gives 60–98%. A perfect whenever run over 5 gives 57–100%. score.ts already reports these intervals. What it cannot do is shrink them.
  • Sampling noise cannot be configured away. The installed @anthropic-ai/sdk@0.116.0 marks temperature @deprecated: "Models released after Claude Opus 4.6 do not support setting temperature. A value of 1.0 … will be accepted … all other values will be rejected with a 400 error." Neither classifier.ts nor summarize.ts sets it, so production samples at the default of 1.0 and an honest eval must match. Haiku 4.5 predates the cutoff, so pinning a lower temperature there would be a change to production, not to the eval, and one that breaks at the next model upgrade. The SDK also has no logprobs field, so the Anthropic paper's "use next-token probability" variance reduction is not available. Repeated trials are the only lever.
  • Money is not the constraint. One comms run is about 151k input tokens (604,786 characters of assembled requests ÷ 4) and about 7k output. On Haiku 4.5 at the repo's price table ($1 in, $5 out per million), that is about $0.19 per run, or about $1.90 for a 2-variant × 5-trial comparison. The Batch API would halve it. The constraint is labels.

2.3 · What the frameworks offer against what alfred needs

Two structural mismatches recur across every framework:

  • They factor a run as prompts × providers × tests. In alfred, a prompt is a TypeScript function of live data (rubric, people roster, thread, example set), not a template. A "provider" is a model that needs its own call parameters. The workable integration in every framework is a custom provider or task that calls alfred's own builder and call function. That makes the framework's prompt and provider layers bypassed ceremony.
  • They score by averaging assertions. Per-test pass/fail, rolled up into a mean. Alfred's headline metrics are directional rates over subsets (recall over the fixtures that should be queued, precision over the asap calls) with Wilson intervals. Those metrics would be re-implemented on top of any framework anyway.

2.4 · Prototype: both TypeScript frameworks can drive alfred's code, and neither adds what is missing

Throwaway prototypes lived in the session scratchpad; none of this is committed. Each built every request with the real buildCommsRequest over the real FIXTURES. A canned stand-in replaced the model (this container has no ANTHROPIC_API_KEY). "Variant B" was rigged to flip 9 fixtures.

# promptfooconfig.yaml (abridged)
prompts:  [{ id: A, raw: 'variant A' }, { id: B, raw: 'variant B' }]
providers: [{ id: file://provider.ts }]   # imports workers/src/comms/{prompt,eval/fixtures}.ts
tests: file://tests.ts                     # generates one test per FIXTURES entry
derivedMetrics: [{ name: tier_accuracy, value: tier_exact / __count }]

$ PROMPTFOO_DISABLE_TELEMETRY=1 npx promptfoo eval --no-cache
  ✓ 127 passed (93.38%)   ✗ 9 failed   Duration: 2s
  variant A  {"tier_exact":68,"tier_accuracy":1}
  variant B  {"tier_exact":59,"tier_accuracy":0.8676}
  • promptfoo imported alfred's extensionless TypeScript modules with no resolve hook, which is a point in its favour. It wrote ~/.promptfoo/promptfoo.db (SQLite) and an install id. The comparison it produced was two pass rates. There was no statement of whether 68 against 59 is a real difference; by §2.2, 9 one-way flips is.
  • Evalite (evalite.each for variants, trialCount for repeats, both confirmed in the 1.0.0-beta.16 type definitions) ran 136 evals in 174 ms and printed "Score 93%". Its first run failed: Vite parsed workers/tsconfig.json and could not resolve its extends: "@tsconfig/strictest" until the repo's node_modules existed. That is a small sign of the coupling a second test runner brings into a repo whose back-pressure rules are written around Jest.

2.5 · The practices worth taking

fetched means the primary page was read in this session. snippet means the claim rests on search-result text, because the domain was blocked by this container's egress proxy.

P1 · Report uncertainty on every number.

"Report the SEM, derived from the Central Limit Theorem, alongside each calculated eval score." Alfred already does this, using Wilson intervals, which suit its small n better than the CLT.

Anthropic, A statistical approach to model evaluations fetched

P2 · Compare paired, not side by side.

"Conducting a paired-differences test lets us eliminate the variance in question difficulty and focus on the variance in responses." For two classifiers on one test set, Dietterich (1998) finds McNemar has low Type I error and is the acceptable choice when each is run once. A paired bootstrap generalises to any metric, including recall and precision deltas.

Anthropic statistics post fetched; Dietterich 1998 snippet

P3 · Resample, and cluster by fixture.

Reduce variance by "resampling answers from the same model several times, and using the question-level averages". Treat the trials of one fixture as a cluster: "clustered standard errors … can be over three times as large as naive standard errors."

Anthropic statistics post fetched; LLM outputs vary even under greedy decoding because of batch-variant kernels (Thinking Machines, 2025) snippet

P4 · Measure reliability as pass^k, not only pass@1.

pass^k is "the probability that all k trials succeed". It is the right lens when a user sees one sample per item, as the owner does in the Comms queue. A message that comes out asap on 3 of 5 runs is a coin flip for the owner.

Anthropic Engineering, Demystifying evals for AI agents fetched

P5 · Grade by code first, then model, then human, and automate.

"More questions with slightly lower signal automated grading is better than fewer questions with high-quality human hand-graded evals." When a model grades, have it reason first and output a constrained label.

Anthropic docs, Create strong empirical evaluations fetched

P6 · Start small and use real failures.

Begin with "20–50 simple tasks drawn from real failures". Split capability evals (hard, low pass rate) from regression evals (target close to 100%).

Anthropic Engineering, Demystifying evals fetched

P7 · Error analysis before metrics.

Read real outputs, write open-ended notes (open coding), then cluster them into failure modes (axial coding). Keep going until new reviews stop revealing new modes. Avoid generic off-the-shelf metrics. This matters most for the Reader, whose failures are not yet named.

Husain & Shankar, AI Evals FAQ fetched via a mirror

P8 · If you use an LLM judge, make it binary and validate it.

Prefer pass/fail over 1–5 scales. Build the judge by "critique shadowing" a domain expert. Report the judge's TPR and TNR against human labels, not raw accuracy, and re-validate it periodically.

Husain, Creating a LLM-as-a-Judge… snippet; AI Evals FAQ fetched via a mirror

P9 · Judges carry bias.

LLM judges show position bias, verbosity bias and self-enhancement bias. The mitigation is to judge twice with the order swapped and call a disagreement a tie. Pairwise comparison is more stable for subjective axes; direct scoring suits objective checks.

Zheng et al. 2023 (MT-Bench); Yan, Evaluating the Effectiveness of LLM-Evaluators snippet

P10 · Expect criteria drift.

"Grading outputs helps [people] define those very criteria." The rubric for the Reader should be a living artifact, refined while grading, not fixed in advance.

Shankar et al. 2024, Who Validates the Validators? snippet

P11 · Hold something out.

Tune on dev and report holdout. A large gap between the two means the prompt memorised the fixtures.

This is the weakest-sourced principle here: practitioner consensus snippet, backed by the in-repo skill-creator doing exactly this.

3 · Technical shape

This is enough for a refinement session to expand. It is not the spec.

Interfaces (sketch)

// workers/src/eval/types.ts: pure, jest-tested, imported by the scripts
interface Variant<F> {
  label: string;                        // 'v4', 'v5-draft', 'v4@sonnet-5'
  model: string;
  run(fixture: F, env: EvalEnv): Promise<TrialOutput>;  // build + PRODUCTION call + post-process
}
interface Suite<F, J> {
  name: 'comms' | 'inbox' | 'reader';
  fixtures: readonly F[];
  split(fixture: F): 'dev' | 'holdout';
  judge(fixture: F, output: TrialOutput): J;     // a code grader wherever possible (P5)
  correct(judgment: J): boolean;                 // the pass/fail that pairing and pass^k use
}
interface TrialRecord {                          // one JSONL line
  suite: string; variant: string; model: string; promptVersion: number;
  fixtureId: string; split: 'dev' | 'holdout'; trial: number;
  output?: unknown; failure?: string; usage?: { in: number; out: number }; ms: number;
}

// workers/src/eval/paired.ts
mcnemarExact(fixes: number, breaks: number): number   // two-sided p (the §2.2 numbers)
pairedBootstrap(records, metric, { iterations: 10_000, seed }): { delta; low; high }
stability(records): { stableRight; flaky; stableWrong }  // pass^k

Files a later story would touch

  • New: workers/src/eval/{types,runner,paired,stability}.ts and their tests. The runner takes its caller as an argument, so its tests never make a network call.
  • New: workers/scripts/eval-compare.ts and an eval:compare script, for example npm run eval:compare -w workers -- --suite comms --a v4 --b v5-draft --trials 5.
  • Refactor: comms-eval.ts onto the runner (the Wilson scorer stays), with a shared readDevVar and price table.
  • Extend: comms/eval/fixtures.ts with a split field. An examples snapshot becomes a variant dimension, so production's 12-example prompt can also be measured.
  • New suite: src/eval/inbox/, seeded from classification_corrections and labelled by the owner. The fixture's own row is excluded from its few-shot block.
  • Reader: reader-eval.ts --compare A,B emits a self-contained HTML page. It shows the summaries side by side in randomised order, captures a preference plus one line of critique, and exports JSON. This follows P7–P10 and the eval_review.html precedent.

Suggested order (each step pays for itself)

  1. Measure the noise floor first. Run today's comms prompt at k = 5 on Haiku (about $1). If several fixtures flip between identical runs, every single-run comparison made so far was partly noise. That includes the ALF-244 eval bar, which was specified as a single-run before/after comparison and was not run in the session that shipped it (demo §6).
  2. Extract the runner and the paired statistics, then refactor eval:comms onto them.
  3. Grow the comms set toward 150 or more fixtures from real traffic, defaulting to holdout.
  4. Build the Inbox suite.
  5. Build the Reader pairwise review page. Consider an LLM judge only after about 50 owner labels exist.

4 · Sidebars: appealing alternatives we're not taking

promptfoo

This is the obvious candidate, and the prototype proves it works. It has the prompts × providers matrix, --repeat, a disk cache, llm-rubric and select-best judges, a good local viewer, full Anthropic support, and MIT licensing. OpenAI's own Evals product is shutting down on 30 Nov 2026, and OpenAI reportedly points its users to promptfoo as the migration target.

Why not:

  • At 2.0 GB it cannot sensibly enter the single workspace lockfile, so it would live as an unpinned npx side-tool.
  • Its matrix is the wrong factorisation for alfred (§2.3).
  • It has no paired statistics, so the one thing alfred lacks would still be hand-written.
  • Telemetry is on by default.
  • It is now owned by OpenAI and is reportedly being folded into OpenAI's enterprise agent platform. It is still MIT, but the roadmap belongs to someone else.

Revisit if alfred wants adversarial testing of the Comms prompt. That prompt ingests untrusted mail and texts behind <<<MESSAGE>>> delimiters, and security testing of AI apps is promptfoo's specialty. That would be a separate spike.

Evalite (or Sentry's vitest-evals)

It is the lightest TS-native option: 84 MB, evalite.each variants, trialCount, and a local UI.

Why not:

  • It is built on Vitest 4, which would be a second test runner beside Jest. The back-pressure rules, ESLint scoping and skills all assume Jest.
  • v1 is still beta (1.0.0-beta.16) and has a peer dependency on the Vercel ai@^6 SDK.
  • Scoring is a mean. There are no directional metrics and no paired statistics.

Revisit if the Reader review UI outgrows a static HTML page.

Inspect AI (UK AISI)

It is the most rigorous framework surveyed. Epochs with reducers, stderr() on by default, multi-model eval sets, and inspect view are all real and current (0.3.271, 26 Sep 2026).

Why not: it is Python only. Alfred's prompt assembly is TypeScript over TypeScript types, so every sample would cross a subprocess or HTTP bridge, or the builders would be ported and would drift. Take its ideas, and none of its code.

Hosted platforms (Braintrust, LangSmith, Langfuse Cloud, Arize Phoenix)

They offer good TS SDKs, dataset versioning, pairwise experiments, and free tiers that fit one user.

Why not: the valuable eval data here is the owner's private mail and texts. The current fixtures are synthetic, but real-traffic fixtures, which §1 recommends, would be uploaded to a third party. Self-hosting Langfuse means running Postgres, ClickHouse and app servers for a single-user project. None that we found computes paired significance tests either.

OpenAI Evals (repo and hosted)

Why not: the hosted platform goes read-only on 31 Oct 2026 and shuts down on 30 Nov 2026. The repo's README points to the dashboard, and it is Python.

Anthropic Console "Evaluate" tab

Historically it offered side-by-side prompt versions and graded test cases in a UI.

Why not: it needs {{variable}} templates and cannot run alfred's TypeScript builders or post-processing. It is manual. Its current feature set could not be confirmed, because the doc URL now serves generic eval guidance.

An LLM judge for the classifiers

Why not: the classifiers have exact labels, so a code grader is strictly better (P5). A judge only earns its place on the Reader's free text, and there only after validation (P8).

Public benchmarks (HELM, lm-evaluation-harness)

Why not: these run fixed academic tasks to rank model capability. They say nothing about whether Haiku triages this owner's mail well. The question "is Sonnet 5 worth it for Comms?" is answered on alfred's own fixtures.

Gating evals in CI or pre-push

Why not: it spends money and needs a network, which breaks the repo rule. With k = 1 it would also turn sampling noise into flaky gates. The pure statistics and scorer are unit-tested; the runs stay deliberate and manual.

The Batch API by default

It is 50% cheaper, and Anthropic lists "large-scale evaluations" as a use case.

Why not by default: at about $0.19 per run, the saving is cents. It adds submit, poll and collect code, and most batches take up to an hour. Keep it as an option once suites grow.

Evaluating the Code module's agent sessions and launch prompts

This is out of scope. It is a multi-turn, tool-using, repository-mutating task where a single trial costs dollars and minutes. It needs the agent-eval toolkit: pass^k over task outcomes, and graders on transcripts and on the resulting pull request. The nearest in-repo art is the adversarial-review step and skill-creator's trigger evals.

If wanted it would be its own spike, and Anthropic's Demystifying evals for AI agents is the starting point.

Open questions

  • How noisy is Haiku on these fixtures? This is unknown until step 1 runs. The size of the flaky set decides whether k = 5 is enough.
  • Where does the owner's private data go? Real-traffic fixtures contain it. Options are to keep them in the database and export on demand into a gitignored directory, or to commit only redacted and synthesised derivatives. The current fixtures are committed because they are synthetic. This needs the owner's call.
  • Model comparisons carry a prompt-tuning bias. The comms prompt was tuned against Haiku, so comparing Sonnet on that prompt tests "Sonnet on a Haiku-tuned prompt". This is reasoning, not a measurement. Record it whenever a model comparison is reported.
  • Does the comm_corrections window hold enough signal to mine for new fixtures? It sees demotions, not false negatives (the fixtures.ts header). New recall fixtures still have to come from the owner reading the shelf.
  • Is the Console Evaluate tab still offered, and can it run cross-model? This could not be verified in this session. It does not change the recommendation.
