ALF-319 — Incorporating Jesse Vincent’s Superpowers into the alfred SDLC

Don’t install Superpowers. Repo settings can’t load it in cloud sessions, it duplicates most of alfred’s SDLC, and it fights the PR contract. Adapt three of its ideas instead.

Where we landed

Superpowers is a whole methodology for one human working in one interactive session: brainstorm, spec, plan, execute, then pick how to merge. alfred already splits that same arc into separate phases that the orchestrator routes and that end in PRs. Bolting the plugin on would give every session two competing processes. Three ideas are worth porting into alfred’s existing skills, each as its own story: (1) adapt systematic-debugging into a technique skill that the bug skill points at; (2) give implement-epic the on-disk progress ledger that subagent-driven-development uses to survive compaction; (3) add writing-plans’ Review Focus idea to the refinement spec’s acceptance criteria. If you’d rather have evidence than this argument, §7 sets out an A/B test that would prove me wrong.

The evidence

Everything below is for whoever builds on this. Acting on the answer needs only what’s above.

What Superpowers is

obra/superpowers is an MIT-licensed Claude Code plugin from Jesse Vincent and Prime Radiant. Upstream head is v6.4.2 (2026-09-25). The official marketplace pins v6.4.1 (sha 5bf4e78), which shows it lags upstream by about a week. The plugin is two things:

  • 15 skills: brainstorming, writing-plans, executing-plans, subagent-driven-development, dispatching-parallel-agents, test-driven-development, systematic-debugging, verification-before-completion, requesting-code-review, receiving-code-review, using-git-worktrees, finishing-a-development-branch, writing-skills, using-superpowers and diagnosing-superpowers.
  • A SessionStart hook (hooks/session-start, on startup|clear|compact). It injects the full using-superpowers skill, wrapped in <EXTREMELY_IMPORTANT>You have superpowers. That skill says: “If you think there is even a 1% chance a skill might apply … you ABSOLUTELY MUST invoke the skill”, and it must do so “BEFORE any response or action — including clarifying questions, exploring the codebase”. This bootstrap is the engine of the whole plugin. Without it, the skills are just a library.

The intended flow (README, “The Basic Workflow”) runs: brainstorming → using-git-worktrees → writing-plans → subagent-driven-development or executing-plans → test-driven-development throughout → requesting-code-review → finishing-a-development-branch. A human approves at each gate. Spec and plan documents land in docs/superpowers/specs/ and docs/superpowers/plans/.

It changes fast. There were 30 releases between 2025-11-24 (v3.5.1) and 2026-09-25 (v6.4.2), crossing three major versions (v4.0.0 in Dec, v5.0.0 in Mar, v6.0.0 in Jun). Skill bodies are large: subagent-driven-development is about 4.8k words, writing-skills 3.8k, executing-plans 3.2k and brainstorming 2.6k.

Background: the ticket very likely traces to the Cognitive Revolution interview in docs/communication-firewall/cognitive-revolution-transcript.md. There, Steve Newman says Superpowers is “the only thing I’ve really installed” and that he runs /systematic-debugging by name. His setup is a single developer in a local terminal, with no orchestrator, no PR contract and no CI-enforced block. That is exactly the context where a whole bundled methodology earns its keep, and it is not alfred’s context.

Can it even load in an alfred session?

alfred launches every SDLC session as a claude.ai/code?repo=…&q=… link (frontend/lib/code/links.ts, buildUrl). Every session is therefore a cloud session on a fresh clone. Claude Code’s cloud-environment docs, under “What carries over from your setup”, are explicit:

Plugins and marketplaces declared in your repo’s .claude/settings.json — No — A cloud session doesn’t install the plugins a repository turns on under enabledPlugins, including ones from the marketplaces it lists under extraKnownMarketplaces.

Observed in this very session, which agrees with the docs. alfred’s .claude/settings.json enables frontend-design@claude-plugins-official. Even so, ~/.claude/plugins/installed_plugins.json was {"version":2,"plugins":{}} at session start, and no frontend-design skill appeared in the session’s skill list. Side finding: that enabledPlugins entry only does anything in local sessions. Every alfred-launched session silently ignores it.

The route that does work: install from the environment

The same docs say repo files under .claude/skills/ are carried over, and so are skills enabled on claude.ai. Plugins can also be installed by the environment’s setup script before Claude starts. I tested the CLI side in this container:

$ claude plugin install superpowers@claude-plugins-official
√ Successfully installed plugin: superpowers@claude-plugins-official (scope: user)
$ claude plugin list
  > superpowers@claude-plugins-official   Version: 6.4.1   Scope: user   Status: √ enabled
$ claude -p "…list skills starting with 'superpowers:' … did your context include 'You have superpowers'?" --max-turns 1
superpowers:brainstorming, …, superpowers:writing-skills   (all 15)
YES

So a setup-script line would put the full plugin, bootstrap hook included, into every new session. It is technically viable. Its costs are structural:

  • It lives outside git. The environment’s setup script is per-environment configuration in the claude.ai UI. It isn’t reviewed, versioned or visible in the repo, and it applies to every repo that uses that environment.
  • It is invisible to the session ledger. code_sessions.skills is derived from .claude/skills/*/SKILL.md paths as of base_sha (tools/session-ledger/src/replay.ts, SKILL_PATH_RE; llm-evaluation skill). A plugin version that changes under you would confound every model or prompt comparison the ledger exists to make.
  • It follows the marketplace’s pin, not yours, unless the script pins a git sha itself.

Where the plugin would collide with the PR contract

These come from reading the skills against alfred’s launch prompts and SDLC skills. None was observed live. I tried to run alfred’s bypass and bug launch prompts headless in throwaway worktrees with the plugin installed, but the session’s permission classifier blocked spawning nested agent sessions. Treat this section as the hypotheses that the §7 experiment would test.

  • Two documents, two homes. On architectural work, brainstorming’s HARD-GATE requires a design approved in chat and then a spec at docs/superpowers/specs/YYYY-MM-DD-*-design.md, followed by a plan at docs/superpowers/plans/. alfred’s refinement requires docs/specs/<REF>.html from the template, with the spec-path block checked by alfred-frontmatter. In an implementation session, writing-plans would also commit a plan document that nothing archives.
  • Gates that look for a human who has gone. writing-plans ends by asking the human to choose “Subagent-driven” or “Native” execution. finishing-a-development-branch presents a menu of options. alfred’s prompts already define the gate (“ASK ME HERE” only when scope is unclear) and the ending (open a PR, adversarial review, stop).
  • Ask or decide? subagent-driven-development says “Rulings, not stalls … A running plan does not wait on a human”, with a ledger of rulings. implement-epic says “Stop and ask the human in the tab”. Both are defensible, but loading both leaves the model to arbitrate.
  • Who wins on priority. using-superpowers says “User instructions (CLAUDE.md, AGENTS.md …) take precedence over skills”. alfred’s CLAUDE.md says nothing about Superpowers, though, so every conflict above would be settled by the model’s judgment in each session. The 1% rule and the EXTREMELY_IMPORTANT framing push that judgment toward the plugin. alfred’s own SDLC skills load because the prompt names a path, not because of a louder bootstrap.
  • Context cost. The bootstrap is about 3.2 KB (roughly 800 tokens) on every startup and compaction, before any 2.6k–4.8k-word process skill is invoked.

What’s worth taking, and the shape of each port

All three are adaptations into alfred’s skill library. They follow CLAUDE.md’s rules for editing skills: read skill-creator for a new skill and compounding-learning for an update, then pass skill-lint. Where text is copied rather than paraphrased, keep the MIT copyright notice (Jesse Vincent, 2025) in the skill folder.

5.1 A debugging technique skill (highest value)

The bug skill says what must be true: the bug is reproduced, a test is red, the cause is fixed. It says nothing about how to find a root cause once the obvious first read fails. systematic-debugging fills exactly that gap:

  • Instrumentation at component boundaries for multi-layer systems. This matters for alfred, whose path runs browser → Next.js route → Supabase → Worker → daemon.
  • A single written hypothesis, tested with the smallest possible change, one variable at a time.
  • “If 3+ fixes failed: question the architecture”, a stop rule alfred lacks.
  • The root-cause-tracing.md backward-tracing reference.

Shape: a new .claude/skills/systematic-debugging/ (or a name in alfred’s style), cut to the technique. Drop the process parts the bug skill already owns, and drop condition-based-waiting, because the playwright, storybook and supabase skills already carry alfred’s flake guidance. Adapting find-polluter.sh to Jest is optional. The bug skill’s step 1 and step 3 link to the new skill. It also fits the CI-red handling in implementation sessions, where “flake is not a root cause” already sets the expectation. A replay of a past Bug: ticket with and without the skill (llm-evaluation’s replay procedure) is the natural acceptance test.

5.2 A progress ledger for implement-epic

subagent-driven-development’s Setup calls this “the single most expensive failure observed”: a controller loses its place after compaction and re-dispatches tasks it had already finished. implement-epic is the one alfred lane long enough to compact mid-run, and it has no ledger. grep -i "ledger\|compact" on its SKILL.md finds nothing. Shape: a git-ignored progress file whose first line names the epic spec, with one Slice N: complete <sha> line per integrated slice and a rule to trust the ledger and git log over memory after compaction. The SDD loop also reviews every task for spec compliance. Whether implement-epic should add that, given that the epic lane is “deliberately left out” of adversarial review for now (links.ts, adversarialReviewStep), is a separate cost question. It isn’t part of this port.

5.3 Review Focus in refinement specs

writing-plans asks the plan’s author to list the “five input classes or failure modes the spec implies but no task’s tests exercise”, then add a test for each to the task that owns it. It names the right worry: “the spec’s silence on an input is not permission for that input to break the program”. In alfred, this belongs in the refinement spec’s acceptance criteria, as a short traced list of edge inputs each pinned by an impl criterion. It doesn’t belong in a separate plan document. Shape: one optional subsection in .claude/skills/refinement/assets/spec-template.html’s detail and one rule line in the refinement skill. It’s the smallest of the three; drop it if the spec template’s budget can’t absorb it.

Alternatives we’re not taking

Install the plugin via the environment setup script

It works (§2), and it is the only way to get the bootstrap. It’s ruled out as a default because it sits outside git and the ledger, applies to every repo in the environment, and adds a second process that fights the PR contract (§4). It stays the right vehicle for the experiment in §7.

Enable it in .claude/settings.json

It does nothing in cloud sessions, per the docs and per observation (§2). It would only affect local sessions, which alfred doesn’t launch.

Vendor all 15 skills into .claude/skills/

This would load in cloud sessions, minus the hook. But it doubles the SDLC skill set with rival descriptions that trigger on the same phrases (“implement the spec”, “fix the bug”). It would also import a release cadence of about three per month, and the composable-shared-skills spike already showed that copies rot. Without the bootstrap it also loses the thing that makes Superpowers Superpowers.

Enable it as a claude.ai skill

“Cloud sessions automatically load skills you enable on claude.ai.” This is per-user and spans every repo, with no hook. It has the same invisibility to git and the ledger as the setup script, and less of the plugin.

Do nothing

This leaves the debugging technique on the table, and that’s the one piece with clear marginal value. It’s also the piece Newman reaches for by name.

Cost & open questions

  • Effort. Each port is one small, docs-only story under .claude/skills/, with no app code. Ports 5.1 and 5.2 deserve a replay-based check through llm-evaluation, not just a lint pass.
  • Unverified: real behaviour under the plugin. §4 is reasoning only. To falsify it, create a second cloud environment whose setup script runs claude plugin install superpowers@claude-plugins-official (ideally pinned to a sha), then replay three to five past tickets per lane (bug, bypass, implementation) in both environments. Compare cost, turns, PR-contract violations (block, spec-path, archive, stray docs/superpowers/ files) and adversarial-review findings. Since the ledger can’t see the plugin, tag those sessions by environment. If the plugin lane wins clearly, this recommendation is wrong and should be revisited.
  • The inert frontend-design entry. Should it stay (for local sessions) or go, now that it’s known not to load in alfred’s cloud sessions? Whoever added it may believe it’s active.
  • Telemetry. If the full plugin were ever installed, brainstorming’s optional visual companion loads a logo from Prime Radiant’s site that reports the plugin version (opt out with SUPERPOWERS_DISABLE_TELEMETRY or DISABLE_TELEMETRY). None of the ports carry it.
