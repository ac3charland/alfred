ALF-348 — An MCP server for Alfred, or a skill?

Both, for different jobs. Build one small MCP server inside the Next.js app with its own scoped key, covering tasks, items and the wiki. Keep the skill to explain how to read the results.

Where we landed

Build one remote MCP server at frontend/app/api/mcp, not two. “Skill or MCP?” is a false choice. A skill is instructions Claude loads when it needs them. An MCP server is typed tools plus credentials plus reach. Today’s alfred skill does both jobs, and the client half is the weak part: curl scripts with the admin ingest key baked in, which work only where code execution can reach Vercel. A custom connector accepts a fixed API-key header, so no OAuth is needed on day one. One connector then works in claude.ai, Desktop, mobile, Cowork and Claude Code cloud sessions. The wiki needs no separate server. It is already a Supabase snapshot with a search RPC: two more tools on the same server.

The story I’d cut: “Alfred MCP v1”. About eight read-heavy tools, plus capture and complete-task as the only writes. A new MCP_API_KEY, not the ingest key. Comms stays out entirely.

  1. Most of Alfred can’t be reached by a key today

    Only 7 of 55 route files accept the ingest key; every wiki route needs a browser session.

    Grep of frontend/app/api; see §1

  2. The skill’s key is a master key

    A valid ingest key gets the service-role client, which bypasses row-level security.

    resolveIngestClient in lib/api/auth.ts; see §5

  3. A connector reaches more places than a skill

    Connector traffic goes through Anthropic’s servers, so it skips sandbox egress rules on every surface.

    Claude connector and cloud-environment docs; see §2

  4. The wiki lookup is nearly free

    The wiki_pages table and the search_wiki_pages RPC already exist.

The evidence

Everything below is for whoever builds on this. Acting on the answer needs only what’s above.

What Claude can reach in Alfred today

Claude reaches Alfred two ways today. The alfred skill, installed on claude.ai, ships five shell scripts: post-weekly-plan, create-plan-items, plan-items, pr-ratio and habits, plus a Python helper that converts timestamps to local time. Each script curls a keyed route with the base URL and key baked in. Separately, cloud Code sessions reach the two ledger routes with a proxy-injected LEDGER_API_KEY.

How the 55 route.ts files under frontend/app/api authenticate:

CredentialRoutesWhat it unlocks

So “more flexible interactions” is blocked by the auth surface, not by the protocol. Claude can’t list the Inbox, search tasks, complete one, or look anything up in the wiki today, whether through a skill or through MCP. Whatever gets built, the real work is a keyed, narrowly scoped read path into lib/data.

The protocol itself. The current spec revision is 2026-07-28. Streamable HTTP becomes stateless: the Mcp-Session-Id header is removed, and every POST carries Mcp-Method/Mcp-Name headers. HTTP+SSE is deprecated. On auth, Client ID Metadata Documents replace Dynamic Client Registration, which stays only as a fallback. Statelessness suits Vercel functions well, since a server with no session state is just a route handler. I could only confirm the spec through secondary write-ups and the changelog URL, because modelcontextprotocol.io is not on this session’s network allowlist. Check the transport page before building.

Next.js hosting. Vercel’s mcp-handler package (formerly @vercel/mcp-adapter) exports createMcpHandler for an App Router route and withMcpAuth(handler, verifyToken) for bearer verification. It also serves the protected-resource metadata endpoint if OAuth is added later. Confirm it supports the 2026-07-28 revision before adopting it; one Nov 2026 tutorial uses v2.3 on MCP SDK v2.

Why an MCP server, and why keep the skill

What a skill can’t do well here

  • It can’t hold a secret. The key sits in plain text in the skill’s scripts, and anyone with the skill bundle has a service-role key. Rotating it means rebuilding and re-uploading the skill and editing the Siri Shortcut, because they share the same key. A connector’s header lives in account settings. A cloud session’s key lives in a network secret the VM never sees.
  • Reach depends on the sandbox. A skill script runs only where code execution is on and the sandbox can reach alfred-six-gamma.vercel.app. A connector bypasses both. That matters most for the phone chat, where most capture-and-lookup moments happen.
  • It’s fragile. The skill spends a paragraph on finding its own scripts (“this skill has moved between them before, and a stale path fails as ‘the alfred call errored’”), and pipes output through Python to fix timestamps. In a server, both become plain server code with tests in check:fast.
  • No types. An MCP tool has an input schema Claude must satisfy. Today the scripts pass hand-written JSON files through curl --fail-with-body. The Zod schemas in lib/api/schemas.ts can serve as the tool schemas directly.

What the skill still does best

The skill’s best content isn’t the curl calls. It’s the interpretation rules: done, not raw status; untriaged overlaps the other counts rather than adding to them; read due_date literally; never call a habit “Established”; a 500 on create-items means nothing was written. That is domain judgement, and it costs context only when the skill is in use. Put the one-line invariants in each tool’s description and in the server’s instructions. Keep the longer explanations in a slimmed skill with no scripts. The week-plan upload, a 30–50 KB HTML body, also fits a file-based skill better than a tool argument; it can stay a script until the MCP tool is proven.

One server, not a separate knowledge MCP

The ticket asks for a separate lookup MCP for the knowledge repo. That isn’t needed. Following the llm-wiki spike, the private wiki repo is already mirrored into wiki_pages by the Worker (workers/src/wiki/sync.ts). The table carries title, summary, tags, sources, links, body and a weighted tsvector, and search_wiki_pages(p_query, p_limit) returns ranked hits with snippets. Two tools, wiki_search and wiki_read_page, cover lookup. A second server would mean a second connector, a second key and a second set of tool definitions loaded per conversation. Inside Claude Code, though, the better lookup is to clone the wiki repo and grep it. MCP adds the most where there’s no checkout: chat and mobile.

Keep the tool count small. docs/skill-suggestions.md already cites selection accuracy dropping as the tool pool grows (HumanMCP 87.4% → 65%). Claude Code’s tool search softens this, but claude.ai chat loads connector tools up front.

Technical shape

One route, frontend/app/api/mcp/route.ts (or [transport] if the handler requires it). It is a stateless Streamable HTTP handler that calls the same lib/data functions the session routes use. A candidate v1 tool set:

ToolBacked byKind
search_items (text, type, folder, state, due window)the query behind GET /api/itemsread
get_item (with children)items/[id] GETread
list_foldersGET /api/foldersread
plan_items, habits, pr_ratiothe existing keyed routes, with timestamps localized on the serverread
wiki_search, wiki_read_pagesearch_wiki_pages, getWikiPageBodyread
capturePOST /api/items logic (lands untriaged in the Inbox)write, additive
complete_tasktasks/[id]/completewrite, reversible in the app

Mark the reads with readOnlyHint so clients can auto-approve them, and leave the two writes on “ask”. Deliberately left out of v1: delete, move, reorder, anything under comms, Software Factory dispatch (already “a human act in the app”), and the reader. The comms firewall’s retention design (“safe to lose and not safe to keep”) argues against copying message text into chat transcripts at all.

Auth, phased. Phase 1: a new MCP_API_KEY checked in constant time, following the validateLedgerKey pattern, sent as a fixed header from the claude.ai connector and as a network secret in cloud environments. It still resolves to the admin client because Alfred is single-user, but only the tool list decides what it can touch. Phase 2, if wanted: OAuth through Supabase Auth or a hosted provider, so the token is user-scoped and RLS applies again.

Security: the risk is the combination, not the protocol

This server combines private data (tasks, the wiki), untrusted content (Reader posts and wiki pages filed from web sources, both readable through the tools), and some ability to act (capture, complete). That combination is the prompt-injection “lethal trifecta”. The repo already treats it seriously: the ledger and research keys were made narrow because those sessions read untrusted text. Mitigations, in order of value:

  1. Give the server its own key, never INGEST_API_KEY. That also lets us later take the ingest key out of the skill and rotate it, leaving only Siri holding it.
  2. No destructive tools. Both writes are additive or undoable in the app.
  3. Keep the write tools on per-call approval in the connector settings, and turn them off for Research mode.
  4. Return snippets and bodies as data; never pass them through into tool descriptions or server instructions.

Privacy note: connector calls go Claude → Anthropic → Vercel → Supabase. Wiki bodies already reach Anthropic whenever a Claude session reads the repo, so this adds no new party.

Alternatives we’re not taking

Just extend the skill with more scripts

The cheapest path, but it spreads the admin key further, works only where code execution can reach Vercel, and every new script needs keyed routes built anyway. Once those routes exist, an MCP wrapper over them costs little.

A separate knowledge-base MCP server

Ruled out above. Same database, same deployment, no reason for a second connector and key.

Supabase’s own MCP server, or a generic Postgres MCP

That exposes raw SQL with a service-role credential. Claude would have to rediscover the domain rules (done vs status, the inherited item types) on every call, and nothing stops a delete. This is the opposite of a narrow surface.

Hosting it in workers/

Cloudflare has good MCP tooling, but the queries, Zod schemas and RPC wrappers live in frontend/lib. A Worker would duplicate them or force a shared package first. Revisit only if Vercel function limits bite.

A local stdio server on the Mac

claude.ai, mobile and cloud sessions can’t reach it (“local MCP servers configured through claude_desktop_config.json aren’t available in Cowork or claude.ai”). It would also tie lookups to the Mac being awake.

OAuth from day one

It’s the more correct design, but it brings in an authorization server and the CIMD/DCR choices for a single user. A fixed header is officially supported and enough to learn whether the tools get used.

Cost & open questions

Effort: about 1–2 sessions for v1. Most of it is the tool layer over existing lib/data functions plus tests. Add one dependency (mcp-handler + @modelcontextprotocol/sdk), one env var, and a demo doc that runs a real MCP client against the local route. Money: none beyond normal Vercel invocations.

  • Is mcp-handler on the 2026-07-28 revision? If not, a hand-written stateless handler on the SDK may be simpler. Check the README and changelog first.
  • Do MCP Apps (UI resources) render in claude.ai yet? If so, a week plan could render inline instead of via upload. Not verified here.
  • Which writes does the user actually want from chat? The v1 list is a guess based on the existing skill’s scope: capture and complete. Snooze or reschedule may matter more.
  • Wiki privacy labels. The llm-wiki spike plans per-page visibility computed from sources, but wiki_pages has no such column yet. For a private, single-user connector that’s fine. If a shared connector ever appears, filter on it first.
  • Does the Siri Shortcut keep the ingest key? If so, consider giving it its own capture-only key, so a leaked key can no longer read everything.
