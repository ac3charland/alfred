ALF-351 — Consolidate Cloudflare cron triggers to one every-minute trigger

Yes, one * * * * * trigger can replace all five, but only if each due unit still gets its own invocation, because merging them into one run would exhaust the 50-subrequest budget.

Revised 2026-11-09: Cloudflare’s docs were read in a second session. Limits and trigger counts are confirmed, but a self-binding and a fresh callee budget are still undocumented, so the probe still gates the build.

Where we landed

Don't run the units in one handler. Reader (48 of 50), retention (50) and notify (up to 50) are each sized to a whole invocation, and every 30th minute four units are due together. Make the minute trigger a thin dispatcher: derive the due units from event.scheduledTime and hand each to the Worker itself as a separate invocation. Probe that first: the docs are silent on both a Worker binding to itself and the callee getting a fresh budget. If the probe fails, the fallback is the Paid plan, which makes consolidation unnecessary. The next story would be the probe, then the dispatcher, with the first story gated on the probe result.

The evidence

Everything below is for whoever builds on this. Acting on the answer needs only what’s above.

Why: the code today, and why in-process dispatch fails

workers/wrangler.toml:87 registers five crons: */2, */3, 17 9 * * *, */5 and * * * * *. workers/src/index.ts:293-336 dispatches on event.cron string equality, one branch per constant. The Free plan allows five triggers per account, and the code and the cloudflare-workers skill both say all five are used. The notify comment (index.ts:200-210) says the next scheduled feature must share notify’s budget or go Paid. That scarcity is the motivation for this spike.

The five units were split onto separate triggers for one stated reason: the Workers Free plan allows 50 outbound fetches per invocation, and sharing a tick made units starve each other (index.ts:154-158, wrangler.toml:69-75; the skill states the same rule at .claude/skills/cloudflare-workers/SKILL.md:188).

Nothing here is small enough to ride along. Every 30th minute (minute 0 and 30) the tick, poll, reader and notify are all due at once, so merged in-process they would need roughly 150+ fetches against a ceiling of 50. The overshoot throws part-way, and the repo records that this only shows up with real data, never in stubbed tests. Reader also runs for up to ~10 minutes (reader/scheduled.ts:150-155), so a serial single handler would hold notify behind it and break notify’s “at most a minute late” promise. Running the units in parallel fixes the latency but not the shared budget.

The CPU ceiling is a second shared limit. The retention comment budgets the wiki sync’s parsing at about 6 ms (index.ts:186-187), which only makes sense against the Free plan’s 10 ms CPU limit per invocation, so merged units would also pool CPU. A later docs read confirmed it: 10 ms CPU per HTTP request and per Cron Trigger on Free.

One benefit comes free with a single expression. Offset-stepped ranges are normalised by the scheduler and collapse onto other schedules (index.ts:160-168, skill lines 149-156). With one trigger, that whole class of bug and the “unrecognised cron” fall-through disappear.

Technical shape

Which units are due

Derive the minute from event.scheduledTime (the intended fire time, so a late delivery doesn’t shift the schedule), not from Date.now(). 60 is divisible by 2, 3 and 5, so minute-of-hour modulo gives the same cadence as today’s */N expressions, repeating every 30 minutes.

const d = new Date(event.scheduledTime), m = d.getUTCMinutes();
notify:    always
tick:      m % 2 === 0
poll:      m % 3 === 0
reader:    m % 5 === 0
retention: d.getUTCHours() === 9 && m === 17   // 17 is odd, 17%3=2, 17%5=2: coincides with notify only

Per 30 minutes: notify 30, tick 15, poll 10, reader 6. The maximum concurrent units in any minute is four. Express this as a pure dueUnits(scheduledTime) function, and hold the table { name, due, run } in code so a new feature is one row, with no trigger and no wrangler change.

Giving each unit its own budget

The recommended mechanism is a self service binding that exposes each unit as a WorkerEntrypoint RPC method. The minute handler awaits Promise.allSettled over the due units. A failed unit cannot skip the others, because each runs in its own invocation with its own try/catch, as retention already does. RPC methods are not publicly routable, unlike a fetch route, which would need HMAC protection. The dispatcher spends one subrequest per due unit, at most four.

The dispatcher is itself an invocation with its own 50 fetches, so it can run one unit inline (notify, which idles at one fetch) and fan out only the others. That saves a call every minute. The docs say a single request may make at most 32 Worker invocations (each service-binding call counts), so four calls sit far inside it. Whether a cron-started run counts as a “request” for that cap is undocumented.

Observability

wrangler tail will show every invocation as * * * * *, so log one line per dispatch naming the units fired (and never log secrets).

Alternatives we’re not taking

One handler running every due unit in-process

The simplest design, and the one the title implies. Ruled out by the shared 50-fetch budget and shared CPU: reader alone uses 48, and four units coincide every 30 minutes.

Partial consolidation

Folding only “small” units into notify. Nothing is small: notify idles at one fetch but is sized to 50 when busy, and every other unit is sized to a full invocation. This is the status quo the comments already describe.

Upgrade to the Workers Paid plan instead

Not ruled out; it is the fallback and arguably the cheaper answer. The repo’s own notes say 1000 subrequests per invocation on Paid, which makes in-process dispatch viable, and the trigger count stops being scarce. It trades engineering for a recurring cost, and the docs list 250 cron triggers on Paid against 5 on Free. It is a product decision for the owner.

Queues, Workflows or Durable Object alarms as the fan-out

Each adds a new binding and operational surface. Queues are available on Free, but include only 10,000 operations a day, with 24-hour retention. The reader of the docs estimated roughly 3 operations per message (from memory, unconfirmed). Fan-out averages about two due non-notify units a minute, so about 3,000 messages a day and about 9,000 operations, which is borderline. Use Queues only if the self-binding probe fails and the Paid plan is unwanted, and confirm the per-message operation count first.

Cost & open questions

Effort: small. It is roughly one file of dispatch logic, one config line, and tests rewritten as a table. The unit modules (runSweep, runCommsPoll, runReaderTick, runNotifyTick, retention) are untouched.

Confirmed from the docs (read by a second session with access, not by me; verify against the live pages before relying on them): Free allows 5 cron triggers per account (250 on Paid); 50 subrequests per invocation; 10 ms CPU per HTTP request and per Cron Trigger; 100,000 requests a day. A service-binding call counts toward the caller’s subrequest limit. A named WorkerEntrypoint can be bound via entrypoint.

Still undocumented, and gating the recommendation:

  • Can a Worker bind to itself? A one-hour probe settles it: deploy the self-binding on Free.
  • Does the callee get its own 50-fetch and 10 ms CPU budget? Test by having the callee make 51 fetches and, separately, burn more than 10 ms of CPU while the caller idles. The limits page has a “subrequests to internal services: 1,000” row it does not explain, so the answer may be better than 50.
  • Do service-binding calls count against the 100,000 daily requests? Today’s five triggers fire roughly 2.9k times a day, so even doubling it is far inside the allowance.
  • Delivery guarantees for cron (skipped or duplicated minutes) are not documented. Treat the units as needing to tolerate both.

Risks: a missed or delayed minute loses that minute’s units, as it does today. Duplicate or late delivery behaviour is unchanged only if each unit is already idempotent, which I did not audit. The cutover is one wrangler deploy (merging deploys, per the skill), swapping the trigger set and code together.
