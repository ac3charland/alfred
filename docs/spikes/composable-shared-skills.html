Spike · findings

Composable shared skills across repos

Can the SDLC skills be decomposed so the general guidance lives once in oddobot-skills and each consuming repo contributes its own project-specific material — without either half rotting?

1 · Where we landed

Build a small composer, not a framework. Each shared skill becomes a template in oddobot-skills carrying variables and named slots. Consuming repos vendor a committed copy of those templates, supply their own vars.json and fragment files, and a compose step emits a generated-but-committed SKILL.md. Insights discovered in a project flow back up through an inbox in the shared repo, with the one judgment step — integrating prose — left to a human or an LLM, never to a script.

On the larger question: the plumbing is commodity (copier, cruft), and the skills-specific tooling genuinely does not exist. But demand is currently thin, and only one piece of this is novel: LLM-mediated semantic merge of prose, with bidirectional flow. Build the composer as a standalone package, instrument which mechanisms actually fire, and revisit the “is this a product” question in 60 days with data rather than a hunch.

2 · Why

2.1  The divergence is phrase-level, not section-level

Diffing the four candidate skills between alfred and motivic produces roughly ten distinct divergences. Exactly one is a self-contained block that plain concatenation could express (motivic's “Publish the spec as a Claude Artifact” step). Every other one is woven into a sentence:

SkillDivergenceShape
refinementdocs/specs/ALF-42.html → MOT-42Token substitution
refinementMockup sources: frontend/app/globals.css + *.styles.ts → frontend/components/atoms/Path substitution
refinement“a migration number above all” → “a fixture index, anything handed out in order”Example substitution
refinementWhole Claude-Artifact publishing stepAppendable section
implement-spec, epic-refinement“The check enforces…” → “Where installed, the check enforces…”Conditional hedge
compounding-learningThree separate hand-maintained lists of which skills exist in the repoEnumeration

Two consequences. First, a concatenation-only composer — the Vercel shape — captures one divergence in ten. Variables are not optional. Second, the conditional-hedge class dissolves without machinery: write the shared sentence as “Where the alfred-frontmatter check is installed, a PR missing the block fails CI”, which is true in both repos, and no {{#if}} is ever needed.

One candidate needs no composition at all. compounding-learning's entire divergence is three hand-maintained enumerations of which skills exist in the repo. An agent can run ls .claude/skills/. Deleting those lists makes the skill 100% shareable with zero machinery. The cheapest composition is the divergence you delete — audit each candidate for this before building it a composer.

2.2  Manual copying has already rotted

The What to produce list in refinement, as committed today:

alfredmotivic
1.A spec at docs/specs/<REF>.htmlA spec at docs/specs/<REF>.html
2.— missing —Publish the spec as a Claude Artifact
3.A pull requestA pull request

alfred/.claude/skills/refinement/SKILL.md:62 is literally numbered 3. with no 2. above it — a hole left by copying between the repos. This is the failure the spike exists to fix, and it also constrains the mechanism: an ordered list inside a composable region is a trap, because inserting a slot shifts every ordinal after it. Shared templates should use lazy 1. numbering (markdown auto-numbers) or named steps.

2.3  The generated-file trap is the sharpest risk

CLAUDE.md's compounding-learning rule instructs every agent to record an insight into the SKILL.md, the same turn it hits the gotcha. If SKILL.md becomes generated output, that edit is silently wiped on the next compose. This is the most likely way the system rots, and it needs three defences, not one:

  • A DO-NOT-EDIT — generated from <source> banner atop every composed SKILL.md.
  • A recompose-diff check in check:fast that fails when the committed output differs from a fresh build — catching the wipe before it merges.
  • An edit to compounding-learning itself teaching the routing decision, so “where does this go” is answered explicitly rather than by vibes.

2.4  Vercel's pattern does not transfer

vercel-labs/agent-skills composes react-best-practices from ~40 files under rules/, each with title / impact / tags frontmatter, compiled by pnpm build into AGENTS.md. That works because the atoms are independent rules. The SDLC skills are narrative workflows, where project detail is woven mid-sentence.

More importantly, the rules/ split is authoring convenience for Vercel, not a consumer extension point. The npx skills CLI has no idea those files exist; a consumer cannot add a rule. Their model is one-directional publish: add defaults to symlinking each agent to one canonical copy, update overwrites, there is no lockfile, no drift detection, no merge strategy, and no documented story for local modification or contributing back. Skills are read-only artifacts; if you disagree with one, you fork. That is coherent — and it is the opposite of what we need.

3 · Technical shape

3.1  Layout

oddobot-skills/
  skills/refinement/
    SKILL.md.tpl              shared prose + {{VARS}} + <!-- slot: name -->
    skill.json                declares vars and slots (required | optional)
  scripts/compose.mjs         zero-dep; vendored alongside the content
  inbox/<repo>/<skill>/*.md   fragments awaiting integration

alfred/.claude/
  shared-skills/              VENDORED — never hand-edited
    .manifest.json            { source: "ac3charland/oddobot-skills", sha: "…" }
    refinement/SKILL.md.tpl
    scripts/compose.mjs
  skills/refinement/
    SKILL.md                  GENERATED · COMMITTED · DO-NOT-EDIT
    local/vars.json           { "REF_PREFIX": "ALF", "spec-artifact-publishing": null }
    local/fragments/*.md      project content + queued insights

Vendoring means a literal copy of the upstream source committed into the consuming repo — present in any clone, including a fresh Claude Code web container with no network. npm run skills:sync is the only writer: shallow-clone upstream, overwrite, record the SHA, recompose.

3.2  The fragment — one file format for two purposes

---
slot: spec-authoring-gotchas
scope: shared            # or: project
---
Don't put acceptance criteria inside <details> — reviewers skim past
a collapsed block and sign off without reading it.

compose treats both scopes identically, so the insight is live in this repo the moment it is written — zero cross-repo latency at the point of learning. scope only declares where it eventually belongs. Fragments in a slot sort by filename.

3.3  Upstream flow

StageWhereTriggerDoesNature
1alfred / motivic CImerge to mainCopies scope: shared fragments into oddobot-skills/inbox/ via PRDeterministic
2oddobot-skillsinbox non-emptyIntegrates fragments into the template prose; PR against the templatesJudgment
3oddobot-skills CImerge to mainOpens skills:sync + recompose PRs in each consumerDeterministic
Stage 2 cannot be a script, and this is the crux of the design. A GitHub Action can only append the fragment verbatim — producing exactly the bolt-on accretion compounding-learning exists to prevent. The skill would then state the same thing twice, in two voices, in two places. Such a PR looks finished — green checks, sensible diff — which is what makes it dangerous: it invites rubber-stamping while every one of them still needs the merge-into-the-prose work done by hand.

The inbox aggregates, which a per-repo promotion job structurally cannot. If alfred and motivic both learn the same thing, stage 2 sees both fragments side by side and writes one good sentence. The tell that a promotion worked: the composed SKILL.md diff downstream is near-empty — the text moved from slot to body and what the agent reads barely changed. A large diff means the integration rewrote meaning.

3.4  Two tiers, only one gets machinery

Tier 1 — parameterized divergence

Ticket prefixes, repo paths, the Artifact-publishing step. Permanent, expected, per-repo.

Mechanism: vars and slots. The composer's job.

Tier 2 — a general rewrite of shared prose

An improvement to the core body that applies to every consumer. No local mechanism at all — it goes straight upstream as a PR to oddobot-skills.

Why no mechanism: the patch-queue machinery that would justify a local override assumes waiting days on someone else's maintainers. We are upstream. With skills:sync as one command, the full round trip — PR up, merge, sync down, recompose — is about five minutes. A patch queue to avoid five minutes is machinery that outlives its justification.

The one case that bites: an agent mid-session on a feature branch hits a general gotcha and cannot merge an upstream PR itself. It files a tier-2 note in the inbox describing the change, and that note does not compose into the local SKILL.md. The repo's agents don't benefit until it syncs. That is a real, knowing loss. If it turns out to hurt, the cheap fix is Debian's pressure mechanism rather than its machinery: let such a note compose into a marked “Pending upstream” section, and have compose warn once it has survived N syncs.

3.5  Two failure modes named “routing around”

ModeSymptomDefence
a. The pass never runsFragments pile up, the library ossifiesStage 1 in CI — fires on merge, needs no habit
b. Nothing gets marked scope: sharedQueue stays empty; the system looks healthyDO-NOT-EDIT banner + recompose-diff check + compounding-learning teaching the scope decision explicitly

Mode (b) is the quieter one. Writing a local fragment will always be less work than editing shared prose, and marking everything scope: project is the choice with no consequences. CI does not touch this; only the three defences above do.

4 · Appealing alternatives we're not taking

Use copier instead of building a composer

copier is a project-scaffolding tool with copier update: a native three-way merge that syncs a generated project with an evolving template while preserving local edits. A .copier-answers.yml is the manifest; a weekly CI job that opens an MR when the template moves is an established idiom. It looks like a near-perfect fit.

Ruled out Its model assumes the output is hand-edited — that is what the merge is for. We chose add-only, where output is generated and a check fails if anyone touches it. Those premises conflict at the root. Secondary friction: one answers-file per destination (per-skill config means N invocations); Jinja delimiters collide with skill content that legitimately contains {{ }} and {%; no named-slot concept; and it puts Python in a check:fast gate that currently has one runtime.

Steal The design, not the tool: answers-file-as-manifest, three-way merge as the conflict model, CI-opens-an-MR-when-upstream-moves.

Adjacent copier is right for scaffolding a new repo with the whole alfred/motivic setup — CLAUDE.md, husky, check tiers, tools/ — where output-you-edit -freely is exactly the model. Different problem, worth its own look.

npm git dependency on oddobot-skills

Elegant versioning, no vendored copy, no sync script.

Ruled out oddobot-skills is private, so every npm ci — in CI and in every ephemeral Claude Code web container — would need a GitHub token. Install-time network and auth is exactly the dependency vendoring exists to remove.

Git submodule

True single source with real SHA pinning.

Ruled out Submodules need explicit init; a fresh web-session clone can land with an empty directory and therefore no skills at all. The failure is silent and total.

Claude Code plugin marketplace

alfred/.claude/settings.json already carries enabledPlugins, so repo-level plugin enablement is a mechanism in use here today.

Ruled out for composed skills Plugin skills install per-developer and cannot be merged with project-local fragments. Still a reasonable route for fully-shared skills like code-walkthrough that need no composition. (Whether a marketplace can be served from a private repo was not verified.)

Conditionals in the template ({{#if}})

Would let one template carry both “the check enforces this” and “where installed, the check enforces this”.

Ruled out Requires a real template engine and makes shared prose unreadable as prose. Normalising the sentence to the universally-true phrasing kills the entire class for free.

Full override / local patch queue

Maximum expressiveness — every divergence we have today becomes representable, and Debian's debian/patches model is proven at far larger scale.

Ruled out A project could silently fork the shared prose and it would never show in a diff, which is most of the value gone. Reconsider only if tier-2 latency measurably hurts.

Stage 2 as a scheduled Claude job, now

A cron Action in oddobot-skills running Claude against the inbox weekly, fully autonomous.

Deferred, not rejected Manual first: the inbox PRs are visible enough that a full queue can't be forgotten, and automating later needs no redesign since the artifact is a PR either way. Doing it now means debugging the integration prompt at the same time as the composer.

5 · Is this a project of its own?

5.1  What already exists

The plumbing is commodity. copier and cruft have solved template → many-downstream-instances, keep-in-sync, preserve-local-edits for years, including three-way merge and CI-raises-an-MR automation.

The skills-specific case is empty. anthropics/skills Discussion #380 requests exactly this — an extends: frontmatter field, motivated by DRY violations and “teams must fork the entire skill to customize it.” Posted 13 Feb 2026. Commenters proposed mixins, skill.lock, routing skills, tiered loading. Five comments, two reactions, and no maintainer response in seven months.

Read that in both directions. Nobody has built this — an opening. Almost nobody is asking — a thin market.

5.2  What is genuinely novel

Prose has no merge semantics. copier, cruft, Kustomize, Helm, Terraform modules, Nix overlays — every one assumes structured data or code, where three-way textual merge is meaningful. Hit a conflict inside a markdown paragraph and you get <<<<<<< markers in prose: the accretion problem again, with worse ergonomics.

And every one is one-directional. There is no copier push. git subtree has bidirectional flow but no templating. Nothing has both.

So the durable primitive is not composition — it is LLM-mediated semantic merge of prose documents with a bidirectional flow, novel because it only became possible in roughly the last eighteen months. Skills are just the first compelling use case; it applies identically to CLAUDE.md files, runbooks, style guides, ADRs, onboarding docs.

This reframe has a strategic consequence: if Anthropic ships extends:, it vaporizes the composition half overnight and does not touch the merge half. That argues for building the merge primitive and treating composition as scaffolding around it.

5.3  Arguments against

  • n = 2 repos and one user. There is no evidence yet about which mechanism carries the load. If vars fire forty times and semantic merge fires twice, there is no project — just a script.
  • The funnel is narrow. A user needs multiple repos, and enough skill volume that divergence hurts, and the discipline to run a sync. “The market will arrive” is the most reliable way to lose a year.
  • Counter-argument: the composer is getting built for alfred and motivic regardless. The marginal cost of a clean standalone CLI boundary over a script buried in tools/ is perhaps 20% — a cheap option worth buying.

5.4  Recommended posture

  1. Build the composer as a standalone package with a real CLI boundary. Use it in both repos.
  2. Instrument it. Over 60 days, count how often each mechanism fires: vars, slots, tier-2 upstream rewrites, integration conflicts. That is free product research.
  3. Post in Discussion #380 — the cheapest way to learn whether anyone else has this problem.
  4. Revisit with numbers. A working prototype plus a real use case is a far stronger starting position than a framework built on a hunch.

Risks

  • Secret placement. Stage 1 needs a token with write access to a private repo, sitting in public alfred's secrets. Needs to be got right.
  • PR noise. Three repos auto-PRing each other is real churn unless stage 3 is batched or auto-merged.
  • Oscillation. A bad integration syncs back down and lands wrong text in both repos rather than one.
  • Vendored staleness. A vendored copy goes stale silently; the manifest SHA is the only visible signal until a --check mode exists.

Open questions

  • Is stage 2 manual or a scheduled Claude job for v1? (Leaning manual — see §4.)
  • oddobot-skills is private while alfred is public, so vendoring publishes the shared content anyway. Is the privacy buying anything, and should the shared repo just be public?
  • Can a Claude Code plugin marketplace be served from a private repo? Unverified, and it decides whether the fully-shared skills can take the simpler route.
  • Does skill-lint need a rule for composed skills — e.g. failing a SKILL.md that lacks the DO-NOT-EDIT banner?
  • How should composed output interact with the “generated files are excluded from formatting & linting” rule? skill-lint should still lint it (it is what the agent reads), but the fix belongs in the template.
