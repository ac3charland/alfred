Spike — LLM wiki: architecture and location

Where Karpathy's LLM-wiki pattern should live, who writes it, how it stays private, and what part of it (if any) is Alfred.

01

Where we landed

Q1 — Public, private, or a mix?

Private-first. Every raw source gets a sensitivity label set by a script, never by Alex or the model; every wiki page's visibility is computed from its sources: list. Nothing is exported. A public garden stays a real later goal, built as a separate deterministic export step when there's demand to show for it.

Q2 — Alfred module, or standalone?

Both, split by role. The store is a new private git repo of plain markdown — never Alfred's Supabase. The writer is a Claude session working the repo's files. Alfred is the feed (an inbox for Reader posts and captured ideas) and a thin read-only reading room (Day 2) — not a native module of rows.

Q3 — Where does it live?

A new private GitHub repo, cloned to ~/docs/Claude/Wiki/ on the Mac as a sibling of the Productivity Coach folder, never nested in it. Links run one way, coach → wiki. The wiki never reads coach files.

The build is two one-day chunks:

  • Day 1 — the wiki itself, no Alfred code. Create the private repo and skeleton, write the CLAUDE.md schema and the three scripts, clone it locally, stand up a separate "Wiki" Claude Project, drop one pointer row into the coach's index.md, and ingest a handful of real sources by hand — seeded from Obsidian book notes and Instapaper highlights — to prove ingest → index → log → lint end to end.
  • Day 2 — the Alfred Knowledge module, thin. A snapshot-on-push read view built from the same pattern that already serves specs, plus a keyed inbox endpoint so Reader posts and captured ideas can flow into an ingest session. No LLM write path through Alfred, no graph view.

A reader who stops here knows the shape of the build. Everything below is the evidence and the detail.

02

Why

2.1The privacy mechanism

Karpathy's pattern already asks for a sources: citation on every page. The design here makes that structural rather than a courtesy:

  • Every raw source in raw/ carries sensitivity: public | licensed | private, set by a script from a fixed mapping table keyed on source type. Anything unmatched defaults to private. Alex can lower a label by explicit command; nothing raises one automatically.
  • Every wiki page carries sources:, and a script computes the page's visibility as the most restrictive of those sources. A page with no sources is private. The model never writes visibility or sensitivity.
  • Publishing is a separate export step to a separate public target, never a flag filtering the private tree.

The reasoning behind putting this outside the model: the model's context window, not the files, is the main leak path. What a page cites is a claim the model makes about itself, not a record of what it actually used. In Karpathy's own description, a single source touches 10–15 pages during ingest, and "good answers" from a query get filed back too — so a private source's contamination can spread across the tree in ways a citation list won't catch. Three research results back this up:

  • ConfAIde (ICLR 2024): LLMs reveal private information in contexts humans wouldn't, GPT-4 39% of the time, ChatGPT 57%.
  • PrivacyLens: agents leak in 25.7% (GPT-4) to 38.7% (Llama-3-70B) of cases, even when given explicit privacy instructions.
  • FlowSeal: labeling data by provenance and checking every write with a deterministic interceptor outside the model, plus an isolated LLM checker for declassification, cut item-level leakage from 52.2% to 0.5%.

That last number is the design principle in one sentence: the model that saw the conversation shouldn't also decide what's safe to release. So the export script checks provenance on every allowlisted page, strips links to anything not exported, copies only referenced assets, and publishes a snapshot with no git history — because git history can't be undone, and flipping the private repo to public later would be the single biggest irreversible action in the whole design. An isolated LLM privacy check runs as a second, weaker layer. Alex reviews the diff by hand the first time any page is promoted.

Comms and firewall messages are never a wiki source. That's not a stricter rule invented for this spike — it defends a decision already made (60-day comms retention, so alfred's copy stays "safe to lose and not safe to keep"). Chat transcripts aren't sources either; only notes Alex explicitly asks Claude to file are.

2.2Why storage is the repo, not Alfred

Three separate facts rule out Supabase as the store, and a fourth rules out the Alfred monorepo as the location for content:

  • Alfred's own storage sweeps by design. Reader post text is nulled at 90 days (0036_reader_operability.sql, ALF-232 D13); the comms mirror deletes at 60 (wrangler.toml cron comment). ALF-7 D2 is explicit: "alfred mirrors, it is never the store of record." A wiki that's supposed to compound over years can't sit on a table designed to forget.
  • There's no keyed write path for what an ingest needs. The only key-authenticated write the alfred skill can reach is POST /api/items; PATCH and DELETE are session-only (frontend/app/api/items/[id]/route.ts). One ingest touches 10–15 pages, so this would mean building a keyed CRUD API, a batch/transaction RPC, and rename-with-link-rewrite from scratch — none of which exists today.
  • Wiki pages don't fit the item model. The Reader epic already decided a post is never an item (ALF-232 D1); a wiki page fits worse still — it's edited in place forever, it links many-to-many, and it has no status. Pages would need their own tables (wiki_pages, wiki_links, wiki_log, a revisions table) to replace what git already gives away free.
  • Committing into the Alfred repo has a CI tax. Every commit runs root check:fast via the pre-commit hook — skill-lint, migration-lint, type-check, lint, unit tests across every workspace. Paying that on every wiki ingest is absurd, and it also means wiki content would sit in the context of factory agents working on unrelated code.

2.3Why Alfred is still the reading room

Alfred's whole premise is a single unified second-brain interface, and routing around it for anything Alex actually wants to read works against that. The precedent already exists: week plans are written by a Claude skill as HTML and rendered inside Alfred through a sandboxed iframe (weekly-plan-view.tsx) — the skill owns the writing, Alfred owns the display. A circular usage trigger ("why would I reach for something that's never been in Alfred?") was explicitly rejected as a reason to defer this. So Day 2 gives the wiki the same split: a Claude session (and, eventually, the repo's own git history) is the writer and source of truth; Alfred is a thin, read-only mirror built from the same fetchSpec snapshot pattern that already serves specs.

2.4Why a strict split from the coach folder, one way

The coach folder is already a small, working wiki about Alex: an index, progressive disclosure, synthesis pages, git history. The new wiki is deliberately scoped to everything outside that — the world, and Alex's ideas about it. Keeping them physically separate does three things at once:

  • It's the cheapest privacy firewall available. Coach files hold sleep, binge days and family detail. If the wiki repo never ingests them, no synthesis step inside the wiki can accidentally carry them toward a page that's later exported.
  • It protects the coach's per-chat budget. Every coach chat already reads a ~22 KB fixed set (index.md, current-system.md, protocols.md). Merging the folders means either bloating that read or letting the keystone-file rules apply to wiki sessions that don't need them.
  • It keeps ownership honest. The coach's files are commitments — "never skipped," enforced mid-conversation. The wiki's pages are LLM-maintained and periodically linted. Those are different governance models, and blending them would let autonomous wiki maintenance edit files that are supposed to hold Alex's word.

The coach's index.md gets exactly one "Read As Needed" pointer row to the wiki. The wiki never ingests coach files — links run coach → wiki only, never the reverse. This is a convention, not a structural guard (nothing stops a session from reading both), so its own honest failure mode is drift; the mitigation is that the wiki folder isn't connected to coach sessions by default.

2.5The format constraints — and why they're expensive to reverse

Three consumers have to read the same files unconverted: Obsidian on the Mac, Alfred's react-markdown + remark-gfm renderer, and a static-site generator later. That forces three rules into the schema on day one:

  • Standard relative markdown links ([habit formation](../concepts/habit-formation.md)), never [[wikilinks]]. Obsidian's backlinks and graph work fine with relative links; GitHub, react-markdown and every SSG render them; wikilinks render as literal text in Alfred and lock the format to Obsidian- or Quartz-only tooling.
  • YAML frontmatter on every page, with the fields listed in §3.2.
  • No Obsidian-only syntax — no ![[embeds]], no callouts, no Dataview — and assets in one fixed folder with relative paths.

Of the three, the link syntax is the one choice that's genuinely expensive to reverse: it's woven into every page's body text, not a frontmatter field a script can rewrite in one pass. Get it wrong on day one and a later migration means touching every link in every page by hand.

03

Technical shape

3.1Repo skeleton

~/docs/Claude/Wiki/              ← clone of private repo
  CLAUDE.md                      ← schema (see 3.3)
  index.md                       ← content catalog, by category; rebuilt on every ingest
  log.md                         ← append-only; `## [YYYY-MM-DD] ingest | Title`
  raw/YYYY/YYYY-MM-DD-slug.md    ← write-once; frontmatter below
  raw/assets/
  wiki/{concepts,entities,sources,questions}/*.md
  scripts/                       ← sensitivity mapper, visibility computer, lint
                                    (later: export)
  .gitattributes                 ← log.md merge=union

3.2Frontmatter

A raw source, script-populated fields marked:

---
source_url: https://example.com/article
captured: 2026-09-23
origin: mine                # public | mine
sensitivity: private        # ← script-set from source type, never hand-written
---

A wiki page:

---
title: Habit formation
summary: How repetition and cue design compound into automatic behavior.
sources:
  - raw/2026/2026-09-12-atomic-habits-notes.md
visibility: private         # ← computed: most restrictive of sources, fail-closed
created: 2026-09-12
updated: 2026-09-23
tags: [psychology, behavior-change]
---

3.3CLAUDE.md — the schema's table of contents

One file at the repo root, so any clone (Mac or cloud) picks it up automatically. It has to cover, in order:

  1. Layout — where each file type lives, per the skeleton above.
  2. Frontmatter — required fields per file type, per §3.2.
  3. Link rules — relative markdown only, never wikilinks, never Obsidian-only syntax.
  4. Ingest / query / lint workflows — the three Karpathy operations, written as concrete steps for this repo.
  5. Router — where a new fact goes: action → Alfred; a fact about Alex → the coach folder; knowledge or a thought about the world → this wiki.
  6. House style — lean pages, no archaeology, single source of truth per fact.
  7. Visibility rule — computed by script, fail-closed to private, never hand-set by a session.

3.4The three scripts

ScriptWhat it checks / sets
Sensitivity mapperSets raw/*.md frontmatter sensitivity from a fixed mapping table keyed on source type. Unmatched sources default to private. Alex can lower a label by explicit command; nothing raises one automatically. The model never touches this field.
Visibility computerReads a wiki page's sources: list, looks up each cited source's sensitivity, and sets the page's visibility to the most restrictive value found. A page with an empty sources: list is private. The model never writes this field.
LintFrontmatter present on every page; every relative link resolves; every page appears in index.md; no orphan pages (no inbound links); visibility fails closed to private when missing.

3.5Sync discipline

One remote, one long-lived branch. A session opens with git pull --rebase and makes one commit per ingest, titled like the log entry it wrote; it pushes at the end. raw/ is write-once by convention, promoted to a CI check once an autonomous writer exists. index.md is never hand-merged — on conflict, re-derive the affected section; once there's a second concurrent writer, generate it by script from page frontmatter instead. log.md gets merge=union in .gitattributes so concurrent appends merge cleanly. A future autonomous writer works on ingest/<date>-<slug> branches and opens a PR — the merge is the review.

3.6Seed content, Day 1

The wiki seeds from two sources Alex already has: his existing Obsidian book notes (his own notes, never the book text) and his Instapaper highlights (his highlights plus a source_url back to the article). Both are origin: mine, which sidesteps the licensed sensitivity class entirely for the seed — the sensitivity mapper still runs and sets a value, it just resolves to public or private rather than licensed. The full raw-source scope and the ingest bar ("read/discussed" vs. "saved") are open question 1 in §5.4, not settled here. First pages target what the coach folder can't hold: an essay pipeline/seed page, an llm-maintained-knowledge concept page built from this spike's own sources (public-eligible), a Building Alfred story-arc page (every source already public), and Motivic product-research notes — never self-knowledge pages, which stay in the coach.

3.7Day 2 — the Alfred Knowledge module

Thin, read-only, and built from pieces that already exist:

  • Snapshot on push. Reuse the fetchSpec pattern in workers/src/github.ts, which already pulls markdown from GitHub and snapshots it into Supabase on merge. It needs the read PAT's scope extended to cover the new private repo.
  • The shell. A Knowledge tab wired into modules.ts plus the six files that list the module set (switcher, nav, mobile nav, router, command palette, view heading), with a seeded provider like the other modules have.
  • The read view. react-markdown + remark-gfm, the same stack that already renders specs in components/code/spec-view.tsx, with relative-link resolution added so wiki links work inside Alfred's route structure.
  • Search and backlinks. Full-text search over the snapshot text; backlinks computed from the links present at snapshot time (not live, not a graph).
  • The inbox. A "Send to wiki" verb added to Reader posts (whose overview jsonb, per ALF-232 D6, is already shaped for this), plus knowledge items — an item_type reserved since 0001_initial_schema.sql and unused today — feeding a keyed GET /api/knowledge/inbox endpoint. A wiki-ingest skill pulls from that endpoint during an ingest session.

What Day 2 deliberately doesn't build: any LLM write path through Alfred (the LLM writes git, not Supabase), and a graph view (force-directed layouts are non-deterministic, and every visual-state component needs a Storybook snapshot — a graph needs a seeded layout just to be testable).

3.8Data flow

sources → raw/ → Claude session → wiki/ + index + log → (a) Alfred now, (b) export + SSG later

The UI-surface question packs three separate jobs into "where does the wiki render": the LLM's own read/write, Alex's browsing, and the feeds coming in from Alfred. Trimmed from report 02 §3's full matrix (which also scores design fit and edit-reviewability) to the rows and columns that carried the decision.

Native Alfred module (pages as rows)

Appealed One place for everything; Alfred's shell and UI polish are real, and the Reader shipped in about a day.

Ruled out Wiki pages fit the item model worse than a Reader post already does (ALF-232 D1). The only keyed write is POST /api/items — no batch, no rename-with-link-rewrite. It would need its own tables to replace what git gives free, and it prices out at roughly 3–5× the Reader's build. Graph view also hits the Storybook snapshot gate.

Wiki inside the coach folder

Appealed Zero new infrastructure; one folder, one grant, one place Claude already reads every chat.

Ruled out Bloats the coach's fixed per-chat read; the keystone-file rules (read both files in full, every chat) would apply to sessions that don't need them; and it removes the cheapest privacy firewall — a wiki that can synthesize patterns.md into a page is a wiki that can leak it.

Alfred monorepo

Appealed "One repo so agents have full context" is already the stated reason for Alfred's monorepo shape, and backup/CI infrastructure already exists there.

Ruled out The repo is public by construction, every commit pays the check:fast CI tax, and factory agents working unrelated code would load wiki content into their context.

Per-page publish flag on the same tree

Appealed Simple metadata, and it's what the digital-garden tools actually do — Obsidian Digital Garden's dg-publish: true, Quartz's ExplicitPublish, Obsidian Publish's publish: true/false.

Ruled out The model writes the frontmatter, so the flag certifies itself. Git history holds every earlier state of a page, including before it was cleaned. Links and backlinks leak a private page's title from a public one even when the private page itself never gets flagged.

Claude Project panel / memory

Appealed Already available, zero setup, works from the phone today.

Ruled out No git, no diffs — uploaded copies drift from the folder. Its retrieval is RAG, which is exactly the "rediscover every time" model this pattern replaces. Writes to it bust the whole project's prompt cache on every change. Memory is a size-capped fact store, not a place for a compounding page tree.

Obsidian Sync / iCloud as the store

Appealed Native mobile browsing with graph and backlinks working immediately, no phone-side gap.

Ruled out A third party holds the vault; whether Obsidian Sync and a git clone coexist cleanly in one vault is unverified; iCloud alone is unreachable while the Mac sleeps, which blocks any future cloud- or phone-started ingest; and it costs $4–5/mo without answering the actual store-of-record question. Obsidian stays in the design, just as a free viewer on the git clone, not as the store.

05

Cost & open questions

5.1The two-day estimate, calibrated

The Reader is the closest real yardstick in this codebase: 2 stories, about 14.6k lines including tests and stories, spec-to-both-merged in roughly a day (9/17 23:30 to 9/18 22:13 by git log). But 59 of the 108 non-merge commits since 9/19 were Reader/comms follow-ups — liveness, refetch, reconnect. Read against that: Day 1 (files, scripts, schema, seed ingest — no Alfred code) is a genuinely self-contained one-day chunk, which matters because week 26's "day-sized chunks" experiment runs directly on it. Day 2 (thin, snapshot-on-push, no write path, no graph) sits at roughly 1× the Reader's build, so 1–2 days — but the Reader's own tail is a warning that a "done" module still draws a string of small follow-ups afterward.

5.3Anti-goals

  • Ingesting everything — breaks the "what's new to me" property the wiki exists for.
  • A UI, SSG, or graph view before ~30 pages.
  • Autonomous ingest before a month of reviewed ingests.
  • Moving patterns.md or protocols.md into the wiki.
  • Tasks or habits in the wiki — Alfred owns anything with a day.
  • A sax-practice log (an existing anti-rock; Motivic is that product).
  • Per-post Reader personalization (already a non-goal, ALF-232 D7).
  • A weekly review that reads the wiki in addition to everything else, rather than in place of something.

5.4Open questions for epic refinement

  1. Raw-source scope and the ingest bar — "read/discussed" versus "saved."
  2. Repo name (it will appear in URLs if a public export ever happens).
  3. Whether Rock 2's "LLM-wiki implemented in Alfred" needs rewording, or Day 2 satisfies it as written. Alex hasn't answered this yet.
  4. Whether the Motivic/Chad reference docs migrate out of the coach folder.
  5. Verify live: Quartz's link resolution for standard markdown links and ExplicitPublish behavior; whether Obsidian Sync and a git clone coexist cleanly (only relevant if Obsidian Sync is ever wanted for the phone).
  6. The wiki-ingest skill's exact contract with GET /api/knowledge/inbox.
  7. The GitHub read PAT's scope for the new private repo (Contents: read only, matching today's wrangler.toml convention).

5.5Optional experiment

Offered, not prescribed. "Compiled, not re-derived": for the first ~5 sessions after Day 1, log every historical or topical question a session asks as query | hit / miss / wrong in log.md. Confidence rises if at least ⅔ are hits, Alex corrects fewer than 1 in 5 claims, and there are zero record-contradicting answers. Each failure mode teaches something different: mostly misses means the wrong page set, not a tooling problem; frequent corrections means human review stays mandatory; Alex never opening a page himself means it's a Claude cache and every UI ambition should drop. n≈5 is weak evidence on its own — weight it accordingly, not as a verdict.
