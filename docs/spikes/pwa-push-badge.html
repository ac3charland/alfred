Home Screen badge and push for Comms

Yes: an installed iOS web app can take pushes and a badge, from our Worker, with no new service. The badge can only track what we are willing to notify about.

Where we landed

Build it, but make the badge count ASAP only, not the sidebar's queueCount. iOS requires every push to show a notification, so a badge that includes the today and whenever tiers would mean buzzing you for them too. Send from a dedicated invocation, not the comms tick, which can already spend 49 of its 50 subrequests. Ship the foundation and a real-device test first; the payload questions below need your phone, and this session has none.

Next story I would cut: Web Push for ASAP comms, gated on a device spike of the two open payload questions.

    iOS shows the badge only if notifications are granted, and pushes must be visible.

    Silent badge-only push is unconfirmed — §1

The evidence

Everything below is for whoever builds on this. Acting on the answer needs only what’s above.

Why

What the platform allows

  • Badging on iOS: navigator.setAppBadge arrived in Safari 16.4, for Home Screen web apps only, and the badge displays only once notification permission is granted (WebKit, Badging for Home Screen Web Apps).
  • Push on iOS: Home Screen web apps only, iOS 16.4+, a web app manifest with display of standalone or fullscreen, and the permission prompt must follow a user tap. I confirmed these across four vendor guides, not on Apple's own page: the Apple page was unreachable from this sandbox, so treat them as likely, not verified.
  • Declarative Web Push (iOS 18.4+) lets the payload describe the notification with no service worker: a top-level web_push: 8030 key, with app_badge inside notification in WebKit's own sample. A WebKit bug report argues app_badge belongs at the top level, and I could not tell which is shipping. That is open question 1.
  • Silent push: I found no source saying a badge-only push is allowed on iOS. Classic Web Push on Safari requires a visible notification per push; I am reasoning from that and have not verified it for the declarative form. That is open question 2, and it decides whether the badge can ever go down from the server.

What I ran

A throwaway script (scratchpad, not committed) generated a P-256 receiver keypair and auth secret as PushManager.subscribe() would, built a request with @block65/webcrypto-web-push 2.0.0, and decrypted the body with http_ece, an independent implementation. The declarative payload round-tripped byte for byte. The request carried the vapid authorization scheme with k=, content-encoding: aes128gcm, plus ttl, urgency and topic. The library imports no node:crypto. The encrypted body came out at 4096 bytes, the typical push-service cap, because the library pads to the full record; a payload carrying a sender name and tier is nowhere near it.

What that proves: a Worker can build a valid encrypted push. What it does not: that Apple's service accepts ours, or that a phone shows anything. Only a device test settles that.

Technical shape

Frontend

  • app/manifest.ts (Next's metadata-file convention; confirm it serves /manifest.webmanifest) with display: standalone, plus a static public/sw.js if we use classic push as the fallback.
  • The auth middleware will block both. frontend/middleware.ts exempts only image extensions and a few paths, so an unauthenticated fetch of the manifest or sw.js redirects to /login. Both must join isPublicPath.
  • An “Enable notifications” control in settings that calls Notification.requestPermission() from a tap, subscribes, and POSTs the subscription to an API route.
  • A foreground hook that sets the badge from the Comms store whenever the app becomes visible, so a count the server could not lower is corrected the moment you open Alfred.
  • You must remove and re-add the Home Screen shortcut after the manifest ships (vendor guides say iOS reads it at install time; unverified here).

Database

One migration (next number is 0054): push_subscriptions (endpoint unique, p256dh, auth, created, last success) and a notified_at on comm_messages, so a re-run verdict that lands on ASAP twice does not notify twice. Run migration-lint; the service-role Worker needs grants like the other tables.

Worker

  • A push.ts beside comms/: read subscriptions, buildPushPayload, fetch each endpoint, delete on 404/410, stamp notified_at. VAPID keys and subject go in secrets, set by hand like the others.
  • Trigger. runCommsSweep is budgeted to 49 of 50 subrequests in its worst case (COMMS_SWEEP_LIMIT = 6, comment in workers/src/comms/sweep.ts), and the Free plan allows five cron triggers, four in use (wrangler.toml). Options: a fifth cron that does only pushes (last free slot, up to a minute of added lag, and it burns an invocation on empty ticks); or a database-triggered POST to a new HMAC-verified Worker endpoint, modelled on /comms/ingest, which gets its own budget and fires on the event. I would try the second and have not verified the Supabase side.
  • Payload: sender display name and tier only, never the body. The ingest code already treats message text as other people’s private words; a lock screen is the widest place to leak it. Apple’s service cannot read the payload (RFC 8291), but the phone displays it.

Testing

The Worker sender and the subscription route take ordinary Jest tests against a mocked fetch; the badge hook takes a React Testing Library test against a stubbed navigator.setAppBadge. Nothing in CI can exercise delivery to iOS, so the repo’s “every requirement in a test” standard stops at Apple’s boundary; the device test is a manual demo-doc step.

Alternatives we’re not taking

Telegram (the existing notifications spike)

notifications-spike.md chose Telegram for outbound alerts, and it works with no manifest, no service worker and no device-quirk risk. But it badges Telegram’s icon, not Alfred’s, and it keeps another app on the Home Screen. That undercuts your goal here, so for comms I would not use it. It stays the better fit for operational alerts, like a failed backup, that need no badge.

Badge only while the app is open

Free and needs no push, but the badge is then a lie whenever Alfred is closed, which is exactly when a Home Screen badge is read. It is still worth shipping as the foreground correction above.

A native iOS app

Fixes every platform limit, at the cost of an Apple developer account, signing and a second codebase for a single-user tool. Not proportionate yet.

Cost & open questions

Effort: moderate: a migration, a Worker module, a route, a manifest, a settings control and a hook, plus one library dependency (the Worker currently carries only the Anthropic SDK and yaml; the encryption is small enough to vendor if that bothers you). Money: none found; Apple’s push service is free to use.

Latency is the part that may disappoint. An email reaches you after the Gmail poll (every 3 minutes), then the next classifier tick (every 2), and the classifier judges six messages a tick, so a burst takes longer. Expect up to roughly 5 minutes, against near-instant for native Mail. iMessage comes through the Mac daemon, about once a minute, and only while the Mac is awake. If you are removing your mail app, ask whether an ASAP email arriving five minutes late is acceptable. If it is not, the fix is upstream, not in the push.

Open questions, in order of how much they decide

  1. Where does app_badge go in the declarative payload, and does 18.4+ honour it? Test on your phone with a hand-sent push.
  2. Can a push lower the badge without showing a notification? If not, clearing a message on desktop leaves the phone stale until you open Alfred.
  3. Does Alfred need classic Web Push as a fallback for iOS before 18.4? Only if your phone is older.
  4. Is ASAP-only the right count, or do you want today to notify too? That is your call, and it sets how loud the phone gets.
  5. Delivery when the Home Screen app has been force-quit, and Focus-mode behaviour. Vendor guides mention reliability reports; I have no first-hand evidence either way.
